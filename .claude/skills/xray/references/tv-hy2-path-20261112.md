# 电视 HY2 路径与恢复（2026-11-12）

适用 X96 上现有 sing-box / SmartTube。设备地址、PID、boot ID 从当次现场取，不照抄本文。
不处理 Netflix 登录、遥控或 DRM。secret、签名 URL、API 密钥不写入技能、记忆或 git。

## 取证

- root 用 `/system/xbin/su`。`/system/bin/su` 链到 Magisk，shell 用户直接执行会 Permission denied。
- 多行命令不要塞进 `adb shell su -c`。脚本 push 到 `/data/local/tmp`，再执行。
- Clash API 的 `now` 可能带空格，响应也不一定是 chunked。只打印线路名。
- 固定探针口：19101 Rack HY2、19102 Rack Reality、19103 ZGO Reality、19104 ZGO HY2、19105 Rack Reality IPv6。这些口不经过 `youtube-video` 选择器。测完删除 `adb forward`。
- Cloudflare 单次 12MiB 会 403。比较吞吐用相同字节数，6MiB 可以用。256KB 探针和空闲 cwnd 不能当视频带宽。
- 解码宽高为 0 时不推定画质。`vdec` 的 frame rate 字段不可信。MediaSession 可以 state=3 而 position 一直是 0；连续帧计数才是进度。一次帧读数不是持续增帧曲线。

## 选择器

守护优先级和 sing-box 默认值不是同一份清单。2026-11-12 现场：守护顺序是 ZGO HY2 → ZGO Reality → Rack HY2 → Rack Reality → Rack Reality IPv6；`youtube-video` 的配置默认值是 `yt-zgo-reality`。

`probe_profile=tiered` 时，视频恢复只在“正在播放”时计数。播放判定包含 SmartTube / YouTube TV 的 resumed Activity，也包含任意一条 chain 里有 `youtube-video` 的连接。官方 YouTube TV 在后台留下连接时，桌面看起来空闲，守护仍会认为视频活跃。

切回更高优先级需要该候选连续 3 次全量成功，并且当前选择已保持 5 分钟。全量探针间隔 300 秒，一次只探一条备用。当前线路健康时，低优先级线路不能立刻挤掉它。只在桌面等 5 分钟，或只播几十秒，都不会完成这次切回。

2026-11-12 10:50 软件重启（boot `aee5c30b`）约 42 秒 DNS ready。本 boot 没有 `selection_verified`，视频选择器一直是 `yt-rack-hy2`，ZGO HY2 探针本身有成功记录。短播公开测试片约 20 秒后 state=3、帧 890、drop 0，googlevideo 走 Rack HY2。宽高为 0，不能称为 4K 验收。包仍是 warmup-v1，系统 DNS 偏好和禁用自动网络错误修复保持。未改生产。软件重启不是断电。

## 吞吐结论

家庭出口到美西约 200ms。Reality 单流约 7.5–10.5Mbps，低于这条 4K60 片源约 17Mbps。HY2 单流更高。同一条 HY2 上多连接没有稳定快过单连接；ZGO 与 Rack 同时等同一批数据时，总有一边在时限内下不完。换播放器不能提高这条隧道。不要把 aria2 一类分段下载直接装进边播路径。

维持单条 ZGO HY2 优先和 10 秒起播缓存。选择器暂时停在健康的 Rack HY2 时，按上面的恢复规则观察，不手工改生产来“催”它切回。
