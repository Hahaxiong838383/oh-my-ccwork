# team — 多重意见圆桌讨论

让 grok 和 codex 两个独立引擎，对你给的东西（代码 / 方案 / 想法 / 问题 / 文档）提供多重独立视角。核心价值：独立错误分布，交叉验证——两家共识的判断置信度高，分歧的地方要认真对待，不要各打五十大板和稀泥。

**不写代码**。这不是委派实现的通道，是"找两个高手一起议一议"。

## cc 的角色：调度者，不是模板执行器

收到需求后：

1. **理解需求**——用户到底想让两家看什么、关心哪个角度(bug？架构？可行性？反方意见？)
2. **现场组织 prompt**——针对这个具体需求写一段专家级 prompt，不要套死模板。原则：
   - 给两家一个贴合任务的专家身份(不是泛泛的"你是专家"，要具体："你是资深XX工程师/架构师/产品顾问")
   - **反讨好**：明确要求"如果不同意/觉得有问题，直接说，不要附和"——否则两家都说"挺好的"，多重视角就废了
   - **逼深度**：要害问题优先，不要罗列一堆正确但无关痛痒的浅层观察
   - **禁正确的废话**：不需要"这个方案总体不错"之类的开场，直接进观点
   - 需要审查代码/方案时，把内容原样附在 prompt 里(不要只给摘要，两家要看到真实内容)
   - 结尾要求按真实身份署名：grok→「署名：grok（xAI）」/ codex→「署名：codex（OpenAI）」
3. **写 prompt 到临时文件**，调用 `bash ~/mycc/.claude/skills/team/dispatch.sh <prompt文件>`
4. **读回两家产出**：`/tmp/team-grok.md` + `/tmp/team-codex.md`
5. **综合汇报**给用户：
   - 两家共识的点→高置信度，直接点出
   - 分歧的点→都摆出来，不要替用户选边，除非有明显证据支持一方
   - 某家失败(脚本会在 stderr 打印失败原因)→如实告知，别假装成功

## 降级链(遇到失败先看这个，不要自己瞎调试)

- grok：`omp xai-oauth/grok-4.3`(本机OAuth) → CPA中转(日本自建，独立网络路径) → `grok-build` CLI(最终兜底)
- codex：网关2→网关3→网关1(各带重试，流式) → `omp openai-codex/gpt-5.4`订阅(最终兜底)
- 若某条 OAuth 兜底报 401：先查 `omp auth-broker list` 有没有 `<provider>-device` 的 headless 变体，device flow 能在非交互 Bash 里安全后台跑（不会像交互式浏览器回调那样崩），验证码/URL 转给用户在浏览器完成即可
- 两条链完整细节 + 设计决策见 memory `project_team_skill_multi_opinion`(改降级链前必读)

## 示例

用户说"用 team 看看这个登录逻辑有没有安全问题" →
1. 读用户指的代码文件
2. 组织 prompt："你是资深安全工程师，审查以下登录逻辑代码是否存在安全漏洞(注入/越权/凭据泄露/会话管理缺陷)。发现问题直接指出严重程度，没发现真问题不要硬凑。[附代码]"
3. 调 dispatch.sh，读回两家意见
4. 汇报："grok 和 codex 都指出 XXX 是真问题(两家共识)；grok 额外提到 YYY，codex 没提(待你自己判断相关性)"
