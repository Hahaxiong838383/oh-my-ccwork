# ProtoPie 运行状态与连接生命周期

用于 Warp 宿主内的 Cloud 轮播、浏览器控制连接、内存增长和重启状态排查。来自 NIO Warp 实测；实现、计数含义和限制须以当次源码重新核对。不要将案例的测试时长或连接上限写成所有项目的默认值。

## 先区分四条链路

| 对象 | 可用证据 | 不能据此推导 |
|---|---|---|
| 单链接播放器 | 当前页面身份、媒体时钟、就绪状态 | 自动轮播已启动 |
| 自动计划 | run ID、状态、item ready、倒计时、切源记录 | 网页已经从头重播 |
| 捕获与输出 | 绑定窗口、源屏、视口/捕获尺寸、帧与可见输出 | 所有键鼠正常、真实玻璃观感正确 |
| 输入所有权 | 当前绑定文档、焦点、接管状态、事件回执 | 播放页正常便必然有输入焦点 |

用户说“卡住”时先对齐时间、PID 和 run ID，查看 UI、页面及帧是否仍变化。计时/切源正常但画面没重新开始，应检查同链接页面是否被复用；不要仅凭观感判死锁或先重启掩盖现场。

## 新计划与预览复用的语义

- 确认启动自动联动是单来源预览还是恢复自动计划。未获需求依据，不把修复状态提示改成自动续播功能。
- 界面显示单链接预览状态与计划状态，时长/进度明确属于哪个对象。保留准备、暂停、完成、失败等可区分状态，不虚构原型自身播放进度。
- 若“开始新计划”要求从头演示，首项即使与已打开链接相同也应进入新文档。只查看已打开来源的“预览所选”可以保留复用；不要为修首项而刷新所有入口。
- 用操作前后 target ID 与文档时间标识（如 `performance.timeOrigin`）确认是否真的重播，随后验证首项就绪、进度递增与完整一次轮换。目标 ID 没变不单独等于未重载；文档标识也需要检查。

## 内存增长需要对象证据

1. 在同 PID、同屏幕/计划条件下记录 App footprint、RSS、系统内存压力/交换和浏览器进程树；把热身峰值与持续斜率分开。
2. 通过有时限的堆摘要或独立最小复现定位对象类型与创建频率。历史 WebSocket task 对象数不能当作当前 TCP 连接数；调用 cancel、任务列表为空，也不能证明对象已经释放。
3. 控制连接按命令频繁创建若被证实是增长来源，优先评估浏览器级持久连接与页面 session。只按页面复用仍可能按换页次数累积，应覆盖页面轮换。
4. 对照实验明确是真实 App/Chrome，还是生产网络层加模拟服务。不同阶段的断言数或内存增量不得拼成同一场长稳结果。

## 复用不能破坏页面和输入归属

- 连接、页面 session、请求 ID、操作代次各有明确所有者，过期回包不能改变新来源。
- 取消/超时/断线及时结束在途等待并回收会话，队列和重连有边界。结果未知的点击、按键、导航等动作不要盲目自动重发。
- 准备新页时保留旧的有效画面、就绪后切换可以是合理策略；失败/取消必须回收候选页，成功后回收旧自有页。验证就绪后仅剩预期页，不全杀 Chrome 或关闭用户其他标签。
- 准备期短暂双页与长期遗留多页要分开记录；看到就绪后单页不能承诺交接期声音从不重叠。
- 输入桥与控制连接可能相互独立。保留焦点、松键、Esc、AA 边缘及光标恢复机制，验收范围按实际事件记录。
- 保留可明确切换的旧控制机制和源码/App/最新参数配对回滚；说明降级模式仍可能保留原问题。不能只备份旧二进制便忽略现场新调值。

## 冷启动连接计数

先查计数在握手前还是成功后递增。保存的 DevTools endpoint 可能过期，Chrome 刚启动也可能尚未监听。累计连接/断开数要结合 boot time、App/Chrome 启动时间、错误时点与类型、后续快照增量解释。

若系统日志显示失败均在启动期，后续请求成功增长、连接计数不变、捕获健康，可以确认已恢复；没有逐次证据时只能说“当前正常，历史原因待定”。同时确认冷启动失败是否消耗总重连预算，不把无限探测或无限重启当修复。

## 验收与运维范围

- 按用户指定时长执行；若缩短测试，停止原采样任务并记录窗口和剩余限制。10 分钟结果不能外推全天。
- 人工每日开关机和无人值守需求不同。自动重启、续播、输入脚本是独立产品行为，不因看到内存增长就自动加入。
- 正常重开、物理重启、合盖/换屏分别记录。`/tmp` 工具可能在重启后消失；工具不存在不是 App 故障，恢复探针前核对其源码、读写能力和目标归属。
- AX 操作可能已触发界面重建，却返回失效元素错误。先核对选择值、页面身份和日志等后置状态，再判断是否重试；不要重复发送结果尚不明确的点击。
- 验证诊断文件可重新解析、来源/安装指纹一致；不要以脚本退出码或“已写入”日志替代实际内容校验。
