# plan-ceo — CEO 视角审查

> 灵感来源：gstack-plan-ceo-review（Garry Tan / YC）
> 工程视角问"怎么做"，CEO 视角问"值不值得做、做多大"。

## 核心问题

工程师问：**这个计划可行吗？**
CEO 问：**这件事值得全力投入吗？范围够大吗？10 分里能得几分？**

## 四种审查模式

| 模式 | 使用场景 |
|------|---------|
| **范围扩展** | 感觉做的事情太小，有没有更大的机会？ |
| **选择扩展** | 当前方案只考虑了一种路径，有没有其他选法？ |
| **保持范围** | 现有范围合理，但需要确保每个部分都做到位 |
| **范围缩减** | 当前计划太大，MVP 是什么？什么可以砍？ |

## 执行流程

### Step 1：理解当前计划

阅读或让老板描述当前的工程/产品计划，理解：
- 要做什么
- 目标用户是谁
- 成功标准是什么
- 预计范围

### Step 2：CEO 三连问

对每个计划，问这三个问题：

**1. 前提挑战**
> "这个计划背后的核心假设是什么？如果这个假设错了，整个计划还值得做吗？"

**2. 机会大小**
> "如果这件事做对了，最大的可能是什么？是一个小功能，还是可以成为核心竞争力？"

**3. 完整性检查**
> "如果一个你非常在乎的用户用这个产品，他们会给几分（满分10分）？4分和10分之间的差距在哪里？"

### Step 3：生成挑战清单

基于分析，生成一份挑战清单：

```
## CEO 挑战清单

### 前提挑战
- [假设 A]：[如果这个假设错了，会怎样？]
- [假设 B]：[...]

### 范围机会
- [当前范围]：[可以扩展到的更大机会]
- [替代路径]：[没有考虑过的方向]

### 完整性缺口
- [缺少的功能/体验 1]
- [缺少的功能/体验 2]

### 建议
[明确建议：保持/扩展/缩减，以及理由]
```

### Step 4：给出明确立场

不含糊，给出一个明确建议：

| 建议 | 含义 |
|------|------|
| 全力做，但要更大 | 范围扩展，值得投入 |
| 全力做，当前范围合理 | 聚焦执行，不要分心 |
| 先验证再全力做 | 核心假设太脆弱，先做最小测试 |
| 重新定义再做 | 方向对，但切入点需要调整 |
| 暂缓，不是最高优先级 | 有更重要的事要先做 |

## 10 星产品检查

gstack 的核心理念：如果用的人喜欢，就会给 10 星；如果给不到 10 星，就还没做完。

检查清单：
- [ ] 核心用户流程是否顺滑？
- [ ] 是否解决了真实的痛点？
- [ ] 用户第一次用的时候是否能理解？
- [ ] 是否有"wow moment"？
- [ ] 是否有让用户反复来用的理由？

## 错误与救援登记册

对于高风险决策，生成一个"如果这样会怎样"的清单：

```
## 故障模式分析

| 场景 | 概率 | 影响 | 救援方案 |
|------|------|------|---------|
| [假设 A 是错的] | 高/中/低 | 高/中/低 | [怎么调整] |
| [竞争对手做了类似的事] | ... | ... | ... |
| [用户不买账] | ... | ... | ... |
```

## 使用时机

| 时机 | 说明 |
|------|------|
| 工程规划完成后 | 在开始写代码前，做一次 CEO 视角审查 |
| 感觉做的东西太小 | 主动触发，问"有没有更大的机会" |
| 项目中途方向迷茫 | 重新校准，确认这件事还值得继续做 |
| 发布前 | 检查是否真的做到了 10 星 |
