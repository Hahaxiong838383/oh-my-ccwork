# 决策记录

> 决策记录是给**未来 agent** 看的上下文恢复文档。
> 不是给人看的流水账，是 agent 做回溯分析的数据源。

## 触发词

- "/decision"、"记录决策"、"写决策记录"

## 核心原则

1. **"放弃了什么"比"选了什么"更重要** — 选了什么看代码就知道，放弃了什么只有决策记录里有
2. **记"什么条件下该翻"** — 约束条件变了，决策可能就该翻了
3. **从对话上下文自动提取** — agent 写草稿，人扫一眼确认，不增加额外负担
4. **兼容现有格式** — 追加到项目的 `04-决策记录.md` 末尾

---

## 决策类型

| 类型 | 代号 | 典型场景 |
|------|------|---------|
| Bug 修复 | `fix` | 发现 bug → 排查 → 定位根因 → 修复 |
| 架构变更 | `arch` | 重构、模块拆分、技术栈迁移 |
| API/接口变更 | `api` | 接口设计、协议变更、数据格式调整 |
| 配置/运维 | `config` | 服务器配置、部署方式、环境变量 |
| 产品设计 | `design` | UI/UX 决策、功能取舍、交互模式 |
| cc 自闭环 | `auto` | cc 自主决策闭环：发散→选方案→执行→验证→迭代（P40） |

## 执行流程

### Step 1: 确定项目

从当前对话上下文判断属于哪个项目。如果不明确，问一句：

> 这条决策记录归到哪个项目？

然后定位到 `2-Projects/P{XX}-xxx/04-决策记录.md`。

### Step 2: 从对话上下文提取信息

回顾当前对话（以及可能的 compacted summary），提取以下信息。**不需要人手动提供**，agent 自己提取，提取不到的标「待补充」。

### Step 3: 按模板生成草稿

用下面的模板生成决策记录草稿，展示给人确认。

### Step 4: 直接追加

cc 自主追加到 `04-决策记录.md` 末尾（在 `*最后更新*` 行之前），**不等人确认**。同时更新最后更新日期。

- auto 类型：标题用 `[auto-{序号}]` 前缀

## 决策记录模板

```markdown
## [标题]（[日期]）

<!-- type: fix | arch | api | config | design -->
<!-- status: 生效中 | 已替代 by [标题] | 待实施 -->
<!-- scope: 前端 | 后端 | Worker | 服务器 | 全栈 -->
<!-- files: file1.ts, file2.ts -->
<!-- related: [关联决策标题1], [关联决策标题2] -->

### 现象

[用户/系统遇到了什么问题？怎么发现的？]

### 排查过程

[怎么定位到根因的？查了什么日志、读了什么代码？]
[这段对未来 agent 遇到类似问题时有诊断参考价值]

### 根因

[一句话说清楚为什么会出这个问题]

### 候选方案

| 方案 | 做法 | 优点 | 缺点/风险 |
|------|------|------|----------|
| A. [名称] | [描述] | [优点] | [缺点] |
| B. [名称] | [描述] | [优点] | [缺点] |
| C. [名称] | [描述] | [优点] | [缺点] |

### 决策

**选择**：[方案 X] — [名称]

**理由**：[为什么选这个，核心判断依据]

**放弃的方案**：
- [方案 Y]：[为什么放弃，什么条件下可以重新考虑]
- [方案 Z]：[为什么放弃]

### 改动

[改了哪些文件，每个文件改了什么]

### 验证

[怎么验证的？测试结果？]

### 什么条件下该翻这个决策

[列出当时的约束条件。这些条件变了，就该重新评估]
- [约束 1]
- [约束 2]

### 教训

[踩了什么坑？以后怎么避免？]
```

## 字段必要性

| 字段 | 必须 | 说明 |
|------|------|------|
| 标题 + 日期 | 必须 | |
| HTML 注释 header | 必须 | type/status/scope/files/related |
| 现象 | 必须 | 没有现象就没有决策 |
| 排查过程 | 可选 | fix 类型建议写，design 类型可跳过 |
| 根因 | 必须 | 不写根因的修复是瞎改 |
| 候选方案 | 必须 | **这是决策记录最核心的部分** |
| 决策 + 理由 | 必须 | |
| 放弃的方案 | 必须 | **比"选了什么"更重要** |
| 改动 | 建议 | 方便代码考古 |
| 验证 | 建议 | |
| 什么条件下该翻 | 必须 | **决策的保质期标签** |
| 教训 | 可选 | 有就写，没有不硬凑 |

## 按类型裁剪

不同类型的决策，侧重不同字段：

| 类型 | 重点字段 | 可精简字段 |
|------|---------|----------|
| `fix` | 排查过程、根因、教训 | 候选方案（如果修法明显只有一种） |
| `arch` | 候选方案、放弃理由、翻转条件 | 排查过程 |
| `api` | 候选方案、改动、向后兼容 | 排查过程 |
| `config` | 现象、改动、教训 | 候选方案（如果选项少） |
| `design` | 候选方案、用户视角、放弃理由 | 排查过程、根因 |
| `auto` | 候选方案、决策理由、执行结果、迭代记录、复盘标签 | 排查过程、根因、改动 |

## HTML 注释 header 说明

用 HTML 注释写在标题下方，人读 Markdown 时不碍眼，agent 用正则/字符串搜索可以提取：

```markdown
<!-- type: arch -->
<!-- status: 生效中 -->
<!-- scope: 后端 -->
<!-- files: adapters/official.ts, http-server.ts, index.ts -->
<!-- related: v2 Session API 改造 -->
```

**status 流转**：
- `待实施` → `生效中` → `已替代 by [新决策标题]`
- 被替代时，在旧决策上加一行 `<!-- superseded: true -->`

**未来 agent 搜索方式**：
- 按类型：`grep "<!-- type: fix -->" 04-决策记录.md`
- 按状态：`grep "<!-- status: 生效中 -->" 04-决策记录.md`
- 按文件：`grep "official.ts" 04-决策记录.md`

## auto 类型（cc 自闭环决策）

auto 类型是 cc 自主决策闭环时的记录格式（P40 cc大脑训练）。与其他类型的区别：

1. **不等人确认**：cc 自主追加
2. **标题前缀**：`[auto-{序号}]`
3. **额外字段**：执行结果、迭代记录、复盘标签

**auto 模板**：

```markdown
## [auto-{序号}] {标题}（{日期}）

<!-- type: auto -->
<!-- status: 生效中 -->
<!-- scope: {范围} -->
<!-- risk: 🟢/🟡 -->

### 现象

[为什么要做这个决策/行动]

### 候选方案

| 方案 | 做法 | 优点 | 缺点/风险 |
|------|------|------|----------|
| A. [名称] | [描述] | [优点] | [缺点] |
| B. [名称] | [描述] | [优点] | [缺点] |

### 决策

**选择**：[方案 X]
**理由**：[核心判断依据]
**放弃的方案**：[方案 Y]：[为什么放弃]

### 执行结果

[成功/失败/部分成功，具体描述]

### 迭代记录

（如有多轮迭代）
- Round 1: [做了什么] → [结果] → [判断]
- Round 2: [调整] → [结果]

### 复盘标签

`#可复用` / `#待优化` / `#踩坑`
```

**与标准模板的差异**：
- 省略：排查过程、根因、改动、什么条件下该翻
- 新增：执行结果、迭代记录、复盘标签、risk（风险等级）
