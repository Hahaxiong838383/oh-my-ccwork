# 升级与恢复

操作前读home-lan的 `4-Assets/Code/fnmedia-ext-hardening/README.md`、`BUILD-MANIFEST.json` 与 `maintenance/README.md`。本文件解释容易误判的环节，不复制临时sudo/helper命令。

## 更新有三条不同路径

| 路径 | 执行位置与判断 |
|---|---|
| 插件版本 | 管理页向NAS队列提交请求，home-studio用户级维护timer消费；HTTP工作进程不下载执行代码。上游仅文档/版本变化可走受审自动构建，核心源码/依赖变动标needs_review，适配加固后发包 |
| 官方影视升级后的复连 | 独立监督器核真实监听进程、exe/摘要与公开协议；未知版本通过检查后仅probation试运行，后续异常恢复官方入口。不能承诺任意未来版本完全兼容 |
| 影片内容 | NAS内刷新热榜和海量库分类/首页、失败保留旧内容及退避；深页按需读取。home-studio离线不等于内容不再刷新 |

维护单元active不足以证明更新生效：核真实heartbeat、request_id消费、已安装版本、可信树、last-good和错误状态。`needs_review`不是更新关闭；报告本地版本与上游待适配版本，避免误读为安装失败。对失败安装保留状态，停止重复重装。

## 准备可审核的部署

1. 核本次用户授权、正在播放的会话和操作窗口。先完成源码审查、构建、测试、包校验与恢复准备；只有已有授权未覆盖的生产动作才询问，不要求用户重批已授权动作。
2. 记录当前官方程序/manifest/nginx三个摘要、进程和socket归属；持久状态做私有备份。比较升级回调停服时的一致备份，避免把播放期间合法历史变化判成损坏。
3. 从已提交的 `git archive` 干净导出构建，不把worktree的 `.git` 文件、state、凭据、tests混进FPK。固定上游提交、补丁摘要、fnpack及离线wheel，补丁重建后逐文件核对源码。
4. 用当前正式App Center更新通道，核 `canUpgrade`、本地包与NAS回读SHA。升级只动独立插件；不要修改官方二进制/nginx/数据库，或用卸载重装代替更新。

`trim-cli 0.1.1` 的已知本地FPK缺口由维护仓 `local_upgrade.py` 适配：复用CLI OAuth、短时loopback代理、固定NAS和插件路径，`packageType=path`，允许固定NAS的官方refresh转发。不要导出/解密session或把token搬到NAS；后续CLI可能修复，先检查实装版本，不盲目套旧适配器。

## 验收与恢复

- 回读App Center版本/服务、实际载荷摘要、官方三文件摘要、socket的真实监听者及健康正文 `ok=true`，不能只有HTTP200。按任务核用户配置/历史/收藏、匿名管理/媒体拒绝、真实登录正例或明确缺失层次。
- NAS隔离进程使用已安装模块+真实源的完整正文/缓存/资源回收，是服务端证据；不能标为官方登录播放器E2E。重新部署后旧验收不自动继承。
- 提前准备包级恢复：fnOS可能拒绝降级，可将已知良好旧代码仅提升为更高版本、校验载荷/包摘要，并预存NAS。版本号须高于本次将安装的目标包，载荷与持久数据格式须适合本次恢复；历史恢复包不能自动沿用。维护器现有“失败尝试旧FPK”是尽力恢复路径，不能作为唯一保障；已确认某版本组合拒绝降级时，不重复同一安装尝试。准备/上传/预检都不等于已安装恢复或恢复演练通过。恢复后的可信树、last-good、维护状态也需核实。
- 优化开关可用于退回旧媒体路径，实际生效仍须验证；不能把关开关当作包级恢复已完成。停用/异常恢复使用插件可信源码树中的 `proxy/recover.py` 或 `deploy/uninstall.sh --stop-only` 既有机制（维护补丁目录本身不含这两个独立文件），最后核socket归属，不手删官方socket。
- 部署成功后恢复原维护timer状态，核已装版本、可信树、last-good与心跳。发布快照从home-lan提交blob取字节，逐文件SHA记录来源；备份、安装包、OAuth和原始媒体请求不入Git。

历史样本：2026-10-31的0.2.19.4是0.2.19.2旧代码的递增恢复包，未安装，不能当最新功能版。实际版本、包路径和校验值查最新实施报告与构建锁。
