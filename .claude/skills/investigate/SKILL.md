# investigate — 根因分析框架

> 灵感来源：gstack-investigate（Garry Tan / YC）
> 适配 cc 使用习惯，中文优先。

## 铁律

**禁止在找到根本原因之前开始修复代码。**

看到"症状"就改代码 = 医生不做检查就动手术。症状消失 ≠ 问题解决，只是把 bug 推到了更深处。

## 四阶段执行流程

### Phase 1：根因调查（不碰代码）

1. **读错误信息**：完整读取堆栈、日志、控制台输出
2. **定位来源**：错误在哪个文件、哪一行触发？
3. **读上下文**：读相关代码（前后50行），理解意图
4. **问问题**：
   - 这段代码在什么条件下能正常工作？
   - 是什么改变了？（最近的 git commit 是什么？）
   - 用户操作了什么触发了这个？

### Phase 2：模式分析

1. **复现路径**：能稳定复现吗？触发条件是什么？
2. **影响范围**：这个 bug 影响哪些功能？有多少用户路径受影响？
3. **根因分类**：
   | 类型 | 特征 |
   |------|------|
   | 逻辑错误 | 代码意图正确，但边界条件没处理 |
   | 竞态条件 | 异步/并发场景下的顺序问题 |
   | 数据问题 | 输入数据格式/内容与预期不符 |
   | 依赖问题 | 外部服务/库的行为变化 |
   | 配置问题 | 环境变量、配置项缺失或错误 |
   | 状态问题 | 全局状态/缓存/session 异常 |
   | 静默成功 | "没反应"且无报错 → 请求其实 200 成功，但返回了被前端忽略的状态字段（`deduplicated`/`skipped`/`already_exists`/`noop`），或成功路径压根没给用户反馈。**"没反应"≠ 失败，优先怀疑"静默成功"**：先看 Network 真实响应体，再看前端是否消费了所有有意义的字段 |

### 延迟问题必须拆层

“转圈很久”不能直接归类为网络故障。至少拆成以下四段，并为每段记录时间：

| 层级 | 证明方式 | 常见根因 |
|------|----------|----------|
| 控制面 | RPC 请求/响应耗时、队列等待 | 历史数据过大、共享队列阻塞、客户端回调超时 |
| Provider 到站 | DNS/TCP/TLS、HTTP 状态、首个 SSE event | 代理、网关、上游首包慢 |
| 任务生命周期 | `inProgress` / `completed` / `failed` | 用户把流式 reasoning 当成最终完成，或 UI 未正确收尾 |
| 执行负载 | 模型轮次、上下文 token、工具耗时 | 高推理、长上下文、多轮工具、长命令 |

只有控制面或 Provider 到站异常时才改网络/服务；控制面毫秒级、Provider 已 `200` 且 Turn 仍 `inProgress` 时，应继续观察任务或降低推理/新建短线程，禁止用重启掩盖正常执行。

### Phase 3：假设验证

1. **写出假设**：基于 Phase 1-2，写出至少一个具体假设
   - 格式：我认为根因是 [X]，因为 [证据]
2. **设计验证**：如何证明/证伪这个假设？
   - 添加日志/断点
   - 构造最小复现用例
   - 对比正常/异常两种状态
3. **执行验证**：运行验证步骤，记录结果

### Phase 4：实现验证

1. **确认根因**：假设被证实了吗？用具体代码行/日志作为证据
2. **设计修复**：修复最小改动是什么？有没有副作用？
3. **修复 & 测试**：
   - 修复代码
   - 写一个能复现原 bug 的测试（防止回归）
   - 验证修复有效

## 输出格式

调试完成后输出：

**症状**：[用户描述的问题，一句话]

**根因**：[一句话说清楚为什么会出这个问题]
证据：[具体代码行 / 日志片段]

**排查过程**：
1. [观察到了什么]
2. [检查了哪里]
3. [怎么验证假设的]

**修复方案**：[改了什么，为什么这样改]

**防回归**：[写了什么测试，或者应该写什么测试]

**后续风险**：[还有没有类似的地方可能出同样的问题？]

## 实战技巧：前端「没反应」类 bug 的浏览器内端到端验证

验证前端修复（尤其文件上传、表单提交这类"靠交互触发"的路径）时，preview/自动化工具通常**没法直接传本机文件**。可在页面上下文里造真实交互：

```js
// preview_eval 里执行：从后端已有数据 download 端点取内容 → 造 File → 塞进隐藏 input → 派发 change
const blob = await (await fetch(`/api/banks/${ver}/download/source`)).blob();
const file = new File([blob], 'x.csv', { type: 'text/csv' });
const input = document.querySelector('input[type=file]');
const dt = new DataTransfer(); dt.items.add(file);
input.files = dt.files;
input.dispatchEvent(new Event('change', { bubbles: true }));  // 触发真实 React onChange → 真实上传
```

- 改一个字节（如末尾加 `\n`）即可让内容 hash 变化，验证"新建成功"分支；原样重传验证"去重/重复"分支——一份数据测两条路径。
- **Claude_Preview MCP 在 monorepo 里会跑自己的 `/tmp/narrative_preview` 静态服务、无视 `launch.json`**：绕过法 = 自己 `npm run dev` 起 vite，再用 `preview_eval` 把 `window.location` 跨源导航到本机 vite 端口，后续 eval/snapshot 都在真页面里跑。
- 验证后查 `preview_console_logs(level=error)` 确认零报错，再看 DOM 文本（比截图更权威，截图视口可能异常窄）。

## 反模式（禁止）

- 看到错误信息直接改代码，没有找到根因
- 用 try/catch 吞掉错误，假装问题不存在
- 改完代码说"应该好了"，没有验证
- 只改症状，没有检查是否有其他地方有同样的问题
- 修复后没有写防回归测试
