# investigate — 根因分析框架

> 灵感来源：gstack-investigate（Garry Tan / YC）
> 适配 cc 使用习惯，中文优先。

## 铁律

**禁止在找到根本原因之前开始修复代码。**

看到"症状"就改代码 = 医生不做检查就动手术。症状消失 ≠ 问题解决，只是把 bug 推到了更深处。

---

## 触发词

- `/investigate`、`/debug`
- "帮我调试"、"为什么报错"、"根因分析"

## 四阶段执行流程

### Phase 1：根因调查（不碰代码）

1. **读错误信息**：完整读取堆栈、日志、控制台输出
2. **定位来源**：错误在哪个文件、哪一行触发？
3. **读上下文**：读相关代码（前后50行），理解意图
4. **问问题**：
   - 这段代码在什么条件下能正常工作？
   - 是什么改变了？（最近的 git commit 是什么？）
   - 用户操作了什么触发了这个？

### Phase 2：模式分析

1. **复现路径**：能稳定复现吗？触发条件是什么？
2. **影响范围**：这个 bug 影响哪些功能？有多少用户路径受影响？
3. **根因分类**：
   | 类型 | 特征 |
   |------|------|
   | 逻辑错误 | 代码意图正确，但边界条件没处理 |
   | 竞态条件 | 异步/并发场景下的顺序问题 |
   | 数据问题 | 输入数据格式/内容与预期不符 |
   | 依赖问题 | 外部服务/库的行为变化 |
   | 配置问题 | 环境变量、配置项缺失或错误 |
   | 状态问题 | 全局状态/缓存/session 异常 |

### Phase 3：假设验证

1. **写出假设**：基于 Phase 1-2，写出至少一个具体假设
   - 格式：我认为根因是 [X]，因为 [证据]
2. **设计验证**：如何证明/证伪这个假设？
   - 添加日志/断点
   - 构造最小复现用例
   - 对比正常/异常两种状态
3. **执行验证**：运行验证步骤，记录结果

### Phase 4：实现验证

1. **确认根因**：假设被证实了吗？用具体代码行/日志作为证据
2. **设计修复**：修复最小改动是什么？有没有副作用？
3. **修复 & 测试**：
   - 修复代码
   - 写一个能复现原 bug 的测试（防止回归）
   - 验证修复有效

---

## 输出格式

调试完成后输出：

**症状**：[用户描述的问题，一句话]

**根因**：[一句话说清楚为什么会出这个问题]
证据：[具体代码行 / 日志片段]

**排查过程**：
1. [观察到了什么]
2. [检查了哪里]
3. [怎么验证假设的]

**修复方案**：[改了什么，为什么这样改]

**防回归**：[写了什么测试，或者应该写什么测试]

**后续风险**：[还有没有类似的地方可能出同样的问题？]

---

## 反模式（禁止）

- 看到错误信息直接改代码，没有找到根因
- 用 try/catch 吞掉错误，假装问题不存在
- 改完代码说"应该好了"，没有验证
- 只改症状，没有检查是否有其他地方有同样的问题
- 修复后没有写防回归测试
