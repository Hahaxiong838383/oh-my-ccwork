# brain-review — 纲领对齐自检

> 在对 mycc-brain 进行重大改动前，基于 MANIFESTO.md 进行系统自检，确保改动方向与纲领一致。

## 触发时机

- brain 新功能开发前
- brain 架构变更前
- brain 自进化系统调整前
- 用户主动要求 `/brain-review`

## 执行流程

### Phase 1: 加载纲领上下文

依次读取以下文件，构建完整决策上下文：

```
必读（纲领层）：
1. 2-Projects/brain-product/MANIFESTO.md           — 项目最高指导原则
2. 3-Thinking/07-自主进化动机系统方法论.md           — 四项目分析的理论基础

必读（工程层）：
3. 2-Projects/brain-product/mycc-brain/CLAUDE.md    — 版本管理、部署规范
4. 2-Projects/brain-product/mycc-brain/package.json — 当前版本号

按需读取（如果涉及对应模块）：
5. 2-Projects/brain-product/BRAIN-MEMORY-BLUEPRINT.md — 记忆系统蓝图
6. 2-Projects/brain-product/mycc-brain/src/config.ts  — 配置结构
7. 最新的 HANDOFF-*.md                                — 最近阶段交接
```

### Phase 2: 七维自检

对照 MANIFESTO.md 的核心原则，逐维度检查当前状态：

#### 维度 1: L0 宪法合规

```
检查项：
□ 本次改动是否触及 L0 边界文件（MANIFESTO.md、SOUL.md）？
□ 如果触及，是否有运行时门控机制防止意外修改？
□ 身份内核是否有漂移风险？（长 session 场景）
□ 审计日志是否覆盖 L0 相关操作？

状态：[通过/风险/缺失]
建议：[如有风险，给出具体修复方案]
```

#### 维度 2: 适应度对齐

```
检查项：
□ steering_tax 指标是否已实现？当前采集状态？
□ trust_score 是否有量化机制？当前值？
□ 本次改动预期对 fitness 公式的影响？
  fitness = value_created × trust_score / steering_tax
□ 改动后 fitness_delta 是否 > 0？

状态：[通过/风险/缺失]
建议：[如 fitness_delta 可能为负，需要说明理由或调整方案]
```

#### 维度 3: 三层进化一致性

```
检查项：
□ 本次改动属于哪一层？（规则层/配置层/模型层）
□ 是否遵循"三层递进，不跳级"原则？
□ 规则层是否稳定？（如果不稳定，不应触碰配置层/模型层）
□ Skill 生命周期（创建→使用→老化→修补/淘汰）是否完整？

状态：[通过/风险/缺失]
建议：[如跳级，需要说明为什么当前情况是例外]
```

#### 维度 4: 安全与治理

```
检查项：
□ 风险分类是否覆盖本次改动？（low/medium/high/critical）
□ 累积风险评分是否会超过日限（100 分）？
□ 否决螺旋检测是否接入？
□ 不可变审计日志是否记录本次改动？
□ 验证引擎三防（防验证逃避、防早停、防静默吞错）是否就绪？

状态：[通过/风险/缺失]
建议：[标注本次改动的风险等级和预估分值]
```

#### 维度 5: 双模运行影响

```
检查项：
□ 本次改动影响在线模式还是离线模式？还是两者？
□ 在线模式：请求处理管道的哪个步骤受影响？
□ 离线模式：数据整理/模式挖掘/进化执行/分辨率推进，哪个阶段？
□ 轨迹记录（成功/失败双流）是否保持完整？

状态：[通过/风险/缺失]
建议：[如影响在线模式，需要评估延迟影响]
```

#### 维度 6: 用户建模影响

```
检查项：
□ 本次改动是否影响用户建模能力？
□ peer_card 数据结构是否需要变更？
□ steering_tax 采集是否受影响？
□ 辩证推理管道是否保持完整？

状态：[通过/风险/缺失]
建议：[如影响用户建模，需要数据迁移方案]
```

#### 维度 7: 决策原则排序

```
对照 MANIFESTO 第十节的 7 条决策原则，逐条审视本次改动：

1. 安全 > 能力          — 本次改动是否引入安全风险？
2. 可观测 > 可自主      — 改动后是否能观测到变化效果？
3. 可回滚 > 可优化      — 改动是否可逆？回滚方案？
4. steering_tax↓ > 功能↑ — 改动是否降低用户纠正频率？
5. 失败经验 ≥ 成功经验  — 失败轨迹是否被保留？
6. 实时沉淀 > 批量整理  — 信息是否在产生时即记录？
7. 三层递进，不跳级     — 是否尊重进化速度梯度？

违反项：[列出违反的原则编号和原因]
豁免理由：[如果有正当理由违反某条原则，说明]
```

## 优化建议

按优先级排序，每条建议包含：

## 注意事项

- 这个 skill 是**只读审查**，不修改任何代码
- 如果发现 MANIFESTO.md 需要更新（比如路线图 checkbox），提示用户确认后再修改
- 自检报告的 fitness_delta 是预估值，实施后需要实际验证
- 对于 NO GO 结论，必须明确说明阻塞原因和解决方案
