# retro — 工程复盘

> 灵感来源：gstack-retro（Garry Tan / YC）
> 复盘不是批评，是校准。

## 定位

定期回顾工程工作，发现规律、优化节奏、沉淀经验。

不是：写工作报告、汇报给上级。
是：给自己和 cc 看的，让下一周比这周更聪明。

---

- `/retro`

- "工程回顾"、"周复盘"、"月复盘"

| 参数 | 含义 | 示例 |
|------|------|------|

| `30d` | 最近一个月 | `/retro 30d` |

## 执行流程

### Step 1：获取 git 数据

```bash
# 获取指定时间窗口的提交记录
git log --since="7 days ago" --oneline --stat --author="$(git config user.name)"

# 获取修改文件统计
git log --since="7 days ago" --pretty=format:"%H" | xargs -I{} git diff-tree --no-commit-id -r {} --name-only | sort | uniq -c | sort -rn | head -20

# 获取每天提交数量
git log --since="7 days ago" --pretty=format:"%ad" --date=short | sort | uniq -c
```

### Step 2：分析维度

**工作节奏分析**
- 活跃天数（工作日 vs 周末）
- 每日提交密度（高强度 vs 稳定节奏）
- 最高产的时间段（早晨/下午/深夜？）
- 连续工作 vs 间隔工作

**工作内容分析**
- 提交类型分布（feat/fix/refactor/docs...）
- 最频繁改动的文件（热点文件）
- 新增 vs 删除代码量比例

**质量信号**
- fix 类提交的密度（越高可能意味着越多 bug）
- 同一文件多次修复（可能是设计问题）
- 回滚/revert 次数
- 提交信息质量（描述清晰 vs 模糊）

### Step 3：提炼亮点和改进点

**亮点**（值得继续的）
- 这期间完成了哪些有价值的事情？
- 有没有特别聪明的技术决策？
- 节奏感怎么样？

**改进点**（下一步可以优化的）
- 有没有反复修复同一个地方的迹象？
- 有没有某天工作量特别不均匀？
- 文档/测试提交的比例够吗？

## 输出格式

```
## 工程复盘 [时间范围]

### 工作概览
- 活跃天数：X 天（共 Y 天）
- 总提交数：N 次
- 净代码量：+X 行，-Y 行
- 涉及文件：N 个

### 提交类型分布
feat: X%  fix: X%  refactor: X%  docs: X%  其他: X%

### 热点文件（修改最频繁）
1. [文件路径] — X 次
2. [文件路径] — X 次
3. [文件路径] — X 次

### 工作节奏
[描述工作节奏，几点比较活跃，哪天特别高产]

### 亮点
- [完成了什么有价值的事]
- [什么决策做得好]
- [什么代码写得优雅]

### 改进建议
- [什么地方可以做得更好]
- [有没有需要补测试/文档的地方]
- [下一步最值得关注的风险]

### 下周焦点
[根据分析，建议下周优先关注什么]
```

## 高级：模式识别

如果有足够的历史数据（多次 retro），可以发现长期规律：

- **工作节奏偏移**：节奏是在变规律还是变混乱？
- **技术债趋势**：fix 类提交占比是否在上升？
- **重构效果**：重构后同区域的 bug 修复是否减少？
- **文件热度图**：哪些文件一直是修改热点，可能需要重新设计？
