# rule-compress — 万能公式 v1 规则压缩引擎

> 方法论来源：飞书万能语法修正版2（GbUKwTTWFiIL0JkYL0HcXnNqnog）
> 首次实战：2026-04-28 CLAUDE.md 压缩（307→165 行，-46%，0 信息损失）
> 配套规范：`mycc/docs/rules/SCHEMA.md`

把任何"散文式规则集合"无损压缩为"4 维优先级矩阵 + 索引下沉"结构。

## 参数

| 参数 | 说明 | 默认值 |
|------|------|--------|
| `<target>` | 目标文件路径（必填） | — |
| `--dry-run` | 只输出分析报告，不写文件 | false |
| `--sink-dir <path>` | 子文件下沉目录 | `docs/rules/` |
| `--schema <path>` | SCHEMA 规范文件路径 | `docs/rules/SCHEMA.md` |
| `--backup` | 压缩前自动备份 `.bak.<date>` | true |
| `--verify` | 压缩后跑验证 | true |
| `--cross-engine` | 检查 codex/gemini 跨引擎兼容性 | false |

## 核心方法论：4 维优先级矩阵

每条规则打 4 个分，决定它在压缩后放哪一层：

| 维度 | 取值 | 含义 |
|------|------|------|
| **是否常用** | 必需 / 常用 / 可选 | 实际触发频率 |
| **是否必选** | 必选 / 可选 | 缺了规则还成立吗 |
| **优先级** | P0 / P1 / P2 / P3 | 抽取/加载顺序 |
| **权重** | 0.35 / 0.60 / 0.75 / 0.85 / 1.00 | 连续值打分 |

### P 分级规则

| 级别 | 权重 | 压缩后位置 | 判定标准 |
|------|------|-----------|---------|
| **P0** | 1.00 | 主文件**全文保留** | 每次对话都生效，缺了就偏 |
| **P1** | 0.75-0.85 | 主文件**压成表格行** + 子文件详情 | 条件触发，高频 |
| **P2** | 0.60 | 主文件**仅索引行** + 子文件详情 | 特定场景才相关 |
| **P3** | 0.35 | 主文件**仅索引行** + 子文件详情 | 极少触发 / 一次性 |

## 执行流程

### Phase 0：前置确认

1. 读目标文件，统计基线：行数 / 字符数 / 标题数 / 规则条数
2. 检查 SCHEMA 文件是否存在（`--schema` 路径）
3. 检查下沉目录是否存在（`--sink-dir` 路径）
4. 如果 `--dry-run`，跳到 Phase 1 只输出分析，不执行 Phase 2-5

**输出**：
```
[rule-compress] 目标：<file> | 基线：<N> 行 / <M> 字符 / <K> 条规则
[rule-compress] SCHEMA：<存在|不存在> | 下沉目录：<存在|不存在>
```

### Phase 1：规则盘点 + 4 维打分

逐条扫描目标文件中的规则（标题/列表/表格都算"一条"），输出打分表：

```markdown
| # | 规则名 | 是否常用 | 是否必选 | P 级 | 权重 | 当前行数 | 压缩后位置 |
|---|--------|---------|---------|------|------|---------|-----------|
| 1 | 中文回复 | 必需 | 必选 | P0 | 1.00 | 5 | 主文件全文 |
| 2 | HANDOFF | 常用 | 可选 | P1 | 0.85 | 15 | 主文件表行+子文件 |
| ... | ... | ... | ... | ... | ... | ... | ... |
```

**打分依据**（不靠拍脑袋）：
- 是否常用：看规则的触发条件频率（每次 session / 每天 / 每周 / 很少）
- 是否必选：假设删掉这条，cc 核心行为是否崩坏
- P 级：综合以上两维 + 历史使用数据
- 权重：P 级对应的默认权重，特殊情况可微调

**等待老板确认打分表后，才进 Phase 2。**

### Phase 2：备份 + 压缩

1. **备份**（`--backup` 开启时）：
```bash
cp <target> <target>.bak.$(date +%Y%m%d)
md5 <target>.bak.$(date +%Y%m%d)
# 确保 .gitignore 有 *.bak.* 规则
```

2. **生成压缩后主文件**：
   - P0 规则：全文保留在主文件，精简措辞但不删信息
   - P1 规则：压成万能公式表（一行一条：RULE-ID / 触发 / 动作 / P-权重 / Why）
   - P2/P3 规则：只在索引表留一行（RULE-ID / 子文件路径 / P-权重 / 触发场景）
   - 保留所有 link / 引用 / 关键词（含旧名别名）

3. **生成子文件**（`--sink-dir` 目录）：
   - P1 的子文件：RULE-ID 命名，含完整 Why + How to apply + 例外
   - P2/P3 的子文件：同上 + 4 维优先级表头
   - 格式遵循 SCHEMA.md 标准

4. **生成/更新 SCHEMA 文件**（如不存在）：
   - 从 `references/SCHEMA-TEMPLATE.md` 复制模板
   - 或读取 `mycc/docs/rules/SCHEMA.md` 作为参考

### Phase 3：验证（`--verify` 开启时）

跑 3 项验证：

**3.1 RULE-ID 全覆盖**
```bash
# 从旧文件提取所有标题/规则名 → 在新文件 grep 命中
# 期望：N/N 命中率 100%
```

**3.2 链接存活**
```bash
# 检查主文件所有 markdown link 指向的文件是否存在
find <sink-dir> -name "*.md" | wc -l
# 对比主文件引用数
```

**3.3 关键词保留**
```bash
# 从旧文件提取关键术语（RULE-ID / 专有名词 / 旧名称）
# 在新文件+子文件中 grep 确认无遗漏
```

**输出**：
```
[rule-compress] 验证结果：
  RULE-ID 覆盖：N/N (100%)
  链接存活：M/M (100%)
  关键词保留：K/K (100%)
  压缩比：-X% 行 / -Y% 字符
```

### Phase 4：跨引擎兼容（`--cross-engine` 开启时）

检查压缩后的规则是否能被其他引擎正确召回：

1. **检查 AGENTS.md**：如果目标是项目级 CLAUDE.md，确认 AGENTS.md 有"项目规则索引"章节
2. **codex 召回测试**（可选）：用 `codex exec` 测试 RULE-ID 命中
3. **输出兼容性报告**

### Phase 5：收尾

1. 输出压缩报告（前后对比表）
2. 如需 git commit，列出精确文件清单
3. 提示后续动作：
   - 新增规则走 SCHEMA
   - 定期复盘（推荐 1 周后跑 `/retro` 或专用校准 prompt）

## 适用场景

| 目标文件类型 | 适用度 | 备注 |
|-------------|--------|------|
| `CLAUDE.md`（项目级规则） | ✅ 最佳 | 首次实战验证 |
| `~/.claude/rules/*.md`（全局规则） | ✅ 推荐 | 13 条散文可压缩 |
| `memory/MEMORY.md`（记忆索引） | ⚠️ 需评估 | 已是索引格式，收益可能有限 |
| `multi-agent/RULES.md`（路由规则） | ⚠️ 需评估 | 先评估后决策 |
| 事件流（RECENT_EVENTS / task-log） | ❌ 不适用 | 不是规则，是时序数据 |

---

## 反模式（禁止）

| 反模式 | 危害 |
|--------|------|
| P2/P3 详情砍掉只留索引行 | **有损压缩**，边缘情况判断失分 |
| Why 段一律换成"详见子文件" | 失去 inline 判断能力 |
| 不同优先级混进一张表 | 失去 P 排序意义 |
| 一次性全文重构多个文件 | 高风险，应逐文件迭代 |
| 4 维打分靠拍脑袋不靠数据 | 标准失效，回归散文式 |
| 压缩后不跑验证 | 可能丢信息而不自知 |

## 案例库

### Case 1：CLAUDE.md（2026-04-28）

- 压缩前：307 行 / 13.0 KB / 25 标题
- 压缩后：165 行 / 8.9 KB / P0x6 + P1x9 + P2-P3x10
- 压缩比：-46% 行 / -32% 字符
- 验证：18/18 RULE-ID 全命中 / 链接全存活 / 关键词零遗漏
- 跨引擎：codex 3 组测试全 PASS（AGENTS.md 单层入口足够）
- codex 对抗评审：verdict=PASS-WITH-CHANGES，4 条最低修改全吸收
- 备份：`CLAUDE.md.bak.20260428`（md5: 5bcf423ca5579b9c882a5c2f972a6a48）

---

### Case 2：MEMORY.md（2026-08-07）—— **review 结论是「不压缩」**

适用度表里对 `memory/MEMORY.md` 标的「⚠️ 需评估，收益可能有限」被实测证实，记下来省得再跑一遍。

- 基线：87 行 / 13.9 KB / 62 条常驻（★项目 13 + ★参考 8 + ★教训 41 + 🗂 场景簇 11）
- **4 维 P 矩阵在这里不适用**：MEMORY.md 不是规则集而是索引，「下沉到子文件」这一步
  早就完成了（789 个 topic + INDEX-full.md）。真正的判据是文件自己第 9 行写的那条：
  **「踩进这个坑时，我会想到搜什么词？」** 想得到 → 场景簇；想不到 → 常驻。
- 字节分布实测：★教训 6961B/41 条（最大头）、🗂场景簇 2816B/11 条（占全文 20%，均 256B）。
  **两条簇行违反了文件自己的规矩**（L92=547B、L85=465B，塞的是摘要不是关键词）。
- 打分结果：41 条教训里只有 **13 条**「事后想得到搜什么词」够格降级，1 条可合并 → 41→27，
  预计 13.9KB→约 10.8KB。
- **川哥决定：先不动，绊线由 12KB 放宽到 14KB。**
  理由是我在报告里必须说清的那句——降级**在文件层无损**（789 个 topic 一个不动），
  **但在「我会不会想起来看」这一层有损**，而那恰恰是常驻的全部意义。
  62 条是当前真实需要，不是膨胀。

**方法论收获（v1 补丁，已同步 `~/.claude/rules/tools.md`）**：
绊线漂过时，**默认动作不是压缩，是先问「是不是真需要」**。
压缩的收益是省字节，代价是赌「下次踩到时搜得到」——
对「我不知道自己在坑里」那类条目，这个赌注是负期望。
**索引类文件跑本 skill 时，先做 Phase 0-1 出报告并停下等确认，不要默认进 Phase 2。**

## 迭代更新指南

本 skill 本身也遵循迭代原则：

1. **新增案例**：每次成功压缩后，在"案例库"追加一条
2. **调整打分标准**：如果发现某类规则的 P 级判定不准，修正"打分依据"
3. **扩展验证项**：如发现新的信息丢失模式，追加到 Phase 3
4. **方法论升级**：4 维矩阵如有更好的分级方式，升版为 v2（需老板确认）
5. **版本号**：当前 v1.0，重大变更升 minor，补丁不升版
