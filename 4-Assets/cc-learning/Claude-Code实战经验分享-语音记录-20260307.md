## 一、项目结构与知识管理

### 核心理念：让 CC 够得着你的信息

把所有需要 CC 知道的信息放在它可以读取的地方——同一个代码仓里，按需调用。

**三层分类结构**：
- **Inbox**：日常研究、想法、灵感。想法成熟后可提升为项目
- **Projects**：正式项目，每个项目有标准结构（项目定义、需求清单、任务队列、决策记录）
- **Thinking**：有价值的思考、判断、方法论

**使用方式**：
- 随时让 CC 调研某个东西，存入 Inbox
- 想法成熟后，从 Inbox 提升为 Project
- 树状结构让 CC 知道需要什么信息时去哪找

## 二、AI 时代的文档哲学

### 核心认知：文档是给未来的 CC 看的

传统文件是给人看的，但 AI 时代变了——**文档更多是给 AI 看的**。包括代码也是一样，100% 的代码都是 CC 写的，CC 自己看。

**六条设计哲学**：

1. **文件即指令**：写文件时想"CC 拿到后能干什么"，不只是存档给人看
2. **单一事实来源**：一个状态只在一个地方维护，不散落到不同地方，避免前后矛盾
3. **触发条件可执行**：给 CC 的指令要精确、可判断，不能模糊（如"PE 小于 15 时买入"而非"低点买入"）
4. **Git 即时间机器**：记录前后变化和上下文
5. **人决策 Agent 执行**：人做关键决策，Agent 负责执行
6. **结构化数据与自由文本分层**：分散存储，按需调用

### 结构即能力

想让 CC 有新能力？加一个结构化文件就行。加文件 = 加功能。

## 三、决策记录：最珍贵的文档资产

### 为什么决策记录如此重要？

CC 能通过 Git 看到文件变了什么，但**不理解为什么变**。如果不记录决策背景，未来的 CC 就无法理解当时的设计意图。

### 决策记录要记什么？

- **背景信息**：当时发生了什么，约束条件是什么
- **候选方案**：有哪些可选方案
- **最终决定**：选了什么
- **放弃了什么**（比选了什么更重要！选了什么看代码就知道，放弃了什么只有当时才知道）
- **改动文件**：涉及哪些文件变更
- **什么条件下翻这个决策**：约束条件变化时需要重新评估

### 决策类型

- Bug 修复
- 架构变更
- API 接口设计
- 功能取舍（做什么、不做什么）

### 关键认知

> AI 越聪明，它需要越多的上下文才能更理解你。你的决策记录就是它最好的学习资产。

## 四、Skill 技能系统

### Skill 是什么？

**一句话：说明书。** 把人类的知识、流程封装成一段文档描述，CC 需要时直接看说明书就知道该怎么干活。

### 三层 Skill 架构

**第一层：原子化技能**
- 单一功能，如：飞书通知（tell-me）、图片生成（brush）、skill 创建器（skill-creator）
- 每个 Skill 做一件事

**第二层：领域技能**
- 某个领域的具体工具，如：
  - 标题生成（title）：专门给公众号起标题
  - 公众号排版（gzh）：专门渲染排版
  - 精修（polish）：专门精修文章
  - 测试审查（test-review）：检查测试用例完整性
  - Next.js 开发指南（nextjs）：写代码的最佳实践

**第三层：路由技能（技能编排）**
- 告诉 CC 什么情况下用什么技能
- 如 create-system（创作系统入口）：写标题用 title，排版用 gzh，精修用 polish
- 如 dev-team（开发团队）：写测试 → 测试审查 → 写代码 → 测试 → 验收 → 文档同步

### 在 CLAUDE.md 里做初筛路由

```
写代码 → dev / dev-team
写文章 → create-system（内部路由到具体技能）
信息采集 → collect
复杂任务 → team
```

### 按需加载

技能多了（60+）会占上下文。解决方案：
- 不是所有技能都做成 Skill 文件，有些放在文档里也能被 CC 搜到
- 通过路由技能实现按需加载，而非全部注入

## 五、软件开发的四个时代

### 1.0 纯人力时代

人写需求文档 → 人写设计方案 → 人写代码 → 人写测试 → 人测试 → 人改 Bug → 人部署 → 人更新文档

**人既是执行者，也是推动者。**

### 2.0 ChatGPT 时代

人让 AI 写需求 → 人让 AI 写代码 → 人让 AI 写测试 → 人让 AI 改 Bug → 人让 AI 更新文档

**人变成指挥官，AI 执行，但节点间的推动仍靠人。** 很多人还停留在这个阶段。

### 3.0 AI 自驱时代（当前主流实践）

人给出想法 → AI 自己拆需求 → 写测试 → 审查 → 写代码 → 测试 → 改 Bug → 更新文档 → 人做最终验收

**人只负责起点（想法）和终点（验收），中间全自动。** 通过 Dev Team 技能实现。

### 4.0 永动机时代（探索中）

AI 自己醒来 → 自己找活（从功能清单/竞品分析）→ 自己设计 → 自己实现 → 自己验收 → 自己迭代

**人只需要搞一个定时任务，AI 按功能清单自动实现、自动验收、自动迭代。**

> 写代码只是一个场景，这个模式可以推演到：写文章、发小红书、信息采集、日程管理……一切重复性工作都可以用这个框架接管。

## 六、贾维斯模式：多 Agent 架构

### 设计哲学

把自己想象成一个皇帝，只跟一个贾维斯对话。贾维斯收到任务后，自己去后台起 Agent 执行，不阻塞主对话。

### 核心规则

- **超过 1 分钟的任务** → 全部 spawn 子 Agent，主 CC 只编排验收
- **简单问答** → 直接回，不起 Agent
- **需要干活** → 创建 team，后台执行，完成后通知
- **跨机器** → 通过 mycc API 通信

### 实际效果

- 主 Agent 永远不被阻塞，随时可以聊天
- 子 Agent 后台跑任务，跑完自动通知
- 可以同时并行多个任务

### 贾维斯的灵魂

CLAUDE.md 是灵魂，但光有它还不够。还需要：
- 后台任务机制
- Todo 系统
- 记忆系统
- 定时心跳巡逻

## 七、定时心跳系统

每半小时唤醒一次，从焦点池中挑一个任务执行。

### 11 个巡逻任务示例

- 审视最近对话，发现缺什么 Skill → 写到候选池 → 飞书通知
- 扫描过期项，该催的催一下
- 扫描 Inbox 里的想法和笔记，挑可以推进的自己推进
- 定时采集热点信息
- ……

### 关键：让 CC 有主观能动性

CC 自己去扫描 Inbox 里的想法 → 挑能推进的 → 自己执行下一步 → 飞书通知结果

## 八、信息采集实战（小红书为例）

### 流程

1. CC 通过 Chrome DevTools 操控浏览器
2. 上小红书搜索关键词（如"小龙虾安装"）
3. 自动筛选高互动量帖子
4. 采集内容，边采集边写入 MD 文档
5. AI 分析洞察，保存到 Inbox

### 重点

- 采集过程中边采边写文档，断了重启后 CC 能看到之前采集了什么，接着操作
- 可配置为定时任务（如每天 9:30 采集 → 9:40 根据热点写文章）
- 不只是小红书，GitHub Trending、各平台热点都可以用同样模式

### 官方会不断补齐基础能力

蚁群系统做完两天后官方出了 Agent Team，MYCC 远程做完后官方出了远程功能，定时任务做完后官方也出了……

2. **AI 落地方法论**：知道 CC 的能力边界在哪，什么能做什么不能做

> 官方做的是公约数，服务绝大多数用户。深入具体业务流程的经验，才是你的护城河。

## 十二、Q&A 精华

**Q：给 CC 第一版文档，过几天要改版，怎么处理？**
A：用决策记录。每次改动都记录为什么改、改了什么、放弃了什么。这样未来 CC 能理解演变过程。

**Q：经验越来越多，怎么管理？**
A：定期让 CC 做"萃取"——扫描文档，过时的抛弃，好的保留。相当于知识瘦身。

**Q：CC 的能力边界指什么？**
A：做一切事情的边界，不只是写代码。比如知道它一次能重构 5 万行代码，知道它在哪里容易偷懒。模型进化后边界会上升，你的经验也随之增值。

**Q：如何用 CC review 代码？**
A：前期架构要好（模块化、组件化）→ 让 CC 按文件提取功能清单 → 写测试用例 → 重构 → 保证测试通过。标准优先。

**Q：硬件配置要求？**
A：MacBook 16G 够用。云服务器 2 核 4G 够用。关键不在硬件，在于使用方法。
