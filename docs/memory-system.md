> 从 CLAUDE.md 下沉，详细描述 cc 的三层记忆架构。

## 短期记忆（自动注入）

每次对话时，通过 hooks 自动注入：
- `0-System/status.md`：当前状态快照、今日焦点
- `0-System/user-profile.md`：用户画像汇总（v5.6 新增，每周自动重建）
- 配置位置：`.claude/settings.local.json`

## 滚动事件流（24h，EvoMap Memory Bridge）

**Session 开始时必读**：
- `0-System/RECENT_EVENTS.md`：最近 24h 重要事件（上次做了什么、当前状态）

**关键词召回（方案C，2026-03-09 起；v5 RRF 融合升级 2026-03-29）**：
- 读取用户第一条消息的关键词
- v5: 三路检索（关键词+TF-IDF+向量）经 RRF 融合排序，注入匹配的 `[project/*]` 类别
- `[user/*]` 和 `[agent/*]` 类别**始终注入**，不受关键词过滤
- v5 L0: 所有 project/agent 类别的一行概览始终注入（~400 token），让 cc 知道存在哪些记忆
- 无命中时：只注入 `[user/*]` + `[agent/*]` + L0 概览
- 映射示例：
  - 飞书/机器人/卡片/消息/通道 → `[project/技术-飞书]` + `[project/技术-飞书多通道]`
  - 黄金/金价/数据/采集 → `[project/技术-数据]` + `[project/技术-RSS采集]`
  - Bug/错误/修复/报错 → `[project/Bug-Fix]` + `[project/Bug-Fix-已知]` + `[project/Bug-Fix-MCP]`
  - 知识库/Wiki/FUTURUS/飞书文档 → `[project/FUTURUS知识库]`
  - 配置/后端/端口/mycc/启动 → `[project/配置-mycc后端]`
  - 路径/文件/脚本 → `[project/路径-关键文件]`
  - 产品/需求/PRD/功能设计/做一个/想法/用户/app → `[project/产品-prd]`
  - 智能家居/HA/HomeAssistant/灯/开关/米家/小爱/传感器 → `[project/智能家居]`
  - 贾维斯/Jarvis/ESP32/语音终端/唤醒词/小智/xiaomusic/音乐播放 → `[project/贾维斯-语音终端]`

**Session 结束前必写（三步）**：
1. 追加本次操作到 `RECENT_EVENTS.md`（流水账，格式：`- \`HH:MM\` 事件描述`）
2. **六维度扫描提取**原子 Item 到 `0-System/memory-items.md`（结构化事实，只写新发现/变更）
   - Item 格式：在对应命名空间类别下追加一行 `- 简洁的可复用事实`
   - 命名空间：`[user/*]`（跨项目通用）或 `[project/*]`（mycc 专属）
   - 叶子原则：每条 Item 只写一个独立事实，不含推论或多个并列事实
   - 原则：每条 Item 独立可检索，过期的直接删除或标 `[已废弃]`
   - **六维度 checklist**（v5.6 升级，借鉴 ASMR 六维度摄入，2026-04-02 起执行）：
     提取 Item 前，用以下 6 个维度扫描本次 Session，确保不遗漏：
     | 维度 | 提取什么 | 写入命名空间 |
     |------|---------|------------|
     | ① 个人信息 | 用户身份、角色、硬件、习惯的新发现 | `[user/基本]` `[user/偏好]` |
     | ② 偏好变更 | 用户表达的偏好、工作风格、沟通方式变化 | `[user/偏好]` `[user/方法论]` |
     | ③ 事件事实 | 部署、配置、Bug 修复等技术事实 | `[project/*]` 对应类别 |
     | ④ 时间数据 | 有时效性的安排、截止日期、里程碑 | 加 `[event:YYYY-MM-DD]` 标签 |
     | ⑤ 更新/修正 | 与已有 Item 矛盾或补充的信息 | 触发矛盾检测（见步骤 3） |
     | ⑥ 助手信息 | cc 自身的能力变化、踩坑教训、skill 经验 | `[agent/技能]` `[agent/踩坑]` |
     - 每个维度快速过一遍（~5 秒），有新发现才写，无则跳过
     - 六维度是 checklist 不是模板——不要为凑维度写无价值的 Item
3. **矛盾检测**：写入新 Item 前，对同类别已有 Item 做冲突扫描（详见下方「语义矛盾检测」）

## v5.6 升级（2026-04-02，借鉴 ASMR 架构）

> 理论来源：Supermemory ASMR（Agentic Search and Memory Retrieval）——
> LongMemEval 98.6% SOTA。核心洞察：结构化多维度摄入 + 实时矛盾检测 > 被动向量检索。

### 语义矛盾检测（替代被动清理）

**旧方案**：矛盾检测仅在每日 04:00 定时清理时执行，新旧矛盾 Item 可能共存数小时。
**新方案**：写入时实时检测，灵感来自 ASMR 的 isLatest 标记机制。

**三步法**：
1. **同主题定位**：写入新 Item 时，扫描目标类别中含相同 `#tag` 或相似关键词的已有 Item
2. **矛盾判定**：新旧 Item 描述同一主题但结论不同（端口/路径/版本/方案/状态变化）
3. **自动处理**：
   | 情况 | 处理 |
   |------|------|
   | 矛盾 + 旧无 `#base` | 删除旧 Item，写入新 Item |
   | 矛盾 + 旧有 `#base` | 新写为 `→supersedes:`，旧基线及 Δ 全删 |
   | 补充（非矛盾） | 新写为 `→Δ:基线关键词` |
   | 无关 | 正常写入 |

**判定标准**（避免误杀）：
- 同一 `#tag` + 同一主题实体 + 结论不同 → 矛盾
- 同一 `#tag` + 不同主题实体 → 无关（如两个不同服务都有 `#端口`，不矛盾）
- 不确定时保留两者，在新 Item 加 `[?conflict]` 标记供人工确认

## v3 升级（2026-03-23，借鉴 Supermemory）

### 双时间戳（temporal grounding）

每条 Item 支持两个日期：
- `[YYYY-MM-DD]` — 写入日期（原有）
- `[event:YYYY-MM-DD]` — 事件日期（新增，可选）

事件日期参与评分：已过期事件自动降权（0.05），即将发生的事件自动提权（1.0）。

### 关系版本链（relational versioning）

通过 `→updates:关键词` 标记，新 Item 自动取代同类别中的旧 Item。
引擎在注入时将被取代的条目 score 归零，只展示最新版本。

### 主动遗忘（smart forgetting）

每日 04:00 定时任务自动清理 + 巩固：

**遗忘规则**：
1. eventDate 过期 >7 天 → 删除
2. 写入 >90 天且 ★<3 → 归档到 `memory-archive.md`
3. 写入 >120 天 → 无条件归档

**Δ 自动巩固（睡眠巩固，PI-LLM 启发，2026-03-31 起）**：
4. 同一 `#base` 下的 `→Δ:` 条目 ≥ 3 条 → 触发**重建基线**
   - 将 #base + 所有 Δ 合并为新的 #base（保留最新信息）
   - 删除旧的 #base 和所有已合并的 Δ 条目
   - 新 #base 的星级 = 旧基线星级（不变）
   - 新 #base 的日期 = 当天（刷新 write_date）
   - 合并时保留所有具体值（路径/端口/版本号），丢弃过程性描述

**执行流程**：扫描 memory-items.md → 对每个类别检查 Δ 堆叠数 → 满足条件时就地合并 → 写回文件

### 搜索升级（TF-IDF cosine）

类别模糊匹配从 Jaccard 集合交集升级为 TF-IDF 余弦相似度，对长短文本差异更鲁棒。

### 实时捕获优化

Auto-capture 冷却时间从 60s 降至 30s，提高中途记忆捕获频率。

### 多模态记忆（预留）

格式预留 `[source:image/video/camera]`，实施时机：接入外接摄像头后。

## v6 升级方向：因果关联（IIT 启发，2026-03-31 规划）

> 理论来源：整合信息理论（IIT）—— 意识的量由信息整合度 Φ 决定，关键在于组件间的因果连接。

### 因果关联标记

当前 memory-items 的条目之间是扁平的（仅有 supersedes 版本链）。v6 引入显式因果关联：

```
- 某条 Item 内容 [→caused: 另一条关键词] [←caused-by: 触发条关键词]
```

**因果类型**：
| 标记 | 含义 | 示例 |
|------|------|------|
| `→caused:X` | 本条导致了 X 的产生 | 发现 bug → 导致修复方案 |
| `←caused-by:X` | 本条由 X 触发 | 修复方案 ← 由 bug 触发 |
| `→evolved:X` | 本条演化为 X | 旧方案 → 演化为新方案 |

**写入规则**：
1. 因果关联**可选**，仅在关系明确时标注（不强制每条都关联）
2. 优先标注跨类别的因果链（如 Bug-Fix → 配置变更 → 性能改善）
3. 因果链有助于 friction-patterns 的根因追溯

**预期收益**：
- 检索时可沿因果链扩展召回（查到 bug 时自动关联修复方案）
- 为 evolution-log 的自省提供更丰富的上下文
- 长期积累后可生成「知识因果图谱」，量化系统的信息整合度

## v4 升级（2026-03-27，借鉴 TurboQuant 失真率理论）

> 理论来源：TurboQuant (arXiv:2504.19874) — 向量量化的信息论下界证明：
> 压缩 4 倍时理论最优失真 ≈ 1/256（即 99.6% 信息可保留）。
> 核心启发：**基础编码 + 残差修正** 优于完全替代；每层压缩应有明确的失真预算。

### P0: 残差版本链（替代旧 →updates 语义）

**旧方案**：`→updates:关键词` 让旧 Item score 归零，信息完全丢失。
**新方案**：基线 + 增量（Δ），类比 TurboQuant 的 `x̃ = Q_mse(x) + ||r|| · Q_qjl(r)`。

**三个标记**：
- `#base` — 基线事实，记录该主题最稳定的核心信息（低频变化）
- `→Δ:基线关键词` — 增量修正，记录相对于基线的变化部分（高频变化）
- `→supersedes:基线关键词` — 完全重写（仅当基线本身已错误/过时时使用，取代旧 →updates）

**规则**：
1. 一个主题首次写入时正常写，不需要任何标记
2. 同一主题第二次变更时，把原条目标为 `#base`，新增的写 `→Δ:基线关键词`
3. 增量（Δ）可堆叠：多次小变更各自独立记录，检索时按时间排序叠加
4. 增量堆叠 ≥3 条时，触发**重建基线**：合并所有 Δ 到新 #base，清除旧 Δ（每日 04:00 自动巩固检查，见下方「Δ 自动巩固」）
5. `→supersedes:` 是核弹选项：旧基线 + 所有 Δ 全部 score 归零，仅当根本性变化时使用

**格式示例**：
```markdown
- ★★★ cc-remote V4：阿里云香港 FRP 中转，域名 cli4.hahaxiong.cc [2026-03-15] #base #cc-remote
- ★★ Δ 修复 WebSocket 重连超时 [2026-03-20] →Δ:cc-remote-V4 #cc-remote
- ★★ Δ deploy-user.sh 改为两步写配置（先 HTTP 再 SSL）[2026-03-26] →Δ:cc-remote-V4 #cc-remote
```

**检索行为**：
- 命中 `#base` 时，自动拉取同类别下所有 `→Δ:该基线关键词` 的条目
- 展示顺序：基线在前，Δ 按时间升序
- Δ 条目单独命中时，同样自动拉取其基线

### P1: 分层失真预算

> 信息论保证：每层压缩的失真有理论下界 D ≥ 4^{-b}。
> 我们为三层转换定义可操作的质量标准。

**Resource → Item（RECENT_EVENTS → memory-items）**：

| 必须保留（≥95%） | 允许丢弃 |
|------------------|---------|
| 决策结论（做了什么、选了什么方案） | 时间修辞（"先…然后…最后"） |
| 关键参数（端口、路径、版本号） | 中间调试过程 |
| 因果关系（为什么这样做） | 情绪表达 |
| 失败教训（踩了什么坑） | 重复确认对话 |

**检查规则**：提取 Item 时自问——"如果只看这条 Item，下次遇到同样场景能直接复用吗？" 如果不能，说明丢了关键信息。

**Item → Category（memory-items → MEMORY.md）**：

| 必须保留（≥80%） | 允许丢弃 |
|------------------|---------|
| 主题存在性（"有这个东西"） | 具体参数值 |
| 位置指针（"去哪里找"） | 实现细节 |
| 当前状态（运行中/已废弃） | 历史变更过程 |

**检查规则**：MEMORY.md 的每一行应能回答"这个主题还活着吗？详情去哪看？"

**RECENT_EVENTS 滚动清理时的失真预算**：

超过 24h 的事件在从 RECENT_EVENTS 清除前，必须确认：
1. 已提取为 memory-items（如有可复用事实）
2. 或该事件无跨会话价值（纯执行日志）

违反预算的信号：下次 session 问"上次那个 XXX 怎么配的"却找不到 → 说明 Resource→Item 转换丢了关键信息，需要补提取。
