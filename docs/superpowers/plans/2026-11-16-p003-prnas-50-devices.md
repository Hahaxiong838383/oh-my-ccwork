# P003 PRnas 归档、50台设备与可编辑扩容执行计划

> 执行方式：codex 主实现，Grok 独立评审固定候选；按 `executing-plans` 逐项实施。本文的复选框均为未来验收事项，未执行不打勾。

**目标：** 在保留正常语音、方舟问答和既有设备上传合同的前提下，支持50台设备的数据接入与PRnas归档，后台可编辑规划设备数量，后续扩容不再修改20/32之类业务常量。

**架构：** 阿里云继续保存最新状态、近期原始事件、事实和幂等记录；PRnas异步接收Ark历史检查点和数据库一致性备份。本期Analytics复用整库备份，不建立第二套逐事件归档台账。设备请求及语音查询不等待NAS。后台分别显示规划配额、实测安全容量、已验证规模和当前开启数量。

**技术：** 复用现有Node 24、TypeScript/Hono、SQLite、Vue后台及Python/SSH/rsync定时任务，不新增数据库集群或对象存储平台。

**设计依据：** 用户已选择“阿里云实时数据＋PRnas历史/备份”，要求50台及可编辑扩容；基线见《P003_PRnas方舟存储可行性评估_20261116.md》。本文进一步冻结实现口径。当前为计划评审阶段，未开发、未扩盘、未部署、未开启新增设备。

## 一、范围与必须保持的行为

- 50台指数据接入与留存规模，**不代表50路实时语音并发**；不调整语音Worker并发、搜索或倾听灰度名单。
- 本期同时规划50台Ark快照，以及兼容旧客户端的50台Analytics上传。只有前者通过时，不得宣布后者通过。
- 初始规划配额50，管理界面允许1–1000正整数。1000仅是输入和请求大小保护，不是承载承诺。
- 现有设备16 KiB快照正文、每分钟12次限流、Analytics每批200条/2 MiB、单writer、两请求并发保持不变。
- Analytics原始记录14天、事实90天、诊断样本3天、聚合载荷90天和永久幂等记录保持现有语义，不为NAS新增事件TTL门槛。Ark待归档记录和待传备份文件必须NAS确认后才能清理。本期不承诺90天连续原始埋点逐条恢复。
- 现有默认23点日批不改；不默认假定新端分层上传已覆盖全部设备，不以未测压缩率计算承载量。
- 账号、SN、epoch、grant及normal/gm/unknown隔离保持。未知值不补0，快照不是完整收益流水。
- **完整可恢复游戏存档不属于已实现能力。** 本期预留存储位置即可；需要端侧完整导出/导入合同时另做最小合同及恢复验收，不强迫当前设备仅为NAS迁移做OTA。
- 源码、测试、负载证据和线上实机证据分别出结论，不能互相替代。

重点复核五类情况：配额与名单并发修改（A01–A03）；NAS断网、满盘及确认丢失（A11–A13）；日批与维护/备份重叠（A06–A10）；换绑、GM和旧身份重放（A04/A05/A15）；永久幂等记录增长及资源预算失真（A12/A14）。各项均有对应实现任务和测试，不能只做正常路径。

## 二、后台交互和扩容规则

入口：现有 **Worker管理 → 数据埋点 → 上传与容量配置**，新增“存储与归档”区域；沿用搜索、多选、全选筛选结果。方舟授权区域显示同一规划配额及独立开启数量。

| 页面字段 | 本轮设计 |
|---|---|
| 规划设备上限 | 默认50，可编辑；保存后不重启，不自动开设备 |
| 已验证规模 | 本轮目标50，只读；附验证时间、候选版本与测试负载 |
| 当前安全开启上限 | 系统根据云盘、归档缓冲、维护吞吐、已验证规模计算 |
| 当前开启 | Ark、Analytics各自显示；两个名单独立，不互相扩大 |
| 容量预测 | 当前配额对应30/90天预测、NAS配额和预留空间 |
| 归档状态 | 最近成功时间、待传条数/字节、最老积压、NAS连接状态 |
| 不足原因 | 明确显示磁盘、维护滞后、NAS积压或尚未验证哪个限制生效 |

例如设定100、已验证50时，页面显示“规划100；当前可开50；扩至100需容量验证”，不能显示100台已支持。

容量API新增随配额变化的`target_devices_bytes`、`target_devices_fit`及限制原因。旧`twenty_devices_*`字段保留一版兼容既有读取方，页面不再固定展示20台。NAS预算是应用层项目预算，实际准入还要读取NAS卷剩余空间；不能把设定1 TiB误称已独占分配或忽略其他项目占用。

Ark与Analytics分别计算安全容量，不让Analytics满载误关Ark。共同规划配额不涉及计费或跨库设备名额事务。

保存规则：

1. 配额可提高，但实际启用仍受相应功能安全上限约束。降低至任一功能已启用数量以下返回409，保持原值和现有名单，提示先选择停用范围。
2. 配额、设备名单均有revision；在提交前重新核对最新revision/容量，避免两个管理页面竞态绕过上限。容量结果超过120秒或异常时禁止新增开启，紧急关闭仍可用。
3. 持久配置仅服务端使用，不进入安卓设备配置快照，不因改容量反复触发false→true补传。
4. 移除Ark `.max(32)`、`>=32`、`slice(0,32)`及环境静态名单对扩容的阻挡。原环境允许名单作为一次性迁移种子，**不自动授予新设备**。新设备须在后台选中且核对当前有效身份。
5. 事实代理范围跟随Ark权威授权范围；搜索/倾听派单范围保持原样。Ark管理请求上限改64 KiB以支持配置名单，设备快照16 KiB上限不改。
6. 已验证规模由实际压测工具输出的记录更新，不能在普通配额输入框手填即生效。旧文档有14个合成主体/84,000条集中上传与维护重叠证据，代码常量20不等于已压测20。迁移采用可追溯的实际测试档，保留现有授权，不能将未知Ark容量或“目标50”预填为“已验证50”。50→100复用同一参数化工具，无需修改业务代码；仍需真实资源及数据兼容。

## 三、数据保存和故障语义

### 最新状态与历史

最新快照仍每台一行、每次有效上报覆盖更新。历史采用**每5分钟一个检查点＋关键变化立即留档**；比较余额、星尘、补勤卡、奖励领取状态、来源和内容版本，不因采集时间或每秒倒数变化额外归档。保留90天，后续调整留存先重新测容量。

需要留档的快照与最新行在同一SQLite事务写入待归档表。包内记录设备、身份epoch/grant、snapshot_id、捕获/接收时间、schema和内容hash。进程重启不丢已确认的待归档版本。同ID重放不增加历史版本。

这是检查点和关键变化历史，不是每次上报报文永久保存，也不是完整游戏恢复包。客户端在服务器拒收后可能用更新快照替换待发旧快照，因此只对**服务器已经accepted且按策略应归档**的版本保证无丢失。

### 事件和备份

Analytics复用现有Backup API生成整个事件库的一致性副本，其中含当时仍在保留期的raw/aggregate/diagnostic、事实和seen。NAS保存备份清单和时间点，不新增每条事件的归档引用或单时间戳高水位协议；载荷按原TTL清理，seen继续留云端。备份恢复只承诺备份时点及其内容，不冒充完整逐事件永久历史。

归档由独立进程打包压缩，NAS每5分钟主动拉取完成包，校验文件大小、条数、SHA256后原子落地，再回传受限确认。包传到一半、确认丢失、同包重传均可重入；未确认不得删云端待传包。

NAS仅能读取已发布包，并通过受限命令确认已知包ID/hash；不授予任意云端root操作。凭据不进仓库，不开放NAS公网入口。传输支持断点续传，初始一个活动归档任务，避免归档/备份占满磁盘IO。

云端保留一份完成的数据库备份，生成下一份时还需运行库和暂存备份，**峰值按三份算**。NAS保7份日备及4份周备；校验新备份并完成隔离恢复验证后才轮换旧副本。NAS故障期间暂停产生重复全库备份，保留已有完成副本与Ark历史待传。

完整备份只允许一个任务运行；修改现有`--keep 2`策略与容量公式必须同批交付。以实测证明“一份运行库＋一份已完成本地备份＋一份生成中备份”，未消除额外副本前仍按实际四份或更多计量。过期`.partial`只能按任务身份核实后回收，不误删仍运行的备份。

### NAS离线

按下面的验收负载设计72小时Ark历史离线缓冲，初始预算8 GiB，和Ark/Analytics库落在容量统计的同一云数据盘，避免漏算。Analytics继续正常写本地运行库，NAS断线期间不反复产生全库备份。正常时Ark归档积压目标不超过15分钟；连续1小时失败告警，24小时阻止扩大开启名单。队列达到容量阈值，相关需要留档的新快照返回可重试503，绝不accepted后静默删除历史；正常聊天继续。

72小时档明确为：50台，每台每小时最多60次关键变化，加12个定时检查点，归档正文平均不超过2 KiB；正文合计约0.531 GB，加索引、WAL、生成中包后实测不得超过8 GiB。此频率是验收档，不是新增业务限流。**不承诺50台持续以16 KiB、12次/分钟满速更新72小时**；该极端仅快照正文就约39.6 GiB。极端流量必须被容量/限流机制明确拒收并保留已接受记录。NAS恢复后按可验证带宽限速追赶，目标24小时内消化72小时验收档积压。

## 四、50台容量预算与资源决策

本轮测算保守采用旧raw每设备每日6000事件：50台即300,000事件/日、200条/批共1500批。快照压力档按每设备10秒一次、平均1 KiB；历史按上述检查点策略计量。关键变化额外字节必须实测，不能只算定时检查点。

容量同时观察事件数量和实际落盘字节，不能仅凭“每天6000条”忽略大正文。旧模型每事件1280/1024/400字节只是既有测量基准；新索引、较大事件及暂存空间取实际高值重新预测。接近预算时先限制新增放量，再按已声明的入站策略背压。

| 项目 | 规划值及限制 |
|---|---|
| 当前云盘空闲 | 前次只读实测15.68 GB，实施前再核 |
| 50台30天运行库新增预算 | 约20.01 GB，已含旧模型10%余量 |
| 50台90天运行库新增预算 | 约48.21 GB，raw14天、fact90天、seen90天增长 |
| 90天云端峰值 | 三份库＋8 GiB缓冲＋4 GiB预留＋512 MiB WAL约158.04 GB |
| 建议云数据盘 | **200 GiB独立数据盘**，当前服务器不换；需确认可挂载、费用与实测IO |
| NAS项目初始预算 | **1 TiB**，不是占用整卷；至少20%预算余量，可调整 |
| NAS90天粗估 | 11份备份约530 GB，加Ark历史检查点、关键变化、元数据；不额外建设90天原始事件归档 |

以上是旧模型规划值，未含新归档索引的实测增量，不是最终账单或压测结果。开发后按真实SQLite文件/WAL/归档体积重算。200 GiB是否足够以验收为准，不足时增加磁盘或调整经批准的数据策略，不虚报通过。

阿里云提供向现有ECS挂载数据盘的机制，但目标实例的盘类型、可用区、挂载名额及费用尚未核准；实施前按控制台实际条件确认，初始化只针对确认空的新盘。[阿里云数据盘挂载说明](https://www.alibabacloud.com/help/en/ecs/user-guide/attach-a-data-disk)

永久seen持续增长：同负载180天运行库约60.09 GB，三份库和相同预留约193.68 GB，接近200 GiB盘容量，必须滚动预测并在预计30天内不足时提示扩盘。不能称永久稳态。后续扩100台也需重算，配额变大不等于磁盘自动变大。

如果暂不扩云盘，可以先交付50台最新快照、历史归档和后台配额，但**不能宣布50台旧raw埋点全量可用**。本计划完整目标以磁盘条件和性能验收满足为前提。
