# CONTEXT-BUDGET: 上下文预算意识

| 字段 | 值 |
|------|-----|
| 优先级 | P2 |
| 权重 | 0.60 |
| 是否常用 | 可选 |
| 是否必选 | 可选 |
| 触发条件 | 长任务（预估 >30% 上下文）/ status.md/RECENT_EVENTS.md 接近上限 |

## 动作

- **工作记忆精简**：`status.md` 保持 <50 行，`RECENT_EVENTS.md` 保持 <80 行，超出主动清理旧条目
- **大任务分治**：预估超过当前上下文 30% 的任务，拆分为子任务分发给 codex/gemini，每个子任务获得新鲜上下文
- **中间结果外化**：长任务的中间产出及时写入文件（而非堆在上下文里），后续步骤从文件读取
- **反模式**：在单个上下文中塞入 >5 个大文件全文阅读 ← 应该有选择地读取关键段落

## Why

来源：GSD 上下文管理策略 — 上下文膨胀是长任务质量衰减的根因。

实证：cc 对话超过 100K token 时，对早期信息的召回率显著下降；超过 150K 后开始出现幻觉（编造文件路径、API 名）。

## How to apply

判断"是否需要分治"的简易公式：
```
预估输入字符 + 预估输出字符 > 60K → 必须分治
20K-60K → 优先用文件外化中间态
<20K → 直接做
```
