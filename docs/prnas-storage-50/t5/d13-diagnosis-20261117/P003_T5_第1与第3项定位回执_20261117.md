### 1.4 确定的软件恢复缺口

重复组于北京时间 **16:40:51.477** 发起合成请求，**16:40:59.492** 收到503，耗时8015.770ms；writer promise等待8003.545ms。

- 同期检查点从16:40:51.366到16:41:01.490，历时10124ms，报告内部耗时9496.182ms。
- 事后逐ID只读核验，该批**200条event与200条seen均已提交**。具体提交完成时刻未单独埋点，不能认定提交发生在8秒期限之前。
- 客户端成功ACK合计36600条，数据库本轮实际36800条；差额恰为这200条。这是“提交结果没有交付给客户端”，不是已证实的数据丢失。
- 超时后 `storage_ready=false`，后续一直503，直到16:51:35仍未恢复；检查点已正常，`sql_busy=0`、无OOM。随后停止自有测试，保留库与WAL。

代码链已核：`AnalyticsWriter` 的8秒任务定时器置 `failed=true`、拒绝当前等待并请求关闭writer；晚到结果只释放资源。已核的HTTP生命周期没有在writer排空后重建或主动退出，PM2的现有进程退出/内存策略不会单凭 `/ready=false` 重启它。生产writer、启动脚本与本次核验版本SHA一致，生产实际生命周期也已只读核对。

**这是可复现、可针对修复的恢复缺口。实际复现在隔离服务，不能说生产已经发生同一次故障。** 本轮没有对全机所有外部监控做全面审计。

### 1.5 不能据此直接决定换服务器

0.5核／768MiB是压测保护配额。生产Brain/Analytics所在PM2 cgroup的CPU/内存限额为max；Analytics另有PM2的512MiB进程内存重启阈值，二者不是同一概念。

内存上限触发已观察到，但额外1536MiB单变量组**未运行**：优先保留失败数据库，现有剩余空间不满足另开完整clone的预留要求。因此内存、磁盘规格与测试配额的贡献尚未完全分离，不能宣布“必须换服务器”或“只是压测限制”。

### 3.2 分段证据排除了“只是冷盘”

冷读首请求实际读取约1.38MB，evidence SQL一般约68–80ms；暖DB、零实际读盘时也能失败。2核的三次冷启动首请求仍失败。因此不能把全部失败解释为冷盘或仅CPU不足。

后续直接记录了grant、发出请求、headers、body、schema解析和**原125ms采纳判断**，没有修改120ms中止计时与125ms判定：

明确失败样本 `d13s-noevict-1 / 0-0`：

| 环节 | 结果 |
|---|---:|
| 本地grant | 0.117ms |
| 进入fetch封装 | 0.919ms |
| reader整个handler | 34.549ms |
| SQL执行合计 | 4.999ms；实际读盘0字节 |
| headers到达（自fetch开始） | 116.417ms |
| body完整（自fetch开始） | 121.335ms，HTTP200 |
| 产品内部采纳判断 | **128.422ms，adopted=false** |

**这个样本不是权限慢、不是SQL冷读慢，而是完整本地HTTP处理路径已经耗尽预算，虽然200和body到达，history仍被产品层丢弃。** 尚未把handler外的所有耗时再分到具体底层库/调度函数，不能把它全称为某个库的初始化时间。

只预热一个不查数据库的HTTP常量路径，后续三组首请求均完成响应解析并通过采纳判断，总时长为86.028／128.957／63.460ms；其中仍有一组不满足p99≤100ms安全余量。预热有效，但**尚不能单独宣布根治**。

观测时还区分了两种情况：`adopted=true`可能只是采纳超时竞速返回的unknownHistory；只有HTTP200、body完整、response-schema已解析、采纳判断通过同时成立，才算远端history响应被实际采用。这个验收缺口已补证。
