# T5 600k rollup 独立排查

结论：云端当前 30 秒失败主要落在冷读取等待；已经命中覆盖索引，不是遗漏索引、600k 超过事实数上限或 JSON 语义错误。已给出一行低风险窄投影候选，但它只减少 JS 行构造开销，**不能宣称根治冷 I/O，也不能据此关闭 T5**。

## 证据边界
- 固定源码基线 `65c86916e1e6a64352ec75d3c2b6eebb364e649a`。本次只在私有归档改动，不改主树、不 SSH、不操作生产。
- 原云端停上传后独立维护仍两天 budget_exceeded，dirty_days=2；查询计划明确 t5_experiment_cover。
- 主13随后在相同600k隔离库执行本文只读诊断脚本，结果已独立解析为 CLOUD-SCAN-SUMMARY.json。
- full：30.01秒仅442624行，CPU约3.09秒，磁盘读约155MB；narrow紧接着读取600k耗11.73秒、CPU2.31秒、磁盘再读约56MB；parse第三次600k耗2.39秒、CPU2.40秒，磁盘读取增量0。三个不是等冷条件，**不能把30秒→11秒算成窄投影收益**。同查询索引、缓存暖后全量扫描足够快。
- 这能定位至冷读取路径。还不能凭这组样本区分磁盘级别、物理页离散度、其他宿主I/O和资源调度的各自比例，不能直接说“阿里云故障”。

## 最小候选
- `rollup-narrow.patch` 仅把 SELECT * 替为实际用到的6列。保持原 WHERE、ORDER BY、事务、30秒/100万上限、预算失败回滚和脏日标记。
- 基线SHA与patch SHA及原/新文件SHA见 EVIDENCE.json。没有自动建索引、预热后台任务、放宽预算、增量水位或新表。
- 本地新建同50设备、同catalog的600k事件等量事实夹具（120万fact，约998MB），原实现两维23.77秒完成。该快速本地盘不代表云端性能。
- 同一夹具顺序A/B/B/A：两维平均墙钟 25960.40→22718.32ms，平均CPU 18094.76→15987.39ms。样本小、缓存和本机负载未全隔离，仅可看作约12% CPU开销改善的初证。
- 四次100条设备日摘要与两条全局日摘要字节一致，SHA均7cf65c2c4c209ceb27ad0a93afcb5e741eefed0c3c9e40df64d29c404b0b336f，fact保持120万。1000条预算负向测试保留原摘要、dirty=2，不假报成功。
- analytics-maintenance、analytics-fact-layout、analytics-ops三组现有回归全部PASS。无需因一行可逆优化增加复杂新测试架构。

## 建议主13执行顺序
1. 可按逐文件hash核同合入窄投影，先不把它计作冷IO修复。
2. 在现有隔离600k库做一次与原始故障等冷的原/候选对照；保留全部超时与冷启动样本。
3. 完整T5仍需要足够成熟数据容量及I/O余量。资源决策应包含存储类型/IOPS/吞吐；仅增加容量数字不能自动保证此项达标。
4. 不以反复预热掩盖冷启动，不增大30秒预算，不在持续上传期间每次预算耗尽后无限重试。当前并发读快照升级会因写入而失败，是诚实保留旧摘要的既有机制，不应简单吞错或删除dirty。
5. 50台、成熟库、24小时、语音并行压测、NAS断线恢复仍按原T5门槛，未通过项不能关闭。
