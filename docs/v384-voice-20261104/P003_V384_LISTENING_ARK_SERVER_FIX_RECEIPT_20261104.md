## 2. 两处根因与改动

### H1：正确识别但回答“暂时查不到”

实际 Worker 把问题提交为前一段“请问 方舟里的补勤卡”和后一段“有什么用”；前段被打断，未播出正文。原静态用途路由未覆盖这类省略资源名的追问，且当轮知识召回仅匹配当前段；后一段因此未走固定用途答复，转入普通模型。这不是库存缺失，也不是本轮 ASR 把“补勤卡”识别错。

修复后，短用途追问可以继承最近一条用户消息里唯一、明确的方舟资源。在身份、设备范围及有限直答门满足时，完整问句和这种拆句均能返回已核实用途，例如：

> 补勤卡用于符合条件的历史航线节点补签，补签后的奖励还需按设备页面提示领取。

只承接明确上下文；已覆盖的换题、引用、外部游戏、多资源和明确否定用例不继承。未走有限直答时同源知识仍可召回，这不代表任意模型输出已获得确定性保证。用途回答与实时库存隔离，不能拿未知余额当0，也不因用途问句虚构数量。历史完整HTTP请求正文未留存，本次根因由实际Worker提交顺序、固定旧源码行为和隔离重现共同支持。

### L1：识别正确却没有 exit proposal

失败 trace：`d25125e7-ce8d-4ff4-8c47-1f8431ed4936`。

真实 Worker 已收到“恢复聊天”“结束倾听恢复聊天”“小可结束倾听”。旧解析器只接受更窄的完整口令，这些句子都未匹配退出分支。当时对应退出时刻均被有效续租覆盖，不能归因于15秒授权过期。

修复后，在已授权、具备语音控制能力的倾听/反馈状态中，支持上述短口令及“退出倾听模式”“恢复普通聊天”等明确整句。普通聊天不会把短句直接当倾听控制；引用和叙述等负例保留。

仍走原协议：可信 `listening.proposal` → 客户端发送关联的退出请求 → 匹配 request_id/seq 的 `completed(normal)` → 恢复同房普通对话。服务端不会跳过客户端确认自行宣布页面已退出。准备反馈或正在反馈时退出，也会撤销旧反馈的播放许可。
