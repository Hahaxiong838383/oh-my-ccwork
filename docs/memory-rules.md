# Memory Rules v1.0

> 记忆系统规则规范。用途：brain post-hook prompt / Air CLAUDE.md include。
> 单一真相源，版本化管理。

## 1. 摄入规则（六维度扫描）

提取记忆前，用以下 6 个维度扫描对话内容，确保不遗漏：

| 维度 | 提取什么 | 写入命名空间 | 示例 |
|------|---------|------------|------|
| ① 个人信息 | 用户身份、角色、硬件、习惯的新发现 | `[user/基本]` `[user/偏好]` | `- ★★ 川哥主力机是 MacBook Air M3 [2026-03-10] #硬件` |
| ② 偏好变更 | 用户表达的偏好、工作风格、沟通方式变化 | `[user/偏好]` `[user/方法论]` | `- ★★ 用户偏好「够用就行，先跑起来再迭代」的工作风格 [2026-03-15] #工作风格` |
| ③ 事件事实 | 部署、配置、Bug 修复等技术事实 | `[project/*]` 对应类别 | `- ★★ mycc 后端端口从 18080 改为 19080 [2026-03-20] #端口` |
| ④ 时间数据 | 有时效性的安排、截止日期、里程碑 | 加 `[event:YYYY-MM-DD]` 标签 | `- ★★ OpenSpace MCP 7天检查点 [2026-03-30] [event:2026-04-06] #里程碑` |
| ⑤ 更新/修正 | 与已有 Item 矛盾或补充的信息 | 触发矛盾检测（见第 3 节） | `- ★★ Δ FRP 端口改为 22022（原 22021）[2026-03-25] →Δ:cc-remote-V4 #cc-remote` |
| ⑥ 助手信息 | 助手自身的能力变化、踩坑教训、skill 经验 | `[agent/技能]` `[agent/踩坑]` | `- ★★ Node.js fetch() 网络错误真实原因在 error.cause 里 [2026-03-18] #踩坑` |

**叶子原则**：每条 Item 只写一个独立事实，不含推论或多个并列事实。

**质量判定**：提取 Item 时自问——"如果只看这条 Item，下次遇到同样场景能直接复用吗？" 如果不能，说明丢了关键信息。

**不要凑数**：六维度是 checklist 不是模板——没有新发现的维度直接跳过，不写无价值的 Item。

## 2. 存储格式

### 2.1 命名空间

| 命名空间 | 范围 | 典型类别 |
|---------|------|---------|
| `[user/*]` | 跨项目通用 | `[user/基本]` `[user/偏好]` `[user/方法论]` `[user/topOfMind]` |
| `[project/*]` | 项目专属 | `[project/技术-飞书]` `[project/配置-mycc后端]` `[project/Bug-Fix]` 等 |
| `[agent/*]` | 助手自身 | `[agent/技能]` `[agent/踩坑]` |

### 2.2 Item 格式

```
- ★★ 内容描述 [YYYY-MM-DD] #tag
```

- `★` 数量表示重要性：`★` = 低价值，`★★` = 常规（默认），`★★★` = 关键事实
- `[YYYY-MM-DD]` 为写入日期（必填）
- `#tag` 为主题标签，用于矛盾检测和版本链关联

### 2.3 双时间戳

- `[YYYY-MM-DD]` — 写入日期（必填）
- `[event:YYYY-MM-DD]` — 事件发生日期（可选，用于有时效性的事项）

示例：
```
- ★★ 产品 Demo 日 [2026-04-01] [event:2026-04-15] #里程碑
```

### 2.4 版本链（#base / Δ / supersedes）

通过版本链管理同一主题的信息演变，保留历史而非覆盖：

**三个标记**：
- `#base` — 基线事实，该主题最稳定的核心信息
- `→Δ:基线关键词` — 增量修正，相对于基线的变化部分
- `→supersedes:基线关键词` — 完全重写（仅当基线本身已错误/过时时使用）

**规则**：
1. 一个主题首次写入时正常写，不需要任何标记
2. 同一主题第二次变更时，把原条目标为 `#base`，新增的写 `→Δ:基线关键词`
3. 增量（Δ）可堆叠：多次小变更各自独立记录
4. 增量堆叠 ≥3 条时，触发重建基线：合并所有 Δ 到新 #base，清除旧 Δ
5. `→supersedes:` 是核弹选项：旧基线 + 所有 Δ 全部废弃，仅当根本性变化时使用

**格式示例**：
```markdown
- ★★★ cc-remote V4：阿里云香港 FRP 中转，域名 cli4.hahaxiong.cc [2026-03-15] #base #cc-remote
- ★★ Δ 修复 WebSocket 重连超时 [2026-03-20] →Δ:cc-remote-V4 #cc-remote
- ★★ Δ deploy-user.sh 改为两步写配置（先 HTTP 再 SSL）[2026-03-26] →Δ:cc-remote-V4 #cc-remote
```

## 3. 矛盾检测（三步法）

写入新 Item 前，必须对同类别已有 Item 做冲突扫描：

### 步骤

1. **同主题定位**：扫描目标类别中含相同 `#tag` 或相似关键词的已有 Item
2. **矛盾判定**：新旧 Item 描述同一主题但结论不同（端口/路径/版本/方案/状态变化）
3. **自动处理**：

| 情况 | 处理方式 |
|------|---------|
| 矛盾 + 旧无 `#base` | 删除旧 Item，写入新 Item |
| 矛盾 + 旧有 `#base` | 新写为 `→supersedes:`，旧基线及 Δ 全删 |
| 补充（非矛盾） | 新写为 `→Δ:基线关键词` |
| 无关 | 正常写入 |

### 判定标准（避免误杀）

- 同一 `#tag` + 同一主题实体 + 结论不同 → **矛盾**
- 同一 `#tag` + 不同主题实体 → **无关**（如两个不同服务都有 `#端口`，不矛盾）
- 不确定时保留两者，在新 Item 加 `[?conflict]` 标记供人工确认

## 4. 遗忘与巩固

### 遗忘规则

| 条件 | 处理 |
|------|------|
| eventDate 过期 >7 天 | 删除 |
| 写入 >90 天且 ★<3 | 归档到 `memory-archive.md` |
| 写入 >120 天 | 无条件归档 |

### Δ 自动巩固（基线重建）

当同一 `#base` 下的 `→Δ:` 条目 ≥ 3 条时，触发基线重建：

- 将 #base + 所有 Δ 合并为新的 #base（保留最新信息）
- 删除旧的 #base 和所有已合并的 Δ 条目
- 新 #base 的星级 = 旧基线星级（不变）
- 新 #base 的日期 = 当天（刷新写入日期）
- 合并时保留所有具体值（路径/端口/版本号），丢弃过程性描述

## 5. 失真预算

每层信息压缩都有明确的质量标准，确保关键信息不丢失。

### Resource → Item（流水账 → 结构化事实）

| 必须保留（≥95%） | 允许丢弃 |
|------------------|---------|
| 决策结论（做了什么、选了什么方案） | 时间修辞（"先...然后...最后"） |
| 关键参数（端口、路径、版本号） | 中间调试过程 |
| 因果关系（为什么这样做） | 情绪表达 |
| 失败教训（踩了什么坑） | 重复确认对话 |

### Item → Category（事实条目 → 高层索引）

| 必须保留（≥80%） | 允许丢弃 |
|------------------|---------|
| 主题存在性（"有这个东西"） | 具体参数值 |
| 位置指针（"去哪里找"） | 实现细节 |
| 当前状态（运行中/已废弃） | 历史变更过程 |

### 违反预算的信号

下次对话问"上次那个 XXX 怎么配的"却找不到 → 说明 Resource→Item 转换丢了关键信息，需要补提取。

## 6. 因果关联标记（可选）

当 Item 之间存在明确的因果关系时，可用以下标记建立关联：

| 标记 | 含义 | 示例 |
|------|------|------|
| `→caused:X` | 本条导致了 X 的产生 | 发现 bug → 导致修复方案 |
| `←caused-by:X` | 本条由 X 触发 | 修复方案 ← 由 bug 触发 |
| `→evolved:X` | 本条演化为 X | 旧方案 → 演化为新方案 |

**写入规则**：
1. 因果关联**可选**，仅在关系明确时标注（不强制每条都关联）
2. 优先标注跨类别的因果链（如 Bug-Fix → 配置变更 → 性能改善）

## 7. LLM 输出 JSON Schema

LLM 提取事实时的标准输出格式：

```json
{
  "facts": [
    {
      "namespace": "project/技术-飞书",
      "content": "飞书卡片消息最大字数 30000",
      "keywords": ["飞书", "卡片", "字数限制"],
      "dimension": "事件事实",
      "tags": ["飞书卡片"],
      "star": 2
    }
  ],
  "skip_reason": null
}
```

**字段说明**：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `namespace` | string | 是 | 命名空间路径，如 `user/偏好`、`project/技术-飞书`、`agent/踩坑` |
| `content` | string | 是 | 单条原子事实，遵守叶子原则 |
| `keywords` | string[] | 是 | 用于矛盾检测和检索的关键词（2-5 个） |
| `dimension` | string | 是 | 六维度之一：`个人信息` / `偏好变更` / `事件事实` / `时间数据` / `更新/修正` / `助手信息` |
| `tags` | string[] | 是 | 主题标签，对应 Item 格式中的 `#tag` |
| `star` | number | 是 | 重要性：1=低价值，2=常规（默认），3=关键事实 |
| `event_date` | string | 否 | 事件日期 `YYYY-MM-DD`，仅时间数据维度使用 |
| `base_ref` | string | 否 | 版本链引用，填写时表示 `→Δ:` 或 `→supersedes:` 的目标基线关键词 |
| `version_type` | string | 否 | `delta` 或 `supersedes`，与 `base_ref` 配合使用 |

**规则**：
- `facts` 为空数组时必须给 `skip_reason`（说明为什么本次对话无可提取事实）
- `star` 默认 2（★★），1=低价值，3=关键事实
- `dimension` 必须是六维度之一的中文名
- `content` 必须是自包含的完整句子，不依赖上下文即可理解
