## gemini（产品节奏）

在 Demo/原型阶段，**「过早优化基础设施」是产品开发的头号杀手。** 你的 7575 字手册对于现代 LLM（尤其是 Gemini 1.5 Pro/Flash）来说，仅占 Context Window 的极小部分，连 RAG 都不是必须，直接塞 System Prompt 才是性能上限。

以下是针对评审问题的深度回答：

### 1. cc「先接入手册」对吗？有没有低估「早建基础设施」的长期复利？

**cc 是对的。你没有低估复利，反而是规避了「伪需求复利」。**

*   **架构是为了解决痛点，而非完成愿景：** 基础设施的「复利」只有在规模化阶段（Lore > 100万字、实体关系 > 1000个、QPS > 100）才会产生。在 Demo 阶段，你的痛点是「小可不知道世界观」，方案 A 只需 1 小时配置就能验证「知道后话术是否变丰富」。
*   **迁移成本误区：** 将结构良好的手册（Markdown）迁移到 KG 或向量数据库的成本极低。反之，如果你先建了 KG，但后来发现小可与 Lore 的交互更多是「情感共鸣」而非「实体检索」，那你辛苦建的关系拓扑就是无用功，那才是巨大的「负资产」。
*   **阶段匹配原则：** 现在的核心目标是**验证「知识能提升用户体验」这个假设**，而不是验证「我能写出复杂的记忆路由」。

### 2. 何时从「塞 Prompt」升级到「分层记忆」？（定量/定性阈值）

当满足以下任意 **2 条** 信号时，启动基础设施建设（方案 B）：

*   **Lore 体量突破阈值：** 纯文本超过 **10 万字**。此时即使 Context 塞得下，模型对中间内容的注意力（Lost in the Middle）也会下降，且 Token 成本开始让老板心疼。
*   **推理深度崩溃（Reasoning Collapse）：** 用户开始问「A 的父亲的战友留下的那个宝箱在哪？」。如果小可在 Context 里绕晕了，说明需要 **Knowledge Graph** 处理多跳关系。
*   **知识更新频率（Volatility）：** 世界观不再是「静态圣经」，而是随玩家行为动态演进（如：生态缸里新长出了一棵树，所有角色都要知道）。**实时性需求**是向量库/结构化层接入的强信号。
*   **工程性能瓶颈：** API 响应时间由于注入了超长 Prompt 导致 TTFT（首字延迟）超过 **5 秒**，或单次对话成本超过 **0.1 元**。

### 3. 如何设计 A 方案，才能为将来升级铺路？

不要只是把 7000 字当成一大段文本塞进去。要用 **「手册即代码 (Manual as Resource)」** 的思维来写：

*   **高度结构化（Markdown 规范）：** 必须使用严格的 `#` 层级。
    *   `# Entity: Xiao Ke`
    *   `## Relations: [Friend of Player, Guardian of Oasis]`
    *   `## Attributes: { "Tone": "Playful", "Energy": 80 }`
    *   这种格式，未来跑一个 Python 脚本就能一键 Ingest 到 GraphDB 或 VectorDB。
*   **唯一标识符（Identifier Injection）：** 对关键地点、道具、角色使用统一的名称。不要一会儿叫「专注夜航」，一会儿叫「夜间专注」。
*   **路由占位符：** 在代码层面，不要直接拼接 Prompt，而是封装一个 `KnowledgeEngine.get_context(scene_id)`。现在这个函数返回手册全文，未来它可以变成 RAG 的查询入口。**接口保持不变，后端平滑切换。**
*   **真实性边界明确化：** 手册中必须明确哪些是「死知识」（不可更改的世界观），哪些是「活状态」（玩家进度）。在 Prompt 注入时，物理隔离这两个 Block。

### 结论
**立即执行方案 A。** 用 20% 的努力解决 80% 的「话术重复」问题。把剩下的 80% 精力放在打磨小可的**性格颗粒度**上，那才是 KidsHub-AI 的灵魂，而不是那个暂时还用不上的分层记忆引擎。

## grok（第一性原理）
**架构决策评审：先接入手册（A）是正确的第一性选择。** cc 的初判成立，且从本质上讲判断精准。以下从第一性原理直接回答 3 个问题，给出结论 + 推理链。所有判断基于当前 KidsHub-AI 实际状态（纯前端组装 prompt + WS 下发 + gemini 直调、global prompt 仅 1 段极简世界观 + device_state mock + 已实现的 fact pool + framing layer、手册 7575 字尚未接入）。

### 本质拆解（第一性原理）
当前瓶颈是**知识可得性（availability）**，而非**知识结构化推理能力（structured multi-hop reasoning）**。

- 小可的生成分布条件熵极低：输入侧世界知识 ≈ 1 段高抽象 + 少数几条 mock 事实（即使加了池化和 framing）。无论 framing operator 选“现象邀请”还是“归因充能”，它能合法操作的 payload 就那么点。听起来像“录音”或“轮换背诵”，根源是“知道的事”太少，不是“对已知的事不会多角度组织”。
- 分层混合记忆（KG + 向量 + 结构化 + 情景 + 编排）解决的是**知识海量后的可追溯、可归因、多跳一致性问题**（从 100 到 1000+）。它在知识为 0 或极小时几乎不产生增量价值，反而增加系统复杂度和延迟。
- 游戏 lore 的确高度关系化 + 静态圣经 + 动态状态并存，调研的终态方向正确。但**复利只在知识量级 + 查询复杂度 + 跨会话连贯需求同时满足时才真正启动**。demo 阶段强行上全栈 = 经典过早优化（YAGNI），同时把验证“懂世界观 → 话术变丰富”这个最关键的 0→1 假设推迟数周。
- cc 的“瓶颈是有无、非结构化推理”论断成立。没有反例能推翻：当前所有重复案例（夜航呼唤、回归承接等）都是因为可引用的事实母题单一，手册没给之前 framing 再高级也只能在同一贫瘠集合上采样。

早建基础设施在 demo 阶段是**净负债**：沉没成本（多存储同步、检索编排、调试工具、延迟掩盖）、迁移摩擦（双写期、prompt 形态和结构化形态不一致导致的幻觉回归）、以及最危险的“假设未验证就重度投资”。

### 1. cc「先接入手册」对吗？有没有低估「早建基础设施」的长期复利或迁移成本？

**结论：cc 完全正确。低估风险很小，反而早建的长期复利被严重高估，迁移成本被严重低估。**

推理链：
- 手册本身已经是“未来友好”的 ingest 原料：10 节结构（世界观核心不变量 / 角色 / 速查表 / 真实性边界） + 明确区分“世界里有这些东西/机制” vs “此刻数值/变化走 device_state”。这比一团 unstructured 文本好拆实体、关系、规则、约束。
- 把 L1 核心常驻 + L2 按场景/速查表路由注入 prompt，正是把静态 lore 做成“权威只读层”的正确中间态。将来上 KG 时，这份手册 + 实际运行日志（哪些 lore 被频繁引用、哪些 framing 有效）就是最好的 seed 数据和 eval set，不会“白做”。
- 晚建的“绑定成本”主要表现为“prompt 里散落知识引用”。通过下面第 3 点说的模块化注入 + source tagging + 版本化，这个成本是可控且低的。真正的绑定是“把 lore 硬编码到 scene example 或全局模板死区”，而当前架构（compose + variables + framing）已经天然反对这种硬编码。
- 早建的真实代价：要同时维护 prompt 形态（当前权威）和结构化存储形态（未来权威），同步 device_state（实时）+ 手册（静态）+ 会话情景。demo 阶段每次改 lore 都要双侧更新，PM 调试成本指数上升。等验证失败（或部分失败），就是数周打水漂 + 重写 ingest pipeline。
- 反例：很多游戏/叙事 AI 项目在 lore 只有几千字时就上 GraphRAG/Letta 类系统，结果是检索噪音大、幻觉归因反而变难、PM 完全看不懂“为什么这次小可这么答”。等真正海量 lore 上线时，早期仓促建的 schema 往往要推倒重来。

调研给的是“正确终态形状”，不是“现在必须一次性建成”。跳过轻量验证直接跳终态，是典型的“为远期架构服务当前 demo”的反模式。

### 2. 决定「何时从塞 prompt 升级到分层记忆」的触发条件/信号是什么？给可判断的定量阈值。

**结论：必须用多信号 AND 触发，而非单一指标。核心是“flat context + 当前注入方式已经系统性失效”，而非“lore 看起来够复杂了”。**

推荐可落地的判断阈值（按优先级排序，建议在 KidsHub 工作台里加埋点 + PM 定期人工评测）：

| 信号维度 | 定量阈值（建议） | 判断方法 | 为什么这个值 |
|----------|------------------|----------|-------------|
| 静态 lore 规模 | 手册 + 后续扩展 > 12k-15k 有效字符（~4k-5k tokens 核心内容），或可提取实体 > 80-100 + 平均关系密度 >2.5 | 手册版本 + 简单实体抽取脚本计数 | 超过这个量，单次 assembled prompt 开始吃紧，截断风险上升，L1/L2 静态注入的维护成本变高 |
| 场景/玩法覆盖失败率 | PM 盲评或用户测试中，“因缺少世界知识导致只能打太极/泛泛而谈/拒绝展开”的比例连续 1-2 周 >25% | 工作台里加“知识不足”标记 + 定期导出评测集 | 直接度量“有无知识”的业务影响，比字数更准 |
| 查询类型分布（多跳/跨节关联） | 需要跨 3+ 手册节进行关联推理的 query 占比 >15-20%（连续采样 50-100 条真实/测试对话） | 简单分类或人工标注（“藏品机制 + 生态缸演变 + 新手光环联动”这类） | 这是结构化推理真正有价值的场景；低于这个比例，section 路由 + framing 就够 |
| 上下文压力 + 一致性失效 | 单次 prompt 经常 >8k-10k tokens（接近模型有效上限），或出现“手册内容被截断导致遗漏/幻觉”的可观测 case >5% | prompt 长度监控 + debug 流关键词匹配 | 这是工程硬约束信号 |
| 产品真实信号 | 真实设备上线后，跨天/跨周连贯回忆需求显著上升（“你上次说的那个机械恐龙后来...”“光环机制和昨晚夜航收益有关系吗”），且 retention 数据把“世界一致性”列为 top 变量 | 真实日志 + 留存分析 | demo 阶段这个信号天然弱，但一旦出现就是最强的升级信号 |

**额外规则**：任何单一阈值触发都只算“观察期”。必须 2 个以上核心信号同时满足 + 团队共识（尤其是产品负责人）才能启动分层记忆项目。否则继续在 prompt 层做“轻量结构化”（实体速查表、场景-子节映射、规则约束 JSON）。

### 3. 若先接入手册，怎么设计才能「不浪费、为将来升级铺路」？

**结论：现在就把“手册 = 独立、模块化、可路由的静态 lore 层”做对，prompt 注入只做薄薄的一层选择 + 声明，而不是把内容融进全局模板或场景卡。**

具体现在就该做对的事（按实施顺序）：

1. **手册保持独立 source of truth**：docs/12-小可世界观知识手册.md（或导出为结构化版）是唯一权威。不要把大段文字复制进 scene-cards.ts 或 global-prompt.ts。接入时只做“引用 + 版本”。

2. **Prompt 里显式分区 + 元数据声明**（最重要护栏）：
   - 新增 lore 变量或直接在 global 尾部/ addendum 前注入三个块：
     - 【小可世界观知识手册 - 核心（常驻）】：世界观核心 + 能量因果链 + 三句信念 + 真实性边界 + 红线。
     - 【小可世界观知识手册 - 场景素材（本轮）】：按当前 card + 速查表静态映射挑选 1-3 个相关 subsection（藏品、生态缸演变、新手引导回忆锚点等）。
     - 【小可世界观知识手册 - 边界与速查】。
   - 每块开头必须声明：“以下内容来自《小可世界观知识手册 vX》，仅用于理解世界里存在什么机制和素材。任何实时数值、今日/此刻变化、已锁定收益必须严格来自 device_state。冲突时以《小可 AI 产品定义》为准。绝不编造未在 device_state 里出现的事实。”
   - 这条声明本身就是未来迁移到结构化层时的“契约”。

3. **注入机制模块化（为将来检索/路由铺路）**：
   - 在 compose.ts / store 里增加 `loreContext`（或扩展 variables）。
   - 用现有速查表（九、可聊素材速查表）做**静态路由表**：card2/3/6 → 夜航 + 生态缸 + 藏品 subsection；card4 → 新手成长线 + 回忆锚点等。
   - framing 层保持正交：手册提供“能合法聊什么”，framing 决定“这次用什么角度组织”。
   - 每张卡进入时，除了 fact sampling + pickFreshAngle，还要 pick 一次 lore subsection（可记录最近用过的，避免连续重复同一块手册内容）。

4. **轻量实体/关系准备（零额外 infra）**：
   - 手册里关键实体第一次出现时规范命名（方舟、小可、光灵、生态缸、星尘/家族币、三色光环、藏品-探险家宝库/星梦奇境 等）。
   - 可选：单独维护一个小 `lore-entities.json`（id、canonical_name、type、核心属性、允许在哪些场景被主动提起），供未来 KG 抽取直接复用。当前只用于 prompt 里的“精确引用”提示。
   - 速查表已经是极好的“场景 → 素材”映射，保留并扩展它。

5. **版本 + 可观测 + 变更友好**：
   - 手册带版本号，注入 prompt 时带 `lore_version: v0.2`。
   - 工作台右栏增加“世界观知识注入预览”区（类似当前 device_state 现实片段），PM 能一眼看到本次到底塞了手册的哪几节。
   - 所有 lore 变更走 PR + 手册 diff，prompt 组装时可打印被注入的 subsection 列表进 debug 流。

6. **不要做的事（避免将来推倒）**：
   - 不要把整本手册硬塞进 global prompt 常驻。
   - 不要在 scenePrompt 示例或 addendum 里写死具体 lore 句子。
   - 不要现在就引入向量检索或 KG schema（除非你愿意为 demo 阶段的噪音和双维护成本买单）。
   - 保持“手册 = 静态只读世界存在层”和“device_state + confirmed_memories = 动态已锁定事实层”严格分离。

**接入后立即验证**：用手册 L1/L2 后，连点高风险卡 10-20 次，人工或简单多样性指标（语义 embedding 距离 + PM 主观丰富度）对比前后。成立则继续迭代轻量路由；不成立则先回退手册范围或调整 framing，而不是怪“知识不够结构化”。

### 最终推荐
坚定执行 **A**：本周内把 7575 字手册按上述模块化方式接入 KidsHub 工作台（L1 常驻核心 + L2 场景路由 + 明确边界声明 + 预览区）。跑通假设验证。把 cc 调研里提到的终态架构当“北极星文档”而非当前 sprint backlog。

这不是保守，这是工程第一性：**在知识为 0 时，先解决“有无”；在知识量到需要结构化治理时，再解决“如何组织”。** 顺序反了，复利永远到不了。
