## 3. 接口与显示口径

| 调用方 | 接口 | 身份 |
|---|---|---|
| 安卓状态/使用时长 | `POST /v1/device/telemetry` | 原Device Bearer，SN取鉴权身份 |
| 安卓方舟快照 | `POST /v1/device/ark/state` | 原Device Bearer |
| 小程序 | `GET /v1/parent/devices/dev_50b5415662259045/dashboard?timezone=Asia/Shanghai` | 当前登录家长Bearer |

**小程序字段映射：**

| 页面数据 | 接口字段 | 显示与核验规则 |
|---|---|---|
| 家族币 | `data.ark.wallets.family_coin` | 先看ark.available；不可用或该字段null显示暂无数据，真实0显示0 |
| 星尘 | `data.ark.wallets.stardust` | 同上；不得与家族币混用 |
| 补勤卡 | `data.ark.inventory["M-CARD-001"]` | 同上；单位张 |
| 资产更新时间 | `data.ark.captured_at_ms`、`received_at_ms` | 分别为采样和接收时间；显示上次同步，不称实时余额 |
| 今日设备使用时长 | `data.usage.today.focus_minutes` | 先看同层available；缺测null，不能拿旧data.today.focus_minutes的默认0兜底 |
| 近7日使用时长 | `data.usage.daily[]` | 7个北京时间自然日，每日独立date/available/focus_minutes/updated_at_ms；未测日不补假0 |
| 亮度、开盖、有人 | `data.device.brightness_level/lid_open/present` | 与当前有效状态快照核对；null不当false或0 |
| 最近状态上报 | `data.device.updated_at_ms` | 采样时间最新快照的首次接收时间；晚到旧快照不替代最新状态；与使用时长及资产时间独立 |
| 近期上报状态 | `data.device.online` | 沿用最近10分钟状态快照规则；不等于真人在位或网络探活 |

使用时长口径：开盖＋摄像头真实有人＋MCU状态可用，含普通游戏、设置和聊天，**不要求进入“专注模式”**。事件名沿用focus_segment，但页面不据此宣称学习质量或全天完整时长。分钟按有效片段的毫秒总和四舍五入，不是先逐段取整再相加。

资产只展示当前有效授权下的最新normal快照。授权后新unknown/gm快照被成功接收并成为当前快照时，dashboard返回`ark.available=false`、`reason=non_normal`，资产和source_mode等元数据为null；不能期待小程序接口直接回显unknown。没有有效当前快照时为`reason=no_snapshot`；不能凭端侧说unknown就预设云端已收到。normal中的单字段null仍是未知，不补0。

若资产不可用的reason是`not_enabled`或`identity_mismatch`，由服务端核范围、总闸、当前身份和grant，不当成unknown存档空态通过。

按客户端《P003_mini008_服务器联调准备回执_20261111.md》的实现约定，开盖有人时5分钟状态心跳，其他情况30分钟；本轮还需观察实机是否实际执行。不开盖/无人时可能出现`online=false`但设备仍联网，不能仅据此判定断网。使用时间和资产时间也不能用状态心跳代替。

## 4. 按顺序执行的真人用例

### T01：身份、登录和页面基线（约3分钟）

1. 安卓记录实际mini版本、SN、六服务状态、pending，以及当前存档source_mode。服务端核原owner和epoch，不要求导出凭据。
2. A登录小程序，从自己的设备列表进入C对应页面。小程序同事保存一次dashboard响应及截图，记录页面版本和入口。
3. 服务端记录测试前最新状态、有效focus基线、Ark current。若Ark无快照或unknown，页面显示暂无数据可以通过空态基线，不能判资产功能失败。

**通过：**身份/public_id/原归属一致，A可读；接口值和页面空态一致。后续所有用例都与这个基线比较，不预设初始余额或时长为0。

### T02：两次真实状态变化＋两个心跳（约10–12分钟，可与T03并行）

1. 真人调亮度到一个与当前不同的值，记CST操作时间和设备实际值。
2. 等该变化的真实新snapshot收到业务ACK后，小程序手动刷新，服务端核入库记录，再比对页面。**第一轮完整对账后**再改第二个不同亮度，避免被正常合批合并。
3. 保持开盖有人，观察两个正常5分钟状态心跳：使用不同snapshot_id，接收时间前进，页面最近上报相应更新。

**记录：**两次变化和两次心跳各自的snapshot_id、采样/接收毫秒、上传请求标识、业务ACK、dashboard请求标识及截图。

**通过：**设备值→上传→库中该快照→dashboard→页面一致；重放旧snapshot不冒充新心跳。dashboard目前不返回状态snapshot_id，服务端用该ID定位库记录，再按值及`data.device.updated_at_ms`对照，不能编造页面字段。

### T03：真人在位使用、离座/合盖暂停（约5–8分钟）

1. 记录基线后开盖、保持真人在摄像头有效范围内；正常浏览、游戏或设置均可，持续至少两分钟，实际取得两个已完成的约60秒非重叠片段。
2. 安卓确认这两段进入上传队列并取得业务ACK。服务端按event_id核有效起止、首次接收时间及日汇总；小程序刷新查看今日与近7日。
3. 真人离座或合盖，安卓记录识别到暂停的实际状态时间与补尾事件；待已产生的尾段/积压送完后继续观察约两分钟，确认没有新的在位片段增长。

**通过：**新增有效片段的起止与真实状态相符；增量按实际accepted片段计算，无重叠或重复累加。页面分钟与总毫秒四舍五入结果一致；暂停后允许已有尾段晚到，不能把补传当成“仍在计时”。缺测日保持null；合法短段可能显示0分钟且available=true。

### T04：家族币、星尘、补勤卡（有normal存档时执行，约5分钟起）

1. 安卓确认当前真实存档为normal且采样时间晚于本轮授权时间。若仍unknown/gm，只执行T06空态，把本项标记“待合格normal存档”，不清档、不改来源标签。
2. 记录真实Runtime投影的家族币、星尘、补勤卡三字段，以及设备界面实际显示值；取得一份新Ark快照的业务ACK。
3. 服务端按snapshot_id/sequence核库；小程序刷新核三字段与更新时间。normal中的null按未知显示，不能为凑通过改成0。
4. 通过产品正常允许的领取或消耗产生一次真实资源变化，再按同样链路复核。没有可用的正常变化操作就标记该子项待验，不用GM或改库制造。

**通过：**当前normal快照三字段逐项一致；至少一次正常资源变化能够同步。实际出现真实0时额外核页面显示0；没有真实0样本，保留该子项未验。

### T05：队列与重复（先观察；主动断网恢复可另约）

1. 记录已有pending、上传批次及ACK，检查正常上传后按同ID结算。响应`snapshot:null`表示events-only，属于合法情况；请求不含状态时应省略snapshot。
2. 若自然重试出现duplicate，核相同ID未重复计入时长，重复ACK可使队列正确结算。没有出现重复就记“未观察到”，不发伪造事件。
3. 若现场另做短时断网恢复，先记起止和原队列，恢复后按原ID核重试与出队；不清队列、不重装。此扩展不是第一轮页面联调的前置。

**通过：**观察到的队列/ACK与服务端结果一致，不能用pending=0代替单条业务验收。未执行的离线/重复场景不得标PASS。

### T06：未知与零、A/B隔离（约3–5分钟）

1. 用C真实unknown状态核资产显示暂无数据；使用缺测日也显示暂无数据。没有该状态样本则保留相应子项待验。
2. B用自己的有效登录token请求C的同一dashboard，应返回HTTP404及`error=not_found`。B自己的设备列表不包含C。
3. 小程序A→B→A切换，B页面不得残留A的资产/时长；切回A后重新请求，显示A最新数据。测试期间不发绑定请求、不改变owner。
4. 若有normal真实0或已上传短使用片段四舍五入为0，验证0能正常显示；与null的空态分开。

**通过：**同接口隔离与页面缓存均正确。B若返回401，先解决B登录有效性，不能把401当作权限隔离通过。

## 5. 对账时必须保存什么

一次上传只记录一条简明链路：**设备ID/数据ID＋采样时间 → 上传HTTP和业务ACK → 数据库记录 → dashboard响应 → 页面截图**。

安卓上传RID和小程序读取RID通常不同；它们不是同一个请求。服务端用同设备、数据ID和采样/接收时间关联，不强求两个RID相同。旧日志若无RID，保留这一限制，按数据ID和CST缩小窗口。

| 通道 | 必记业务ACK |
|---|---|
| Telemetry | `ok`、`data.batch_id`、`data.snapshot.accepted`、`data.snapshot.duplicated`（或data.snapshot:null）、`data.acked_event_ids`、`data.duplicated_event_ids`、`data.rejected`、`data.server_received_ms` |
| Ark | `ok`、`status=accepted/duplicate`、`received_at_ms`；另记请求里的snapshot_id/sequence/source_mode |
| dashboard | HTTP、`ok`、data.device、data.usage、data.ark及本次读取时间；保留实际页面对应截图 |

Telemetry快照重放可同时返回`data.snapshot.accepted=true`和`data.snapshot.duplicated=true`，这两个布尔值不是互斥状态；表示已确认该ID，但没有新增一份快照。事件的重复则看`data.duplicated_event_ids`，不要混用两种ACK。

日志使用现有工具采集即可，不要求临时开发新采集系统。提交日志前移除Authorization、短信码、完整手机号、Wi-Fi密码；不要把原始token发群。

## 6. 遇到异常怎么处理

| 现象 | 处理与责任 |
|---|---|
| Ark403 | 安卓保队列并按至少15分钟退避；服务端按完整ID/时间核scope、grant和当前鉴权身份，记录响应error；不要仅凭403判断凭据坏了 |
| Ark409 before_grant | 授权前快照可能触发；沿客户端既有处理，等待授权后真实新采样，不重新领证或清队列抢跑 |
| 其他409/400 | 保存实际error和请求的数据ID/字段类型，服务端定位stale/conflict或schema分支；不只报状态码 |
| Telemetry200但rejected非空 | 逐条记event_id/reason；其他accepted仍有效。核非法片段、重叠或同ID不同内容，不重生成ID掩盖冲突 |
| 401 | 沿现有登录/设备凭据流程排查；记录角色及时间，不输出token，不重绑 |
| 429/网络/5xx | 沿原重试与Retry-After策略，保留待发；不连续手点制造更多请求 |
| dashboard503 | 服务端查数据依赖；小程序显示暂不可用，不把故障渲染成余额0或空态验收通过 |
| ACK成功、页面没变 | 先比较同一次dashboard原始响应与页面；响应对而页面错由小程序查字段/缓存，响应也旧则由服务端与安卓按数据ID定位 |
| 亮度两次只见最后一次 | 若上一次尚未合批发送，可能是正常合并；按T02先完成一次ACK和页面对账再执行第二次 |
