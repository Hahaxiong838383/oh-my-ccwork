## 3. 自动登记的身份依据：工程师需要核清这一处

**自动化不等于“任何登录用户自报一个SN和公钥就能占用这个SN”。** 设备自己生成的签名证明它持有私钥；单靠这个签名不能证明自报SN属于真实厂商设备。

本次建议使用“自动签发的设备身份凭证”，把完整SN、key_id、公钥指纹与签发方绑定。小程序只转发可公开的身份凭证；后台核签发来源后再接纳该公钥。无需完整证书CA系统，也不把服务器签名密钥写进APK。

身份凭证应由下列已有可信流程自动取得，工程师先核现状，再冻结一种实际可用的来源：

| 设备现状 | 自动获取方式 | 使用边界 |
|---|---|---|
| 已持有服务器签发、仍有效且sub等于本机SN的设备凭据 | 设备直接向服务端认证，并证明持有该长期私钥，自动换取绑定SN及公钥的身份凭证；不经小程序传递业务Token | 可用于旧设备自动迁移；不能作为“完全无凭据首次开箱”的唯一方案 |
| 首次开箱、还没有设备业务凭据 | 在烧录/初始化/产测流程中，由受控工具自动获取绑定本机SN、公钥指纹的身份凭证并保存到设备；设备首次接入时自动携带 | 工具自动完成，不能退回工程师逐台复制公钥或手写台账；需核现有工具/发行链路是否已有该能力 |

**目前尚未核实C机存在上述任一可用来源。** 这一项由设备开发与服务端直接对齐，不要求川哥判断密码学方案。设备同事只需回报“现有来源/对应代码位置/是否需补开发”，不要把Token或私钥发进群。

如果C机尚无可信初始化材料，服务端与设备端须先补这条自动链路，再运行首次绑定；不能通过人工预录C来冒充通过。也不能让设备先领取绑定后才有的业务Token，再要求它用该Token申请第一次绑定。

## 4. 完整自动联调顺序

测试账号记为A，另一账号记为B；**C机是设备，不是测试账号C**。A/B沿用现有手机号登录，不要求改回微信手机号授权或新增第二套账号。

1. **服务端确认可测**：自动准入版本已部署、回滚记录齐全；C机没有因本轮人工创建台账/绑定。若已有真实owner，记录并沿原归属处理，不清绑定制造空白状态。
2. **小程序登录A并连接BLE**：自动读取本机SN、key_id、完整长期公钥、可信身份材料和协议能力。每次使用本轮会话材料，不重放11:12旧challenge。
3. **小程序自动申请挑战**：通过现有后台域名提交身份及会话材料。服务端先验证身份来源，生成账号/设备/公钥/本次BLE会话限定的短期挑战。挑战阶段只保存待验证记录，不提前占用永久owner或生成业务凭据。
4. **设备本机确认并签名**：小程序把服务端待签名原文传给设备；设备核对本机身份/会话，完成本地确认后签名；小程序转交签名，不自行重排签名原文。
5. **服务端自动完成登记与绑定**：确认签名及条件仍有效，事务内创建或幂等复用台账、公钥、策略及owner/版本/回执；并发请求不得覆盖他人owner或替换已登记公钥；停用、撤销或保留历史归属墓碑的设备不得当新设备自动恢复。Brain初始化作为可重试后续步骤。返回bound、binding_id、public_id、真实brain_state。
6. **配网与领证**：小程序显示“已绑定，待配网”并发送Wi-Fi设置。设备联网后自己claim，服务器签发业务凭据，设备解密、落盘并用该凭据认证。小程序回读到activated才显示已激活。Wi-Fi或领证失败保留原归属。
7. **首条真实数据与隔离**：设备产生一条实际亮度变化并上报；服务端按SN+snapshot_id核入库，小程序A刷新读到相同值与更新时间。切B后列表不含C机，直接请求C机详情不能读到A的数据。

新自动准入涉及challenge/confirm合同扩展或版本协商，当前v1请求严格限制字段，**不能直接往现役v1请求多塞公钥就认为已接通**。具体新增字段、签名字节与兼容方式由13/37同设备开发冻结后给正式接口合同。合同须绑定签发方、产品/用途、SN、公钥指纹、有效性及撤销规则；签名覆盖本次账号/声明摘要/BLE会话/领证材料/随机数与期限，自动登记使用明确的用途标识，避免跨协议复用。现有BLE每条JSON明文上限2024字节，新增公钥和紧凑身份声明须实测总包长；超限时明确材料分块与摘要校验，不假定已有传输分片支持无限消息。此文不虚构已经上线的新接口。

既有业务路径供对齐：

- Base URL：`https://kidshub-ai.hahaxiong.cc`
- 小程序：`POST /api/parent/ble-bindings/challenge`、`POST /api/parent/ble-bindings/confirm`、`GET /api/parent/ble-bindings/{binding_id}`；使用家长登录Token。
- 设备：`POST /v1/device/pairing/claim`；绑定后的设备凭据由该流程交付，小程序不代存。
- 真实数据：设备`POST /v1/device/telemetry`；小程序`GET /v1/parent/devices/{public_id}/dashboard`。

## 5. 怎么验收“确实自动”，而不是后台手动放行

| 用例 | 通过标准 |
|---|---|
| 首次自动接入 | 有可信初始化材料、此前未入台账的C机，经真实BLE/本机确认自动生成台账、公钥和归属；全程没有管理员手工登记动作 |
| 重试与断网恢复 | 同账号重复confirm/重试不重复建设备或Brain；Wi-Fi失败保留绑定，原账号恢复后可claim并认证 |
| 防冒认与归属保护 | 非可信签发、SN/公钥不匹配、无设备有效签名均被拒；B不能抢绑A的设备；相同SN不同key不自动覆盖；停用/撤销记录不被自动复活 |
| 凭据确实可用 | 设备保存凭据后真实认证通过，服务器activation_state=activated；只收到claim响应不算完成 |
| 最小真实数据闭环 | 实机状态、上传ACK、数据库行、小程序页面四处一致；B读不到 |
| 兼容与回滚 | 既有设备语音/上传/绑定保持；自动准入总闸关闭可阻止新增登记，已绑定设备仍能使用，不回灌整库或删除真实新归属 |

首轮只测正常链路、一次重试、跨账号隔离和最小必要负向用例；不扩大到全平台故障注入或完整PKI工程。
