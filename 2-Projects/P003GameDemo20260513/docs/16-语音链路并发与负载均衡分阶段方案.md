# P003 语音链路（ASR→LLM→TTS）并发与负载均衡分阶段方案 · v1

> 目标：为「小可」儿童语音 AI 设计务实、可演进的并发与负载均衡方案。
> 范围：**仅公司站演示版**（阿里云 HK 单服务器、Hono + ws、pm2 单进程）。
> 前提：严格基于现状事实（见 §现状），前一轮 codex 评审结论（15-账号体系与并发方案.md）已确认瓶颈不在 Node 本身。
> 定位：**15 的前瞻续篇**。15 解决 <50 原型生存；本文解决 50 → 数百 → 更多的分阶段路径 + 现在该埋的低成本扩展点。
> 日期：2026-06-15
> 署名：grok（xAI）设计 · cc（Claude）验收

---

## 现状事实（唯一真相源，勿臆测）

- **产品**：P003 KidsHub 儿童读写台语音 AI「小可」，公司站演示版。
- **后端**：Node.js（Hono + ws）单进程，pm2 跑在 1 台阿里云 HK 服务器。
- **语音链路**（每用户 1 条浏览器 WS 长连接 → 1 个 VoicePipeline 实例）：
  - ASR：火山引擎 BigModel 流式识别，每连接 1 条到火山的 WS，实时 PCM16 帧。
  - LLM：Gemini，走私有代理网关（OpenAI 兼容 SSE 流式），每轮对话 1 个流式 HTTP。
  - TTS：火山 Doubao 双向流，每轮 1 条到火山的 WS，流式分句合成。
- **现状（15 已盘点）**：无连接上限、无并发闸、无 LB、无 cluster、无背压保护。代码位置参考：`pipeline.ts`、`volc-asr.ts`、`volc-tts.ts`、`gemini-llm.ts`、`index.ts`。
- **已知瓶颈（15 codex 评审结论）**：50 并发下瓶颈在**外部 provider 配额**（火山 ASR/TTS 账号并发数 + Gemini 代理网关规格）+ **背压**（buffer 无上限/无超时/TTS 不主动 close），不在 Node 进程 CPU/内存。
- **当前目标**：<50 并发。产品要扩，账号持续增多（核心前瞻：50 → 数百 → 更多）。
- **硬约束**：原型/早期阶段，**绝不过度工程**；优先低成本、可分阶段演进；单台服务器起步。

**重要**：本方案所有结论都建立在「外部依赖是稀缺资源」这一第一性事实之上。Node 进程本身在 50 路时仍有余量。

## 1. 单进程内并发模型（保护外部 provider + 不误伤用户）

### 设计原则（第一性）
- 保护**最稀缺资源**（火山并发槽位 + Gemini 代理规格 + 按量计费成本），而不是保护 Node CPU。
- **分层而非单一数字**：全局 cap 防止 Node 事件循环被拖垮；各阶段 cap 直接映射外部 provider 硬配额。
- **背压必须有界 + 可观测**：无界 buffer = 50 路堆 48MB+（15 已量化）。
- **准入控制（admission）在入口**：WS upgrade 阶段就决定接不接，而不是让链路跑一半再 OOM/429。
- **用户体验优先**：超限时给友好提示（“小伙伴太多啦，稍等一下再试”），而不是静默失败或卡住。

### 推荐实现结构（单进程内）
```ts
// 概念模型（现在就该抽象，低成本）
type Stage = 'asr' | 'llm' | 'tts';
class ConcurrencyGate {
  // 全局（保护 Node 自身 + 总成本）
  private global = new Semaphore(40); // 初始值，压测后调

  // 分层（直接保护外部）
  private perStage = {
    asr: new Semaphore(30),   // 火山 ASR 并发
    llm: new Semaphore(25),   // Gemini 代理并发
    tts: new Semaphore(30),   // 火山 TTS 并发
  };

  // 每个 provider key/account 还可以再套一层细粒度（见 §2）
  async acquire(stage?: Stage): Promise<Release> { ... }
}
```

**每条 VoicePipeline 生命周期**：
- WS upgrade → 尝试 `gate.acquire()`（全局 + 可选 asr）
- 首轮对话：`asr.acquire()`（ASR WS 建立时） + `llm.acquire()`（每轮） + `tts.acquire()`（每轮 TTS WS）
- 结束或错误 → 立即 release（关键：TTS 必须在 `onSentenceEnd` / 错误后 `close()` 并 release）
- 连接级超时 + 空闲超时（15 已要求）。

### 背压与连接闸
- **ASR 侧**：`pendingBytes` / `pendingChunks` 上限（15 已提出），超限主动断 ASR WS + 回压浏览器端（readyState 检查或 pause 采集）。
- **TTS 侧**：每句结束后必须 `ws.close()`（15 已要求），严禁积累。
- **全局发送前**：检查 `clientWs.bufferedAmount` > 阈值则暂停上游读取。
- **WS Server 配置**：`new WebSocketServer({ maxPayload: 64 * 1024 })`（15 已要求）。
- **准入拒绝**：`activePipelines >= 60`（50 用户 + 20% 重连/并行余量）时，在 `upgrade` 阶段立即返回 503 + JSON 提示，不建立 VoicePipeline。

### 阈值怎么定（公式 + 经验）
1. **从外部配额反推**（最重要）：
   ```
   单阶段 cap = min(该 provider 单账号并发上限 × 账号数, 期望并发 × 1.2 安全系数)
   ```
   示例（假设值，**必须实测**）：
   - 火山 ASR：单账号并发 20 → 初期 2 账号 → cap=35（留余量给 failover）
   - Gemini 代理：规格未知，假设支持 30 并发流 → cap=25
   - 全局 cap = min(各阶段 cap 之和 × 0.7, 服务器 FD/内存预算) ≈ 40

2. **从 Node 侧经验值**（50 路数据）：
   - 峰值 socket ≈ 150-200（50 inbound + 50 ASR + 50 TTS）
   - RSS 基线 200-400MB（外部慢时 buffer 再 +100MB）
   - 事件循环延迟 p95 作为健康信号（clinic/0x 持续监控）

3. **动态调参**：所有 cap 放 env + 热重载（或 admin 接口），日志打 `inflight/asr/llm/tts`。压测脚本（15 §3.4 的 A/B/C）必须能快速验证新阈值。

**为什么不误伤正常用户**：
- 分层 cap 让“ASR 慢但 LLM/TTS 空闲”的用户不被全局一刀切。
- 准入只在入口拒绝，新用户明确知道“稍等”；已在对话中的用户不受影响。
- 背压是“慢下来”而非“丢弃”，儿童场景可接受短暂等待。

**现在就该埋的低成本扩展点**（零额外 infra）：
- `ConcurrencyGate` 类 + Semaphore（推荐用 `p-limit` 或自实现带 release 的简单版）
- 每阶段 + 全局 acquire/release 埋点（结构化日志：`inflight` `stage` `accountId` `latency`）
- 所有 provider client 构造/使用必须经过 gate（强约束）
- 友好拒绝响应 + 前端文案（“当前小伙伴较多，请稍候”）

**未来才做的重活**：跨实例全局 gate（见 §4）。

**触发升级到下一阶段的信号**（明确、可观测）：
- 持续 30+ 并发时，经常出现 429 / provider 并发上限错误（即使有重试）。
- p99 TTFT（首字延迟）或端到端说话延迟明显上升（> 1.5s 儿童可感知）。
- 压测 C 脚本下，外部 provider 利用率长期 >85%，而 Node CPU <50%、event loop 正常。
- 运营要求同时支持 80+ 账号隔离测试（单账号配额不够）。

## 2. 外部 provider 负载均衡（真正的瓶颈所在）

这是本方案的核心。**扩 Node 不如先扩 provider 账号**（成本最低、复杂度最低）。

### 核心抽象：Provider Pool / Router
为每种外部服务建**独立池**：

```ts
interface ProviderClient { /* ASRClient | TTSClient | LLMClient */ }

class AccountPool<T> {
  constructor(private accounts: AccountConfig[]); // key + endpoint + 权重 + 限额描述
  async acquire(): Promise<Lease<T>>; // 返回带 release 的 client + 内部 in-flight 计数
  // 内部实现：加权轮询 + 每账号 in-flight 计数 + 健康状态 + 最近错误时间
}
```

**调度策略（务实优先级）**：
1. **健康优先**：circuit breaker（连续 N 次错误或 429 标记该 key 冷却 30-60s）。
2. **配额感知**（如果 provider 返回头）：优先剩余配额高的 key（Retry-After、X-RateLimit-Remaining）。
3. **最少 in-flight**：同健康下选当前正在用的最少的账号（避免把一个 key 打满）。
4. **加权轮询**（fallback）：权重 = 账号规格（企业账号权重高）。

**故障转移**：
- 单次请求/流失败：自动换下一个健康 key，最多 1 次重试（LLM 侧 15 已要求“已收到首个 delta 不重试”）。
- ASR/TTS 长连接中途断：当前 turn 失败降级（提示用户“网络小波动，重试一下”），新 turn 重新选 key。
- 全池耗尽：拒绝新 turn 或新连接（走 §1 准入）。

**多账号管理**：
- 配置驱动（`PROVIDER_ASR_KEYS=json-array` 或独立 env + 热重载）。
- 每个 key 单独的 `maxConcurrent`、`rpm`、`daily`（用于本地估算，不作为硬限，provider 才是真相）。
- 账号增多时：**只需加 key 到配置**，零代码改动。运营/成本侧新增账号即可。

**健康检查**：
- 被动（推荐）：每次 acquire 使用后记录成功/失败、延迟。
- 主动（可选，Phase 1+）：每 30s 对每个 key 做一次轻量 ping（ASR/TTS 可能需建立短连接测试；Gemini 可发极小 prompt）。
- 暴露指标：`provider_account_inflight{account="asr-01"}`、`provider_error_rate`、`provider_latency_p95`。

**为什么这是真 LB**：
单进程内，pool 就是在做“账号级负载均衡 + 配额保护 + 故障转移”。比加 Nginx 有效得多，因为它理解“这是长连接流式 + 每轮 TTS 独立建连”。

**现在就该埋的低成本扩展点**（强烈推荐立即做）：
- 把现有 `volc-asr.ts` / `volc-tts.ts` / `gemini-llm.ts` 的 client 构造**全部收敛**到 `AccountPool`。
- 每个池暴露 `getStats()`（inflight per account + healthy count）。
- 在 pipeline 建立 ASR/LLM/TTS 时必须 `const lease = await pool.acquire(); ... lease.release()`。
- 配置热重载（至少重启 pm2 时生效；理想是 SIGHUP 或 admin 接口）。
- 结构化日志打 `provider` `accountId` `stage`。

**未来才做的重活**：
- 跨实例共享池状态（需要 Redis 或中心 quota 服务）。
- 智能配额预测（根据历史说话时长估算未来 5min 消耗）。

**触发信号**：
- 单个账号经常 429，即使 pool 有其他账号可用（说明调度策略或健康检查有 bug）。
- 运营新增账号后，需要改代码才能用（配置没驱动化）。
- 想做成本归因（哪个账号花了多少钱）时。

**诚实标注不确定处**：
- 火山 BigModel ASR / Doubao TTS 的**真实并发连接配额**（bigasr.sauc 等）必须去控制台或企业合同核实。15 已列为待确认。
- Gemini 私有代理网关的**当前规格**（并发流数、TPM、是否按项目 tier）必须核实。
- 火山是否支持“企业账号池”或更高并发包（vs 多个低配账号的性价比）。

## 3. 应用层水平扩展（单进程撑不住时怎么扩）

### 触发信号（严格按顺序，避免过早）
1. **最先发生（最可能）**：外部 provider 配额打满 + 多账号成本已高 → 先垂直加账号（§2）。
2. **其次**：单台服务器资源耗尽（CPU 持续 >70% + event loop delay p95 > 20ms，或内存持续上涨怀疑泄漏），**而 provider 仍有余量**。
3. **可靠性需求**：老板要求“单点故障不能让演示中断”。
4. **账号隔离需求**：不同测试组/不同地区需要强隔离。

**明确说：当前（<50）+ 短期（到 150 左右）大概率还不需要水平扩展。** 先把 §1 + §2 做扎实。

### WS 长连接负载均衡难点
与普通 HTTP 完全不同：
- 连接是**有状态 + 长寿**（整个对话期间 ASR WS + 可能的多个 TTS WS 都挂在同一条 inbound WS）。
- 中途切实例 = 必须迁移 3 条外部流 + VoicePipeline 内存状态（buffer、状态机、LLM context）→ 几乎不可能无损。
- 儿童交互对**延迟抖动极度敏感**（一次 500ms 卡顿就会“哇，小可坏掉了”）。

**推荐选择**（务实）：
- **优先 sticky session（会话粘性）**，而不是共享状态。
- 粘性方式：L7（应用层）基于 cookie（`x-p003-session` 或 upgrade 时生成的 session id）或 IP hash（对公司站内网测试够用）。
- 禁止用“纯 L4 无状态”把 WS 随意打散。

**VoicePipeline 状态处理**：
- **保持本地**（默认策略）：VoicePipeline 实例 + 它持有的 3 条外部 WS 永远只活在一个 worker / 一个实例上。
- **无状态化代价极高**，不推荐早期做：ASR/TTS 是双向流，中间要维持火山侧的会话上下文（识别结果累积、合成状态）。强行无状态化需要把所有音频帧、识别中间结果、LLM history 全塞进 Redis + 精确时序恢复，延迟和复杂度爆炸。
- 仅当真正需要“用户中途换设备继续同一对话”时，才考虑把**非实时状态**（对话历史摘要、当前场景配置）外提。

### 优雅扩缩容（长连接不能粗暴断）
- **扩容**（加实例/加 worker）：LB 直接把新连接导新实例；老连接自然留在老实例。零影响。
- **缩容**（下线实例）：
  - 标记为 `draining`。
  - 停止接受新 WS upgrade。
  - 等待所有现有 VoicePipeline 自然结束（或设置一个“优雅等待上限”，超时后才强制 close 并提示用户“会话已结束，请重新连接”）。
  - 观测指标：`draining_connections` 归零后才真正下线。
- pm2 集群模式注意：ws upgrade 通常需要 master 处理或使用 `sticky-session` 模块，实测后决定是否值得（很多时候单进程 + 更强服务器更简单）。

**单机多进程 vs 多实例起步建议**：
- Phase 1 先尝试 **pm2 cluster + sticky**（低成本，在同一台服务器内验证粘性逻辑）。
- 真正上多服务器时才引入阿里云 SLB / Nginx + 粘性配置。

**现在就该埋的低成本扩展点**：
- VoicePipeline / pipeline 构造时**绑定 sessionId 或 accountId** 到 inbound WS（方便 LB 做 affinity）。
- 所有状态（当前 turn、LLM history 快照）都封装在 VoicePipeline 实例内部，不散落在全局。
- 增加 `/health?draining=1` 接口供 LB 探测。
- 日志中必须包含 `instanceId`（pm2 实例名或 hostname）。

**未来才做的重活**：
- 真正的无状态 VoicePipeline（把 ASR/TTS 流式状态外化）。
- 连接迁移 / 热迁移。
- 基于用户 ID 的分片（voice shard）。

## 4. 共享状态（什么时候才需要引入）

**当前（单实例）完全不需要**。一切都在进程内存：in-flight 计数、provider 池健康、活跃 VoicePipeline 列表。

**需要共享的场景（按出现概率排序）**：

| 需要共享的内容 | 目的 | 阶段 | 方案建议 |
|----------------|------|------|----------|
| Provider key in-flight + 健康 | 跨实例协调“别把同一个账号打满” | 多实例后 | Redis + 轻量 Lua 脚本，或干脆**不共享**，让 429 驱动本地 failover（推荐先不共享） |
| 全局/ per-account 限流计数 | 防止同一家庭一天刷太多（成本控制） | 账号体系成熟 + 多实例 | Redis 计数器 + 滑动窗口 |
| 用户会话非实时状态（历史、偏好、当前场景） | 支持跨设备续聊、后台恢复 | V1.5+ 功能需求 | 先放 SQLite/Postgres；真需要低延迟才 Redis |
| 活跃连接列表（用于运维踢人） | 运营后台 | 多实例运维需求 | Redis set（带 TTL） |

**强烈推荐的务实态度**：
- **默认不共享 provider 状态**。多实例时每个实例有自己的 AccountPool，独立 failover。外部 provider 429 是最终的协调信号（简单、正确、一致）。
- 只有当“成本失控”或“一个实例把所有 key 打光导致其他实例全 429”成为真实痛点时，才引入中心化的 quota bookkeeper。
- Redis 引入门槛：**至少 2 个以上生产实例在跑 + 明确业务需要跨实例协调**。

**现在埋的点**：
- 所有限流/计数逻辑走抽象接口（`RateLimiter`），内存实现先跑；未来换 Redis 实现不改业务代码。
- 关键计数（inflight per provider account）暴露 Prometheus 风格指标，便于未来加中心化时对账。

## 5. 分阶段演进路线（50 → 数百 → 更多）

| 阶段 | 目标并发（活跃说话用户） | 架构形态 | 主要动作 | 成本/复杂度增量 | 明确“还不需要”的事 | 触发升级信号（必须同时满足 2 条以上） |
|------|--------------------------|----------|----------|------------------|--------------------|-------------------------------------|
| **Phase 0**（当前） | <50 | 单进程 + provider pool 起步 + 分层 gate + 背压 | 实现 AccountPool（ASR/LLM/TTS）；ConcurrencyGate；至少每个 provider 2-3 key；按 15 完成背压 + 准入 | 低（纯代码抽象 + 多账号成本） | Redis、cluster、多服务器、共享状态、无状态 pipeline | 经常打 provider 配额上限；运营要 80+ 账号隔离测试 |
| **Phase 1** | 50-150 | 垂直扩账号为主 + 单机多 worker（pm2 cluster + sticky）或更强单服务器 | 完善 pool 健康检查 + 热重载；加更多火山/Gemini 账号；单机 cluster 验证粘性；压测到 100+ | 中（账号成本线性涨 + 少量运维） | 多台服务器、Redis（除非真痛）、无状态化 | provider 配额仍不够 + 单进程 CPU/memory 持续高；p99 延迟开始爬 |
| **Phase 2** | 200-500 | 多实例（2-4 台） + 粘性 LB（阿里云 SLB / Nginx） + 最小 Redis（可选） | 引入外部 LB + session affinity；实例 draining 流程；provider pool 仍本地为主；监控 instance 级指标 | 中高（服务器成本 + LB 配置 + 运维） | 共享 pipeline 状态、连接迁移、复杂 quota 服务 | 单台已加到物理上限；需要多可用区容灾；单个 provider 账号池管理已成为运维瓶颈 |
| **Phase 3+** | 500+ | 可能的分片网关 + 更智能调度，或接受“每个活跃家庭占一个昂贵槽位”的商业现实 | 评估是否需要 Session Gateway（用户 WS 终结在网关，内部 turn 路由）；或直接谈火山/Gemini 企业大配额；或引入队列化非实时场景 | 高（架构重构风险 + 延迟可能上升） | 除非业务证明“必须支持千人同时在线说话”，否则别做 | 成本模型已证明需要极致利用率；儿童交互延迟容忍度被业务接受可放宽 |

**核心演进哲学**：
- **永远先垂直（加账号）后水平（加实例）**。
- **永远先粘性后共享**。
- **每一步都必须有明确的“还不需要”清单**，防止架构师自我感动。

## 6. 第一性原理总结

### 这条语音链路的根本约束是什么？
1. **外部依赖的硬配额是第一稀缺资源**（火山并发槽 + Gemini 代理规格 + 按音频秒数/ token 计费）。Node 进程 CPU/内存/连接数在可预见规模内是**非瓶颈**。
2. **长连接 + 双向流式实时性**：ASR 和 TTS 是必须维持到说话/听音结束的 WS。中间任何 reroute、序列化、反序列化、跨实例拷贝音频帧都会直接破坏儿童“自然对话”的核心体验。
3. **会话是“胖的”且“有状态的”**：一个活跃 VoicePipeline 同时持有 1 inbound WS + 1 ASR WS + 0~N TTS WS + LLM 上下文 buffer + 状态机。迁移代价远高于普通 HTTP 请求。
4. **延迟敏感 + 成本敏感**：儿童 300-500ms 卡顿即可感知；每多一个账号都是真金白银。

### 负载均衡的核心矛盾是什么？
- 传统 LB 的假设是“无状态、短请求、可随意重试和重路由”。
- 本场景的假设是“有状态、长胖会话、外部槽位稀缺、实时性要求高”。
- 矛盾：**想平衡负载** vs **不能打散会话**；**想保护 provider** vs **不能让用户排长队或突然断**。

### 方案如何顺应而非对抗这些约束？
- **分层保护**：全局 gate（保护 Node + 总成本） + 阶段 gate（保护具体 provider） + 账号级 pool（保护单 key 配额）。
- **垂直优先**：账号池化 + 多 key 是性价比最高的“扩容”。
- **粘性至上**：LB 只做“把整个用户会话粘到一台实例”，实例内再做精细的账号级调度。
- **准入在最外层**：不让超额的会话建立起来（比建立后挤占资源文明）。
- **背压 + 优雅关闭**：承认外部会慢，保护自己不被拖死，同时给用户明确信号。
- **演进只在必要时跨越复杂度边界**：Phase 0/1 几乎全是代码抽象 + 配置 + 运营动作（加账号），不碰 infra。

**一句话总结**：  
**把“账号”当做可横向扩展的计算单元，把“用户会话”当做不可分割的粘性工作单元，用分层门控和背压保护稀缺的外部槽位**。这是对本语音链路物理与经济约束的最小对抗方案。
