### Part 1: 方案挑战与补充 (2025-2026 最新现状)

*   **ASR 补充与纠偏**：
    *   **SenseVoice-Small**：【已验证】`sherpa-onnx` 支持的 SenseVoice-Small 为非自回归模型，虽然支持流式分块输入，但其端到端延迟依赖于外部 VAD 断句。在短语音、低语速的儿童场景中，首字延迟与断句截断感明显强于 Zipformer (Transducer)。
    *   **Whisper-ONNX 方案 (遗漏)**：【已验证】`sherpa-onnx` 实际上支持 Whisper-tiny/base。但 Whisper 架构在手机 CPU 上 RTF 极差（通常 > 0.5），且无原生流式端点检测，直接排除。
    *   **Paraformer-zh (遗漏)**：【已验证】阿里开源的 Paraformer-zh (small) 同样可通过 `sherpa-onnx` 部署。在成人场景下其抗噪和领域词识别好于 Zipformer-small，但对童声同样缺乏优化。
*   **TTS 补充与纠偏**：
    *   **Kokoro-82M**：【推断】在中文场景下属于“画饼”方案。其中文音素转换器（G2P）极其不稳定，发音机械感重，且现阶段无任何中文童声音色。
    *   **ChatTTS / CosyVoice**：【已验证】端侧完全不可行，自研或剪裁版在端侧 RTF > 3.0，延迟以秒计。但它们是**自托管（Self-hosted）**服务器部署的黄金方案。

### Part 2: 两个硬门槛的现实判断

*   **门槛 ①：中文童声 on-device ASR 能否“可用”？**
    *   **直接使用成人模型**：【已验证】**不可用**。5-10 岁儿童的发音器官未发育完全、共鸣腔窄、基频高（常在 250Hz 以上，成人多在 100-200Hz），且伴随发音不清、叠词、非规范语序。现存的开源端侧成人模型（Zipformer-small/Vosk）直接识别 5-10 岁童声，CER（字错率）通常在 40% - 60% 之间，demo 阶段即会引发频繁的语义理解失败。
    *   **微调（Fine-tune）的性价比**：【推断】**极低且难以落地**。ChildMandarin 等开源儿童数据集规模小、底噪复杂。在端侧小模型（如 Zipformer-small 14MB）上微调，极易发生灾难性遗忘或过拟合，且由于端侧算力限制，无法支持大模型的泛化能力。预计投入 2 周以上研发微调，CER 仅能勉强降至 25%-30%，仍达不到“流畅对话”的 demo 体验。
*   **门槛 ②：端侧复刻「小可」音色是否现实？**
    *   **端侧零样本克隆（ZipVoice）**：【已验证】**不现实**。Pixel 10 Pro 等旗舰机 RTF 勉强接近 1.0，意味着生成 3 秒语音需要耗时 3 秒，首包延迟（TTFB）极高。对于需要“丝滑对话”的儿童产品，这是毁灭性的体验。
    *   **离线固化 Embedding**：【推断】**音质和还原度无法通过 demo 验收**。端侧 VITS 的表征能力极弱，通过 10 秒参考音频提取的 Speaker ID 在 VITS 下极易失真，带有严重的金属电音，且无法复刻「小可」的儿童情感与语气。
    *   **唯一可行端侧替代方案**：【建议】若必须端侧，应当**放弃零样本克隆**，改为**离线微调单人 VITS 导出 ONNX**。在服务器端使用「小可」的 Volcano 原始音频（约 1-2 小时）离线训练一个单说话人 VITS 模型，再导出为 60MB 左右的静态 ONNX 部署于端侧。

### Part 3: 第一性原理对抗：On-Device vs. Self-Hosted

川哥的真实动机是**【可控 / 不依赖第三方（避开火山引擎的限制/断供风险）】**，且**明确未将“无网离线使用”列为动机**。

*   **端侧部署（On-device）的代价**：
    1.  **识别率骤降**：被迫妥协使用小型 ASR 模型，面对童声识别率低。
    2.  **音色劣化**：由于端侧算力限制，TTS 必须采用陈旧的 VITS 架构，「小可」音色变僵硬、无感情。
    3.  **集成重构**：Android 原生层（C++ / JNI / Asset 释放管理 / 线程调度）与 WebView 的 JS Bridge 交互极其繁琐，且需针对不同手机做 CPU/NPU 兼容性调试。
    4.  **性能发热**：端侧同时运行 ASR (监听) + VAD + TTS (生成)，中端机持续运行 10 分钟必发热降频，导致卡顿。
*   **自托管部署（Self-hosted）的优势**：
    1.  **完全控权**：自己租用 GPU 服务器（如 GPU 云主机、私有工作站），避开火山引擎限制，同样满足“不依赖第三方”的动机。
    2.  **降维打击的质量**：ASR 可上 SenseVoice-Large 或 Whisper-Large-v3-Turbo，配合优秀的自研 VAD，童声识别率可与火山云媲美；TTS 可上 CosyVoice，利用零样本克隆（Zero-shot）直接完美复现「小可」特定音色。
    3.  **零重构成本**：客户端继续保留现有的 WebSocket 架构，仅修改服务器端点 URL，实现无缝切换。
*   **对抗性结论**：
    *   【建议】**Demo 阶段，On-device 是极不理性的选择。** 它为了一个“川哥不需要的离线属性”，牺牲了“童声识别率”、“小可音色自然度”和“研发速度”这三个生命线级别的体验。
    *   **推荐方案为 Self-hosted。** 一台 RTX 4090 / A10G 级别的 GPU VPS 即可支撑 demo 阶段的并发，且音色与识别率能达到商业级表现。

### Part 4: 推荐方案与落地路径

#### 方案一：若妥协并选择自托管（Self-Hosted，强烈推荐）
*   **技术选型**：
    *   **ASR**：**SenseVoice-Small/Large (FunASR)** 或 **Faster-Whisper-Large-v3** + **Silero VAD**。
    *   **TTS**：**CosyVoice (300M)**。利用 Volcano「小可」的 15 秒高清音频作为 Prompt 固化，实现高保真童声克隆。
*   **落地路径**：
    1.  租用一台带 GPU 的 VPS（如 RTX 4090 或 A10G）。
    2.  使用 FastAPI + WebSockets 封装 ASR 和 TTS 接口，支持流式双向通信。
    3.  客户端仅修改现有 WebView / 原生薄壳的 WebSocket 链接指向自建服务器，验证对话流稳定性。
*   **得失**：
    *   *得*：童声识别率极高，音色 95% 还原火山引擎，开发耗时 2-3 天，完全控权。
    *   *失*：需支付服务器租金，无网不可用。

#### 方案二：若坚持走端侧（On-Device）
*   **技术选型**：
    *   **ASR**：`sherpa-onnx` + **Zipformer-zh (small)**。
    *   **TTS**：`sherpa-onnx` + **单人 VITS (ONNX)**（自训练）。
*   **落地路径**：
    1.  **ASR 童声兜底**：使用开源 ChildMandarin 数据集对 Zipformer-small 进行微调，随后通过 ONNX 工具链量化为 int8 格式。
    2.  **TTS 音色微调**：收集「小可」音色至少 1 小时的纯净录音，使用 VITS 框架离线训练单说话人模型，导出为 ONNX，置入 Android `assets` 目录。
    3.  **工程集成**：
        *   在 Android 原生层编写 `AudioRecord` 采集线程，通过 C++ API 喂入 `sherpa-onnx` ASR 进行流式识别。
        *   识别结果通过 `@JavascriptInterface` 投递给 WebView 的 JS 引擎。
        *   WebView 返回待播放文本后，由 Native 调用 `sherpa-onnx` TTS 进行推导并利用 `AudioTrack` 播放。
*   **得失**：
    *   *得*：0 运营成本，极端情况下支持完全离线。
    *   *失*：童声识别经常卡壳（CER > 25%），「小可」音色退化为冰冷机械音，APK 体积暴增 > 150MB，开发周期至少 3-4 周。

### Part 5: 关键风险与真机实测项

1.  **ASR 童声真机 CER 测试（P0 级）**：【建议】必须实测 5-10 岁儿童在嘈杂和安静环境下的表现。若 CER > 25%，小家伙会因反复“听不懂”而瞬间失去产品兴趣。
2.  **端侧回声消除（AEC）失效风险**：【推断】在 on-device 方案中，当 TTS 正在发声时，儿童随时可能打断（Duplex 交互）。如果 Native ASR 无法获取 WebView 播放的音频回路进行硬件级 AEC，ASR 会将 TTS 播放的“小可自己的声音”误识别为用户输入，导致系统死循环自我对话。
3.  **CPU 降频与 RTF 恶化**：【建议】在千元级 Android 测试机上，连续进行 50 轮对话测试，监控 CPU 温度与 RTF 趋势。若因发热导致 RTF 超过 1.0，首包延迟将从 200ms 飙升至秒级，导致产品不可用。
