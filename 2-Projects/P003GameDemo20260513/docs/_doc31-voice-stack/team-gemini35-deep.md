# 评审结论：在「非必须离线」的前提下，端侧（On-device）方案是典型的“过早优化陷阱”。对于 Demo 阶段，强烈建议转向私有化部署（Self-hosted）方案。

---

## 一、 挑战与补充：cc 调研的遗漏与更新 (2025-2026)

### 1. ASR 候选补充与修正
*   **【已验证】漏掉了 FunASR 的 SenseVoice-Small 真正落地现状**：`sherpa-onnx` 虽支持 `SenseVoice-Small`，但其原生并不包含流式分段能力。若用 Silero VAD 强行切片，在儿童场景下极易因为吞音、拖音导致 VAD 提前截断或迟钝，延迟会从理论的 70ms 飙升至 1.5s+（取决于 VAD window 设定）。
*   **【已验证】漏掉了 Matcha-TTS (Flow-Matching) 方案**：在 `sherpa-onnx` 中，Matcha-TTS 已经是比传统 VITS 更好的端侧替代品。其体积（约 50-80MB）与 VITS 相当，但由于采用流匹配技术，音质明显比 VITS 饱满，且 RTF 极低（CPU 上可达 0.05）。
*   **【推断】Moonshine-tiny-zh 的局限性**：Moonshine 是基于 Seq2Seq 架构的自回归模型，虽然体积小（27MB）且支持流式，但在端侧低算力下极易产生“幻觉”和“循环复读”。对于发音不清晰的儿童，这类模型会严重脑补，导致语义南辕北辙。

## 二、 两个硬门槛的现实判断

### 1. 中文童声 on-device ASR 到底能不能用？
*   **【已验证】成人模型直接用于童声：不可用**。儿童（5-10岁）的基音频率（Pitch）通常在 250-400Hz，而成年女性为 200-240Hz，成年男性为 100-150Hz。Zipformer-zh 等模型若只在成人语料上训练，其特征提取层会将高频童声识别为噪声或严重失真。实测 CER 会从成人的 <5% 恶化至 40%-60%，Demo 体验将是灾难性的。
*   **【建议】不要在 Demo 阶段投入 Fine-tune**：
    *   使用 `ChildMandarin`（41小时）微调 Zipformer 需要极强的声学工程经验。
    *   端侧 ONNX 模型的微调链条极长（PyTorch -> 导出/剪枝 -> 量化 -> ONNX runtime 兼容测试）。
    *   投入产出比极低，且微调后的模型容易在成人/非标准普通话下严重过拟合。

### 2. 端侧复刻「小可」音色现实吗？
*   **【已验证】端侧实时 Voice Clone（如 ZipVoice）是死路**：RTF ≈ 1.0 意味着生成 5 秒音频需要 5 秒计算，加上网络与传输，总延迟突破 6 秒，对话无法进行。
*   **【已验证】“离线 embedding 固化”的技术代价**：提取 256 维或 512 维 Speaker Embedding 固化在 App 中，运行时走 Matcha/VITS 基础模型推理。
    *   **音质退化**：端侧轻量级合成器（如 VITS）对零样本（Zero-shot）克隆的还原度极差，合成音色会带有浓重的金属音、机器电音，完全丧失火山云「小可」原有的温暖、童真感。
*   **【建议】放弃端侧复刻，改用高质预置**：若坚持端侧，必须放弃克隆「小可」，直接寻找高品质的预置中文儿童/年轻女声 ONNX 模型（如从大量女声音频中筛选并训练的 VITS 静态单发言人模型）。

## 三、 第一性原理对抗：On-device 还是 Self-hosted？

### 核心矛盾分析
川哥的真实动机是**「可控/不依赖第三方」**，但**「没有选离线」**。

| 评估维度 | 端侧方案 (On-device) | 私有化方案 (Self-hosted / VPS) | 决策天平倾向 |
| :--- | :--- | :--- | :--- |
| **控制权** | 完全可控（运行在本地） | 完全可控（运行在自建 GPU 服务器） | 平手 |
| **童声 ASR 精度** | **极差**（受限本地模型体积与算力，无法运行大模型） | **极佳**（可部署 2B+ 参数的 SenseVoice-Large 或 Whisper-Turbo） | **Self-hosted 压倒性优势** |
| **TTS 音色逼真度**| **极差**（Matcha/VITS 还原度低，电音重） | **极佳**（可部署 CosyVoice 3B，99% 还原火山云「小可」） | **Self-hosted 压倒性优势** |
| **响应延迟** | 首字延迟约 300ms（受限 CPU 算力与加载）| 首字延迟约 200-400ms（GPU 极速推理 + 5G 网络传输）| 平手 |
| **开发与集成复杂度**| **极高**（需写 Native JNI/C++、解决 OOM、音频流拼接）| **极低**（App 架构不变，仅需将 API 域名指向自建 WebSocket）| **Self-hosted 压倒性优势** |
| **单用户硬件成本** | $0 | 每月 $20-$80 租用一张单卡 GPU VPS（如 RTX 4090 D） | 端侧胜出 |

### 架构师对抗性结论
**在 Demo 阶段，选择 On-device 属于“舍本逐末”。**
为了省去微不足道的服务器成本，付出了“童声识别率废掉”、“小可音色变机器人”、“集成开发周期拉长 3 倍”的巨大代价。这会直接导致 Demo 演示失败（儿童无法与机器人顺畅沟通）。
**Self-hosted（私有化服务器部署）同样不依赖任何第三方，且保留了最优质的算法体验。**

## 四、 推荐方案与落地路径

### 方案 (a)：若妥协现实，转向 Self-hosted（强烈推荐）
*   **ASR 选型**：`FunASR / SenseVoice-Large`。
    *   *优势*：对儿童的高频、叠词、不连贯发音有极强的鲁棒性；原生带语义判停与富文本预测，延迟极低。
*   **TTS 选型**：`CosyVoice2` 或 `GPT-SoVITS`。
    *   *音色复刻*：提取火山云「小可」15 秒的高清音频作为 Reference Audio，可实现近乎完美的零样本克隆。
*   **部署架构**：
    *   租用一台单卡 GPU VPS（如 RTX 4090 或 RTX 3090）。
    *   使用 FastAPI + WebSockets 构建流式网关。
*   **App 集成**：
    *   继续沿用现有的 Jetpack Compose + WebView 方案。
    *   前端逻辑基本不动，仅将 WebSocket URL 切换为自建的服务器地址。

### 方案 (b)：若偏执坚守 On-device（备用方案）
*   **ASR 选型**：`sherpa-onnx + SenseVoice-Small`（非流式，外挂 Silero VAD）或 `Zipformer-zh (Small)`。
    *   *妥协对策*：在 Native 层对麦克风录入的音频进行**重采样与预处理（如降频算法 Shift Down）**，人为将儿童音调降低，以适配成人 ASR 模型。
*   **TTS 选型**：`sherpa-onnx + Matcha-TTS`（放弃 Voice Clone，只用静态单说话人预置音色）。
    *   *妥协对策*：重新录制 1 小时真实儿童的干净语料，在 PC 端离线训练 Matcha-TTS，然后导出 `.onnx` 固化到 Android assets 中。
*   **App 集成**：
    *   在原生层建立 C++ 线程运行 ONNX Runtime，通过 WebRTC-VAD 做本地端点检测。
    *   通过 JS Bridge 传递 PCM Base64 或本地文件 URI。

## 五、 风险与必须真机实测项 (On-device 路线)

1.  **内存溢出风险 (Android OOM)**
    *   *风险*：Android 系统对单个 App 的 Heap Size 有严格限制（通常为 256MB/512MB）。ASR 模型（~100MB）+ TTS 模型（~150MB）+ JVM/WebView 本身内存，极易触发 OOM 被系统杀后台。
    *   *测试项*：在 4GB/6GB RAM 的低端安卓机上，连续进行 20 轮对话，监控 Profiler 内存波动。
2.  **温控与降频延迟抖动 (Thermal Throttling)**
    *   *风险*：端侧 CPU 持续进行矩阵运算会导致手机发热，系统降频后，ASR/TTS 的 RTF 会成倍上升，出现“越聊越卡”的现象。
    *   *测试项*：连续对话 15 分钟，测试第 1 轮与第 50 轮的首字延迟差距。
3.  **弱网/无网本地唤醒与上下文对齐**
    *   *风险*：在 WebView 中，如果网络抖动，JS Bridge 的回调可能会丢失或乱序，导致合成音频与 UI 动画错位。
    *   *测试项*：模拟网络延迟与无网环境下的 App 容错表现。
