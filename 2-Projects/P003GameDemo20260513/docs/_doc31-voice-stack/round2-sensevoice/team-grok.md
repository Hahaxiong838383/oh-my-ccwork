**结论先行**：SenseVoice 不值得作为主力 ASR，Zipformer-zh 应为唯一主力；情绪功能有理论潜力但实际落地价值低、代价高，建议暂不纳入或仅作为远期异步旁路。cc 的“Zipformer 主 + SenseVoice 旁路”方案是最优可行路径，但需严格验证并行资源占用，否则直接放弃 SenseVoice。

**问题 1 判断**：SenseVoice 情绪识别 + 音频事件检测对儿童情感陪伴的真实价值极低，属于 demo 噱头而非产品跃升。  
- 中文儿童场景下，哭声/生气标签的召回与精确率缺乏公开实测数据（已知事实仅列成人 CER）；成人模型在儿童高频哭闹、尖叫场景退化是共性，川哥已明确“不用太在意”。  
- LLM 消费方式：即使拿到 emotion tag，也只能追加到 prompt（如“用户当前情绪：sad，请用温柔语气回复”），但这与直接用 LLM 上下文理解孩子话语几乎等价，且引入噪声（误判会让小可回应诡异）。  
- 产品体验：逐字字幕 + 实时打断才是 5-10 岁孩子感知到的核心，情绪标签对“听出开心/难过”帮助微乎其微。诚实判断：不构成区分度。

**问题 2 判断**：SenseVoice 模拟流式对实时对话 + 逐字字幕的代价是硬伤级。  
- 无 partial 输出 → 字幕只能整句后一次性出现，破坏“打字机”逐字体验，这是小可最痛的实时反馈。  
- 判停完全依赖外挂 Silero VAD → 天然 endpointing 缺失，延迟必然高于 Zipformer 的 Transducer 判停（已知事实明确标注“需外挂”）。  
- 对比 Zipformer：真流式 + 逐字 partial + 天然 endpointing，直接解决“判停时快时慢”的历史痛点。代价对比：SenseVoice 在流式体验上输得彻底。

**问题 3 判断**：两者结合在端侧中端机上不可行。  
- 体积：14MB + ~100MB = 114MB+，远超中端机舒适内存预算；同时加载两个 sherpa-onnx 模型会导致发热、掉帧、后台被杀。  
- 算力：双模型并行推理（即使一个旁路）在 Snapdragon 7/8 Gen 系列中端机上难以 sustain 实时。  
- 可行路径仅剩：Zipformer 主线程跑完整对话（字幕+判停），SenseVoice 仅在用户主动触发或对话结束后异步跑一次情绪分析（非实时旁路）。但即使异步，也增加集成复杂度与维护成本。结论：二选一更干净。

**问题 4 明确推荐**：本地 ASR 选 **Zipformer-zh 作为唯一主力**。  
落地路径（按 sherpa-onnx 现有经验）：  
1. 主模型：sherpa-onnx Zipformer-zh small（14MB），启用 true streaming + partial result + endpointing，直接喂 WebView 字幕与打断逻辑。  
2. 情绪功能：本轮完全跳过；若川哥坚持二期验证，再评估 SenseVoice 异步调用（一句话结束后单次推理，不阻塞主流程）。  
3. Fun-ASR-Nano 仅作为备选提及，不纳入本轮候选。  
此路径与 cc 初判一致，且已通过“主+旁路”压力测试：旁路方案在资源上不可持续，SenseVoice 精度优势不足以抵消流式与体积损失。

**风险**：  
- AEC：本地 ASR 录到云 TTS 小可声音仍需播放时压制（已知事实），Zipformer 真流式对 AEC 窗口更敏感，需提前验证。  
- 中文儿童 CER：Zipformer 在儿童场景的实际表现仍需实测（成人“好”不等于儿童“好”）。  
- 未来演进：若 sherpa-onnx 后续支持 SenseVoice 真流式或模型压缩到 30MB 以下，再重评。

【已验证】：表格中流式/体积/情绪/集成事实；sherpa-onnx 团队经验。  
【推断】：中端机并行资源占用、儿童情绪标签准确率、LLM prompt 消费效果。  
【建议】：本轮锁定 Zipformer，情绪功能列入二期 roadmap 单独验证。
