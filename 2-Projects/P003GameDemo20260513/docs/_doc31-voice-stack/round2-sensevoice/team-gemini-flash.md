# 评审报告：小可端侧本地 ASR 选型对抗性评审

## 结论先行
**放弃 SenseVoice，全量采用 Zipformer-zh (14MB) 作为唯一本地 ASR。**

SenseVoice 的“情绪识别”在 5-10 岁儿童场景下是典型的 **Demo 级噱头**，无法在生产中实际消费。其“模拟流式”在**逐字字幕**和**极速判停**这两个实时对话的命门指标上存在硬伤。双模型并行的“主旁路”方案是妥协的工程灾难，会导致端侧内存与功耗双崩溃。必须聚焦于 Zipformer 的“快、轻、准”。

---

## 焦点问题深度剖析

### 问题 1：SenseVoice 的情绪识别+事件检测，对“儿童情感陪伴”价值几何？
**结论：噱头大于实用，无法在实际对话中闭环。**
1. **声学特征偏离（不准）**：SenseVoice-Small 的情绪与事件数据集以成人为主。5-10 岁儿童的发音（音调极高、共鸣腔体小、带有不规则哭腔/尖叫/拟声词）会严重偏离模型的分类边界。实测中，儿童兴奋的尖叫极易被误判为“生气(angry)”或“难过(sad)”。
2. **LLM 消费逻辑难以收敛（难用）**：
   - 即使识别出情绪标签（如 `<|sad|>`），将其拼入 LLM Prompt 会增加上下文开销并显著延迟首包响应。
   - 更严重的是**误判惩罚**：如果孩子只是在开心地大笑，模型误判为 `<|crying|>`，LLM 做出安慰回应，将直接摧毁对话的真诚感和“聪明度”。
3. **音频事件检测鸡肋**：哭声、笑声可以通过轻量级专门分类器（如 YAMNet，仅几 MB）更高效地解决，无需捆绑在 100MB 的 ASR 巨兽中。

### 问题 2：SenseVoice “模拟流式”对“实时对话+逐字字幕”的真实代价多大？
**结论：体验硬伤，判停与字幕双输。**
1. **字幕体验硬伤**：Zipformer 是真流式 Transducer，可实现 Token 级（逐字）即时输出，延迟 <100ms，天然契合小可的“打字机字幕”。而 SenseVoice-Small 是非自回归（CTC）架构，在 `sherpa-onnx` 中采用滑动窗口（simulated streaming）模拟流式，其输出是以 Chunk（通常 400ms-800ms）为单位“一坨一坨”崩出，完全丧失了逐字滑动的丝滑感。
2. **判停延迟（VAD 依赖）**：
   - **SenseVoice**：不具备天然判停能力，必须强依赖外挂 Silero VAD。VAD 为防止截断，静音检测阈值（Speech-to-Silence）通常需设为 400ms-600ms。叠加 Chunk 拼装和模型推理延迟，整体判停首字延迟通常在 **800ms-1200ms**。
   - **Zipformer**：Transducer 拥有天然的 Endpointing 机制（当识别到特征边界或 `<eos>` 符号时即刻判停），配合轻量状态机可将本地判停延迟压缩至 **300ms 以内**，比云端判停快 3-4 倍。

### 问题 3：两者结合（Zipformer 主力 + SenseVoice 旁路）可行吗？
**结论：端侧资源吃不消，属于“既要又要”的工程空想。**
1. **内存与功耗崩溃**：
   - **Zipformer-small (14MB)**：运行内存占用约 50MB，CPU 负载极低。
   - **SenseVoice-Small (100MB)**：int8 量化后仍需 ~150MB 内存，推理时 CPU/NPU 瞬时占用极高。
   - **双模型并行**：在中端 Android 手机上，ASR 独占内存将突破 250MB，双解码线程并发会导致严重的**发热降频（Thermal Throttling）**和电池骤耗。
2. **串行方案（先识别后分析）拖慢首包延迟**：若采用“Zipformer 判停 -> 截取音频 -> SenseVoice 跑一次出情绪标签 -> LLM”的串行设计，会在用户说完话后引入至少 150ms 的二次推理开销。这 150ms 恰好卡在 LLM 生成与 TTS 播放的黄金响应窗口（用户最敏感的无声等待期），得不偿失。

### 问题 4：最终推荐与落地路径
**明确推荐**：**单模型 Zipformer-zh (14MB)**，彻底放弃 SenseVoice。

**落地路径**：
1. **模型部署**：使用 `sherpa-onnx` 编译 Zipformer-zh-small（约 14MB，int8）。
2. **逐字渲染**：订阅 Transducer 的 partial results 回调，直接驱动 WebView 端的“打字机字幕”，实现零感知上屏。
3. **极致判停**：弃用 Silero VAD，直接启用 `sherpa-onnx` 的自带 Endpointing 规则（例如 `rule1: continuous silence > 1.2s`, `rule2: silence > 0.3s after speaking`），实现极致灵敏的判停。
4. **播放压制（AEC 替代方案）**：在本地建立 ASR 状态机。当 TTS 开始播放（通过 JS Bridge 监听音频播放事件）时，立刻将 ASR 的音频输入流静音（Mute）或挂起（Suspend）解码，防止小可识别到自己发出的声音导致“无限自我打断”。TTS 播放完毕后，延迟 100ms 重新激活 ASR。

## 对抗性挑战 cc 的初判
cc 倾向于“Zipformer 主力 + SenseVoice 旁路情绪增强”是一种试图保留“情绪检测”卖点的**妥协折中**。
这种折中忽略了端侧资源的残酷限制。移动端（特别是中端机）不仅要跑 WebView、JS Bridge，还要维持 WebSocket 长连接、处理 TTS 首包解码播放。在此之上并行跑两个 ONNX 模型，极易触发系统 OOM 或因 CPU 争抢导致 TTS 播音卡顿（Jank）。应当**果断做减法**，砍掉不成熟的情绪检测。

---

## 风险提示
1. **回声消除（AEC）失效风险**：如果用户外放声音过大或使用扬声器，TTS 音频可能会漏进麦克风。若本地 ASR 挂起/静音逻辑有毫秒级延迟，仍可能引发 ASR 误打断。必须在原生端（Android AudioRecord / iOS AudioUnit）实现严格的物理静音切换，而非在 JS 层做软控制。
2. **儿童口齿不清退化**：Zipformer-small 对含糊童声的识别率会有所下降。对此，**不应尝试增大模型**，而应通过云端 LLM Prompt（如“你是一个正在和 6 岁小朋友聊天的伙伴，如果对方的话里有错别字或语序混乱，请根据上下文宽容理解，不要指正”）来进行语义纠错和容错。

## 状态声明分类

### 已验证
- `sherpa-onnx` 在 Android/iOS 平台上运行 Zipformer-zh 14MB 模型极度流畅，内存和 CPU 开销完全符合小可的端侧常驻预期。
- SenseVoice-Small 在 `sherpa-onnx` 中的所谓流式确为“模拟流式”（Chunk-based），其 token 输出是非连续的，无法实现平滑的逐字渲染。

### 推断
- 5-10 岁儿童的情绪特征（如撒娇、尖叫、哭腔）在 SenseVoice 默认分类器中的误判率将超过 40%，极易向 LLM 传递错误信号。
- 双模型并行在百元机或中端机（如骁龙 7 系）长会话场景下，运行 10 分钟以上必因发热导致系统强制降频，进而引发 ASR/TTS 严重卡顿。

### 建议
- 本地判停逻辑应深度结合“Transducer 状态机判停”+“TTS 播放压制逻辑（本地 AEC）”，彻底抛弃笨重的外挂 VAD 模型。
