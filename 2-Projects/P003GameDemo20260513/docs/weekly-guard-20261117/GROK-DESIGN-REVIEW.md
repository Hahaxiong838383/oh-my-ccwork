# P003 小程序周报自动计算 · 独立设计审查与交叉测试设计

署名：Grok（xAI，Grok 4.7）｜2026-11-17

审查性质：设计审查和测试设计。本文不验收新实现。没有修改生产或源码，没有 commit，没有读取凭据，没有请求生产接口，也没有用真实业务库跑计算。服务端测试和小程序测试本次都没有执行；下面引用的测试，只说明阅读时它们锁定了哪些断言。

阅读期间工作树在变。第一次读到的家长周报 GET 仍是旧的内联日表求和；再次读取时，该 GET 已改为调用周报服务，并出现计算模块、报告存储、60 秒调度、后台周报路由和小程序解析面板。下文对草稿的意见对应该次重读。源码若继续变化，以后的独立源码验收必须重新取证，不能把本文当成通过结论。

对照材料：已批准方案《小程序数据与护眼周报：后台自动计算方案》（2026-11-17，署名为 codex），以及《小可周报「护眼守护」数据问题》。方案里的只读样例没有在本次重放。

## 1. 结论

正式周报应继续走现有 `GET /v1/parent/devices/{public_id}/weekly-report`。旧字段保持原算法和原类型。新结果放在新增的 `report` 对象，家长端和后台读同一份已保存结果。

已经可以固定的口径：

- 单设备，北京时间自然周，区间是周一 00:00 含、下周一 00:00 不含。
- 周报主值用真实 `focus_segment`。补充估算另列，不进入日均，也不进入活跃天数。
- 日均分母固定为 7。先把本周真实毫秒加总，只在展示前换算成分钟。
- 活跃日只认按自然日切开、再合并重叠和端点相接之后的最长一段，原始毫秒大于等于 300000。
- 坐姿次数只认 `posture_reminder` 且 `outcome` 精确等于 `played` 的唯一 `event_id`，按发生日归周。超过 672 保留真实数并标异常。
- 缺测是 `null`，确认的 0 才是 0。旧字段里已经长期用 0 表示“日表没有行”的计数，继续保持 0，不改成 `null`。
- 周日 22:00 的第一版要能和周一 00:00 之后的周界闭合区分开。首次发布时间保持不变，迟到数据只修订受影响的周。

本次独立脚本在 `TZ=UTC` 下复核了日期和阈值。旧默认周起点在 2026-11-17 12:00（北京时间）得到 2026-11-17；同一时刻按日历日计算得到 2026-11-16。299999 毫秒和 299500 毫秒用 `Math.round(ms/1000)` 都会变成 300 秒，但都没有达到 300000 毫秒门槛。

## 2. 旧周起点错在哪

旧实现的日期加减本身能跨月、跨年。它先取 `YYYY-MM-DDT00:00:00+08:00`，再加上 8 小时，然后取 UTC 的日期，用来抵消 `toISOString()` 的 UTC 日期。这 8 小时要保留。首页滚动 7 天用的是同一类补偿，不能把它当成周报 bug 删掉。

错误在星期计算。代码把北京时间零点解析成前一日 16:00 UTC，再对该瞬间调用 `getUTCDay()`。星期因此永远取到前一天。以周一为 0 时，默认窗口实际是：

| 北京时间 | 旧默认 `week_start` | 自然周周一 |
| --- | --- | --- |
| 2026-11-16 00:00 或 12:00 | 2026-11-10 | 2026-11-16 |
| 2026-11-17 12:00 或 20:00 | 2026-11-17 | 2026-11-16 |
| 2026-11-18 至 11-21 的 12:00 | 2026-11-17 | 2026-11-16 |
| 2026-11-22 12:00、21:59、22:00、23:59 | 2026-11-17 | 2026-11-16 |
| 2026-11-23 00:00 | 2026-11-17 | 2026-11-23 |
| 2026-11-15 23:59:59（即 15:59:59Z） | 2026-11-10 | 2026-11-09 |

因此这不是“周二碰巧偏一天”。周二到周日会落到本周二；周一和周一 00:00 会落到上一周的周二。只为 11 月 17 日写一条断言，盖不住周一和周日 22:00。

把进程时区设成 `Asia/Shanghai` 也修不好。`getUTCDay()` 看的是 UTC 星期，不看进程时区。独立脚本就是在 `TZ=UTC` 下跑出上表的。

新的 `weekStartOf` 先用 +8 小时偏移得到日历日，再对这个日历日的 `T00:00:00Z` 取星期。抽样里的周一、周日 22:00、周一 00:00、跨年和 `2026-11-15T16:00:00Z` 都落到正确的周一。小程序草稿里的 `beijingWeekStart` 在同批时刻与它一致。两者仍是两份实现，以后要用同一组时刻做对照，不能各写一个自比测试。

现有 HTTP 默认周测试若只断言“返回值等于 `weekStartOf(Date.now())`”，则函数算错时测试仍会通过。必须把时钟钉在上表的至少四个点：周一 00:00、周二 20:00、周日 21:59:59、周日 22:00:00、下周一 00:00。

非法日期也不能靠旧加减。`2026-11-31`、`2026-02-30`、非闰年 `2026-02-29` 都能被四位正则接受，并且被日期解析滚到下一个真实日期，旧路径会返回 200 和另一周。`2026-00-10`、`2026-11-00` 则会在 `toISOString()` 抛 `RangeError`。新校验用整段往返比较拒绝这些值并返回现有 `bad_request`，这是该收紧的行为。服务测试已覆盖 `2026-02-30`；源码验收再补 `2026-11-31` 和非闰年 `2026-02-29`，确认状态是 400 而不是 200 或 500。

## 3. 三套现有口径不能混用

真实连续门槛不能借用下面任何一套的“秒”或“分钟”：

| 现有出口 | 实际含义 | 周报若直接复用会错在哪 |
| --- | --- | --- |
| 旧周报日表 | `guarded_ms` 在当天有 correct 或 deviated 姿态轮时等于当天全部 `focus_ms`；`posture_alert_count` 是日表 `reminder_played` 之和 | 守护分钟不是真实用眼时长。没有日表行时，求和结果是 0 |
| `usageRange` | 按先到顺序丢掉后来的整段重叠，只留不重叠的部分 | 方案要求重叠只计一次并保留不重叠的延长部分。整段丢弃会少计 |
| `buildHistoricalUsage` | 真实片段、在位、姿态和奖励高水位分开后再取当日较大值；秒数用 `Math.round` | `observed_seconds >= 300` 会把 299500 毫秒和 299999 毫秒都当成 5 分钟。在位窗口本身就是 300000 毫秒，姿态回看是 60 秒 |

活跃天数的顺序必须是：先按北京时间零点切开，再在当天合并重叠和端点相接，最后用合并后的最长毫秒比较 300000。先把全周合并再切开，会把午夜两边相接的两段合成一段。

补充量的输入应是历史用法里的当日合计高水位，也就是已经包含真实片段的 `total_seconds`。周报再计算“合计减本算法真实秒”。若把 `estimated_seconds` 填进这个字段，不重叠的补充会被 `max` 吃掉。奖励 301、600、902 只留 902。奖励上报 0 是补充侧的确认 0，不是真实计时 0，也不能产生活跃日。

未来结束时间：历史用法和计算草稿都会因为 `end > now` 丢弃整段。一段本可达到 5 分钟、结束时刻只超当前时间 1 毫秒的片段，结果是无效，不是活跃。这是当前草稿测试已经锁定的选择。源码验收要明确保持这个选择，或者单独改口径并改测试；不能在接线路由时悄悄改成“保留已发生前缀”。

## 4. 草稿里已经可见、但本文不验收的风险

这些是阅读到的实现选择和测试盲区，供下一轮源码审查逐条重证。本文不判断这批测试是否通过。

1. 同一响应里可以有两个 7 日窗口。显式 `week_start=2026-11-17` 时，旧字段仍从 11 月 17 日算到 11 月 23 日；`report.week_start` 归一成 11 月 16 日。这个分裂能保住旧调用，但现有测试只核对了两个起点字符串。它没有放一条“只发生在周一”的真实片段或 played 提醒。那样旧字段应为 0，`report` 应为 1。只发生在下周一 00:00 的事件则相反：旧窗口算入，自然周不算入。

2. 迟到修订测试用两段首尾相接的 300 秒。并集是 600 秒，直接相加也是 600 秒，所以它证明不了去重。有区分度的重叠是 09:55:00–10:00:00 加上 09:58:20–10:01:40：并集 400000 毫秒，直接相加 500000 毫秒。

3. 有数据的服务测试把片段放在周二，却只断言周一那格的真实秒数是 `null`、周合计是 600。片段若被时区错放到周三，这个断言仍然成立。必须同时断言 2026-11-17 的真实秒数、最长连续和活跃标记，以及周一、周三为空。

4. 周日 22:00 的阶段计算是对的：`publishAt` 等于 2026-11-22T14:00:00Z，`periodEnd` 等于 2026-11-22T16:00:00Z。也就是北京时间周日 22:00 到下周一 00:00。进程若在 UTC 环境把“周日 22:00”理解成 `2026-11-22T22:00:00Z`，那已经是北京时间周一 06:00，自然周已经换成 11 月 23 日。当前草稿用周期终点减 2 小时，不依赖进程时区；验收要用上面两个 UTC 瞬间钉住阶段，防止以后改成主机本地 `getHours()`。

5. 对外状态在周日 22:00 到周一 00:00 之间仍是 `published`。内部阶段 `early` 只进了指纹，没有进响应。小程序面板把 `published` 显示成“已发布”。方案要求这一版写明截至 22:00，并且不能当成完整周的最终结果。周一 00:00 才跑到的补生成，若之前没有首版，状态也是 `published`，截止时间等于周期终点，看不出错过了周日首版。

6. `data_cutoff_at_ms` 被限制在周期终点以内。12 月补传仍会计入原周，更新时间会变，但“数据截至”仍停在下周一 00:00。面板两行都会画出来，截至行会短于实际纳入的证据。

7. `coverage.complete` 固定为 false。面板因此始终把日均标题写成“已同步折算日均”，并始终显示覆盖不足。已发布且 7 天都有真实片段的周，也没有另一个标题可用。活跃天数只要有任何真实片段就 `available=true`；其余天都很短时，值是 0，面板显示“已确认 0 天”。缺测日和“7 天都确认未达 5 分钟”必须能被测试区分。

8. 无历史授权范围时，证据从该设备 scope 第一次打开的时刻起算。更早的真实片段会算出 `null` 并被保存。对话历史配置缺失、或配置的不是当前设备，都会走这条路径。配置存在但解析失败时，周报 GET 会变成 503，不限于那一台设备。生产设备已有的本周证据是否可见，取决于这个既有配置是否正好覆盖它。源码验收要用“功能上线前已经存在的片段”做夹具，确认授权设备仍能算进原周，未授权设备不会把别的绑定范围带进来。

9. 同一家长解绑再绑回，scope 改变，已保存周报对该读取变为另一份空报告；旧日表字段仍按设备继续能算。方案禁止把旧主人的报告自动划给新主人。同一主人绑回后是否还能看到自己发布过的周，当前草稿的测试期望是不能。这是产品行为，验收前要写成明确期望，避免一轮说它通过、下一轮说它丢数据。

10. 读取会写报告。指纹包含覆盖原因。分析依赖失败时，原因会改成保留补充的字样，秒数可以不变，修订号仍可能增加。现有依赖失败测试核对了秒数和遥测失败时的修订号，没有核对分析失败时修订号不变。指纹比较在写入事务之外，两个并发保存可能基于同一个旧修订各写一次。

11. 进程启动就对全部活跃绑定设备跑刷新。若第 8 条未收口，启动本身会把“空的当前周”写成报告，并把证据起点冻在启动时刻。

12. 同一 GET 的鉴权比旧实现严：草稿要求家长角色、家长账号角色和设备 active。旧实现只核对当前绑定的家长账号。设备角色令牌因此会从 200 变为 404。这可以保留，但要记成明确的合同变化，不能写成“旧接口行为没变”。错误时区仍是 400。B 账号仍应是 404。缓存头 `no-store` 已在草稿路由上设置，源码验收要防它被去掉；只改 JSON 而不禁缓存，修订后的 22 点首版会被旧响应盖住。

13. 上传协议在阅读到的设备 POST 里仍是原校验、原幂等和原事件类型。周报不得新增必填上传字段。`focus_id` 为空的 played 仍然计数。重复 `event_id` 不增加次数。冷却、姿态轮、心跳和未知 outcome 不进次数。只有冷却、没有 played 时，新指标是确认 0；只有未知 outcome 或完全没有提醒时是 `null`。

14. 672 没有截断，也没有异常标记。方案要求超过时保留真实数并提示。测试要用 673 和确认 0 各一条。

15. 示例页仍有固定的 10 次、0.8 时、6 天。新面板在标成内测真实数据的页面里，按秒展示并换成了分钟。现场另一套 live 页面不在本次阅读可以证明的发布路径里。API 相同不等于现役小程序已改。家长 Web 仍展示旧的达标率和守护分钟。

## 5. 旧字段怎么保持兼容

顶层这些键继续存在，算法不改：

| 旧字段 | 保持的结果 |
| --- | --- |
| `week_start` | 调用方没传时，改为正确的自然周周一。调用方传了合法日期时，保持“从该日起连续 7 个日历日”，即使那天不是周一 |
| `eye_health_rate` | 只含 correct 与 deviated 的百分比，分母为 0 时保持 `null` |
| `guarded_minutes` | 日表近似值：当天有有效姿态轮才把当天 focus 算进去，周毫秒合计后再四舍五入成分钟 |
| `posture_alert_count` | 日表 `reminder_played` 之和。没有行时仍是 0。不从原始事件回填日表 |
| `percentile` | 保持 `null` |
| `highlights` | 保持空数组 |
| `data_quality.valid_posture_rounds` | 保持 correct 加 deviated |
| `data_quality.missing_hours` | 保持 `null` |

默认周起点修正会改变“未传 `week_start`”时旧字段的数值窗口。这是方案已经点名的缺陷修复，不是顺手重算旧口径。显式周一的请求，旧数值应和修复前用同一日表算法算出的结果一致。

新指标与旧指标允许不相等。有真实片段但没有有效姿态轮时，`report` 的真实秒数大于 0，`guarded_minutes` 仍为 0。原始 played 与日表不一致时，以原始事件给出 `report` 的次数，同时保留日表上的旧次数，不写回日表。验收比较的是“家长 GET 的 `report` = 后台 GET 的 `report` = 小程序使用的同一对象”，不是“`posture_alert_count` = `report` 的次数”。

`report` 缺失、依赖失败或绑定范围变化时，优先整段沿用上一份有效报告，或返回带原因的不可用。不要把旧字段改成 `null`，也不要把 `report` 的 `null` 写成 0 去凑旧字段。家长 Web 在报告对象存在时会直接把 `guarded_minutes` 拼进“分钟”；这个值必须继续是数字。

小程序解析只接受 `data.report`，并且要求报告里的周一和设备与请求一致。顶层旧字段不能被当成新周报。非周一的查询即使 HTTP 200，也不能让小程序把归一后的另一周显示成用户刚选的那一周；当前解析会拒绝这种错位，这个拒绝要保留。

## 6. 交叉测试

夹具全部用合成时间、合成设备和不含个人身份的事件。不上传虚构数据去证明生产通过。家长读取和后台读取各打一次，比较去掉传输外壳后的 `report`。小程序只消费这次返回，不在页面里再算一遍。

| 编号 | 输入 | 旧字段 | `report` 与展示 |
| --- | --- | --- | --- |
| D1 | 时钟分别钉在第 2 节的五个边界，不传 `week_start` | 顶层 `week_start` 等于自然周周一 | 与客户端周一相同；周二 20:00 为 `collecting` 且发布时间为空；周日 22:00 为可区分的首版；下周一 00:00 才是周界已到 |
| D2 | `week_start=2026-11-17`，唯一 played 和唯一 5 分钟片段都在 11 月 16 日 | 次数和守护分钟按 11 月 17 日至 23 日计算，应为 0 | 自然周是 11 月 16 日，次数 1，活跃 1。小程序若请求的是 11 月 17 日，不能把 11 月 16 日的报告显示成所选周 |
| D3 | 只在 2026-11-23 00:00 有 played | 从 11 月 17 日开始的旧窗口计入；从 11 月 16 日开始的自然周不计入 | 11 月 16 日那周的次数保持 `null` 或原确认值，不把下周一算进本周 |
| D4 | 无任何事件的完整周 | 提醒次数 0，守护分钟 0，达标率 `null`，`missing_hours` `null`，百分位 `null`，高光为空 | 三项都是 `null`，原因是未收到数据。页面显示暂无数据或未能确认，不显示 0 |
| D5 | 有遥测，提醒只有 `suppressed_cooldown` | 旧次数仍按日表 | 新次数是 0，可用。页面显示已上报 0 次 |
| D6 | outcome 为大写或未知，另有一条 `played` | 旧次数只反映日表曾接受的 played | 新次数只计精确 `played`。未知单独不能把整个指标变成确认 0 |
| D7 | 同一 `event_id` 重放；另一个 id 的 focus_id 为空且 played | 日表不重复增加 | 新次数各计一次。刷新不增加修订号 |
| D8 | 299999 毫秒、299500 毫秒各一段 | 不改旧守护分钟算法 | 活跃 false。禁止用四舍五入后的秒数再判断 |
| D9 | 端点相接的 150000+150000；中间空 1 毫秒的同样两段；三段各 2 分钟且有间隙 | 旧字段不使用这个门槛 | 相接为活跃 1；有间隙和三段短片段都是活跃 0，但真实总秒数仍在 |
| D10 | 09:55–10:00 与 09:58:20–10:01:40 重叠 | 旧日表可能按入库规则另计 | 真实时长 400 秒，不是 500 秒；最长一段达到门槛 |

## 7. 独立复核脚本

脚本不导入应用，不打开应用数据库，不读取环境凭据。在任意目录执行：

```bash
TZ=UTC node /path/to/p003-weekly-oracle.mjs
```

本次运行的关键结果已写入第 2 节和第 6 节。SQLite `strftime('%Y-%m-%d', ms/1000.0, 'unixepoch', '+8 hours')` 与 JS 偏移日在 11 月 17 日零点前后 1 毫秒、11 月 23 日零点前后各抽了样，结果一致。这只说明这几个边界当前一致。原始 played 的 SQL 归日和 focus 的 JS 归日仍应在源码验收里各留一条午夜断言，避免以后只改其中一处。

脚本正文：

```javascript
import { DatabaseSync } from 'node:sqlite';
const DAY = 86400000, H8 = 8 * 3600000;
const dayOf = (ms) => new Date(ms + H8).toISOString().slice(0, 10);
const utcDateAdd = (date, days) => new Date(Date.parse(`${date}T00:00:00Z`) + days * DAY).toISOString().slice(0, 10);
const legacyDateAdd = (date, days) => new Date(Date.parse(`${date}T00:00:00+08:00`) + days * DAY + H8).toISOString().slice(0, 10);
function legacyDefaultWeek(now) {
  const today = dayOf(now);
  const dow = (new Date(`${today}T00:00:00+08:00`).getUTCDay() + 6) % 7;
  return legacyDateAdd(today, -dow);
}
function serverWeekStart(now) {
  const date = dayOf(now);
  const weekday = new Date(`${date}T00:00:00Z`).getUTCDay();
  return utcDateAdd(date, -((weekday + 6) % 7));
}
function clientWeekStart(now) {
  const local = new Date(now + H8);
  local.setUTCDate(local.getUTCDate() - ((local.getUTCDay() + 6) % 7));
  return local.toISOString().slice(0, 10);
}
function phase(now, weekStart) {
  const periodEnd = Date.parse(`${utcDateAdd(weekStart, 7)}T00:00:00+08:00`);
  const publishAt = periodEnd - 2 * 3600000;
  return now < publishAt ? 'collecting' : now < periodEnd ? 'early' : 'ended';
}
function merge(intervals) {
  const out = [];
  for (const item of intervals.slice().sort((a, b) => a[0] - b[0] || a[1] - b[1])) {
    const last = out.at(-1);
    if (last && item[0] <= last[1]) last[1] = Math.max(last[1], item[1]);
    else out.push([...item]);
  }
  return out;
}
function activeFrom(segments, weekStart) {
  const by = new Map();
  const weekEnd = Date.parse(`${utcDateAdd(weekStart, 7)}T00:00:00+08:00`);
  for (const [start, end] of segments) {
    let cursor = Math.max(start, Date.parse(`${weekStart}T00:00:00+08:00`));
    const stop = Math.min(end, weekEnd);
    while (cursor < stop) {
      const date = dayOf(cursor);
      const sliceEnd = Math.min(stop, Date.parse(`${date}T00:00:00+08:00`) + DAY);
      const list = by.get(date) ?? [];
      list.push([cursor, sliceEnd]);
      by.set(date, list);
      cursor = sliceEnd;
    }
  }
  const days = {};
  for (const [date, list] of by) {
    const merged = merge(list);
    const longest = merged.reduce((max, item) => Math.max(max, item[1] - item[0]), 0);
    days[date] = { longest, active: longest >= 300000, roundWouldPass: Math.round(longest / 1000) >= 300 };
  }
  return days;
}
```

用第 2 节的时间戳调用 `legacyDefaultWeek`、`serverWeekStart`、`clientWeekStart` 和 `phase`。用第 6 节 D8–D11 的毫秒区间调用 `activeFrom`。期望里，299999 和 299500 的 `active` 为 false，同时 `roundWouldPass` 为 true。
