## 0. TL;DR（一句话推荐）

**不直接套用任何单一重型记忆系统（mem0 / Zep / Letta），而是自建一套「轻量分层 user memory」：会话内滑动窗口（解决多轮无上下文）+ 结构化画像（懂这个孩子）+ 按需情节记忆（长期陪伴感）+ 延迟解耦（预加载注入 + 异步写）+ 本地隐私底座。** 借鉴它们的范式，不背它们的运维和隐私包袱。理由是三条独立证据链（KidsBench 反推结论 / 2026 语音工程约束 / 川哥 13 号文档已认可的工程哲学）全部收敛到同一答案。

## 2. KidsBench 评测的 9 个记忆系统，给了什么结论

KidsBench（`~/mycc/2-Projects/kidsbench-eval/`）本质是 **K12 中文陪伴场景的记忆系统对抗评测**，5 维（①意图 ②情绪 ③安全 ④记忆召回 episodic/semantic/procedural ⑤跨会话一致性），目标是「**反推自研记忆设计原则**」而非选型。已接入 9 系统（**已验证**，依据 docs/CAPABILITY_MATRIX + 各 *_VERIFIED_FACTS + project memory）：

| 系统 | 范式 | 表征 / 检索 | 早晚绑定 | 一句话定位 |
|---|---|---|---|---|
| **mem0** | vector-first 记忆层 | vector+entity / hybrid rerank | 早绑定（写时抽 fact） | 最快上手的 cross-session 个性化；语义记忆强、时序弱 |
| **Zep/Graphiti** | temporal 知识图谱 | 时序 KG / 16 recipes 多跳 | 早绑定（事件链） | 时序最强（「Q1 时什么是真的」）；重运维（图库） |
| **MemoryOS** | OS 式三层 | raw+vector+短/中/长 | consolidation | 三层老化整理；episodic+semantic |
| **MemMachine** | LTM+STM | 自带 score | 早绑定 | 长短期记忆分离，server 化 |
| **Cognee** | 知识图谱 cognify | GRAPH_COMPLETION | 早绑定（cognify 建图） | 图谱合成；**溯源最弱、无局部隔离**（隐私不利） |
| **Memobase** | **用户画像导向** | profile（LLM merge） | 早绑定（buffer→flush） | **专为「用户画像」设计**，date-level 溯源；最贴 K12 |
| **ReMe** | agentic 检索 | 多次 LLM 循环 | 晚绑定 | 读时多跳推理；贵、慢 |
| **Letta(MemGPT)** | OS 自管理 | core/recall/archival | 模型自管理 | 长时自治 agent；对语音过重 |
| **Hindsight** | **早/晚绑定可切** | recall(读不调LLM)/reflect(LLM合成) | 双模式 | 唯一一刀切早晚绑定的对照系统 |

**KidsBench team 三方（cc×grok×gemini）已挖出的核心结论**（**已验证**，依据 docs/EVAL_PARADIGM_RESEARCH 2026-06-09）：

1. **不存在全局冠军**——最优范式是 workload 的函数，不是排行榜。
2. **K12 真实 workload = 写极多、读极稀但深、高情感连续性**（W_daily 写读比 ~18:1，极端 ~120:1）→ **指向晚绑定 / 混合**，而非纯早绑定向量库。
3. **四维对抗矩阵**谁赢：①情感破 schema（「我是漏气的气球」3 月后回指）→ 晚绑定 ②超长聚合（学期提了几次妈妈不理解）→ 早绑定 ③画像自我纠正（讨厌→喜欢番茄）→ 晚绑定时序自愈 ④稀疏隐含情绪（5 天微弱沮丧）→ 晚绑定二次涌现。**结论：情感粘性场景偏晚绑定，高频可累加趋势偏早绑定 → 真实产品要混合。**
4. **K12 隐私是一等硬约束**：被遗忘权的「级联删除 + 可能重合成」成本，在儿童产品可能压倒性，通用 benchmark 给不出。
5. **反馈环路腐蚀**：晚绑定 synthesis 的幻觉会写回历史→永久沉淀→长期崩塌。静态评测测不出，需动态沙盒。
6. **出题/设计的北极星 = 情感粘性**：懂我→喜欢→粘性→爱用，情感/兴趣/承诺 > 关系 > 习惯 > 学业工具。

→ KidsBench 的结论不是「选某一家」，而是「**K12 该自研一套以画像 + 情感情节为主、混合早晚绑定、隐私本地化的记忆**」。这恰好就是本方案。

## 3. 2026 最新调研补充（标来源）

**记忆系统 benchmark（本轮观察，WebSearch 2026-06）**：
- LongMemEval：Zep/Graphiti **63.8%** > Mem0 **49.0%**（时序推理差 ~15 分）；Mem0 2026 自报 LoCoMo 92.5% / LongMemEval 94.4% @ <7k token（口径差异大，自报需打折）。
- 定位共识：Mem0 = 最快个性化；Zep = 时序事实；Letta = 长时自治 agent。
- 来源：[Medium AI Agent Memory 2026](https://medium.com/@wasowski.jarek/i-compared-5-ai-agent-memory-systems-across-6-dimensions-none-wins-6a658335ed0a)、[Mem0 voice agents guide](https://mem0.ai/blog/ai-memory-for-voice-agents)、[Redis agent memory](https://redis.io/blog/ai-agent-memory-stateful-systems/)

**语音场景工程约束（关键，本轮观察）**：
- 语音对话 **sub-200ms 才自然**，casual < 1s 总延迟；记忆检索（向量库 50–300ms 往返）是**主链路延迟瓶颈**。
- 行业范式：**session 开始预加载近期记忆 + 每轮异步写 + working memory 严格 session+TTL + long-term 按用途拆**；写操作**移出关键路径**（异步不阻塞）；长会话用**滑动窗口 + 检索恢复**（生产最常见模式）；逐轮写比会话末写**抽取质量更高**。
- 来源：[Mem0 voice guide](https://mem0.ai/blog/ai-memory-for-voice-agents)、[arXiv VoiceAgentRAG dual-agent](https://arxiv.org/pdf/2603.02206)

**儿童隐私监管（本轮观察，2026）**：
- FTC 新版 COPPA 强调 notice/consent + **数据最小化** + 透明；加州要求 AI 陪伴对未成年人**每 3h 提醒休息 + 提醒是 AI**；**Maryland 拟禁止用儿童 chatbot 交互数据训练模型**。
- 来源：[TrustArc 2026 儿童数据指南](https://trustarc.com/resource/ai-childrens-data-2026/)、[California Lawyers Assoc.](https://calawyers.org/privacy-law/regulatory-focus-on-ai-companion-chatbots/)

→ 三方调研全部强化同一结论：**语音 + 儿童 = 必须轻量、预加载注入、异步写、本地化、可删除、不训练**。

## 4. 小可现状：一张白纸（已验证，Explore 读源码）

| 维度 | 现状 | 证据 |
|---|---|---|
| 跨会话记忆 | ❌ 无 | WS 断开即丢 |
| 多轮对话累积 | ❌ 无 | LLM 每轮仅 `[system, 当前user]`，无 history（`pipeline.ts` streamChat） |
| 孩子画像 | ⚠️ 存了不用 | `profile-store.ts` 存 nickname/birthday/gender，**不注入 LLM** |
| LLM client | ❌ 不支持 history | `gemini-llm.ts`/`deepseek-llm.ts` 只收 systemPrompt+userText |
| 持久化 | 单向只写 | `conversation-store.ts` 仅统计用，不回灌 |
| 人设 | 固定写死 | `DEFAULT_SYSTEM_PROMPT`，全孩子同一份 |
| 多孩子 | 一账号一孩子 | `profile-store` `LIMIT 1` |
| prompt 组装 | **前端** | `apps/web/src/kidshub/prompts/`，server 只存不改 |

**最痛点排序**：① 多轮无上下文（孩子说「再讲一个」小可懵）② 画像存了不用（profile 数据浪费）③ 零跨会话（每次见面像第一次）。

## 5. 推荐方案：自建「轻量分层 user memory」

### 5.1 为什么不直接套 mem0 / Zep / Letta（5 条理由）

1. **语音延迟**：它们为文本 agent 设计，检索（50–300ms）+ 读时 LLM 抽取会击穿 sub-second 语音预算。
2. **运维包袱**：引入 Qdrant（mem0）/ FalkorDB（Zep）/ server（Letta），小可现在是 `node:sqlite` 单体，过重；KidsBench 自己跑这些就踩了三 venv 冲突 / torch×3 / HF 击穿一堆坑。
3. **隐私**：cloud 版（mem0/zep cloud）= 儿童数据出境 + 训练风险（撞 COPPA/Maryland）；OSS 版的「自主抽取」黑盒，不可审计、不可控删除（Cognee 甚至无局部隔离）。儿童产品需要**结构化、可审计、可级联删除**。
4. **成熟度错配**：小可白纸 + 内测期，过早上重型基础设施 = docs/13 已批判的「为远期架构服务当前 demo」反模式（团队三家一致反对）。
5. **KidsBench 的结论本就是「反推自研」**：它评测这些不是为了选一家背回来，而是为了提炼「K12 该怎么自建」。

### 5.2 但借鉴它们的范式（取其魂，不背其壳）

| 借鉴对象 | 借鉴什么 | 用在哪层 |
|---|---|---|
| **Memobase** | 结构化用户画像 schema + buffer→flush | L1 画像 |
| **mem0 voice guide** | 异步写出关键路径 + session 预加载 | 延迟架构 |
| **Letta / 生产范式** | 滑动窗口 + 检索恢复 | L0 working |
| **Hindsight** | 早/晚绑定按层分工 | L1 早 / L2 晚 |
| **Zep/Graphiti** | 时序事实（事实会变） | L3 远期 |

### 5.3 四层架构

```
L0 Working Memory（会话内 · 内存 · 零延迟）
   多轮对话滑动窗口（最近 6–10 轮），存 VoicePipeline 实例 + sessionId，TTL 随连接
   → 解决最痛的「多轮无上下文」。前置改造：LLM client 支持 messages[] history
   范式：纯 episodic、append、无 LLM

L1 Profile 画像（长期 · 早绑定 · 结构化 schema）★ 懂我粘性核心
   稳定画像：昵称/年龄/性别（已有）+ 兴趣[恐龙,奥特曼]/偏好称呼/口味/性格/近期情绪锚点
   写：每轮对话后【异步】用 LLM 按固定 schema 抽取「画像增量」，merge 进 profile（buffer→flush）
   读：session 开始一次性预加载 → 注入 systemPrompt → 对话中【零检索】
   范式：semantic、结构化、可审计可删除（隐私友好）

L2 Episodic 情节记忆（长期 · 晚绑定友好 · 按需检索）☆ 长期陪伴感
   重要情感/事件片段（带时间戳原文）：「上次考试难过」「养了布偶猫团子」
   写：异步，标记 importance + emotion + ts
   读：仅话题相关时检索（混合模式 50–200ms），可预取，不阻塞主链路
   起步：关键词 + 时间 + importance 排序检索（不上向量库）；不够再升 L3
   范式：episodic、晚绑定（读时 LLM 复原情感）→ 对应 KidsBench D1/D3/D4

L3 时序语义图（远期 · 数据驱动才上）
   只有当「事实会变」（搬家/换学校/不再讨厌番茄）成高频需求 → 引 Graphiti 式时序 KG
   现在做 = 过度工程
```

### 5.4 延迟架构（语音铁律 · 决定成败）

- **读 = 预加载**：WS 连接建立时一次性拉 (L1 profile + L2 近期情节摘要)，拼进 systemPrompt。对话过程中**不做同步检索**。
- **写 = 异步 fire-and-forget**：每轮对话后台抽取画像/情节，完全出主链路，失败不影响语音。
- **working = 内存**：滑动窗口零延迟。
- 话题切换才触发 L2 语义检索，且可由「下一问可预测」做预取（dual-agent 思路）。

### 5.5 隐私架构（儿童硬约束）⚠️ demo 阶段不实施 → 见 [docs/18 附录 A](./18-记忆系统实施计划.md)，接真实儿童用户前必补

- **本地优先**：记忆全存生产 `node:sqlite`，**绝不入第三方记忆云**（出境/训练风险）。
- **数据最小化**：L1 结构化 schema 只存必要画像字段，**不长期留全量原始 transcript**（或短 TTL）。
- **可级联删除**：账号/孩子删除时级联清记忆（复用现有 `deleteInvite` 级联，扩到 memory）。
- **不训练**：明确记忆数据不用于任何模型训练（Maryland 风向）。
- **家长可见可控**：admin / 家长端可查看 / 编辑 / 清空孩子画像（COPPA notice/consent + 加州）。
- **隐私墙**：儿童记忆数据禁外派任何外部引擎做处理（抽取用的 LLM 走自有网关，且 prompt 不带跨孩子数据）。

### 5.6 多孩子隔离（川哥之前问的「会不会混」）

- 记忆 key = **(account_id, family_member_id)**，孩子间物理隔离不串味。
- 现状一账号一孩子（`LIMIT 1`）→ 若一个家庭多孩子，需放开 family_member 维度 + 记忆按 member 分桶。
- account 级隔离已能分不同家庭（accountId 锚点），这条已成立。

### 5.7 ⚠️ 开放设计决策（请 team 重点评审）：记忆注入点放哪？

现状 systemPrompt 在**前端**组装（`kidshub/prompts/`），server 只存不改。user memory 该注入哪？

- **方案 X（前端拉取注入）**：前端组装 prompt 时调后端 `GET /memory/{member}` 拉 profile+情节，拼进 systemPrompt 下发。优点：不破坏「prompt 前端组装」现架构；缺点：真实设备端也要实现一遍。
- **方案 Y（后端注入）**：server 收到对话时，自己从 DB 读 memory 追加到 systemPrompt 末尾。优点：端无关、一处实现、隔离更强；缺点：要改「server 只存不改 prompt」的约定，需与前端 framing/死活分离协调。
- cc 初判**倾向 Y**（记忆是后端职责，端无关，隐私更可控），但需 team 确认与现有前端 prompt 架构（13 号死/活分离 + framing 正交）不冲突。

## 6. 演进路线（数据驱动 · 分阶段 · 多信号升级扳机）

| Phase | 内容 | 工作量 | 解决 |
|---|---|---|---|
| **P0 立即** | L0 working memory（LLM 支持 history + 滑动窗口）+ L1 profile 注入（数据已有，先用起来） | ~1–2 天 | 多轮无上下文 + 画像浪费 |
| **P1 一周** | L1 画像 schema 扩展 + 每轮异步抽取 + session 预加载 + 家长端可编辑画像 | ~1 周 | 懂我粘性 |
| **P2 按需** | L2 情节记忆（关键词+时间+importance 检索起步） | 按需 | 长期陪伴感 |
| **P3 远期** | 向量检索 / 时序 KG（仅当 P2 简单检索证明不够） | 数据驱动 | 多跳 / 事实演变 |

**升级扳机（复用 13 号「多信号 AND」哲学，≥2 信号 + 共识才升级）**：
- L2→L3 向量：情节量 > X 条且关键词检索召回失败率 > 25%；或「跨多条情节关联」query 占比 > 15–20%。
- 任何单信号只算观察期，不单独触发。

## 7. 与现有架构 / roadmap 的衔接（不返工）

- **docs/13（lore）**：L_user 与 L_world 正交，注入时**物理分区**（死知识 lore / 活状态 device_state / **用户记忆 user_memory** 三块分离声明），复用 13 号「死/活分离 + 多信号扳机」哲学。
- **docs/06 personality 5 维**（imagination/courage/humor/curiosity/warmth，V1.51 换肤换人格）：人格预设是「小可怎么说」，user memory 是「小可记得孩子什么」，正交可叠加——画像注入 + 人格数值注入同一 systemPrompt 不同块。
- **docs/06 VoiceResponse 结构化输出**（V1.53，text/action/emotion/intent）：异步画像抽取可复用同一次 LLM 调用的结构化产物（intent/emotion 顺便沉淀进画像），省一次调用。
- **前端 `kidshub/prompts/` + `knowledge/`**：注入点决策（§5.7）须与之协调。

> KidsBench 评了 9 家得出「K12 没有全局冠军、该自研画像+情感混合记忆」→ 2026 语音工程要求「预加载+异步写+本地化」→ 儿童隐私要求「最小化+可删+不训练」→ 小可是白纸正好一次设计对 → 所以**自建轻量四层（working/画像/情节/远期图谱）+ 延迟解耦 + 隐私底座**，分阶段数据驱动演进，而不是背一个重型系统的运维和隐私债。

## 9. Team 三发对抗综合（2026-06-18 · grok-4.3 / gpt-5.5 / gemini-3-flash，56s 全 RC=0 无降级）

> 总评：三家一致认可「P0/P1 自建轻量 L0+L1」方向站得住，但 v0.1 **低估了儿童合规、记忆质量（时效/幻觉）、流式首包阻塞、记忆准入** 四类难点。下面按置信度分层 + cc 裁决。

### A. 三家共识 → 必修（高置信）

1. **别「完全排除」mem0/Zep，留作离线评测基线**（grok 致命 + codex 重要 + gemini）。生产主线自建，但用 KidsBench（本来就在跑这些系统）+ 小可脱敏集做**离线对照**，用数据证明自建的召回/误记/延迟/删除成本优于或接近重型系统，而非靠理念判断。→ §5.1「完全排除」改为「生产自建 + 重型系统作离线基线对照」。
2. **L2 不能纯关键词**（三家）。儿童语言高度隐喻/指代/口语（「那只大蜥蜴」=霸王龙、「上次说的团子」），纯关键词召回会崩。→ 见 B-2 裁决。
3. **隐私严重不足**（三家，含 2 条致命）。最尖锐：**主 LLM + 异步抽取 LLM 本身就在处理儿童对话**（codex 致命）——「不进记忆云」远不够。补齐清单见 D。
4. **异步写不能裸 fire-and-forget**（三家）。会丢失/重复/乱序/幻觉污染。→ 改 Buffer-Flush（累积 3–5 轮微总结）+ 持久化 outbox + 幂等 key + pending→active（经置信度/确认才进稳定画像）。
5. **延迟真正的阻塞点是 connect 同步操作 + LLM Prefill**（三家），不是 v0.1 说的「零检索就安全」。→ connect 阶段**只读预先算好的 memory digest，禁止调 LLM**；注入做**摘要化 + token 预算检查 + 动态层级缩减**（不注入原文/50 条）；ASR final → LLM start 之间禁任何同步检索；实测端到端 P99 而非声称零检索。

### B. 关键分歧 → cc 裁决

1. **注入点（§5.7）**：codex【致命】+ gemini【重要】坚决要 **Y 后端注入**；grok 要 X 前端拉（担心与 13 号冲突 + 硬件端要重写）。**cc 裁决：采纳 Y，但做成「后端 Prompt Orchestrator」**——后端物理分区组装 `[人格]+[lore]+[user_memory 后端独占]+[实时context]`，前端/硬件端只提交 persona/lore 选择 + 会话上下文。**grok 担心的「硬件端要重写记忆逻辑」恰恰被 Y 解决**（编排在后端，端更瘦）；且 gemini 指出「家长一键遗忘要即时从 context 剔除」前端拉做不到、只有后端注入能做到。代价：需在 docs/13 补「user_memory 区块由 server 注入」变更记录。
2. **L2 检索起步**：grok 保守（合并进 L1 buffer，>200 条再向量）/ gemini 激进（直接 sqlite-vss + bge-small）/ codex 中间（结构化事件表 + SQLite FTS5 + rerank）。**cc 裁决：取 codex 中间态 = 结构化事件表 + FTS5 起步，预留向量列**。理由：① 纯关键词三家否决 ② 直接上向量对 node:sqlite 要装扩展且白纸期数据少收益不明 ③ FTS5 是 sqlite 内置零依赖（分词+BM25），远强于纯关键词、又不背向量运维 ④ codex 的结构化 schema（`who/topic/entities/emotion/valence/time/source_quote/importance/confidence/expiry`）同时解决 gemini 的发育漂移和 codex 的幻觉防线。FTS5 召回不够时再加 sqlite-vss 向量列（KidsBench 已有 bge-small-zh 经验，92MB）。

### C. 三方补的真盲点（v0.1 漏的，必补）

1. **记忆时效性 / 儿童发育漂移**（gemini 致命 + codex 呼应）：5 岁喜欢奥特曼，8 岁觉得幼稚；瞬时情绪（「今天讨厌数学」）不能固化成长期画像。→ L1 加 `last_updated`+`confidence`+来源；**矛盾检测**（孩子表达相反偏好→触发更新而非追加）；L1（稳定、家长可编辑、低争议）与 L2（带时间戳/来源/置信度/可过期事件）**严格分离**，L2→L1 升级须多次出现 + 时间跨度 + 孩子/家长确认。
2. **记忆准入策略（admission policy）**（codex 重要）：不是所有孩子说的都该记。默认**不存**精确地址/联系方式/学校班级/第三方儿童身份/健康心理/家庭冲突；自伤等安全风险只存最小 safety flag + 短 TTL + 高权限访问。
3. **反馈环路 / 幻觉防线**（codex 重要）：每条记忆留来源原句 + 抽取模型版本 + 置信度 + 最后验证时间；重要事实在对话中自然确认，不确认不进稳定画像；家长编辑优先级 > 模型抽取。
4. **同设备多孩子 speaker 识别**（codex 重要）：一台读书台兄弟姐妹共用，ASR 不知当前说话人，`(account_id, member_id)` 再准也会写错孩子。→ 会话开始**显式选孩子 / 绑定 / 声纹 / 轻确认**；低置信说话人只用会话短记忆，不写长期。

### D. 隐私加固清单（合并三家）⚠️ demo 阶段不实施，移至 [docs/18 附录 A](./18-记忆系统实施计划.md)

- 第三方 LLM 链路受控：零留存 / 禁训练 / 数据地域 / 最小字段发送 / 敏感字段脱敏 / 供应商审计（codex）
- 记忆准入策略 admission policy（codex，见 C-2）
- at-rest 加密（SQLCipher）+ 访问审计日志「谁何时读了哪条 profile」（grok）
- 家长同意版本持久化 + 撤回即停止处理 + 按字段删除 + 数据导出 + 保留期配置 + **删除证明**（codex+grok）
- 家长「一键遗忘」即时从 LLM context 剔除（gemini，依赖后端注入 Y）
- 默认关闭非必要长期记忆（high-privacy by default）

### E. 工作量 / 扳机修正（次要共识）

- P0 拆两步：先只做会话内 history（不写持久记忆），稳定后再注入已有 profile 字段（codex）。v0.1「1–2 天」偏乐观。
- 升级扳机改为**先建可观测指标**（首 token 延迟 / 记忆命中率 / 误提率 / 孩子纠正率 / 家长删除率 / 敏感误存率 / 跨孩子串记率），用**连续 2 周真实数据 + A/B** 校准，不预设百分比（三家）。

### F. 定稿 v0.2 净变化（一句话）

四层架构与「自建轻量 + 延迟解耦 + 隐私本地」大方向**保留**；**新增**：注入点定为后端 Orchestrator（Y）/ L2 = 结构化事件表+FTS5（非纯关键词非直接向量）/ 记忆时效性+矛盾检测 / 记忆准入策略 / 幻觉确认防线 / speaker 识别 / 异步写改持久队列+pending→active / 隐私加固 6 项 / mem0·Zep 降级为离线基线 / 扳机改实测指标。**P0 仍是「先会话 history + profile 注入」，最快见效。**
