## 2. 账号方案（分用户分账户 · 原型够用）

### 2.1 账号怎么来：三选一（推荐 B 邀请码）

| 方案 | 做法 | 取舍 |
|---|---|---|
| A 预置账号 | 运营预建账号发人 | 最省，谁是谁靠手记 |
| **B 邀请码自助**（推荐） | 运营发码，家长用码+设密码自助建账号 | 无需短信/微信，可控可追溯 |
| C 手机号验证码 | 手机号+短信 | 最真实但需短信服务，原型过重 |

### 2.2 实现要点（v2 补 codex 采纳）

1. **`account` 表**：`id / login_name / password_hash / role(parent\|admin) / created_at`。原型先 1:1 `family`。
2. **`invite_code` 独立表**（codex：邀请码是发放/核销资产，不是 account 字段）：`code_hash UNIQUE / used_by / used_at / expires_at`；注册在**事务内** `UPDATE...WHERE used_at IS NULL` 成功才建 account（防并发抢码/复用）。
3. **登录 + 库选型**（codex：贴合 ESM）：`POST /api/auth/login` → **bcrypt async** 校验（不用 compareSync，会阻塞事件循环）→ 签 **JWT 用 jose**（不用 CJS 的 jsonwebtoken）+ `iss/aud/iat/exp` + 高熵 `AUTH_JWT_SECRET`。`/api/auth/check` 改用 Authorization header（token 不进 URL 日志）。
4. **🔴 WS 鉴权**（codex 重点·浏览器硬限制）：**浏览器原生 WS 不能自定义 Authorization header** → 用**短期 `wsToken` query**（登录 JWT 换 60–300s 一次性 wsToken）或 **HttpOnly cookie + Origin 校验**。改动面：前端所有 `getVoiceWsUrl()`/`new WebSocket` 统一带 token；server **upgrade 阶段先校验**，失败 401/销毁 socket、不进 `handleUpgrade`；`VoicePipeline` 构造接 `authContext`。
5. **🔴 accountId 隔离闭环**（codex 重点·光放 JWT 不够）：
   - 业务表（feedback/child/session）补 `account_id/family_id/child_id`；
   - 所有 parent 查询**强制** `WHERE account_id=?` 或 join family；admin 路由单独放行全量；
   - `session.meta` **只允许** `sceneId/captureMode/tutorialUnitId`，孩子资料由服务端按 JWT child scope 查（不再信客户端自报昵称/年龄）。

### 2.3 顺手修 3 隐患

🔴 明文口令 → bcrypt + 移出明文（注：该口令历史上进过记忆索引，一并清）｜🔴 全局爆破锁 → per-account/per-IP｜🟡 token 无过期 → JWT exp。

**工作量** ≈ 1–2 天（真微信完整版）。

### 2.4 ★ 原型 Phase 0 落地版（推荐）：10 固定账号 + 邀请码 + mock 授权

川哥定的原型简化（2026-06-15）：限定 **10 个固定账号**、邀请码分发、web 页面**模拟微信授权**（不接真微信）。是 §2.1–2.3 的进一步减负——**绕开最重的真微信 OAuth**。

**与真微信版取舍**：

| 项 | 真微信版 | 原型 mock 版（本节·推荐） |
|---|---|---|
| 账号来源 | 开放注册/自助建 | **10 行固定 seed**（不开放注册） |
| 邀请码 | 独立表+事务防抢码 | **10 个码**简单映射即可 |
| 登录授权 | 真微信 OAuth(state/code2session/回调) | **mock 授权页**（仿微信 UI，点授权即过） |
| 服务号资质/短信 | 需要 | **不需要** |
| accountId 隔离 + WS 鉴权 | 需要 | **仍需要**（和登录真假无关，是分账户底盘） |

**mock 授权链路（形状同真微信，未来只换中间一段）**：
```
web 输入邀请码 → 后端校验(10 码之一)
→ 【mock 微信授权页：仿"小可想获取你的昵称头像 [授权]"】
→ 点授权 → 后端取码绑定的预置账号 → 发 JWT
→ web 存 token → 换 wsToken 带进语音 WS
```
**关键**：mock 只替换"微信那一下"，保留「校验码→后端发身份→token→带进 WS」的真实身份流转；将来接真微信只换授权页一步，前后端不返工（对上 [14-架构](14-三端互通架构设计.md) 的 account_identity 预留）。

**不能因登录是 mock 就省的 2 个底盘**（codex 🔴 仍适用）：accountId 落库隔离（10 测试者数据分开）+ WS 握手鉴权（身份带进语音）。其余 codex 🔴（OAuth 状态机等）被此简化绕过。

**工作量** ≈ 1 天（比真微信版省一半）。

## 3. <50 并发处理方案

> 瓶颈不在 Node 进程，在 **3 个外部依赖 + guard 自堵 + 背压炸点**。

### 3.1 瓶颈排序（v2 修正：guard 不裸奔）

| # | 瓶颈 | 处理 |
|---|---|---|
| 🔴 1 | guard 自堵（同 IP 60/天耗尽）+ x-forwarded-for 可伪造 | **先** WS JWT + 全局连接闸 → **再**改 per-account；`TRUST_PROXY`/代理 IP 白名单；`GUARD=0` 只内网/鉴权后用 |
| 🔴 2 | Gemini 私有代理网关（50 路流式无防护） | 加超时+重试+并发信号量（见 3.2）+ 压测 |
| 🔴 3 | 背压炸点（ASR/LLM/TTS 无上限无超时） | 见 3.2 |
| 🟡 4 | 火山 ASR/TTS 配额 | 查控制台、不够扩容 + 失败降级 |
| 🟡 5 | 单进程 + 同步 DB | 并发闸 + DB 分页/索引/busy_timeout |

### 3.2 处理动作（v2 补 codex 量化）

**🔴 背压防护**（codex 量化：火山卡 30s，50 路堆 ~48MB 线性涨）：ASR `connect timeout` + `pendingBytes` 上限超限断开；TTS `onSentenceEnd` 后 close；LLM/TTS 设 turn timeout；`WebSocketServer({ maxPayload: 64*1024 })`；发送前查 `ws.bufferedAmount`。

**🔴 LLM 防雪崩**（codex：50 路同时 503 统一重试→瞬间 100 路）：
- in-flight 信号量默认 **20–30**，压测后调；公式 `min(代理并发, Gemini RPM × 平均流时长/60, 内部预算)`；
- **只重试 5xx/网络错误、最多 1 次**、指数退避+jitter；**已收到首个 delta 不重试**；429 尊重 `Retry-After`。

**🟡 并发闸语义**（codex：别用一个数字管全部）：upgrade 阶段 active WS > 60 友好拒绝（50 用户 + 20% 重连余量）；ASR/LLM/TTS **各设独立 in-flight cap**。

**🟡 SQLite**（codex：同步 API 卡事件循环）：分页 + 索引 + 事务批写 + `busy_timeout`；Phase 0 不必换 PG，但别把"WAL"当无限并发写保证。

### 3.3 容量数量级（codex 估算，写进方案）

50 活跃用户 ≈ `50 inbound WS + 50 ASR WS + 0–50 LLM HTTP + 0–50 TTS WS` = 峰值 **150–200 个 socket/fd**（TTS 不及时 close 稳定态也近 150）；**RSS 200–400MB**（外部慢致 buffer 堆积再 +100MB）；CPU 主要是 ~500 条/s 音频帧转发，通常非瓶颈。真正风险：无上限 payload、同步 DB、大量 TLS 回调同时到达。

### 3.4 压测三脚本（codex 具体化，证明 50）

- **A** 50 WS 空连 → 看 FD/RSS 基线
- **B** 50 `chat.trigger` → 压 Gemini/TTS（不含音频）
- **C** 50 路 16k PCM 每 100ms 发、持续 10–30s 再 `audio.end` → 全链路真实负载

**指标**：RSS/heap/external、event loop delay p95、fd 数、ASR/LLM/TTS in-flight、队列等待、429/5xx/close code、各段 TTFT/P95/P99、`pendingChunks`、`bufferedAmount`、SQLite 写耗时。

### 3.5 可观测（codex）

固定日志字段：`accountId/childId/sessionId/turn/provider/stage/latency/errorCode/inflight/queueMs`。

## 6. Phase 0 执行计划（★ 零破坏现有 web）

> 硬约束（川哥定 2026-06-15）：**绝不影响当前 web 上正在跑的功能**（现有 admin 单口令登录 + 语音体验）。
> 核心思路：**不靠"小心改现有"，靠"结构上让现有路径根本不进新分支"**——即使新代码有 bug 也波及不到运行中的功能。

### 6.1 五个保护手法（贯穿全程）

1. **新增不改**：新文件/新路由/新表/新组件，最小化触碰现有代码
2. **feature flag**：`VITE_ENABLE_INVITE_LOGIN` + 后端 env，默认 **false**
3. **向后兼容**：accountId 隔离 + WS 鉴权都「有身份用身份、无身份退回现有行为」
4. **每步回归**：现有 admin 登录 + 语音体验每步 E2E 验证不退化
5. **可回退**：基于 tag `p003-pre-3end-arch-20260615`，每步小 commit

### 6.2 执行步骤（每步独立可验证可回退）

| 步 | 做什么 | 碰现有？ | 验证 |
|---|---|---|---|
| **0 数据准备** | 10 行 account seed + 邀请码（独立表/sqlite，不动 feedback.db 现有表） | ❌ 零触碰运行代码 | 现有功能必然不受影响 |
| **1 后端登录路由** | 新文件 `routes/invite-auth.ts`：`POST /api/auth/invite`(校验码→jose JWT)。**不动 `auth.ts` admin 登录** | ❌ 新文件 | 现有 `/api/auth/login` 照常；新路由独立测 |
| **2 前端 mock 授权** | 新组件 `InviteLoginPage`(邀请码+仿微信授权页) + flag(默认 false) | ⚠️ flag 关时现有 `LoginPage` **1:1 不变** | flag 关→现有登录原样；flag 开→新流程 |
| **3 accountId 隔离** | 业务表加 `account_id`(nullable)；查询**有 account 按其过滤、无身份(admin/匿名)保持现有全量** | ⚠️ 向后兼容 | 现有 admin 看 feedback 全量照常；新用户只看自己 |
| **4 WS 鉴权** | WS 握手**有 wsToken 解析身份、无 token 退回现有匿名**；`pipeline.ts` 只加一处"读 authContext" | ⚠️ 最敏感·纯可选增量 | **现有匿名 WS 继续工作(语音不断)**；新用户带 token 身份正确 |
| **5 E2E+灰度** | 回归现有 admin+语音 E2E 不退化 + 新流程 E2E；都过才决定是否默认开 flag | — | 双轨验证 |

### 6.3 最大风险点 + 对策

Step 4 WS 鉴权要碰 `pipeline.ts`（核心语音链路）。对策：做成**纯可选**——无 token 完全走现有路径，改动隔离在「读 authContext」一处，**不动核心 ASR→LLM→TTS 流**。现有体验零风险。

### 6.4 落地节奏

Step 0→1→2 可连续（纯新增）；Step 3、4 向后兼容增量（每步回归）；Step 5 灰度。**工作量 ≈ 1 天**，每步可独立上线/回退。
