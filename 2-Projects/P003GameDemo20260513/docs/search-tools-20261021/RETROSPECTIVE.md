## 经验教训

| 问题/证据 | 原因 | 今后的做法 |
|---|---|---|
| Git 已有工作树，Codeg 前端看不到 | 只完成 Git 登记，没有 Codeg 文件夹记录 | 同时核对 Git/应用目录两层登记，前端看不见时先查已有映射，不重复建分支 |
| 前端显示两个目录，但均“暂无会话” | 历史仍归 mycc 原会话，目录不会自动继承记录 | 用户要求接续时创建历史快照并导入目标文件夹；原会话保留 |
| 原连接正在执行，不能冒险原地 fork | Codeg acp_fork 的前端调用会更新原连接/session关联 | 通过受支持的原生 fork 指定目标cwd和完成轮次，再导入新ID；不直接改应用DB |
| 不同接口的会话计数不同 | 原生轮次、Codeg展示段和摘要计数不是同一口径，运行后还会变化 | 记录接口、边界、时间、ID；用内容和归属核对，不拿单一count断言丢失 |
| 找入口时递归扫描用户目录、尝试root Keychain浪费时间 | 没先利用当前部署路径、静态接口及已注入认证 | 限定搜索范围；检查可用工具与环境变量名；凭据仅内存使用，不输出值 |
| Git 分支隔离容易被误当设备灰度 | 线上派单仍由签发服务agentName决定 | 独立候选进程、数据目录、认证SN名单与派单；补共享入口时明确变更及回滚 |
| Search/Tool Calls跑通，但普通P2样例没选Fetch | 能力接入与自动选用、执行成功是不同证据 | 分层记录；受控Fetch单列，不把没抓取的样例当全链通过 |
| 本机账本高频全量读写造成尾延迟 | 性能路径做全表解析/持久化 | 有界索引和逐行持久化，保恢复语义；账本P95不能代替RTC指标 |
| 短答案与来源仍可能质量不足 | API成功和回答正确不是一回事 | 独立事实/时效/适用范围样本；答案长度约束与真实API回归分别测 |
| 续讲按文本与played_samples估算 | 缺少字级对齐，极早打断可能重复短片 | 如实记录限制，真人早/中/末段打断验收，不承诺精确续讲 |
| 用户把prompt发到新会话后旧会话仍有维护任务 | 两个会话可能同时写同分支/重复部署 | 新会话专注灰度；旧会话独立文档分支归档，绝不修改活跃工作树 |
