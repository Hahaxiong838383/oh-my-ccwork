## 本轮实际改动

- Worker 分解 TTS 的 DNS、TCP、TLS/WebSocket、预连接等待和提供方首 PCM 时间；连接失败按阶段脱敏，禁止输出签名 URL 或凭据。
- Worker 修复搜索结果播放期间单字“对”被开场回声门吞掉的问题。仅已满足“搜索结果 active、首 PCM 已发、精确附和、输入结束”的输入放行到搜索专用续播路径；没有放宽普通开场回声规则、控制出口或首句合同。
- Brain 保留搜索失败阶段与子类型，区分真实回答和失败说明，避免将 `completed` 误算成功。复核保留因果和适用例外，反馈具体未问数字；仍为一次检索、最多两次答复生成、原20秒总预算，全部后台执行。
- 候选 Worker 专属 `RES_OPTIONS=timeout:1 attempts:2`。隔离丢包实验有改善，但真实 DNS 长尾仍存在，不能记为性能已修好。现役与全机 DNS 未修改。

## 已定位与尚未定位

1. 真实TTS连接曾DNS等待5010ms；另一次系统调用取证看到连接本机53端口后poll超时5005ms，证实等待在解析链路，尚不能单独判定stub还是上游丢包。
2. 调整候选重试后，第15对B轮两个预连接DNS仍分别4005/4004ms失败；新连接随后成功，预连接等待4065ms、正文5599ms。单次resolver timeout不是整个getaddrinfo期限。
3. 第29对B轮正文3049ms，其中首句就绪前约2771ms、提供方首PCM268ms、预连接等待0。其它慢轮也有生成阶段和提供方差异，不能全部归因DNS或搜索代码。两臂旧版观测能力不同，阶段分解不能单独证明增量因果。
4. 模型复核改进了部分答案，但不能作为事实正确性的独立证明。含羞草内容失败保留，不能因HTTP成功、任务完成或有来源而放行。
5. 最终R15d的case5实际转写“恩恩”进入普通聊天，回到旧帽子话题，故原用例5整体仍失败。已追加一个严格限于搜索上下文的写法补丁，见[后续源码修复](R15_FOLLOWUP_ACK_ALIAS_20261024.md)；此补丁未部署，不计入R15d通过项。
6. 到期演练的Worker授权检查按时生效，但删除LiveKit房间的网络请求失败；服务端job结束不等于客户端已退出。该请求的传输失败已定位，尚未确定为DNS还是其它连接阶段，不直接套用TTS的DNS根因。第一次演练还遇到SSH/封装退出码和迟到清理问题，全部保留为失败；第二次没有把客户端等待超时改成成功。
