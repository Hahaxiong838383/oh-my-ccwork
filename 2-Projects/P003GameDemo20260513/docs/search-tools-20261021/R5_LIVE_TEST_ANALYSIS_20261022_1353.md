## 已确认的云端问题：口头答应了，但没有搜索任务

| 北京时间 | 证据 | 结论 |
|---|---|---|
| 13:44:53～13:45:20 | ASR 为“我查一下…”形式；没有对应任务；普通 LLM 给出帮忙查询、等待的承诺 | 没进入任务通道，聊天却承诺执行 |
| 13:46:58～13:47:10 | ASR 为“帮我查查…”形式；没有新增任务；普通 LLM 又给出查询、等待的承诺 | 明确搜索口语漏识别，同样出现虚假承诺 |

根因已由源码和独立执行确认：`search_policy::intent` 只认固定前缀，以上两种形式均返回 `None`，标准“帮我查一下…”返回搜索意图。对当前源码编译运行三条断言通过，未修改项目源码。

同时，Brain `searchChatPolicy` 已包含“不自行声称正在发起查询、接单由任务通道确认”的提示词，实测仍被普通回答违背。**只增强提示词不够**；必须让执行承诺受任务真实状态约束。

其中“帮我查查…”应补入明确请求识别；“我查一下…”可能是 ASR 缺词，也可能是用户描述自己的动作，不应无条件扩大为搜索。未能确认请求时应澄清，不能假装已经发起。

定位：Worker `src/search_policy.rs`、`src/search_tasks.rs`；Brain `src/tools/search-chat-policy.ts`、`src/routes/custom-llm.ts`。

重复时间分布与端侧约 5 秒的静默退出策略相容，但服务器没有 Android 的 `exit_reason`，无法区分用户手动退出、静默计时器或其他状态机触发。**不能把它写成已经证实的端侧缺陷，也不能声称云端重启/到期关闭造成。**

已完成结果后的正常静默退出与“尚有可续讲结果时过早退出”需要区分。优先让端侧按上述房间/trace 对齐：退出原因、触发计时器及 deadline、最后下行音频、最后输入、搜索 pending/remainder 状态、是否收到退出控制。若产品需要等待搜索/续讲时保持会话，再设计有上限、可取消的状态协同，不能简单永久延长超时。

## 下一步建议（未执行新修复）

1. **优先修云端漏派单和虚假承诺**：补明确口语变体和断句测试；含糊表达澄清；任务未接单时禁止执行型承诺。覆盖否定、引用、改查、取消，普通聊天继续不等待搜索。
2. **补接单链路诊断和有限恢复**：区分 transport/timeout/HTTP/上游处理，幂等核账与后台有限重试；用受控延迟/断连验证，不影响现役设备。
3. **端侧提供退出原因后联合修复**：先明确约 5 秒退出是否设计行为，再决定 pending/remainder 与空闲策略怎样协同。
4. 当前继续测试可使用标准“帮我查一下＋主题”；长插话或再次打断后，在退出前明确说“继续刚才的搜索结果”。该建议是绕开已知覆盖缺口，不代表问题已修复。
5. 维持现有两设备 P1 范围和原到期时间；不因本轮分析扩大设备、开启 P2 或延窗。
