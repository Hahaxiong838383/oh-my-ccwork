## 需要修什么

10月30日 B/S10-a：云端受理查询后播放了等待词，结果到达前端侧 `idle_timeout` 退房。v367 反编译显示，远端开始发声会清除 `responsePending`；空闲判定没有独立的“搜索仍在等待”状态。因此“我去查一查”会被当成已经答完。

只给既有 idle watchdog 增加有界的搜索待办保护。麦克风、首句 `input_ready`、真实发声状态、插话、主动退出均沿用原合同。不要假发 `speaking=true`、播放空音频或把全部对话超时改长。

## 事件合同

沿用可靠 `control` 数据通道，事件为 `session.search_pending`：

```json
{
  "trace_id": "当前会话的 trace",
  "ts_ms": 0,
  "src": "worker",
  "type": "session.search_pending",
  "lane": "L2",
  "payload": {
    "protocol": 1,
    "room": "当前已认证房间",
    "epoch": 1,
    "sequence": 1,
    "pending": true,
    "valid_for_ms": 25000
  }
}
```

- 只接受当前房间可信 Worker participant 发送、当前 `trace_id` 与 `room` 一致的消息；不能只检查 JSON 中的 `src`。
- `sequence` 会话内递增；`epoch` 在替换、取消等控制时推进。旧序号、旧 epoch、其他房间或旧 trace 一律忽略。
- 首次提交后最多保护 25 秒；服务器任务原期限仍为 20 秒，额外余量仅覆盖传输/领取。相同查询约每 2 秒重申剩余期限，普通聊天不会续期。
- 同一 epoch 首次接到 `pending=true` 时，以**本机单调时钟**建立 `deadline=now+clamp(valid_for_ms,0,25000)`。后续同 epoch 心跳只允许 `deadline=min(deadline,now+valid_for_ms)`，不能延长。
- `pending=false` / 期限到达立即释放该保护。同 epoch 已终止后，即使迟到的 true 消息序号较新，也不要重新激活。新查询的新 epoch 可建立新的期限。
- false 在连接仍存在时最多发送三次，间隔约 2 秒；不等待确认、不阻塞语音。完成/取消后“继续讲”不能复用旧查询的等待期限。新查询才重新建立期限。
- 切房、断连、结束聊天和主动退出时，无条件清理状态。断房不保证还能收到最后一个 false，不能依赖它才能退出。

## 最小实现位置

1. 在现有可信 control 事件分发处维护 `room/trace/epoch/sequence/deadline/terminal`；字段格式错误直接忽略。
2. 在既有 idle 判断中增加 `searchPending = now < deadline && !terminal`。把它作为正在等待业务答复的条件；保持既有用户输入和真实音频 activity 处理。
3. 等待词开始/结束仍可调用原 `responseCompleted()`，但不得清掉独立 `searchPending`。
4. 收到取消/完成消息或超时后恢复正常 idle 逻辑；不要在状态切换瞬间强制退房。等待保护期间，用户仍可说话、打断、取消或主动退出。

不要求新增 UI；如需诊断，只记录事件类型、epoch、sequence、剩余毫秒与清理原因，不录入儿童正文或凭据。

|---|---|
