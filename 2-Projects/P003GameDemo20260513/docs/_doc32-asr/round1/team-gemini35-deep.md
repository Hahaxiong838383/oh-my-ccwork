# 「小可本地 ASR 集成实施方案 (docs/32)」对抗评审报告

本次评审为只读评审，不修改任何代码与配置文件。以下针对实施方案的合理性、漏洞及开放决策进行深度对抗评审，按严重程度（阻塞性 vs 优化项）排序。

---

## 一、 阻塞性问题（必须修改才能开干）

### 1. 【问题】WebView 与原生的麦克风抢占及状态冲突
* **为什么是问题**：方案设计了「纯浏览器/降级时回退云火山 ASR」的 fallback 机制。在 Android 系统中，当 Web 层调用 `getUserMedia` 试图获取麦克风，而原生层（跑 KWS 唤醒词或 ASR）仍然持有 `AudioRecord` 实例时，会导致严重的底层音频硬冲突。WebView 往往会抛出 `NotReadableError` 或捕获到静音流；反之亦然。现有的 ASR 状态机和 JS Bridge 均未定义在降级或切换到云端时，原生层如何完全释放并让出硬件麦克风句柄。
* **建议修法**：在 `AsrBridge` 中增加显式的麦克风控制权交割协议。当 `isOnDeviceAsrAvailable() == false` 或触发降级时，原生层必须销毁或彻底 `release()` 原生的 `AudioRecord`，在原生释放完毕并回调通知 Web 端后，WebView 才能发起 `getUserMedia` 流程。

### 2. 【问题】Web 物理静音 AEC 时序滞后导致 ASR 自激
* **为什么是问题**：方案提出在 TTS 播放时通过 Web 发送 `notifyTtsState(true)` 物理静音原生 ASR。由于 JS Bridge 跨端调用是异步的（涉及 WebView UI 线程调度和 Java 消息循环），当 Web 执行 TTS 播放时，音频可能已经从扬声器输出，而原生 ASR 在数十毫秒后才收到静音指令。这极短的时间差足以让麦克风录入小可自身 TTS 的首个字音，导致 ASR 错误转写，引发严重的自激与死循环。
* **建议修法**：引入“播放前置确认屏障”。Web 端在收到 TTS 播放指令后，**禁止立即播放音频**；必须先调用 `notifyTtsState(true)`，等待原生层返回 Promise 确认「ASR 写入线程已暂停挂起」后，Web 端再正式启动 TTS 播放。或者更彻底地，将 TTS 播放能力也桥接至原生，由原生统一调度播放与录音的时序。

### 3. 【问题】KWS 切换 ASR 释放重开导致的“首字截断”
* **为什么是问题**：如果在唤醒命中后，销毁 KWS 的 `AudioRecord` 再重新分配/启动 ASR 的 `AudioRecord`，硬件启动延迟（通常在 100ms - 500ms 之间）会形成录音真空期。此时儿童在听到唤醒反馈后立即说出的前几个字（如“我想听...”中的“我想”）会被完美截断。
* **建议修法**：**必须**将 KWS 与 ASR 合并为单一 `AudioEngine`（如决策 5 所提）。使用一个常驻的 `AudioRecord`，并维护一个约 800ms 的环形 PCM 缓冲区。当 KWS 触发唤醒时，立刻把该缓冲区内的历史 PCM 数据与后续实时流一并送入新创建的 ASR `OnlineStream`，实现无缝“回溯式”ASR 启动。

### 4. 【问题】复用 `chat.trigger` 协议导致反馈录音库（captureMode）音频丢失
* **为什么是问题**：现有的云火山模式下，ASR 转写在服务端进行，服务端自然拥有原始音频流，可以直接在 `captureMode='feedback'` 时将孩子原声落库。一旦改成端侧 ASR 并复用 `chat.trigger(text)`，服务端只收到文本，完全丢失了孩子的原始音频文件，导致反馈库（用于后续 ASR 训练和语义纠错分析）直接废弃。
* **建议修法**：重构 `chat.trigger` 或新增专门的 `asr.final` 协议。当 `captureMode` 开启时，原生 ASR 不仅要触发文本，还必须将本次对话对应的原生 PCM 内存块（本地保存为轻量 WAV）通过 HTTP POST 或 WS 二进制通道异步补传给服务端，以便服务端重新关联文本与音频。

## 二、 优化项问题（可在编码期迭代）

### 5. 【问题】高频 Partial ASR 喂字幕导致 WebView UI 线程卡死
* **为什么是问题**：Zipformer-zh 流式识别的解码帧间隔通常为数十毫秒。如果原生 `onAsrPartial` 每次出词都直接无脑回调给 WebBridge，WebView 会在短时间内收到大量密集的 JS 调用。在低端机型上，这会抢占 WebView 单一的渲染主线程，造成界面动画卡顿、字幕渲染延迟。
* **建议修法**：在原生 `AsrBridge` 侧增加时间节流（Throttle）机制。限制 `onAsrPartial` 的回调频率最高为每 100ms 一次，且只有在转写文本内容真正发生改变时才发起跨端通信。

### 6. 【问题】端侧多模型运行导致的低端儿童平板内存 OOM 风险
* **为什么是问题**：小可的受众是儿童，其手持设备常为低端 Android 平板（2G/3G RAM 极其普遍）。同时运行 WebView（~200MB+）+ 唤醒词 KWS（~50MB）+ Zipformer ASR（模型落盘 50MB 级，运行时内存可能达 150MB+），极易触及 Android 进程的 OOM 阈值而导致应用被系统强杀。
* **建议修法**：初始化 `OnlineRecognizer` 时，原生层必须通过 `ActivityManager.MemoryInfo` 检查可用内存。若系统可用内存低于安全线（如小于 400MB），应强制将 `isOnDeviceAsrAvailable()` 设为 false，优雅回退到云端 ASR 模式，保护主进程不崩溃。

### 7. 【问题】童声判停起点值（rule2）硬编码硬着陆
* **为什么是问题**：方案建议将 rule2 取 1.2s - 1.5s（否决了 0.3s 的激进做法）。虽然方向正确，但不同年龄段、不同语言熟练度的儿童，其说话停顿差异极大。硬编码在原生层会导致后期调优极为被动。
* **建议修法**：在 `startAsr(mode, options)` 中支持动态传入配置参数。将 `minTrailingSilence` 作为 Web 配置项（可在后台动态下发），由 Web 侧根据画像或配置动态传给原生 JNI，以便在线热调优。

## 三、 对抗性决策判断与解答

针对方案末尾的开放决策，给出明确结论：

1. **模型起点**：**首选 type 9 (14M) 跑通集成，但生产必须用 type 20 (int8-2025)。** 14M 模型由于参数量极小，对口齿不清、带有童音和情绪波动的儿童语音识别率（CER）极差。必须以 14M 快速建立 JNI 联调，但保留一键切换 type 20 的能力，作为最终交付标准。
2. **麦克风衔接**：**必须复用同一 AudioRecord。** “释放重开”方案带来的切换 gap 会导致首字丢失率达到 100%（根据 Android 硬件起麦常识），属于体验性自杀，不可采纳。
3. **判停起点值**：**童声 rule2 起点应取 1.2s。** 小于 1.0s 会导致儿童在想词时被粗暴截断，大于 1.5s 会让对话显得极其迟钝。应支持 Web 端动态下发该值。
4. **server 协议**：**反对裸复用 `chat.trigger`。** 必须扩展协议以支持 `captureMode` 反馈音频的后置上传，否则会废掉反馈分析库。
5. **原生结构**：**必须合并为单一 `AudioEngine`**，作为 `AudioRecord` 的唯一持有者和数据分发源，避免双开抢占。

## 结论与总评

**总评：该方案目前不能直接进入 P1 写码。** 
必须先修改并收敛 **【阻塞性问题 1、2、3、4】**，明确「AEC 播放前置确认屏障协议」、「单 AudioEngine 环形缓冲区衔接」以及「反馈库音频补传机制」的设计细节后，方可定稿开干。
