## 一、可直接转发的人话版说明

家长任务按这条流程做：家长在小程序为绑定的读写台创建任务，填写任务描述、使用时长和奖励家族币；服务器保存后，安卓方舟接收任务并记录真实使用。达到条件后，孩子收到“任务已完成，等待家长确认奖励”的反馈，此时不加币。家长在小程序再次确认后，服务器登记唯一奖励，安卓自动到账，孩子不用再点领取。设备离线时显示“家长已确认，待到账”，联网后继续同步；重复确认或重试只发一笔。小程序和Worker后台都要看到任务进度、待确认、待到账、已到账及最新余额。本轮优先复用现有计时、游戏钱包和R1上传链路，补齐任务管理、家长确认、设备回执及收益汇总；当前是设计对齐，正式接口仍待开发上线。

## 二、已确定的产品流程

| 步骤 | 用户看到什么 | 三端应做什么 |
|---|---|---|
| 1. 家长创建 | 已创建，等待设备接收 | 小程序提交描述、目标时长、奖励币数；服务端核当前绑定并保存 |
| 2. 安卓接收 | 任务出现在方舟，开始显示进度 | 安卓拉取并存盘，回执收到的任务版本；只在云端保存不能标成设备已接收 |
| 3. 孩子完成 | 任务已完成，等待家长确认奖励 | 服务端核定真实使用达标；安卓展示完成反馈，小程序出现待确认任务；钱包不加币 |
| 4. 家长再次确认 | 家长已确认，待设备到账 | 服务端复核条件并生成唯一结算；奖励金额取已保存的任务规则，不信任客户端临时传入金额 |
| 5. 安卓到账 | 家族币到账，显示本次奖励 | 安卓自动执行已确认奖励，把加币、去重记录、业务流水一起存盘；孩子无需再领取 |
| 6. 三端同步 | 任务已到账，余额和历史更新 | 安卓回传到账结果、R1流水和新资产快照；服务端关联同一笔奖励，后台与小程序读取同源结果 |

主状态：**等待设备接收 → 进行中 → 已完成待家长确认 → 家长已确认待到账 → 已到账**。

“任务完成反馈”和“奖励到账反馈”分开，分别去重；重复拉取或重启不反复弹出。设备不支持时显示“待升级”，换绑或换档时显示“归属/存档待核”，不能假报任务已执行。

## 三、计时、任务与余额的建议口径

以下为实施建议，需在正式接口合同中固定；不能把全部细节视为已获产品逐项确认。

- 任务时长复用已上传的真实 `focus_segment`。重叠片段取并集，重复上报不重复计时，跨日按北京时间拆分。首页姿态、在位、心跳等推算量不参与任务发币；周报的连续5分钟活跃规则也不直接用于任务达标。
- 阅读打卡按每日累计目标分钟；使用频次按每周达到单日门槛的天数。沿用附件限制：每个设备每模板最多1个未归档任务，分钟1–300、奖励1–500币、频次1–7天。描述上限建议200字。
- 新任务从创建生效后计时，不把创建前历史使用拿来发新任务奖励。首日/首周按剩余窗口；重复任务每周期独立核算、独立确认。
- 修改不追溯改变本周期规则；取消保留原记录。取消前已完成、取消后才补传的有效证据仍可补算，并保留该旧周期的家长确认入口；取消后的使用不再计入。
- 日常游戏奖励与家长任务共用使用证据，但分别判定奖励；同一个任务周期只能发一笔，不能因为换了请求键再次发币。
- 保留当前设备游戏钱包。**服务端决定任务是否达标、应发多少及唯一结算；游戏可花余额仍由设备钱包承载，云端展示已同步副本。** 小程序不得使用“旧快照余额＋本次奖励”制造新余额。家长已确认但设备未到账的金额单列，余额保留最后同步时间。
- 本方案未将全部游戏收入和消费迁成服务端钱包，因此不承诺设备离线时服务端仍有实时权威总余额。正常/GM/unknown来源继续区分，不为了显示任务奖励而把整个钱包改标normal。

## 四、三端分工

| 负责方 | 本轮需要补齐 |
|---|---|
| 服务端 | 任务增删改查、当前绑定权限、周期规则快照、真实时长核算、待家长确认状态、确认后的唯一结算、设备同步与到账回执、R1关联、资产与收益查询 |
| 安卓方舟 | 拉取任务并存盘、展示任务/真实进度/完成反馈、拉取家长已确认奖励、复用游戏钱包原子加币与去重、上报到账/R1/新快照 |
| 小程序 | 真实任务表单和列表、待确认入口、家长确认操作、待到账/已到账展示、刷新进度和资产；移除任务Demo本地加币行为 |
| Worker后台 | 对应设备下显示任务描述、目标、奖励、周期进度、已下发/已接收版本、家长确认状态、到账状态、结算与流水关联及同步时间；与小程序同源 |

安卓通过既有设备鉴权和HTTPS拉取任务；启动、联网、进入任务页及时同步，在线按约定频率刷新。第一版无需新增消息队列或推送平台。现有30分钟配置轮询不能直接当作即时任务交付机制。

## 五、建议接口清单（均未上线）

家长接口沿用现有账号及设备归属，不新增另一套登录或绑定体系；设备接口沿用当前设备凭据；后台沿用管理员权限。

| 调用方 | 方法与建议路径 | 用途 |
|---|---|---|
| 小程序 | GET / POST `/v1/parent/devices/{public_id}/tasks` | 列表、待确认筛选、新建任务 |
| 小程序 | GET / PATCH / DELETE `/v1/parent/devices/{public_id}/tasks/{task_id}` | 详情、修改未来规则、归档取消 |
| 小程序 | POST `/v1/parent/devices/{public_id}/tasks/{task_id}/occurrences/{occurrence_id}/confirm` | 家长再次确认发币，返回唯一结算及待到账/已到账状态 |
| 安卓 | GET `/v1/device/ark/parent-tasks` | 当前任务、进度、完成反馈及家长已确认的待执行奖励 |
| 安卓 | POST `/v1/device/ark/parent-tasks/receipts` | 任务已存盘、完成反馈已展示、奖励已到账或执行失败回执 |
| 后台 | GET `/api/admin/devices/{sn}/miniapp/tasks` | 任务、进度、确认及到账状态；详情路径在正式合同中补齐 |

没有孩子领取接口。设备任务GET只取得已确认的奖励，不代替家长确认。

正式合同需给出：完整请求/响应JSON、字段类型和单位、枚举、缺省与null含义、当前绑定检查、版本冲突、创建/确认幂等键、重试规则、空列表、校验失败、状态冲突和重复确认样例。无登录401、其他家长404、参数错误400、版本/状态冲突409、依赖不可用503为建议口径。

## 六、兼容与对账要求

1. **保留现有上传合同。** focus计时继续走原Telemetry；奖励流水继续走原R1 URL、结构和ACK，不要求为这个功能重做已有上传协议。
2. **补齐奖励来源的读取。** 计划用R1既有字段关联：`reward_instance_id=settlement_id`、`source_kind=parent_task`、`source_id=周期ID`。服务端须核对结算、金额、币种、设备和存档后计入收益；只增加来源字符串白名单不够。
3. **一笔收入只算一次。** 服务端结算、设备到账回执、R1流水和资产快照是同一行为的不同证据，不能重复累计收益。ACK只证明收到流水，不证明任务已达标或币已到账。
4. **允许离线与乱序。** 孩子可离线积累使用证据，联网补传再核算；家长确认后设备离线则待到账。到账已存盘但回执丢失时，重试同一结算，不再加币。R1与快照先后到达均可补齐对账。
5. **保留当前归属。** 任务/结算绑定当前家长、设备、绑定代次和存档；换绑后停止旧任务及新奖励授权。已发授权遇到解绑进入待核，不承诺跨网络瞬时撤销，不自动补发到新身份。
6. **保留核算证据。** 任务周期与结算不能随原始遥测日志清理而丢失。旧记录、删除任务和已到账奖励均可追溯。

## 七、第一轮联调验收

以家长A和C机为首轮范围，保留现有绑定与存档。测试金额在正式联调窗口明确，不向生产预先注入奖励。

| 场景 | 必须看到的结果 |
|---|---|
| 创建并接收 | 家长A创建1分钟、小额币任务；服务器有记录，C机存盘并回执对应版本 |
| 完成未确认 | 真实使用达标，孩子收到完成反馈，小程序显示待家长确认；该任务尚无发币结算，钱包没有该任务增量 |
| 家长确认 | A在小程序确认，产生唯一settlement_id；安卓自动存盘到账，三端显示同一笔奖励 |
| 重复与并发 | 连续确认、不同幂等键重试、安卓重启或回执重放，均不再加一笔 |
| 离线恢复 | 确认时C离线显示待到账；恢复联网后执行原结算，回执丢失也不重复发币 |
| 历史与变更 | 跨日、补传、修改/取消、日志清理按固定规则核算，创建前使用不挪给新任务 |
| 权限与存档 | 家长B不能操作A的任务；解绑重绑/换档不能把旧奖励发到新身份 |
| 页面刷新 | 小程序和后台任务状态、资产收益及奖励历史均更新；同一奖励只有一条可追溯收入 |

余额核对须同时考虑测试期间其他游戏收入和消费，不能只用“前后差值=任务奖励”判断。每轮回执记录读取时间、HTTP状态、任务/周期/结算ID、设备版本、R1 record_id和对账结果，账号手机号脱敏，不附token或儿童正文。
