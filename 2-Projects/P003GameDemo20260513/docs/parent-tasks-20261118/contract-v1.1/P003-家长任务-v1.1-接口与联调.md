# P003 家长任务 V1.1 · 接口与联调

**适用团队**　服务端、安卓方舟、家长小程序、Worker 后台。**当前进度**　产品规则与验收口径已定版，等待研发回执。360 于 11 月 18 日 11:25 交付了设计稿；当时验证过的 HTTP 200 属于周报。家长任务的开发接入和真机联调结果仍待研发回填。

V1.1 在 V1.0 上补齐两项验收。孩子达标和钱包到账分别提示一次，同一笔到账奖励在小程序与后台的收益历史各显示一条。第 3 节沿用 V1.0 的全部 9 个接口、请求与响应。随包 JSON 顶层的 `contract_version` 是交付版本 `1.1`，设备 HTTP 正文里的 `contract_version` 继续传 `"1.0"`。360 早期交接稿中的接口草案已由第 3 节取代。[配套联调样例](P003-家长任务-v1.1-联调样例.json)

## 1. 主流程与验收标准

家长在小程序分别选择**目标和奖励家族币数**。方舟接收并保存任务，服务端根据已入库的真实使用记录核定进度。达标时锁定本期规则和奖励，家长确认后才产生发放授权。方舟钱包实际入账一次，并回传持久化回执。孩子无需再点领取。

主样例由家长选择 **20 分钟、35 家族币**。假设起始余额 100，期间没有其他收支：

| 时刻 | 孩子在方舟看到什么 | 家长在小程序看到什么 | 小程序、后台各自的本笔收入 |
|---|---|---|---|
| 19 分钟，尚差 1 分钟 | 当前进度，钱包 100 | 进行中，余额 100 | 0 条 |
| 满 20 分钟，等待确认 | 主动提醒开启时，首次提示“任务已完成，等待家长确认奖励”。钱包 100 | “待你确认 · 35 家族币”，余额 100 | 0 条 |
| 家长确认，设备离线 | 钱包 100，恢复联网后同步原授权 | “已确认，待到账”，余额 100 | 0 条 |
| 钱包实际入账，可信到账回执先到云端 | 钱包 135。主动提醒开启时，首次提示“35 家族币已到账” | 任务“已到账”。最近可信余额仍为 100 时，标“余额同步中” | 若逐笔流水仍在同步，可稍后刷新 |
| 对应钱包快照与关联的逐笔流水均同步，随后刷新或重启 | 钱包 135。重进任务页可查看到账结果 | 余额同步为 135 | 各 1 条 +35，同一结算；刷新后仍各 1 条 |

真实快照先到时，小程序可先显示 135。任务保持“已确认，待到账”，直到服务端核实该笔到账回执。流水 R1 和快照的到达顺序不影响最终条数。

### 孩子端两次提示如何去重

| 提示 | 第一次显示的依据 | 已显示的判定 |
|---|---|---|
| “任务已完成，等待家长确认奖励” | 方舟同步到服务端核定的本期 `awaiting_confirmation`，且允许主动提醒。此时还没有结算 ID | 按本期 `occurrence_id` 记录达标提示已展示。同一任务下一期有自己的周期 ID，可再次提示 |
| “35 家族币已到账” | 方舟钱包在当前绑定和存档下实际提交这笔结算，金额取本笔实际入账值，且允许主动提醒 | 按 `settlement_id` 单独记录到账提示已展示。先前显示过达标提示，仍应显示首次到账提示 |

方舟将两种展示记录分别保存在对应账号、绑定代次和存档的本地数据中。对同一周期或结算，重复拉取、返回页面、重启应用、重复确认或回执重试后，已经展示的那条提示都不重弹。关闭 `sync_to_xiaoke` 时，两种主动提示均为 0 次；孩子仍可在任务页查看状态，实际入账、余额和家长端确认照常。研发回执用同一任务的端侧展示记录或录屏核对次数，沿用现有 `task_received`、`wallet_applied` 两种设备回执。

### 小程序与 Worker 后台怎么核对一笔收入

1. 两端复用服务端核实的同一笔任务收入。在当前账号归属下按 `settlement_id` 去重。收益记录可追溯至 `source_kind=parent_task`、`source_id=occurrence_id`、`reward_instance_id=settlement_id`，并核对金额、币种与存档。
2. 达标和家长确认只更新任务状态。服务端核实 `wallet_applied` 后，任务可显示“已到账”。收益历史允许等原有逐笔流水同步，到账凭证与 R1 对上后，两端各有一条该笔正收入。后续补到的证据仅更新同笔记录。重复读、重试和乱序到达均保持各一条。金额相同但结算 ID 不同的两笔真实收入，各自保留。
3. 验收时在**小程序收益历史**和 **Worker 后台收益历史**分别查同一结算，核对两边条数均为 1、金额均为 +35；同时查该任务状态及最新可信余额。任务列表、余额差和 R1 的 ACK 都不能代替这两份历史读数。可以通过服务端的结算与流水映射查证，家长页面无需展示内部 ID。

现有逐笔流水读取入口为小程序 `GET /v1/parent/devices/{publicId}/ark/records`、后台 `GET /api/admin/devices/{sn}/miniapp/records`。两端均可按 `resource_id=family_coin` 筛选，结果也包含其他家族币收支。现有普通收益来源判定尚缺 `parent_task`，研发须回执如何把有效任务结算关联到两个视图的同一笔流水。仅筛选家族币或查看昨日收益汇总无法核对单笔。

## 2. 配置和核算

| 创建字段 | 每日阅读打卡 `daily_reading` | 每周使用频次打卡 `weekly_usage` |
|---|---|---|
| `goal_minutes` | 每日目标 1–120 整分钟，默认 30 | 每个达标日的门槛 1–120 整分钟，默认 30 |
| `required_days` | `null` | 每周 1–7 个自然日，默认 5 |
| `reward_coins` | 每期 1–500 整枚，默认 30 | 整周达标后一次发 1–500 整枚，默认 150 |
| 共用字段 | 两种均可选 `repeat` 或 `once`；`sync_to_xiaoke` 默认 true，只控制主动提醒；`description` 由家长选填 | 描述只在小程序和管理端使用，设备同步行的 description 固定为 null；V1.0 接口约定最多 200 个 Unicode 码点；省略、null 或空串均表示未填写 |

- 北京时间自然日、周一至下周一，以毫秒半开区间开始含、结束不含。首次从创建当日／当周起点核算归属明确的历史。按现行 Telemetry 已接收的 `focus_segment` 累加；同设备同事件重传只计一次，同设备后到的重叠片段沿用现网整条拒收。跨午夜按两天拆分，同一有效片段可用于不同任务。
- 按本期合计毫秒判达标。进度显示截断一位小数，59 秒显示 0.9 分钟，目标 1 分钟须满 60 秒。周任务按每天是否过门槛计天数。没有证据显示“暂无已同步记录”；有多少算多少；任务侧无 72 小时补传截止。跨换绑的使用须能证明发生时归属，不凭相同设备号迁给新家长。
- 列表一行对应一个周期。待确认置顶，进行中按最后编辑时间正序。上周待确认与本周进行中可并列，动作指向所点的周期。进行中编辑立即重算本期，达标锁定后不可改删该期。每设备每模板最多一个仍在计时或将继续开期的任务。一次性任务进入待确认或离开计时后可再建。
- 删除停止该任务后续计时和开期，保留历史及待确认入口。删前已发生的使用补传后可让旧周期重新待确认；新任务使用新 ID，可复用同周期真实历史。例如 28 分钟加删前发生、删后才收到的 5 分钟，旧、新任务各按 33 分钟核算，分别达标且分别获确认时各发一笔。

## 3. 服务端接口清单

路径均以既有服务域名为根。`P` 表示 `/v1/parent/devices/{publicId}/tasks`，`D` 表示 `/v1/device/parent-tasks`。花括号部分替换为服务端返回的 ID。列表和详情用外部设备 `publicId`，家长侧没有设备 SN。随附 JSON 的每个步骤均给出展开后的路径。

| 调用方 | 方法与新路径 | 请求要点 | 成功结果 / 使用时机 |
|---|---|---|---|
| 小程序 | `POST P` | 模板、时长、奖励、重复、提醒、描述；周模板另填达标天数 | 返回定义和首个周期。历史已足够，可立即返回待确认 |
| 小程序 | `GET P` | 活跃 / 历史视图，按游标翻页 | 按期展示进度、奖励、允许操作与钱包状态。无任务返回空列表 |
| 小程序 | `GET P/{task_id}?occurrence_id=…` | 指定任务和周期 | 取该期的规则、进度、结算和真实钱包余额；复核金额与刷新页面用 |
| 小程序 | `PATCH P/{task_id}` | `occurrence_id`、`expected_definition_version` 和要改的配置 | 仅更改进行中的该期及后续规则，重新核定；旧期锁定金额保持 |
| 小程序 | `DELETE P/{task_id}?occurrence_id=…&expected_definition_version=…` | 指定当前进行中周期和版本 | 返回停止时间；不再开期，旧数据、结算与确认权保留 |
| 小程序 | `POST P/{task_id}/occurrences/{occurrence_id}/confirm` | 正文 `{}`，金额由服务端读取 | 返回此周期唯一结算及状态。家长等待设备自动到账 |
| 方舟 Launcher | `POST D/sync` | 合同版本、客户端版本、当前绑定代次、存档 ID/来源，以及同步游标 | 返回任务/周期及有效的结算授权。拉取成功只代表拿到响应 |
| 方舟 Launcher | `POST D/receipts:batch` | 逐条提交任务已落盘或钱包已入账凭证 | 逐个返回成功、已重复、拒绝及原因，设备据此出队 |
| Worker 后台 | `GET /api/admin/devices/{sn}/miniapp/parent-tasks` | 沿用管理端读取权限 | 按同一任务、周期、结算读取进度、到账及对账状态，供排查 |

**共用约定。** 时间戳 `*_ms` 为 Unix 毫秒，时区 `Asia/Shanghai`，币数为整枚。JSON 请求使用 `Content-Type: application/json`，成功响应包在 `ok=true` 和 `data` 中；失败时 `ok=false`，`error` 和 `reason` 是机器可读字符串，见随包样例。家长携带现有家长 Bearer 凭据，服务端验证当前租户及设备绑定；设备携带现有设备 Bearer 凭据，服务端由凭据确定设备，核对绑定代次与目标存档。首次未取得可信存档上下文时可保留待发结算，暂不发可执行授权。换绑清除本机旧租户缓存，旧奖励保留在原账号。在途回执只能对原归属核账；旧凭据失效后无法安全核实时，旧账转待核，新租户不补领。管理端只读排查，发币入口属于家长。

**创建和编辑。** `template` 由家长选择，创建后不可改；`repeat`、`goal_minutes`、`required_days`、`reward_coins` 和 `sync_to_xiaoke` 在创建时传入家长最终选值。创建时描述可省略、传 null 或空串；返回未填写的描述统一为 null。PATCH 主动清空用 null 或空串。PATCH 只提交需要修改的可编辑配置；未提交的字段保留。日模板的 `required_days` 为 null。

**写请求与并发。** 小程序创建、修改、删除、确认均带 `Idempotency-Key`。同一调用方对同一路径同键同内容重试返回原操作结果；同键不同内容返回 409。修改与删除须在同一事务内校验当前期、定义版本及可操作状态。已经锁定或版本过时返回 409，刷新详情。确认以服务端归属和周期 ID 做唯一约束；换请求键、并发点击也必须返回同一个 `settlement_id`。确认请求不接收手机指定的发币金额。确认重试遇已存在结算，仍以同一 settlement 为准；若客户端拿到缓存的旧写响应，用详情 GET 刷新当前到账状态。

## 4. 方舟入账与三端对账

- `task_id` 标识任务定义；`occurrence_id` 标识列表中该次日/周周期；`settlement_id` 标识该周期唯一收入。历史行使用自己的规则版本和金额。设备接收指定版本并落盘后上报 `task_received`。设备版本用明确任务合同能力判断，不能仅看共用的安卓 versionCode。
- 方舟执行授权前校验设备、绑定代次、实际存档、币种、金额和有效期；过期时重新同步同一结算。授权只对接收这次同步的已鉴权设备有效，设备以该身份、绑定代次与存档共同隔离缓存。普通发放要求可确认归属的正常存档；缺失或冲突则保留待核。钱包把入账结果和结算去重凭证一起持久化，重启凭同一结果补报。缓存尽力保存；无法证实是否入账时停在待核，不再向新存档发一次。
- `wallet_applied` 携带结算与周期、目标存档、整枚币数、入账时间、关联流水及入账后真实快照的标识。服务端核对授权及已持久化的结果后才把任务标为 `paid`。批量回执的 HTTP 200 可部分成功；只出队逐项成功或已重复的条目。临时失败按退避重试，同 ID 异内容或归属冲突待核。
- 余额取 Ark 真实快照的 `wallets.family_coin`，币种与钱包的 `C-FAMILY-001` 对应。无可信余额返回 `null`；真实为零才返回 0。已入账但回执因离线迟到时，仍按执行时的有效授权核对。重新在线时不可按新币数或新结算补发。同一授权上下文内，入账回执引用的 `post_snapshot_id` 与入账后的快照关联，防止把旧余额当新余额；多个收支并发时按结算/流水关联，不用余额差倒推单笔是否成功。
- 保留现有 `POST /v1/device/telemetry`、`POST /v1/device/ark/state`、`GET /v1/device/ark/records/context`、`POST /v1/device/ark/records:batch` 原协议。新增服务端校验让 R1 的 `source_kind=parent_task`、`reward_instance_id=settlement_id`、`source_id=occurrence_id` 对应到同一笔授权和钱包变更。R1 只补逐笔对账，迟到不重复发币，不妨碍已核实的到账状态。

### 响应里哪些字段驱动界面

| 字段 | 约定 |
|---|---|
| `definition_version` / `rule_version` | 前者校验编辑、删除时有无并发修改；后者标识当前这行周期实际采用的规则。进行中重算时更新；锁定旧期保留自己的规则与币数。 |
| `device_received_version` | 方舟已落盘并回执的定义版本；null 表示尚无已接收证据，低于当前版本说明设备仍待同步新版。 |
| `state` / `actions` | `active` 进行中，允许的操作由服务端返回 `edit/delete`；`awaiting_confirmation` 待确认，可 `confirm`；`pending_payment` 已确认待到账；`paid` 已到账；`ended_below_target` 已结束暂未达成，后续可因补传转待确认；`needs_review` 归属或入账待核。后四种默认仅查看。读取详情不授予发币权。方舟收到同名 actions 时只用作展示，家长操作须走家长鉴权入口。 |
| `progress` | `usage_seconds` 为本期累计完整秒，`received_usage` 表示是否有可用真实片段。周任务返回 `qualified_days` 和逐日进度；用每天的秒数判单日达标，不能把周累计秒数除以门槛当作天数。 |
| `settlement_id` / `wallet` | 到确认才有结算 ID。钱包读模型以 `family_coin`、`snapshot_id`、`sync_state` 返回最近可信余额。`synced` 为已同步，`syncing` 为等待对应钱包快照，`unknown` 为暂无可信余额。余额与单笔到账状态分别渲染。 |

### 同步、分页与异常

家长列表以 `view=active|history` 选择当前/历史（默认 active），`limit` 默认 20、上限 100，后续用返回的 `next_cursor` 作为 `cursor`，null 表示最后一页。历史可看已结束或已到账行；旧期后来达标就重回当前待确认列表。

设备同步用响应中的 `server_now_ms` 与授权到期毫秒核对。首次取全量，后续可携 `since_cursor` 取增量。同一批次各页固定 `snapshot_version`，用 `next_cursor` 续页；到 `has_more=false` 才保存最终 `sync_cursor`。分页中断保留旧缓存和游标，错误响应不视为空列表。全量完整收齐后替换可用任务缓存；增量中 `deleted_task_ids` 仅停止对应定义，仍有效的旧周期、授权、钱包去重记录和待发回执要保留。客户端可在启动、联网恢复或进入任务页同步，服务不可用仅影响任务模块。游标失效后从全量重取。

| HTTP / 结果 | 三端处理 |
|---|---|
| 400 参数校验失败 | 提示修改目标分钟、币数、必填字段等；确认接口不接受客户端自报奖励。 |
| 401 / 403 / 404 | 401 沿现有登录或设备凭据恢复；403 表示当前角色/功能无权；家长查询不存在或不归自己绑定的设备或任务统一返回 404。 |
| 409 状态或幂等冲突 | 刷新该期：未达标不得确认，锁定后不得编辑；同请求键异内容、旧绑定/旧存档回执不能照单重放。同步游标失效走全量。 |
| 426 旧版设备无任务能力 | 提示待升级，保持设备原有功能。服务端按当前合同能力决定是否下发可执行授权；不以 APK versionCode 单独判定。 |
| 429 / 503 | 遵从 `Retry-After`（秒）；未返回时做有界退避。重试写请求复用原幂等键或原回执 ID。 |

## 5. JSON 主线与边界样例

以下正文和对象直接取自随包 JSON。JSON 的顶层包装只用来组织测试；每一步的 `request` 和 `response` 才是该接口的 HTTP 请求、响应。顶层的 `acceptance_cases` 描述客户端操作和跨端查账的预期结果，供研发验收使用。样例使用合成身份，默认省略鉴权值；实际调用时由各端使用本环境已有凭据。各场景独立，按同一场景的步骤顺序使用。

**小程序创建。** 调用 `POST P`，在请求头传 `Idempotency-Key: fx-create-01`。本例已同步当日历史 19 分钟，再收到 1 分钟即达标。家长提交以下配置。
