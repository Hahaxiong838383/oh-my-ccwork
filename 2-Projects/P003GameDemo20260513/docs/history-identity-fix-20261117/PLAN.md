# 小程序历史、时长与微信身份修复实施计划

> 执行方式：并行实现、逐项回归、独立复核后发布；用户已授权直接修复、上线和验证。

**目标：** 小程序与 Worker 管理后台显示同一设备真实可用的历史使用、奖励、库存及微信身份。

**依据：** [本轮审计](../history-identity-audit-20261117/AUDIT.md)；2026-11-17 用户追加口径：奖励进度秒计入使用时长，允许后台依据在位、姿态记录计算。

**架构：** 保留现有父账号、绑定版本、Ark 授权及短信登录。历史数据经 Analytics 内部只读接口提供，与遥测计算结果在同一个 Dashboard DTO 中供两端复用；微信身份由服务端使用客户端一次性登录码交换后保存。

## 决策与约束

- 用户的新口径覆盖此前技能中“禁止将奖励进度/在位用于时长”的旧限制。记录真实秒数与计算来源，不能把连续累计检查点逐条相加，也不能叠加同一时段的多种来源。
- 在位/姿态只推导有证据且有上限的区间；缺少结束事件不延伸至当前时间。历史总计另行展示，不限制为近 7 天。
- 旧事件可以作为历史观测显示，明确发生时间、接收时间、覆盖和来源未核实状态；不将 unknown 或 GM 自动变成 normal，不虚构双币余额。
- 当前 C 机历史例外沿用显式完整绑定作用域，不放开其他设备、转绑前数据和过期游标。
- 微信 AppID 以服务端配置为准，客户端上报用于核对；OpenID/UnionID 只接受微信服务端交换结果。手机号一致才能补齐当前账号，冲突不自动合并。
- 不解绑真实设备、不改队列、不恢复业务数据库、不发送测试短信；缺少真实微信授权时不宣称真人授权已验收。

## 重点边界

1. 301→600→902 秒与在位区间重叠，只计一次；重置、跨日、异常时钟明确处理。
2. 历史读取期间解绑/换绑，不能返回旧作用域结果。
3. 单一数据域不可用不应隐藏其他已知历史数据。
4. 已有账号重新微信授权，不创建重复家庭，不覆盖冲突 OpenID/UnionID。
5. 生产微信配置与真实授权是分别验收的状态；已有用户未经微信授权不能凭空补出身份。

- [ ] 外部依赖：生产AppSecret及真实微信用户授权仍待提供；微信平台尚未发布。本轮代码/服务/构建验证不能替代此项。
