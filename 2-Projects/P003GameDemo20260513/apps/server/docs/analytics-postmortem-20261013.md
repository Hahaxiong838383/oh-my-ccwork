## 经验与以后执行的规则

| 经验教训 | 本轮证据 | 下次怎么做 |
|---|---|---|
| 先确认瓶颈再选服务器 | 旧慢窗磁盘忙约 99%、iowait 94–98%、计算 1–6%、steal 0；当前 2 核 4GiB 经软件优化已过原目标 | 同时看 CPU 计算/等待、盘延迟、WAL 与事务分段；云盘型号用云侧元数据核实，不能由 ROTA=1 推断机械盘 |
| 同步 SQLite 会拖住 HTTP 接入 | 同一请求串联计时显示长等待主要在 request 回调之前；COMMIT 到 HTTP end 最大约 1ms | 用同一请求的时间线定位，不拿不同样本的 P95 直接相减；不要把提交后 ACK 当作未经证实的根因 |
| 缓存不是越大越好 | 96MiB writer 时延通过但整进程 RSS 278.22MiB，仍 FAIL；64MiB writer + 主查询 8MiB 全门通过 | 统计整个 Node 进程峰值，包括 worker；同时验时延、内存、完成率和既有业务健康，启动 RSS 不能代替峰值 |
| 独立上传通过不等于运维重叠安全 | 第一轮维护重叠只完成 17,000 条；无过期数据时 fact TTL DELETE 仍扫描百万行 | 发版前增加上传与维护重叠；检查实际 DELETE 的查询计划，用现有复合索引逐维范围查找；保持每表限额与事务回滚 |
| 低时延不等于吞吐提高 | 最终成功请求时延达标，但 198 次退避、193.646 秒总耗时仍在 | 同时报告成功请求分位、重试次数、总耗时与完整 ACK/数据库对账；保留失败、超时和未完成报告 |
| 优化必须保住数据语义 | 全程 FULL、提交成功后 ACK；超深坏事件曾在 structuredClone 阶段拖累同批正常事件 | IPC 传原始 JSON 文本后在 worker 校验；异常事件隔离、幂等、部分 ACK、丢 ACK 重放、失败回滚都要覆盖 |
| 聚合与保留期需要一起设计 | 原始数据保留 14 天，日报 90 天；仅靠原始记录不能支持晚到后的完整重算 | 使用最小化聚合事实保留历史贡献，seen 保留；迁移逐行核验 rowid 与九列，不只比较总数，不自动扩大日预算 |

## 保留的失败与没有采用的方案

- 合并提交没有改善目标场景，不采用；扩大缓存的 96/128MiB 候选有时延或内存失败，不能只挑通过指标。
- 不降低 SQLite FULL、不在事务提交前 ACK、不延长 HTTP 超时来换取通过，也不清空已提交的假数据或 seen。
- 90 秒截断来自旧隔离 wrapper，不是生产维护预算；正式 CLI 子进程 240 秒、systemd 300 秒。维护在负载开始后 25 秒启动，25 秒不是预算。
- TTL 旧单独探针约 5.43 秒、新探针整段约 4ms，缓存状态不同，不宣称固定倍速，也不据此解释旧 90 秒失败的全部原因。
- 端侧 10–20 分钟错峰、独立数据盘和长期拆分服务器仅为后续建议，未用于本轮通过计算，未改 APK、购机或迁库。基础设施重评入口见[服务器选型](analytics-server-sizing-20261013.md)。
