## 经验、失误与以后执行的规则

| 经验教训 | 这次发生了什么 | 后续固定做法 |
| --- | --- | --- |
| 权限问题和身份口径应分开说 | 服务器入口可用，真正缺失的是完整 MCU/JWT 身份；先前表达让用户以为要重新给权限 | 先只读核实入口；分别说明连接失败、认证失败、身份未对齐，不把三者混为一个阻塞 |
| 设备“SN”需要标明来源 | 客户端准备文档将 ADB 尾段当作云端 SN | 开窗前建立 MCU/JWT sub、ADB serial、客户端构建、台账四项对应；白名单始终使用已确认的完整云端身份，公开回执只留末 8 位 |
| 约定 RID 不等于实际 RID | 云端已经收到 13 批，但按旧 `ana-07000180-` 查到 0 | 同时看目标设备键、接收时段、批次数及实际 RID；对齐请求头与 ACK `request_id`，不改历史 RID 来制造命中 |
| HTTP 200 不等于全部 accepted | 13 批均 200，却有 27 条属性校验拒绝 | 每批校验 accepted/duplicated/rejected 互斥且覆盖提交 ID；再核 raw/seen/settlement。拒绝项终态处置仍需端侧确认 |
| 入库数不应直接减旧 pending | 2408 有效事件少于旧 pending=2423，但结算总数实际为 2435 | 以同轮起止 pending、期间新增、三分区和终态移队对账；未确认新增来源时不称丢失或重复 |
| 自动关闭要独立于对话存活 | 原 30 分钟窗口在下一条用户消息之前已经关闭 | 先注册并核验持久到期任务，再开总闸；报告绝对起止时间，任务失败重试，并保留关闭回执 |
| 已到期的窗口应重新开窗 | 用户要求延长时旧窗口已实关，并存在关闭间隔 | 先查 state/timer/owner；为新窗口使用新 ID、快照与截止时间，不把旧窗口改成“始终开放” |
| 关闭采集不等于回退数据 | 原窗口结束时已有真实 raw/seen，随后窗口继续使用同一数据库 | 先关总闸，再目标上传 false、白名单 0；保留新 DB/WAL/seen/HMAC，不恢复旧整库或清队列 |
| PM2 的环境边界必须收窄 | 控制器进程会临时加载管理员与签名密钥 | 只在远端进程内用现有受控 env；调用 PM2 时清理继承环境，普通 restart 重读 env-file，不使用 `--update-env`；不输出 token |
| 验证准入不必污染真实事件 | 开窗后需要确认目标能通过、其他设备仍被拒绝 | 目标空批应为 400 INVALID_BATCH，其他有效设备应为 403；另外核完整配置和非目标配置哈希，探针不插入事件 |
| 回执与交接包应冻结 | 延长后的回执已交给用户，用户确认已发送 | 保留 MD/JSON/校验表与 ZIP 的原字节；Git 归档引用同一文件，后续状态写新快照，不悄悄覆盖旧包 |
| 归档和生产操作要区分 | 当前任务只是经验、记忆和 commit+push，联调仍可能进行 | 在既有隔离分支提交具体文件，核远端 SHA 与工作树；不用全仓同步覆盖生产或 Air 的其他未提交工作 |
