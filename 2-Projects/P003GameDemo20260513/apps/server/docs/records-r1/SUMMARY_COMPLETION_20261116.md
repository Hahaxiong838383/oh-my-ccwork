# 两摘要与真实上报对账执行记录

用户要求：补齐昨日收益、最新物品和真实上报对账，并更新 Air Downloads 同名联调回执。

## 本轮实施口径

- 昨日收益：北京时间昨天实际领取的 normal reward_claim/tank_unlock 正向家族币、星尘分别合计；消费不抵扣，补领按实际领取日。只称“昨日已上报收益”，有值仍为 partial_history；未收到某币种收益保持 null。
- 最新物品：当前授权可见的全部存档/缸中，已同步获得记录的最新整组；含生态缸物品、小可装饰、待激活。不是当前缸或完整库存。不能越过最新 gm/unknown 回退旧 normal。不可归时的获得记录使“最新”不可确定；激活必须原归属/同存档/同实例对齐，不能再次计数。
- 现有设备、usage、Ark 保持；新记录查询异常单独降级。coverage.complete=false 保持。
- 选择已有真实记录的最小摘要投影。完整旧档库存或当前缸摘要需要端侧基线，不能由余额或到达顺序推断。

这是执行本次补齐要求的实现选择，不将它追记为用户已逐项确认的历史产品裁定。

## 执行计划

- [x] 在 records-store/contract 增加有界摘要查询，验证原 records、mini008、Telemetry 回归与 schema。

- [x] 只从真实设备日志/原记录/服务端数据库/API 获取对账证据；没有真实记录或手机证据即写未验，不注入生产合成业务。
- [x] 更新仓库回执及 Air 指定文件，备份原文并回读 SHA；明确已实现、已部署、真实入库、手机显示四层状态。

## 审核重点

1. 昨日按发生北京时间而非逻辑日/接收日；未知和异常时钟不虚构日期。
2. 没收到不能补 0；累计允许安全整数，不受单笔 1e9 上限误伤。
3. 新近 GM/unknown 获得不能被筛掉后回退旧 normal。
4. 激活只改变已获实例状态，不能跨 save/grant/epoch 或增发数量。
5. 数据不完整和真实设备未验在 API 与回执中保持显式。
