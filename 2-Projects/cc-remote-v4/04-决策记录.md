## V4 多版本服务清理 + 守护体系定版（2026-03-22）

<!-- type: config -->
<!-- status: 生效中 -->
<!-- scope: 全栈 -->
<!-- files: start.sh, watchdog.sh, api.py, ttyd-wrapper.sh, install-daemon.sh -->
<!-- related: V4 开机自启（2026-03-22 02:08） -->

### 现象

cc-remote 存在 V0/V3/V4 三套残留服务（launchd plist + 进程 + 临时文件），导致：
1. 端口/进程冲突
2. 维护时无法确定哪个服务在工作
3. 用户报告"连不上"时排查困难

### 排查过程

- `launchctl list | grep cc.remote` 发现 4 个守护进程同时加载（cc.remote.v3、dev.cc-remote、cc.remote.frpc、cc.remote.v4.frpc）
- `/tmp/` 下存在 5 个不同版本的 Caddyfile 和日志文件
- watchdog.sh 引用的 Caddyfile 路径（`/tmp/cc-remote-Caddyfile`）与 start.sh 生成的路径（`/tmp/cc-remote-v4-Caddyfile`）不一致

### 根因

多版本迭代过程中，旧版服务未被清理，新版服务的路径/配置未统一。

### 候选方案

| 方案 | 做法 | 优点 | 缺点/风险 |
|------|------|------|----------|
| A. 增量修复 | 逐个修 watchdog 路径、start.sh set-e、plist KeepAlive | 不停服 | 改一个可能引发另一个问题（事实已验证） |
| B. 干净重部署 | git checkout 恢复原版 → 删旧 plist → tmux kill-server → start.sh 重启 → install-daemon.sh | 状态完全可控 | 需要短暂停服 |
| C. Docker 化 | 把所有服务打包为 docker-compose | 彻底隔离 | 改造量大，ttyd+tmux 在容器里有兼容问题 |

### 决策

**选择**：方案 B — 干净重部署

**理由**：方案 A 已经在实践中失败（连续改 5 个文件导致服务全挂），证明增量修复对这种多组件服务不可行。方案 B 停服时间 <10 秒，风险最低。

**放弃的方案**：
- 方案 A（增量修复）：已验证失败。改 api.py 会丢 sessions dict 状态、改 start.sh 的 set-e 影响 tmux 创建、改 watchdog 路径不一致会导致 Caddy 起不来。条件耦合太深，不适合在线修
- 方案 C（Docker 化）：长期可考虑，但当前 ttyd+tmux+launchd 组合在原生环境运行稳定，容器化收益不明显

### 改动

- 删除 3 个旧版 plist（cc.remote.v3、dev.cc-remote、cc.remote.frpc）
- 清理旧版 tmp 日志（cc-remote-frpc.log、cc-remote-v3.log、cc-remote.log）
- git checkout 恢复 V4 全部文件到提交版本
- install-daemon.sh 重装 V4 两个 plist

### 验证

- `launchctl list | grep cc.remote`：只有 cc.remote.v4 和 cc.remote.v4.frpc
- 7 个组件全部在线：Caddy(:19443) / ttyd×3(:19001-19003) / API(:19100) / FRP / watchdog
- tmux 三个 session 存在
- 远端 cli4.hahaxiong.cc 返回 200
- 用户确认可正常连接使用

### 什么条件下该翻这个决策

- V4 架构需要大改（如增加 Docker 支持、换掉 ttyd、迁移到 K8s）
- 服务组件数量增加到 watchdog 管不过来的程度
- 需要支持 Windows 服务器（launchd 不可用）

### 教训

1. **不要在运行中的生产服务上直接改代码**：应该 git 分支改好 → 停服 → checkout → 重启
2. **两次修复没解决就立即 git checkout 回退**：越改越乱的沉没成本陷阱
3. **多组件服务的耦合比看上去深得多**：watchdog/start.sh/api.py/ttyd-wrapper.sh 四个文件的路径、进程名、tmux session 名必须完全一致
4. **清理旧版要彻底**：plist + 进程 + 日志 + 端口，漏一个都可能在下次排查时造成混淆

## V4.1.2 连接速度优化（2026-03-22）

<!-- type: config -->
<!-- status: 生效中 -->
<!-- scope: 前端 + Caddy + FRP -->
<!-- files: panel/index.html, Caddyfile, frpc.toml -->
<!-- related: V4 多版本服务清理（2026-03-22） -->

### 现象

手机端登录后，终端连接耗时较长（约 3-5 秒），用户体验不佳。

### 根因

三方面叠加：
1. 前端同时预加载 3 个 CLI 的 iframe（claude/codex/gemini），实际只用 claude
2. ttyd 的 JS/CSS/WASM 静态资源每次都重新下载，未设缓存
3. FRP 隧道传输未启用压缩，文本数据占用带宽大

### 候选方案

| 方案 | 做法 | 优点 | 缺点/风险 |
|------|------|------|----------|
| A. 只预加载 claude | `preloadTerminals()` 过滤只加载 claude iframe | 减少 2/3 初始请求 | codex/gemini 首次切换需等待 |
| B. Caddy 静态缓存 | Caddyfile 添加 `Cache-Control: max-age=604800, immutable` | 二次访问秒开 | 版本更新需用户清缓存（但 ttyd 版本稳定，极少更新） |
| C. FRP 压缩 | frpc.toml 添加 `transport.useCompression = true` | 减少传输带宽，对终端文本压缩率 90%+ | 需评估是否影响前端 WebSocket |

### 决策

**选择**：方案 A + B 先行，方案 C 待确认后加入

**理由**：
- A 和 B 无风险、立竿见影
- C（FRP 压缩）经评估：snappy 压缩在传输层透明处理，不影响前端 WebSocket 和 ttyd 显示。但属于传输层变更，单独提交便于回滚

**放弃的方案**：无放弃，三个方案均可用，只是分步实施

### 改动

**v4.1.2（已提交 5211e0c3）**：
- `panel/index.html`：`preloadTerminals()` 从 `allSessions.filter(s => s.default)` 改为 `allSessions.filter(s => s.default && s.cli === 'claude')`
- `Caddyfile`：添加 `@static path_regexp \.(js|css|wasm|map|ico|png|svg|ttf|woff2?)$` + `header @static Cache-Control "public, max-age=604800, immutable"`

**v4.1.3（待加入）**：
- `frpc.toml`：添加 `transport.useCompression = true`

### 验证

- v4.1.2 已部署，Caddy reload 成功
- 回滚点：`git checkout v4.1.1` 即可恢复

### 什么条件下该翻这个决策

- ttyd 版本频繁更新（缓存导致加载旧版 JS）→ 改用 ETag 而非 immutable
- 多用户同时在线场景 → 需要预加载所有 iframe
- FRP 压缩引入延迟或显示异常 → 回滚到 v4.1.2
