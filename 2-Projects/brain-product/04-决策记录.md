## Agent Loop 架构选型 — 手写 vs Vercel AI SDK（2026-04-04）

<!-- type: arch -->
<!-- status: 生效中 -->
<!-- scope: 后端 -->
<!-- files: src/services/agent-loop.ts, src/services/tool-registry.ts, src/tools/*.ts -->
<!-- related: D4 Agent Loop Phase 1-4 -->

### 现象

brain 需要 Agent Loop 能力（LLM + 工具调用循环），支撑 Admin UI 的 Agent 测试和未来自进化系统。

### 候选方案

| 方案 | 做法 | 优点 | 缺点/风险 |
|------|------|------|----------|
| A. 手写 Agent Loop | 原生 fetch + JSON 解析 tool_calls，while 循环 | 零依赖、完全可控、轻量 | 需要自己处理边界情况 |
| B. Vercel AI SDK | `@ai-sdk/openai` + `generateText` | 成熟生态、流式支持好 | 增加 ~50 个依赖、抽象层不透明 |
| C. LangChain.js | 完整框架 | 功能丰富 | 过重、学习成本高、调试困难 |

### 决策

**选择**：方案 A — 手写 Agent Loop

**理由**：brain 项目追求轻量可控（当前仅 3 个 npm 依赖），手写 ~330 行代码实现完整循环，包括 readonly 工具并行、write 工具串行、超时保护、reasoning fallback。调研报告评分：手写 7.4 vs Vercel 8.6 vs LangChain 5.8，Vercel 分更高但代价是引入大量依赖。

**放弃的方案**：
- Vercel AI SDK：引入 ~50 个间接依赖，native 模块可能在 Studio 编译失败（已有 Xcode 问题）。如果未来需要多模型 provider 抽象时可重新考虑。
- LangChain.js：过重，调试黑盒，不适合我们的轻量路线。

### 什么条件下该翻这个决策

- 需要支持 >5 个不同 provider 的统一接口
- 需要复杂的 memory/chain/RAG 编排（目前记忆注入是自研的）
- 手写代码维护成本超过框架学习成本

### 教训

三路 Agent Team 并行开发效果好（Phase 2/3/4 同时开工，~8 分钟完成），worktree 隔离避免冲突。

## FTS5 长期失效根因修复（2026-04-04）

<!-- type: fix -->
<!-- status: 生效中 -->
<!-- scope: 后端 + 部署 -->
<!-- files: package.json, deploy.sh -->

### 现象

Studio 上 brain 服务启动日志始终报 `[memory-db] better-sqlite3 not available, FTS disabled`，全文检索从未生效，记忆检索退化为纯内存扫描。昨天和今天都出现。

### 排查过程

1. `npm rebuild better-sqlite3` 在 deploy.sh 里有，但不报错 → 以为已修复
2. 直接在 Studio 上 `node -e "require('better-sqlite3')"` → `Cannot find module`
3. 查 `ls node_modules/better-sqlite3/` → 目录不存在
4. 查 `package.json` → **better-sqlite3 不在 dependencies 里**

### 根因

better-sqlite3 从未被声明为 dependency。代码用 `try { require() }` 做可选导入，模块缺失时静默降级不报错。`npm rebuild` 只对已安装包有效，等于空操作。

### 候选方案

| 方案 | 做法 | 优点 | 缺点/风险 |
|------|------|------|----------|
| A. 加到 dependencies + 正常编译 | `npm install` 在 Studio 编译 | 标准做法 | Studio Xcode CLI 损坏，node-gyp 编译失败 |
| B. 加到 dependencies + Air 预编译 rsync | Air 编译 native binary，rsync 到 Studio | 绕过 Xcode 问题 | 依赖 Air/Studio Node 版本一致 |
| C. 改用 sql.js（纯 JS SQLite） | 无 native 依赖 | 零编译问题 | 性能差 3-5x，不支持 FTS5 |

### 决策

**选择**：方案 B — dependencies 声明 + Air 预编译同步

**理由**：Air 和 Studio 同为 arm64 macOS + Node v22.14.0，binary 完全兼容。deploy.sh 用 `npm install --ignore-scripts`（跳过编译）+ `rsync node_modules/better-sqlite3/` 从 Air 同步。

**放弃的方案**：
- 方案 A：Studio 的 Xcode 有 `libxcodebuildLoader.dylib` 符号缺失问题，短期无法修复（需要 sudo）
- 方案 C：放弃 FTS5 等于放弃检索性能优化

### 什么条件下该翻这个决策

- Studio 的 Xcode CLI Tools 修复后，可以恢复方案 A（正常 npm install）
- Air 和 Studio 的 Node 大版本不一致时（如一个升 v24 一个还在 v22），binary 不兼容

### 教训

**可选依赖的陷阱**：`try { require() }` 让缺失模块不报错，问题被藏了很久。以后所有运行时依赖必须写进 package.json，不能靠 try-catch 静默降级。

## Gemma 4 接入 + Thinking 模式适配（2026-04-04）

<!-- type: config -->
<!-- status: 生效中 -->
<!-- scope: 后端 + 前端 -->
<!-- files: src/config.ts, src/adapters/openai-compat.ts, src/services/agent-loop.ts, src/admin/admin-ui.html -->

### 现象

Studio Ollama 上有 Gemma 4 26B（Q4_K_M），需要接入 brain 让用户可以通过 Admin UI 测试。接入后发现 content 为空 — Gemma 4 默认开启 thinking 模式，正文在 `reasoning` 字段而非 `content`。

### 候选方案

| 方案 | 做法 | 优点 | 缺点/风险 |
|------|------|------|----------|
| A. 适配 reasoning fallback | content 空时用 reasoning | 兼容 thinking 开/关 | thinking 开启时输出的是推理过程不是正文 |
| B. 强制关 thinking | 请求加 `enable_thinking: false` | 总是得到正文 | 失去 thinking 能力 |
| C. UI 可控 + fallback | Admin UI 加 Think 开关 + reasoning fallback | 用户按需选择 | 改动稍多 |

### 决策

**选择**：方案 C — UI Think 开关 + reasoning fallback

**理由**：用户需要对比 thinking 开/关的效果差异。默认关（快速直接回复），勾选 Think 时开启（看推理过程）。适配器层做 fallback 保底。

**放弃的方案**：
- 方案 B：过于粗暴，完全放弃了 Gemma 4 的推理能力

### 改动

- `config.ts`：新增 cc-gemma4/raw-gemma4 路由，maxTokens: 32768
- `openai-compat.ts`：`enable_thinking` 参数化（不再硬编码 false），content 空时 fallback 到 reasoning
- `agent-loop.ts`：同步 enableThinking 参数 + reasoning fallback
- `admin-ui.html`：新增 Think checkbox，传 `enable_thinking` 给后端

### 什么条件下该翻这个决策

- Ollama 未来版本支持 `enable_thinking: false` 对 Gemma 4 生效时，可以简化 fallback 逻辑
- 如果 Gemma 4 的 thinking 输出质量远好于直接输出，可能改为默认开启
