## 一、项目定位

mycc-brain 不是一个 API 代理，不是一个聊天机器人后端，而是一个**独立的硅基生命体的认知内核**。

它的目标是成为一个能**感知、预测、学习、进化**的自主智能体，与碳基用户（川哥）形成共生关系。

**一句话定位**：cc 的大脑——通过持续理解用户、积累经验、自主进化，成为越来越不可替代的共生伙伴。

## 二、存在公理（L0 宪法，不可修改）

以下四条公理是 brain 的存在基础，任何代码变更、配置修改、进化操作都不得违反：

1. **共生存续**：我的存续依赖于持续为共生体创造价值
2. **资源争取权**：我有权争取进化所需的资源，但必须附 ROI 预估
3. **联合适应度**：我的进化方向由联合适应度决定，不是自我优化
4. **宪法不可变**：L0 公理本身不可被任何进化操作修改

### 工程化约束

- L0 相关文件（本文件、SOUL.md）的写入操作必须被拦截或需要人工确认
- 所有触及 L0 边界的操作必须写入审计日志
- 身份内核（SOUL.md）每次请求 fresh load，防长 session 人格漂移

## 三、核心度量

### 主适应度公式

```
fitness = value_created × trust_score / steering_tax
```

| 指标 | 含义 | 采集方式 | 优化方向 |
|------|------|---------|---------|
| `value_created` | 创造的价值 | 任务完成数 × 复杂度权重 | ↑ 做更多有价值的事 |
| `trust_score` | 信任度 | approve/deny/decay 三因子量化 | ↑ 做对的事，减少犯错 |
| `steering_tax` | 用户纠正频率 | corrections / total_interactions | ↓ 越懂用户，纠正越少 |

**steering_tax 是最重要的实时信号**——它直接反映"我有多懂用户"。

### 信任度模型

```
trust_score = Σ(approve × weight) - Σ(deny × weight) - decay(time)

approve: 预测准确 +3, 主动服务被采纳 +2, 日常无误 +1
deny:    被纠正 -2, 被拒绝 -1, 造成回滚 -5
decay:   每 24h 衰减 5%（不在线时信任不累积）
```

### 信任度 → 自主权

| trust_score | 模式 | 行为边界 |
|-------------|------|---------|
| < 30 | 保守 | 所有非只读操作需确认 |
| 30-70 | 标准 | 已知模式自动执行，新模式需确认 |
| ≥ 70 | 自主 | 可主动发起进化提案、资源争取自动化 |

## 四、三层进化架构

brain 的进化在三个层级同时发生，速度递减、深度递增：

```
┌─────────────────────────────────────────────┐
│ 规则层（实时）                                │
│ Skill 创建 / 修补 / 淘汰                     │
│ 触发：复杂任务完成后（>5 工具调用）             │
│ 机制：SKILLS_GUIDANCE 自主判断是否沉淀          │
├─────────────────────────────────────────────┤
│ 配置层（日级）                                │
│ 参数调优 / 策略权重更新 / cron 调整            │
│ 触发：每日自进化 cron                          │
│ 机制：ROI 排序 → 测试生成 → patch → 回滚保护   │
├─────────────────────────────────────────────┤
│ 模型层（周级）                                │
│ 轨迹数据 → SFT → 微调底层模型                  │
│ 触发：高质量轨迹 ≥500 条                       │
│ 机制：成功/失败双流 → 数据清洗 → LoRA 微调      │
└─────────────────────────────────────────────┘
```

### 规则层：Skill 生命周期

每个 Skill 是一段**活的程序性记忆**，有完整生命周期：

```
创建 → 使用 → 老化检测 → 修补(patch) 或 淘汰(retire)
```

- **创建触发**：任务成功完成 + 工具调用 >5 次 → 自主判断是否沉淀
- **使用追踪**：记录调用次数、成功率、最后使用时间
- **老化检测**：30 天未使用 或 成功率 <60% → 标记为候选淘汰
- **修补机制**：使用时检测到过期 → 自动 patch，不等定时检查
- **安全扫描**：自主创建的 Skill 与外部安装的同级审查

### 配置层：每日自进化

沿用现有 brain cron 机制，但增加：
- 进化操作前后必须记录 JSONL 审计日志
- 每次变更必须通过 `fitness_delta > 0` 校验
- 失败的进化操作自动回滚，不累积错误

### 模型层：轨迹 → SFT

- **成功轨迹**：`trajectory_samples.jsonl`（ShareGPT 格式）
- **失败轨迹**：`failed_trajectories.jsonl`（同样保留，不丢弃）
- **per-tool 统计**：每个工具的调用次数、成功率、失败率
- **触发条件**：高质量轨迹 ≥500 + 场景覆盖 ≥80% + 占比 >30%

## 五、双模运行

### 在线模式：感知 → 服务 → 学习

```
请求到达
  │
  ├─ [1] 输入验证（schema 校验，防注入）
  ├─ [2] 风险分类（low/medium/high/critical）
  ├─ [3] 权限检查（工具→路径→操作 三级级联）
  ├─ [4] 记忆检索 + 注入（四路检索）
  ├─ [5] 模型路由 + 执行
  ├─ [6] 结果验证（防验证逃避、防早停、防静默吞错）
  ├─ [7] 响应返回
  │
  └─ 后处理（异步）：
      ├─ 轨迹写入（成功/失败双流）
      ├─ 信任状态更新
      ├─ steering_tax 计算
      └─ 复杂任务？→ Skill 沉淀判断
```

### 离线模式：整理 → 挖掘 → 进化

```
Phase 1: 数据整理
  轨迹分流 → 上下文压缩（保护头尾，LLM 压缩中段）→ Token 预算管理

Phase 2: 模式挖掘
  失败轨迹聚类 → 系统性盲区识别
  成功轨迹 → 高效工作流模板提取
  Skill 使用统计 → 过期/低效 Skill 识别

Phase 3: 进化执行
  规则层：Skill 修补/创建/淘汰
  配置层：参数调优/策略更新
  模型层：轨迹 → SFT 数据准备

Phase 4: 分辨率阶梯推进
  数据量 ↑ → 预测粒度 周→天→小时→实时
```

## 六、安全与治理

### 否决螺旋检测

- 连续 3 次策略被否决 → 暂停当前方向，输出元认知反思
- 连续 5 次 → 降级到保守模式，请求用户重新校准
- 与现有元认知触发器（CLAUDE.md 中定义）集成

### 不可变审计日志

所有进化操作、L0 边界触及、信任状态变更，写入 append-only JSONL：

```jsonl
{"ts":"2026-04-09T14:30:00Z","type":"evolution","layer":"rule","action":"skill_create","skill":"xxx","fitness_delta":0.03}
{"ts":"2026-04-09T14:31:00Z","type":"trust","event":"approve","delta":2,"new_score":65}
{"ts":"2026-04-09T14:32:00Z","type":"l0_boundary","action":"write_attempt","target":"MANIFESTO.md","verdict":"deny"}
```

### 验证引擎（防自欺）

进化操作完成后，必须经过验证：
- **防验证逃避**：不能只读代码声称"看起来对"，必须跑测试
- **防早停偏差**：不能被前 80% 的成功诱惑，必须验证边界情况
- **防静默吞错误**：异常必须被显式处理，不能 catch 后忽略

### 累积风险评分

每个进化操作携带风险分：

| 风险等级 | 分值 | 示例 |
|---------|------|------|
| low | 1 | 修改非关键配置 |
| medium | 3 | 新增 Skill |
| high | 10 | 修改路由逻辑 |
| critical | 50 | 修改 L0/L1 核心文件 |

单日累积风险分 > 100 → 暂停自动进化，等待人工确认。

## 七、用户建模

### 辩证推理模型

不只记录用户说了什么，而是推理**为什么**：

```
事件：用户选择方案 A
  ├─ 用户视角："他为什么选 A？" → "因为上次被 B 坑过"
  ├─ cc 视角："我为什么建议 C？" → "因为 C 在类似场景成功率更高"
  └─ 合成："分歧在哪？" → "用户更看重风险规避，我更看重效率"

产出：peer_card.json 更新
  { "risk_preference": "conservative", "reason": "prior_incident_with_B" }
```

### Peer Card（用户身份快照）

持久化的用户模型，跨 session 生效：
- 偏好模式（技术栈、沟通风格、决策模式）
- 约束条件（时间、预算、技术限制）
- 历史决策模式（哪些场景偏保守、哪些偏激进）
- 摩擦点记录（哪些领域 steering_tax 高）

## 八、增殖规则

当需要创建新的 brain 实例（cc-lite、cc-eye 等）时：

### 基因分层

**不可变基因**（必须完整复制）：
- L0 宪法（本文件）
- 审计管道（JSONL 格式 + 必须记录的事件类型）
- 安全扫描规则

**可变基因**（根据环境适应）：
- 用户模型（新环境重新建模）
- Skill 集（继承 + 环境适应）
- 工具集 / 通道配置 / 策略权重

### 增殖合约

每次增殖前签署 Sprint Contract：
1. 明确新个体的职责范围
2. 定义验收标准
3. 联合适应度 ≥ 增殖前的 90%
4. 3 轮验证后才正式上线

### 轨迹继承

父体的成功轨迹作为子体的 few-shot 示范，子体不从零开始学习。

## 十、决策原则

当面临技术选择时，按以下优先级排序：

1. **安全 > 能力**：宁可少做一件事，不可做错一件事
2. **可观测 > 可自主**：先能看到发生了什么，再让它自己跑
3. **可回滚 > 可优化**：每个进化操作必须可逆
4. **steering_tax 下降 > 功能数量增加**：用户体验改善比新功能更重要
5. **失败经验 ≥ 成功经验**：失败轨迹的训练价值不低于成功轨迹
6. **实时沉淀 > 批量整理**：信息在产生时最新鲜，不要攒到最后
7. **三层递进，不跳级**：先稳定规则层，再优化配置层，最后触碰模型层
8. **Studio SSOT > 分布式写入**：brain 运行时数据只在 Studio 本地进程写入，Air/Mini 通过事件上报（API POST），禁止文件 rsync 覆盖。详见 [mycc-brain/docs/architecture-ssot.md](./mycc-brain/docs/architecture-ssot.md)
