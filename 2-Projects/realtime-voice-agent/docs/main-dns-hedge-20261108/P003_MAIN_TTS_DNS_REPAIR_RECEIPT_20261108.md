## 结论与方案

主池此前仍依赖系统解析路径，TTS 域名解析挂起时，重新建立连接仍可能卡在同一路径。本轮复现了旧版有 ASR 输入、没有可听答复；新版本在相同故障下注入同一音频，利用独立上游恢复语音。

这不能把全部历史慢响应归为腾讯 DNS：当前机器的系统上游是 Google/Cloudflare，本轮没有证明某一家供应商是历史唯一根因。

采用 Codex/Grok 一致推荐的最小方案：TTS 解析等待超过 **200ms**，在需要时使用系统已配置的真实上游作为备用；全进程最多 **2 个额外查询并发**、不排队。保留已有 650ms 连接恢复和总 10s 截止；正常快速解析不发起备用。没有新增常驻探测服务、定时压测或全机 DNS 自动切换。200ms 是备用启动阈值，不是完整语音答复时延保证。

快速 NXDOMAIN、无地址回答及快速连接拒绝保持原错误；两个解析路径或后续 TLS/供应商同时不可用时仍按预算失败。TLS 证书校验、SNI、TTL/CNAME 和地址族处理保持，未固定供应商 IP。
