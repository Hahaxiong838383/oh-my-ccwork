# 百度天气扩城可行性 · REA与HK实测

**结论：具备从七城扩展到国内大量城市的可行性；本次完成研究取证，没有把百度适配器部署到小可。** 当前P1仍使用R8七城墨迹适配器；R9只修改灰度授权时长上限并将原两台窗口顺延至2026-10-24 23:59。不能把网站抽测通过写成小可全国天气已上线。

## 1. 实际读取了什么

- 使用home-studio已安装的REA 6.7.0，独立Chromium152浏览用户提供的[百度天气页面](https://weathernew.pae.baidu.com/weathernew/pc?query=%E5%8C%97%E4%BA%AC%E5%A4%A9%E6%B0%94&srcid=4982&forecast=long_day_forecast)，另验证成都、辽宁朝阳、北京朝阳三个场景。四次证据complete，步骤completed，浏览器均已清理。无登录、无Cookie导入、未调用其他智能体编写代码。
- 页面HTML包含`window.tplData`的JSON值：当前天气、位置、日期、逐小时、多日预报和生活指数。不需要执行网页JavaScript即可读公开数据；试验使用JSON解码，不使用eval。
- 北京当前气象源字段和逐小时资源均标为`moji`。因此百度是一个城市检索/聚合入口，**不是已经证明独立于墨迹的气象来源**。
- 从实际HK Brain节点每隔至少2.1秒读取一份公开页面，共46组：31个省会/首府/直辖市查询、香港/澳门/台北、8个非省会/县级地点、3组朝阳歧义查询、1个不存在地点。原始HTML与完整REA结果只留私有目录。

脱敏逐项结果、返回城市、天气站ID、时间、响应SHA及REA锚见 [覆盖实测JSON](BAIDU_WEATHER_COVERAGE_PROBE_20261022.json)。这不是全国穷举或长期SLA测试。

## 2. 结果和必须处理的陷阱

| 检查 | 观察 |
|---|---|
| 45组真实地点查询 | 全部HTTP200且有结构化天气；包含泉州、洛阳、宜昌、喀什、延吉、大理、义乌、昆山，不局限当前七城 |
| 日期/时效 | 45组页面基准日均为2026-10-22，均包含22/23/24日；当前更新时间17:25或17:30，多日列表40项 |
| 读取耗时 | 45组131–381ms，中位157ms；只计该次HTTP读取，不含语音、排队/播报，不是P95性能承诺 |
| 页面体积 | HTTP原始HTML约107–110KB；浏览器渲染DOM约322KB，后续适配器应读取原始响应并设上限 |
| 不存在地点 | “火星市不存在”也返回HTTP200，但没有tplData；必须按无有效结果失败，不能只验200 |
| 同名地点 | “朝阳”→站点101010300（北京朝阳）；“辽宁朝阳”→101071201；“北京朝阳”→101010300。三者`position.city`都只写“朝阳”，仅比城市文字会误判 |
| AQI | 字段名`ps_pm25`和多日`listAqiVal`容易混淆PM2.5浓度/AQI；没有逐字段独立对照前，不直接替换现有AQI播报 |

多日列表可见40天不代表40天预测精度已验收。小可首轮扩城仍应只开放当前温度和今/明/后天，避免同时扩大时间、指标和地理范围。

## 3. 两条接入路线

| 路线 | 对当前个人内测的适用性 | 条件与代价 |
|---|---|---|
| 固定百度网页适配器 | 推荐先做独立候选验证；无需新增账号，HK实际可读取，覆盖明显大于七城 | 属于网页内部结构，非稳定API合同；须严格校验站点、城市与日期，超时/改版/异常时明确失败 |
| 百度地图正式天气API | 后续稳定化优先评估；官方按行政区划查询，位置回显包含省/市/区/ID | 需要服务端AK及对应权限/额度；本次未申请账号、未购买、未使用未授权密钥，不能声称API已开通 |

[官方国内天气API](https://lbsyun.baidu.com/docs/webapi?title=weatherinquiry/weather/base)支持按行政区划查实时及未来7天天气；[使用准备](https://lbsyun.baidu.com/docs/webapi?title=weatherinquiry/weather/prepare)要求注册开发者并使用服务端AK。官方[行政区划CSV](https://mapopen-website-wiki.bj.bcebos.com/cityList/weather_district_id.csv)本次读取250819字节、3395条数据行（另1行表头），列含省/市/区/行政代码和坐标；SHA256 `1b7d93257df5992c5b31895e37406023a5926e819166c47d5e827867f7b970d0`。**行政字典条数不等于这3395个地点已通过网页/API逐个取数验收。** 字典坐标也不是设备GPS。

## 4. 建议的具体改动

1. **统一城市字典。** 从公开行政区划建立带来源/版本的省、市、区和别名字典；使用标准代码识别地点，单独绑定已核天气站ID。IP9得到的省市先做字典归一，兼容自治州/地区/盟等名称，不能一律追加“市”。同名地区用IP省份上下文或明确地名消歧，仍不确定才澄清。
2. **扩展结构化天气任务。** Worker目前`search_routing.rs`只有七城表；Brain的`weatherRequestSchema`也只接受七城ID。两端共同新增可校验的地点字段/版本，保留旧任务合同。明确城市优先于IP定位，未知城市不偷换成本地天气；不能只在后台追加触发关键词就算扩城。
3. **独立固定适配器。** Brain新增百度天气模块，只请求固定HTTPS域名与路径、服务端构造query；限制响应体（建议256KiB）、单次3秒/总6秒、禁止重定向，JSON仅当数据处理。按省市＋站点＋指标＋绝对日期缓存5分钟、同请求合并、失败冷却和限频。
4. **强数据校验。** 核中国地区、标准地点、预先核验的天气站、北京时间、接单时冻结目标日、更新时间和温度范围。HTML200但缺数据、城市/站点不一致、过期、缺目标日都明确失败。网页文字不作为提示词指令，未知字段不执行。
5. **保留后台任务链。** 定位/取天气全部在现有后台执行，主对话不等网络。领取/补播/插话/续讲/取消/改查沿原任务ID和回执；前台确认必须在服务端接单之后。它是固定天气来源适配，不要求开启P2任意抓取。
6. **后台可见且可回滚。** 在搜索灰度展示天气来源开关、字典版本、已验证覆盖范围、数据城市/站点/更新时间和失败原因。只为原两机发布，默认新来源关闭。现有七城保留旧适配器；扩城来源失败不能退化为未校验城市的LLM天气答案。回滚先撤新配置/新任务字段，再退二进制，保留任务账本。

实际涉及：Worker `search_routing.rs`、`search_tasks.rs`及预览工具共享合同；Brain `device-location.ts`归一、`search-routing-config.ts`、`search-tasks.ts`、`search-runtime.ts`、新增天气适配器/地点字典；后台路由配置、状态和证据展示。沿用两个现有工作树和分支，不新开、不合main。

## 5. 扩城上线门

- 先以城市/地区目录确定分母；地区名唯一性、同名消歧、天气站与行政区映射须可审计。先验证国内地级市，再单列县区/自治州/港澳台；没有覆盖的返回不支持，不报“全国全部”。
- 把本轮46组纳入数据源验收；再加常见同名区县、IP9别名、带省份/不带省份、无效地名、海外同名、站点错配、404/429/HTTP200无数据、慢响应、截断、过期和跨日。
- 对自动IP城市与指定成都/泉州/喀什等新城市跑真实RTC；查询中聊天、取消/改查、旧房退出和明天跨日都留任务＋数据＋字幕/音频证据，实机听感单列。
- 独立候选构建/回滚演练通过后再发布来源开关。新来源上线前，当前七城能力和已延长的48小时窗口正常保留。

本次可确认“百度入口有显著更广的城市覆盖，值得按上述设计接入”；不能确认“所有国内城市已经可用”，也没有将研究探针写入线上天气任务流程。
