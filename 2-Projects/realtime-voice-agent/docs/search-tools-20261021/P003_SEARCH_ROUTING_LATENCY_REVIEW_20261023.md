# 小可搜索与任务路由：对话延迟复盘

**结论：普通聊天没有被串行接到搜索后面，路由判断也很轻；但现在还不能验收为“加搜索后完全不变慢”。发现了新增的流式输出等待风险，以及本次设备会话中真实存在的 TTS 长尾。两者需要分开处理。**

本轮只读服务器、核对源代码、分析现有日志，并做本地纯函数复现。没有修改业务代码、部署、灰度开关、设备范围、截止或额度，没有新增真机/合成 RTC 会话，也没有调用模型生成测试回答。昨天 R11 的24项功能通过，不等于性能无回归；之前这部分验收覆盖不足。

## 3. 搜索为什么没有直接挡住普通聊天

代码核对得到以下路径：

1. Worker在本地匹配规则与会话状态，不为每句话再请求一次路由大模型。
2. 搜索命中后用 `try_send` 派给后台任务；提交、轮询、领取结果的HTTP请求均在独立异步任务中，音频主循环不等待这些HTTP返回。
3. 规则每5秒后台刷新，聊天读取已有快照；**不是每次讲话多等5秒**。搜索有独立HTTP客户端，未与聊天共用同一连接池。
4. 普通聊天仍走候选 Brain 的双模型响应机制；搜索没有替换它。候选 Worker关闭了额外的裸模型兜底，而Brain内部仍启用race，这一点与现役Worker配置不同，需纳入后续性能对照，不能把整个配置说成完全相同。
5. 结果需等到安全空闲点才能播放，用户新说话优先；不能为了让搜索数字好看而抢占聊天。

今天一个可核对的例子：00100004同一房间10:42:54.935提交搜索；10:43:01.336提交普通聊天；10:43:03.286已输出聊天正文；搜索结果到10:43:10.736才开始输出。它证明聊天没有等结果播完才开始，不证明人在设备端实际听到了每段，也不是故障注入下的延迟压力测试。

对应源码：Worker `src/pipeline.rs` 的提交分流、`src/search_tasks.rs` 的本地路由/try_send/后台run/pull_routing；Brain `src/routes/custom-llm.ts` 的普通聊天入口。以上均在现有两个专用工作树核对。

## 4. 需要处理的实际问题和风险

### 4.1 搜索新增的防误承诺过滤器覆盖到了普通聊天

候选 Brain 在用户话语包含“查、搜、天气、温度”等词时启用 `createSearchClaimFilter`。即使路由结果是普通聊天，也会先扣住生成内容，等到 `。！？!?` 或换行再检查并放行。因此“天气为什么变化”“烤箱温度怎么调”也会进入这层。

本地直接运行当前函数，合成两段正常回答：

| 输入段 | 过滤关闭 | 过滤开启 |
|---|---|---|
| 调节温度要先看刻度； | 立即返回这一段 | 空，继续等 |
| 再按说明书操作。 | 返回第二段 | 此时才一并返回两段 |

Worker原有切句器支持分号，而该过滤器不放行分号，因而确实存在新增等待路径。首段逗号提前切句启用时也会被上游攒句抵消。

**限定结论**：已经复现“安全普通内容被延后释放”；还没有同话术、同模型输出的线上A/B，不能给出线上净增加了多少毫秒。普通RTC原本也会等部分句末边界，因此不是每一条被过滤的回答都会同幅度变慢。今天00100004的21轮聊天中，有5轮命中这组入口关键词。

建议改成有边界的增量检查：安全内容尽早放行，只扣留尚未排除的执行承诺；保留跨token、引用、否定、分号与长句测试。不能简单删除防线，也不能超时后直接放行未检查的“已接单/已取消/已查到”文本。

### 4.2 最慢聊天的主要等待在TTS预连接，且现有指标漏记了这段

00100004，房间 `sn-BJP00326060100100004-1792723287`，turn 5：

| 同轮证据 | 结果 |
|---|---|
| 提交时间 | 10:42:13.136 |
| 路由完成间隔 | 约0.183ms，判为普通聊天 |
| TTS预连接 | `warm_connect_ms=5262` |
| 发文本后TTS首包 | 287ms |
| 正文首帧 | 10:42:18.736，提交后约5599.5ms |
| 同轮既有body-ready指标 | 1460ms，明显低估 |
| 承接音长度 | 2120ms，没有盖住后续全部等待 |

源码原因明确：`tts.rs` 会先 `warm.take().await`，而讯飞返回的TTFB从取到连接后才计时；`pipeline.rs` 用“合成调用前经过的时间＋该TTFB”估算ready，漏掉调用内部等待预连接的时间。因此该轮不能拿1460ms当真实正文到达。

本轮检查发现TTS两个源文件相对本地origin/main没有分支差异；目前证据定位到TTS连接链路，**没有证据证明这5秒由搜索查询造成**。DNS/TCP/TLS/上游握手各段仍缺日志，不能继续武断归到某一个网络环节。

建议先补完整计时，再针对慢握手设计有总预算、有并发上限、可取消的重试/备用路径，在候选服务验证。不能直接关闭预热，也不能把讯飞单会话连接当可长期任意复用的池。

03800006另有5.465s预连接；设备离开后仍有合成与播出队列日志。需继续检查退出时任务取消和清理，避免残留请求消耗资源；这些日志不代表离线设备还在发声。

### 4.3 承接音和搜索确认话术也占播放时间

今天00100004的承接音为0.92～2.48s，中位1.36s。一些普通轮正文数据已较早产生，但必须排在承接音后。例如10:51:51这一轮承接音2.48s，正文首帧2.50s。承接音让“有回应”较早出现，也可能让“说到答案”较晚，不能只统计首个声音。

搜索确认还需完整800ms静默窗口、TTS合成以及确认话术播放；之后结果再等安全空闲点和领取。部分查询1～3秒已经ready，但结果约6秒才开始输出，主要不是在持续查资料。建议优先缩短确认话术并复用预合成短音频，保留真实接单确认、插话优先和结果不抢话的约束。

### 4.4 其他需要在对照中覆盖的影响

- 后置“帮我查一下”接管上一问时，历史移交完成前下一轮会跳过投机生成，可能失去提前量。本次日志未见移交结算事件，不能把当前慢轮归因于它。
- 搜索与聊天仍共享主机、部分Brain事件循环和上游账号资源；异步不等于无资源竞争。11:00采样时Worker/Brain CPU空闲约97%以上，分别约6.0GB/2.35GB可用内存，未见swap或IO等待压力；**这是当时采样，不是10:42慢轮瞬间的资源曲线**。
- 普通聊天还经过配置读取、提示词和原有知识护栏流程；需分段计时，不能把全部LLM之前的时间都叫路由耗时。
- 昨天零搜索连续插话出现旧话题回流仍未关闭，属于对话正确性/打断问题，不能用本次延迟统计替它验收。

## 5. 下一轮建议与验收门槛

建议继续使用既有Brain/Worker分支和独立工作树，先在候选上解决上述问题，不扩大设备范围，不改首句认证合同，不缩短ASR判停去制造表面提速。

| 顺序 | 工作 | 预期收益 |
|---|---|---|
| 1 | 给room/turn补齐路由、模型可见首字、首段可合成文本、预连接等待、首PCM、承接音结束、正文首帧时间；修正body-ready口径 | 能准确解释慢在哪一段，不再把5.6秒看成1.46秒 |
| 2 | 收窄普通聊天的搜索误承诺过滤等待，并验证分号/短句/跨token边界 | 减少新增功能对无搜索聊天的间接影响，同时保留真实执行边界 |
| 3 | 检查TTS慢预连接与退出后的残余合成；设计受限的恢复路径 | 降低当前已看到的5秒级长尾，减少无效请求 |
| 4 | 优化承接音长度、搜索确认短音频及结果调度 | 更早说到实质内容；不给正常聊天加等待 |
| 5 | 用当前部署版本做性能对照，再决定部署 | 功能正确与延迟无回归分别验收 |

性能对照至少覆盖：普通日常话题；含天气/温度/搜索字样但无需搜索的话题；后台搜索时聊天；结果播放时插话；后置查询移交；取消改查；退出重连；上游延迟/失败。冷启动与热会话分开，普通聊天与搜索确认/结果分开，中断轮与自然完成轮分开。

两级验证：先用相同合成输入和隔离身份做可重复的候选/基线对照，再做同设备真人听感复核。持有人正在测试时不暗中切其链路。其他设备仅作为辅助体验对照。

建议发布门槛（**目标，不是本次已达成**）：路由判定P95不超过5ms；同场景普通正文延迟相对基线中位数增量不超过100ms、P95增量不超过200ms；5秒以上非人为打断长尾逐条解释；搜索上游变慢或失败时聊天仍能继续，不能等搜索超时。每组需足够重复样本并报告数量和未完成轮；当前18个正文样本不足以宣布稳定P95通过。

本轮完成了只读复盘、日志配对及纯函数复现。修复、受控性能对照和设备实听验收尚未完成；服务端发送成功不作为设备已听到的证据。本轮报告与证据仅本地落盘，未commit或push。
