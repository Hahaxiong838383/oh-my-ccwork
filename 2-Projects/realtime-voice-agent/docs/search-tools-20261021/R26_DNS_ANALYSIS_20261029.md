# R26 普通聊天 TTS 解析长尾：诊断与局部修复

状态：修复代码、Linux 检查和最终产物固定普通聊天 RTC 延迟门通过；搜索功能回归与发布结论见本轮最终验收记录。本人编写与验证，未委派。

## 1. 已知原因与证据边界

R25 固定 40 样本 / 20 对普通聊天对比，配对差经验 P90 为 +4301.477ms，超过 +300ms 门限。不是“所有对话都变慢 4.3 秒”，而是这批配对差的尾部恶化。该批 B 为 b011c254…，最终 R25 功能产物为 78cb7e46…；不能混用。

| R25 慢样本 | DNS | TCP | TLS / WebSocket | TTS 上游首音频 |
|---|---:|---:|---:|---:|
| B0 | 5017ms | 53ms | 167ms | 269ms |
| B9 | 5066ms | 305ms | 154ms | 277ms |
| B10 | 5016ms | 53ms | 174ms | 296ms |

阶段证据指向 DNS 等待，而不是天气抓取、搜索路由或 TTS 合成耗时。普通聊天没有触发 R25 的搜索控制复核，R25 本身没有修改 TTS connector；这些事实不足以证明本轮回退完全与代码无关。

已确认的结构性缺陷：650ms 后启动的备用 TTS 握手，仍调用同一个 `voice_connect`、同一个异步 resolver 和同一个 systemd stub，因此不具备独立 DNS 后备。慢例的备用约 1352ms 在 resolve_tcp 阶段失败，主路仍等待约 5 秒。

尚未确认：异常事务究竟阻塞在本地 stub、到上游的网络、递归解析服务，还是解析器重试组合。累计 systemd timeout 从历史 428 到本轮 432，不能绑定到某条样本。依赖源码表明 request timeout 不是整个查询链的总截止；不能仅看到约 5 秒就推断某个默认超时配置未生效。

这些是 2026-10-29 本次只读快照。Brain 的阿里内网 DNS 不能直接移到非阿里 Worker。阿里公共 DNS 是另一项服务，IPv4 为 223.5.5.5 / 223.6.6.6；官方列有香港节点，可以在 Worker 上比较实际效果，不应凭供应商名称选择。

16:51 收尾复核时，Worker 当前选中上游已是 **8.8.8.8**，两项上游配置及 stub 路径 / 文件哈希保持不变。`Current DNS Server` 是解析服务当前选择，不是固定配置；不能据选择变化认定人为改过 DNS，也不能把该变化独自归因到某条 TTS 请求。

已有只读非计费诊断：12 次冷进程查询全部成功，DNS 2–12ms，一次 TCP 1097ms；既有 stub 和两上游的 UDP/TCP、A/AAAA 共 12 次查询成功，DNS 1–181ms。冷进程不代表 stub 或公共递归缓存已清空；未冲刷生产缓存。短探测没有复现原 5 秒间歇问题，不能据此宣告问题消失。诊断不发送 TTS 凭据或计费文本。

建议：本轮不全机更换 DNS，不新增 AliDNS 配置，保留局部有界后备。此短样本只说明当前节点、当前时段、该 TTS 域名的表现，不代表供应商长期可靠性排名，也不能把一次超时断言成阿里服务故障或限流。如果后续持续取证支持更换，再仅在候选验证，不能把 Brain 的阿里内网地址移植到 Worker。

## 3. 本轮改动与收益

仅候选异步 TTS 链路可启用 `P003_TTS_DNS_HEDGE_V1=1`，默认关闭，且限制为已知讯飞公开 TTS 主机名：

1. 原系统解析先运行。解析在 200ms 内完成时，没有额外上游查询。
2. 解析仍 pending 时，尝试直接查询系统已配置的上游。全进程最多两个后备请求名额，不排队；没有可用名额就保留原路。
3. 后备只在系统确由 systemd stub 管理时启用，从其上游配置读取最多两个合法地址。不改系统 DNS，不硬编码第三方公共 DNS，不用于内部域名。
4. 正常结果沿用 DNS TTL；保留 IPv4/IPv6、TCP 地址错峰、TLS/SNI 和证书校验。后备失败不取消仍可能成功的原路；取消释放名额和竞争任务。
5. 既有首音频总预算保持 10000ms。200ms 是启动后备的等待值，不是对所有异常承诺 200ms 内出声。
6. 连接日志新增 `dns_path`，区分 system_resolver / configured_upstream / system_os / literal_ip，方便后续把真实慢例与解析路径关联。

预期收益：避免本地 stub 的单点长尾同时拖住主备 TTS，快路径保持原行为。若两个上游、公共网络或 TTS 服务同时异常，本修复不能保证无延迟；这也是仍须固定端到端对比和真人复验的原因。

## 4. 验证约束

固定主解析故障的红测先失败；修复后，独立后备在 300ms 测试截止内成功。新增测试还覆盖快路径零后备、TTL、后备失败保留主路、名额用尽不排队、取消释放和 IPv6。Linux 最终 477/477，release / ABI 通过。未新增依赖。

一次全测出现存活性测试的 750ms 外层 guard 超时，原失败日志保留；分离前后两段 DNS fixture，并将仅用于存活性断言的 guard 放宽到 2 秒覆盖 UDP 重试 / 调度，最终全测通过。未证明首次失败的唯一原因，不能归因成已确认的 CPU 抢占；300ms 快后备断言和正式性能门没有放宽。

最终二进制 SHA-256：`4f45d8c8c26b025908822fcaf7ff97eeedd79153603eccc6789be6b7dfe46854`。Worker 实现提交：`7338a68120293e41f15da319c995463c2803b306`。Brain 沿用 R25 最终两项源码；不把 R25 历史测试说成本轮重新执行。

本轮固定 40 个 RTC 样本，A0–9 / B0–9 / B10–19 / A10–19，20 对；A 为现役 R24，B 为上述 R26 最终产物并包含 R25 三项修复。门限仍为配对差中位 ≤100ms、经验 P90 ≤300ms、新增正文缺失 0；全部尝试保留，不剔除、不补抽样。矩阵期间不改 DNS，不另跑 DNS 比较暖缓存。

固定矩阵实测：40/40 样本，20/20 可比对；配对差中位 **−51.0155ms**、经验 P90 **+148.884ms**、新增正文缺失 **0**，通过既定门限。A / B 均未触发搜索控制复核。它是本次有限样本通过，不是长期 P95 或全链路零延迟保证。

探针沿用的 `brain_manifest_sha256` 字段实际存放 `r24-baseline` / `r26-artifact-spec` 标签，不能把它冒充密码学哈希；原件保留。Brain 版本绑定来自切换步骤核验的实际源码 SHA、环境摘要与本轮文件清单，Worker 每条样本另核实际运行二进制 SHA。

连接阶段另有实际后备证据：A2 的 connect_id=9 解析 **5023ms**，TCP55ms、TLS/WS184ms；B17 的 connect_id=75 使用 `configured_upstream`，解析 **212ms**，TCP54ms、TLS/WS176ms。B 的 20 个房间里，81 条成功连接计时的 DNS 最大212ms；两个后备启动事件中一次成功接管。另有3条取消连接记录保留，其中一条在 resolve_tcp 等待901ms后取消，未返回独立 DNS 时长，不能填成0或隐去。A 为86条成功、1条 resolve_tcp 失败。

记录范围包含预连接和备用连接，不把每条连接当独立性能样本，也不把 A2 / B17 当同一故障的严格因果配对。原外部 DNS 事务的具体延迟位置仍未取证，但局部后备的真实生效已被观测到。

矩阵后继续 R25 八项功能回归及最终产物新→旧→新回滚。仅测试环境使用合成 SN / 独立数据与路由；真人版本、窗口与系统 DNS 在诊断阶段保持原样。最终发布 / 阻塞及功能证据在验收记录汇总。
