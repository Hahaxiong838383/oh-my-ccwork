## 二、确定的问题与仍缺的根因

**确定：诊断没有覆盖实际接房进程。** Brain签票四轮都是`selected_agent=rust-worker`、`canary_reason=lease_invalid`。R4的`lease_age_ms=5765415`，约96分钟；`lease_remaining_ms=-5750415`。Android已声明相关能力，不能归因为未声明倾听能力。此前部署成功、开关开启、服务active，都不等于复测时实际落到诊断池。

**未确定：第二条ASR从PCM发送到final交付之间具体卡在哪。** 现有日志没有该连接的`written / responses / definite / final_delivered`，无法区分入队/写出、供应商返回空结果或无定句、事件交付等分支。不能把“没有观测到final”直接写成“供应商未返回任何内容”。

本轮不支持以下归因：DNS/TLS建连超时、搜索工具卡住、LLM响应慢、TTS播放卡住、Android崩溃。R4第二条连接已成功，而问句没有进入回答轮。也没有证据证明Android上行完全正确或供应商有故障。

11月16日只读现状：倾听Worker本地健康约0.6秒新鲜，Brain倾听health文件约3.9秒新鲜、租约剩约11.1秒。这说明读取时租约有效，不证明11月11日问题已修复，也不证明之后持续稳定。当前二进制/PID已经变化，不能用今天的运行版本反推历史版本。历史租约停止同步的更底层原因未在本轮唯一定位；不得据旧记录贸然重启当前健康服务。

## 三、是否过度工程化、影响什么

诊断提交`1cc55436`是有截止时间、按完整SN启用的计数观察，没有增加逐句LLM请求，也未改识别供应商、判停、队列容量或关房时间。Grok已独立审查该合同，并第二次交叉核对Brain历史签票和V2房间归属，同意上述结论。现阶段再加框架、换供应商、扩队列、盲目延长超时或把空结果补造成final，都缺乏依据。

实际需要收敛的是运维验收：**以真实trace命中的池、进程和诊断记录为准，不能只看配置和服务在线。** 保留租约失效回主池的保护，不为了测试绕过健康检查。

核心体验受影响：用户问了问题，小可没有回答，随后空闲退出。房间能关闭、六服务正常、无Fatal/ANR，只说明恢复/进程健康；不能替代ASR功能验收。

## 四、最小后续动作

1. 服务端先完成诊断覆盖预检：确认目标池有效租约、当前二进制包含诊断、完整SN/截止时间正确，并用实际分配的trace确认命中池和诊断汇总。发生主池回退时，该轮须明确标为“未覆盖诊断”，立即停止该批；不得当诊断样本继续跑。
2. 覆盖成立后，再做2–4轮定向复现，继续使用相同WAV与相同问法，首个NO_FINAL立刻停批。不要现在重跑30轮，也不要让安卓先改一轮代码。
3. 按第二条连接的独立generation/request_id对账：`rtc_seen → accepted/full/closed → taken/written → responses/definite → final_delivered → asr final received`。写入socket成功仍不等于供应商应用已收到；累计计数不当作单次连接增量，`definite-final_delivered`不当作丢失数。
4. 只修被证据命中的一处，再回归原失败语料。若仍缺供应商响应，才用已有原WAV做受控直连与RTC对照；同语料与不同声学入口分别标记，不用另一个合成WAV冒充原现场。
5. 修复后完成既有普通对话验收（30轮及少量真人自然问法），逐轮有问句final、回答和正常退出，不再发生无法解释的NO_FINAL。没有受到修改影响的倾听、资产问答不重复做全套矩阵；容量/输出门失败/Worker替换的异常场景保留原有独立状态，不宣称本轮通过。

服务器负责租约/派单覆盖和上述统计对账。安卓侧现阶段保持现有v394取证能力、WAV及停批规则即可；不需要因此新增状态机或OTA。实际接房池若缺诊断版本，应先准备精确增量与回滚点，空闲时发布，不能仅给不含诊断的旧二进制设置环境变量。
