## 1. SN 由**后端**写进 token，不是安卓直传 worker

安卓仍然负责读 SN 并上报——只是**上报给后端**，由后端签进 token 带到 worker。

```
安卓读 SN ──POST /v1/device/session{sn}──► 后端
                                            ├─ 校验设备白名单（SN 未注册→拒发）
                                            ├─ 生成 session_id
                                            └─ 签 token: identity=dev-<SN>, room=sn-<SN>-<ts>
                                     ◄──{session_id, room, token, url, expires_at}──┘
安卓 ──token 进房──► LiveKit ──dispatch──► rust-worker（从 identity 读 SN）
```

**为什么不让安卓直传 worker**：

1. **token 是签名的，identity 改不了**；设备自报的 SN 是未签名数据，可伪造 → 埋点被污染，而被污染的埋点比没有埋点更糟（你会据此下结论）。
2. **白名单校验是刚需**：读写台是产品设备，没有白名单意味着任何拿到 token 签发路径的设备都能连上来吃并发槽位。后端签发时顺手校验，零额外成本。
3. token 本来就必须后端签（room 锁死 + TTL），把 SN 写进去**不增加任何一次网络往返**。
4. worker 侧省掉一套解析 + 校验代码。

⚠️ **要安卓端确认的一件事**：Android 10 起 `Build.getSerial()` 对普通应用受限。读写台若是自有 ROM / 系统签名应用则不受影响，但请明确**读取方式**（系统属性？厂商 API？系统签名权限？），以及**恢复出厂后 SN 是否变化**——SN 不稳定的话整套归因的地基就是松的。若不稳定，改用「首次激活时后端下发的 device_id + SN 作属性」。

## 2. 生命周期：两个状态，安卓端必须明确区分并上报

川哥的约束：**休眠可断开，息屏不能断开**（息屏仍需语音交互）。这两条在安卓上是完全不同的工程量。

### A. 息屏但保持会话 —— 要正面对抗系统，不是"什么都不做"

安卓在息屏后会掐后台麦克风、掐 CPU、掐网络。要保住会话，端侧至少需要（**具体版本要求请安卓端按 targetSdk 核实，此处为待确认清单而非结论**）：

| 项 | 作用 | 不做的后果 |
|---|---|---|
| **前台服务 + `foregroundServiceType="microphone"`** | Android 10+ 后台采麦克风的前提 | 麦克风静默 |
| **`FOREGROUND_SERVICE_MICROPHONE` 权限**（Android 14+） | 同上，新版更严 | 服务起不来 |
| **PARTIAL_WAKE_LOCK** | Doze 下保住 CPU，音频线程不饿死 | 音频卡顿/断流 |
| **电池优化白名单** | Doze 掐网络 | RTC 断流 |
| **WiFi 高性能模式 / 禁 WiFi 休眠** | 保住上行 | 上行断 |

**失败长什么样**：worker 日志 `audio in (10s) frames=0` —— 房间还连着、信令正常、页面看着一切正常，就是没有声音上来。这个诊断已经写进操作手册 §7，对上了直接查端侧息屏策略，不用再猜。

### B. 深度休眠 —— 主动断，别等超时

- 进休眠前**主动 `room.disconnect()`**，让 worker 正常收尾并删房。
- **别靠超时断**：超时会留下房间残留窗口（有删房兜底，但那是兜底不是设计）。

### C. 唤醒重连要快 → **token 预取**【设计】

服务端侧就绪耗时【实测】：进房后 LLM 预热 200–400ms、TTS 池再约 1 秒，**约 1–1.5 秒就绪**。端到端重连耗时【待测】（含设备连接建立 + ICE + dispatch）。

能省的是后端那一跳：

- 设备在**上一次会话结束时就预取下一张 token**（后端用未来时间戳预生成 room 名）；
- 唤醒时直接用缓存 token 连，省掉一次后端往返；
- 用掉后立刻再预取一张；缓存 token 设短 TTL（如 24h），过期自动重取。

同时并行做信令域名的 DNS/TCP/TLS 预热（Python 线 SDK 的 `prewarm()` 是同款思路）。

## 3. 埋点分工：先划清"谁看得见什么"

**这一步不做，最后会发现最想归因的那类问题两边都没采。**

| 只有端侧看得见 | 只有服务端看得见 | 两边都要 |
|---|---|---|
| 麦克风权限状态 | 各段延迟分解（eou/stt/ttft/ttfb） | **session_id** |
| **息屏/休眠状态迁移** | **ASR 零结果**（单字丢弃） | sn |
| 前台服务存活 / 被系统杀 | 打断次数 | ts |
| 网络类型与切换（WiFi/4G） | LLM/TTS/RTC 错误 | |
| 电量 / 是否插电 | 轮次数、会话时长 | |
| **唤醒→首帧音频端到端耗时** | 结束原因 | |
| 触发语音的用户操作 | | |

### 🔴 session_id 必须由后端签发时生成，并同时下发给设备

两侧埋点靠它 join。**没有共同主键，两套数据永远拼不起来**——你会有一堆端侧事件和一堆服务端事件，就是对不上是哪一次会话。这是整套埋点最容易漏、补起来最贵的一环。

左列那些是这套方案真正的增量价值：服务端只能看到"连接断了"，**看不出是休眠、是被系统杀、还是崩了**——而这三种的处置完全不同。

数据模型（事件字段、SN 缺失标记、双通道落盘、隐私边界）见 `RUST-LINE-TELEMETRY-PLAN.md`，那份的结论此处全部沿用，尤其：
- SN 缺失填 `null` + `sn_source=missing`，**绝不填 `"unknown"` 这种像真值的占位**；
- 默认不采音频、不采字幕原文。

## 4. 接口契约（后端需要提供的最小集）【设计】

```
POST /v1/device/session      # 换取会话
  ← {sn, app_ver, fw_ver}
  → {session_id, room, token, livekit_url, expires_at}
  → 403 设备未注册 / 429 并发已满（明确区分，别都返 500）

POST /v1/device/session/prefetch   # 预取下一张（同上结构，room 名用未来时间戳）

POST /v1/device/events       # 端侧埋点批量上报
  ← {session_id, sn, events:[{ts, event, ...}]}
  → 202
  # 断网时端侧本地排队，重连补传；失败不得阻塞语音主链路

设备鉴权：设备密钥或证书。SN 本身不是凭据，不能拿 SN 当身份。
```

**429 要真的会发生**：见下条。

## 5. 🔴 先解决并发：现在只有 2 路

`WORKER_MAX_JOBS=2`【实测】。读写台是产品线，2 台设备同时在线就满，第 3 台的表现是**静默接不上**——和派单失败、网络故障完全同形。

### 实测结论（2026-08-14，64.90 真实通话，probe 走完整 STT→LLM→TTS 链路）

机器：4 核 Xeon Gold 6248 @2.5GHz / 3915 MB 内存。

| 量 | 值 | 说明 |
|---|---|---|
| **固定开销**（worker + EOT sidecar + 判停模型 + 声纹模型，全部热加载后） | **≈430 MB** | **进程级单例，不随 job 增长**。其中 sidecar 单进程就 302 MB |
| **每路 job 边际内存** | **≈12–18 MB** | job 关闭后不回落是 allocator 保留，下一个 job 复用（2 路只在 405MB 基础上加了 24MB，实证复用） |
| **每路 job CPU** | **≈0.3 核**（整机 7.5%） | 1 路 7.5% → 2 路 15.0%，线性 |
| unit 现有内存闸 | MemoryMax=1.2G / High=900M | 按 430+18×N，1.2G 可容 ~40 路，**不是瓶颈** |

**→ 瓶颈是 CPU，不是内存。** 按 0.3 核/路，4 核机给 Rust 线留 2 核即可支撑 **6 路**，仍为三条 Python 线和系统留 2 核。

**建议 `WORKER_MAX_JOBS=6`**（现为 2）。理由：内存只需 430+6×18≈540 MB，远低于现有 1.2G 闸，无需改内存配置；CPU 占 1.8/4 核，生产 Python 线（forkserver 子进程各 350–440 MB、CPU 更重）有充足余量。

⚠️ **这个数的适用边界**：实测用的是**单轮短对话 probe**。真实设备会话更长、轮次更多，VAD 持续跑、声纹每轮比对，**每路 CPU 可能高于 0.3 核**。上规模前应补一次「多轮长会话 × 6 路并发」的持续压测再确认。

其余仍需做：后端在槽位满时返回**明确的 429**，端侧给用户可理解提示，而不是静默失败。

目标并发要川哥给个数（首批几台设备、峰值几路同时在线），超过 6 路就要考虑加机器而不是继续调这个参数。

## 6. 分阶段（每阶段一个卡点）

| 阶段 | 安卓（codex） | 后端 | worker（cc） |
|---|---|---|---|
| **S1 打通** | 官方 SDK 进房、前台服务、主动断开 | `/session` + 白名单 + session_id | 从 identity 取 SN，落 `session_start`/`turn`/`session_end` |
| **S2 归因** | 端侧事件上报 + 本地排队补传 | `/events` 收集 | `asr_empty` + `error` 事件 |
| **S3 稳态** | token 预取、息屏策略调优 | `/prefetch`、429 | 并发扩容、查询脚本 |

S1 的 worker 改动集中在新增 events 模块 + 少数调用点，**不碰现有行为逻辑**。

## 7. 验收（按"要采回的数据"逐条对，不是数代码写完没）

1. **息屏实测**：设备息屏后完整对话一轮，worker 侧 `frames>0`。这是本方案最核心的一条，**必须真机息屏验，模拟器和亮屏都不算**。
2. **休眠→唤醒重连**：断开后唤醒，测端到端到首次可对话的耗时，补上【待测】那个数。
3. **负向验证（必做）**：故意让设备不带 SN 走一次，确认落到 `sn_source=missing`，**不是被默认值悄悄填上**。没做这步等于没验——判据写错时它恒绿。
4. **session_id join 验证**：拿一次真实会话，端侧事件与服务端事件用 session_id 关联，能拼出完整时间线。拼不上就是主键设计没落地。
5. **并发上限验证**：打满槽位，确认第 N+1 台收到 429 而不是静默失败。
6. **隐私回归**：确认 `turn` 事件里没有字幕原文。
7. **双通道对账**：JSONL 条数 == journald 事件条数。

## 8. 等 codex 架构文档回来后要确认的三件事

1. **SN 读取方式与稳定性**（见 §1 末）——地基问题，优先级最高。
