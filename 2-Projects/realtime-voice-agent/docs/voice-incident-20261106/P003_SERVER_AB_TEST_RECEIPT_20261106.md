## 3. 响应与断续：分开看

第一批允许服务端衔接音的样本，在两池都观察到衔接音结束后等待正文的空档，服务端 `underrun_ms` 为 75–753 ms。这个现象在没有安卓参与时也能发生，因此不能把所有“断断续续”归因设备网络。

随后在同一个灰度池、同一 WAV、同一脚本和累计样本时钟下，只改变本次测试会话的衔接概率，按 1 → 0 → 0 → 1 顺序对照：

| 测试会话衔接概率 | 服务端欠载空档 |
|---|---|
| 1，第 1 次 | 160 ms |
| 0，第 1 次 | 0 ms |
| 0，第 2 次 | 0 ms |
| 1，第 2 次 | 312 ms |

策略是否被 Worker 接受、filler 是否播放、正文自然播放完成均对照 journal。此处只改测试 token 的受信 metadata，后台全局设置和真实设备风格配置没有改。LLM 输出仍有随机性，这 4 次是小样本机制验证，不是统计容量结论。

剔除衔接音后，四个两池普通样本的“上传末包 → 客户端首个非零正文 PCM”为约 1.10–2.03 秒；本轮这些样本未出现正文播放欠载。TTS 已预热，首 PCM 为约 252–296 ms。这里是合成 PCM/服务器网络下的样本耗时，不是设备实际说完到扬声器的时延，更不是 P95/P99 或冷连接 10 秒问题已解决。

优化方向明确：避免高概率的短衔接音过早播放后接一段等待；先结合现有风格概率和正文是否即将就绪处理。不能为遮住等待增加更多语气词，也不能把 filler 首声计作正文首声。

## 4. 失败记录没有抹掉

共 29 次尝试，其中 28 次进入 RTC 测试：

- 24 次通过各自观测断言，包含预期失败条件的负例；不是 24 次正常问答。
- 2 次主池“不订阅后应自动关闭”断言失败，均实际复现未自动关房；保留为服务端生命周期差异/缺口。
- 2 次强化测量误报：`journalctl -o json` 将含控制字符的 MESSAGE 输出为字节数组，早期解析器只处理字符串，漏掉已存在的正文播放完成日志。原失败保留；离线同日志对照证明旧解析匹配 0 条、修正后各匹配 1 条，再进行真实复验。
- 另 1 次在前置阶段退出，原记录只有退出码及 stderr 字节数，原因未归档；不能猜成容量问题或业务故障。后续补了前置 stderr 留档。

初期外层套件仅报告传输退出状态，不能反映内层探针失败。最终控制器已修正：内层 rc、result、房间清理和 helper 结果全部核对；最后一次主池负例的内层与外层均明确返回 1。资源创建/关闭使用独立计数，正文完成结合服务端 `SourceDrained` 且 `played_frames>0`，不再只凭字幕和静音两秒。

v1 使用有序历史缓冲加速发送；v2 改为 40 ms 块间等待；v3 按累计样本时钟调度。它们分别保留，不混在一起计算实时性能。早期首声含 filler，只能作为“有输出”证据。

## 5. 对原故障的最终判断

**已经缩小到的范围：**

1. 事故 B 的 ASR、LLM、TTS 已经产出；本轮相同文本也可在真实灰度池完成输出。不能把它直接归因“搜索模型卡住”。
2. 不订当前输出轨足以在没有安卓状态机的情况下重现 G2 的 5 秒门失败、正文 0 帧、灰度关房。
3. 新 job 不发 begin 足以重现 G3 的 `begin_timeout`；若随后确实有有效 RTC 语音输入，服务端可以继续回答。
4. 主池的 pipeline 结束不自动结束房间、以及衔接音到正文的空档，是本轮独立发现/复现的服务器侧问题。

**仍未定位的关键边：**

- 历史 G2：安卓记录订阅音轨，但没有 publication SID；Worker 没确认到当前轨。是旧轨订阅、SDK 恢复时序、SFU 订阅通知，还是 Worker 事件过滤，仍不能唯一判定。新测试的 SID 不能回填旧现场。
- A 类约 4.2 秒准备失败与约 10.1 秒 RTC 连接失败：服务器到 SFU 通过不等于设备网络路径通过，尚不能细分 DNS/TCP/TLS/WebSocket/ICE。
- 倾听能力 adapter 开启时的普通聊天与设备签票链尚未在本轮模拟。不能将“现役倾听灰度池普通语音通过”扩写成“倾听全部路径无问题”。

因此，搜索/倾听改动涉及的共享生命周期确实需要对照，不能推给安卓；但当前也没有证据将最初的输出订阅丢失全部归罪于搜索功能。
