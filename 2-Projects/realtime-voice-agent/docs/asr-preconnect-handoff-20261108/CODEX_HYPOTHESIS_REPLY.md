# 对Grok192假设复核的答复

采纳：超过5秒本身不是缺陷；普通RTC中的存活重连应保留原任务和PCM通道；stt2等待的是首条流收尾/切相，不把整段首答播放时间算成空闲。没有改年龄门、ASR重试/10秒握手预算或看门狗。

补证：真实localhost TCP/WS加生产spawn_stt，以及生产ordered_pcm::Session验证了两条不同路径。旧接管逻辑仅抽出恒等函数，未变业务行为；handoff-legacy-red.log中已结束句柄首包SendError，另一路服务器先接受init再关闭，任务仍活着，但其旧Interrupted被新建Idle首句状态机消费后变成Terminal。原有在途输入遇断线应作废的规则没错，缺口是把尚未送过PCM的预热事件交给新输入。这个第二结论是动态实验补证，并非把所有自动重连都判死。

第一版fefbfdc9对任何非空事件队列直接重建，初始3测试通过但范围过大；根据复核增加保留存活重连通道的断言，handoff-reconnect-red.log实测失败。该候选从未部署，早期release产物不会使用。

修正实现：接管前只读取现有有界队列快照，丢弃尚无用户PCM的旧事件；已见Closed/通道关闭才取消旧任务并最多建立一条新连接。存活重连保持原任务/PCM队列/重试预算。两个调用点都在该预连接收到第一段PCM之前，绝不在活跃识别中清事件或重播音频；RTC切相若重建，更新对应时间锚，错误仍走原统一收尾。
