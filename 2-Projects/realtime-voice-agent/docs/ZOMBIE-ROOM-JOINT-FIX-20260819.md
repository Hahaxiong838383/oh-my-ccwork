# 僵尸房联合修复：worker 侧已上线机制 + 端侧修复建议评审（2026-08-19）

> 面向：P003WebDemo 端侧同学（常连房间/僵尸房看门狗线）
> 背景：8-17 端侧僵尸房自救第二层（3.5s 无 ASR 看门狗）出现跨语音窗口误杀——旧窗口定时器
> 到期误拆正在说话的新窗口。端侧分析与五条修复建议我们全部认可，本文补充 worker 侧
> 本轮上线的配套机制、两侧职责边界、以及联调排障工具。

## 一、结论

1. **端侧五条修复建议全部认可**，按原方案改即可（逐条批注见 §三）。
2. **worker 侧已上线「上行媒体看门狗」**（2026-08-19）：SFU 检测到设备媒体传输断
   （connection_quality=LOST）持续 15s 无恢复 → 服务端主动删房 → 端侧收到**标准
   disconnected 事件**（前端零改动）。效果：**传输层僵尸房从此不再以「room.state
   仍是 connected」的假象存在**——端侧「复用前检查 room.state」的第一层自救从被骗
   变可信。
3. **端侧第二层（无 ASR 看门狗）修好隔离后必须保留**：worker 只能测到「传输死」；
   「采集死」（WebRTC 连接正常、持续发静音，但系统已把麦克风从 WebView 收走——
   息屏省电/音频焦点被抢的典型后果）在服务端看是合法静音，只有端侧「硬件 VAD 说
   在讲话 + 无 ASR」能识别。两侧互补，缺一不可。

## 二、僵尸房的两种死法（排障先分型）

| 型 | 传输层（ICE/RTCP） | worker 收到的音频帧 | 谁能检测 | 处置 |
|---|---|---|---|---|
| **传输死** | 断（NAT 失效/网络切换/WebView 冻结） | 无帧 | **worker（已上线）**：SFU 报 LOST 15s → 删房 | 端侧收 disconnected，下次唤醒正常重连 |
| **采集死** | 正常 | 有帧但全静音（peak≈0） | **只有端侧**：硬件 VAD 报说话 + 3.5s 无 ASR | 端侧看门狗拆房重连（修好窗口隔离后） |

> 注意：硬件 VAD 走 UART 独立链路，它的电平正常**不能证明** WebView getUserMedia
> 流是活的——两条链路独立死活。这是「本地麦克风电平正常但 agent 收不到音频」
> 看似矛盾的根源。

## 三、端侧五条建议逐条批注

1. **speechStart 立即取消上一窗口的无 ASR 定时器** —— ✅ 必改，本次误杀的直接根因。
2. **每个 VAD 窗口独立序号，定时器只处理创建它的窗口** —— ✅ 推荐用「会话代 epoch +
   窗口序号」双层：拆房重建后 epoch+1，旧 epoch 的一切回调（不只定时器）全部丢弃，
   一次解决「残留 vad_end 混入新会话」和「旧定时器跨窗」两类串扰。
3. **触发前再确认：同会话、同窗口、无人在说、上传窗已关、确无 ASR** —— ✅ 对。
   补一条：**若刚收到 disconnected（worker 主动删房）则跳过看门狗直接走重连**，
   别把服务端已处置的传输死再当采集死重复处理。
4. **只接受当前会话内成对 vad_start/vad_end，忽略进入会话时残留的孤立 vad_end** —— ✅ 对，配合第 2 条的 epoch 自然成立。
5. **自动重唤醒期间串行处理房间与麦克风** —— ✅ 必改。另请注意：服务端现在有
   **两个主动关房源**（空闲超时 IDLE_HANGUP + 媒体 LOST 看门狗），disconnected
   随时可能到达，重连状态机要把「服务端主动关房」当**常态输入**处理，与用户主动
   退出走同一条串行路径，不要并发跑两套发布/卸载。

## 四、worker 侧新机制细节（联调用）

- **L1 挂断**：设备 connection_quality=LOST（SFU 基于 RTCP/传输层评估，不受 opus DTX
  静音停包影响）持续 `MEDIA_LOST_HANGUP_S`（默认 15s）无恢复 → `delete_room`。
  瞬时弱网免疫：倒计时内质量恢复即取消。
- **L2 遥测**（只记日志不动作）：worker 每 60s 输出一行
  `media watchdog stats: frames=+N peak=P last_frame_age=X muted=M lost=L`。
  联调僵尸房时把复现时刻发我们，用这行日志直接分型：
  - `lost=True` / frames 停增 → 传输死（L1 会处置）；
  - frames 正常增长但 `peak≈0`，而你们端上硬件 VAD 在报说话 → 采集死（端侧处置）。
- 生效范围:javis 租户 worker + 主 worker;回滚开关 `MEDIA_WATCHDOG=0`。

## 五、成本提醒（供权衡，不强制）

常连房间的服务端成本实测（2026-08-14，静默挂机 5.5 分钟采样）：空闲挂着不说话的
会话仍占 **0.125 核 + ~600MB 级 job 进程 + 一条 ASR 连接持续上送静音**；且 job 槽位
有限，常连模式会把「并发对话数」降级成「接入设备总数」。服务端已用空闲超时兜底
（长时间无语音主动关房，端侧实测约 41s 后自动重连）。若唤醒延迟优化还有余量，
更省的路线是「唤醒即建连 + token 预取」（服务端就绪 1–1.5s 可与用户开口并行），
供后续评估。
