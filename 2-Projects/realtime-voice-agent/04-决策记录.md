## M0 LiveKit 接线与自托管主线（2026-06-23）

<!-- status: 生效中 -->
<!-- scope: Worker / RTC / 体验引擎 -->
<!-- files: src/voice_agent/engines/livekit_bridge.py, src/voice_agent/engines/tier_a_cascade.py, src/voice_agent/app.py, scripts/m0_smoke.py -->

### 现象

M0 需要从「纯接口骨架」推进到可接真实 LiveKit worker，并能自动验收契约事件覆盖；同时明确 LiveKit Cloud 与自托管的主线取舍。

### 根因

实时语音 Agent 的核心差异化在可控、可审计、可替换体验引擎与稳定记忆内核；如果 RTC 层长期依赖 Cloud，会削弱成本、隐私、网络拓扑和压测控制权。

### 候选方案

| 方案 | 做法 | 优点 | 缺点/风险 |
|------|------|------|----------|
| A. LiveKit Cloud 主线 | 从官方项目拿 URL/API key/secret | 最快上线、少运维 | 核心 RTC 层外包，成本和拓扑控制弱 |
| B. 自托管 LiveKit 主线 | 本地 dev → Mini/VPS 部署 LiveKit + TURN + WSS | 可控、可审计、适合 Voice-Eval 压测和隐私边界 | 需要部署与网络运维 |
| C. 先不接真实 LiveKit | 继续保持纯骨架 | 零外部依赖 | M0 无法证明「有声音/可打断/契约打通」 |

### 决策

**选择**：方案 B — 自托管 LiveKit 主线。

**理由**：与产品北极星一致：RTC 只是可替换体验引擎，记忆内核与审计能力才是护城河；自托管更利于压测、隐私和后续部署拓扑控制。

**放弃的方案**：
- 方案 A：可以保留为对照实验，但不作为主线。
- 方案 C：无法完成 M0 验收闭环。

### 改动

- 新增 `LiveKitEventBridge`：桥接 LiveKit session 事件到内部 `EngineEvent`。
- `TierACascadeEngine.start_livekit_job()` 接入 `AgentSession`、Silero VAD、turn detector、打断与假打断事件。
- `app.py` 增加 `python -m voice_agent.app livekit` worker 入口。
- `scripts/m0_smoke.py` 增加离线 M0 验收报告。
- `Makefile` 增加 `run-livekit` 与 `m0-smoke`。

### 验证

- `make m0-smoke`：关键契约覆盖 8/8，基础指标门全 PASS。
- `ruff check src tests scripts`：PASS。
- `mypy`：PASS。
- `pytest`：42 passed。

### 什么条件下该翻这个决策

- 自托管 LiveKit 运维成本显著高于 Cloud，且不影响隐私/审计/压测目标。
- Cloud 路径能提供同等可控的事件审计、网络拓扑和成本边界。
- 后续 Tier B/C 托管 Realtime 成为主线，LiveKit 只做旁挂 STT/turn detector。

### 教训

LiveKit 开源不代表无需 API key/secret；自托管同样需要 key/secret 做 agent 与 SFU 的鉴权和 token 签名，只是 key 由自己的 server 配置而非官方 Cloud 提供。

## Mini + Studio 拆分部署主线（2026-06-23）

<!-- status: 生效中 -->

<!-- files: docs/DEPLOYMENT-MINI-STUDIO.md, docs/ARCHITECTURE.md, README.md -->
<!-- related: M0 LiveKit 接线与自托管主线 -->

### 现象

自托管 LiveKit 主线确定后，需要进一步决定 LiveKit、voice-agent、模型/评测分别部署在哪台机器：Mac mini、Studio M2 Max、云服务器还是 HP/dev198。

### 根因

LiveKit SFU 的核心瓶颈是网络入口稳定性、TURN/WSS 与常驻性；voice-agent worker 和后续本地 STT/TTS/LLM 更吃算力。Mini 与 Studio 通过雷电网桥连接，允许把入口和算力拆开，而不牺牲内网低延迟。

### 候选方案

| 方案 | 做法 | 优点 | 缺点/风险 |
|------|------|------|----------|
| A. Studio all-in-one | Studio 同时跑 LiveKit + worker + 模型 | M0 快测简单，少一台机器 | 入口与模型实验耦合，重启/负载影响进房 |
| B. Mini 入口 + Studio worker | Mini 跑 LiveKit SFU/TURN/WSS；Studio 跑 worker/模型 | 职责清晰，常驻入口稳定，算力独立 | 需要维护两机网络与雷电网桥地址 |
| C. 云服务器入口 | 云上跑 LiveKit/TURN，Studio 只跑 worker | 外网用户体验更可控 | M0 运维成本高，且现有 RackNerd 线路丢包/延迟不理想 |
| D. HP/dev198 主链路 | HP/dev198 跑 LiveKit 或 worker | 算力/实验空间大 | 不如 Mini/Studio 贴近当前编排链路，M0 不必要 |

### 决策

**选择**：方案 B — Mini 入口 + Studio worker。

**理由**：Mini 已是常驻编排中枢，适合放 LiveKit SFU/TURN/WSS；Studio M2 Max 通过雷电网桥与 Mini 相连，适合跑 `voice-agent worker`、Voice-Eval 和后续本地模型。这样既保留自托管可控性，又避免把网络入口与算力实验绑死。

**放弃的方案**：
- 方案 A：可作 M0 临时快测，但不作为主线。
- 方案 C：Beta 外测再评估，当前不把复杂度前置。
- 方案 D：HP/dev198 保留为评测/大模型实验节点，不进入 M0 主链路。

### 改动

- 新增 `docs/DEPLOYMENT-MINI-STUDIO.md` 作为部署拓扑单一说明。
- `docs/ARCHITECTURE.md` 增加 Mini + Studio 自托管拓扑。
- `README.md` 增加部署文档入口。

### 验证

本次是文档/架构落盘；代码质量门沿用 M0 当前结果：`make m0-smoke` 契约覆盖 8/8，`ruff`/`mypy`/`pytest` 全绿。

### 什么条件下该翻这个决策

- Studio 作为 worker 的稳定性不足，休眠/网络/IP 漂移影响会话。
- Mini 上 LiveKit 的公网 TURN/WSS 难以满足外测质量，需要迁云。
- 本地模型全部迁到 HP/dev198，并且 Studio 不再承担算力节点职责。

### 教训

部署实时系统不要只按“哪台机器更强”分配；SFU 是网络入口问题，Agent/模型才是算力问题。雷电网桥的价值是让两者拆分后仍保持低延迟。
