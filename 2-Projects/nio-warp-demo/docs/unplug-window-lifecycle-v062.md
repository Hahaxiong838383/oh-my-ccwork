# v0.6.2 拔屏窗口生命周期修复

## 现象与证据

用户确认 v0.6.1 的无外屏启动和接屏工作正常，但最后一次拔出外屏后程序退出。

本机 `NIOWarpApp-2026-09-07-212503.ips` 记录版本 0.6.1 (11)，异常是 `EXC_BAD_ACCESS / SIGSEGV`，主线程停在 `objc_release → AutoreleasePoolPage::releaseUntil → objc_autoreleasePoolPop`。这是崩溃，不是主动退出流程。

最小复现只创建与正式输出相同的隐藏无边框 NSWindow，不捕获屏幕，不显示覆盖层：

- 默认 `isReleasedWhenClosed = true`：关闭后在池排空时出现 `ProbeOutputWindow release: message sent to deallocated instance`，子进程退出码 133。
- 显式设置为 `false`：相同创建/关闭序列正常结束，退出码 0。
- 复现中的 Zombie 检测仅用于该临时子进程，没有修改生产 App 或系统全局设置。

## 根因与改动

输出窗口由 Swift ARC 的强引用持有，但 NSWindow 默认仍在关闭时自行释放；v0.6.1 的断屏重建显式调用 `close()`，使自动释放与 ARC 释放叠加。控制台窗口原本已关闭这项自动释放，漏掉的是输出窗口。

- 在 `OutputWindow` 的指定初始化器中统一设置 `isReleasedWhenClosed = false`，由 ARC 负责寿命，所有生产初始化路径都获得相同约束。
- 不用“只隐藏不关闭”来绕开释放问题，继续正常关闭和回收旧输出窗口。
- 自动退出策略增加保护：会话重建中、控制台仍可见或已最小化时，不因内部窗口关闭退出。主动退出按钮仍有效。
- 不修改画布、AA、多项式、镜像或已保存配置。

## 回归与边界

自动化覆盖正式五参数初始化路径、关闭后仍持有的引用、重复关闭、300 次创建/关闭/自动释放池排空后的对象回收，以及重建/可见/最小化/正常关闭四种退出决策。

窗口生命周期压力测试不等于 300 次真实 HDMI/USB-C 拔插；物理拔插、休眠唤醒和全屏播放器组合仍需实际场景验证。

本机修复前基线：`.rollback/20260907-212500-window-close-baseline/`，包含 v0.6.1 App ZIP、源码和配置。原始崩溃报告、测试日志和私有回滚包不上传 Git。
