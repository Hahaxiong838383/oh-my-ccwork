## 结论

主要问题在 `native/Sources/NIOWarpApp/ProtoPieSystemDriver.swift` 的 `ProtoPieCDP.call`（当前约第 689–715 行）：每条浏览器控制命令创建一个 `URLSessionWebSocketTask`，取回结果后取消。当前运行环境中，这些短连接的任务及配套 CFNetwork/Network 对象在关闭后仍被保留。不断创建并关闭连接，导致堆内存按命令数量累积。

已确认到“CDP 高频创建/关闭 WebSocket → 任务对象簇残留 → App 堆持续增长”这一可复现路径。尚未拿到 CFNetwork 内部完整持有链，不能断言 Apple 内部具体哪一行或哪一个循环引用有错，也不能把尚未上线的连接复用称为修复完成。

## 1. 实机对象证据

对同一个 NIOWarpApp PID 15475 使用有时限的 `heap --forkCorpse --noContent -s`，分析快照副本，不调试注入、不修改 App；每次约 19 秒完成。输出只用于对象类型/数量/字节统计，原始文本按 250000 字符截存，完整排序前部保留。没有导出完整内存图或页面内容。

| 对象 | 07:19:51 | 07:21:25 |
|---|---:|---:|
| `__NSURLSessionWebSocketTask` | 117237 | 117448 |
| `URLProtocol` | 117238 | 117449 |
| `NWIOConnection` | 117238 | 117449 |
| `CFHTTPMessage` | 703434 | 704700 |

约 94 秒内 WebSocket 任务增加 211 个，配套网络对象同步增长。实际 `lsof` TCP 检查仅看到 1 个已建立连接：这是**任务/网络对象没有回收**，不能误称还有 11.7 万条活跃 TCP 连接。

全仓仅两个 `webSocketTask` 创建入口。另一处 `MouseInputURLSessionWire` 按鼠标映射会话复用连接，不是每个输入事件创建。当前堆中大量 CFNetwork 类型及独立复现，将排查重点从 UI/Metal 收敛到了 CDP 短连接。

稳定监测每约 3 秒至少有 5 次 CDP 请求，切源、准备、几何确认、恢复和清理还会增加请求。不能将稳态频率直接当整夜实际频率。现场每套残留网络对象约为十几至二十 KB，量级与已观察到的约 149 MiB/小时增长吻合。

## 2. 本机最小复现与排除实验

从生产文件原样提取 `ProtoPieCDP.call`，仅调整枚举可见性和测试错误类型。连接独立的 Python 回环 WebSocket 假 CDP 服务，响应固定 JSON、正常回复关闭帧；不接真实浏览器、原型或开发机 App。每组独立进程执行 6000 条命令，结束等待约 8 秒，再读取 `phys_footprint`、malloc 存活数量和字节数。本机 macOS 26.4.1。

| 实验 | footprint 净增长 | 观察 |
|---|---:|---|
| 原样生产调用 | 106.67 MiB | malloc 净增约 98.82 MiB、104 万个存活分配 |
| 直接 `task.cancel()` | 103.02 MiB | 不能消除增长 |
| 每次私有 ephemeral session，结束 invalidate | 191.98 MiB | 不能消除增长，当前实验增长更大 |
| send/receive 都改 completion handler | 102.50 MiB | 首 10 个弱引用仍存活 |
| 仅 send 或仅 receive 改 completion handler | 约 102.4–102.7 MiB | 不能消除增长 |
| 所有命令复用一条 WebSocket | 1.64 MiB | 暖机后未出现同类按命令增长 |
| 仅 JSON 编解码 | 1.42 MiB | 无同量级增长 |
| 仅创建/取消 deadline Task | 1.33 MiB | 无同量级增长 |

原样调用在暖机后约残留 17032 字节/命令。多组结束后 `URLSession.getAllTasks` 为 0，仍不能说明对象已经释放；callback 组保留的仅是弱引用，首 10 个 task 仍非 nil。`production`/`reuse` 组没有放入弱引用观察列表，因此其日志中的 `weak-0` 不能作为对象已释放的证据。

再对独立 callback 程序执行 1000 次后取堆：恰有 WebSocketTask/URLProtocol/NWIOConnection 各 1000、CFHTTPMessage 6000，与现役 App 的堆类型和倍数关系一致。由此排除原型页面内容、实际 Chrome、UI/Metal、纯 JSON 和 deadline Task 是复现该增长所必需的条件。不能据此宣称 App 其他路径绝无任何小问题。

## 3. 开发机同系统交叉复现

把同一组冻结源码送到开发机临时目录独立编译，在 macOS 26.6.2 上连接新建的回环假服务；不接触专用 Chrome 或 NIOWarpApp 的连接。每组 2000 条命令：

| 实验 | footprint 净增 | malloc 净增 |
|---|---:|---:|
| 原样生产调用 | 37.53 MiB | 33.49 MiB |
| completion handler 收发 | 36.34 MiB | 33.34 MiB |
| 单连接复用 | 1.84 MiB | 0.38 MiB |

三组均成功完成，待处理任务数为 0；callback 组弱引用仍活 10 个。假服务由 `finally` 定向关闭，三个测试进程正常退出，未安装任何后台服务或依赖。现役 App PID 15475 没有改变。

## 4. 修复建议与验证边界

下一步应只修 CDP 连接的管理方式，优先消除“每条命令新建连接”，而不是改画面算法或直接用重启掩盖增长。

1. 设计有明确所有者和数量上限的持久控制连接，按请求 ID 路由响应，正确处理并发、超时、取消、断线和旧响应。
2. 不能只做到“每个页面复用一条”便宣布根治：每次切源仍创建/关闭页面连接，可能把按命令增长变成按切源增长。应同时验证页面轮换、失败重试和重连的对象数量是否有界；可评估浏览器级长连接与页面 session 路由，具体方案待实现前确认。
3. 保留当前目标身份、配置代际、精确页面清理和输入安全边界，避免恢复已解决的声音叠加、旧页面捕获或取消泄漏问题。
4. 独立复用实验只证明修复方向有效，没有验证完整 App 的页面切换、连接断开、合盖、鼠标/键盘或长稳。生产修复需先做好现役包/源码/最新配置配对回滚，再做专项回归及同条件连续 8 小时测试。
5. 每日有人正常退出 App/关机的使用场景下，暂不增加自动重启或自动恢复；先验证根因修复效果。

API 语义交叉核对：[Apple 的 WebSocket cancel 文档](https://developer.apple.com/documentation/foundation/urlsessionwebsockettask/cancel%28with%3Areason%3A%29)描述的是发送关闭帧；[invalidateAndCancel 文档](https://developer.apple.com/documentation/foundation/urlsession/invalidateandcancel%28%29)明确对 shared session 无效。文档只解释接口语义，实际对象残留结论来自上述实验；不能凭调用了 cancel 或任务列表为空判定内存健康。
