## 现象和实机证据

用户报告：切换演示链接时，笔记本内屏出现 Chrome 预览窗口后又消失；点击“开始计划”也出现相同现象。

上一轮调查复现时间均为北京时间：

| 时间 | 观察 |
|---|---|
| 08:39:39.249 | 通过当前工作台“开始计划”按钮触发新计划 |
| 08:39:39.314 → 08:39:39.496 | 前台应用由 NIO PID 1624 变为 Chrome PID 1626 |
| 08:39:39.496–39.787 | 同一 Chrome 进程的新窗口 1476 经全屏 Spaces 动画进入内容屏，落定到 `[3432, 0, 1920, 1100]` |
| 08:39:43 | 新来源 `item_ready`，随后旧窗口 1455 被回收 |
| 08:40:13 → 08:40:17 | 下一链接准备并正常就绪 |

检查结束只有一个 NIO 自有预览页面；控制诊断累计 connections=3、disconnects=2、timeouts=0，与调查开始的计数一致。窗口、视口和捕获尺寸匹配，未观察到这次切换导致 Chrome 进程重启。

证据边界：采样直接证明了抢前台与全屏动画，没有逐帧录屏证明内屏完整窗口矩形，也未判定用户所说“两次闪现”分别对应哪个动画阶段。该记录不能扩大为全部输入、声音或长稳验收。

## 原因

`ProtoPieSystemDriver.cloudTarget` 在切换新链接或强制重播时，通过 `NSWorkspace.openApplication` 和 `--app=<URL>` 请求新窗口。虽然设置 `activates=false`，实测 Chrome 仍会前置其现有进程并创建窗口；该设置没有阻止 Chrome 自身的开窗及全屏行为。

`prepareCloud` 等网页内容就绪后才执行窗口定位和全屏验证，准备过程未隔离这些可见过渡。自动准备流程没有调用专供“打开播放器”按钮使用的 `openForUser`，不能将其归因于用户误操作。

这套开窗顺序在 v73/v74 已存在；v75 保证新计划首项进入新文档，因此“开始计划”也会经过该流程。持久控制连接不是本次发现的新增激活入口。

## 优化影响评估（仅候选，未实施）

可考虑仅调整专用 Chrome 已运行时的候选窗口创建、初始位置和前台激活行为，保留独立窗口及现有交接逻辑。后台创建是否真正避免当前 Chrome/macOS 的前置和全屏动画，仍须实机验证。

| 现有功能 | 必须保留的约束 |
|---|---|
| 校正、AA、镜像、预设、取景 | 不改参数和算法；新窗口的 viewport、DPR、捕获尺寸仍须一致 |
| 原圆圈、鼠标、键盘、Esc | 保留已验证的页面焦点桥及 NIO 输出窗输入所有权；新文档就绪后重新绑定目标和尺寸，清理旧指针缓存 |
| 轮播、时长、脚本 | 新计划首项继续真正重播；画面及必要输入就绪后才计时，后台加载不等于可以演示 |
| 失败、取消、声音和页面回收 | 新页捕获成功前保留旧有效页，成功后精确释放旧页；失败只清理本次候选，不关闭用户其他窗口 |
| 首次启动、登录、主动打开播放器 | 保留显式前置和人工处理入口；不能把热切换优化宣称为所有冷启动场景零闪现 |
| 降级 | 现有 legacy 仅切换控制传输，不会回退新的开窗策略；若实施，须另保留旧开窗流程或配对整版回滚 |

特别限制：`ProtoPieCoordinator` 当前按新旧 `windowID` 是否不同决定释放旧会话或候选。直接改成同窗多标签会突破回收假设，并可能捕获错误标签或遗留页面。输入还要求真实 fullscreen 和一致的捕获几何；最小化或隐藏整个 Chrome 不是已验证的替代方案。

请求创建窗口的结果不明时，也不能直接再走一次旧开窗路径，否则可能新增重复页面。应先核对目标归属及清理结果。这些均属于后续实现约束，本次未增加新逻辑。
