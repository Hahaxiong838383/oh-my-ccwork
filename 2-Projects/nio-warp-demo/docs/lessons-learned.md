# NIO 全屏 Warp Demo 经验复盘

## 结论

这次 Demo 最重要的结论不是“把矩形拉弯”，而是把问题拆成三个独立层级：

1. **内容空间**：先扩大虚拟画布短边，确保完整内容有地方布局。
2. **光学空间**：用逆映射生成预畸变画面，使反射后的目标区域恢复方正。
3. **系统空间**：捕获外屏完整桌面，排除自身覆盖层，再将 Warp 结果回显到同一外屏。

只有三层同时成立，才算“完整利用反射屏幕且内容仍然方正”。最大内接矩形只能保证安全显示，不等于完整利用。

## 关键决策

| 决策 | 选择 | 原因 |
|---|---|---|
| 内容利用目标 | 全 Footprint，而非最大内接矩形 | 用户明确要求使用完整反射区域 |
| 画布模型 | 输入源短边可扩展的虚拟画布 | 将“内容容量”和“物理屏分辨率”解耦 |
| 算法验证 | 先做离线双变换闭环 | 可量化覆盖率、误差和越界，避免直接陷入系统工程 |
| 交互验证 | 浏览器双窗口 | 最快验证参数调节、外屏全屏和画布高度变化 |
| 整屏接管 | ScreenCaptureKit + Metal | 浏览器无法处理其他应用窗口，原生链路才能覆盖完整桌面 |
| 同屏回显 | 捕获外屏并排除当前应用 | 保留原有外屏内容，同时避免无限递归回采 |
| 控制台 | MacBook 内屏普通 `NSWindow` | `NSPanel` 在多 Space 和失焦场景下可能不可见 |

## 做对了什么

### 1. 先校准验收口径

最初容易把“校正后方正”理解为在畸变区域内找最大安全矩形。用户真正目标是：

- 反射后完整屏幕区域都被使用；
- 内容依然方正、可读；
- 允许输入源短边扩展，而不是裁掉边缘。

因此验收指标必须同时包含：有效内容覆盖率、像素误差、UV 越界比例和完整边界可见性。

### 2. 用三阶段 Demo 降低风险

- **离线 Python**：证明扩展画布与逆映射数学闭环。
- **浏览器双窗口**：证明 MacBook 控制、外屏输出和参数实时同步。
- **原生 Swift**：证明完整桌面捕获、同屏 Warp 和 60 FPS 链路。

每一阶段只引入一类新风险，问题定位明显快于一步到位开发原生应用。

### 3. 同屏捕获必须排除自身

如果直接捕获外屏并把结果显示回外屏，覆盖层会被下一帧再次捕获，形成递归画中画。正确做法是：

- 使用 `SCContentFilter(display:excludingApplications:exceptingWindows:)`；
- 将当前应用加入排除列表；
- 覆盖窗口保持全屏、无边框、鼠标穿透。

### 4. TCC 权限依赖稳定代码身份

临时构建每次产生不同 designated requirement 时，macOS 可能把它识别成新应用，导致屏幕录制权限反复失效。构建脚本应固定：

- `CFBundleIdentifier`；
- designated requirement；
- 应用路径和可执行文件名。

Ad-hoc 签名仍适合本机 Demo，但正式交付应改为 Developer ID 签名和公证。

### 5. 多屏坐标存在 points/pixels 双口径

MacBook 和 5K 外屏都可能启用 Retina 缩放：

- `NSScreen.frame` 是 points；
- ScreenCaptureKit 配置和纹理通常使用 pixels；
- 窗口位置可能出现负坐标；
- 不能用“第一个屏幕”假定内屏或外屏。

应通过 `CGDisplayIsBuiltin` 识别内屏，并从其余屏幕中选择目标外屏。

## 踩坑与修正

| 踩坑 | 表现 | 修正 |
|---|---|---|
| 只做最大内接矩形 | 边缘被浪费，违背完整利用目标 | 增加虚拟画布短边并按全 Footprint 验收 |
| 只做浏览器全屏 | 只能 Warp 浏览器内容，无法处理其他应用 | 增加 ScreenCaptureKit 原生整屏链路 |
| 捕获和输出同屏未排除自身 | 递归画中画或反馈闪烁 | 从捕获过滤器排除当前应用 |
| 每次构建身份变化 | 屏幕录制权限反复申请 | 固定 bundle ID 与 designated requirement |
| 使用 `NSPanel` 做控制台 | 多 Space 或失焦后窗口不在屏幕上 | 使用普通 `NSWindow` + `orderFrontRegardless()` |
| 用 `open` 启动命令行构建 App | 某些终端上下文中应用启动后立即退出 | `.command` 直接 `exec` App 可执行文件 |
| 只看截图判断成功 | 可能漏掉递归回采、窗口不可见和性能问题 | 同时检查窗口列表、帧稳定性、CPU/RSS 和日志 |
| 把视觉接管等同于可交互接管 | Warp 后看到的位置与真实点击坐标不同 | 明确输入逆映射是独立阶段 |
| 测试图在 Shader 中提前返回 | 普通桌面镜像生效，但标定网格镜像无效 | 所有采样路径先统一执行 `applyMirror`，再进入测试图或桌面渲染 |
| 网格图案过度对称 | 镜像可能已经生效，肉眼仍误判为没变化 | 四角加入粉、青、黄、橙非对称角标，覆盖四种镜像组合 |
| 使用 `⌘⌥Esc` 做紧急隐藏 | 与 macOS“强制退出应用”保留快捷键冲突，无法可靠注册 | 改为 `⌃⌥⌘Esc`，并在控制台明确显示当前快捷键 |
| 紧急隐藏只改变窗口状态 | 覆盖层已隐藏，但控制台仍显示“运行中” | 安全动作必须通过统一状态机回写 UI，禁止窗口状态和按钮状态分叉 |
| 控制台跟随错误屏幕恢复 | 外屏变化后控制台可能被重建到外屏并被 Warp 覆盖 | 每次显示器重建都重新用 `CGDisplayIsBuiltin` 定位内屏 |
| 只以 FPS 判断抗锯齿可用 | 平均帧率正常仍可能存在 GPU 尾延迟或内存持续增长 | 同时验收 GPU 平均、GPU P95、CPU 和 10 分钟 RSS 趋势 |
| 抗锯齿 A/B 左右图案不同 | 颜色、位置和几何差异掩盖算法差异，比较结论不可归因 | 两半屏映射到相同局部 UV，图案/颜色/线宽一致，只改变采样和平滑策略 |
| 标定网格始终解析平滑 | 抗锯齿开关对网格看不出差异，误以为功能未生效 | 标定网格的硬边/平滑边严格跟随总开关 |
| A/B 直接从保存配置生成 | 从无畸变模式进入 A/B 后重新启用 Warp，诊断图被扭曲 | A/B 固定从无畸变配置生成，并恢复进入前的预览模式 |
| Retina 外屏沿用逻辑点尺寸 | 新外屏黑屏或 viewport/scissor 尺寸错误 | 捕获、drawable 和渲染裁切统一使用物理像素，窗口定位保留 points |
| 不同外屏共用全局配置 | 新屏继承旧屏 AA/Warp 参数后内容不可见 | 配置按硬件标识隔离，只允许同分辨率旧配置迁移 |
| 只反转单个弧度参数 | 不能正确反转倾斜、不对称和多项式增量 | 对完整位移场统一取反，并重新归一化铺满 AA 区 |

## 阶段 1 可复用方法

### 1. 所有显示模式共享同一套坐标变换

桌面纹理、标定网格、边界、中心线和角标不能各自实现镜像或 Warp。正确顺序是：

```text
物理像素 → AA 区归一化坐标 → 镜像 → Warp 逆映射 → 内容采样/测试图着色
```

任何调试分支在镜像之前提前返回，都会造成“生产画面正确、测试图错误”的双口径问题。

### 2. 对称测试图必须加入非对称证据

规则网格、中心线和矩形边框在水平或垂直翻转后视觉上仍高度相似，不能作为镜像验收的唯一证据。四个角必须使用不同颜色或编号，并分别验证：

- 不镜像；
- 仅水平镜像；
- 仅垂直镜像；
- 水平与垂直双镜像。

### 3. 安全控制必须独立于主渲染链路

- 紧急隐藏使用系统未保留的组合键 `⌃⌥⌘Esc`；
- 暂停、紧急隐藏、外屏断开和分辨率变化统一进入安全状态；
- 覆盖层先隐藏，再停止捕获或重建资源；
- 控制台状态、按钮文字和实际覆盖层可见性必须同步。

### 4. 抗锯齿采用质量档位和运行时保护

- 关闭：单点采样，用于性能基线和问题定位；
- 性能：4 点自适应采样，作为 5K 60 Hz 日常默认；
- 质量：9 点采样，用于静态标定和质量对比；
- 自动降级只改变当前有效档位，不覆盖用户保存的质量配置。

性能判断不能只看 FPS。至少同时采集 GPU 平均耗时、GPU P95、CPU 和 RSS；尾延迟比平均值更能暴露偶发卡顿。

### 5. A/B 对比必须满足单变量原则

抗锯齿 A/B 的左右两侧必须使用同一张测试图：相同坐标、相同几何、相同颜色、相同线宽和相同背景。每半屏应独立映射到相同的 `0...1` 局部 UV，唯一变量只能是采样和平滑算法。否则肉眼看到的差异无法归因于抗锯齿。

普通标定网格也必须遵守抗锯齿总开关。如果网格始终通过 `fwidth + smoothstep` 平滑，那么桌面纹理虽然已经切换 nearest/多点采样，用户仍会因为网格无变化而判断“开关没生效”。

### 6. 运行时预览需要显式返回状态

无畸变标定和抗锯齿 A/B 都是临时预览，不能直接从保存配置覆盖式切换。进入 A/B 时记录前一预览模式；A/B 配置关闭基础 Warp 和多项式 Warp；退出时恢复进入前模式，并用配置哈希确认没有污染保存配置。

### 7. 反向预畸变应反转完整位移场

玻璃反射示意图显示中心凸起时，屏幕端预畸变应采用中心内凹、两侧翘起的相反趋势。实现不能只把“上下弧度”改符号，而应对基础 Warp 和多项式共同形成的位移场统一反向。反向后重新计算边界并归一化铺满 AA 区，避免越界或边缘裁切。

### 8. Retina 外屏必须分离 points 与 pixels

AU16O 的 `1920×1200 pt` 对应 `3840×2400 px`。窗口位置和尺寸属于 points，ScreenCaptureKit、Metal drawable、viewport 和 scissor 属于 pixels。两套坐标混用会出现黑屏；外屏变化后还应按硬件标识加载独立配置，并在屏幕未唤醒时自动重试。

## 验收方法

### 算法层

- 全 Footprint 有效内容覆盖率不低于 99%。
- 平均灰度误差不高于 4。
- P95 灰度误差不高于 12。
- UV 越界比例接近 0%。
- 手动增加画布高度后仍通过同一组门槛。

### 系统层

- 外屏原有桌面、菜单栏及应用窗口均被整体 Warp。
- 内屏控制台可见并能实时调参。
- 连续截图不出现递归回采或逐帧放大。
- 输出窗口覆盖目标外屏，控制窗口位于内屏。
- 目标刷新率下无持续错误日志，CPU 和内存可接受。
- 重建后屏幕录制权限保持稳定。

### 阶段 1 实机结果

- 三星外屏：`5120×2880 @ 60 Hz`。
- 质量模式：`60 FPS`，GPU 平均 `9.09 ms`，GPU P95 `11.42 ms`。
- 连续 10 分钟：61 个采样，CPU 平均 `8.73%`，范围 `5.8%–24.8%`。
- RSS：从 `130240 KB` 降至 `103408 KB`，无持续增长。
- Swift 测试：`16/16` 通过。
- Release：稳定 Apple Development 身份签名，严格代码签名校验通过。
- 日常配置：性能模式、自动降级开启、标定网格关闭、水平/垂直镜像关闭。

### 用户层

- “完整显示”模式下，四周内容均可见，没有被最大内接矩形裁掉。
- 直线、文字、网格在模拟或真实反射观察面上保持可接受的水平与垂直关系。
- 明确标注鼠标坐标尚未逆映射，避免把视觉 Demo 误当生产交互方案。

## 后续阶段

### P0

1. **外屏验收通过**：保持原始宽高比，目标区域多余内容裁切，支持裁切锚点。
2. **软件验收通过，待玻璃拍摄**：一键无畸变标定临时关闭基础和多项式 Warp，退出后恢复原配置且不写保存档。
3. **外屏验收通过**：抗锯齿总开关、性能/质量档位和相同图案左右分屏 A/B 诊断图。
4. **外屏验收通过**：Retina 物理像素适配、显示器配置隔离和反向预畸变趋势。
5. 增加物理屏点击坐标到原桌面坐标的逆 Warp 输入映射。
6. 固定相机、外屏和反射介质位置，拍摄真实玻璃原始畸变网格。

### P1

1. 从实拍图提取控制点，以 TPS/RBF 或预计算 UV LUT 替换模拟参数。
2. 将控制点、显示器 EDID、分辨率、玻璃和观察位保存为可版本化标定配置。
3. 为自动性能策略增加迟滞、质量恢复和持续告警。
4. 压测外屏拔插、休眠、唤醒和分辨率切换。
5. 在目标 7680×936 硬件上验证刷新率、带宽、延迟和温升。
