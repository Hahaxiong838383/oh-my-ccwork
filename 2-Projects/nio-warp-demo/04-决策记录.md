### 现象

用户先发现反射画面顶部白边，随后反馈合盖再开盖后演示退出，最后在真实合盖期间发现外屏演示停止。目标是笔记本作为演示服务器运行：闭盖保持原 ProtoPie 演示，开盖可继续操作工作台，已调好的 Warp 参数不变。

当前代码基线为 `123153ad6851993ccbf5941d3955aa041c658199`，安装版为 **v0.11.7 (34)**。用户于本轮明确反馈“我盒盖翻盖都正常了”，完整物理开合周期已获现场确认。

### 排查过程

| 阶段 | 证据与处理 | 当时没有证明什么 |
|---|---|---|
| v0.11.5 | Chrome 最大化窗口比网页内容高 32px，整窗捕获带入标题栏；改为外屏原生无边框全屏，窗口、网页及捕获尺寸一致后接通 | 只证明标题栏去除及启动流程正常，没有覆盖物理合盖引起的显示拓扑变化 |
| v0.11.6 | 发现系统重建临时隐藏被写成用户暂停；增加全屏健康检查、异步过期结果保护和工作台边界约束。实测退出全屏、移到内屏后自动恢复 | 窗口退出全屏/迁移是故障注入，不等同于真实合盖；当时仍未检验控制屏从系统屏幕列表消失 |
| v0.11.7 | 真实合盖时只剩 AUO 外屏，CoreGraphics 显示 active=true、asleep=false，系统禁休眠有效；应用却因 `screens.count < 2` 进入待机并销毁输出 | 安装后约两分钟闭盖稳态采样，只证明该段时间持续输出，不能单独证明完整开合周期或长期稳定 |
| 用户最终验收 | 用户实际开合盖后确认均正常 | 此次功能验收不外推为所有显示器、所有睡眠/断电场景或逐帧零丢帧保证 |

### 根因

显示会话把“必须同时存在控制屏和输出屏”当作运行前提，并在任意屏幕变化时无差别销毁输出；因此即使目标外屏仍亮着，内屏因合盖消失也会中断演示。此前修复集中在 Chrome 全屏和暂停状态，遗漏了这个独立的拓扑根因。

### 候选方案

| 方案 | 做法 | 优点 | 缺点/风险 |
|---|---|---|---|
| A. 只重进 Chrome 全屏 | 发现异常便恢复播放器全屏 | 能去标题栏，能恢复窗口位置/尺寸 | 应用已停捕获或等待第二块屏幕时，Chrome 全屏也不能恢复 Warp |
| B. 仅加强系统禁休眠 | 调整电源设置、保活进程 | 适用于真实系统休眠 | 此次外屏已醒着，无法修复应用主动停止；重复配置会掩盖根因 |
| C. 任意屏变都重建或重载 | 所有通知统一停止捕获、重建输出、重开页面 | 实现简单 | 内屏消失、桌面原点变化也打断演示；重载还会丢失原型播放状态 |
| D. 按目标外屏状态分类处理 | 外屏身份、像素模式、缩放不变且醒着则保留资源；控制屏可为空，真正失效才重建 | 合盖继续原演示，开盖恢复操作；保留明确的断开恢复路径 | 必须区分瞬时拓扑、实际断开、用户暂停和无头操作 |

### 决策

**选择 D，并保留 v0.11.5/6 已实现的全屏检查及用户意图保护。**

运行条件是存在可用目标外屏，而非屏幕数量至少为二。唯一外屏支持运行与冷启动；唯一内屏仍不作为 Warp 输出。优先保留已选择的外屏，不能因主屏变化或屏幕数组重排换输出。

- 以目标外屏 identity、物理像素尺寸、backing scale 及 CoreGraphics active/asleep 判断是否可保留。桌面坐标原点只是布局信息，不是重建条件。
- 仅内屏消失或外屏原点变化时，保留 renderer、capture、ProtoPie 页面和 session epoch，仅移动输出窗口；判断必须早于取消任务、递增 epoch 和隐藏画面。
- 真正 inactive 后即使外屏很快返回，也必须完成重建。`outputWasDisconnected` 防止保留路径取消已必需的重建，留下永久隐藏的窗口。
- 系统临时隐藏与用户主动暂停分开记录。系统通知不能把用户的继续演示意图改成暂停；用户暂停、停止和人工打开播放器也不能被自动恢复覆盖。
- 睡眠通知不能替代外屏状态检查。使用已缓存的输出 ID 查询 CoreGraphics，覆盖 `NSScreen` 短暂缺失；“正在重建”或“模式变化”不等于外屏睡眠。
- 无独立控制屏时工作台自动隐藏、不抢焦点。用户明确打开工作台时先暂停演示，再在唯一外屏提供控制；恢复演示后隐藏工作台。开盖将工作台迁回内屏，位置限制在可见范围内。

**放弃的方案及重评条件：**

- 单靠全屏恢复：仅在显示拓扑与捕获都正常、问题确为播放器退全屏时采用；不能替代会话恢复。
- 单靠电源配置：仅在 CoreGraphics/系统日志证明目标外屏或系统真实休眠时重新评估。
- 每次通知强制重建、重开页面：只在输出身份、像素模式、缩放变化或实际断开时重建必要资源；页面仍可用时不主动重载。
- 坚持双屏才运行：该默认已不符合本项目的合盖演示用途；若未来产品要求唯一屏幕必须始终可本地交互，再以显式运行模式重新设计，不能偷偷恢复旧限制。
- 用垂直裁切遮 Chrome 标题栏：不采用。源头去边框，内容适配单独处理；裁切会影响可见内容，且当前画面比例下纵向滑块未必起作用。

- 固化必须让**签名、源码、安装版本、当前参数、配对回滚**五项可相互核对，不能只保存代码 tag。固定安装路径 `/Users/futurus/Applications/NIOWarpApp.app`，记录 designated requirement、源码/二进制指纹与版本；以设备实读值保存快照；本轮用户明确选定14:02快照，之后的活动调整保留不回写。不能把任一旧预设重新套用成“当前值”，也不能因活动值继续变化而静默更换已选定基线。

### 什么条件下该翻这个决策

- 更换外屏、缩放/像素模式、显示排列或多外屏控制策略时，复核输出身份选择和保留条件；不凭历史 display ID 或坐标猜设备。
- macOS、Chrome 或 ScreenCaptureKit 升级导致全屏、窗口迁移、捕获生命周期变化时，重做上述实机检查。
- 原型改为本地 Studio Preview，或提出无外屏运行、唯一屏幕同时控制与展示、断电续播等新要求时，重新定义会话和操作边界。
- 出现长期运行故障时，按故障时长补充持续观测；本次两分钟采样和一次用户确认不豁免新的长稳验证。

### 教训

从用户描述“退出全屏”到实现之间，要同时确认播放器、捕获、Warp 覆盖层和显示拓扑，不能用单一窗口状态代替端到端现象。第一轮修复解决了真实问题，但验收触发条件不完整，漏掉了合盖移除控制屏这一独立路径。之后的证据必须注明触发方式、持续时间、自动化工具与现场确认范围；只有对应的真实行为通过，才宣称该行为修复完成。

## 2026-09-18：鼠标映射使用完整可见曲面，排除Chrome附属窗口

用户批准方案并要求边缘尽量用满。选择实际已渲染三角网格的凹形可见交集，热点距物理边界0.5px，光标图案可裁切；不使用最大内接矩形或光标半径内缩。相对输入默认在源内容空间累计，再沿相同镜像/适配/网格显示指针；CDP只绑定当前Cloud页面。独立偏好不改校正数据。

实机发现“网页尺寸等于纹理尺寸”仍不足以证明坐标一致：Chrome隐藏工具栏被includeChildWindows算入捕获，元数据为936/968缩放。屏幕rect与缩放前内容大小不一致，无法可靠猜网页偏移。采用Cloud-only排除附属窗口，从源头恢复满幅；原生Studio保留children，真实metadata/viewport/texture三方一致才允许点击。必须说明视觉内容约3.3%的旧缩小被消除，不能说画面尺寸完全不变。

恢复先同步归还系统鼠标，再有界释放原页面按钮；快速新会话等待旧释放，退出程序terminateLater等清理，失焦不抢回前台。全局screenRect原点变化不应使局部映射失效，尺寸、缩放、文档和来源变化则必须暂停。新版本软件与真实事件测试通过，真实玻璃与新开合盖周期仍需现场体验；不复用旧版本人验冒充此次已验。详细证据见[发布记录](docs/mouse-mapping-v0120.md)。
