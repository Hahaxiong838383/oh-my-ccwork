## 2. 帧格式

### 2.1 完整帧

```
+--------+-----------+--------------+-------+--------+---------+------+-----+
| Header | FrameType | SerialCount  |  CMD  | Length | Payload | CRC8 | End |
|  1B    |    1B     |     2B       |  2B   |   2B   |   nB    |  1B  | 1B  |
|  0x5A  |  见下表    |   0..65535   |       |        | 0..1024 |      |0xA5 |
+--------+-----------+--------------+-------+--------+---------+------+-----+
         |<---------------- CRC8 覆盖范围 ---------------->|
```

- 固定开销 **10 字节**（Payload 之外的所有字段）
- `Length` **只算 Payload 段长度**，不含帧头帧尾
- Payload 上限 1024（原文标注「暂定」）

### 2.2 FrameType 取值

| 值 | 含义 |
|---|---|
| `0x01` | No ACK（不需要应答） |
| `0x02` | Need ACK（需要应答） |
| `0x03` | ACK OK |
| `0x04` | ACK Error |
| 其他 | invalid value |

事件型报文中，重要消息可用 Need ACK，接收方收到后回复 ACK。

### 2.3 ACK 帧

- **ACK OK / ACK Error 帧没有 Length 和 Payload 字段。**
- ACK 帧的 `SerialCount` 必须等于对应请求帧的 `SerialCount`，`CMD` 必须等于对应请求的 `CMD`，否则视为**无效 ACK**。

⚠️ **原文未给出 ACK 帧的完整字节布局，也未说明此时 CRC8 覆盖到哪。** cc 按定义推断为：

```
Header(1) + FrameType(1) + SerialCount(2) + CMD(2) + CRC8(1) + End(1) = 8 字节
CRC8 覆盖前 6 字节
```

这是**推断**，实现前必须确认 → [ISSUE-08](#issue-08)

### 2.4 字节序：大端（推断）

⚠️ 原文**没有**明文规定 `SerialCount` / `CMD` / `Length` 的字节序。cc 判定为**大端（MSB 在前）**，三条依据：

1. OTA 文件头明文写「MSB 在前，LSB 在后」；
2. Payload 内所有多字节字段都是高位在前（`0x0100` 使用时长 Byte6=高位/Byte7=低位，平面镜距离 Byte11=高 8 位/Byte12=低 8 位）；
3. **文档自带的 CRC8 测试向量可反解验证**：`5A 01 00A1 0001 0000` 按大端解读 = CMD `0x0001`（查询配置参数，Payload Length=0，No ACK，RK3562→MCU），与命令表完全自洽；按小端解读 CMD 会变成 `0x0100`（MCU 上报状态），那 Length 应为 14 而非 0，自相矛盾。

依据链完整但仍属推断 → [ISSUE-07](#issue-07)

### 2.5 CRC8

| 项 | 值 |
|---|---|
| 算法 | CRC-8 / SAE-J1850 |
| 多项式 | `0x1D` |
| 初值 | `0xFF` |
| 输出异或 | `0xFF` |
| 反射 | 否 |
| 覆盖范围 | Header + FrameType + SerialCount + CMD + Length + Payload |
| 不覆盖 | CRC8 字段自身、End |

> 帧格式表中此字段列名为 **CRC8**，而下方说明第 7 条称其为 **Checksum** —— 是同一个字段。

**测试向量（文档原文，cc 已复算通过）：**

```
输入: 5A 01 00 A1 00 01 00 00   (8 字节)
输出: 0x08
```

`crc_reference.py` 已用查表法与位运算法双向复算，均得 `0x08`；并含负向验证（翻转 1 bit 后 CRC 必变）。

### 2.6 解析器强制要求

1. UART 通讯为不定长数据传输
2. 按帧格式进行数据解析与处理
3. **能正确识别粘包**：多个包头包尾完整的数据无间隔连续接收
4. **能正确处理断包**：一个完整数据帧分两次到达，组合后 CRC 正确即有效
   - **组包超时 200ms** —— 识别到包头后计时 200ms，未完成组包则丢弃数据
5. 充分考虑异常情况，避免解析异常导致死机（例如 Length 字段异常大导致越界访问）

## 4. 命令详解

### `0x0000` 查询外设状态 — R→M, No ACK, Len 0

RK3562 主动向 MCU 查询外设状态，会收到 `0x0100` 的回复。

### `0x0001` 查询配置参数 — R→M, No ACK, Len 0

用于配置管理，回复的都是 EOL 写入的参数。RK3562 主动查询配置状态，会收到 `0x0101` 到 `0x0106` 的回复（`0x0112` 的描述也写明由本命令触发）。

⚠️ 但 `0x0101`–`0x0105` 各自的描述又写「RK3562 在发送查询命令（`0x0000`）时回复」，与本条冲突 → [ISSUE-02](#issue-02)

### `0x0100` MCU 上报状态 — M→R, No ACK, Len 14, EVENT+250ms

整机状态周期上报，同时作为 `0x0000` 的回复。

| Byte | 字段 | 取值 |
|---|---|---|
| 0 | 整机工作状态 | `0x01` 待机：上电+前盖关闭<br>`0x02` 待机：上电+前盖开启+平面镜关闭<br>`0x03` 待机：上电+前盖开启+平面镜开启<br>`0x04` 工作：上电+前盖开启+平面镜开启 |
| 1 | LED 开关状态 | `0x00` 关 / `0x01` 开 |
| 2 | LED 亮度 | `0x01` 低 / `0x02` 中 / `0x03` 高 |
| 3 | LED 色温 | `0x01` 冷光（UI 的「绘画」）/ `0x02` 常规 / `0x03` 暖光（UI 的「夜读」） |
| 4 | 电机状态 | ⚠️ **原文取值为空** |
| 5 | 像距 | 单位分米。⚠️ **原文未给范围与无效值** |
| 6 | 使用时长高字节 + 人在状态 | **bit7** = 人在状态（0 不在 / 1 在）<br>**bit6–bit0** = 使用时长 bit14–bit8 |
| 7 | 使用时长低字节 | 使用时长 bit7–bit0 |
| 8 | 霍尔 1（控制 LED） | `0x00` 无磁场，开盖，开灯 / `0x01` 有磁场，合盖，关灯 |
| 9 | 霍尔 2（遮光板识别） | `0x00` 无磁场 / `0x01` 有磁场 |
| 10 | 护眼屏状态 | `0x00` 未接入 / `0x01` 接入 |
| 11 | 平面镜到桌面距离 高 8 位 | 单位 mm×10，整数值传递 |
| 12 | 平面镜到桌面距离 低 8 位 | 同上 |
| 13 | 最低点状态 | **MAX**：`0x00` 未脱磁（不在最低点）/ `0xFF` 脱磁（最低点）/ `0xEE` 不支持脱磁状态查询（仅 MAX 可能返回）<br>**Ultra**：`0x00` 电机不在最低点 / `0xFF` 电机在最低点 |

**使用时长**：Byte6 低 7 位与 Byte7 拼成 15 位值（bit14–bit0），单位分钟，原文示例 `0x1122` 分钟。**暂定由 RK3562 端计时，MCU 端先将该处置 0。**

> Byte13 是 V2.0 从 `0x0111` 并入本报文的，与 `0x0111` Byte1 定义完全相同 → [ISSUE-01](#issue-01)

### `0x0101` 设备类型 — M→R, ACK, Len 2

MCU 在 EOL 收到写入设备类型并写入成功后，通知 RK3562。

| Byte | 字段 | 取值 |
|---|---|---|
| 0 | 设备类型 | `0x00` Air / `0x01` Pro / `0x02` Max / `0x03` Ultra / `0x04` LE Display / `0x05` Max 基础版 / `0xFF` 无效 |
| 1 | 代际编码 | `0x00`、`0xFF` invalid；`0x01`–`0xFE` 设备硬件更新换代版本 |

> `0x05` Max 基础版为 V2.1（2026-07-26）新增。

### `0x0102` 磁栅类型 — M→R, ACK, Len 1

| Byte | 取值 |
|---|---|
| 0 | `0x00` 对向反射膜 / `0x01` 外采磁栅 / `0x02` 自研磁栅 |

### `0x0103` 人在传感器参数 — M→R, ACK, Len 20

| Byte | 字段 |
|---|---|
| 0 | 人在传感器门数 |
| 1 | 无人延时时间（s） |
| 2–19 | 每两字节依次表示门 0–门 8 的运动 / 静止灵敏度：Byte2=门0运动，Byte3=门0静止，Byte4=门1运动，Byte5=门1静止…… **未启用的门填 `0xFF`** |

> 算术自洽：9 门 × 2 字节 = 18 = Byte2–Byte19，加前两字节共 20。

### `0x0104` / `0x0105` 霍尔传感器 1 / 2 配置参数 — M→R, ACK, Len 2

Byte0–Byte1 为霍尔传感器 ADC 值。⚠️ **原文未给编码方式与量纲** → [ISSUE-06](#issue-06)

### `0x0106` 设备 SN — M→R, ACK, Len 20

Byte0–Byte19，ASCII 编码。示例 `BJP250711XXXXXXX0125`，无效值 `BJ000000000000000000`（均为 20 字符）。

### `0x0107` 清除使用时长 — R→M, No ACK, Len 1

Byte0：`0xAA` 清除当前使用时长，其他值无效。

产品需求：设备被移除（未激活）后，RK3562 周期查询激活状态，若一直未激活则**每 10s** 发送一次本命令。

### `0x0108` RK3562 版本号 — R→M, ACK, Len 3

Byte0 主版本号 / Byte1 次版本号 / Byte2 补丁版本号。RK3562 版本更新后发送。

### `0x0109` 强制升级 — M→R, ACK, Len 1

Byte0：`0xAA` 进入强制升级，其他值无效。RK3562 收到有效值后进入升级流程。

### `0x010A` LED 与护眼屏控制 — R→M, ACK, Len 3

| Byte | 字段 | 取值 |
|---|---|---|
| 0 | 开关 | `0x00` 关 / `0x01` 开 |
| 1 | 亮度 | `0x01` 低 / `0x02` 中 / `0x03` 高 |
| 2 | 色温 | `0x01` 冷光（绘画）/ `0x02` 常规 / `0x03` 暖光（夜读） |

> V1.2 起，本命令的控制值与 `0x0100` Byte1–Byte3 的状态回读值定义一致。

### `0x010B` 系统重启 — M→R, ACK, Len 1

Byte0 只有 `0xAA` 有效。表示用户长按了控制按键，重启 RK3562 端。

### `0x010C` Ultra 电机控制方式 1（步进调节）— R→M, No ACK, Len 2

Byte0 调节方向：`0x01` 向上 / `0x02` 向下；Byte1 移动距离（分米）。

### `0x010D` Ultra 电机控制方式 2（目标值调节）— R→M, No ACK, Len 1

Byte0 目标像距（分米）。

### `0x010E` Ultra 电机调节结果 — M→R, No ACK, Len 2

Byte0 结果：`0x00` 调节失败 / `0x01` 调节成功；Byte1 当前像距（分米）。

### `0x010F` MCU 主板按键状态 — M→R, No ACK, Len 1

Byte0 位图，**0 = 按下，1 = 释放**：

| bit | 键位 |
|---|---|
| 0 | 上升键 |
| 1 | 下降键 |
| 2 | 亮度键 |
| 3 | 控制键 |
| 4 | 色温键 |
| 5–7 | invalid |

> V1.2 新增（支持 PCBA 测试），V1.3 调整过 bit 与键位的对应关系。

### `0x0110` 查询高度状态 — R→M, No ACK, Len 1 ⚠️

MAX 查磁栅传感器，Ultra 查电机。Byte0 只有 `0xAA` 有效。原文注明 MAX 和 Ultra 都可使用该命令。

> ⚠️ **V2.0 变更记录声称本命令已删除，但它仍在通讯矩阵中** → [ISSUE-01](#issue-01)

| Byte | 字段 | 取值 |
|---|---|---|
| 0 | 设备类型 | `0x02` TYPE_MAX / `0x03` TYPE_ULTRA |
| 1 | 最低点状态 | **MAX**：`0x00` 未脱磁 / `0xFF` 脱磁 / `0xEE` 不支持查询<br>**Ultra**：`0x00` 电机不在最低点 / `0xFF` 电机在最低点 |

## 5. OTA 升级

### 5.1 OTA 命令详解

#### `0x0200` Query Version — R→M, No ACK, Len 0

RK3562 查询 MCU 软件版本号。**指令发出后 100ms 无应答则超时，超时后重发；3 次超时则流程结束，OTA 失败。**

#### `0x0201` Query Version Response — M→R, No ACK, Len 6

| Byte | 字段 | 原文示例 |
|---|---|---|
| 0–2 | MCU APP Version | `01 00 01` → 1.0.1 |
| 3–5 | MCU BOOT Version | `01 00 00` → 原文文字写「0.0.9」⚠️ [ISSUE-05](#issue-05) |

如果请求数据有问题，不用回复。Byte3–Byte5 为 V1.9 起启用（此前为备用字节）。

#### `0x0202` Request OTA — R→M, No ACK, Len 5 ⚠️

RK3562 指示更新 app 应用程序控制固件，MCU 根据指令决定固件刷新地址。

| Byte | 字段 | 取值 |
|---|---|---|
| 0 | 固件类型 | `0x01` 更新 app 固件 |
| 1–5 | MCU 固件大小（Byte） | ⚠️ 与 Len=5 算术不符 |

⚠️ **两个问题，实现前必须澄清：**
- Byte0(1) + Byte1–Byte5(5) = 6 字节，但 Payload Length 写 5 → [ISSUE-03](#issue-03)
- §6 正文和 `0x0203` 的错误码都预设本命令携带 **start address** 字段，但字段定义里没有 → [ISSUE-04](#issue-04)

时序：发出后等 3s；未收到 `0x0203` 则重发，共 3 次未回复则升级失败。

#### `0x0203` Request OTA Response — M→R, No ACK, Len 1

MCU 收到请求下载命令后执行擦除操作并返回结果。

| Byte0 | 含义 |
|---|---|
| `0x01` | success |
| `0x02` | erase error |
| `0x03` | start address error |
| `0x04` | length error |
| `0x05` | pending |
| `0x06` | Cancel OTA（用户取消 OTA 时返回） |
| `0x07` | CRC error |

#### `0x0204` Transmit Data — R→M, No ACK, Len n

| Byte | 字段 |
|---|---|
| 0 | Package serial counter，取值 1–255 |
| 1–n | MCU image data |

- 一包数据多长由 **MCU 自身 Flash Page / Sector 大小**决定（Pro 版本一包 512 字节）
- **指令发出后 100ms 无应答则超时，超时无重试，OTA 直接失败。** 原因：数据传输涉及 FLASH 写入，下位机是否已写入未知，重试会触发异常

#### `0x0205` Transmit Data Response — M→R, No ACK, Len 2

Byte0 = 收到的 package serial counter（回填 `0x0204` 的 Byte0）。

| Byte1 | 含义 |
|---|---|
| `0x01` | success |
| `0x02` | package number error — `0x0204` 的 Byte0 不连续 |
| `0x03` | Flash program error — MCU Flash 编程出错 |
| `0x04` | Cmd Not Support — 处于 OTA 流程中，收到不支持的指令 |
| `0x05` | workflow error — 流程有误，比如没有执行擦除动作 |
| `0x06` | CRC error — 请求帧 CRC 错误 |
| `0x07` | transmit len too long — 传输数据长度已大于 `0x0202` 声明的长度 |

#### `0x0206` Request Verify — R→M, No ACK, Len 4

Byte0–Byte3 = MCU image CRC32。⚠️ 原文标注「待定，CRC32 写在 MCU image 文件里」。等待 `0x0207` 回复超时 2s。

#### `0x0207` Request Verify Response — M→R, No ACK, Len 1

| Byte0 | 含义 |
|---|---|
| `0x01` | success |
| `0x02` | error |
| `0x03` | pending — CRC 计算中 |
| `0x04` | Cmd Not Support — 处于 OTA 流程中，收到不支持的指令 |
| `0x06` | CRC error |

> 原文枚举中无 `0x05`，照录，非转写遗漏。

#### `0x0208` / `0x0209` Request Reset / Response

- `0x0208` R→M, Len 1：Byte0 = `0xF0`，请求复位
- `0x0209` M→R, Len 1：Byte0 = `0x01` goto reset / `0x02` CRC error

#### `0x020A` 升级进度 — R→M, No ACK, Len 2

| Byte | 字段 | 取值 |
|---|---|---|
| 0 | 升级状态 | `0` 升级正常进行 / `1` 升级失败（原文用十进制书写） |
| 1 | 升级进度百分比 | 0–100 |

**判定升级成功的条件：升级进度 > 99% 且 CRC 校验通过。**

### 5.2 升级流程（Step 0–12）

| Step | 执行方 | 动作 |
|---|---|---|
| 0 | RK3562 | 每次开机向后台查询最新版本（MCU、UI 和 RK3562 打包为一个软件包），有新版本则云端分片下载到 RK3562 内部 Flash |
| 1 | RK3562 | 从软件包读取 MCU image 版本，同时用 `0x0200` 请求 MCU 当前运行版本 |
| 2 | RK3562 | 版本号相同 → 无需升级，退出 OTA，MCU 无影响 |
| 3 | RK3562 | 版本号大于 MCU 版本 → 继续 OTA |
| 4 | RK3562 | 发送 `0x0202` 请求升级，等待 3s；确认后 MCU 执行 boot 跳转及擦除 |
| 5 | RK3562 | 等 `0x0203`；3s 未收到则重发 `0x0202`，共 3 次未回复 → 升级失败 |
| 6 | 双方 | RK3562 发 `0x0204` 数据，MCU Boot 写入并回 `0x0205` |
| 7 | RK3562 | 发送剩余数据 |
| 8 | RK3562 | 数据发完，发 `0x0206` 请求校验，等 `0x0207`（超时 2s） |
| 9 | RK3562 | 校验通过后判断是否还有 block；没有 → Step10；有 → 回 Step4 传下一 Block |
| 10 | RK3562 | 发 `0x0208` 复位 MCU |
| 11 | RK3562 | 读取 MCU 版本号，确认升级成功 |
| 12 | 双方 | 进入正常工作 |

> Step4 原文标注「需要用户确认？？？」，结论是**暂不开发**，放到以后的 OTA 版本再加。
> 原文该节配有画板时序图，声明「该图仅为交互示意图，MCU 内部处理可不按图中流程设计，能稳定完成升级即可」。

### 5.3 升级过程基本要求

1. MCU 控制屏幕显示升级进度百分比，数值由 RK3562 通过 `0x020A` 下发
2. MCU 收到复位指令后，屏幕显示复位相关文字，再进入复位流程
3. 升级过程中 MCU 的屏幕、LED、电机控制应做好处理（暂无详细需求）

### 5.4 升级失败处理

- **RK3562 升级失败**：采用 AB 分区升级，失败后仍使用当前版本软件运行
- **MCU 升级失败**：APP valid 标志有效则继续运行 APP，无效则停留在 boot 中
- 升级失败后需向后台上报，通知到手机端或小程序
- 使用网络升级，为避免网络异常应设计升级超时时间
- 升级重试涉及网络数据重新获取，**实现方案未定**

### 6.1 MCU image 文件（16 字节头）

- 格式：**HEX**，不连续的数据段填充 `0xFF`
- 在文件头添加 16 字节数据信息：

| 字段 | 说明 | 对应服务 |
|---|---|---|
| 文件起始地址 | MCU Image 在 MCU 芯片 flash 分区的起始地址 | `0x0202` 的 start address 字段 ⚠️ [ISSUE-04](#issue-04) |
| 文件类型 | `0` RK3562 / `1` MCU / 其他 | |
| 文件长度 | MCU image 文件长度 | `0x0202` 的 length 字段 |
| CRC | CRC32，`0x11223344` 为有效位，**计算范围仅 MCU Image 数据内容** | `0x0206` 的 CRC 字段 |
| Version | 十六进制，9/10/11 为有效位，例如 `0x010001` = 1.0.1 | 与 `0x0200` 获取的版本号比较 |

`0x0204` 服务传输的数据即为 MCU Image file。

⚠️ 原文未给这 16 字节的逐字节偏移表，且上列字段按 4+1+4+4+4 计为 17 字节，与「16 字节」不自洽 → [ISSUE-12](#issue-12)

### 6.2 打包 OTA BIN（128 字节头）

| 偏移 | 字段 | 长度 | 说明 |
|---|---|---|---|
| 0 | BIN 文件头长度 | 1 | 固定 128（`0x80`） |
| 1 | BIN 文件的校验 | 4 | MSB 在前。含从供应商代码到 Block 数据结束的 CRC32。**保留：端设备无法实现，需在云端上传时校验** |
| 5 | 项目代码 | 8 | ASCII，例如 `Fu_P003` = `46 75 5F 50 30 30 33`。**BIN 文件校验计算范围起点** |
| 13 | 项目编号 | 8 | 保留 |
| 21 | 支持的硬件版本 | 10 | 保留 |
| 31 | BIN 文件长度 | 4 | 不含头 128 字节 |
| 35 | Block 数量 | 1 | BIN 内包含多少个升级包（RK3562/MCU/其他） |
| 36 | 第 1 个 Block 类型 | 1 | `0` RK3562 / `1` MCU / `2` …… |
| 37 | 第 1 个 Block 起始地址 | 4 | MSB 在前 |
| 41 | 第 1 个 Block 长度 | 4 | MSB 在前 |
| 45 | 第 1 个 Block CRC | 4 | MSB 在前 |
| 49 | 第 1 个 Block Ver | 4 | |
| 53 | 第 2 个 Block 类型 | 1 | 同上 |
| 54 | 第 2 个 Block 起始地址 | 4 | MSB 在前 |
| 58 | 第 2 个 Block 长度 | 4 | MSB 在前 |
| 62 | 第 2 个 Block CRC | 4 | MSB 在前 |
| 66 | 第 2 个 Block Ver | 4 | |
| 70 | 第 3 个 Block 类型 | 1 | 同上 |
| 71 | 第 3 个 Block 起始地址 | 4 | MSB 在前 |
| 75 | 第 3 个 Block 长度 | 4 | MSB 在前 |
| 79 | 第 3 个 Block CRC | 4 | MSB 在前 |
| 83 | 第 3 个 Block Ver | 4 | |
| 87 | 资源打包时间戳 | 4 | UNIX 时间戳 |
| 91 | Header Reserved | 33 | 填 `0xFF` |
| 124 | Header CRC | 4 | bin header byte 0–123 的 CRC32 |

数据区：

| 偏移 | 内容 |
|---|---|
| 128 | Block1 data |
| 128 + block1_length | Block2 data |
| 128 + block1_length + block2_length | Block3 data |

> 偏移自洽性：124 + 4 = 128，头部字段连续无空洞，与「头长 128」一致（cc 复算）。

**打包限制：**

1. 支持只有单独文件升级（只有 RK3562 文件，或只有 MCU 文件及其他文件）
2. 存在多个文件时，按 **RK3562 → MCU → 其他** 的顺序生成 OTA 包并填充 Block 数据
3. **不能将 RK3562 文件插入到 MCU 和其他文件之间**制作 OTA 包

### 6.3 CRC32

| 项 | 值 |

| 多项式 | `0xEDB88320`（反射式） |

### ISSUE-01

🔴 **`0x0110` / `0x0111` 存废矛盾**

- 变更记录 **V2.0（2026-07-09）**：「去掉原磁栅状态查询 0x110 和状态反馈 0x111 报文，将磁栅状态反馈增加到状态反馈 0x100 报文里」
- 但通讯矩阵中**两条命令仍然存在**，且内容比 V2.0 之前更完整（新增 Ultra 电机语义、`0xEE` 不支持查询），描述明确写「MAX 和 Ultra 都可以使用该命令」
- `0x0100` Byte13 与 `0x0111` Byte1 的枚举定义**完全相同**，功能重复

**风险**：照矩阵实现 → 可能实现了已废弃命令；照变更记录删除 → 可能删掉 Ultra 需要的主动查询能力。
**待确认**：`0x0110`/`0x0111` 在 MAX/Ultra 上是保留还是废弃。

### ISSUE-02

🔴 **配置参数由 `0x0000` 还是 `0x0001` 触发**

- `0x0000`「查询外设状态」描述：会收到 `0x0100` 的回复
- `0x0001`「查询配置参数」描述：会收到 `0x0101` 到 `0x0106` 的回复
- **但** `0x0101`/`0x0102`/`0x0103`/`0x0104`/`0x0105` 各自的描述都写：「RK3562 在发送查询命令（**`0x0000`**）时，回复 0x010X」
- `0x0106` 只写「发送查询命令时」未给 CMD；`0x0112` 写「发送**配置**查询命令 `0x0001` 时」

**倾向性读法**（仅供参考，非实现依据）：按命令语义，配置类回复应由 `0x0001` 触发，各条目里的 `0x0000` 疑似沿用旧版本的笔误。
**待确认**：`0x0000` 与 `0x0001` 各自触发哪些回复报文。

### ISSUE-03

🔴 **`0x0202` Payload Length 与字节定义算术不符**

Payload Length 列写 **5**，但字段定义为 Byte0（固件类型 1 字节）+ Byte1–Byte5（固件大小 5 字节）= **6 字节**。

两种可能读法：
1. 字段名笔误，应为 Byte1–Byte4（固件大小 4 字节），总长 5 —— 与其余 4 字节长度字段（Block 长度等）宽度一致
2. Payload Length 笔误，应为 6

**待确认**：`0x0202` 的实际 payload 长度与固件大小字段宽度。

### ISSUE-04

🔴 **`0x0202` 缺少 start address 字段定义**

- §6 正文写明「文件起始地址…（`0x202` 服务的 start address 字段）」
- `0x0203` 的错误码含 `0x03 start address error`
- 二者都预设 `0x0202` 携带 start address，**但矩阵里 `0x0202` 只定义了固件类型和固件大小**

**待确认**：`0x0202` 的完整字段构成（很可能与 ISSUE-03 是同一处缺失）。

### ISSUE-05

### ISSUE-13

🟢 **`0x0204` 变长包与 1024 上限的关系**

`0x0204` 的 Payload Length 为 `n`，一包长度由 MCU Flash Page/Sector 决定（Pro 版本 512 字节），而帧定义 Payload 上限「暂定 1024」。两者约束关系与 MAX/Ultra 的实际包长未明确。
