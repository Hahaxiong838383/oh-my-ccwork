## 2. v0.3 合同（按你 §3「需要回交的具体字段/规则」七条）

### 2.1 固定 input_mode 的可信来源与传递点

- 来源：**P003 服务端 `device-session` 签 token 时**写进 `roomConfig.agents[0].metadata`（与 trace_id/session_id/issue_ts_ms 同一 JSON），字段 `input_mode: "ordered_pcm"`；服务端按 env `DEVICE_SESSION_INPUT_MODE_ORDERED_PCM_SNS`（SN 列表，默认空）决定是否写入。**本轮服务端未改**（写入点已定位：`apps/server/src/routes/device-session.ts:193` 的 metadata 对象）。
- 传递点：LiveKit 派单透传 → worker `job.rs` 解析 `JobMeta.input_mode`（`Option<String>`，缺省/未知=`Rtc`）→ 在建通道处一次判定，传入 `run_pipeline(.., hist_rx, input_mode, ..)`；**pipeline 第一帧前固定，房中途不可改**。
- 关闭或协商失败：metadata 无该字段 → 现役路径，且 `p003.audio.history.v1` topic 的包在 job 层直接丢弃（debug 日志）。设备侧「历史功能关闭/能力协商失败」应**在启动实验采音前**回退：判据=设备收到的 Session API 响应里没有 ordered 标记（服务端签 token 时同步返回给设备，与 metadata 同源）。
- 已捕获但不能完整提交 → `result{failed, action=repeat_prompt}`，设备提示重说；**不把半句塞回现役输入**（ordered job 里根本没有现役输入）。

### 2.2 线格式与定界（begin/chunk/end/cancel；ack/result 同格式反向）

| 项 | 规则 |
|---|---|
| 帧 | `"OPCM"` (4B) ‖ `version` u16 BE = 1 ‖ `header_len` u16 BE ‖ header JSON (UTF-8, ≤ 2048 B) ‖ PCM s16le |
| chunk | PCM 字节数 **必须** = `(end − start) × 2`；≤ 7168 样本（14 KiB 载荷；15 KiB 只是 LiveKit 单包的保守应用预算，不当底层保证） |
| 非 chunk | 不得带 PCM（带了整包拒） |
| 校验失败 | `TooShort / BadMagic / BadVersion / HeaderTooLong / BadHeaderJson / OddPayload / PayloadLenMismatch / PayloadOnNonChunk / ChunkTooLarge` → 丢包 + WARN（不建代次） |
| header 字段 | `t, input_id, trace_id, session_id, capture_epoch(u64), wake_generation(u64), seq(u64), start(u64), end(u64), keep_from(u64?), boundary_kind, overlaps_local_playback, sr=16000, ch=1, fmt="s16le", sent_at_ms` |
| 发包者 | 只收身份 == 房名推导的 `dev-<SN>`（`sn-<SN>-<秒>` → `dev-<SN>`；非 sn- 房永不启用）；begin 可早于用户轨订阅到达 |

### 2.3 区间与代次

- 一律半开区间 `[start, end)`，u64；`end` 消息的 `end` 字段 = 最后一个样本索引 + 1 = 必须等于 `received_next`，否则 `missing_seq`。
- chunk 接收规则：`start == received_next && seq == chunks_received` → 收；`end ≤ received_next && seq < chunks_received` → 完全重复，幂等重 ack；其它重叠 → `duplicate_conflict` 终态；`start > received_next` → `missing_seq` 终态。
- 代次：`input_id` 唯一；`(trace_id, input_id)` 是消息归属键；同 job 首个合法 begin 之后，任何不同 input_id 的消息只拒不改状态。

### 2.4 双水位、有界组包、信用

- `ack{received_next, submitted_next, credit_samples, chunks_received, phase}`：每收一片 ack 一次（提交之后发，带最新 `submitted_next`）。
- 组包：设备 40 ms/640 样本 peek 直接发（片长任意 ≤ 7168），worker 侧组包器攒到 3200 样本（200 ms，= 现役 STT 块）写 ASR 队列；末尾不足一块按实际样本数写（`tail_block_samples` 进证据）。**现役 input_ready 不表示历史上传完成**，历史完成只看 `result`。
- 信用：`credit_samples = 128000 − 已收未提交`；worker 提交是即时的，正常情况下 credit 常满；ASR 未连上时块进 128 块队列（25.6 s）而不是留在组包器。

### 2.5 预算与内存

| 项 | 值 |
|---|---|
| 历史积压上限（已收未提交） | 8 s = 128 000 样本 |
| 单代总量（keep_from 起） | 12 s = 192 000 样本 |
| begin→end 超时 | 7 000 ms |
| 尾静音 | 600 ms = 9 600 样本（3 块） |
| worker 入站队列 | 256 包（6 s 按 640 样本分片 = 150 包也放得下）；满则丢包 → 该代因缺片终态 |
| 内存（最坏，单代） | PCM 12 s × 2 B = 384 KB + 入站队列 256 × ≤14 KiB ≈ 3.5 MB + JSON/对象开销 <100 KB；ASR 队列 128 × 6.4 KB = 819 KB（既有） |
| 错误 | `over_cap / timeout / queue_full` 各自终态，证据带计数 |

### 2.6 末尾与 end 语义、单句 job 的收流

- 末尾不足 200 ms：**按实际样本写**（不丢、不补真实语音），随后 600 ms 零样本尾静音，然后 **drop 唯一 ASR 发送端**（现役收流原语：sender 全 drop → 发一次空 NegativeSeq → 等 LastNoSeq）。**没有改成每块/每次 VAD 结束 ASR**；只是实验单句 job 的「输入结束」发生在 `end` 之后而不是 job 关闭时。
- 正式多轮 job 完全不走这条（`stt_pcm_tx` 在现役路径永远是 `Some`，job 关闭时才 drop）。
- 实验 job 首句裁决后不再有输入；回复播完由设备按现有策略断房。

### 2.7 唯一不可逆终态与旧输出过滤

- 终态 = `Terminal{Committed | Failed(reason)}`，只进不出；`result` 只发一次。
- 失败后：hold 的 final 清空；到达的 final 只计 `finals_after_terminal`；包只计 `packets_after_terminal`；`drain_submits` 返回空（零 PCM 再进 ASR）；投机生成在 ordered 模式下从未启动（interim 不进 `pf`）；设备命令/LLM/filler 只在 commit 之后才可能发生，而失败代次永不 commit。
- 显式取消（control cancel 或 `history.cancel`）立即终态并请求收流；旧结果按 input_id + 终态过滤，不是「跳过一条」。

## 4. 队列满与短尾丢失：复现结论与现役路径建议

- 现役事实（代码级，未改）：`pipeline.rs:871 let _ = stt_pcm_tx.try_send(..)` 满则**静默丢一块**（无 WARN 无计数）；`pipeline.rs:951 drop(stt_pcm_tx)` 前 `stt_buf` 里不足 3200 样本的残余不发（job 结束时）。
