# 小可「方舟世界玩法」知识接入方案（静态知识刷新 + 动态状态注入）

> 需求（川哥 2026-09-02）：小可所在世界的游戏体验与各种玩法，要成为 worker 可调取的信息，孩子问起来小可要知道。
> 方法：基于当前 worker 与后台机制盘点（全部读源码，证据标 file:line），不新造系统。证据等级：【已验证】读源码/grep；【推断】；【待 codex 确认】。

## 〇、结论

1. **「小可知道玩法」的机制已经在产**：`xiaoke-kb.ts` 是世界观知识库——13 条目、关键词子串召回 <1ms、单次最多 3 条、附真实性红线，孩子聊到才注入（【已验证】xiaoke-kb.ts:1-30 注释 + 13 个 `key:`）。worker 零改动：注入发生在 server brain 组 prompt 时，worker 调 brain 自动带。
2. **真正的缺口是两个，都不是机制**：
   - **内容过期**：知识库与世界观 base 的数据源是 6-11 的手册 v0.3；G1 奖励线（金币→宝箱→终极大奖三段式）8-28 上线、v179 起全量，**「金币」在手册/知识库/世界观 base 命中均为 0，只在 G1 音频 slot 定义里出现 4 次**（【已验证】`grep -c 金币`：docs/12 手册 0 / xiaoke-kb.ts 0 / prompts.ts 0 / local-audio-generator.ts 4）。孩子说「我刚领了金币」，小可不知道金币是什么。
   - **动态状态盲区**：知识库自己写明「你暂时不知道 ta 的实时数量和宝箱品级，绝不编造具体数字」（【已验证】economy 条目末句）。遥测通道只有 6 类专注/姿态事件，快照 schema 全是设备物理状态（灯/距离/音量/presence/focus），**无任何游戏字段**（【已验证】telemetry.ts `EVENT_TYPES` 六项 + `SnapshotSchema` 15 字段）；G1 六事件在端侧只用于触发本地音频，server 侧 gift/reward 零消费（【已验证】grep rtc/profile/extractor/admin 零命中）。
3. **方案 = 三层，前两层复用在产机制**：L1 刷新静态知识（对齐在产玩法真值）；L2 游戏状态走遥测快照上报 + 命中游戏话题时附实时数（新增字段，不新增通道）；L3 游戏事件进情景记忆（P2）。**不上 RAG/向量**：条目量小，且延迟铁律「ASR final→首 token 禁同步检索」（xiaoke-kb.ts 注释原文）——关键词召回 <1ms 是正解，向量线（companion-kg 400ms 超时降级）已是延迟妥协不再扩。

## 二、缺口实证

| 缺口 | 实证 | 后果 |
|---|---|---|
| G1 三段式缺失 | 「金币」四处 grep：手册 0 / KB 0 / worldview 0 / G1 slot 4；G1 slot scene 原文：「专注完成一段→金币奖励等着领」「攒满进度→宝箱可以开」「完成今天全部学习目标→终极大奖」 | 孩子问「金币能干嘛」「攒多少开宝箱」「终极大奖是什么」——零命中，小可按世界观泛聊或说查不到 |
| 手册时效 | v0.3 停在 6-11；游戏 v99→v184 三个月迭代 | 其它章节（宝箱升级规则/生态缸建筑/藏品清单/光环天数）是否仍与在产一致【待 codex 确认】 |
| 实时数字盲区 | 知识库明文不知道数量；快照无游戏字段 | 「我有几个宝箱」「光环还剩几天」只能答「查不到」——手册 §十 红线要求「还剩 X 天走系统实时」，但系统没有实时 |
| 事件无留痕 | G1 领取/开箱事件不上报 | 「昨天开的宝箱」类回忆无素材；家长端也看不到孩子的游戏成就 |

## 三、方案三层

### L1 · 静态玩法知识刷新（机制不动，内容对齐在产版本）——P0

1. **codex 出「玩法真值清单」**（按 v184 在产）：G1 三段的触发条件与数值口径（一段专注=多久？进度攒满=几段？终极大奖是什么？金币与星尘/家族币的关系）、宝箱品级与开箱规则、生态缸等级与六建筑现状、藏品清单、光环天数、夜航规则、v133-v184 新增/下线的玩法。
2. **知识库更新**：新增 `g1_reward` 条目（关键词：金币/领金币/攒金币/进度条/攒满/宝箱开了/终极大奖/大奖/今天全部完成/学习目标…；内容按真值写，带「数值未公开只讲机制」处理）；economy 条目补金币定位；halo/ecopond/collection/nightsail 逐条核对；`future` 条目把已上线的从「将来会有」移出。
3. **世界观 base 补一句** G1 概念（常驻 1849 字加 ≤60 字），保证零命中时也知道金币存在。
4. **测试**：xiaoke-kb.test.ts 加正锚（「我领了金币」→g1_reward；「终极大奖」→g1_reward）+ 负锚（「金鱼」不命中）。
5. **发版纪律**：每次 Godot 玩法变更，OTA 发布文档附「小可需知」变更段（发版清单加一项），知识库随之更新——否则三个月后再次过期。

### L2 · 动态游戏状态注入（复用遥测通道，字段级新增）——P1

1. **端→server**：`SnapshotSchema` 加 `game` 子对象（`nullish`，老端不发=无）：候选字段 `coins / chests_unopened / stardust / family_coins / ecopond_level / collection_count / halo_days_left / g1_stage('none'|'coin'|'chest'|'final') / g1_today_done / last_chest_grade`——**以 Godot 实际持有的状态为准，字段清单由 codex 定**；`EVENT_TYPES` 加 g1 六事件 + `chest_opened{grade,items}`（端侧事件源已存在，加一路上报）。
2. **server 存**：随 snapshot 落最新快照（表已 append+查最新，零结构改动）；事件进 event 表。
3. **注入**：**只在知识库命中游戏类条目时**（economy/collection/halo/ecopond/nightsail/g1_reward）追加一行「【方舟实时状态·数据】金币 X · 未开宝箱 Y · 生态缸 Lv Z · 光环剩 N 天（截至 HH:MM）」+ policy 一句「数字以此为准，没列出的不编造」；无快照或快照 >24h → 不注入，回落现有「查不到」话术。读最新快照是 SQLite 单行查 <1ms，符合延迟铁律。时效 = 设备 30s 上传节奏。
4. **admin**：设备页展示最新 game 快照（白盒，同遥测风格）。

### L3 · 游戏事件进情景记忆——P2

`chest_opened` / `g1.reward.final_claimed` → 情景记忆 event 类条目（「9-2 开出史诗宝箱得机械恐龙」），复用 memory-item typed 机制（promise/event/preference 已有）→ 重逢与回忆杀素材；家长端周报可见游戏成就。

## 四、不做什么（及理由）

| 不做 | 理由 |
|---|---|
| 向量 RAG 检索玩法（**P0 不上，P1 按数据定**） | 条目量 13→~20；铁律「ASR final→首 token 禁同步检索」。⚠️ 但已有实证教训（memory `kid_speech_semantic_over_substring`，7-13 陪伴域 376 主题）：**子串触发词对儿童口语召回天花板 28%**——孩子说现象不说概念名。玩法词分两类：专有名词（金币/宝箱/光环/生态缸）孩子会直说，子串可靠；现象描述（「那个亮亮的圈」「转的东西」）子串必漏。**P0 先关键词 + 加漏召回观测**（游戏话题轮但 KB 零命中的比例，判据见 §五 K7）；若漏召回显著，复用 companion-kg 已有的 bge 向量线给 13-20 条建向量（成本极低，且它自带 400ms 超时降级），子串降为重排信号 |
| 知识库改 admin 可编辑 | 运营输入进 prompt=注入面；现有代码常量有 12 项测试守护。P1 可迁 JSON 数据文件 + admin 只读预览，编辑仍走仓 |
| worker 侧调取 | 注入在 brain（server），worker 零改动；若走能力方案 L2 tool loop 反而多一跳 |
| 让 LLM 自己「记」玩法 | 真实性红线：只讲已锁定机制、查不到就说查不到；玩法必须来自真值清单不是模型联想 |

## 五、落地顺序

| 步 | 内容 | 依赖 | 量级 |
|---|---|---|---|
| P0 | codex 玩法真值清单 → 知识库刷新 + g1_reward 条目 + base 一句 + 测试 + 发版纪律 | codex 清单 | server 侧一天 |
| P1 | game 快照字段 + g1/开箱事件上报（双端）+ 命中时实时状态行 + admin 展示 | codex 字段清单 + Android 上报 | 双端两三天，遥测线成熟 |
| P2 | 游戏事件进情景记忆 + 家长端成就 | P1 事件 | 一天 |

**漏召回观测（P0 起）**：日志锚 `[xiaoke-kb] miss-suspect`——LLM 回复文本含游戏专有名词（金币/宝箱/光环/生态缸/藏品/星尘）而本轮 KB 零命中 → 计一次疑似漏召回；每周看比例，>20% 即启动向量补召回。

## 六、给 codex 的四项需求（可转联调文档）

1. 在产（v184）玩法真值清单（§三 L1-1 列的项）；
2. Godot 侧可上报的游戏状态字段清单（§三 L2-1 候选供参考）；
3. G1 六事件 + 开箱事件走遥测 batch 上报（沿现有 event schema：`type/occurred_at_ms/data`）；
4. 发版流程加「小可需知」变更段。
