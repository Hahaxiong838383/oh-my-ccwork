> 一句话：**设备声明的能力没问题（全机队都报合同 2），问题是声明包到得晚。** One-shot 首句会话里，能力声明随 `wake` 包在开房后约 1.5–2.5 秒才到，而首句已经在 1.2–1.5 秒提交、大模型 2 秒左右就回了暗号；暗号先到就被 worker 按「未声明能力」压掉。7 天内一半的 One-shot 房声明晚于首句提交，今天 …02000004 的 4 句设备命令 2 句执行 2 句被压，就是这个赛跑。

## 1. 现象（后台卡「模型漏 2」的真相）

后台「语音控设备 24h」卡今天显示「语法命中 4（模型同意 2 / 模型漏 2）」。日志里那两条「模型漏」其实是大模型**认了**（`llm device intent observed … known=true`），但在它之前已被压掉：

```
llm device intent suppressed room=sn-…02000004-1790134809 label=38 reason="android_capability_missing"
llm device intent suppressed room=sn-…02000004-1790134824 label=6  reason="android_capability_missing"
```

我 16:47 的口头汇报把它说成「那台设备没声明音量/亮度能力」，**说错了**：worker 的能力判定不是按标签的，只看合同版本号；这台设备每个房都声明了合同 2。真相在 §3。

## 2. 合同原文与 worker 现行判法

- 合同 v3 §3.1「能力声明（Android → Worker，随 `wake`）」：`{"type":"wake","payload":{"device_command_contract_version":3,"chip_first":true}}`；`=3` 支持全部字段，`=2` 按 2b 行为，缺失或 `<2` 只观察不发慢路（`2026-09-04-语音设备控制双源单核联调合同v3(给codex).md`）。
- v3.1 增量 §0（2026-09-05 与 codex 定）：「能力声明维持合同 2，v3 字段全部可选、未声明 3 前不发新参数」。所以现在机队统一报 2 是**约定状态，不是缺陷**。
- worker（`rust-worker/src/control.rs` 93–95 行）：只有 `type=wake` 的包会被解析成能力声明；`pipeline.rs` 2364–2369 行收到后才把房级 `l2_capable` 置为 `contract_version >= 2`，房一开始是 `false`（`pipeline.rs` 932 行）。
- 慢路门序（`device_intent.rs` `l2_gate`）：`execute_off → no_device_text → android_capability_missing → unknown_label → fast_path_hit → no_trace`。大模型暗号到达时 `l2_capable` 仍是 `false` → 压掉，原因记 `android_capability_missing`。**worker 不会等声明包，也不会事后补执行**（宁漏勿误是对的，但漏在这里是时序造成的）。

## 4. 影响面

- 只影响「唤醒后第一句就是设备命令、且走 One-shot 首句通道」的场景，且要赶上大模型比声明包快。普通多轮对话（RTC）不受影响：声明在孩子开口前 0.6 秒就到了。
- 结果是**漏触发**（灯不动、小可的回话照常），不是误触发。用户再说一遍第二句就走正常路径。
- 词表快路（L1）不受影响：它不看 `l2_capable`。芯片本地命令词也不受影响。

## 5. 修法与分工（三层，可并行；建议顺序 C → A → D）

**A. 端侧（根治，需要 APK）**：让能力声明先于首句到达 worker。两种做法任选其一：
1. One-shot 首句会话里，在发 `begin`（local_receipt / ordered PCM 起始）**之前**先发 `wake` 能力声明包，保证控制通道上 `wake` 排在音频首包前；
2. 或把 `device_command_contract_version` 放进会话申请（`supports=` 那一族声明），由服务端签进受信 metadata，worker 开房即知，不再依赖 `wake` 包时序。做法 2 更稳，但要服务端配合（见 D）。
   验收：One-shot 房里 `l2 capability` 的时间戳 100% 早于第一条 `turn committed`；7 天 `android_capability_missing` 为 0。

**B. 端侧顺带确认**：声明版本要不要升到 3（D0 交接 E.12「contract_version=3 激活 v3.1 芯片语义」）。**升 3 不解决本时序问题**，两件事分开排。

**C. worker 侧缓解（cc，不依赖端侧，等川哥拍板即做，预计半天）**：One-shot 房里大模型暗号到达而 `l2_capable` 仍为 false 时，把暗号**挂起最多 1.5 秒**等声明包（p90 到达 2.5 s，首句提交约 1.3 s，1.5 s 覆盖 p90）；声明到且 ≥2 → 按原门序继续；超时 → 仍压掉，原因记 `android_capability_missing_after_wait`。不会在声明未确认时执行，只是把「立刻压」改成「等一会再判」；普通 RTC 房不受影响（声明已到，零等待）。后台卡同步把这一类从「模型漏」拆成「声明未到（时序）」。

**D. 服务端（cc，配合 A-2）**：会话申请增加合同版本字段并签进 ordered metadata，worker 侧读 metadata 初始化 `l2_capable`。这是长期正解，等端侧选定 A-1 还是 A-2 再做。
