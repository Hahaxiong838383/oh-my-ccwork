## 2. A 段：begin 后为什么还等 1.2 s

- worker 侧只花 344 ms（等用户轨起管线）+ 88 ms（首轮处理），ACK 与 input_ready 在 +351/+434 就发出。**端侧收到它们的时刻（+1625/+1629、+1423）比 `agent_track_subscribed_by_android`（+1575、+1376）只晚 47～54 ms**，三房如此。上行相反很快（begin 接受在管线起后 66～98 ms，即包早就到了或几乎同时到）。
- 所以那 1.2 s 是**端侧订阅 agent 音轨的握手**（agent 轨 +190 发布 → 端侧订阅完成 +1376～1575，即 1.2～1.4 s）；在此之前 SFU 给端侧的数据包也送不到。推断根因在端侧订阅侧 PeerConnection 的 ICE/DTLS（是否走 relay/TCP、是否首次协商），worker 看不见，请你从端侧拿 `connect→ICE connected→DTLS→首个远端数据包` 的时间线；这条是排查，不是本轮改法。
- **改法（端侧，两条，都不需要 worker 改）**：
  1. **历史 PCM 不等 ACK**：begin 之后直接跟历史 PCM（live 部分仍按 credit）。worker 从 job 起就把该身份在 history topic 上的包按序进 256 包队列（≈10 s 的 40 ms 片），管线起（+340）即排空；单代积压上限 8 s、总量 12 s；缺片才失败，失败有 result。收益：首块入 ASR 从 +1650 提前到 ≈+400，final 提前 ≈1.2 s，投机领先从 31 ms 变 ≈1 s——这一步同时修 B 段。
  2. **本地承接不等 ACK**：批次 3 房文件顶层 `worker_capabilities` + 签发 metadata `local_receipt:"v1"` 已经是受信声明，候选成立即冻结即播；ACK 只做事后对账（回 `ignored` 记一条 `local_receipt_contract_mismatch`，这只会在我把 POC env 关掉时发生，我保证批次 3 期间不关）。…9361 的本地候选是在 ACK 到后 93 ms 才成立（你 §3.1「候选/freeze→播放 19 ms」+ 候选要等 accepted），第一声 2.39 s 里 1.2 s 是这个门。
  3. 顺带：冻结不管来自本地候选还是 worker 候选，都播本地承接再 `receipt_done played_ms>0`（…9362 是 worker 候选收尾走了 played_ms=0，worker 只好回垫句，多绕一圈下行 ≈ 90 ms + 垫句本身 1160）。
