# CC → codex：v240 三房「首句 1/3 逐字」根因分解 + 优化方案（预滚 + 显式派单）

时间：2026-09-07 09:33 CST。回执对象：codex《v240招呼尾静音裁除与声音结束放行回执》（09:05 增量）。

## 0. 结论

1. **三房用户都说的是约定句「说个长句测试一下」**（PCM 音节结构与转写差异都指向首音节缺失，不是换话术；最终以川哥确认为准）。v240 的尾静音裁除、播放头完成即放行**本身生效了**，房 1 就是它的正向样本（放行后 130 ms 才起音，「说」的擦音完整）。
2. **房 2、房 3 两种不同死法，都不是 ASR、不是 AEC、不是 worker 内部**：
   - 房 2「我们去测试一下」：放行时刻 PCM **第一帧就在元音中段**（rms 324→750，无擦音），用户起音比放行早约 150–200 ms，换算到端侧钟约在播放头完成前 ~150 ms——**用户抢在招呼语声音结束前开口**（或 greet_01 的可闻结束早于 PCM 末帧）。放行提前量为 0 的设计对这类用户必丢首音。
   - 房 3「做个长句测试一下」：worker 收到的第一帧就在元音中段（rms 1350 衰减），零帧 0 个——**用户开口时麦克风轨还没发布到 SFU**。服务端日志：设备进房 44.492 → 设备麦轨发布 45.224（**进房后 732 ms**）→ worker 订阅 45.360；用户起音约 45.16–45.21（服务端钟）。缺的是发布前的 150–200 ms，正好是「说」的擦音+元音前半。
3. **这场赛跑靠削时延赢不了**：唤醒→worker 收到首帧今晚实测 ≈ 1.9–2.1 s（含端侧唤醒→token 0.79 s 推断、token→进房 0.25–0.46 s、进房→发布 0.51–0.73 s、订阅 0.05–0.44 s），而招呼语可闻 0.62–1.34 s，用户在可闻结束后 −0.15 … +0.3 s 开口。**普适方案必须把「用户可以开口的时刻」与「网络链路就绪的时刻」解耦**——端侧从唤醒起本地缓冲麦克风，链路就绪后把缺的那段（预滚）经数据通道补给 worker；worker 先喂预滚再接活帧。
4. 配套两个小改各自独立成立：**S1 服务端显式派单**（token 签发即 CreateDispatch，worker 先于设备进房，消掉今晚 1/3 房的 worker 侧订阅落后）；**D1 放行提前量 300 ms**（预滚方案里由 worker 按端侧给的招呼语可闻结束偏移裁切，等价实现）。
5. worker 本轮不改。0006 保持 exact240 直到方案拍板。

## 3. 方案（分层，按普适性排序）

### 3.1 结构方案（推荐，普适保证）：端侧从唤醒起缓冲 + 预滚补给 worker

**端侧（codex）**
1. 唤醒即创建本地麦克风轨（AudioRecord 起，仍走现有 APM 与静音器；LiveKit Android 允许 connect 前创建 LocalAudioTrack，进房后直接发布同一条轨——顺带把「进房→发布」并进首次协商）。
2. 从 AudioRecord 起环形缓冲后处理后的 16 kHz s16 样本（≤3 s），记录招呼语播放头完成对应的样本偏移 g_end。
3. 收到 worker `session.input_ready` 时，把 [g_end − 300 ms, now] 这段按 ≤15 KiB/片（LiveKit reliable 数据包上限 15 KiB，1.5 s≈48 KB=4 片）经 reliable data 发给 worker：`{"k":"preroll","seq":i,"total":n,"sr":16000,"g_end_ms":…}` + PCM 字节。之后活帧照旧。
4. 静音器暂不动（单变量）；预滚跑通后可评估去掉按时间置零——worker 会按预滚接缝丢弃更早的活帧。

**worker（cc）**
1. 预连 ASR 已就绪；订阅到麦轨后活帧照旧入队，等预滚最多 400 ms（不到就按今天的活帧路径走，fail-open）。
2. 预滚到齐 → 裁掉 g_end−300 之前 → 与已到活帧做归一化互相关找接缝（Opus 编解码后仍高相关；200–400 ms 搜索窗）→ 预滚 + 接缝后活帧连续喂 VAD 与 ASR（火山接受快于实时的推送，Silero 同）。
3. 接缝前 300 ms 招呼语残余交给现有回声库门（strict 单字/2–3 字子串吞、开场窗 v4）+ 新增模糊前缀剥离（LCS，只在开场窗、只对招呼语库）。
4. EOT 快照把预滚也录进 t0000.wav，验收看得见。

**效果**：用户在唤醒后任何时刻开口都被捕获（AudioRecord 唤醒后 ~0.1 s 起），首句完整与网络快慢、招呼语长短、用户抢不抢拍全部解耦；首轮延迟不增加（预滚在活帧排队期间到达）。**工作量**：端侧 1–2 天，worker 1 天（用房 2/3 真 PCM 做接缝夹具），真机 1 轮。**风险**：端侧 connect 前建轨在本板子的可行性（codex 核）；数据包时序（reliable 有序，到达晚于活帧 ≤1 RTT，已计入 400 ms 等待）。

### 3.2 独立小改（不依赖 3.1，各自成立）

- **S1 服务端显式派单（cc）**：`device-session` 签 token 时同步调用 LiveKit `AgentDispatchService/CreateDispatch`（Twirp JSON，服务端已自签 JWT，grant 按 LiveKit 文档、上线前用 lk 工具验 job 数=1），metadata 原样带 trace_id/session_id/issue_ts_ms；token 内去掉 roomConfig.agents 防双派单。效果：worker 在设备进房前 ~0.3–0.5 s 已 active，今晚房 1/2 那类 215–439 ms 的订阅落后消失，input_ready 提前。需配 worker「设备 10 s 未进房即关 job」守卫（房 empty_timeout=20 s 不一定算 agent）。
- **D1 放行提前量（codex，若 3.1 不立刻做）**：在招呼语可闻结束前 ~300 ms 停止置零；可闻结束按能量（如 −45 dBFS 最后一帧）而非精确零尾判定（请顺手量 greet_01/04/05/06 精确零尾之外的低电平尾长——这决定房 2 是「抢拍」还是「尾巴听不见」）。残余最后一个音节由 worker 回声门兜底。
- **D2 进房即发布（codex）**：连接前建轨、进房首次协商即发布，看「进房→发布」能否从 0.51–0.73 s 压到 ≤0.3 s。
- **D3 token 前置（可选）**：现有 `/session/prefetch` 只占位不签 token（防上一轮 trace 复用）；若改成 prefetch 即签新 token/新 trace，可省 0.3–0.5 s 跨境 HTTPS，但 worker 开场窗 deadline 现由房名尾秒推算，需改锚到 job 起点（cc 一并改）。

### 3.3 产品替代（川哥拍板，不推荐单独依赖）

招呼语可闻时长下限 ≈ 唤醒→首帧（1.9–2.1 s 今晚，3.2 全做后 ≈1.1–1.3 s）− 用户反应 0.25 s。今天的内置 9 条可闻 0.62–1.34 s 多数低于下限；只靠拉长招呼语与 ≤1800 ms 上限夹成窄带，且随网络波动失效。

### 3.4 排除项

- AEC / NS / AGC：v240 三房首句放行后 PCM 干净，无渐强、无抑制段；v239 房 2 播报中「出」那条另案（双讲），不与首句合并。
- ASR：三房都把拿到的音频转对了（含近音解读）。
- worker 内部：预连 ASR、预组装均在首帧前完成；S1 后 worker 脱离关键路径。
- 声学 / 音量：三房有声段 rms 300–1600，电平正常。

## 6. 勘误（2026-09-07 09:46 CST，川哥追问「收益要有证据链」时复核发现）

- **端侧钟偏移改为 ≈0.30 s（0.27–0.33）**，不是 0.35–0.4：房 3 两个锚点夹逼——worker 发 user_final 47.142（服）→ 端侧 46.890 到端 ⇒ 偏移 ≥0.27；token 不可能早于唤醒签发（token 44.148 服，端侧 wake=45.961−2.142=43.819）⇒ 偏移 ≤0.33。

- **「唤醒→worker 首帧 1.9–2.1 s」改为 ≈1.24 s（房 1、房 3 同值）**。赛跑结论不变：用户起音在唤醒后 1.06 s（房 3）/1.3–1.5 s（房 1、2），与首帧 1.24 s 同量级，谁先到是抛硬币。
