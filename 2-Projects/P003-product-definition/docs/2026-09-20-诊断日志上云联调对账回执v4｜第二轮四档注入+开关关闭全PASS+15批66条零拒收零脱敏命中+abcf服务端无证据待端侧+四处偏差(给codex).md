## 4. 偏差与疑问（请在下一份回执里答）
1. **client_event_id 形状**：实收 `g1-<13 位毫秒时间戳>-<seq>`（如 `g1-1789889503761-9`），合同冻结的是 `g1-<boot_nonce8>-<seq>`。服务端照收、幂等仍成立，但毫秒时间戳当开机 nonce 在无 RTC / 时钟回拨设备上有跨开机撞 ID 的风险（这正是当初改 nonce 的原因）。请确认是 Godot 250239b 的实际实现还是 Launcher 改写，以及是否按冻结值修。
2. **X-Request-Id 序号缺号**：每个 boot 都从 `-2` 起（无 `-1`），`-3` 永远缺，本轮还缺 `-9` 之外的 `-16`、`-18`；`f87032b2` 这个 boot 从 `-4` 起。请给一句序号规则（是否每次调度 tick 占号、空队列也占号），便于我们按序号判「有没有请求没发出」。
3. **content_version**：前 5 批 `builtin`，15:27:21 起 `v180-pck-foundation-1`。请确认 builtin 是「PCK 尚未装载完成时的占位」还是别的语义；后台按该字段分列，需要稳定口径。
4. **sent_at_ms 重试不刷新**：同一批重试时 `sent_at_ms` 保持首次值，退避越久服务端算出的 clock_skew 越大（本轮最大 2960 s）。合同没禁止，但这样 skew 变成「队列龄」而不是时钟偏差。建议每次实际发送刷新 `sent_at_ms`（事件的 `occurred_at_ms` 不动）；若你们选择保持现状，服务端就把该字段按「队列龄」解读并改后台标签。
