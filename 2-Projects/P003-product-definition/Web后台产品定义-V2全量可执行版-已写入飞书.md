## 一、产品定位与北极星

Web 后台不是纯管理工具，是两台发动机：

1. **留存真相仪表盘**：让团队看见真实的激活与留存。两套时钟分开管——设备激活时钟以快递妥投为 T+0，孩子使用时钟以闸门 2 通过为 T+0，两个数字分开统计上报，不糅成「激活成功」总称。口径错了所有迭代都会修偏；
2. **反馈闭环发动机**：KidsHub 把孩子和家长的真实声音收进来、聚合、决策、回告——没有它，数据只能告诉我们「用户走了」，永远不知道「为什么走」，其余 16 个功能全得盲改。

**北极星量化目标（埋点照此建表，后台照此出数）**：

| 关键节点 | 目标值 | 事件定义 |
| --- | --- | --- |
| D0 配网前引导转化率 | 85% | 拆包装通电 → 屏弹二维码后家长扫码进小程序 |
| D0 配网成功率 | 75% | 蓝牙握手成功 + WiFi 凭证下发 + 服务器心跳回报 |
| D0 设备激活率（净） | 60% | 闸门 1 三项满足：心跳 + 账号绑定 + 孩子档案 |
| D0 孩子首次有效使用率 | 45% | 闸门 2 三项：物理开盖 + 屏幕交互 + 持续 >5min |
| D1 主动使用读写台率 | 55% | 次日首次开盖 + 孩子发起的对话/操作 |
| D7 有效使用日 ≥4 天率 | 35% | 7 天内有 ≥4 天的「开盖+互动」日（剔除路过 10 秒） |
| D30 留存率 | 25% | 30 天内最近 7 天有 ≥1 次有效使用日 |
| ⭐ D30 孩子主动使用占比 | ≥40% | 真留存判定生死线：主动使用次数 / 总开盖次数，低于此说明留存是家长按出来的虚假活跃 |

一切后台模块必先回答：这对留存的贡献是什么？做砸了什么样？

## 二、统一后台架构与业务边界

**一个统一后台，三大模块**（不拆两个系统）：

- **数据看板（看）**：埋点体系 + 6 大页面 + 产品运营推导看板（第五、六章）；
- **KidsHub 运营台（动）**：反馈闭环的人工操作台，本文核心增量（第七、八章）；
- **运营操作台（管）**：SN/订单与客服工单，保障数据底盘干净（第九章）。

**为什么是一个后台**：
数据、反馈、版本、用户、设备、消息中心是同一套业务对象，KidsHub 决策需要用户上下文与激活质量数据，拆两个系统会切断「收集→聚合→决策→回告→状态回写」闭环。原 A16 所写「本数据后台单独制作设计，不依赖其它体系」指**登录账号体系独立**（不接公司权限中台），不是业务上另立门户。

## 三、角色与权限矩阵

后台从「只能看」升级为「能改状态、能发回告、能动分母」，必须分权。拆 4 类角色：

| 角色 | 权限范围 | 核心业务场景 |
| --- | --- | --- |
| 管理员 | 全局读写 + 账号配置 + 数据导出 | 系统配置、最高决策、产品分析、运营决策、策略制定 |
| 产品经理 | 数据看板（读）+ 主题池复核 + 采纳/金点子库决策 + 版本与致谢 | 版本决策、留存基线监测 |
| KidsHub 运营 | 工单分拣、打标、状态推进、贡献账本、回告发布、复访规则 | 反馈闭环日常运转 |
| 客服专员 | 客服工单池 + SN/订单处理 + 只读看板 | T+5 挽回、退货 SN 清洗 |

**登录页**：

- 账号 + 密码登录，账号密码由后台配置；
- 登录后按角色自动识别可见菜单（管理员可见全部菜单：数据概览、单用户查询、全部用户列表、统计页面、日期范围查询、KidsHub 运营台、运营操作台）；
- 本后台登录体系单独制作，不依赖其它体系。

**分权红线**：「看数据」「改状态/发回告」「改 SN 分母」三类动作不得混在同一角色——混权会导致数据被误洗或反馈被胡乱采纳。

**渐进路线**：P0 可先「管理员 + 运营」两档跑通，P1 拆满 4 角色。

## 四、数据底座与统一口径

全部埋点与推导指标统一遵循以下口径，避免各看板口径打架。**后台不许自己发明口径。**

**统一口径**：

- 活跃：检测到人在时长单日 ≥15 分钟（使用时长 = 摄像头监控到人在的时长）；
- 开盖：包含开盖行为和回归设备前；
- 双时钟：设备本地时钟 + 服务器时钟分别记录（记「事件实际发生时间」与「数据上报时间」两个时间戳）；
- 离线补传：≤7 天内的离线数据允许补传，按实际发生时间回溯修正（孩子离线用、过后补传，会让活跃看起来像「流失又回来」，必须回溯）；
- 退货 SN：呆滞 / 退货 SN 从激活率分母剔除，且状态可重置（翻新二次售出不能直接算「已激活」）；
- 有效使用判定：收益领取 + ≥1 次互动；家长开盖不结算夜航；失败退回单独打标。

**首周主 KPI 口径**：

- 主 KPI：7 天内 ≥4 个产品有效使用日；
- 只用基础读写（未进 AI）的使用日单列，不混入；
- 真信号另看主动会话率 / 主动重启率，剔除家长代操作；
- 暂停 / 补勤：补勤覆盖当天单列「修复性使用日」副指标，绝不灌进主 KPI。

**读数纪律**：

- 儿童正向率阈值高于成人；
- 峰终高光要求更高正向率；
- 警惕幸存者偏差：靠对照实验，而非「有 vs 无」观察；
- 会用会玩反验：撤引导后独立操作率 + 当天 / 次日自发重复率（完成动作 ≠ 达成效果）；
- 隐藏夜航对照实验：撤掉提醒后监测自发开盖率，防「为领奖而开盖」。

**统计口径四件套（不可妥协）**：

- ① 分母用快递妥投信号（不用出库数，渠道压货会让分母失真）；
- ② 毛激活率 / 净激活率（剔除退货）/ 激活后 7 天退货率三个数并列报；
- ③ 退货 SN 状态可重置；
- ④ 双时间戳 + 离线补传回溯 ≤7 天。

**其他贯穿约束**：

- 一户多设备：激活算「设备级」，家庭/设备两层都要能看，否则按账号算虚高、按设备算看不清楚；
- 断网假流失：想用但网络不通是可用性问题，不是真流失，单独区分；
- 学期 / 寒暑假：使用强度随学期假期结构性变化，对比数据只能同周期比；
- 订单与设备打通：出库 SN 绑订单、退货 SN 从分母剔除且可重置，否则永远看不到那批从没上线的呆滞。

## 五、数据埋点体系

**埋点设计原则**：

1. 用户行为全记录：从开机到关机，所有关键交互点埋点；
2. 专注时长优先：以「专注模式」为核心，精细记录使用时长、分段、中断原因；
3. 习惯养成追踪：通过开盖/关盖行为，分析用户使用规律与流失风险；
4. 数据可推导：基于原始数据计算关键指标，为产品迭代提供依据；
5. 活跃天数：检测到人在时长单日 ≥15 分钟。

### 5.1 九类基础埋点（收集型 · 原始数据）

九类基础埋点的字段级明细以《V1.5_1.2 数据埋点需求文档》为唯一来源；下表给出每类埋点的后台展示字段与推导价值，是单用户详情页（6.4）与统计页面（6.6）的数据来源：

| # | 埋点模块 | 后台展示字段 | 推导价值 |
| --- | --- | --- | --- |
| 3.1 | 用户基础信息 | 用户昵称、设备ID、设备型号、固件版本、绑定日期、所属B端客户 | 用户画像与归属 |
| 3.2 | 开盖/关盖行为（核心） | 日均开盖次数、日均使用次数、平均单次使用时长、开盖间隔分布、累计使用时长 | 识别「高频短时」与「低频长时」用户，分析流失风险 |
| 3.3 | 专注模式行为（核心） | 出航模式次数、陪伴模式次数、暂离次数、暂离总时长、平均专注时长 | 暂离次数/总时长→中断频率与使用舒适度；出航/陪伴比例→性格偏好 |
| 3.4 | 夜航报告（离线收益） | 夜航次数、夜航总时长、离线收益领取次数 | 每日回访引擎健康度 |
| 3.5 | 宝箱行为 | 宝箱出现次数、宝箱开启次数、开启率 | 变率强化机制有效性 |
| 3.6 | 生态缸行为 | 互动次数、换水次数、投喂次数 | 养成牵挂强度 |
| 3.7 | 换装行为 | 换装次数、拥有的装扮数、当前装扮 | 个性化投入度 |
| 3.8 | 藏品收集 | 已收集/总藏品数、完成度、最近获得藏品 | 长线收集动力 |
| 3.9 | 设置调整 | 亮度调节次数、音量调节次数、勿扰模式开关次数 | 设备适配度与打扰感 |

### 5.2 激活闸门埋点（接登舰/开机流程上报，后台据此算激活双指标）

**事件 1：device_activation（闸门 1 · 设备激活）**

| 字段 | 含义 |
| --- | --- |
| event | device_activation |
| device_sn | 设备 SN |
| order_bound | SN 是否已绑定订单（出库即绑） |
| heartbeat_ok | 首次心跳是否成功 |
| profile_created | 是否建档（手机号 / 孩子昵称 / 年龄，可跳过） |
| gate1_passed | 闸门 1 是否通过（心跳 + SN 绑定 + 建档） |
| ts | 时间戳（双时钟：设备本地 + 服务器） |

**事件 2：effective_activation（闸门 2 · 有效激活）**

| 字段 | 含义 |
| --- | --- |
| event | effective_activation |
| device_sn | 设备 SN |
| open_lid | 是否开盖 |
| interaction_count | 孩子发起的交互次数 |
| session_duration | 本次使用时长（秒） |
| is_child | 孩子 vs 家长轻量判定（家长开盖不计、不结算夜航） |
| gate2_passed | 是否达成（开盖 + 孩子交互 + 使用 >5min） |
| ts | 时间戳（双时钟） |

采集口径：有效使用判定 = 收益领取 + ≥1 次互动；迎新礼开箱后继续累计互动时长，达成 >5min 即上报 gate2_passed；失败退回开盖 / 触控 / 语音兜底单独打标。

### 5.3 满意度即时反馈埋点（step_satisfaction）

迎新礼 / 开箱 / 夜航领取后几秒，小可顺口问一句「爽没爽 / 懂没懂」，**不给奖励**，盯回应覆盖率 ≥40% + 正向率：

| 字段 | 含义 |
| --- | --- |
| event | step_satisfaction |
| scene | 触发场景（welcome 迎新礼 / box 开箱 / night 夜航领取） |
| answer | 回应（positive 正向 / negative 负向 / none 无应答） |
| covered | 本次是否产生有效回应（算覆盖率） |
| ts | 时间戳 |

### 5.4 新手引导埋点（guide_step）

定位「孩子哪步没学会 / 卡在哪 / 撤引导后能否独立操作」，后台据此展示引导完成质量：

| 字段 | 含义 |
| --- | --- |
| event | guide_step |
| unit | 引导单元（设置 / 登舰 / 夜航 / 专注 / 生态缸） |
| step | 第几步 |
| completed | 该步是否完成 |
| retry_count | 该步重试 / 提示次数（卡点信号） |
| independent_redo | 撤引导后是否能独立完成同操作（会用反验） |
| ts | 时间戳 |

### 6.3 单用户查询

**入口**：

- 顶部搜索框：支持按用户昵称或 device_id 搜索，回车或点击搜索按钮触发查询。

**用户列表（查询结果）**：

- 展示字段：用户昵称、绑定日期、最近活跃日期、累计使用时长、设备型号、7日活跃天数、当前状态；
- 支持点击查看详情进入该用户详情页。

**用户详情页【顶部】关键指标卡片**（推导型指标为该用户最核心的健康度数据，优先于原始埋点展示）：

| 指标卡片 | 展示方式 |
| --- | --- |
| 日均使用时长 | 数值 + 高于/低于均值趋势箭头 |
| 7日活跃天数 | 7格日历小方块，活跃日涂色（周一至周日） |
| 专注模式偏好 | 出航/陪伴比例，小饼图 |

## 七、KidsHub 运营台 ⭐（核心增量）

**KidsHub 的本质：**
**GitHub 的协作骨架 + 游戏化的儿童表达层**。
前台（设备端）是孩子能理解的语音、鼓励、署名；本章定义的是云端协作后台——结构化收集、真实推进、持续反馈。KidsHub 的事务记忆与功能 12 跨会话陪伴记忆是**两层两个库，不合并、不互替**：KidsHub 走自己的结构化后台（谁提的、什么状态、采纳没、贡献账本），要求强一致、可查、可审计。

### 7.0 解耦总纲：「回应」与「真改」是两条独立链路

- **即时回应链（全自动，无人工参与）**：孩子提交 → 云端 AI 当场生成共情话术（「我听到啦、记下来啦，会和大家的想法一起看」）→ 工单状态自动置「已收到」。这条链路不等运营上班，给足被听见的感觉，但**永不承诺「马上改」**；
- **异步决策链（人工拍板）**：后台攒同类反馈 → 运营打标聚合 → 攒够阈值 → 产品决策采纳 / 进金点子库 → 致谢与回告。

实现要点：设备端提交成功的判定只依赖「工单写入 + AI 回应送达」，与后台任何人工动作零耦合；运营处理时效不影响孩子端体验。

### 7.1 跨端反馈工单台

**做什么**：统一接收三路反馈，落成结构化工单。

**工单数据结构（核心字段）**：

| 字段 | 说明 |
| --- | --- |
| feedback_id | 工单唯一 ID |
| source | 来源端：child_voice（孩子语音）/ parent_report（家长周报内回答）/ parent_intercept（流失拦截答卷） |
| child_id / device_sn / family_id | 归属（支持一户多设备两层视图） |
| raw_content | 原始内容：音频 + ASR 文本（孩子）/ 答卷选项与文字（家长），原始记录不可丢 |
| emotion | 情绪极性标签（AI 建议 + 人工可改） |
| topic | 主题标签（AI 建议 + 人工可改） |
| topic_group_id | 归并后的聚合主题 ID |
| status | 已收到 / 评估中 / 已采纳 / 已进金点子库 |
| ts_device / ts_server | 双时钟时间戳 |
| handler / timeline | 处理人与全程操作时间线（审计用） |

**列表与操作**：按来源端 / 情绪极性 / 主题 / 状态 / 时间筛选；点开看原始内容与时间线；批量归并入聚合主题。

**关键约束**：每条必须带来源端标签，孩子与家长反馈共用主题池但不混源；单条全链路可查、可审计、可回看。

**留存逻辑链**：先把「为什么走」收上来；做砸了 = 意见箱石沉大海，其余功能全是盲改。

**📐 原型界面 · KidsHub 反馈工单台（列表 + 工单详情）**

### 7.2 正向状态机台

**状态机定义（终态只有两个，且都是正面）**：

| 状态 | 进入条件 | 操作者 | 孩子端口径 |
| --- | --- | --- | --- |
| 已收到 | 提交成功自动进入 | 系统 | 「我听到啦、记下来啦」 |
| 评估中 | 运营打标并归并入聚合主题 | KidsHub 运营 | 「大家正在认真看你的点子」 |
| 已采纳 | 产品在版本决策中圈定 | 产品经理 | 「你的点子被采纳啦」+ 升版后署名致谢 |
| 已进金点子库 | 产品决策暂不采纳 | 产品经理 | 「你的点子已经进我们的金点子库啦」 |

**关键约束**：

- **界面上不存在「拒绝 / 关闭 / 驳回」按钮**——全正面态是产品红线不是文案技巧；
- 状态变更自动回写设备端（孩子随时问「我上次说的那个怎么样啦」，小可按当前状态回答，禁自由发挥过度承诺）。

**留存逻辑链**：「说了有回音」是孩子继续开口的前提；做砸了 = 一次负面终态就能浇灭表达欲。

**📐 原型界面 · 状态机操作台（状态流转 + 回写记录）**

### 7.3 主题池（双标签聚合）

**做什么**：按「情绪极性 + 主题」双标签聚合，同类合并看量级；同类反馈攒够阈值才进版本决策（改不改、何时改，等聚合量说话，不被单条带节奏）。

**操作流**：工单进池 → AI 给双标签建议 → 运营确认/修正 → 归并入聚合主题（量级实时累计）→ 达到阈值的主题自动标「待决策」提示产品；

**参数**：聚合阈值按主题类型后台可配（建议初版：体验类 ≥5 条、功能愿望类 ≥10 条触发待决策，上线后按真实量级复盘调整——建议值，待产品确认）。

**关键约束**：AI 标签仅是建议（见 7.7）；**人工打标是 P0 合格降级**——AI 聚类赶不上不阻塞上线。

**留存逻辑链**：不聚合就无法从个体吐槽变成版本决策。

**📐 原型界面 · 主题池（聚合视图 + 阈值待决策队列）**

### 7.4 贡献账本

**做什么**：工单被采纳时，运营人工评质量并记入该孩子的贡献值 / 等级 / 署名。

**记分规则**：

- **按「被采纳的质量」驱动、不按提交数量**；不发物质奖励、不发家族币、默认不发补勤卡（防灌水，KidsHub 只保留等级与荣誉作为回报）；
- 质量分档后台可配（建议初版：普通采纳 +1 / 重要采纳 +3——建议值，待产品确认）；
- 等级档位与命名后台可配（初版建议 3-4 级，命名与方舟世界观对齐——待产品定）；
- 署名 = 孩子昵称，优先复用家长在小程序激活时录入的孩子昵称字段，待体验稳定后再逐步开放孩子端自定义。

**账本视图**：按孩子看贡献时间线（每笔来源工单可溯）；按全局看贡献分布（喂 KidsHub 度量看板的分层留存分析）。

**留存逻辑链**：沉没成本——贡献值越攒越离不开；做砸了 = 高贡献孩子留存无抬升，机制白做。

**📐 原型界面 · 贡献账本（孩子贡献时间线 + 等级管理）**

### 7.5 金点子库

**做什么**：暂不采纳建议的正面归宿；支持翻牌、月度回顾、主题征集时回捞进版本池。

**关键约束**：不是回收站，是后续主题征集、版本翻牌、月度回顾的候选池；持续盯「金点子库 vs 已采纳比」防止沦为婉拒垃圾桶。

**留存逻辑链**：「你的点子进了金点子库」让未采纳也是被珍视；做砸了 = 变相拒绝，表达热情熄灭。

**📐 原型界面 · 金点子库（候选池 + 回捞操作）**

### 7.6 版本决策与致谢

**做什么**：

- 产品从「待决策」主题中圈定采纳项 → 打「小改 / 大功能」分级 +「规划中 / 开发中 / 已上线」阶段标记；
- 升版时自动汇总本版所有被采纳工单 → 生成更新说明致谢名单（含每个孩子的署名昵称）→ 下发设备端展示。

**关键约束**：孩子端署名与状态展示归 KidsHub（本章）；家长端回告走第八章；阶段话术是「在做」，不说「已改好」。

**留存逻辑链**：「我说的话真的变成了产品」是 KidsHub 最强的高光时刻。

**📐 原型界面 · 版本决策台（采纳圈选 + 致谢名单生成）**

### 7.7 AI 辅助边界

- **AI 做**：情绪极性识别、主题标签建议、聚类建议、即时回应话术生成、大功能预告文案草稿；
- **人拍板（AI 绝不代劳）**：**采纳决策、终态推进、版本决策、回告发布**——影响用户信任的动作必须人负责，防过度承诺反噬信任。

### 7.8 复访触发台（孩子端，四级降级）

**做什么**：执行四级降级规则，把沉睡的孩子柔性引回 KidsHub。后台管规则配置与触发记录：

| 级别 | 触发条件 | 动作 |
| --- | --- | --- |
| L1 入口冷启动 | 1 周触发 0 进入 | 完成专注后弹引导 + 每周主动唤起一次 |
| L2 提交后不回看 | 提交后 24h 未查看状态 | 小可在下一次主线场景里主动开口「你昨天提的那条小可问到结果啦，要不要听？」 |
| L3 久未提交 | 14 日无新提交 | 小可在出航/破冰里软触发「最近有没有什么想吐槽的」 |
| L4 等级停滞 | 长期初级且无提交 | 进入用户访谈与定义修订流程（后台出名单，人工跟进） |

**关键约束**：**不走推送、不走家长 App**，只在设备端主线场景由小可开口。

**留存逻辑链**：防沉睡——KidsHub 不能是一次性玩具。

**📐 原型界面 · 复访触发台（规则配置 + 触发记录）**

### 7.9 流失拦截台（家长端，与复访触发台分开）

**做什么**：云端活跃度监控命中流失规则 + 30 天频控（同一家长 30 天内最多触发一次）→ 给家长小程序推软化单选题 → 按答案即时分流挽回 → 答案写原始记录并归并主题池（带 parent_intercept 来源标签）。

**挽回分流规则**：

| 家长答案 | 即时挽回动作 |
| --- | --- |
| 觉得没用 | 推送价值解读（孩子数据亮点） |
| 觉得太贵 | 发放搬家券等挽留权益 |
| 不会用 | 推送教程 |
| 只是暂时没空 | 记录，不再打扰（必含此选项） |
| 未作答 | 仅记未作答标记，不追问、不纠缠 |

**为什么与 7.8 分开**：孩子复访走设备端小可、家长拦截走小程序推送——触达通道、对象、话术完全不同，杂糅会互相污染频控。

**留存逻辑链**：流失前拿到「为什么走」，别让家长默默退货。

**📐 原型界面 · 流失拦截台（规则与频控配置 + 答卷记录）**

### 7.10 KidsHub 度量看板【P0】

**看板内容**：

- 孩子侧漏斗：曝光 → 进入 → 开口 → 提交 → 即时回应送达 → 查看状态 → 再次提交 → 升级；
- 家长侧漏斗：小程序 PV → KidsHub 主页 UV → 家长访问后孩子 7 日提交率；
- 质性信号：金点子库 vs 已采纳比、被署名孩子的后续 30 日留存抬升幅度；
- 分层留存：高 / 中 / 低 / 零贡献孩子的 30 / 60 / 90 日留存曲线（分层自然观察，本版不做 A/B）。

**为什么 P0**：KidsHub 是 P0 功能，验证手段不能晚于功能本身——两道验收闸门（见第十二章）没有看板就无法判定。

**📐 原型界面 · KidsHub 度量看板**

## 八、回告路由台（反馈到改进的闭环出口）

**边界铁律**：本章只管**家长端定向回告 + 全体公开预告**；孩子端回告、播报、状态展示、署名一律归第七章，不在此重复。

**回告路由规则**：

| 改动级别 + 阶段 | 路由动作 | 时效 |
| --- | --- | --- |
| 小改 · 已上线 | 按来源用户 ID 定向推给当初提建议的家长 + 落小程序消息中心可重看 | 上线后 48h 内 |
| 大功能 · 规划中/开发中 | 公开预告：进周报首页 + 设备开机预告位（话术「在做」，不说「已改好」） | 并入下周报 |

**送达回写与未达兜底**：

- 推送只是提醒，回告内容必须落小程序「消息中心」可重看；
- 回写送达 / 打开状态；推送 7 天未打开 → 周报二次提醒 + 消息中心常驻红点。

**措辞模板（共创化）**：「因为你的建议，小可又进化了」+ 改后对比图，眼见为实。

**亲子纽带联动**：家长代提、关乎孩子的建议被采纳 → 本台仅触发联动条件，孩子端「爸爸/妈妈的心意」展示由 KidsHub（第七章）承载。

**使用流程**：后台采纳反馈 → 先判来源（孩子→走第七章不归本台 / 家长→进本台）→ 判改动级别 + 阶段 → 按上表路由 → 回写送达/打开状态 → 未达走兜底 → 用户收到回声、更愿继续反馈。

**留存逻辑链**：「你说的→我们听到了→真的改了」；做砸了 = 反馈石沉大海，比不收集更伤。

**📐 原型界面 · 回告路由台（路由队列 + 送达监控）**

## 九、运营操作台

### 9.1 SN 与订单管理【口径 P0 · 操作台 P1】

**口径 P0（聚合层自动生效）**：

- 退货 / 呆滞 SN 自动从激活率分母剔除——这是数据正确性问题不是运营功能，P0 不生效则首发数据全脏；
- P0 期间退货名单由订单系统导入兜底（无人工界面也要保证口径正确）。

**操作台 P1（人工界面）**：

- SN 与订单绑定查询（出库即绑）；
- 呆滞标记：确定已退货的设备打「死货标记」，打标后系统自动从全局激活率分母剔除；
- SN 状态重置：翻新二次售出的设备重置激活状态（不能直接算「已激活」）；
- 换绑 / 解绑处理。

**留存逻辑链**：清洗脏分母；做砸了 = 呆滞退货机把净激活率全盘污染，永远看不到那批从没上线的设备。

**📐 原型界面 · SN 与订单管理**

### 9.2 客服挽回工单池【P1，P0 过渡方案见下】

**触达分级（云端自动执行，扣除周末权重）**：

- T+1 / T+3：自动提醒通道（推送 / 短信等，无需人工）；
- T+5：仍未激活 / 未真用 → 生成人工客服工单。

**工单池（P1 界面）**：

- 接收 T+5 名单；列表展示：设备 SN、家长联系方式、**蓝牙上报的本地错误日志**；
- 错误日志用于区分「卡配网」vs「激活了但孩子没真用」——外呼前必看日志，话术按卡点精准；
- 客服记录外呼结果与挽回状态。

**P0 过渡方案（已拍板）**：P0 期间用「未激活名单每日导出 excel」过渡（复用 6.7 数据导出），客服线下跟进；工单池界面 P1 交付。

**留存逻辑链**：赶在 7 天退货窗口前干预；做砸了 = D0 问题被伪装成「孩子不留存」。

**📐 原型界面 · 客服挽回工单池**

## 十、技术方案与数据链路

**前端技术栈（沿用已验证原型方案）**：

- Vue 3 CDN + Element Plus + ECharts，单页应用架构；
- 无构建工具，直接浏览器打开 HTML 文件即可运行；
- 地图使用阿里 DataV GeoJSON 数据源（国家统计局标准），支持鼠标拖拽、缩放（范围 0.8x~5x），省份点击进入详情、支持返回全国视图。

**数据来源与切换**：

- 当前原型使用 Mock 数据（86 条模拟用户记录）；省份字段采用全国 34 省级行政区完整名称（与国家统计局 GeoJSON 名称一致）；
- 实际接入时替换为后端 API 数据。

**数据链路（两层，P0 必须落地）**：

| # | 工程项 | 说明 | 优先级 |
| --- | --- | --- | --- |
| 1 | 聚合层 | 原始事件 → 推导指标，**服务端聚合（前端只渲染）**；口径全部按第四章执行 | P0 |
| 2 | 后台数据 API | 每页面 1 个聚合接口，Mock → 真数据 | P0 |

**展示约定**：原始埋点接单用户详情 / 统计页（9 模块分区）；推导参考数据由埋点经聚合层计算，是后台重点展示内容；KidsHub 工单与账本数据走 KidsHub 自有结构化存储（强一致、可审计），与埋点聚合链路分开。

## 十二、风险与验收

**验收闸门（两道同过才算达标）**：

- ① 单次贡献闭环可追踪——一条反馈从提交到终态（采纳 / 进金点子库）全链路状态机可见、可拉回、不漏；
- ② 留存价值兑现——KidsHub 活跃孩子的 30 / 60 / 90 日留存率显著高于低/零贡献孩子（分层自然观察）+ 上线后留存切片较基线 ≥5 个百分点。

**数据风险**：聚合层与后台 API（第十章两项 P0）是一切看板的前提，延期则全后台只有 mock。

**运营风险**：状态机长期停在「评估中」= 变相已读不回——运营 SLA：单条工单 7 天内必须从「已收到」推进到「评估中」；30 天内到终态，或保持评估中但复访链路必须正常触发。

**红线回归清单（每次迭代必检）**：

- 状态机无负面态（无拒绝/关闭/驳回按钮与状态）；
- 贡献值按被采纳质量、不按提交数量；
- 不发物质奖励、不发家族币；
- 孩子端回告归 KidsHub（第七章），回告路由台只管家长端 + 全体预告；
- 回应与真改解耦（即时回应链不等人工）；
- 工单来源端标签必带，共池不混源；
- 后台口径与第四章一致，不自造口径。
