# 《P003 Web 后台产品定义（整合方案）》

## 🎯 D.0 核心评审点决议（必吵点站队与定位）

针对评审中必然交锋的核心问题，本方案先亮明底牌与决策依据：

1. **一个后台 vs 两个后台？**
   - **【站队】**：**一个统一后台，分模块管理。**
   - **【理由】**：数据看板（A16）需要与 KidsHub 运营深度打通。单用户查询页面必须不仅能看用户的行为活跃度，还能看他在 KidsHub 提了多少点子、拿到多少贡献。拆分两个独立系统徒增开发对接成本和查表阻力。A16所说的“不依赖其它体系”，是指本后台应有自己独立的**账号密码登录体系**，免接公司复杂权限中台，而非业务系统层面的强行割裂。
2. **角色要不要拆？拆几个？**
   - **【站队】**：**必须拆分，推荐设立 3 类角色。**
   - **【理由】**：后台不再只是“只能看”的白板，加入了状态流转、用户账本修改。建议设立：【管理员】（全局权限）、【产品/数据分析】（只读访问所有看板，做版本决策）、【KidsHub 运营与客服】（操作工单流转、派发贡献、处理退货SN）。
3. **KidsHub 后台 P0 最小集是什么？**
   - **【站队】**：核心骨架必须全上。包含：① 跨端工单收集列表；② 状态机手动流转（收→评→采/金）；③ 荣誉账本手动加分；④ **允许人工打标替代 AI 自动聚类作为合格降级**。AI 辅助可以 P1 补齐，但状态机流转与回写不能卡脖子（PRD 功能 15 核心）。
4. **AI-01 在后台的角色边界？**
   - **【站队】**：**AI 预处理，人工来拍板（人机协同）。**
   - **【理由】**：AI 负责情绪提取、主题分类草案、生成大功能文案初稿，但**修改工单状态、决定是否采纳、发放贡献值、点击推送回告**这四件事，**绝对不许 AI 自动代劳**。防过度承诺反噬信任。
5. **客服工单和 SN 管理放本版还是二期？**
   - **【站队】**：**必须收进本版（7月30日 P1 交付）！**
   - **【理由】**：SN 退货剔除（ACT-01）与 T+5 蓝牙错误日志（功能 3）关乎 D0 激活生死线的净激活率计算。放到二期会导致首发的留存数据全盘污染、算不准。

## 🏗️ D.1 Web 后台整体架构与角色

**后台总体定位** = ① 数据看板（看宏观与个体） + ② KidsHub 运营台（管生态与闭环） + ③ 运营操作台（修底层异常）。

| 角色设定 | 数据与操作范围 | 核心业务场景 |
| :--- | :--- | :--- |
| **管理员** | 全局所有菜单读写 | 系统底层配置、最高决策 |
| **产品/数据分析** | 数据看板模块、度量看板（只读） | 监测留存基线，制定版本开发规划 |
| **KidsHub 运营** | KidsHub 运营模块（全操作） | 处理反馈、发放贡献、编辑致谢公告 |
| **客服专员** | 运营操作台（全操作） | 处理 T+5 挽回电话、执行退货 SN 剔除 |

- **产品运营推导看板**：新增激活双指标漏斗、首周留存达标率、主动使用真留存。

## 🗣️ D.3 KidsHub 运营后台（新增核心）

这是本次补齐 PRD 功能 15/16/17 的核心引擎。本质上是一个**儿童版 GitHub 协同后台**。

### D.3.1 跨端反馈工单台
- **做什么**：统一接收来自设备端孩子的话（含音频与 ASR 文本）和家长小程序端答卷/流失拦截的反馈。列表需呈现：来源端、情绪极性、内容。提供状态机流转操作（状态：已收到 → 评估中 → 已采纳 / 进金点子库）。
- **操作者**：KidsHub 运营。
- **关键约束**：全程全正面态，**没有“已拒绝/已关闭”按钮**。AI 只做情绪识别标注辅助，必须由人工流转。
- **【留存逻辑链】**：**把吐槽变进度。做砸了等于意见箱石沉大海，抹杀孩子最后一点开口的欲望（PRD 功能 15/16）。**

### D.3.2 贡献与荣誉账本
- **做什么**：管理用户的荣誉大盘。当一条工单被操作流转为“已采纳”时，后台弹窗要求运营人工评估质量（如小改/大功能），并向该用户的贡献账本手动加分、触发等级提升。
- **操作者**：KidsHub 运营。
- **关键约束**：奖励只凭“采纳质量”给荣誉，**严禁按“提交数量”给家族币（防刷分灌水）**。
- **【留存逻辑链】**：**沉没成本效应。孩子贡献值越高越觉得有归属感，彻底离不开设备（PRD 功能 15）。**

### D.3.3 主题池与版本决策中心
- **做什么**：人工或 AI 将同类反馈聚合为“主题（Topic）”（如：生态缸优化）。未采纳的主题归入“金点子库”。支持圈选多个主题并入一次“版本升版规划”。
- **操作者**：产品 / KidsHub 运营。
- **关键约束**：金点子库不是垃圾桶，它是产品征集下一期版本的候选池。
- **【留存逻辑链】**：**汇聚同类声音，产品不再盲人摸象式瞎改，让迭代直击痛点。**

### D.3.4 回告路由与公告推送网关
- **做什么**：闭环出口。版本升级后，支持自动读取被采纳工单的来源用户及自定义昵称（署名），生成《更新说明致谢名单》。同时提供定向路由推送——家长代提的反馈走小程序消息中心，孩子本人的反馈走设备端 KidsHub 播报。大功能生成全体公开预告。并监控推送送达与打开率。
- **操作者**：KidsHub 运营。
- **关键约束**：推送 7 天未打开，系统需提供二次提醒触发，并在消息中心挂红点（PRD 功能 17）。
- **【留存逻辑链】**：**让回声追上每次开口。做砸了用户不知道你改了，等于白改，前功尽弃（PRD 功能 17）。**

### D.3.5 KidsHub 度量看板
- **做什么**：统计 KidsHub 的漏斗数据（曝光→开口→查看进度）。监控“高贡献孩子 vs 零贡献孩子”的留存杠杆差值。
- **操作者**：数据 / 产品分析。
- **【留存逻辑链】**：**用数据验证 KidsHub 机制是不是真成了一个长线护城河（PRD 功能 15 验证方法）。**

## 🛠️ D.4 运营操作台（底层异常管理）

本模块解决硬件流转与底层连接的死锁问题，保障数据底盘干净。

### D.4.1 客服挽回工单池 (对应 PRD 功能 3)
- **做什么**：接收 T+5 临近退货窗口仍未配网的设备名单。列表展示：设备号、家长电话，以及最重要的**带蓝牙上报的本地错误日志**。支持客服记录外呼挽回结果。
- **操作者**：客服专员。
- **关键约束**：外呼前必须看错误日志，明确知道家长是“卡在WiFi 5G不兼容”还是“激活了但孩子压根没玩”。
- **【留存逻辑链】**：**赶在 7 天退货窗口前死里逃生。做砸了，硬件成本就眼睁睁亏掉（PRD 功能 3）。**

### D.4.2 SN 与订单管理 (对应 PRD ACT-01)
- **做什么**：设备 SN 的强制解绑、重置状态。支持将确定已退货的呆滞设备打上「死货标记」。
- **操作者**：客服专员。
- **关键约束**：被打上呆滞标记的 SN，系统必须自动将其从全局“设备激活率”的分母中剔除。
- **【留存逻辑链】**：**清洗脏数据。做砸了，退货库里的死机会把首月净激活率等硬指标全盘污染，没人为真实的留存负责。**

## ⚖️ D.5 横切约束（全局铁律）

所有模块在开发与测试中，必须无条件遵循以下约束：

1. **唯一数据源（口径四件套）**：Web 后台的激活率必须以妥投时间为分母计算；必须维护设备真实发生与服务器收到时的**双时间戳**；支持 ≤7 天的离线数据补传回溯。后台不许自己重新发明一套口径。
2. **全正面态回馈（封杀负面词汇）**：KidsHub 所有前端面向用户的流转中，绝对不能出现“已关闭、已拒绝、驳回”等负面状态，最低限度是“进入金点子库”。
