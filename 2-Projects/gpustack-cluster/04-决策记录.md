### 现象

需要将 Mac Mini (M4, 32GB) 和 Mac Studio (M2 Max, 32GB) 组成算力集群，用于本地 LLM 推理。两台机器通过雷电接口直连。

### 排查过程

1. GPUStack 2.x 安装踩了大量坑：
   - Python 版本：系统 Python 3.9 和 brew Python 3.14 都不在支持范围（3.10-3.12），需手动指向 3.12
   - 安装脚本强制加 `[audio]` extra 依赖 openai-whisper，构建失败 → 手动 sed 去掉
   - GPUStack 2.x 需要 PostgreSQL（不再支持 SQLite），但 pipx 安装不含嵌入式 PostgreSQL → 手动 `brew install postgresql@17`
   - 嵌入式 Gateway (Higress) 需要 s6-overlay 启动，macOS pipx 路径不支持 → 用 `--gateway-mode disabled` 绕过，API 改走 `--api-port` (30080)
   - 手动创建 `/var/lib/gpustack/higress/kubeconfig` 解决 kubeconfig 报错
2. Mac Studio Worker 部署：
   - Mac Studio 无网络 → 通过 Mini 设置 NAT + pfctl 共享网络
   - Mini 上 Python 3.11/3.12 的 brew 版本因 OpenSSL 不兼容 macOS 13 → 下载 python.org 官方 3.11.9 pkg
   - GPUStack 2.1.1 实际需要 Python 3.11+（用了 `typing.Self`），3.10 不够
   - Mac Studio 有残留系统代理配置 (127.0.0.1:7890) → 关掉
3. Worker unreachable 根因：
   - Mac Mini 的 `http_proxy=http://127.0.0.1:10808` 环境变量导致 Server 的 worker_syncer 健康检查请求走了 Xray 代理 → 代理返回 503 → Worker 被标记 unreachable
   - 在 launchd plist 中设置 `NO_PROXY=192.168.100.0/24,localhost,127.0.0.1` 解决

### 根因

GPUStack 2.x 设计为 Docker 容器环境（s6-overlay 多进程管理），macOS 原生 pipx 安装缺少嵌入式组件（PostgreSQL、Higress Gateway），需要大量手动适配。

### 候选方案

| 方案 | 做法 | 优点 | 缺点/风险 |
|------|------|------|----------|
| A. Docker 部署 | 两台都装 Docker Desktop，docker run gpustack | 官方推荐，一键搞定 | Mac Mini 没装 Docker，Mac Studio 无网络下载镜像大 |
| B. pipx 原生安装 + 手动适配 | pipx 装 gpustack，手动装 PostgreSQL，禁用 gateway | 轻量，不依赖 Docker | 适配复杂，gateway 功能受限 |
| C. GPUStack 0.6.x | 用旧版（SQLite + 无 Gateway） | 简单 | 功能少，版本太旧 |

### 决策

**选择**：方案 B — pipx 原生安装 + 手动适配

**理由**：Mac Mini 已有大量服务在跑，不想引入 Docker Desktop 的资源开销。手动适配虽然复杂但已完成，集群功能可用。

**放弃的方案**：
- 方案 A（Docker）：Mac Mini 未安装 Docker Desktop，且 Docker 在 macOS 上有额外虚拟化开销。如果未来需要完整 Gateway 功能（分布式推理），可以迁移到 Docker。
- 方案 C（0.6.x）：版本太旧，不支持最新模型格式和调度策略。

### 改动

| 机器 | 改动 |
|------|------|
| Mac Mini | 网络: Thunderbolt Bridge 192.168.100.1, NAT 转发, IP forwarding |
| Mac Mini | GPUStack Server: launchd ai.gpustack, port 30080, gateway disabled, PostgreSQL 5432 |
| Mac Mini | SSH: ~/.ssh/config 添加 macstudio 别名 |
| Mac Studio | 网络: Thunderbolt Bridge 192.168.100.2, 关闭系统代理 |
| Mac Studio | Python: 官方 3.11.9 pkg 安装到 /Library/Frameworks/Python.framework |
| Mac Studio | GPUStack Worker: ~/.local/gpustack-venv, 连接 Mini:30080 |

### 验证

- 两节点均为 `ready` 状态
- Worker healthz 端点可达
- Web UI 可访问 `http://localhost:30080`

### 什么条件下该翻这个决策

- **安装 Docker Desktop** → 迁移到 Docker 方案，获得完整 Gateway 功能
- **GPUStack 发布 macOS 原生支持的版本** → 简化安装流程
- **节点数量 >3** → 可能需要完整 Gateway 做负载均衡
- **需要分布式推理（模型跨节点拆分）** → 必须启用 Gateway

### 教训

1. **GPUStack 2.x 不适合 macOS 原生部署** — 官方只测试 Docker 路径，pipx 路径有大量未覆盖的坑
2. **代理是内网通信的隐形杀手** — `http_proxy` 环境变量会影响所有 HTTP 请求，包括内网健康检查。launchd 服务必须显式设置 `NO_PROXY`
3. **跨 macOS 版本拷贝 brew Python 不可行** — OpenSSL 动态库绑定了编译时的 macOS 版本，必须用 python.org 官方安装器
4. **Mac Studio 的残留系统代理** — 即使没跑代理软件，macOS 系统代理配置仍会影响 pip/curl

## 集群架构：主节点选择（2026-03-31）

<!-- type: arch -->
<!-- status: 生效中 -->

### 现象

两台 Mac 组集群，需决定谁做 Server（主节点）。

### 根因

N/A（新建架构决策）

### 候选方案

| 方案 | 做法 | 优点 | 缺点/风险 |
|------|------|------|----------|
| A. Mac Mini 做 Server | Mini 跑 Server + Worker，Studio 纯 Worker | cc 在 Mini 上，管理方便；Server 轻量 | Mini 的 GPU 弱于 Studio |
| B. Mac Studio 做 Server | Studio 跑 Server + Worker，Mini 纯 Worker | Studio 算力强 | cc 不在 Studio 上，管理不便 |

### 决策

**选择**：方案 A — Mac Mini (M4) 做 Server

**理由**：Server 角色是调度管理，CPU 密集不是 GPU 密集。cc 在 Mini 上运行，可以直接管理 GPUStack。两台都作为 Worker 贡献算力。

**放弃的方案**：
- 方案 B：Studio 作为纯算力节点更合适，不需要承担管理职责。且 Studio 无网络，管理不便。

### 什么条件下该翻这个决策

- Mac Studio 连上网络并安装了更完整的管理工具
- 有第三台性能更弱的机器可以专门做 Server（管理节点不跑推理）

### 什么条件下该翻

- 节点超过 254 台（不太可能）
