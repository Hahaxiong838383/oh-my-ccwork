# Air ChatGPT 代理阻断复盘与防复发

核验日期：2026-10-27，Asia/Shanghai。署名：codex（OpenAI）。

## 结论

反复进入阻断出口的主要原因已确认：Xray 自动切换控制器把单一业务探测失败扩大成整条线路失败，继而选择 `cf-block`。Xray 引擎按配置执行了该决策；目前没有证据表明是两个 ChatGPT App 同时争抢代理造成。上游超时仍存在，本次修复解决的是本机误判、重复阻断和维护程序之间的冲突，不能保证外部网络或服务永不故障。

Xray 的规则采用从上到下首次匹配，balancer 根据 selector/fallback 选出口；相关语义已对照[官方路由文档](https://xtls.github.io/en/config/routing.html)。当前宽 Google 规则遮蔽了后续部分更细规则，OpenAI/Claude/npm 等仍共享 cf-lisa；这是应在后续路由整理时处理的范围，本轮没有顺手改动业务分流。

## 已上线的修复

1. **自动模式区分业务健康与路径可达。** connect/total 超时改为 8/12 秒。仍有获准路径部分可达时保留或选择该代理；三路全部不可达连续 3 轮才阻断。完整健康候选、回切连续健康 120 秒及当前持有 300 秒等机制保留。
2. **消除控制器的重启竞态。** 探测后再次检查配置与实际 override；短暂 API 故障最多快速重试 3 次，每次间隔 2 秒，再恢复常规周期。状态增加最近成功路径和时间、明确且脱敏的错误码。
3. **配置校验容忍纯格式变化。** 新增完整 JSON 语义哈希，保留数组顺序，拒绝重复键和 NaN；真正语义变化仍停止控制。没有绕过校验，也没有自动改成直连。
4. **阻止管理面板独立覆盖受管配置。** 语义相同的保存保持原字节；语义变化返回 HTTP 409 和明确错误，前端停止后续“成功”提示及重启。以后改受管节点/规则须通过同步校验的维护发布流程，不能再在面板盲写。
5. **精确管理主代理生命周期。** macOS 状态、停止和重启只操作 com.xray.proxy；不再以全局 pkill 作为失败兜底。独立 Grok Xray 不随主代理操作被误杀。
6. **取消受管模式每日自动重启。** 规则更新器继续下载资源，变化时只写入磁盘，并持久记录 pending_until_verified；不发 HUP、不自动重启。无更新、PID 变化或下载错误均不会抹掉待应用状态。下次维护需验证后再确认应用，不能把“下载完成”报成“已生效”。
7. **配套日志轮转。** 受管模式下 access.log/xray.log 使用 copytruncate，保持正在写入的 inode；备份失败不截断。复制和截断之间存在少量日志可能丢失的窗口，不能称无损轮转，但不会为轮转重启连接。
8. **源码及安装器防回退。** 已同步 Air 的 failover 源码、prepare 签名生成、测试与说明；旧 manager 主源码保留，最新运行脚本及测试存入其 `maintenance-20261027/`。通用安装器在任何写入或服务操作前拒绝覆盖已有受管安装，避免重装重新带回旧逻辑。第一阶段的 17 个源码/维护文件经版本比对、备份后写入。第二阶段另将管理页与状态接口、知识材料纳入独立分支交付，见下方管理页验收。

## 保留的限制与后续维护

- 三条通道仍共享最终 Lisa 出口；它们提供中转路径容灾，不等于三个独立出口供应商。最终出口或目标服务整体故障不能靠本机调参消除。真正出口容灾需要另行评估第二个获准出口以及账号/IP 稳定性约束。
- 默认 block 和手动 pin 的严格语义保留。pin 指定路径的任一目标不健康时仍会阻断；本轮当前 pin=None。主 Xray 的显式重启仍会断开既有流，恢复探测也需要时间，不能承诺重启零中断。
- 更新受管配置时：先备份并比较现役版本→构造候选→Xray 配置测试→同步生成字节/语义 guard→原子发布→在明确维护时点重启必要服务→验实际 override、主入口和应用。不要只更新 config.json 或只把 guard 改成任意当前值。
- 资源 pending 只能在核对资源哈希、确认主实例启动时间/配置测试和实际入口后由维护流程清除；PID 变化本身不能充当已应用证据。
