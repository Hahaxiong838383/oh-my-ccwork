# fnmedia-ext 播放稳定性方案（2026-10-30）

状态：方案研究，未实施、未部署。Codex负责现有代码及实施边界，Grok经Codeg独立调研与审查（任务accffa99-c8a6-4cff-a31f-ceae26ea1d99）。目标是减少飞牛App/TV在线播放的缓冲停顿，保留原生播放器、手动选线、鉴权及官方可升级性。

## 1. 依据与范围

- 当前生产为本地加固0.2.19.2，源码e6de9a6；上游公开0.2.33，固定提交7e52f8a66e4c3217c10dc8310ee4f609d663468a。不能用上游原包覆盖加固版。
- 最近《敦煌英雄》量子分片816484字节、5.958333秒内容，下载7.257秒；同URL随后2.118秒。下载时间/视频时长分别1.218、0.355。慢样本下载时长比视频时长多1.299秒；串行连续供给模型中对应净供给缺口，不是已测播放器卡顿秒数。证明一个足以卡顿的慢点，不证明每段都慢。
- NAS低负载，连接复用且首字节约0.2秒。已测慢在源→NAS正文；NAS→维护机133Mbps不能代替手机/TV的实际无线或外网链路验收。详细证据见16号报告。
- 0.2.32首分片验活、0.2.33健康评分值得吸收，但不是持续吞吐检测。新版hls_seg依旧整段下载再返回；自动入口line+auto判据冲突仍在。
- 本轮不遥控电视，不新增代理、不改飞牛官方二进制/nginx/数据库，不调整设备网络或轮换凭据。

## 2. 主方案及优先级

采用“实际分片观测 → 起播选满足播放余量的线路并固定 → 同线路小窗口预取”的主方案。流式转发作为独立候选验证，不作为第一版必需项。首版保留完整分片处理，避免同时改动解密、PNG解包、Range及断流重试。

| 工作 | 决定 | 理由 |
|---|---|---|
| 真实分片耗时/时长观测 | 首先做 | 能直接识别本次慢正文；清单快不等于视频快 |
| 有预算的自动选线、会话固定 | 首版核心 | 修复入口问题，避免每次取清单重新竞速 |
| 未来1段串行内存预取 | 同一候选版，独立开关 | 先验证原生请求间隙是否有可利用的提前量，不额外并行抢源站带宽 |
| 上游死链检测、健康信息 | 挑选合并 | 减少假可播；保留本地精确匹配与安全补丁 |
| 无加工分片流式转发 | 第二阶段候选 | 可能提前交付首字节，但不增加源带宽，原生播放器是否提前解码需实测 |
| 多连接切片下载单个TS | 首版不做 | Range支持、对象一致性、限速/429及额外竞争尚无证据支持 |
| 302客户端直连 | 独立条件方案 | 主要可能缓解外网NAS上行瓶颈；本次已测是源→NAS慢，且存在UA/Referer/解密兼容性 |

架构判断置信度高；下面数值均为候选初值，必须经故障回放及真机A/B验收，不是承诺的生产性能。

## 3. 实施设计

### 3.1 先补可区分的测量

在现有鉴权之后、真实分片加载及响应出口记录：排队时间、源站首字节、完整下载时间、重试总时间、真实字节数、对应EXTINF、缓存/预取命中、客户端取消与响应结束。单调时钟计时，分别统计NAS下载与向客户端交付，避免把慢客户端误记成慢源。

核心指标r=完整分片下载耗时/EXTINF；r>1表示不能按该样本速度持续供给，r≤0.7作为初始有余量候选。r包括该次下载重试成本，但不混入客户端发送时间。缓存命中、2KiB验活、取消后的不完整样本不得记为高速完整分片。

按线路+CDN+请求头上下文区分样本，不仅按资源站聚合。使用最近多个真实分片的快/慢平滑估计和超时比例，保留样本量；单次好样本不是长期健康结论。上游sourcehealth可借用结构，但不能原样把main返回成功的零延迟与探测样本混算，也不能把尚未调用的usable函数写成已经生效。

日志仅写耗时、字节、脱敏线路标识及原因码；不打印原始URL、查询串、Cookie、Authorization、AES密钥、用户标识或浏览历史。

### 3.2 自动选线先消除入口歧义

当前涉及play/play、media/range、榜单即时入口、preset/main四条路径，不能只删main的not explicit_line。

- 先用隔离接口回放及允许的真机测试，确认各端初播、手动选线、重试、拖动实际携带的字段。当前stream/list会把第一线路的编码bitrate回给播放器，因此“请求带bitrate”不能直接证明用户手动选择。
- 推荐在现有原生线路菜单增加明确的“自动”选项及独立选择标识；具体标识编码先验手机/TV兼容，不与真实线路编码混用。默认自动和手动首条必须可以区分。无法识别的旧请求保留显式选线语义。
- 服务端在首个main请求选择线路，返回所选线路的单一播放清单。不要把独立资源站伪装成可任意ABR切换的多个码率变体；现有原生手动线路菜单继续保留。真实源自身对齐的码率档位另行处理，不混淆两种概念。
- 若某端只能通过HLS变体菜单切线，尚未验证原生“自动/手动”入口，则该端先沿旧菜单与固定线路路径，不能为启用自动选线删除手动功能。手机、TV分别验入口，不能从Web回放推断全部兼容。
- 为已验证用户建立随机播放上下文ID，贯穿preset/main/seg；它只用于关联状态，不能代替官方鉴权。内容、集数、所选线路、请求头及清单版本固定在上下文内；每个新HTTP请求仍经过官方鉴权。跨用户ID复用拒绝。
- 同一上下文重拉main不竞速，播放满10分钟也不能因全局最快线缓存过期自动换源。新播放/主动改线才建立新上下文；休眠上下文超时后，旧链接仍按原显式线路处理，不偷偷换到新源。容量上限和清理要独立于用户数，不能缓存原始官方token。
- 仅在媒体清单尚未首次返回客户端前允许自动故障切换；清单一旦发出就固定，即使首个分片尚未完成也不重新选源。不同剪辑/广告切除会导致时间轴不一致，不把另一源的第N段拼入当前流。中途持续慢源标记为下次选择不优先，重新开播/手动换线时沿原生续播机制处理，不能承诺跨源精确无缝续播。

### 3.3 选线测真正的视频，限制起播开销

优先复用近期完整分片数据；没有足够样本时，最多两个候选并行。冷选线阶段总预算先取6秒、每候选最多4MiB；预算包含解析/清单/视频采样，并在排队前开始计时，不能让每跳各自重新获得6秒。

采集过滤后清单中的真实媒体分片，排除key、init、已明确识别的广告/占位内容。首次播放取起播附近，续播能获得可靠位置时取该位置附近；极短分片可组合两段。完整下载才有可计算的r；样本过大、超时、取消只记“未完成/低置信”，不能假装测到实际码率，也不使用统一2.5Mbps等阈值代替影片自身需求。

在预算内已有媒体有效且r≤0.7的候选，就可选用并取消其他试探，不等最慢候选；目标是有播放余量，不是证明全网绝对最快。并发竞争会降低观测值，结论只表示当前负载下是否足够；多用户负载时减少额外探测。选中的完整采样分片可供首次播放复用，避免同一分片下载两遍。

全部候选未达到余量时，使用仍可播且证据最好的线路；超时不等于永久死源。所有候选确实不可播才报无可用源。历史选择不再可信时后台更新，不能以单次失败全局封掉整个资源站。

跨源候选沿用本地严格同片/季/集匹配；海量库单源记录不强行扩成多源。全网回源只在明确失效、已有候选不足时开启有界后台搜索，不恢复“无匹配拿第一条”的旧错误。

### 3.4 同源、小窗口、可取消的预取

第一版只对普通VOD完整TS分片开启；MP4、live/LL-HLS、BYTERANGE/fMP4、AES或PNG伪装先沿旧路径，逐类测试后再扩。当前已实测的量子普通TS属于候选适用范围；每个分片仍按实际头部与清单确认，不能只看后缀。

初始prefetch_ahead=1。在当前前台分片的源站读取结束后，根据该上下文已登记清单及当前位置预取下一段；完成后不递归再抓下一段，直到播放器消费推进。仅在代理预取开启且已证实适用的会话中，所选线路最多1个源站分片GET（播放器多个请求需并入/有界排队，不能叠加后台竞争）；关闭预取即移除该限制、保留原前台并发。全局最多2个预取下载；前台缺片永远优先，必要时取消纯投机任务。连续慢段、429或超时增加时暂停新增预取；恢复需新的有效样本。最大2段、累计12秒窗口仅作为后续实验上限，首版不启用，须先证实一段预取收益与网络余量。

初始内存预算：每会话缓存32MiB、全局新增缓存/在途预留128MiB、单预取段8MiB，缓存TTL60秒、无客户端请求15秒即取消纯预取。配额必须先预留、按实际读取更新并覆盖复制/转换的新增缓冲；无Content-Length也按流式读取计数。超过预取预算就停止预取，前台仍走原处理，不将“大分片”变成播放错误。不得将整个长视频缓存到磁盘。

缓存键包含已验证用户、播放上下文、线路、完整上游URL身份、请求头摘要、范围及转换身份；不跨用户共用。完整200/206的语义必须匹配，错误页、截断片和取消片不入成功缓存；拿到完整200不能直接冒充任意206。初版有Range/特殊处理的请求按兼容路径处理，不用不完整缓存拼接。

同一片的前台与预取合并为一次在途下载；用独立producer和等待者计数，单个等待者取消不传染其他等待者，无消费者且不是有效窗口预取时关闭上游。拖动后丢弃旧窗口，停止/断开后取消无人需要的任务并释放预留。不得由任意客户端u参数触发下载任意“下一段”；只从当前已授权清单登记的URL取预取目标，全部经SafeAsyncClient每跳及DNS/IP校验。

预取只增加NAS侧提前量，不会修改原生播放器的缓冲时长。若播放器自身已把相同分片并发预取，代理再做可能没有收益，串行限制还可能降低吞吐；先测原生请求时序，已存在有效并发时保留原前台行为并关闭代理预取，不强制串行。预取上线必须证明新增提前量且不妨碍前台。6秒提前量若遇到持续r=1.218的同类分片，算术上约4.6段就会耗尽；这个是假设序列的容量计算，不是实际播放器测试结果。

### 3.5 流式转发与直连的后续门槛

只有第一版选线+预取未达到目标，才在普通未加密、无需解包、完整对象的分片上试流式；保留SafeAsyncClient，先检查响应状态/媒体头，StreamingResponse在断开/异常时finally关闭上游。响应已发送后不能再返回新的502或把整段重试内容拼上去；只能结束失败响应，由经过验证的播放器重试。AES、PNG、Range等继续保留旧路径。

必须从原生播放器实际消费的飞牛域名/端口测试，而非只测内部UDS；不改nginx以“做出”流式收益。若网关/播放器仍整片缓冲，提前首字节不等于减少卡顿，不能宣称修复。

302直连仅在实测外网NAS上行成为瓶颈且源无需秘密请求头/服务器解密时评估。客户端网络可能比NAS更差；URL暴露、CORS、重定向头丢失及各端解码能力均需验，不作为本轮默认变更。

## 4. 验收标准（未执行）

| 层次 | 必测 | 通过条件 |
|---|---|---|
| 旧问题回放 | 首字节快但body慢、假200错误页、分片404、单源卡死 | 自动选择使用完整媒体证据；无最慢候选拖死；预算到点退出且资源关闭 |
| 选线入口 | Web/手机/TV的初播、手动首条/其他条、旧line+auto、重拉main、续播/拖动 | 新自动入口真正执行；旧line+auto继续原显式线路；手动不被覆盖；同会话线路稳定；无错片/错季/跨源拼段 |
| 缓存与取消 | 同片两个等待者、一个取消、seek、退出、并发用户、预算满 | 上游去重；另一个请求不受取消污染；旧预取停止；无跨用户命中/半片成功/连接泄漏 |
| 媒体兼容 | 普通TS正例；AES/PNG/Range206/fMP4/MP4负锚 | 普通TS优化路径确实被触发；其他类型明确沿旧路径并能播，不能以“未触发优化”冒充优化通过 |
| 权限与设备 | 匿名、非管理员管理、登出、跨用户、重定向到私网；官方三文件 | 原安全拒绝仍有效；每HTTP请求认证；官方二进制/manifest/nginx SHA保持 |
| 性能/体验 | 同片同端同网络旧/新交替；正常源与出现波动的源 | 有实际下载/播放器事件证据，见下列阈值，不以200或NAS低负载当通过 |

离线用可控服务生成正常、一次慢段、连续慢段、断流、忽略Range、错误长度、过期链接等真实HTTP情形，使用实际handler和SafeAsyncClient；不mock掉被测下载/取消/回退，只替换非本次范围的官方认证依赖。旧实现作为对照，故障用例必须能让旧版暴露问题。

真机至少覆盖本次影片及另一个来源影片，分别手机与TV，每端每种关键模式连续20分钟；同源旧/新交替，记录并发负载。目标：出现波动的对照组中缓冲总时长减少至少50%，首帧P95新增等待不超过2秒；手动固定线不得因自动测速增加等待。每轮只有少数开播样本时列出原始值，不声称已得到有统计意义的P95。先做20次可重复冷/热起播检查，再报告分位数。

服务器侧同时核r分布、缓存命中/浪费字节、源请求数、所有新增缓存/在途/转换缓冲合计≤128MiB配额及退出后任务释放，并另测整体RSS，不能把缓存配额等同进程总内存。无拖动连续20分钟时，采样和预取导致的额外源站字节目标≤实际消费字节的10%；频繁拖动按每次最多两段窗口的取消/释放验证，不拿该场景百分比掩盖泄漏。原生播放器可取得buffering/ready事件则用事件时长；取不到时明确依赖实际声画观察并标注测量限制。手机Wi-Fi、TV链路与外网分别验，不能互相替代。

若基线在测试窗口没有卡顿，不能认定新方案减少卡顿；保留候选，等自然波动窗口或受控回放补证。若两条可用源均持续r>1，结论是当前源供给不足，不能靠扩大缓存宣称解决；优先换可用源，必要时另行考虑本地完整媒体。

## 5. 发布与回退

1. 从当前加固真源开隔离分支；记录0.2.19.2恢复点；添加观测/选线/预取独立开关，默认可关闭。先回放入口及取消问题，再写功能，不把所有上游新增模块整包带入。
2. 上游首分片验活、跨记录选线与健康结构逐项移植；保留本地搜索总deadline、shield、精确匹配、用户隔离、SSRF与正式升级机制。每项有独立来源和回归。
3. 离线通过后构建独立FPK，仅在测试播放窗口用官方应用中心升级，不打断用户当前观看。先观测，再按单功能A/B启用选线、预取，最后组合；流式保持关闭。
4. 失败优先关闭新功能，回旧路径，不删除用户配置/历史/收藏；必须演练“已经有新会话及在途预取时关闭开关”，确认停止新预取、清理任务并保持有效请求语义。
5. 包级恢复沿已验证维护流程；不能假定fnOS允许版本降级。若拒绝降级，预备递增包版本的已知良好源码恢复包，经相同正式升级流程恢复；不卸载重装。
6. 每次部署后重新核载荷SHA、官方三文件、配置/历史/收藏及真实播放；验收通过才更新维护器可信树/last-good，并让自动维护识别本地变更，不被下一轮上游拉取覆盖。

## 7. Grok交叉分析后的取舍

Grok独立读源码、证据、RFC、hls.js与Media3，并在临时目录做两种假设播放器模型；未连接设备。双方一致：慢正文已被测到，但实际客户端缓冲/请求时序未知；流式不提升源带宽；同会话固定源；优先验证有界、可取消的预取。

采纳Grok的“一段串行预取”作为更保守初值，同时加原生并发负例门槛：若本来已经提前请求，额外预取可能没收益，不能称零伤害。模型中的卡顿秒数依赖理想化播放器和未知缓冲，不能写成飞牛实测。

以下建议经Codex复核后收紧，不直接照搬：

- `line+auto=1`历史链接也可能来自用户手动点第一变体，不能重新解释为自动授权；须有无歧义的新标识/上下文，旧链接保留固定线。
- 1.2秒截断采样不能取得本次2.118～7.257秒完整分片的r；预算耗尽只能记低置信，不能用于完整分片优选。主案采用有界完整采样及近期真实数据。
- “至少3段、r≥1.15、128KiB下限”是设计假设，不能只因能区分本轮两次数值就当已验证阈值。持续慢告警可结合多段加权r及失败率，但不据此中途跨源拼段；短分片也有EXTINF，不能一律丢弃有效短段。
- 客户端晚1秒请求下一段，不代表预取已经完成；慢片可能还要7.257秒。只有缓存实际完整、请求时命中，才能统计省下的等待；否则是共享在途下载，不计完整命中。
- AES/PNG转换后缓存和本地Range切片扩展不进入首版，避免一次引入多条新兼容分支。先测普通TS，其余保留既有处理。
