## 值得保留的经验

| 这次遇到的判断陷阱 | 下次应如何处理 |
|---|---|
| 看见许可限制，先认定只能购买或改程序 | 先检查该版本已有部署参数，再用实码和隔离运行验证含义；用户已经授权的可逆配置不重复索要相同授权 |
| API 声称 `enforced=false`，实际仍在限制 | 追踪实际消费分支并回读 capabilities；本版 cloud→grace 仍执行门禁 |
| 返回 enterprise / `features=*` 就声称全功能可用 | 本地判定、外部服务配置、客户端能力、真实业务结果分开验收；不把本地模式说成官方购买权益 |
| 修改 `.env` 后就认为生产生效 | 先核启动环境优先级、Compose 渲染及 image ID；重建后从运行中的服务回读 |
| 只顾目标开关，漏掉相邻行为变化 | 同步评估用户注册、AI共享策略、存储上限；本次关闭注册是保持原有有效访问边界，不能固化为所有部署都这样改 |
| 大 bundle 的 REA 请求返回了结果，就算解析完成 | 看 parsed/skipped/partial 和预算；保留失败覆盖，再从内嵌 source map 定位作者模块，记录选择范围 |
| source map 能恢复 TS，就称取得完整开源仓库 | 保留原始 bundle/source-map/恢复文件哈希，明确它是发布物携带的源码映射，不推定仓库完整性或开源许可 |
| 旧源码注释、官网宣传比实际路由更可信 | 相同版本实际分支优先；官网、注释和实现冲突需保留证据，并注明未验证的云产品是否真实提供 |
| 聊天 AI 能用，所以 AI 搜索也应可用 | 沿每个模块检查真实配置解析链；本版聊天可读 DB，搜索只读环境 provider |
| 浏览器存在 MediaRecorder，就认为录音可用 | 在用户实际入口检查 secureContext/getUserMedia/权限；HTTP 安全上下文是独立限制 |
| 数据库备份等于全应用可恢复 | 同时覆盖 WAL、一致性、独立正文/附件/版本和持久密钥，校验归档与还原 DB；没启动恢复应用就不声称完整恢复演练通过 |
| 隔离验证通过，就写成生产功能全部可用 | 分列静态、隔离、生产回读和用户端到端证据；门禁错误变成缺 provider，只证明跨过门禁 |
| CLI 授权刷新失败，推断应用或设备不可维护 | 限定故障在该 profile/通道；不猜 token、不循环登录。已有授权 SSH 与原 Compose 可继续维护，并保留应用中心归属 |

## 不作为通用模板的做法

- `LICENSE_ENFORCEMENT=disabled` 是这版程序已验证、用户授权的个案配置，不是任何 OK笔记版本的默认修复。
- 临时维护凭证只用于当次最小状态验收；不把签发 JWT 的实现打包成日常登录脚本。
- 不依据旧记忆地址自动接模型服务，不为“全开”擅自绑定邮箱、发送真实内容、创建公网入口或购买服务。
- 不把含密钥的备份、完整配置、用户数据或原始闭源程序证据推到 Git。
- 不恢复整份旧 `.env` 来回退两个字段，避免覆盖后来改动和已轮换密钥。
