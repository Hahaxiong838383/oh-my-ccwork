## 经验教训

### 1. 状态字段必须由业务记录驱动

只在设备表上保存 `FLASHED` 无法证明烧录真实发生。正确做法是先写入不可修改的烧录通过记录，再允许设备进入 `FLASHED`；直接修改设备状态必须被控制器拒绝。

### 2. 失败记录和成功记录具有同等审计价值

烧录失败、测试失败不能覆盖或删除。失败记录保留原因和上下文，重试产生新的尝试次数，便于定位批次、工位、工具或版本问题。

### 3. “当前结果”必须由完整历史派生

同一测试可以多次执行。界面显示每项最新结果，但质量判断必须读取全部记录并按时间确定最新一次，不能维护一个容易漂移的独立状态字段。

### 4. 自动化数据只保存引用和脱敏摘要

ERP 保存模板版本、摘要、结构化测量值和 MES/QMS 日志引用，不把可能包含设备凭据、调试日志或敏感原始数据的完整文件直接写入业务库。

### 5. 阶段闸门必须落实到界面

六项全部通过后，工作台只显示“等待 M2.3”，不提供质量放行或入库按钮。阶段边界不能只写在计划文档中，也必须体现在用户可操作范围内。

### 6. 部署验收要同时证明正向和负向

本阶段同时验证了失败烧录后状态不推进、成功重烧后自动推进、未烧录禁止测试、记录不可修改、失败后复测恢复，以及全新浏览器正常路径控制台 0 错误。

### 7. 阶段授权必须覆盖源码、部署、数据库和界面

一次后续执行曾在未获得川哥启动指令时提前生成并部署 M2.3。纠正时不能只删除本地文件：必须恢复 Git 工作区、同步服务器到 M2.2 提交、让迁移删除孤立 DocType/Page，并检查导航和数据库均无 M2.3 残留。阶段闸门必须在每次继续开发前重新核对用户最后指令，不能用“已经写完”倒推“已经授权”。

回退过程中还暴露了 Frappe 的迁移顺序：孤立 Page 先被删除，`after_migrate` 后执行；如果 Workspace Sidebar 仍引用已删除 Page，导航保存会触发链接校验失败。回退前应先移除待删除页面和对象的导航引用，再重跑迁移。

本次真实回退再次复现了该错误，说明仅在文档中规定“先清导航”不够。M2.2 的 `after_migrate` 钩子现在会在保存侧栏和 Workspace 前主动剔除 M2.3 的 Page、质量凭证和库存凭证入口，使目标阶段代码本身具备可重复回退能力。浏览器验收也必须清空本地与会话存储；复用旧存储状态会短暂显示已删除页面，不能据此判断服务器仍有残留。
