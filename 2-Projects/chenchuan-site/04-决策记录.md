## AI 雷达页首访阻塞刷新（2026-06-30）

<!-- type: fix -->
<!-- status: 已部署验证 -->
<!-- scope: 前端 / Next.js App Router 缓存 / 首屏刷新 -->
<!-- files: src/lib/radar/index.ts, src/lib/radar/aihot.ts, src/components/layout/Header.tsx, src/components/home/Hero.tsx, .env.example -->
<!-- related: AI 前沿资讯雷达 -->

### 现象

川哥反馈「AI 前沿资讯雷达」第一次进入时不会自动刷新到最新新闻，常需要再刷新一次。

### 排查过程

1. 直接请求上游 `https://aihot.virxact.com/api/public/items?mode=all&take=10`，确认 2026-06-30 仍有当天最新数据。
2. 请求生产 `https://my.chenchuan.cc/radar`，响应头仍显示 `x-nextjs-cache: HIT`、`x-nextjs-prerender: 1`、`cache-control: s-maxage=900, stale-while-revalidate=31535100`，说明生产仍是 ISR 预渲染版本。
3. 本地 `npm run build` 确认当前代码里的 `/radar` 已是 `ƒ /radar` 动态渲染，6 月 25 日的退出 Full Route Cache 修复在代码层成立，但生产未体现。
4. 继续检查发现 `src/lib/radar/aihot.ts` 全量新闻 fetch 使用 `next: { revalidate: 900 }`，即使页面动态，也仍可能在 Data Cache 过期后的首个请求返回旧数据并后台再生。
5. `/radar` 导航入口使用默认 `<Link>` 预取，静态/缓存状态下可能提前取到旧 RSC payload，点击时直接展示旧内容。

### 根因

这是多层缓存叠加问题：生产仍在跑 ISR 预渲染页；即使部署了动态页，底层 `fetch next.revalidate` 也有 stale-first 语义，叠加 Link 预取后就会出现「第一次进入旧、刷新后新」。

### 决策

**选择**：全量新闻不用 Next Data Cache，改成应用内阻塞式服务端缓存。

**理由**：雷达页的心智是「进入即看到最新一轮」。过期后的首个访问应该阻塞刷新，而不是先返回旧数据再后台更新；同时不能每个用户请求都全量打上游，所以用进程内单飞缓存控频。

### 改动

- `src/lib/radar/aihot.ts`：允许全量新闻拉取使用 `cache: 'no-store'`，绕开 Next Data Cache。
- `src/lib/radar/index.ts`：新增 `RADAR_FEED_CACHE_TTL_SECONDS` 控制的进程内缓存；缓存过期时首个请求阻塞刷新，并用单飞锁合并并发刷新。
- `src/lib/radar/index.ts`：刷新失败且已有旧数据时回退上一份可用数据，但 `ok=false`，前端可诚实展示「信源同步中」。
- `src/components/layout/Header.tsx`、`src/components/home/Hero.tsx`：对 `/radar` 入口显式 `prefetch={false}`，避免点击前拿到旧 RSC。
- `.env.example`：记录 `RADAR_FEED_CACHE_TTL_SECONDS=300`。

### 验证

- 本地 `npm run build` 通过，构建路由表中 `/radar` 保持 `ƒ /radar`。
- 生产 `/var/www/chenchuan-site` 精确同步 5 个运行文件后，远端 `npm run build` 通过。
- 仅重启 PM2 `chenchuan-site`；`p003-voice` 与 `kidshub-voice` 未动。
- 公网 `https://my.chenchuan.cc/radar` 返回 `cache-control: private, no-cache, no-store, max-age=0, must-revalidate`，不再出现 `x-nextjs-prerender: 1` / `x-nextjs-cache: HIT`。
- 公网首屏显示 `上次同步 UTC+8 06-30 22:10`，新闻列表已是 6 月 30 日当天数据。

### 部署记录

- 生产目标：`chenchuan-site:/var/www/chenchuan-site`，PM2 进程名 `chenchuan-site`。
- 回滚备份：`/var/www/chenchuan-site-backups/radar-refresh-20260630-220746`。
- 第一次 `rsync --relative` 源路径用绝对路径，误在远端生成 `/var/www/chenchuan-site/Users/...`，导致构建扫描到错误目录并报 `Cannot find module './types'`。
- 处理：立即删除远端临时 `Users/` 目录，改为逐文件精确 rsync 到目标路径；随后本地与远端 5 个运行文件 sha256 完全一致。

### 后续风险

- 进程内缓存重启会丢，重启后的首访会重新全量拉取，符合预期。
- 如果未来 PM2 开多进程，每个进程各自缓存，会放大上游请求；访问量上来后再升级为 Redis/SQLite 文件缓存。

### 经验教训

- 个人站真实 Next 入口是 `/var/www/chenchuan-site` + PM2 `chenchuan-site`；`/opt/kidshub-personal` 是 `/kidshub-ai/` 后端，不要混用。
- 生产 rsync 禁止偷懒整目录推送；必须先 dry-run，并排除 `data/`、`.env*`、`.next/`、`node_modules/` 等持久化/运行态目录。
- `rsync --relative` 只能从项目根内的相对锚点使用；绝对源路径会把本机目录结构复制到远端，构建器可能误扫进来。
- 部署后验证不能只看页面 200；实时页必须看响应头、路由动态性、首屏同步时间、最新新闻日期四件套。

## AI 雷达页退出整页 ISR 缓存（2026-06-25）

<!-- type: fix -->
<!-- status: 生效中 -->
<!-- scope: 前端 / Next.js App Router 缓存 -->
<!-- files: src/app/radar/page.tsx, src/lib/radar/aihot.ts, src/lib/radar/index.ts -->
<!-- related: AI 前沿资讯雷达 -->

### 现象

川哥发现「AI 前沿资讯雷达」最新文章仍停在 6 月 22 日，怀疑资讯没有更新。

### 排查过程

1. 直接请求上游 `https://aihot.virxact.com/api/public/items?mode=all&take=10`，确认上游已有 2026-06-25 最新数据。
2. 请求生产 `https://my.chenchuan.cc/radar`，HTML 内也能抽到 2026-06-25 的实时资讯和理论雷达日报。
3. 检查响应头发现 `x-nextjs-cache: HIT`、`x-nextjs-prerender: 1`、`cache-control: s-maxage=900, stale-while-revalidate=31535100`。
4. 对照 Next.js 15 文档：`revalidate` 会走 Full Route Cache / ISR，过期后的首个请求会先拿旧 HTML，同时后台再生新页面；Dynamic API（如 `headers()`）可退出 Full Route Cache，但不影响 Data Cache。

### 根因

`/radar` 使用 `export const revalidate = 1800` 做整页 ISR。长时间没人访问或缓存命中时，用户可能先拿到旧的预渲染 HTML，造成「最新文章停在旧日期」的观感；上游数据源本身没有停。

### 候选方案

| 方案 | 做法 | 优点 | 缺点/风险 |
|------|------|------|----------|
| A. 保留整页 ISR | 继续 `revalidate = 1800` | 服务器压力最低 | 首个访问者可能看到旧页面；不适合“实时雷达”心智 |
| B. `dynamic = 'force-dynamic'` | 每次请求动态渲染，并强制所有 fetch no-store | 页面绝不旧 | 会绕开 Data Cache，每次访问都可能全量打上游，风险过高 |
| C. Dynamic API 退出 Full Route Cache | 页面里 `await headers()`，保留 `fetch(... next.revalidate: 900)` | 页面壳每次新渲染，数据层仍 15 分钟缓存 | 比纯静态略多服务器渲染成本 |

### 决策

**选择**：方案 C — 用 `await headers()` 退出 Full Route Cache。

**理由**：雷达页的产品承诺是“实时输出”，整页旧缓存比服务器多一次渲染更伤信任；但上游 `aihot` 聚合一次约 1600+ 条，不应每次访问都全量抓取，因此保留 `src/lib/radar/aihot.ts` 里的 15 分钟 Data Cache。

**放弃的方案**：
- 方案 A：继续 ISR 会复现“第一位访客看到旧页”的体验问题。
- 方案 B：过度修复，可能把访问流量直接放大成上游 API 压力。

### 改动

- `src/app/radar/page.tsx`：移除 `export const revalidate = 1800`。
- `src/app/radar/page.tsx`：引入并调用 `await headers()`，让 `/radar` 成为 request-time dynamic route。
- `src/lib/radar/aihot.ts`：未改动，继续用 `next: { revalidate: 900 }` 控制上游数据缓存。

### 验证

- `npm run build` 通过。
- 构建路由表中 `/radar` 从静态 ISR 变为 `ƒ /radar` 动态渲染。
- 生产侧手动请求已观察到 2026-06-25 实时资讯；本次代码修复用于防止后续再次出现旧 HTML 首屏命中。

### 什么条件下该翻这个决策

- `/radar` 访问量上升到服务器渲染成本明显不可接受。
- 上游数据源提供更适合的增量 API 或服务端持久缓存层。
- Next.js 缓存语义变化，Dynamic API 不再是“退出 Full Route Cache、保留 Data Cache”的推荐方式。

### 教训

实时情报页面不要只看数据源是否新，还要检查 Full Route Cache / Data Cache / CDN 三层缓存；`stale-while-revalidate` 会让“过期首访拿旧页”成为预期行为，不是上游挂了。

## 视频库迁移后 404 与加载优化（2026-07-02）

<!-- type: fix -->
<!-- status: 已部署 -->

### 现象

个人站迁移到韩国节点后，`/videos` 页面能打开，但视频没有预览，也无法播放。

### 根因

公网 DNS `my.chenchuan.cc` 当前命中 `aliyun-kr`（8.213.134.133），该节点 `/var/www/chenchuan-site/media` 目录迁移时为空；`/videos` 页面引用的 19 个视频都在 `/media/...mp4` 下，导致资源 404。

### 修复

1. 将香港源站 `chenchuan-site:/var/www/chenchuan-site/media` 同步到韩国节点 `aliyun-kr:/var/www/chenchuan-site/media`。
2. 韩国节点补 Nginx fallback：`/media/` 优先读韩国本地，缺失时回源香港 `8.218.26.17`，避免后续漏同步直接 404。
3. 修正同步后部分目录权限为 `700` 的问题：目录统一 `755`，文件统一 `644`，否则 Nginx worker 无法进入目录，会误走 fallback。
4. 前端降低首屏视频并发：`/videos` 仅前 4 条 `preload="metadata"`，其余 `preload="none"`；首页视频区仅前 2 条预加载。保留 `poster={video.thumbnail || undefined}` 扩展位。

### 验证

- `npm run build` 本地通过。

### 排查过程

- 韩国机 Node.js 直连报 `UND_ERR_SOCKET other side closed`；curl HTTP/1.1 为空回复，HTTP/2 为 `PROTOCOL_ERROR`。
- `/etc/hosts` 仍钉死 2026-07-02 的火山 CDN 节点 `115.191.7.64`，但上游 GSLB 已轮换节点。
- 通过阿里 DNS 与 Cloudflare DoH 从韩国解析候选 IP，按真实 TLS hostname 探测，`43.159.98.107` / `43.159.99.102` 均返回 HTTP 200。
- 修复前 aihot 最新归档停在 2026-07-12 02:19（北京时间）。

### 根因

为规避早期 GeoDNS 分配到坏节点，运维层将单一 CDN IP 永久写入 `/etc/hosts`；该 IP 退役后，固定解析反而绕过了上游 CDN/GSLB 的节点轮换。同时应用层 fail-soft 吞掉了最终异常，页面总数健康检查又被归档兜底蒙蔽。

### 候选方案

| 方案 | 做法 | 优点 | 缺点/风险 |
|------|------|------|----------|
| A. 再手动更换固定 IP | 把 hosts 改成当前可用节点 | 最快 | CDN 下次轮换会再次失效 |
| B. 本机健康选路 | 独立 DoH 解析候选 IP，逐个验证 TLS + API 内容，自动更新受管 hosts | 不需控制上游域名，避免选中对韩国不可达的边缘节点 | 多一个轻量 cron，需保留回滚和日志 |
| C. 阿里 GTM / Cloudflare Load Balancing | 用自有域名建代理入口和健康池 | 托管监控与自动切换 | 我们不控制 `virxact.com`，需另建反向代理/证书/访问控制，增加费用和中间依赖 |

### 决策

**选择**：方案 B——韩国机本地健康选路。

**理由**：当前只有一个服务器消费该第三方 API，无需为不属于我们的上游域名新增一层公网代理。本地选路可同时验证“韩国可达 + TLS 证书正确 + API 真有数据”，比只看 ping/TCP 更准确。

**放弃的方案**：

- 方案 A：只能暂时止血，会复刻本次故障。
- 方案 C：当多服务器/多业务共享该代理，或已有 Cloudflare Worker/Alibaba ESA 统一出口时再考虑。

### 改动

- `scripts/aihot-endpoint-refresh.sh`：每 10 分钟从 AliDNS + Cloudflare DoH 获取候选，用 `curl --resolve` 校验真实 SNI/API JSON，只在节点变更时原子更新 hosts，保留每次备份。
- `scripts/radar-health.sh`：从“只数页面归档”升级为页面 + aihot 分源状态机，异常/恢复分别通知。
- `aihot.ts`：最终重试失败写 PM2 日志，按5分钟键级冷却，保留 fail-soft。
- `index.ts`：每轮写入 `data/radar-source-health.json`，保留两个上游的条数、状态和最后成功时间。

### 验证

- 本地与韩国节点 `npm run build` 均通过，两个 shell 脚本 `bash -n` 通过。
- 隔离 hosts 副本演练：自动从失效 `115.191.7.64` 切到 `43.159.98.107`。
- 生产恢复：`aihot=2000`、`yuweiwan=593`，两源 `ok=true`；热层继续 5000 条。
- 公网 `/radar` HTTP 200，已出现 2026-07-13 当日 aihot 资讯；手动运行分源健康检查返回 `PAGE=OK / AIHOT=OK`。

### 什么条件下该翻这个决策

- aihot 提供稳定官方域名/专用 API endpoint，不再需要侧边节点选路。
- 个人站扩展到多节点共享同一上游代理，届时改用自有域名 + Cloudflare/Alibaba 托管负载均衡。
