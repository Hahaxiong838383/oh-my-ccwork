## 三、KidsHub AI：升级原小可项目

保留原链接 `/work/ai-hardware-voice-prototype`，避免已有分享、视频关联与搜索入口失效。

### 项目卡拟文案

标题：KidsHub AI｜小可与成长世界

副标题：让孩子更容易开口，也有再次回来的理由。

问题：读写台需要持续使用的理由；等待唤醒、重复说话和缺少连续性的交流，也会消耗孩子的兴趣。

方案：将小可伙伴、可纠正的记忆与成长玩法结合，以 Rust 实时全双工语音基座支撑低延时连续对话，并用自然连说降低开口门槛。

进展：成长玩法已有真机验证，记忆与人格支持追溯和纠正，自然连说完成专项端云验收；各模块按各自发布阶段推进。

首页技术标签建议：Android / Kotlin / Godot / Rust。

可见技术方案行：Android/Kotlin 管设备与语音生命周期，Godot/GDScript 呈现成长世界，Rust Game Runtime 管进度与奖励；Rust 语音引擎经 LiveKit/WebRTC 承接实时对话。

### 详情页拟文案

「用户需要什么」

围绕孩子在读写台前的日常使用，我关注的不只是能否完成一次问答，而是孩子是否容易开口、交流能否接续、再次回来时是否有熟悉感和新的期待。家长关心的则是设备是否容易绑定、使用是否可管理，以及产品能否持续维护。

「产品判断：把再次使用的理由做进体验」

我把每日欢迎、奖励反馈、七日航线与生态缸组织成成长玩法，让参与过程有可见的积累。设备根据在场状态累计有效进度，离开时暂停、返回后继续；钱包、奖励和成长状态支持中断恢复，并通过回执避免重复发奖。这些设计服务于持续参与，不把在场时长解释为注意力或学习效果。

「小可：关系能够延续，也允许被纠正」

小可的记忆从单次聊天记录向持续关系演进：兴趣有真实原话作为依据，称呼和关心事可以更新，不再喜欢的内容能够撤回，约定与重逢可以成为后续交流的线索。人格与语音风格提供不同表达方式，变化保留来源、快照与回滚机制。我关注的是让 AI 更懂用户，同时避免一次误解被固化为长期标签。部分风格能力仍按灰度开放，当前不将设备或账号隔离表述为家庭多人声纹分人记忆。

「自然连说：交互适应孩子，而不是让孩子迁就流程」

孩子可以直接说“小可小可，为什么恐龙灭绝了？”，不用先等唤醒反馈再重新说问题。one-shot（唤醒词和问题连着说）通过短时音频预存与首句完整提交，衔接后续连续对话；超出处理范围时提示重说，能力不可用时回到普通语音流程。核心链路已完成专项验收，仍待与成长玩法版本合包及后续发布验证。

「共同语音基座：低延时的实时双向全双工对话」

基于 Rust 重写的 realtime voice agent，是小可与 MyJavis 共用的语音对话基座。它组织实时收听、流式回复和打断控制，支撑低延时、可接续的双向全双工对话体验。面向小可，我进一步把这套能力与儿童表达、设备状态和游戏界面协同结合。这里的全双工是对话系统能力，不等同于采用了原生端到端语音模型，也不承诺零延迟或所有打断场景已解决。

「技术架构：设备、表现、业务与 AI 服务分层」

Android/Kotlin 保留 Launcher（设备桌面入口）的硬件事件和语音生命周期管理；Godot/GDScript（游戏引擎与场景脚本）负责小可角色、生态缸与成长动画；Rust Game Runtime（本地游戏业务运行时）集中维护奖励、库存、进度和演出回执。各层通过 JSON 语义命令、事件与状态快照协作，界面消费结果，不另建一套发奖逻辑。

小可的设备服务与记忆后台采用 TypeScript、Node.js 和 Hono（轻量 Web 框架），通过 SQLite 保存结构化记忆及来源证据。设备上的成长存档由本地 StateStore 管理，与服务端记忆数据库是不同层次；游戏 Rust 运行时和实时语音 Rust Worker 也不是同一个组件。

「技术取舍：表现可以变化，奖励事实必须一致」

将业务写入集中到 Rust，先保存奖励与回执再播放动画，让中断后可以恢复演出而不重复发奖。保留原 Android 的硬件能力，把场景表现交给 Godot，减少重复实现底层设备控制；代价是跨层接口必须有一致的契约和版本管理。更新分为签名 APK（应用及核心逻辑）与 art-only PCK（美术资源包），后者不等于任意游戏逻辑热更新。

「实时语音采用什么技术」

Rust + Tokio（异步并发运行时）承接音频流与会话任务，LiveKit/WebRTC（实时音频传输）连接设备和语音服务。系统采用 ASR（语音识别）、LLM（语言模型）、TTS（语音合成）的流式级联，通过流水线重叠降低等待；用 Silero VAD + ONNX Runtime 检测语音活动，结合 EOT（语义判停）与打断状态控制，处理用户停顿、插话和后续接续。低延时来自传输、判停、模型响应和播放的共同优化，不把采用 Rust 本身当作性能提升的测量结论。

「one-shot 的实现链路」

设备单麦采集 → 有界内存预滚（暂存唤醒前后的声音）→ 有序 PCM（原始音频帧）上传 → 服务端完整性校验与首句提交 → 同房间切回 RTC（实时音频）连续对话。

关键不是仅仅识别出唤醒词，而是避免建连期间丢失问题前半句，也避免历史音频与实时音频被重复处理。超出缓存或处理预算时取消该次首句并提示重说；能力关闭时回到普通对话。该链路仍沿用前述专项验收与待合包发布的阶段边界。

「从体验原型到可维护产品」

产品已接入真实读写台链路，推进设备身份、家长绑定、运营配置、记忆管理以及应用与场景内容更新。成长玩法、记忆人格和自然连说分别具备阶段性实现与验证证据；这些成果不等同于已在所有设备上完成统一版本发布。

「我的角色与下一步」

我负责产品定义、交互取舍、AI 协同软件实现与验证推进；公司硬件、供应链与量产贡献按实际团队边界说明。下一阶段重点观察开口成功率、重复表达、主动回访、成长玩法持续参与，以及家长反馈，验证产品设计是否真正转化为持续使用价值。目前不公开声称留存或学习效果已经提升。

## 四、H 平台：新增团队 AI 产品案例

建议新链接：`/work/h-platform-ai-assistant`。

### 项目卡拟文案

标题：H 平台｜团队 AI 工作助手

副标题：连接长期记忆、工作知识与任务执行的 AI 工作助手。

问题：入口分散、反复交代背景、长任务结果难追踪，以及个人资料与团队共享边界不清，阻碍 AI 成为日常工作工具。

方案：以飞书为入口，支持用户接入自己的订阅或接口；将长期记忆、个人知识页、任务上下文与共享技能纳入统一 Agent Harness（智能体运行与治理框架），在个人隔离的环境中执行工作任务。

进展：已进入真实多用户运行，具备可管理记忆、任务前混合召回、跨引擎运行适配、长任务后台交付与恢复机制，持续完善使用反馈到改进的闭环。

首页技术标签建议：Agent Harness / 混合检索 / Node.js / SQLite。

可见技术方案行：Node.js + 飞书 WebSocket 接入；ai-memory 全文/向量召回、受预算控制的上下文装配、跨引擎 Harness、Bubblewrap 沙箱与 SQLite 持久交付。

案例导语：H 平台围绕“记得住、找得到、用得上、交付可跟进”设计 AI 工作助手。通过长期记忆与个人知识页管理、任务前混合召回、上下文筛选和跨引擎 Harness，将用户偏好、工作背景、技能与工具接入真实任务；以独立 Worker、受控并发和持久送达链路支撑持续使用。

### 详情页拟文案

「用户需要什么」

团队需要的不是再多一个聊天窗口，而是在日常工作入口里，能够接着背景处理事情、在等待期间看见进度、最终收到结果的助手。与此同时，个人凭据、记忆与定制内容应保持边界，团队能够复用有效方法而不覆盖个人修改。

「产品判断：先融入工作，再扩大能力」

我选择飞书作为入口，支持用户连接自己的订阅或模型接口，让文档、表格、日程等任务从熟悉的协作环境发起。个人空间与共享技能并存，授权成为可以接续的过程，而不是要求用户重新开始整个任务。

### 核心设计亮点：记忆、知识、上下文与运行机制

「长期记忆：把保存、索引和实际使用分开验证」

H 平台在任务结束后由网关触发记忆提炼，围绕明确表达的偏好、决定、项目事实、待办和可复用结果积累工作背景，并与 Agent 主动写入互为补充。记忆内容通过知识页保存，由 ai-memory 的 SQLite 索引和向量能力支持检索；人格、工作约定、项目记忆与常驻偏好各有职责，避免不同载体无边界地重复维护同一事实。

我把“内容已保存”“最新版本已建立检索索引”“相关内容已进入后续任务”视为不同的验证环节。页面更新后显式补算向量、同步时去重并防止导出内容循环回灌；抽取失败与“没有值得记住的内容”分开记录，防止系统故障被当作正常的空结果。

「记忆与知识页管理：用户可以查看、修正和决定保留多久」

用户能够在后台创建、查看、编辑和删除自己的知识页，按事实、规则、决定、经验教训分类，并管理短、中、长期属性以及到期清理。人工分类受到保护，不会被后续自动分类随意覆盖。修改经操作队列送回对应用户的实例执行，并返回实际处理结果；对有原生记忆源的页面，同步维护源内容与检索侧，避免后台修改后又被旧版本覆盖。

当助手人格配置与长期偏好出现矛盾时，系统检测候选冲突并交由用户裁决，保留被取代的内容用于审计；执行前再次核对原文，若用户已修改则重新检测，避免按过期判断覆盖新内容。个人知识页与团队共享技能分别管理，不将共享技能等同于开放个人记忆，也不声称已自动索引所有企业文档。

「上下文召回：由程序触发，结合当前任务与追问背景」

平台在任务执行前主动检索该用户的项目记忆与常驻偏好，不只依赖模型是否想起调用工具。通过 FTS5（全文检索）和向量检索寻找相关知识，并结合当前问题与上一句用户原话处理简短追问；再进行词面相关性重排、空模板过滤、正文摘录、近期历史去重和敏感信息清理，形成供当前任务使用的背景。

召回内容有条数、篇幅和超时预算，避免把整个知识库塞进上下文。检索失败不阻断主任务，但保留状态供排查；私聊与群聊分别设置注入开关，群聊默认不注入个人记忆。这里的预算控制针对检索注入片段，不夸称掌握闭源引擎的全部上下文窗口与压缩行为。

「Agent Harness：让不同引擎遵守共同的工作契约」

Harness 是围绕模型构建的执行与治理框架。H 平台将人格、工作规则、Skills（可复用工作方法）、MCP（工具连接协议）、记忆作用域和任务生命周期接到各引擎的实际运行入口。通过 AGENTS.md 托管块和相应引擎的运行时追加机制刷新规则，并保留用户自写内容；工具按实际兼容性接入，不把配置文件存在当作能力已经生效。

Grok、Kimi 与其他适配引擎在 Runner 内处理协议和入口差异，在平台层共享任务分类、队列、权限恢复、后台交付和结果确认规则。记忆捕获与任务前召回由平台生命周期流程触发，不依赖所有引擎拥有相同的原生 Hooks（生命周期回调）。这体现的是跨引擎产品行为的适配与治理，而非自行重写各模型或宣称所有引擎能力完全相同。

「运行时优化：减少启动、同步和维护对任务的干扰」

消息接入与长任务 Worker 分开管理，通过公平调度和受控并发承接多用户任务。连接分批并发建立，记忆同步与摘要等后台工作延后、错峰；镜像按内容哈希判断是否需要推送，查询向量模型常驻以减少冷加载。将这些工程选择纳入产品体验，是为了减少额外等待与资源争用。

维护时通过配置热加载、选择性重启、等待在途任务结束及临时暂停派发降低干扰；模型连接异常尽量在派发前反馈。当前不将这些机制描述为运行中任务可任意跨进程迁移，也不承诺升级完全无感。

「可观测与可纠正：让配置、召回和执行有据可查」

通过上下文装配报告、记忆检索状态和任务送达记录，检查当前引擎接入了哪些规则、技能与记忆能力，区分“配置未接入”“检索异常”和“执行或交付失败”。装配报告反映可观测的输入与接入状态，不冒充闭源引擎最终发送给模型的完整 Prompt，也不能证明模型一定采纳了某段内容。改进仍由建议、人工确认、应用与回滚组成，保留人的控制权。

「持续使用的基础，是交付可跟进」

H 平台将长任务拆成可感知的进度与后台交付过程，用持久待发送队列、送达回执与重启恢复降低中断风险；在执行前召回相关记忆，减少重复说明背景。更新过程通过热加载、选择性重启和等待任务空闲减少干扰。产品目标是提高可靠性与使用信任，不承诺任务绝不丢失或发布完全无感。

「共享能力，但保留人的控制权」

平台支持共享技能与个人定制共存，保护个人修改。系统改进按建议、人工确认、应用与回滚推进，让能力可以演进，同时保留使用者的判断权和恢复路径。

「技术架构：接入、执行、记忆与交付分开管理」

平台采用 JavaScript ES Modules + Node.js，以飞书官方 SDK 的 WebSocket 长连接接收消息与事件；独立 runner-worker（任务执行进程）和公平调度承接长任务，让消息接入与任务执行分开管理。Bubblewrap（Linux 进程沙箱）约束租户工作目录与工具执行环境，个人凭据、工作文件和记忆按用户隔离。

任务及待发送结果通过 SQLite WAL（预写日志）与 Delivery Outbox（持久待送达队列）保存，收到送达回执后更新状态，为重试和恢复提供依据。记忆能力由 ai-memory 组件提供，结合 FTS5（全文检索）和向量检索，在任务执行前召回相关背景；通过 Ollama 运行嵌入模型生成查询向量。这里的平台服务是 Node.js，不因接入独立记忆组件就描述为 Rust 平台。

「技术取舍：执行结束，不等于用户收到结果」

我把任务执行状态与结果送达状态分开管理：模型完成工作后，结果先进入可恢复的队列，再核对发送回执；同时把个人执行环境与团队共享技能分层。这样能降低重启、网络波动和多用户并发造成的干扰，但仍需管理权限、重试和恢复边界，不承诺绝不丢任务。

「我的角色与当前阶段」

独立完成产品定义与软件开发，一个人 vibe coding 完成，没有团队，AI 是我的手脚。平台已进入真实多用户运行，下一步重点观察首次任务完成、重复使用、结果送达与异常恢复，以及共享技能的实际复用情况。目前不声称已经取得量化的人效或留存提升。
