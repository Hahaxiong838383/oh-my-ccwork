## GEO 搜狐号新版后台登录判定与跨机会话接力（2026-08-28）

<!-- type: fix -->
<!-- status: 生效中 -->
<!-- scope: 后端 | 服务器 -->
<!-- files: services/geo-engine/media-bridge/adapters/sohu.py -->
<!-- related: GEO Media Bridge 托管平台登录 -->

### 现象

用户已在 Studio 浏览器完成搜狐登录，但 GEO 面板持续显示“待扫码登录”。虚拟机截图交互延迟高且无法稳定完成手机号、验证码和滑块操作。

### 排查过程

先确认真实操作链路是 `Air → SSH Studio → Studio Chrome → 临时反向 SSH → company-vm`，再从公司虚拟机通过 CDP 同时读取 Studio 页面。搜狐通行证页显示账号已登录，搜狐号页面实际已进入 `/mpfe/v4/contentManagement/first/page`；适配器 `is_logged_in()` 仅接受旧 `/mpfe/v4/main`，因此误判。

### 根因

搜狐号新版创作者后台路由发生变化，而桥端登录判定把旧路由写死为唯一成功条件。

### 候选方案

| 方案 | 做法 | 优点 | 缺点/风险 |
|------|------|------|----------|
| A. 继续虚拟机截图交互 | 在 Headless 浏览器画面中完成全部登录 | 不需要会话迁移 | 延迟高，验证码和滑块可靠性差 |
| B. 复制完整浏览器 Profile | 将 Studio Profile 整体复制到虚拟机 | 实现简单 | 扩散无关凭据，跨系统 Profile 兼容性和指纹风险高 |
| C. 目标域会话接力 | Studio 完成人工登录，仅迁移搜狐域会话数据 | 轻量、可审计、凭据面最小 | 需要临时 CDP 隧道和平台路由兼容 |

### 决策

**选择**：方案 C，并同步扩展搜狐适配器的新旧后台路径判定。

**理由**：人工验证留在可视 Studio 浏览器，虚拟机只接收搜狐域 Cookie、localStorage 和 sessionStorage；迁移后可关闭源隧道，以最小凭据面获得持久登录。

**放弃的方案**：
- 方案 A：当前虚拟机交互延迟和裁切已证明不适合复杂验证；只有平台提供纯二维码且无需滑块时再考虑。
- 方案 B：完整 Profile 会携带无关站点数据，且 macOS→Linux 的浏览器存储兼容性不可控。

### 改动

- `services/geo-engine/media-bridge/adapters/sohu.py`：登录判定同时接受 `/mpfe/v4/main` 与 `/mpfe/v4/contentManagement`。
- 生产桥端先做文件级热修复并保留回滚点，再将同一修复和回归测试同步到组织仓 `main` Commit `7123c935ea35f0acc0b0b6f2973902d9a600467a`。

### 验证

- Studio 源页面：`/mpfe/v4/contentManagement/first/page`。
- 虚拟机目标页面：迁移后进入相同后台路径，适配器返回已登录。
- GEO：`/distribution/loginview?id=6` 返回 `logged_in=true`，账号 ID `6` 状态为 `active`。
- 关闭 Studio→company-vm 临时隧道后再次验证，目标账号仍保持登录。

### 什么条件下该翻这个决策

- 搜狐提供正式 OAuth、设备授权或可导出的长期令牌时，应改用官方授权协议。
- 平台登录状态不再由 URL 命名空间可靠表达时，应改为后台 DOM/API 双重判定。
- 会话迁移需要跨越多个不相关顶级域时，应引入独立凭据代理，禁止扩大 Cookie 复制范围。

### 教训

平台“账号中心已登录”不等于“创作者后台已登录”；登录验收必须读取最终业务后台 URL，并在断开源浏览器后复验目标 Profile。

## GEO 托管平台采用 Air 本机浏览器会话接力（2026-08-28）

<!-- type: arch -->
<!-- status: 生效中 -->
<!-- scope: 前端 | 后端 | 服务器 -->
<!-- files: services/geo-engine/geo_engine/distribution/external_login.py, services/geo-engine/geo_engine/server/api.py, services/geo-engine/geo_engine/server/dashboard.py, services/geo-engine/deploy/geo-kidshub.nginx.conf -->

### 现象

company-vm Headless 浏览器能维持渠道账号 Profile，但虚拟机交互延迟高、页面裁切，手机号、验证码、滑块等登录步骤难以完成。一次性截图控制可作兜底，但仍无法替代 Air 本机浏览器的完整交互体验。

### 根因

渠道登录状态必须最终落在 company-vm 的持久浏览器 Profile；同时，浏览器必须真正运行在 Air，不能把“从 Air SSH 操作 Studio”误判成“Air 本机浏览器”。纯网页受同源策略限制，不能自行读取第三方 Cookie，因此需要受控本地 CDP + Studio helper 完成最小会话迁移。

### 候选方案

| 方案 | 做法 | 优点 | 缺点/风险 |
|------|------|------|----------|
| A. Air 本机 Chrome + 受限接力 | Air 登录，Studio helper 迁移目标域会话 | 交互流畅、无需扩展、目标 Profile 可持久化 | 需要 Air→Studio SSH 与一次性 handoff |
| B. company-vm 截图控制 | 外部设备操作 VM 浏览器截图 | 登录态天然留在 VM | 延迟高、裁切和复杂控件体验差 |
| C. 完整 Profile/公开 CDP | 复制浏览器目录或长期开放调试口 | 实现直接 | 凭据面过大、跨系统不稳定、安全风险高 |

### 决策

**选择**：方案 A；平台原生二维码继续保留，方案 B 仅作兼容兜底。

**理由**：命令在 Air 本地终端执行，`open` 才会启动 Air 浏览器。Air 只把回环 CDP 临时反向转发到 Studio，helper 仅导出目标平台域 Cookie/localStorage/sessionStorage，经一次性 token 交给 company-vm 导入并验证；无需浏览器扩展，也不公开 CDP。

**放弃的方案**：
- 方案 B：保留但不作为推荐路径，主要用于 Air SSH/CDP 不可用时的简单扫码或低交互登录。
- 方案 C：完整 Profile 和长期公开 CDP 权限远超登录需要，禁止进入标准流程。

### 改动

- Dashboard 在一次性页面生成 Air 命令；命令先创建 `ssh -fN -M -S` ControlMaster 反向隧道，再启动 Air 独立 Chrome，最后复用同一 socket 执行 Studio `geo-login-relay`。
- Studio helper 自动识别目标平台登录成功，只导出目标域 Cookie/localStorage/sessionStorage，并 POST 到 token 绑定的 `/handoff`。
- Media Bridge 私有 `/login/import` 导入 company-vm 持久 Profile并访问发布页验证；跨域、超量和畸形状态 fail-closed。
- Nginx `/connect/` 保持无 Basic Auth、无 access log、不注入 GEO API Token，请求体上限为 512 KB；截图控制仍保留为兜底。

### 验证

- company-vm 定向测试 `39/39`，GEO 全量测试 `96/96`；生成命令通过 `zsh -n`。
- 生产页面包含“先隧道、后 Air Chrome”命令；跨域 Cookie handoff 返回 `400`，桥无密钥返回 `401`，GEO/媒体桥服务均 active。
- 组织仓 Commit `c0e78f196fb0696b05b2d8a4fade9aae0c2d0ee4` 已部署，当前 Release 与回滚点已记录。
- 川哥已在 Air 本地终端执行新页面生成命令，确认 Air 本机 Chrome 正常打开且登录链路可用；真人验收通过，原“待验收”门禁关闭。

### 什么条件下该翻这个决策

- 平台提供正式 OAuth、设备码授权或企业级账号托管 API 时，优先迁移到官方授权协议。
- 需要多人同时登录同一账号、审计每个操作者身份或跨 GEO 实例共享会话时，进程内单机存储应升级为带主体绑定的持久会话服务。
- Air→Studio SSH 长期不可用，或平台明确拒绝 CDP 浏览器时，再评估签名本地 helper 或零信任远程浏览器，不扩大公开接口权限。

### 教训

- “在 Air 上操作”不等于“浏览器运行在 Air”；决定浏览器归属的是 `open` 命令实际执行的 shell。跨机会话接力必须先证明操作端、浏览器端、helper 端和目标 Profile 四个角色没有混淆。
- Web 页面不能替外部设备静默启动本地 SSH/Chrome；正确产品形态是清楚说明边界、提供可复制命令，并让用户在本地终端显式执行。
- 连接端口存在、单测全绿、服务返回成功都不能替代真人登录；涉及验证码、设备指纹和跨机浏览器的流程，最终门禁必须是真实账号的人机闭环。

## GEO PR #23 使用 Git Bundle 与不可变 Release 原子发布（2026-09-01）

<!-- files: deploy/company-vm/cutover-geo-engine-release.sh, /home/futurus/.config/systemd/user/geo-engine.service, /home/futurus/.config/systemd/user/media-bridge.service -->

### 现象

PR #23 已具备合并条件，需要在不触碰本地既有脏工作树、不向 company-vm 复制组织仓 Token、不中断已有账号会话和未决分发任务的前提下完成生产升级。服务器离线构建新 venv 时还缺少 `setuptools`，不能依赖临时联网安装。

### 根因

生产发布同时跨越私有 Git 权限、不可变源码、Python 运行环境、SQLite 迁移和双服务切换；直接在现网目录 `git pull` 或临时补依赖会让版本、凭据和回滚边界不可审计。

### 候选方案

| 方案 | 做法 | 优点 | 缺点/风险 |
|------|------|------|----------|
| A. Git Bundle + 不可变 Release | 本地隔离仓生成完整 Bundle，服务器构建新 Release/venv，候选端口验证后切 symlink | 不复制 Token、Commit 精确、可原子回滚 | 发布步骤较多，必须保存依赖资产和旧 Release |
| B. 现网目录直接 pull | 在当前 Release 中拉取并重启 | 快 | 污染不可变目录、失败时难判断源码与迁移状态 |
| C. 复制 GitHub Token 到服务器 | 服务器直接访问组织仓 | 后续拉取方便 | 扩大长期凭据面，不符合最小权限 |

### 决策

**选择**：方案 A；以 Git Bundle 传递完整提交历史，分别建立 GEO、GEO venv 和 Media Bridge 不可变 Release，候选验证通过后先停 GEO、再停 Bridge，切换三条 symlink，最后先启 Bridge、再启 GEO。

**理由**：该方案同时满足凭据最小化、Commit 可追溯、SQLite 迁移前置验证和秒级回滚。新 venv 缺 `setuptools` 时，不临时联网补包，而是复制已验证旧 venv、同步新 `geo_engine` 源码并重写 entrypoint，再用同版全量测试证明运行时完整。

**放弃的方案**：
- 方案 B：只有无状态服务、无本地数据库且现网目录允许漂移时才可重新考虑。
- 方案 C：只有服务器接入正式机器身份、短期凭据代理或只读 Deploy Key 后才可重新考虑，禁止复用个人 PAT。

### 改动

### 教训

不可变 Release 不只约束源码，还必须同时约束 venv、媒体桥资产、数据库迁移和服务启动顺序；“服务能启动”不足以判绿，必须补账号状态、单实例锁、数据库完整性、公网健康和回滚记录五类证据。
