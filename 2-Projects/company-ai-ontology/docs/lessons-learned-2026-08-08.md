# Company AI Ontology 阶段经验教训

## 公网看板与状态通道

1. 公网可视化不应改变 QNAP 的网络边界。复用 H 控制面的 HTTPS 与管理员认证，在 aliyun-hk 只开回环端口，由 Mini 维护到 QNAP LAN 网关的反向 SSH，比复用失效 FRP 或裸开公网端口更安全、也更容易回滚。
2. 状态探针必须是固定白名单，不是通用反向代理。QNAP 只代理五个健康路径；H 控制面再按字段白名单构造脱敏 DTO，拒绝非 loopback 状态 URL、上游重定向、超时和大响应。
3. “组件健康”与“业务完成”要分层显示。Knowledge Connector 容器已健康可以标绿，但试点文档分享权限、真实 ACL 正负验收、10 人 Canary、真实 P2、ERP 和社媒接管仍应保持灰色。
4. 公网页面验收不能停在 curl。最终同时验证了未认证跳转、认证后页面/API、敏感字段扫描、真实 Chrome 渲染、控制台零错误、无横向溢出，以及绿色 4 项/灰色 5 项的生产门禁表达。
5. 部署脚本自身也可能报假故障。本轮 h-control 重启后的首次 curl 碰到监听尚未恢复，随后进程、端口、Nginx、环境和日志均正常；应按前置检查验证真实状态，不因单次瞬时失败回滚健康服务。

日期：2026-08-08

## 阶段结论

公司 Bot、通讯录、CPA H 引擎和 Knowledge Connector 服务骨架已跑通，但“本地代码修复”“生产部署”“整库 Canary”和“正式导入”是四个独立阶段。产品研究部知识库只读审计发现的两个权限放大 P0 已在本地 `2026-08-08.3` 修复并通过 Connector/Agent Core 14/14，但 QNAP 仍运行 `2026-08-08.2`，正式导入继续禁止。

## 经验教训

### 1. 飞书授权是三道门

API Scope、通讯录数据范围和应用可用范围彼此独立。后台显示“权限已开通”不能证明人员可见，也不能证明员工能找到 Bot。验收必须分别调用真实 API，并用真实员工完成可见性测试。

### 2. 通讯录必须递归展开

顶层授权范围只是入口，不是完整组织树。本次 4 个入口实际展开为 83 个部门；若只同步入口部门，会形成看似成功但严重漏人的假阳性。

### 3. 身份同步不是员工能力

通讯录批量同步必须是后台服务作业，只允许专用服务身份和 HMAC 接口。员工对话身份必须明确 403，避免 Company Agent 被错误提升为通讯录超级管理员。

### 4. 最小字段和幂等优先

P0 的人员对象只需要任务派发所需字段。邮箱、手机号、私聊正文和私人属性既非必要，也会放大泄露面。重复同步必须 Upsert，不得重复创建。

### 5. 不自动停用“本轮未出现”人员

通讯录范围可能因管理员配置、接口波动或部门调整暂时收缩。当前阶段仅更新可见人员，不自动禁用缺席人员；后续应通过连续多轮缺席、离职事件或人工确认再停用。

### 6. App 可读不等于员工可读

公司知识 Connector 可以使用 App 身份建立索引，但回答员工问题时必须重新按员工、部门、项目和文档 ACL 过滤。没有 `Permissioned Evidence Package` 的内容不得进入 Company Agent 上下文。

### 7. 部署完成不等于当前版本验收

QNAP 滚动升级应先 Agent Core、后 H-Lite。每次升级后重新验证版本、健康、WebSocket、真实消息、Outbox、去重、权限负测和 `restart_count`；不能沿用旧版本的通过记录。

### 8. 传输包和生产凭据必须短命

部署包不得包含 App Secret、访问令牌或明文环境文件。临时包在本机、中转机和 QNAP 使用后均应清理；Git、记忆、日志和验收文档只保存 secret 指针与脱敏证据。

### 9. JSON 不应直接穿过 Compose 字符串插值

显式知识资源 JSON 在 `.env` 中合法，不代表经过 Compose YAML 插值后仍保持原样。本次容器因引号被解析而循环重启。结构化配置应使用 Base64 或只读配置文件传递，并在启动时严格解码校验。

### 10. 中文知识召回不能依赖整句匹配

Postgres `simple` 分词和整句 `ILIKE` 对中文自然问句召回不足。生产链路验收首次出现“ACL 正确但 Evidence 为 0”，最终通过英文标识优先、中文 2–4 字关键词匹配和结果排序修复。权限正确不等于召回正确，两者必须分别验收。

### 11. Grok Build 自定义模型必须使用独立别名

若 CPA 自定义模型与 Grok Build 内置模型同名，运行时会优先走内置 xAI 鉴权，而不是自定义 `base_url`。生产配置使用 `cpa-grok-4-5` 作为本地别名，再映射上游 `grok-4.5`；API Key 只通过 `env_key` 注入，不能写入 TOML、参数、日志或 Git。

### 12. 公司 QNAP 与家庭 QNAP 必须视为两个安全域

本项目中的 QNAP 只指公司局域网的 `prnas` / `prnas-pub`、`TS-X65`、当前地址 `192.168.61.18`。家庭 QNAP 不属于本项目，不能复用公司项目的目录、Compose、端口、卷、凭据、备份、恢复或验收结论。今后任何 QNAP 操作必须先核对用途、主机别名、型号、当前地址和项目根目录五元组；只说“QNAP”而目标不唯一时必须停止确认。

### 13. 骨架完整不等于企业本体一次建全

P0-S 固定了 13 个命名空间、类型基类、双时间、Provenance、Event Envelope、Data/Logic/Action 契约、版本和安全路径，但没有提前填满 ERP、市场、产品和组织全部语义。稳定契约先行可以减少后续重构；空对象和猜测字段先行只会把错误理解固化为兼容负担。

### 14. Compiler 与 Registry 必须承担治理而非只做目录

Compiler 需要检测悬空关系、继承循环、绕过 Gateway 的工具路径和破坏性兼容变更；Registry 需要记录 Proposal、批准、来源提交、迁移计划、唯一 active 版本、历史再激活和漂移状态。只有“能列出类型”不算 Ontology 治理基础设施。

### 15. 新架构不能制造第二套事实真源

P0-S 通过逻辑 Schema、View、版本列、Provenance 和 Domain Event 扩展现有 PostgreSQL 事实表，没有为了 V3 再复制目标、任务、权限和成果表。Qdrant、Redis 和控制面状态仍是可重建派生层；任何恢复和对账都回到 Postgres 与 Git Definition。

### 16. 地基验收必须证明重复执行与故障后仍成立

首次部署成功不足以证明地基稳定。本次同时验证了迁移重复执行、部署幂等、并发部署收敛、Registry 重启恢复、历史版本再激活、最小权限、漂移对账、生产备份验证和认证后公网状态。后续 Foundation 变更必须保持同一验收维度，不能只跑单元测试或看容器绿色。

### 17. 单资源 fail-closed 不能外推为整库安全

显式资源在 `1063004` 时安全跳过，只证明没有继承 ACL 的单资源路径。整库路径会预先传入空间成员，导致同一错误在另一调用形态下可能变成可索引。安全结论必须覆盖所有入口和参数组合，不能从一个绿色用例推广到整套 Connector。

### 18. ACL 错误优先级必须高于任何继承权限

文档 ACL 读取失败意味着权限状态未知。空间公开、空间成员已知、App 能读取正文或文档位于该知识空间，都不能把未知改写成已知。正确顺序是先确认文档 ACL 成功，再判断是否声明继承；错误路径必须在正文读取前终止。

### 19. 位置关系不等于权限继承关系

文档位于知识空间只说明内容组织位置，不自动证明它继承空间成员。只有文档 ACL 明确出现 `wikispaceid` 才能展开空间权限；否则只使用直接 ACL。任何基于路径、父节点或空间枚举结果推断授权的算法都会放大权限。

### 20. 原始授权主体必须端到端保真

Connector 能看到 `department/openchat` 不等于检索层能执行这些权限。成员类型需要从飞书原始字段正确映射到 ACL 表，Retrieval 还必须理解当前会话的群组证据与撤权语义。只修入库、不修查询会形成假阴性；直接把群成员当个人永久授权则会形成假阳性。

### 21. 撤权验收必须修改真实授权关系

仅删除测试行、改变 Prompt 或模拟 Principal 不能证明撤权。可靠做法是使用用户身份创建无业务数据的临时文档，保持公司 App 只读，真实增加并移除员工协作者，再通过 Connector 重同步和 Agent Core 负测证明旧员工 Evidence 归零。测试结束后必须删除临时文档和所有 Token、成员 ID、Chunk 与 ACL。

### 22. 生产候选必须同时保留源码与镜像回滚点

仅有运行镜像但构建源目录已被清理，会让下一次修复无法可靠复现。本轮把候选源码放入版本化发布目录，构建前保存旧源码、配置、Knowledge Schema dump 和旧镜像标签，并实际执行旧版回滚和新版恢复。今后 Connector 发布不能只依赖 `latest` 标签。

## 固化方法

1. 先定义服务身份、员工身份和管理身份的权限矩阵。
2. 用真实 API 分别验证三类飞书授权。
3. 递归同步组织树，最小字段写入 Principal。
4. 连续同步两次验证幂等，并执行员工 403 负测。
5. 对新增 diff 做敏感字段扫描，再构建和滚动部署。
6. 先 Agent Core、后 H-Lite，逐层健康后再继续。
7. 用新版本启动后的真实消息和真实读回作为验收证据。
8. 将权限、数量、版本和时间都标记为快照，避免过时事实被当作永久真值。
9. 操作 QNAP 前核对公司资产五元组，禁止把家庭 NAS 或历史 TS-431P 资料带入生产。
10. Ontology Definition 变更先编译、分级兼容性、提交 Proposal 和迁移计划，再批准部署和对账。
11. 对 Foundation 同时执行隔离数据库、生产整栈、重启恢复、重复执行和最小权限验收。
12. 整库知识同步必须先做只读 ACL 分布审计，再按直接授权、空间继承、无继承、ACL 失败和撤权建立测试矩阵。
13. ACL 错误路径必须断言正文接口零调用；权限继承必须以文档 ACL 中的显式 `wikispaceid` 为唯一依据。
14. 撤权测试必须使用真实飞书权限变更，并验证撤权员工、跨部门人员、原始 Token 和直接链接均不能命中 Evidence。
15. 每次生产构建保存版本化源码、旧镜像标签、数据库 Schema 快照和校验清单，并执行可逆恢复验证。

## Goal 2 收口后的路线经验（2026-08-09）

### 23. 有对象名不等于公司大脑工作逻辑已经显式化

Source、Evidence、Claim 和 DecisionCase 解决“系统里有什么”，但不能单独回答“请求当前在哪一步、为什么停住、下一步需要谁批准、用了哪些证据”。必须增加 WorkCase、WorkStage、状态机、阶段输入输出和可回放事件，才能形成真正可运营的公司大脑。

### 24. 真实员工 Canary 应验证稳定协议，不应替架构找方向

如果在 P0-EPI、P0-DEC 和回答契约仍将变化时先扩到 10 名员工，得到的只是旧行为反馈，后续还要重新培训和验收。正确顺序是先稳定大框架，再用 10 人 Canary 检验真实权限、并发、理解成本和业务效果。

### 25. 显式推理不能演变为保存隐藏思维链

公司需要审计的是证据、规则、主张、假设、未知、冲突、批准和结果，不是模型内部逐 token 推理。后者不稳定、不可作为业务事实，还会放大隐私与安全风险。持久化内容必须是结构化、可验证、可授权的推理产物摘要。

### 26. 工作实例状态与业务事实必须分开

WorkCase `completed` 只表示一次分析或回答完成，不代表 P2 完成、Action 成功或经营目标改善。执行成功、业务流程成功和目标成功仍必须由 Verification 分层记录，避免再次把 HTTP 200、飞书 ACK 或模型回答当成业务结果。

### 27. 全链路先固化契约，激活范围必须逐阶段推进

“骨架完整、血肉渐进”意味着 Goal 4 可以一次定义 Intake 到 Learning 的完整阶段，但只激活认识闭环；Decision、任务和学习保持灰色，等 Goal 5 再接真实业务。这样既避免后续重构，也不会把未实现能力包装为生产完成。

## Goal 4 生产收口经验（2026-08-09）

### 28. migration 成功不等于运行角色真的能读稳定 View

表、RLS、View 都创建成功，管理员查询也正常，但 `ontology_app` 缺少 View 的 `SELECT` 仍会让生产状态接口返回 PostgreSQL `42501`。迁移验收必须同时检查对象存在、底层表权限、View 权限和真实应用角色查询，不能只用管理员账号验证。

### 29. 反证和有效期必须从 Connector 数据一路映射到 Evidence Package

纯函数单测能识别 `contradicts` 和 `validUntil`，不代表生产检索结果真的携带这些字段。知识资源 metadata 和 Ontology attributes 必须显式映射 sourceSystem、validUntil、supports/contradicts、epistemicType 和 sourceReference，否则线上所有证据都会被误当成普通支持事实。

### 30. 有身份但无授权证据时应在策略层失败关闭

Principal 存在但 Evidence 为 0 时继续调用 H 引擎，会增加成本、放大幻觉面并把远程模型故障引入本可本地回答的权限拒绝路径。正确做法是直接形成 `insufficient_evidence`、跳过模型、返回固定可审计解释；不存在 Principal 则形成 `permission_denied`。

### 31. 生产脚本不得通过 stdin 直接管给含 docker exec 的远端 shell

`docker compose exec -T` 可能消费剩余 stdin，导致后续脚本静默丢失或提前结束。所有复杂 QNAP 发布、回滚和验收脚本必须先传为远端文件，再按文件执行；脚本内部 heredoc 才是可控边界。

### 32. 验收器不能硬编码历史版本总数

Registry 保留历史版本元素，Schema 升级后 `elements` 总数会累加。把旧版 71 写死为生产断言会把正确升级判成失败。验收应检查“唯一 active 版本 + active 版本元素数 > 0 + Git/本地/active Hash 一致”，历史总数只作审计，不作当前版本真值。

### 33. 回滚必须同时证明旧版可运行和新版可恢复

只保留旧镜像标签不算回滚闭环。本轮真实切回 Schema `3.0.0`、Agent Core `2026-08-08.4` 和旧 Caddy 路由，验证旧版健康后再恢复 `3.1.0`/`2026-08-09.1`/active Work Protocol，并确认三个容器 `restart_count=0`、WorkCase 事件回放不变。

### 34. 管理页面绿色必须来自业务状态，不来自代码已合并

P0-EPI 只有在 QNAP active、fixture 正负测试、回滚恢复和真实浏览器验收全部通过后才标绿。Decision、Plan、Execution、Verification、Learning 即使契约已存在，也必须保持灰色，直到 Goal 5 有真实 Decision Lineage 和业务结果证据。

## Goal 5 生产收口经验（2026-08-09）

### 35. 幂等返回相同对象还不够，状态推进也必须幂等

Decision 审批重放虽然能返回同一个 Decision，但如果仍重复推进 WorkCase、重复追加阶段事件，审计时间线就会失真。幂等验收必须同时检查对象 ID、`replayed` 标志、事件数量和状态推进次数。

### 36. PostgreSQL 多态 JSON 函数不能依赖未知参数猜类型

`jsonb_build_object` 接收 bind parameter 时，驱动传入的 unknown 类型可能在生产触发多态解析错误。进入 JSON 构造、数组或复合类型函数前，应显式转换为 `text`、`uuid`、`jsonb` 等确定类型，并用真实 PostgreSQL 版本验证。

### 37. 最小权限不仅是撤销权限，还要把初始化责任放到正确组件

Agent Core 不应初始化 Action Gateway 的目标状态。即使是演示目标，也应由真正拥有目标系统写权限的 Gateway 完成，保证未来切换真实 ERP、飞书或报表时不会形成旁路写权限。

### 38. 历史验收计数必须限定业务对象，不能统计全库

旧 P0 任务事件按全表固定等于 10 验收，新 P2 进入后会把正确系统判成失败。稳定验收器应按外部键、Run ID、时间窗或受控标签限定对象；全库总数只适合观测，不能作为版本升级后的固定断言。

### 39. 失败 Canary 也是审计事实，但不能长期冒充待执行业务

删除失败 WorkCase 会破坏证据，保留为 `plan_pending` / `execution_pending` 又会污染管理看板。正确做法是保留对象和 append-only 事件，同时把 WorkCase 标为 `blocked`、Decision 标为 `superseded`、Lineage 显示为 `retired`；成功 Lineage 的退役必须强制拒绝。

### 40. Definition 来源与 Runtime Release 必须分开记录

本轮 Ontology Definition 内容未变，Registry Source Commit 应继续指向 `e6a98c6dc`；运行时修复则用独立 Runtime Release Commit `19793e100` 记录。把任意最新提交都写成 Definition 来源，会破坏 Git/Registry 对账语义。

### 41. 三层成功必须独立验证，Learning 只能先成为提案

Action 读回成功只证明技术执行；业务流程成功和经营目标成功必须由 Verification 分别给出证据。Learning 在没有 Change Proposal 审批、兼容性检查和回滚计划前只能是 `proposed`，不能让模型自动改本体或流程。

## Goal 6-A 回滚恢复经验（2026-08-10）

### 42. 生产切换后的健康断言必须轮询，不可即时判定

第一次 Domain Connector 回滚中，旧版 `2026-08-09.2` 实际已成功启动，但外层包装器在核心服务尚未完成 ready 时立即断言，误判失败并触发自动恢复。正式演练改为轮询核心服务健康后，`.3 → .2 → .3` 在 41 秒内完成。任何容器切换验收都必须区分“进程已启动”“健康检查已通过”“业务数据已验证”三层状态。

### 43. 灾备闭环要验证数据不变和禁止副作用

仅证明旧版和新版都健康仍不足以关闭门禁。本轮同时固定跨阶段数据指纹，核对 ERP 95、Market 369、ActionIntent 0、Delivery Outbox 0，并在恢复后复跑完整 `verify.sh` 和真实 Chrome `59/59`。只读 Connector 的恢复演练必须证明没有员工投递、没有业务写回、没有 Cursor 泄露、没有端口变化。

### 44. 工程完成不等于用户已经体验验收

### 45. 验收入口必须成为 Goal 的正式交付物

本轮在 Goal 完成后才由用户追问“怎么体验验收”，说明最终交付缺少人类可操作入口。以后每个 Goal 必须在完成前提供一页式体验验收包：直接 URL、登录说明、5–10 分钟操作路径、关键数值、可复制 Bot Prompt、通过/失败判据和明确关闭项。白盒回答系统如何运行，运行看板回答当前状态，Bot 验收回答员工如何使用；三者职责不能混用。

- 必须指定唯一 DRI 和一条真实 P2，完成任务提案、批准、投递、成果提交和 DRI 验收闭环。

## Goal 6 UAT 与多组件发布经验（2026-08-10）

### 46. 版本号正确不等于生产源码正确

H 公网 `/healthz` 曾报告 `v1.56.1`，但生产 Dashboard 与 Whitebox 文件仍是 UAT 修复前内容，导致运行真值字段、光晕分层和真实浏览器验收失败。根因是服务在 `12:04` 启动，而对应修复直到 `12:45`、`12:51` 才提交，版本常量与实际目标文件发生漂移。以后发布必须从已推送的唯一 Source Commit 构建，发布后同时对账版本、Source Commit、目标文件哈希、API DTO 和真实 DOM；版本徽标只能作为一项证据。

### 47. 同版本重新覆盖会掩盖漂移，修复应升补丁版本

发现 `v1.56.1` 标识下的源码漂移后，没有继续以同一版本覆盖，而是发布 `v1.56.2`，把“发现漂移、修复漂移、生产验收”形成新的可审计事件。即使用户可见功能不变，只要生产运行内容发生修复，也应提升补丁版本并建立独立回滚锚。

### 48. 幂等验收必须使用全新请求标识

Agent Core `2026-08-10.1` 首次三问验收触发 PostgreSQL `23514`；修复后若复用同一 `run_id` / `idempotencyKey`，只会重放第一次持久化失败，不能证明热修生效。重试故障必须区分“业务重放验证”和“新版本重新执行”，后者使用全新请求标识，并同时断言 `provider=policy-engine`、不调用 H 引擎、不新增 ActionIntent/Outbox。

### 49. 治理意图与数据库稳定枚举必须解耦

`system_status`、`operating_model_explanation`、`personal_identity_handoff` 是策略层治理意图，不应直接写入数据库受限的 `work_mode`。正确做法是保留治理意图供回答和审计使用，同时映射到既有稳定枚举 `answer_query` / `situation_analysis`。新增策略标签前必须检查持久化契约，避免模型路由语义直接穿透数据库约束。

### 50. 生产重启授权必须精确到服务和当前窗口

本轮 QNAP 发布授权不包含 H 控制面重启。发现 H 生产漂移后先只读取证，明确说明只会重启 `h-control`、正常中断预计 2–5 秒、异常自动回滚最坏窗口，再获得单独授权。实际 systemd 停止与启动发生在同一秒，完整发布与验证耗时 29 秒，`NRestarts=0`。任何跨组件 Goal 都不得继承另一组件的重启授权。

## P1-SI-A contract-only 发布经验（2026-08-10）

### 51. “部署候选契约”不等于“激活候选 Schema”

P1-SI-A 的 `3.4.0` 仍是 `contract_only / deploymentAllowed=false`。用户授权部署后，正确动作是把候选编译能力放进生产 Registry 镜像，同时保持 active Definition、Registry Source Commit 和数据库 Schema 为 `3.3.0`；不能把“部署”误解成绕过 Goal 7、Source Registry、DRI 和 Shadow 门禁直接激活。

### 52. 单组件发布必须在构建阶段零中断，在切换阶段最小中断

Ontology Registry 新镜像先在旧容器继续服务时构建，并通过独立容器离线编译候选 `3.4.0`；验证通过后才 `--no-deps --force-recreate` 单独切换 Registry。本轮切换窗口为 2 秒，其他服务未重启。未来契约、Connector 或 Agent 单组件更新继续禁止使用全栈 `compose up`。

### 53. contract-only 发布要同时证明“新能力存在”和“旧生产真值未变”

只看到候选编译成功不够。本轮同时验证：候选 Hash 正确、兼容性为 compatible、Action Type 增量为 0、active Schema/Hash 仍为 `3.3.0` 原值、Registry `in_sync`、Agent Core productionReady、各 Connector/Gateway ready、restart count 为 0。两侧证据缺一，都不能宣称安全发布。

### 54. 授权发布不自动包含真实回滚演练授权

发布脚本必须先创建旧镜像标签、环境备份、Release Manifest 和自动失败恢复；但成功发布后再主动切回旧镜像属于新的生产切换。本轮只验证回滚抓手可用，没有擅自执行真实回滚。今后“有回滚能力”和“已做真实回滚演练”必须分开陈述。

## P1-SI-B～G 战略情报工程候选经验（2026-08-10）

### 55. 来源准入和内容留存必须分成两次判定

Source Registry 判定允许访问某个来源，只说明这次网络请求获得公司批准，不代表可以保存返回正文。`reference_only / metadata_only / summary_metadata` 必须在 Raw Snapshot 层丢弃响应体，只保留 Hash、长度、来源和时间；`metadata_only / reference_only` 还要在 normalized item 层去掉摘要。采集权限和留存权限合并判断，会让“允许看”被错误放大为“允许长期复制”。

### 56. 可部署包通过静态测试不等于 Runtime 已验证

Compose、脚本、资源限制和授权门禁可以在没有容器运行时的开发机上完成静态与负向验证，但镜像是否可构建、镜像 digest 是否固定、候选 SQL 是否能在真实 PostgreSQL 应用并恢复、QNAP 资源是否满足，只能由对应 Runtime 证据证明。验收字段必须显式拆成 `engineering_package_verified`、`image_build_verified`、`sql_runtime_verified` 和 `company_qnap_deployed`，禁止用一个绿色状态覆盖四层事实。

### 57. 关系矩阵覆盖完整不代表因果语义可信

PESTIM 4644 条矩阵能够证明 43 个外部维度与 108 个 GoalFacet 在结构上全部有映射，但大量“目标直接影响”“O1目的”“灵魂优先”等模板文本不能证明真实因果链。正确做法是先筛选 20～50 条高价值候选，固定为 `generated_draft / unverified / inactive`，再由实名 DRI 重写逻辑、补充正反证据、适用条件、滞后和验证指标，而不是批量激活整张矩阵。

### 58. 七日 Shadow 的最小单位是真实自然日，不是运行次数

Shadow 生成器只能提前创建 `pending_real_run / simulated=false` 的证据模板；七次短时运行、补录数据或模拟日期都不能替代七个真实自然日。每个自然日都必须保存来源成功率、重复率、时效、成本、资源、撤销生效、last-good、敏感信息和业务副作用计数，缺少资源或副作用证据的当天不能通过。

### 59. 战略情报部署必须只操作自己的服务边界

P1-SI-H 发布脚本只能启动、冻结或回滚 Intelligence Orchestrator 和临时 Collector，不能借雷达部署重启 Agent Core、H-Lite、Connector、Gateway 或数据库。部署授权、数据库迁移授权、服务重启授权和真实回滚授权互不继承；即便最终共用 Postgres、Redis、Qdrant 和 Outbox，也不得绕过既有权限、安全网关和发布来源证明。

### 60. Runtime 验证必须连清理路径一起通过

第一次 CI 把相对项目目录交给 Docker，挂载路径被误判为卷名；第二次迁移、19/19 强制 RLS 和 baseline restore 虽然都通过，但容器 UID 创建的宿主目录无法由 Runner 清理，最终任务仍应判失败。修复方式是先把项目路径规范化为绝对路径，并用临时 Docker Volume 承载 PostgreSQL 数据，退出时先删容器再删卷。Runtime 验收不仅要证明主流程成功，还要证明临时容器、卷、目录和凭据全部可回收。

### 61. 飞书 CSV 只是人工审核传输层，不是授权真源

飞书表格适合多人填写，但单元格会把数字、数组、对象和空值统一弱化成文本。正式闭环必须把 CSV 重新导入为强类型 JSON，再由机器契约执行 final 校验和 compile；不能直接把“表格里看起来已填完”解释为来源已获许可或因果关系已审核通过。

### 62. 人工审核必须把只读候选锚点带回并做防篡改校验

如果 CSV 导入时只读取审核人填写的字段、再从当前模板补回 source name、Hash、维度和指标，就会隐藏飞书导出过程中的误改或候选版本漂移。正确做法是把只读字段原样带回，逐项与当前 Source Registry 或 P003 候选目录比较；Key、Hash、入口、原始逻辑、建议角色或指标任一变化都 fail-closed。

### 63. 审核通过不能只靠一个勾选框

P003 关系即使具备语义重写、正反证据和指标，也必须显式记录适用、激活、暂停和失效条件，并在编译结果中保留外部因素、目标 GoalFacet 与传导路径。只有 `reviewChecklist=true` 而缺少这些结构化条件，无法支持后续监测、暂停、撤销和回放。

### 64. 部署前验证器必须按编译后状态验收

Source Registry 工程目录状态是 `candidate`，人工审核编译结果状态是 `shadow_reviewed`。部署前验证器如果复用默认校验却仍只允许 `candidate`，会在真实审批完成后错误拒绝合法发布包。每个发布门禁都必须使用它实际接收的生命周期状态做正负测试，不能只证明上游编译器单独通过。

### 65. 实名审核数据必须与 Git 模板分离

Git 只保存脱敏契约、候选锚点和空白模板；包含真实姓名、目录 Principal、审批理由与内部证据引用的回填结果默认进入 `~/work-private/company-ai-ontology/reviews/` 或批准的公司受控目录。工程可复现性由模板 Hash、候选 Hash 和编译器保证，不应以把实名审批表提交 Git 为代价。
