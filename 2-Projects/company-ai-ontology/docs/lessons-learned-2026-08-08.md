# Company AI Ontology 阶段经验教训

日期：2026-08-08

## 阶段结论

公司 Bot 与飞书通讯录只读同步已经跑通，但“消息能收发”和“公司 AI 可安全回答所有内部问题”是两个不同阶段。当前已证明 Bot 接入、最小身份同步、服务身份隔离和幂等链路；下一阶段必须补齐 H 引擎生产凭据、知识 ACL Connector、真实员工 Canary 和真实 P2 闭环。

## 已验证事实

- QNAP H-Lite 为公司独立飞书 App/Bot 的唯一主订阅实例，员工私人 Bot 不迁移、不切换 Consumer。
- 真实消息覆盖 `p2p:post`、`p2p:text`、`group:text`，3 次完成、0 失败、3 条去重记录。
- 飞书通讯录 4 个授权入口递归展开为 83 个可见部门，共同步 414 名可见人员。
- 首次同步新增 414；重复同步新增 0、更新 414，证明 Principal Upsert 幂等。
- 同步只保留姓名、飞书身份和部门；邮箱、手机号和私人文本属性命中 0。
- 仅 HMAC 服务身份 `company-directory-sync` 可写入；普通员工身份负测返回 403。
- Agent Core `2026-08-08.1`、H-Lite `2026-08-08.2` 健康，飞书长连接在线，容器 `restart_count=0`。

以上数量是 2026-08-08 的生产权限快照，不应写成永久常量。

## 经验教训

### 1. 飞书授权是三道门

API Scope、通讯录数据范围和应用可用范围彼此独立。后台显示“权限已开通”不能证明人员可见，也不能证明员工能找到 Bot。验收必须分别调用真实 API，并用真实员工完成可见性测试。

### 2. 通讯录必须递归展开

顶层授权范围只是入口，不是完整组织树。本次 4 个入口实际展开为 83 个部门；若只同步入口部门，会形成看似成功但严重漏人的假阳性。

### 3. 身份同步不是员工能力

通讯录批量同步必须是后台服务作业，只允许专用服务身份和 HMAC 接口。员工对话身份必须明确 403，避免 Company Agent 被错误提升为通讯录超级管理员。

### 4. 最小字段和幂等优先

P0 的人员对象只需要任务派发所需字段。邮箱、手机号、私聊正文和私人属性既非必要，也会放大泄露面。重复同步必须 Upsert，不得重复创建。

### 5. 不自动停用“本轮未出现”人员

通讯录范围可能因管理员配置、接口波动或部门调整暂时收缩。当前阶段仅更新可见人员，不自动禁用缺席人员；后续应通过连续多轮缺席、离职事件或人工确认再停用。

### 6. App 可读不等于员工可读

公司知识 Connector 可以使用 App 身份建立索引，但回答员工问题时必须重新按员工、部门、项目和文档 ACL 过滤。没有 `Permissioned Evidence Package` 的内容不得进入 Company Agent 上下文。

### 7. 部署完成不等于当前版本验收

QNAP 滚动升级应先 Agent Core、后 H-Lite。每次升级后重新验证版本、健康、WebSocket、真实消息、Outbox、去重、权限负测和 `restart_count`；不能沿用旧版本的通过记录。

### 8. 传输包和生产凭据必须短命

部署包不得包含 App Secret、访问令牌或明文环境文件。临时包在本机、中转机和 QNAP 使用后均应清理；Git、记忆、日志和验收文档只保存 secret 指针与脱敏证据。

## 固化方法

1. 先定义服务身份、员工身份和管理身份的权限矩阵。
2. 用真实 API 分别验证三类飞书授权。
3. 递归同步组织树，最小字段写入 Principal。
4. 连续同步两次验证幂等，并执行员工 403 负测。
5. 对新增 diff 做敏感字段扫描，再构建和滚动部署。
6. 先 Agent Core、后 H-Lite，逐层健康后再继续。
7. 用新版本启动后的真实消息和真实读回作为验收证据。
8. 将权限、数量、版本和时间都标记为快照，避免过时事实被当作永久真值。

## 下一阶段门禁

- H 引擎企业凭据必须通过安全指针配置，并完成真实生产推理验收。
- 飞书公司知识 Connector 必须实现 ACL 映射、撤权收敛和越权负测。
- 10 名真实员工 Canary 必须覆盖并发会话、多人 @ 隔离、失败重投和真实送达。
- 必须指定唯一 DRI 和一条真实 P2，完成任务提案、批准、投递、成果提交和 DRI 验收闭环。
- ERP M3 与社媒保持只读证据源；ERP M4 和 MediaCrawler 风控恢复继续等待显式指令。
