# 电视代理迁到网关层：架构方案（2026-11-20）

> 目标：电视盒不再跑任何代理；由 Armbian 盒子当网关做分流与出口聚合；YouTube 等需翻墙的走节点，其余国内直连；多路并行 + 多协议，让电视拿到最大带宽。
> 本文是**方案**，实施按 §7 阶段推进，每阶段独立可回滚。

│  电视盒 .144 │──────────────────────────┐
└──────────────┘                          │
┌──────────────┐                          ▼
│ 其他设备(可选)│──────────────▶ ┌─────────────────────────────┐

                                │   ├ 国内 geosite:cn → direct│

                                └──────────┬──────────────────┘
                                           │ 出口池（多协议并行）
        ┌──────────────────┬───────────────┼──────────────┬─────────────────┐
        ▼                  ▼               ▼              ▼                 ▼
  HK hy2(UDP)       HK Reality(TCP)   HK Reality(v6)  Rack hy2        ZGO Reality

## 3. 组件选型

| 层 | 选择 | 理由 | 不选什么 |
|---|---|---|---|
| 分流引擎 | **sing-box**（TUN + rule_set + sniff + DNS） | 一套搞定规则/TUN/DNS/hy2；配置单文件；我们已熟悉 | 不用 Clash（hy2 支持弱）、不用 iptables+redsocks（维护地狱） |
| 出口协议 | **hy2(UDP) + VLESS-Reality(TCP) + Reality over IPv6** | 三种通道特性互补：UDP 抗丢包、TCP 稳定、IPv6 绕开 IPv4 限速 | 不押注单一协议 |
| 并行/均衡 | **多实例 + nftables ECMP**（P1）→ **Xray balancer**（P2） | sing-box 无 balancer；ECMP 零新增组件即可真并行 | 不指望 urltest（它只选一条） |
| 加速 | IPv6 优先 + BBR/fq + hy2 brutal + 关 mux | 实测 IPv6 快 170×；BBR 已在 | 不上 mptcp（两端都要支持） |

## 4. 多路并行 / 负载均衡 / 多协议 / 加速 —— 具体怎么做

### 4.1 多协议并存（基础）

一条线路同时挂三种出口，按可用性自动取舍：

```jsonc
// HK 三通道
{ "tag": "hk-hy2",    "type": "hysteria2", "server": "10.10.10.1", "server_port": 9445, ... },
{ "tag": "hk-reality", "type": "vless", "server": "10.10.10.1", "server_port": 8445, "tls": {"reality": {...}} },
{ "tag": "hk-v6",      "type": "vless", "server": "2001:df1:7880:6::1ca", "server_port": 443, ... }
```
> `hk-v6` 必须配 `"domain_strategy": "prefer_ipv6"`，否则仍走 IPv4。

### 4.2 并行/均衡（三档，按投入递增）

**档 A：urltest（0 成本，但只选一条）**
```jsonc
{ "type": "urltest", "tag": "auto", "outbounds": ["hk-hy2","hk-reality","rack-hy2","zgo-reality"],
  "url": "https://www.gstatic.com/generate_204", "interval": "1m", "tolerance": 50 }
```
适合"自动选最快"，但**单流只走一条**。

**档 B：多实例 + nftables ECMP（推荐，真并行）**
```
sing-box-A ─ socks 127.0.0.1:1081 → hk-hy2
sing-box-B ─ socks 127.0.0.1:1082 → hk-v6
sing-box-C ─ socks 127.0.0.1:1083 → rack-hy2
```
nftables 按五元组哈希分发（视频的多条 HTTP range 连接天然散开）：
```
nft add rule inet fw4 prerouting ip daddr @googlevideo tcp dport 443 \
  meta mark set jhash ip saddr . ip daddr . tcp sport mod 3 \
  meta mark 0 dnat to 127.0.0.1:1081 \
  meta mark 1 dnat to 127.0.0.1:1082 \
  meta mark 2 dnat to 127.0.0.1:1083
```
> 实测意义：YouTube 一条视频通常开 3–8 条连接 → 3 路并行可把 6 MB/s 变成 ~10–18 MB/s。

**档 C：Xray balancer（功能最全）**
Xray 网关 + `balancer`（`strategy: leastLoad` / `random`），hy2 用 sing-box 暴露成 socks 塞进去：
```jsonc
{ "tag": "b", "selector": ["hk-hy2-socks","hk-reality","hk-v6","rack-hy2"],
  "strategy": {"type": "leastLoad", "settings": {"expected": 2, "maxRTT": "2s"}} }
```
优点是决策更聪明，缺点是两套组件都要维护。

### 4.3 加速清单

| 项 | 做法 | 预期 |
|---|---|---|
| **IPv6 优先** | `domain_strategy: prefer_ipv6` + 出口用 v6 地址 | 实测 170× |
| BBR + fq | 已开（`net.ipv4.tcp_congestion_control=bbr`） | 已生效 |
| hy2 brutal | `"up_mbps"/"down_mbps"` 按 50/200 填 | 丢包时比 TCP 稳 |
| 关 mux | Reality 出口 `"multiplex": {"enabled": false}` | 视频多连接更快 |
| DNS 预解析 | sing-box DNS + `cache_capacity` | 减少首帧等待 |
| 大缓冲 | `sysctl net.core.rmem_max=16M` 等 | 高 BDP 链路吞吐↑ |

### 关键坑（都已解）

1. `{"action":"sniff"}` 必须写全 `"sniffer":["tls","http","quic"]`，否则**不嗅探**。
2. **TUN 转发的流量即使嗅探成功也不按域名路由**（实测），必须用 **IP 段**兜底：Google/YouTube 的 13 个 CIDR 直接 `outbound: proxy`。
3. Android 用**按网卡分表**（`table eth0`）而不是 main 表，改默认路由必须同时改 `table eth0`。
4. 旧 sing-box 会留下 `VIDEO_DNS`(REDIRECT 5354) 与 `VIDEO_DNS4_GUARD`(REJECT) 两条 iptables 链 + 一批 `ip rule`，**不清理会导致全设备 DNS 挂**。
5. Magisk `service.d` **执行所有文件**（不看扩展名），备份文件留在里面会被当成启动脚本。
6. sing-box 1.14 需要 `route.default_domain_resolver`；DNS server 不能 `detour: direct`。
7. 规则集（geosite/geoip .srs）在国内拉不动，要在有代理的机器下好再传过去。

### 实测带宽（当晚，波动大）

| 路径 | 值 |
|---|---|
| 组网上限（HK 本地文件） | **10 MB/s** |
| hk-hy2（UDP 过组网） | 0.36–1.37 MB/s |
| hk-reality（TCP 过组网，当晚新开 xray） | 0.19–0.83 MB/s |
| hk-v6（IPv6 直连 Reality） | 0.17–0.92 MB/s |
| rack-hy2 / zgo-reality | 0.77 / 1.02 MB/s |
| **电视盒 4K 播放实测** | **24–27 Mbps 持续 60 秒，state=3，force_skip_cnt=0，解码 3840×2160** |

### P2 未做（多实例 + ECMP）

原因：单路已能撑 4K（24–27 Mbps），当前瓶颈是国际链路本身（0.2–1.4 MB/s 波动）而非出口选择。是否需要并行，取决于该链路是否按"单流"限速——需要一次对照实验（同目标、1 流 vs 4 流并发）才能判断，留待下一步。

## 10. P2 结论：不做 ECMP，改"同出口多流"（2026-11-20 22:30 实测）

用独立测试实例（4 个 socks 口分别绑不同出口，不动生产 TUN）做三组对照：

| 组 | 配置 | 实测 |
|---|---|---|
| A | 单流走 hk-hy2 | **7.8 MB/s（64 Mbps）** |
| B | **同出口** hk-hy2 三路并发 | **10.4 MB/s（85 Mbps，+33%）** |
| C | **不同出口**四路并发（hk-hy2 / hk-reality / zgo-reality / rack-hy2） | **1.66 MB/s（13 Mbps，远低于单流）** |

**判读**：这条链路不是"按单流限速"，单流就能吃掉大部分带宽；再叠加更差的出口（zgo 0.6、rack 0.3）反而把总吞吐拉低。所以：

- ❌ **不做** 多实例 + nftables ECMP（会把流量分到慢出口）
- ✅ **保留** urltest（始终选当前最快的那一条）
- ✅ 视频的多连接天然就在"同出口"上并发，已拿到 +33% 的多流收益

### 当晚还踩到的两个坑

1. **DNS 返回 IPv6 会让流量绕开代理**：`dns.strategy` 必须 `ipv4_only`，否则解析出 `2401:...` 后直连 IPv6 出境、被墙、表现为 TLS 握手失败。
2. **hy2(UDP 过组网) 对 TLS 大包不友好**：同一出口下 `nc` TCP 握手成功，但 TLS `ServerHello`（证书约 4KB）常被丢，表现为 `SSLHandshakeException: connection closed`；换直连 TCP 出口（zgo-reality）能过握手。
3. TUN 转发流量即使开启 `sniffer` 也**不按域名路由**（实测），必须叠加 Google IP 段规则。

## 12. TR3000 + U 盘：双网关冗余（2026-11-21 01:00 完成）

### 一次失败的教训：不要做 extroot

TR3000 的 USB 驱动（`kmod-usb-storage`）装在 overlay 里，把 overlay 迁到 U 盘后形成死锁：
**挂载 U 盘 → 需要驱动 → 驱动在 U 盘上 → 永远挂不上**，路由器直接起不来。
只有把 USB 驱动编进内核才能做 extroot，这台机器不行。

**结论：TR3000 的 U 盘只做数据盘（`/mnt/usb`），不做 extroot。**

### 实际落地方案

| 组件 | 位置 | 说明 |
|---|---|---|
| U 盘 | `/mnt/usb`（ext4，3.8G，fstab 开机自动挂载） | 存二进制、配置、规则集、日志 |
| sing-box | `/mnt/usb/proxy/sing-box`（**musl 版**，42.4M，从 OpenWrt 包 `apk extract` 提取） | 官方 GitHub 版是 glibc 动态链接，**在 OpenWrt 上跑不了** |
| 配置 | `/mnt/usb/proxy/config.json` | TUN `172.20.0.1/30`、**MTU 1280**、socks 1081、clash 9091；出口 6 条（含 hy2，需 `with_quic`，要用完整包不是 tiny） |
| 排除段 | `route_exclude_address` | `10.10.10.0/24`(组网) `192.168.1.0/24`(局域网) `172.20.0.0/30`，避免把 EasyTier 和管理流量卷进代理 |
| 自启 | `/etc/init.d/dsh-backup-gateway` → `/etc/dsh-backup-start.sh` | 包装脚本等 U 盘就绪（最多 90 秒）再 exec，规避开机时序竞争 |
| DNS | TR3000 上的 dnsmasq 监听 `192.168.1.254:53`，上游 8.8.8.8 被本机 sing-box 劫持 | 给电视盒在备用路径下提供干净解析 |
| 防火墙 | 新建 zone `tun`（`tun1`，masq+mtu_fix）+ forwarding `lan→tun` | 不加这条，转发流量会被 fw4 丢掉 |

### 电视盒自动回退（功能健康度判据）

`/data/adb/dsh-gateway/watch.sh` 每 10 秒判定一次：

```
健康 = 当前网关可达 + 能通过它 TCP 连上 142.250.0.1:443（只有代理真通才成立）
连续 2 次不健康 → 切到另一条网关（.19 ↔ .254）
```

**不能只 ping**：主网关进程停了但主机还在，ping 照样通，必须用"能不能真连出去"判断。

### 演练结果

| 场景 | 结果 |
|---|---|
| 停掉主网关 `dsh-gateway` | 电视盒 **18 秒**内自动切到 `192.168.1.254` |
| 备用路径连通性 | DNS 干净（142.251.155.4）、Google 443 OK |
| 备用路径播 4K | **state=3、3840×2160、12 Mbps**（hy2 走组网） |
| 恢复主网关 | 电视盒自动切回 `.19`，4K 播放继续 |
| TR3000 冷启动 | U 盘挂载、备份网关、dnsmasq、防火墙 zone 全部自动就绪 |
