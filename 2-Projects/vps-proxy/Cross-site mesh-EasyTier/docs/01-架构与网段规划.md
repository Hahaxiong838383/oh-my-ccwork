## 二、网段规划与冲突核对

这一节是**逐条核对过的**，不是照抄常见写法。

| 段 | 用途 | 谁在用 |
|---|---|---|
| `10.10.10.0/24` | EasyTier 虚拟主网段 | 全部节点 |
| `10.10.61.0/24` | 公司有线段的**对外映射** | `192.168.61.0/24` 经 mini/dev198 导出 |
| `10.10.1.0/24` | 家庭段的**对外映射** | `192.168.1.0/24` 经 linux-lan 导出 |

**已存在网段（必须避开）**：

| 现有段 | 是什么 | 与上表冲突？ |
|---|---|---|
| `192.168.61.0/24` | 公司有线（Mini/Studio/dev198/QNAP） | 不冲突 |
| `10.9.1.0/24` | 公司 WiFi | 不冲突（`10.9.x` ≠ `10.10.x`） |
| `192.168.1.0/24` | 家庭 LAN | 不冲突 |
| `192.168.100.0/24` | Mini↔Studio 雷电网桥 | 不冲突 |

> ⚠️ **为什么一定要做 CIDR 映射**：家里和公司的真实段不能直接导出。
> Air 在家时物理上就在 `192.168.1.0/24`；studio/dev198 物理上就在 `192.168.61.0/24`。
> 直接导出会让这些节点收到一条**与自己本地网段重叠**的隧道路由，本地网络当场中断。
> 映射到 `10.10.1.0/24` / `10.10.61.0/24` 后，隧道路由与任何节点的本地网段都不相交。

**映射后的访问方式**（真实 IP 末位不变，只换前缀）：

```
QNAP  192.168.61.18  →  从家里访问 10.10.61.18
公司网关 192.168.61.254 →  10.10.61.254
家里某设备 192.168.1.50 →  从公司访问 10.10.1.50
```

## 三、端口规划（关键，与常见文档不同）

野草云面板侧有**客户不可关闭**的供应商防火墙，入站白名单只有：

```
tcp 22 · udp 22 · tcp 80 · tcp 443 · tcp 8888 · icmp · ipv6-icmp
```

所以中继节点落在已放行端口上：

| 端口 | 协议 | 用途 | 实测 |
|---|---|---|---|
| `443` | tcp | 主 TCP 通道 | OPEN 48ms |
| `22` | udp | 主 UDP 通道（与 sshd 的 tcp 22 不冲突） | 已连通 |
| `80` | tcp | ws 兜底通道 | OPEN 51ms |
| `15888` | tcp | 管理 RPC，**仅 127.0.0.1** | 已收回本地 |

客户端节点监听 `11010 tcp/udp`（仅供同局域网内直连，不需要经过公网）。

## 四、链路拓扑与选路

```
     ┌──────────── 公司有线 192.168.61.0/24 ────────────┐
     │  mini ◄──0.6ms──► studio ◄──0.5ms──► dev198     │   全部 p2p 直连
     └───────────────────┬──────────────────────────────┘
                         │ 48–52ms  (tcp+udp 双通道)
                         ▼
                  ┌─────────────┐
                  │  hk-relay   │  香港 · 发现 + 中继兜底
                  └─────────────┘
                         ▲
                         │ 待测（家侧节点未部署）
     ┌───────────────────┴──────────────────────────────┐
     │  linux-lan（家 有线）        air（移动）          │
     └──────────────────────────────────────────────────┘
```

**选路策略**：全节点 `latency_first = true`，按**实测延迟**选路而非跳数。

这个选择不是默认照抄——家是**中国移动**、公司是**北京联通**，移动↔联通跨网直连质量在国内长期不稳。
所以「打洞成功的直连一定比绕香港快」在这套网里**是个待验命题**，不能预设。
`latency_first` 让 EasyTier 自己按实测挑，而不是我们替它假设。

## 五、冗余设计

| 冗余点 | 做法 |
|---|---|
| 上游通道 | 每个节点同时配 `tcp://…:443` 和 `udp://…:22`，任一被中间网络掐掉仍能建链 |
| 公司侧子网网关 | mini 和 dev198 **同时**导出 `192.168.61.0/24`（故意的，不是配置重复），任一台关机不影响家里访问公司内网 |
| 局域网直连 | 公司三台互相配了静态 IP 的 peer，同网段直连不依赖香港节点 |

> 本方案**没有**添加任何公共 `--external-node`。这是刻意的：与「自建节点、发现过程可控」的目标一致。
> 代价是 hk-relay 挂掉期间新节点无法发现彼此（已建立的 P2P 链路不受影响）。

## 六、代理共存（macOS 上的 Clash / Xray）

三层，缺一不可：

1. **代理规则里为 VPS 公网 IP 单独放行**，且必须在虚拟段规则之前：
   ```yaml
   - IP-CIDR,207.57.124.191/32,DIRECT,no-resolve
   - IP-CIDR,10.10.10.0/24,DIRECT,no-resolve
   - IP-CIDR,10.10.61.0/24,DIRECT,no-resolve
   - IP-CIDR,10.10.1.0/24,DIRECT,no-resolve
   ```
2. **EasyTier 侧 `bind_device = true`**，出站 socket 绑物理网卡，绕开 TUN 路由劫持。
3. **不开 Magic DNS**（`accept_dns = false`），避免和 Clash 的 DNS 抢系统配置。

第 1 条里 VPS 公网 IP 那行是**原方案缺失的关键**：EasyTier 连的是 `207.57.124.191`，
它不在 `10.0.0.0/8` 里，原方案给的虚拟段 DIRECT 规则一条都管不到它。
