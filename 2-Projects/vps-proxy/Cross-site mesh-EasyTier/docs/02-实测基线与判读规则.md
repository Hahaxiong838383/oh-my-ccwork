### 1.3 NAT 类型（`easytier-cli peer` 实测）

| 节点 | NAT 类型 | 含义 |
|---|---|---|
| mini / studio / dev198 | **Symmetric** | 对称 NAT — 最难打洞的一类 |
| hk-relay | PortRestricted | 供应商防火墙只放行特定端口，STUN 探测被限所致 |
| linux-lan / air / hk-relay | **PortRestricted** | 端口受限锥形 —— 可与对称 NAT 打通 |

> **打洞成功的关键就在这张表**：公司侧三台全是对称 NAT（最难打洞），但家侧是端口受限锥形。
> 「对称 ↔ 端口受限」可以打通，只有「对称 ↔ 对称」才几乎无解。
> **家侧这台是整张网能直连的单点**：若哪天家里换路由器/运营商导致 NAT 变成对称，
> 家↔公司会立刻退化成走香港中继（~96ms），`mesh-status.sh` 会把这种退化标黄。

## 二、⚠️ 判读规则：不要用 ping 中继虚拟 IP 判断链路健康

**这是本次部署最容易误导人的一个读数，必须跟基线一起交付。**

现象：`ping 10.10.10.1`（中继节点自己的虚拟 IP）稳定丢包 **10–31%**。
但同一时刻同一目标：

- iperf3 TCP：**88 Mbits/sec，106 MB 只重传 45 次**（≈ 0.04%）
- 底层公网 ping 同一台机器：**0% 丢包**（100/100，两台节点各测一次）

**排除过的解释**：
- ❌ 「用户态 ICMP 限速」—— 把发包率从 5/秒降到 1/秒，丢包率**一点没变**（都是 30%），假设被推翻。

**A/B 实验（在 dev198 上做，做完已完整还原）**：

| 通道配置 | ICMP 丢包 | 隧道内延迟 |
|---|---|---|
| `udp + tcp` 双通道（当前生产配置） | 30% | **49 ms 稳定** |
| 仅 `tcp` | **0%** | **avg 394 ms / max 1680 ms**（pipe 9） |

TCP-only 的延迟爆炸是典型的 **TCP-over-TCP**：在 TCP 上承载 TCP，两层重传叠加，
一旦底层重传就整条队列堵住。**所以双通道是正确配置，不要为了「消灭丢包数字」去掉 UDP 通道。**

**「UDP/22 被中间设备限速」这个假设已被证伪**：面板加了 `udp 11010` 规则后换端口复测，
丢包 21.5%（11010）vs 18.5%（22），吞吐两边都是 ~86 Mbps —— **没有差别**。
该规则最终用于增加第三条冗余通道，是可用性收益，不是性能收益。

**机制至今未查明**，两个假设都倒了（限速、端口）。但它**不影响任何真实流量**，
所以不再投入排查，只保留下面的运维判读规则。

**运维上怎么办**：
- ✅ 判断链路健康用 `iperf3` 吞吐，或 ping **两个客户端节点之间**的虚拟 IP
- ❌ 不要用 `ping 10.10.10.1` 的丢包率做告警判据 —— 它会永远看起来像坏的

## 三、关于 EasyTier v2.6.4 本身的几条实测事实

这些在官方文档里查不到或与文档不符，都是本次实验得出的：

1. **`--check-config` 只验 TOML 语法，不验键名。** 注入不存在的顶层键或 `[flags]` 键，
   照样返回 PASS。所以它不能作为「配置正确」的证据。

2. **启动日志回显的 TOML 只显示与默认值不同的项。** `[flags]` 段看起来很短是正常的，
   **不代表配置没生效**。缺了这条判读规则，下一个看日志的人必然误判。

3. **`multi_thread` 和 `bind_device` 默认已是 `true`**（`--help` 说 multi-thread 默认单线程，是过时的）。
   用二分对撞验的：写 `= false` 会被回显，写 `= true` 不回显 ⇒ 默认即 true。

4. **`rpc_portal` / `rpc_portal_whitelist` 写在 TOML 里不被识别**（未知键静默丢弃）。
   必须用 CLI `--rpc-portal 127.0.0.1:15888` 覆盖，否则管理口裸奔在 `0.0.0.0:15888`。

5. **`tcp://0.0.0.0:443` 会自动同时监听 `tcp://[::]:443`**，双栈无需手写。
   （macOS 上 `0.0.0.0` 与 `[::]` 同端口会报一条 `AddrInUse` WARN，v6 socket 已收双栈流量，不影响功能。）

6. **`launchctl bootout` 是异步的**，返回时旧 job 常常还没销毁完，紧接着 `bootstrap`
   会得到 `Bootstrap failed: 5: Input/output error`，且失败后处于「新旧都没有」的状态。
   必须轮询确认消失后再 bootstrap（部署脚本已处理）。

7. **IPv6 在这套网里不是优先项**：公司侧无全局 IPv6；家侧有原生 v6 但到香港
   **v6 = 140ms vs v4 = 48ms**，慢 3 倍。留作备用通道，不做优先级倾斜。

8. **Web 控制台的设备列表，只显示「主动连过配置服务器」的节点。**
   节点从本地 TOML 启动是不会出现在里面的 —— 数据库里连 devices 表都没有，
   设备状态是 web 服务的**内存态**，靠 `--config-server` 那条活连接维持。
   要出现就得给每个 `easytier-core` 加：
   `--config-server udp://10.10.10.1:22020/<用户名>`（地址用虚拟网 IP，
   22020 不在供应商防火墙白名单里，公网打不进来）。

9. **`--config-server` 在 macOS 上会让服务起不来，Linux 上却没事。** 报错：
   `HOME is not set, cannot resolve machine id state directory`。
   该参数需要一个持久化的 machine-id，状态目录从 `$HOME` 解析；
   **systemd 会自动给 root 服务设 `HOME=/root`，launchd 不设任何环境变量**。
   修法：plist 里加 `EnvironmentVariables: HOME=/var/root`（macOS root 家目录，已实测确认）。
   这是「同一个参数在两个平台行为不同」的典型，只在一个平台验过就推全网必然出事。

10. **前端的 API Host 默认指向官方公共服务器 `https://config-server.easytier.cn`**，
    不是自建的这台，且从国内实测**连不通**（curl 返回 HTTP 000），
    表现为验证码图片加载不出来、注册提交无反应。
    要在登录/注册页把 API Host 手工改成 `http://10.10.10.1:11211`。
    ⚠️ `easytier-web-embed --api-host` **改不动它** —— 内嵌前端是预编译的，
    默认值写死在 JS 里（实测：JS 里搜不到 `11211`，也没有任何运行时配置端点，全 404）。

11. **判断「设备都上报了吗」不要看控制台的 Device Count。**
    在 VPS 上抓包才是独立通道：`tcpdump -ni easytier0 "udp port 22020"` 数不同源 IP；
    **中继节点自己的会话走 loopback**，要另外抓 `-ni lo` 才看得到 —— 只抓 easytier0
    会稳定少数一台，看起来像有个节点没上报。

## 五、吞吐分析：家→公司上行为什么只有 ~5 Mbps（2026-08-16）

**不是家宽上行不够（千兆宽带，标称上行 200Mbps），是丢包。**

单流 TCP 吞吐有硬上限，由 Mathis 公式决定：`≈ 1.22 × MSS / (RTT × √丢包率)`

| 参数 | 值 |
|---|---|
| MSS | 1320 B（EasyTier MTU 1360 − 40） |
| RTT | 18 ms |
| 丢包 | 3.3% |
| **理论上限** | **≈ 0.49 MB/s** |
| **实测单流** | **0.55 MB/s** |

误差 10% 以内。**在 3.3% 丢包下，一条 TCP 流下面有 200 Mbps 还是 200 Gbps 都跑不过 ~5 Mbps。**

判决性证据：**6 并发流跑到 3.14 MB/s（25 Mbps），近似线性叠加**。
若瓶颈是带宽，并发只会互相抢；能叠加就说明是丢包限制。

### 排除掉的其他解释

- ❌ **隧道开销**：同一对机器，走真实局域网 IP 2.85 MB/s vs 走 mesh 2.79 MB/s —— 差异≈0
- ❌ **MTU 1360 偏小**：影响每包效率约几个百分点，与 40 倍差距不在一个量级
- ❌ **VPS 上开 BBR**：该链路是 Air↔公司**直接 UDP P2P**，流量根本不经过 VPS

### BBR 的适用边界

BBR 只影响**本机作为发送端**时的行为，且只有 Linux 有：

| 路径 | 发送端 | BBR |
|---|---|---|
| linux-lan / fnos2 → 公司 | Linux | ✅ BBR 已配置；任务前仍需分别实时检查拥塞控制与实际接口 qdisc |
| dev198 → 家 | Linux | ✅ 已开（但该方向本就 113 Mbps 不慢） |
| **Air → 公司** | **macOS** | ❌ **macOS 不提供 BBR**，无解 |

⇒ 大文件从家传公司，默认**先在家庭 LAN 落到 linux-lan，再由它跨站发送**；fnos2 仅在实时验证 SSH 身份、磁盘、路由和拥塞控制后使用。
中转不会消除 Air 的 Wi-Fi 第一跳，但会把它缩短为局域网落盘，并让有线 Linux 独立完成可续传的长任务。Air↔公司曾观测到 `2–6%` 端到端丢包，Wi-Fi 是风险因素，不能写成已证明的唯一根因。

批量文件并发应从 4 路起测，再试 8 路；`rclone --transfers` 只增加文件级并发，单个大文件需另选后端并发或分块方案。完整 SOP 见 `~/mycc/.claude/skills/cross-site-file-transfer/SKILL.md`。
