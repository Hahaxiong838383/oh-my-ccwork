# 原方案评估与优化决策

> 评估对象：`野草云-EasyTier-异地组网完整方案.html`
> 评估时间：2026-08-16 · 评估人：cc
> **本文所有结论都标了证据来源。标「实测」的都在本次会话里跑过；没跑过的一律标「未验证」。**

---

## 一、结论先行

原方案的**技术选型是对的**（EasyTier + 自建共享节点，去中心化 Mesh，私有模式），架构图和目标描述也准确。
但它是一份**没有落地跑过的方案**——照着它一步步做，会卡在第一步且极难自查，因为最关键的失败点会伪装成另一个问题。

按严重度分三档：

| 档 | 数量 | 性质 |
|---|---|---|
| **P0 直接不通** | 3 项 | 照做必然失败，且症状具有强误导性 |
| **P1 安全** | 2 项 | 密钥泄露面 / 管理口裸奔 |
| **P2 正确性** | 2 项 | 会造成本地网络中断或规则失效 |
| **P3 缺失** | 4 项 | 没有验收标准、没有巡检、启动时序、平台冲突 |

## 二、P0：照做必然失败的三项

### P0-1 · 端口 11010 被供应商防火墙静默丢弃（最致命）

**原方案怎么写的**：VPS 上 `ufw allow 11010/tcp`、`ufw allow 11010/udp`，然后 `--listeners tcp://0.0.0.0:11010`。

**实际情况（实测 + 面板截图佐证）**：野草云在**面板侧**有一层供应商防火墙，面板明确写着
「当前产品不允许客户启用或关闭防火墙」。入站白名单只有 7 条：

```
tcp 22 · udp 22 · tcp 80 · tcp 443 · tcp 8888 · icmp · ipv6-icmp
```

VPS **内部**的 ufw 是 inactive、iptables 全 ACCEPT（实测），所以原方案教的 `ufw allow` 改的是一层
根本没在拦你的东西。真正拦你的那层，你在机器里看不见。

**实测证据**（三个独立视角，含期望成功的锚）：

| 端口 | 从家里 Air | 说明 |
|---|---|---|
| 22 | **OPEN 49ms** | ← 锚：已知必然开，证明探针可信 |
| 443 | **OPEN 48ms** | |
| 80 | **OPEN 51ms** | |
| 11010 | **TimeoutError** | 超时而非 RST ⇒ 被丢包，不是端口没开 |
| 15888 | TimeoutError | |

**为什么这条最危险**：TCP SYN 被静默丢弃的症状（客户端一直 `Connecting`、日志只有超时）
与「NAT 打洞失败」**完全同形**。按原方案排查，你会一路怀疑 NAT 类型、怀疑运营商、怀疑 EasyTier，
唯独不会怀疑那个你在机器里 `iptables -S` 看得清清楚楚全是 ACCEPT 的防火墙。

**优化决策**：**不去面板加规则，直接把服务落到已放行端口**。

```toml
listeners = [
    "tcp://0.0.0.0:443",   # 主 TCP
    "udp://0.0.0.0:22",    # 主 UDP（与 sshd 的 tcp 22 不冲突，实测）
    "ws://0.0.0.0:80",     # WebSocket 兜底
]
```

这不只是绕开限制，**本身就是对你「P2P 稳定性」目标的正向优化**：443/80 是全世界最不可能被
中间设备拦截的端口，公司网、酒店 WiFi、蜂窝网、机场网络一律放行。把节点间的会合点放在这两个
端口上，等于把「能不能建链」这件事的失败面砍掉一大半。

> 若日后想额外开 11010，面板「添加规则」还有 93 条余量。但不必要——现在这套已经全通。

### P0-2 · `-d` 不是「后台运行」，是 `--dhcp`

**原方案怎么写的**：客户端命令 `sudo easytier-core -d --network-name ...`，上下文当成后台运行。

**实际（`easytier-core --help` 原文）**：

```
-d, --dhcp [<DHCP>]
    automatically determine and set IP address by Easytier, and the IP address
    starts from 10.0.0.1 by default. Warning, if there is an IP conflict in the
    network when using DHCP, the IP will be automatically changed.
```

真正的后台参数是 `--daemon`。

**连带矛盾**：原方案第 3 节写「建议 10.10.10.0/24」，第 5 节又用 `-d`。这两者互斥——
开了 DHCP，IP 由 EasyTier 自动分配且**冲突时会自动改**，你规划的网段和固定 IP 全部作废。
后果是「今天 SSH 得通的地址，明天变了」，而且不报错。

**优化决策**：全部节点用 `ipv4 = "10.10.10.X"` 显式固定，不用 DHCP；后台交给 systemd / launchd。

### P0-3 · 子网代理是空头支票

**原方案怎么写的**：第 7 节「组网后可实现的效果」列了「打印机、NAS 等可被任意设备访问」。

**实际**：全文没有任何 `--proxy-networks` / `[[proxy_network]]` 配置。没配这个，
只有装了 EasyTier 的机器能互访，NAS、打印机、路由器后台一台都够不到。承诺的效果拿不到。

**更糟的是照直觉补也会出事**。如果按最自然的写法直接导出：

```toml
[[proxy_network]]
cidr = "192.168.1.0/24"     # ← 危险
```

那么 **Air 在家时物理上就在 192.168.1.0/24**，它会收到一条指向隧道的 `192.168.1.0/24` 路由，
覆盖掉自己的本地网络——家里的网当场断，且断的方式看起来像「EasyTier 把网搞坏了」。
公司侧同理：studio / dev198 本身就在 192.168.61.0/24。

**优化决策**：必须做 CIDR 映射，把被导出的真实网段映射到一个全网都不会撞的虚拟段。

```toml
[[proxy_network]]
cidr = "192.168.61.0/24"
mapped_cidr = "10.10.61.0/24"    # 家里用 10.10.61.18 访问 QNAP(192.168.61.18)
```

网段冲突已逐条核对，见 [`01-架构与网段规划.md`](01-架构与网段规划.md)。

## 三、P1：安全

### P1-1 · network_secret 明文进 systemd unit

原方案把 `--network-secret YourStrongSecretHere` 直接写进 `/etc/systemd/system/easytier.service`。
该文件默认权限 **644**，机器上任何本地用户 `cat` 一下就拿到全网密钥——拿到就能加入你的整张网。

**优化决策**：密钥只存在于 `/etc/easytier/node.toml`（**600 root:root**），
unit 里只出现文件路径。密钥源头在 `~/.mycc-secrets.env`（600，不进 git），
部署脚本用 stdin 通道下发，**不经过命令行参数**（`ps` 可见即泄露）。

### P1-2 · RPC 管理口裸奔，而且改不掉（坑中坑）

EasyTier 默认把管理 RPC 开在 `0.0.0.0:15888`。原方案没提这件事。

我按常理在 TOML 里写了 `rpc_portal = "127.0.0.1:15888"`，`--check-config` **返回 PASS**，
重启后 `ss` 一看仍然是 `0.0.0.0:15888`——**这个键名根本不被识别，被静默丢弃了**。

**根因（实测）**：`--check-config` 只校验 TOML **语法**，不校验键名。见下面第五节的实验。

**优化决策**：用 CLI 参数覆盖（CLI 由 clap 定义，是权威通道）：

```
ExecStart=/usr/local/bin/easytier-core -c /etc/easytier/node.toml --rpc-portal 127.0.0.1:15888
```

实测已收回到 `127.0.0.1%lo:15888`。

## 四、P2：会造成实际故障的两项

### P2-1 · 代理规则那一节，解决的不是真正的问题

**原方案给的规则**：

```yaml
rules:
  - IP-CIDR,10.0.0.0/8,DIRECT,no-resolve
  - IP-CIDR,192.168.0.0/16,DIRECT,no-resolve
```

这解决的是「**访问虚拟内网 IP 时不要走代理**」。但真正会让你连不上的是另一件事：

> **EasyTier 自己去连 VPS 时，连的是 `207.57.124.191` 这个公网 IP——它根本不在 `10.0.0.0/8` 里。**

Clash/Mihomo 开 TUN 模式后会接管默认路由，EasyTier 的出站被卷进代理，
表现为「建链慢 / 时断时续 / 延迟莫名多几十毫秒」，而你按原方案加的规则一条都管不到它。

**优化决策**（两层，缺一不可）：

1. 代理规则里**为 VPS 公网 IP 单独放行**，并放在虚拟网段规则之前：
   ```yaml
   - IP-CIDR,207.57.124.191/32,DIRECT,no-resolve   # ← 关键，原方案缺这条
   - IP-CIDR,10.10.10.0/24,DIRECT,no-resolve       # 虚拟主网段
   - IP-CIDR,10.10.61.0/24,DIRECT,no-resolve       # 公司映射段
   - IP-CIDR,10.10.1.0/24,DIRECT,no-resolve        # 家庭映射段
   ```
   注意用**精确网段**而不是原方案的 `10.0.0.0/8`——后者会顺手把一大片无关地址也变成 DIRECT。

2. EasyTier 侧开 `bind_device = true`，把出站 socket 绑到物理网卡，从根上绕开 TUN 路由劫持。
   （实测 v2.6.4 该项**默认已是 true**，但我们显式写出来，防止未来默认值漂移。）

### P2-2 · `After=network.target` 时序不足

原方案 unit 用 `After=network.target`。这个 target 只保证网络**栈**起来了，
不保证接口拿到 IP。开机时 EasyTier 可能在没有地址的情况下启动，bind 公网监听失败。

**优化决策**：`After=network-online.target` + `Wants=network-online.target`。

## 五、实测过程中反证掉的几条「常识」

这一节记录的是**我自己原本打算写进方案、但被实测推翻的推断**。

### 5-1 · `--check-config` 通过 ≠ 配置正确

负向验证结果：

| 注入内容 | `--check-config` | 结论 |
|---|---|---|
| 顶层写一个不存在的键 | **PASS** | 未知键被静默忽略 |
| `[flags]` 写一个不存在的键 | **PASS** | 同上 |
| 故意的 TOML 语法错误 | FAIL | 只拦语法 |

**所以 `CHECK_PASS` 只能证明「这是合法 TOML」，不能证明「这些键 EasyTier 认识」。**
把它当配置正确性的判据，就会像 P1-2 那样：配置写了、检查过了、参数根本没生效、全程无红灯。

### 5-2 · `multi_thread` 和 `bind_device` 的默认值，文档是错的

`--help` 写 `multi-thread ... default is single-thread`。用二分对撞实测（EasyTier 启动时会
回显它实际加载的 TOML，且**只回显与默认值不同的项**）：

| 写入 | 是否被回显 | 推出 |
|---|---|---|
| `multi_thread = false` | ✅ 回显 | 键名有效，且**默认是 true** |
| `multi_thread = true` | ❌ 不回显 | 等于默认值 |
| `bind_device = false` | ✅ 回显 | 键名有效，且**默认是 true** |
| `bogus_flag_name = true` | ❌ 不回显 | 未知键确认被丢弃 |

结论：v2.6.4 的 `multi_thread` / `bind_device` **默认已经开**，`--help` 的描述过时。
原方案没设这两个参数，其实并没有损失——但也不是因为它想对了。

> **附带一条判读规则（必须跟配置一起交付）**：启动日志里的 TOML 回显**只显示非默认值**。
> `[flags]` 段看起来很短是正常的，**不代表配置没生效**。没有这条规则，下一个看日志的人必然误判。

### 5-3 · 「IPv6 更好」在这套网里不成立

我原本准备把「双栈 + IPv6 优先」写成 P2P 稳定性的头号杠杆。实测：

| 站点 | 公网 v4 出口 | IPv6 |
|---|---|---|
| 家（linux-lan） | 120.244.92.131 中国移动 | ✅ 原生 `2409:8a00:8470:f480::/64` |
| 公司（mini 有线） | 222.128.47.46 北京联通 | ❌ 无全局 v6 地址 |
| 公司（dev198） | — | ❌ 无全局 v6 地址 |
| 香港 VPS | 207.57.124.191 | ✅ 原生 |

两个反驳：

1. **公司侧根本没有 IPv6**，所以 v6 无法用来打通「家↔公司」这条最关键的链路。
2. 即便家↔香港这条能走 v6，**实测 v6 反而更慢**：`v6 443 = 140ms` vs `v4 443 = 48ms`，
   慢 3 倍（移动的 v6 到香港绕路了）。

所以本方案**不把 IPv6 设为优先路径**。EasyTier 会自动双栈监听（实测 `tcp://0.0.0.0:443`
会同时加上 `tcp://[::]:443`），留着当备用通道即可，不做任何优先级倾斜。

### 5-4 · 「P2P 一定比走中继快」——这套网里是个待验命题

家是**中国移动**、公司是**北京联通**。移动↔联通跨网互访质量差是国内长期存在的问题。
所以「打洞成功 = 更快」在这里**不能默认成立**：直连可能比绕香港还慢。

而且实测 mini 的 NAT 类型是 **Symmetric（对称 NAT）**——最难打洞的一类。

这正是把 `latency_first = true` 设为全局默认的原因：它按**实测延迟**选路，而不是按跳数。
真实数据要等家侧节点上线后跑基准才有，见 [`03-验收与调优.md`](03-验收与调优.md) 的 A/B 流程。
**在拿到数据之前，本方案不对「该走直连还是走中继」下结论。**

## 六、P3：原方案缺失、本项目补上的东西

| 缺失 | 补法 |
|---|---|
| 没有验收标准（什么叫"装好了"） | `deploy-node.sh` 内置**四项断言**，任一不过即失败退出 |
| 没有巡检 | `mesh-status.sh` 逐节点取视角，链路降级成 relay 立即标黄 |
| 没有基准 | `bench.sh` 跑吞吐/延迟，并做 KCP 开关的 A/B |
| 没有配置版本管理 | 配置模板全部进 git，密钥用占位符，部署时渲染 |
| 没有卸载路径 | `uninstall-node.sh`（先想好怎么回来，再动手） |

关于验收断言，有一条是本次部署**真踩出来**才加的：

> 首次部署 mini 时，我的客户端模板漏了整个 `[network_identity]` 段。节点用默认值加入了
> 一个名为 `default`、密钥为空的网络。此时 **进程 active ✅ / TUN 拿到虚拟 IP ✅ /
> connector 状态 `Connected` ✅** ——三项全绿，唯独 peer 表里只有自己。
> 因为 TCP/UDP 通道建得起来，不过的是握手鉴权。
>
> 当时脚本第 3 步只**打印** peer 表、不**断言**，于是假绿灯直接放行。
> 所以现在的验收必须包含一条**只有真的入网才可能满足**的判据：至少看见 1 个远端 peer。

## 七、保留了原方案的哪些判断

不是全盘推翻。以下这些原方案是对的，本项目原样继承：

- **选 EasyTier**：跨平台、P2P 能力强、支持私有模式、资源占用低——选型没问题。
- **`--private-mode true`**：只有持同一 network_name + secret 的节点能握手/中继，避免变成公开中继。
- **自建共享节点而非用公共节点**：数据与发现过程可控。本项目**没有**添加任何公共 `--external-node`，
  与原方案「数据不经过第三方控制平面」的目标一致。
- **每台设置有意义的 hostname**：直接采纳。
- **架构图的数据流描述**（P2P 实线 / 发现中继虚线）是准确的。
