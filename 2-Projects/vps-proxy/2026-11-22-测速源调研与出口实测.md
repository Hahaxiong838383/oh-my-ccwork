| hetzner_sg 1GB.bin | **9.73** | 1.01 | 1.95 | Range 206 正常 |
| hetzner_fsn 100MB.bin | 7.02 | 0.63 | 2.44 | 欧洲源站 |
| cloudflare 50MB | 9.93 | 1.20 | 0.77 | HK 连测 3 次 10.0/10.1/10.1，最稳 |
| leaseweb hkg 100mb | 12.84 | 0.75 | 0.58 | 仅 HTTP，本地 PoP |
| vultr hnd 100MB | 1.82 | 0.70 | 0.63 | 慢 |
| proof.ovh.net 100MB | 2.54–6.53 | 0.57 | 2.02 | 抖动最大 |
| ash-speed.hetzner.com 100MB | 2.4–6.0 | — | — | 美东，抖动 ±30% |
| github drawio 99MB | 8.86–9.69 | 1.22–1.31 | 2.02–2.56 | 需 `-L` |

关键判读：

1. **同一个链路，换目标就会改变排名**：hk-hy2 上 google=11.0 > cf=9.9 > hetzner_sg=9.7；而 rack-hy2 上 cf=1.20 > google=0.92。所以"用哪个源"会直接改变出口选择的结论 → 必须固定主指标。
2. **时变性大于目标差异**：zgo-hy2 的 google 在 20 分钟前是 2.16–2.33 MB/s，现在是 0.74 MB/s。**单次采样不足以判决出口好坏**，至少要 2–3 轮交替采样。
3. **HK 出口 ≈ 10 MB/s（80 Mbps）**，另外两条 ≈ 0.6–2 MB/s（5–16 Mbps）——后者根本不够 4K。

## 三、比选站点更重要的方法论（实测证据）

### 3.1 小文件会低估 4–5 倍

HK 直连（同一台机器、同一条链路）对 Cloudflare 测三种大小：

| 请求 | curl 报的 speed_download | 真实吞吐 size/(total−ttfb) |
|---|---|---|
| 1,000,000 B | 5.28 MB/s | **24.4 MB/s** |
| 10,000,000 B | 18.09 MB/s | **24.6 MB/s** |
| 50,000,000 B | 22.95 MB/s | **24.4 MB/s** |

真实吞吐恒定 24.4 MB/s；`speed_download` 把 TCP+TLS+首字节（ttfb≈0.13–0.15s）算进了分母。
**1MB 文件低估 4.6 倍**。原用 `10Mb.dat`（10MB）在慢链路上同样低估 → 阈值失真。

### 3.2 因此的采信规则

- 文件 **≥ 50 MB**（8 秒窗口在 10 MB/s 下要 80 MB 才截不完；50MB 已把误差压到 7% 内）
- 优先 `size/(time_total − time_starttransfer)` 而不是裸 `speed_download`
- `-H 'Accept-Encoding: identity'`（禁压缩，否则 body 变小数）
- **不跟随重定向**（`--max-redirs 0`），除非明确用 GitHub（需 `-L`，且链接会 302 到带签名的临时地址）
- 一次判决至少 3 轮交替采样

### 3.3 可直接用的模板

```bash
probe() {  # probe URL BYTES
  curl --http1.1 --max-redirs 0 --max-time 8 \
    -H 'Accept-Encoding: identity' \
    --range "0-$(( $2 - 1 ))" -o /dev/null \
    -w 'code=%{http_code} size=%{size_download} speed=%{speed_download} ttfb=%{time_starttransfer} total=%{time_total} ip=%{remote_ip}\n' \
    "$1"
}
# 主指标
probe 'https://dl.google.com/go/go1.23.0.linux-amd64.tar.gz' 104857600
# 中立国际源站（Range 206）
probe 'https://sin-speed.hetzner.com/1GB.bin' 104857600
# 快检（不要加 Range，加了也忽略）
curl -s --max-time 8 -H 'Accept-Encoding: identity' \
  'https://speed.cloudflare.com/__down?bytes=50000000' -o /dev/null \
  -w 'code=%{http_code} size=%{size_download} speed=%{speed_download}\n'
```

### 3.4 门槛（4K）

YouTube 帮助中心：4K 持续约 20 Mbps（≈2.5 MB/s）——[观看网速要求](https://support.google.com/youtube/answer/78358?hl=zh-Hans)。
上传建议里的 53–68 Mbps 是片源码率，不能当播放门槛（[编码建议](https://support.google.com/youtube/answer/1722171?hl=en)）。

- 切换线：< 2.5 MB/s 且连续两轮 + 快检同样低
- 健康线：≥ 4 MB/s（32 Mbps），留余量给 QUIC/多流竞争

### GitHub 作为测速源的取舍（两边结论都保留）

- grok 侧：`github.com/...` 是 **302**，落地 `release-assets.githubusercontent.com`，响应头 `Windows-Azure-Blob` / `Via: varnish` / `X-Cache: HIT` → **Fastly 边缘缓存**；签名 URL 约 1 小时过期，不能硬编码进 cron；`codeload.github.com` 忽略 Range。
- 本机实测：跟随重定向后 **200、99 MB @ 8.86–9.69 MB/s（hk-hy2）**，完全可用。
- 结论：**可做第三源，不做主源**（需 `-L`、资产可能被删、边缘缓存掩盖国际段）。

## 七、优化落地（2026-11-22 晚，已上线）

### 7.0 结论：电视现在拿到的带宽从 9 → 17–19 MB/s，出口固定在最快的 hk-hy2

| 时点 | 出口 | 实测（Google 25MB 串行） | CPU idle |
|---|---|---|---|
| 优化前 | zgo-hy2（选择器停在这） | 0.6–2.4 MB/s | 34% |
| 优化中 | hk-hy2 | 8–11 MB/s | 34%（受日志自旋压制） |
| **优化后** | **hk-hy2** | **16.8 / 19.0 / 16.9 MB/s（≈135–152 Mbps）** | **95.8%** |

### 7.1 真正的瓶颈不是出口，是网关被日志自旋吃掉了 1.5 个核

- `/var/log` 是 **47M 的 zram 卷**（armbian-ramlog，`/etc/default/armbian-ramlog` SIZE=50M）。
- 它被写满 → `rsyslogd` 每条日志都 `No space left on device` → 它把报错再写进 journal → journal 再被 rsyslog 读回 →
  **自旋**。实测：`rsyslogd` 106–175% CPU、`systemd-journald` 54%，**5 分钟产生 5 万条日志**，load 4.9/4 核。
- 处置：停 rsyslog → 清空 `/var/log/syslog`（42M）→ 重启 rsyslog（立省 1.5 核）；
  `SIZE` 改 192M（**需重启才生效**，当前 47M 也够用，因为日志级别已降到 warn）；
  新增 `dsh-log-guard.timer`（每 5 分钟，>85% 自动截断并重启 rsyslog），防止复发。
- 生产 sing-box 日志级别 `info` → `warn`，噪声大降。

> 教训：**"带宽不够"要先看 CPU 和磁盘。** 同一台机器、同一个出口，仅修掉日志自旋，吞吐就从 9 MB/s 回到 19 MB/s。

### 7.2 出口选择器：v3（卡了才轮下一个）→ v4.1（实测带宽择优）

- 侧车：`dsh-probe.service` 跑第二个 sing-box，把 5 条出口各映射成一个 SOCKS 口（19201–19205），
  配置由 `dsh-gen-probe.py` 从生产 config 自动生成；**测量全程不碰生产选择器**，不影响正在播放的流。
- `dsh-pick-exit.sh v4.1` 逻辑：
  1. 每 10 分钟只体检**当前出口**（Google 12MiB / 5s，低于底线复测一次防冷启动误判）；
  2. 需要时才全量扫描：当前 < 2.5 MB/s、电视卡顿（state=6 或码率<2Mbps）、或满 6 小时；
  3. 全量 = 5 条出口**并行探路**（8MiB×2 轮）排序 → **前二串行复测**（25MiB/6s，取绝对值）；
  4. 新出口须 ≥ 当前 ×1.25 且 ≥ 2.5 MB/s 才切；**切换后复验，验不过自动回滚**。
- 一次全量扫描 ≈ 27s（并行探路 12s + 串行复测 12s + 交叉源）。
- 4K 门槛：YouTube 官方 20 Mbps = 2.5 MB/s；健康线 4 MB/s（32 Mbps）。

### 7.3 1 分钟存活看门狗

`dsh-watch-exit.timer` → `dsh-watch-exit.sh`：每 60s 用当前出口打一发
`https://www.youtube.com/generate_204`（约 0 字节，几乎不耗流量）。
连续 2 次失败 → 触发全量择优。实测：把选择器强行指到死出口 `hk-reality-test` 后，
看门狗 66s 内自动切回 hk-hy2 并复验通过（日志：`switch hk-reality-test(0.0MB/s) -> hk-hy2(9.46MB/s verified=9.55)`）。

### 7.4 清掉两个死出口 + 开机默认值

| 出口 | 状态 | 处置 |
|---|---|---|
| `hk-v6`（2001:df1:7880:6::1ca:8445） | 网关无可用 IPv6 出口：ICMPv6 通、TCP/443 全 000 | 从 outbounds 与 auto/proxy 成员中移除 |
| `hk-reality-test`（10.10.10.1:8445） | 端口开放但 VLESS 握手失败，000 | 同上移除（hy2 已覆盖 HK，无需 REALITY） |

- `proxy` 选择器加 `"default": "hk-hy2"`：**重启/断电后直接落在最快出口**，不再默认 `auto`（urltest 按延迟挑，会挑到近而慢的出口）。
- 生产配置备份：`/etc/dsh-gateway/config.json.bak-20261122`；旧选择器备份：`/usr/local/sbin/dsh-pick-exit.sh.v3.bak`。

## 八、更正与澄清：`hk-v6` 到底坏在哪（2026-11-22 深夜复核）

上一轮我写「网关无可用 IPv6 出口」过粗，复核后分三层：

| 层 | 实测 | 判断 |
|---|---|---|
| 野草云 HK 的 IPv6 | `2001:df1:7880:6::1ca/64` 在位；`curl -6 https://ifconfig.co/ip` → **200，返回自身 v6 地址** | **野草云 v6 健康** |
| 家 → HK 的 v6 路径 | `ping6` 0% 丢包 82ms；v6 上 **22/80/443/8443/8444/8888 全部 3/3 或 10/10 可建连** | 路径基本可用 |
| HK 的 xray 端口 | v6 上 **8445 = 0/3、0/10，8446 = 0/3**；同一 8445 在 **v4 上 OPEN** | **端口级过滤** |
| HK 本机策略 | `ip6tables -S` 全 ACCEPT、`ufw inactive`、`*:8445` 正常监听、`::1:8445` 本机可连 | 排除野草云防火墙 |
| 网关 AAAA 解析 | `getent ahostsv6 dl.google.com` 空；`www.cloudflare.com` 只回 `::ffff:` v4-mapped | **AAAA 被有意抑制**（`dns.strategy=ipv4_only`，为防电视拿 AAAA 直连出境踩坑，见 2026-11-21 教训 #3） |

结论：
1. **不是野草云 IPv6 坏**，是「家里→HK」这段对 **8445/8446 两个代理端口**的过滤（v4 同端口正常），
   而 `hk-v6` 出口恰好写死 `2001:df1:7880:6::1ca:8445` → 必然 000。
2. 我上一轮"`curl -6` 全 000"里混了 **DNS 假信号**（AAAA 被有意关掉），已更正。
3. 复活 `hk-v6` 的前提是：在 HK 上给 v6 单独开一个**非 844x 的端口**（8888/8443 之类可达端口），
   并且网关侧只对该出口用字面地址、不放宽全局 AAAA。
4. **当前不建议做**：收益不明（hk-hy2 已 16–19 MB/s），却要重新碰「安卓拿 AAAA 直连」的历史坑。保持 `hk-v6` 移除状态。

| 尝试 | 结果 |
|---|---|
| VLESS + REALITY（与 8445 同密钥/SNI `www.microsoft.com`） | 网关侧 `reality verification failed`，三采全 000 |
| 同参数换 **xray 客户端**（HK 本机 → `[::1]:19443`） | **200 通过** → 服务端 REALITY 配置没问题 |
| 降到 MTU 1400 再试 REALITY | 仍 000（不是 MTU/黑洞） |
| 改成 **VLESS + TLS**（LE 证书 `derp.hahaxiong.cc`，uTLS chrome，alpn h2/http1.1） | **206，13.9 / 13.7 MB/s** |

结论：**网关 sing-box 1.14.4 与 Xray 26.11.9 的 REALITY 握手不兼容**（这也解释了之前 `hk-reality-test` 一直 000）。
`hk-v6` 因此走标准 TLS，不用 REALITY；老的 8445 REALITY inbound 原样保留（给手机/其他客户端用）。

### 9.4 自动化

- `dsh-hkv6.timer`（10 分钟）→ `dsh-enable-hkv6.sh`：检测 19443 可达即自动接入（幂等，已启用则静默退出）
- 出口清单单一真源 `/etc/dsh-gateway/probe-exits`，选择器与看门狗都从它读，加/删出口只改这一处
- 探针侧车现有 6 条出口 SOCKS 口（19201–19206），全量扫描 ≈37s

### 9.5 遗留

- hk-v6 的 v6 路径有突发卡顿，暂列备路；晚高峰若 hy2 掉速，选择器会按实测自动切过去。
- HK 上 19443 用的是 LE 证书，续期后需把新证书复制到 `/etc/xray/tls/`（xray 以 `xray` 用户运行，读不到 `/etc/letsencrypt`）。
