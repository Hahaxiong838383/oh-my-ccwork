## 最值得保留的教训

| 误判或遗漏 | 本次证据 | 后续做法 |
|---|---|---|
| 系统 DNS 正常就认为 APP 正常 | SmartTube 32.68 开启 Google 明文 DNS，走独立解析器与进程缓存；系统 flush 不覆盖它 | 先核实际版本、有效 profile、解析分支，再验证同一 APP 的首页和实播；不把 helper 成功当应用成功 |
| 改一次偏好就认为会保持 | 运行后 DNS1 回到2；已装版本的长缓冲处理存在强制 Google DNS 路径，但未捕获本次对应分支日志 | 修改设置时找所有写入方；使用原生“禁用自动网络错误修复”，清楚记录它同时影响两类自动切引擎；重开后和实播后均回读 |
| 读源码 HEAD 代替已安装版本 | 32.68 长缓冲处理是 restartEngine，新 HEAD 才是 restartTheApp | 固定 APK 对应主仓与子模块 commit，序列化字段、分隔符、profile 键都按该版本核对 |
| 交互 shell 测过就认为开机可用 | post-fs-data 主规则成功，异步 watcher 的 dirname 路径失败；断电时 system iptables 也曾暂不可用 | 使用纯 shell 路径计算、绝对 BusyBox；测试无效 PATH 下的真实入口及后台子进程，保留有界重试。最后仍须新 boot 的 audit_ready |
| Linux 工具兼容就认为 Android 兼容 | 该 Magisk BusyBox flock 不支持 -w 或数字 FD 模式 | 用设备实测的 pathname+command 模式，并在隔离测试禁用不支持能力；真机独立 netns 验规则和计数 |
| iptables 规则存在就代表保护有效 | 更早的 RETURN/ACCEPT、netd 插入的 OUTPUT 钩子可抢先匹配 | 核链内有序前缀和 OUTPUT 首钩，处理 -S 的规范化；双栈 TCP/UDP 都覆盖，校时 mark255 例外单独验证，失败不撤保护 |
| 缓存配置开启就认为实际命中 | 软件启动后 fd 打开和新域名写入已验；断电后文件使用已验，旧过期记录未找到 | 分开记录配置、文件打开、真实写入、跨启动查询命中。旧条目过期不算持久化失败；文件存在也不算命中。CDN 不锁固定地址 |
| 墙钟或 logcat monotonic 永远可信 | 断电日期回2024，校至2026后早期 monotonic 事件变负数 | 以同 boot 内核 startticks / 实测 CLK_TCK 比较启动时序，前后核 PID/boot 身份不变 |
| 解码帧增长就算 SmartTube 播放通过 | 新开机先播放 DIYP 直播，之后用户才打开 SmartTube；画质对话框也可覆盖持续播放 | 结合前台包名、APP PID、codec 与连续帧取证；换片分段，驱动宽高0不推断分辨率 |
| 仓库或旧 stage 总是当前运行真源 | 两个启动脚本追加修正在9文件release事务之外 | 核运行目录、release和当前SHA；外部脚本查 boot-assets-current.json。未来改9文件之一须同步更新/退役迁移事务，避免下次开机漂移拒启 |

## 本次验到哪里

- 三项：SmartTube 系统 DNS/IPv4优先；Magisk 早期双栈 DNS 保护；sing-box 1.14.3 store_dns 与 optimistic 5分钟。
- 隔离验证：66项保护/boot断言、26项真实缓存断言、17项事务测试、15项集成断言、6项接线测试；另有 Android 独立 netns 与合成事务 apply/rollback。
- 软件重启后新域名查询使生产缓存出现相应记录，文件 SHA/mtime 改变；实际进程 fd 打开该文件。
- 用户断电后新 boot：保护8.26秒、SmartTube进程29.67秒、校时52.66秒、完整DNS78.89秒、启动审计79.64秒；一次早期工具不可用及时间源重试自行恢复。
- SmartTube DNS1及禁自动修复true保持；最后2560×1440实播，连续帧2369→3018→3664、丢帧和软硬解码错误0。保留的1935行日志中八类网络/证书/播放异常0。

短期观察不等于长期稳定；本轮没有实测生产缓存跨启动查询命中、主出口在实播中故障迁移、Netflix回归或提速百分比。
720p/1440p样本不表示更改了用户的默认画质；本轮没有调整画质。
