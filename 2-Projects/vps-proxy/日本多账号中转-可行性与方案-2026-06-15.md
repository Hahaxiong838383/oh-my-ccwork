# 日本服务器自建 ChatGPT Pro 多账号中转 — 可行性分析与方案

> 2026-06-15 | team 三发对抗评审（grok-4.3 / gpt-5.5 / gemini-3.1-pro）+ cc 综合 + 独立 WebSearch 交叉验证
> 目标机：阿里云轻量日本东京（别名 `aliyun-jp`，2vCPU / 1GiB RAM / 30G SSD / 0 swap，已安全加固）

---

## 结论（先行）

**技术上可行，但有两个硬门槛：① 必须加 2GB swap（否则必 OOM）② ChatGPT Pro 多账号 API 化聚合违反 OpenAI ToS，封号风险是头号风险、不可消除、只能自担。**

**主方案不是上 Sub2API/LiteLLM 这类重栈，而是扩展你已跑通的 389 行 Python wrapper**（加账号池 + sticky），内存可焊死在 ~200MB。三家引擎一致推荐此路。

---

## 一、可行性判断：加 swap 后可行，1G 内存是生命线

当前机器仅 **~530MB 可用内存 + 0 swap**。三家一致结论：**裸跑任何带 dashboard + 多账号的栈 99% OOM**。

内存预算（三家估算综合）：

| 组件 | 内存 | 说明 |
|---|---|---|
| OS 基础（Ubuntu+sshd+systemd） | ~450-500MB | 已占，压不下去 |
| Docker daemon + containerd | 70-130MB | 装 Docker 的代价 |
| Tailscale | 30-80MB | 网络层 |
| 扩展版 Python wrapper（含账号池） | 80-200MB | 主服务，可控 |
| SQLite + 内置 dashboard | <50MB | 轻量 |
| **合计新增** | **~250-450MB** | **超出当前 530MB → 必须 swap** |

→ **必须先挂 2GB swap**（SSD 性能尚可，应对 Python GC 峰值 + 低频 dashboard 查询足够）。这是低配机跑流式 LLM 服务的生命线，不是让服务长期靠 swap 跑。
→ 若后续并发上升或要完整 metrics，建议升到 2GiB RAM。

## 二、方案选型：扩展现有 wrapper（主）

| 方案 | 内存 | 评价 | 决策 |
|---|---|---|---|
| **扩展现有 Python wrapper + SQLite** | ~200MB | 已跑通最难的 codex app-server(WS)→SSE→OAuth；加账号池+sticky 是增量；零重型依赖 | **✅ 主方案（三家一致）** |
| LiteLLM | 300-500MB | 真实成熟标杆，但①对本场景偏重②不天然解决"订阅后端 API 化"③sticky 到具体账号仍要自己实现 | ❌ 1G 上必崩 |
| Sub2API | 重（PG+Redis） | 真实活跃，但是带支付/拼车/用户系统的**重平台**，你自用 2-3 账号功能过剩 | ❌ 内存不够+过剩 |
| CLIProxyAPI | 中（Go） | 真实最活跃，Go 省内存、原生 Codex+多账号 OAuth；但引入新栈+维护未知 | 🔸 备选/PoC 对象 |
| codex-lb | 中（FastAPI） | 真实、最专注 Codex 多账号；活跃度偏低 | 🔸 备选/PoC 对象 |

**为什么主方案是"扩展现有"**：最大的未知风险不是"会不会写网关"，而是 ChatGPT 后端适配 / OAuth / SSE / Codex 兼容——**这些你的 389 行 wrapper 已经全部验证过了**。在已验证的轻量基座上增量最稳、最省内存、最可维护。

## 四、推荐架构 + sticky 机制

```
多台 Codex CLI（含隔离网络机）
        │ OpenAI 兼容 HTTP / SSE
        ▼
   Tailscale 内网（WireGuard，不开公网端口）
        ▼
 ┌─────────────────────────────────────┐
 │  日本机 aliyun-jp（+2G swap）         │
 │  扩展版 Python wrapper（单进程 async）│
 │   ├─ 账号池: Pro 账号 A/B/C (OAuth)  │
 │   ├─ sticky 路由（解析 conv_id）     │
 │   ├─ 健康/限速/cooldown/用量         │
 │   ├─ SQLite（映射表+用量）           │
 │   └─ 内置 /admin dashboard (静态HTML)│
 │            │ 各账号 codex app-server  │
 │            ▼                          │
 │       OpenAI/ChatGPT 后端（日本IP直连）│
 └─────────────────────────────────────┘
        │ fallback（日本挂了切美西）
        ▼  美西 racknerd 现有单账号 wrapper
```

**sticky 核心（三家一致，关键技术点）**：必须在 **Python 代码层解析请求体的 `conversation_id`** 做路由——Nginx/Caddy 层做不到（要解析 JSON body）。
- 新对话 → 选健康账号轮询/加权 → 写 `conv_id → account` 映射进 SQLite
- 已有对话 → 查映射强制回原账号；原账号不可用 → 返回明确错误（不默认换账号，否则上下文错乱）
- 流式中途不换账号、retry 不换账号

## 五、新旧架构关系：日本主用 + 美西 fallback（我的推荐）

| 选项 | 谁主张 | 取舍 |
|---|---|---|
| **日本主用 + 美西 fallback** | grok + gpt（2票）+ cc | 日本是单点 + 订阅中转不稳定因素多 + 封号风险，保留已验证的美西兜底几乎零成本 |
| 全量迁移废弃美西 | gemini（1票） | 延迟决定体验（70ms vs 194ms），但牺牲了兜底 |

**cc 推荐并存+fallback**：Codex CLI 可配多 profile/endpoint，日本主、美西备。日本机一挂或被限流时切美西。迁移分三阶段：①现有 wrapper 原样迁日本验证 ②加多账号池+sticky ③美西转 fallback。

## 六、风险（不回避，严重性排序）

1. 🔴 **ToS / 封号（头号、致命、不可消除）**：ChatGPT Pro 禁止账号共享 + API 化。多账号轮询池易被 OpenAI 风控（IP 频次/行为特征）判定滥用 → 封号/限速/降级。**这是订阅非 API 用途，合规做法是用官方 API。此风险只能自担。**
   - ⚠️ 注意：你的 wrapper 走的是**官方 codex app-server 客户端协议**（不是 web 逆向），风控暴露面比逆向小，但"多账号聚合"本身仍违规。
   - cc 立场：**不设计绕风控/伪装客户端**（这是红线）。gemini 提的 curl_cffi 防指纹属规避检测，cc 不主动做。
2. 🟠 **机房 IP 风控（待验证）**：cc 实测日本机 TCP 可达 OpenAI（401），但**没测真实 OAuth 流量是否被风控**——阿里云机房 IP 可能比住宅 IP 更易触发验证。上线前需小流量真实验证。
3. 🟠 **1G OOM**：加 swap + 单进程 async + 限并发(3-6 流) + 日志轮转 + Docker memory limit 350-450MB 缓解。
4. 🟠 **单点故障**：日本机挂 = 所有 Codex 不可用 → 美西 fallback + 定时备份 SQLite/配置。
5. 🟡 **sticky 难点**：见第四节，必须代码层做。

---

## 七、最小落地骨架（若决定推进）

1. **基建**：`fallocate -l 2G /swapfile`（+chmod 600 + mkswap + swapon + 写 /etc/fstab）；装 Docker
2. **核心**：单 Python async 容器，全局 `AccountPool = {acct1, acct2, acct3}`，sticky 走 conv_id；SQLite 存映射+用量
3. **网络**：装 **Tailscale**，Codex 客户端走 `100.x.x.x` 内网 IP 直连——不开公网端口（契合当前云防火墙只放行 SSH+ICMP），加密 + 绕扫描
4. **dashboard**：wrapper 内起 `/admin` GET 路由，读 SQLite 渲染静态 HTML（不上 Grafana）
5. **客户端**：`~/.codex/config.toml` 配 model_provider 指向 Tailscale IP + wire_api；多机复制同一份
6. **不要**：Postgres / Redis / Grafana / Prometheus / 浏览器自动化

## PoC 实测结论（2026-06-15，cc 在 aliyun-jp 实跑）

川哥决策：仅 OpenAI（不要 Gemini）/ 弃用 racknerd 不做 fallback / 先 PoC 再定。

| 验证项 | 结果 |
|---|---|
| **机房 IP 直连 OpenAI 风控** | ✅ **未触发**，直连正常（gpt-5.5 返回 PONG，无验证/拦截）→ **不需要 xray 绕美宅** |
| 内存（1G+2G swap） | ✅ 跑时 528Mi 可用，swap 0B 未用 |
| 架构连通 | ✅ exec-server 常驻(ws:4002) + wrapper(4001) + OpenAI 兼容格式可返回 |
| **旧 wrapper 协议** | ⚠️ 与 codex 0.139 exec-server **不兼容**（旧 `thread/start` 协议已变，content 返空）→ 需适配重写 |
| 延迟 | codex exec 冷启动 ~7s（上界，不可日常用）；app-server 常驻预期 ~2-5s（参考现有 racknerd wrapper）；大陆→日本网络仅 ~70ms |

- **美宅方案否决**：实测「美宅」lax-relay 出口 IP = AS906 DMIT **机房 IP（非住宅）**，与阿里云日本机房 IP 同性质，绕行多 113ms 却无抗风控收益 → 弃。
- **新权衡（PoC 暴露）**：旧 wrapper 虽"已跑通"，但 codex 0.139 协议变更使其需重写适配；而 [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI)（Go，原生跟随 codex 版本 + 多账号 OAuth）可能开箱即用支持 0.139 → **"扩展旧 wrapper" vs "用 CLIProxyAPI" 需重新权衡**（旧 wrapper 先发优势被协议变更削弱）。
- **结论**：核心可行性（机房 IP / 内存）✅ 验证通过，方向成立。

### PoC 第二阶段：CLIProxyAPI 单账号实测（2026-06-15）✅ 全绿

team 选 CLIProxyAPI 后落地验证（装 v7.2.5 Go 二进制 43MB + config: session-affinity/commercial-mode/绝对 auth-dir + codex device code flow 授权 1 个账号 + systemd 正式服务）：

| 验证项 | 结果 |
|---|---|
| OpenAI 兼容端点 | ✅ `/v1/models` 列 gpt-5.5；`/v1/chat/completions` HTTP 200 |
| 延迟 | ✅ 日本本地 **2.0s**；大陆经隧道端到端 **3.6-3.9s**（app-server 常驻，远胜 codex exec 冷启动 7s） |
| 多轮对话上下文连续 | ✅ 记住前文答 42 |
| 内存 | ✅ CLIProxyAPI RSS 仅 **42MB**，系统 503Mi 可用 + 2G swap（0 用） |

**踩坑（已记 memory）**：①账号侧默认关「设备代码授权」开关，device-login 前要先开；②systemd 起服务必须 `Environment=HOME=/root`，否则 `~/auth-dir` 解析失败立即退（setsid/systemd-run 同坑）；③ssh 后台进程持有会话 fd 致 stdout 不 flush（改 systemd 服务解决）。

**用上 ChatGPT Team 额度（关键坑，已解）**：device 授权默认只绑个人 free workspace（token `organizations` 只有 Personal、`plan_type=free`）。解法三步：① team **管理员**在 Workspace Settings 开启 workspace 级「Device Code authorization」+「Allow members to use Codex」（codex issue #9253：workspace 没开则 headless 授权拿不到 team，只给个人）② 重新 device-login → 拿到 `-team` 后缀凭证（`plan_type=team`，team 专属 account_id `bb9119be…` ≠ free 的 `ee6dd579…`）③ 同一 email 会同时存 free + team 两份凭证文件，**删掉 free 只留 team**，否则 round-robin 会混用个人额度。实测删 free 后请求 HTTP 200，走 team 额度。

**PoC 总结论**：CLIProxyAPI 开箱可用，省去自写 wrapper 一大半工程，team 选型验证成立。

### Dashboard 公网化（2026-06-15）✅

- **面板**：CLIProxyAPI 自带 `/management.html`（中文 web，纯前端、零额外服务器内存），数据来自 `/v0/management/*`（`auth-files` 账号/plan/健康/用量、`api-key-usage`、`logs`/错误日志）
- **访问**：`https://api.hahaxiong.top/management.html`（secret-key 登录）
- **链路**：用户 → Cloudflare(橙云) → nginx(80/443 自签证书) → CLIProxyAPI:8317；CF 隐藏源站 IP（安全加分）
- **关键配置**：`remote-management.allow-remote: true`（否则面板调管理 API 报 403 "remote management disabled"）+ secret-key + `usage-statistics-enabled: true`
- **踩坑**：①域名走 CF 橙云（解析到 CF IP 非源站 47.74.43.55），certbot HTTP-01 不能直接用 → 改 nginx **自签证书 + CF Full 接住**（不需 Origin Cert）；②nginx 新增 `listen` 要 **restart 非 reload**（同 sshd 坑）；③**`ssh -n` 会丢弃 stdin 管道**，`cat conf | ssh -n 'cat>file'` 把配置写成空文件（传文件绝不能用 -n）
- **副产物**：API 端点同域名公网可用 `https://api.hahaxiong.top/v1` + api-key → **codex 客户端可直接用公网域名，不必 Tailscale**
- **安全**：管理 API 公网开放、仅 secret-key 保护；fail2ban 评估=**不装**（流量经 CF、源站只见 CF IP，封不到真实攻击者，且 key 已防爆破，防护应放 CF 层如 CF Access/WAF）；建议加 CF Access 或 nginx basic auth（待定）

### 最终架构：双入口（2026-06-15 完成）

**关键设计——管理面板和 API 分两个入口**（因 CF Bot Fight Mode 按 TLS 指纹拦 Bun/omp，curl/codex 放行）：

| 入口 | 域名 | CF | 证书 | 用途 |
