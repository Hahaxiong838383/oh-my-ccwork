# 电视启动第二阶段优化方案（2026-10-30）

本轮只读研究与方案设计，没有修改现网、重启或操作前台。当前已部署基线仍是90ef15c，网络就绪77.30秒；下列改进尚未实现。目标先设40～50秒，必须以修改后实际重启验收，不承诺直接达到。

## 已测事实

同boot `cc87426c-5bc4-4fb8-a62f-01a6d5f208e4` 的Android事件payload显示启动动画于23.485秒结束；这不等于已经证明`sys.boot_completed`切换时刻。脚本的53.57秒`android_boot_complete`是执行检查点，不能解释成系统本身耗了54秒。

| 时间点 | 已观察到的事件 |
|---|---|
| 8.17秒 | 早期DNS保护安装 |
| 23.485秒 | Android启动动画结束（EventLog payload，uptime） |
| 53.57秒 | boot脚本通过Android完成检查 |
| 54.15秒 | 双来源校时验证完成 |
| 59.51秒 | 主代理进程启动 |
| 59.85秒 | guardian启动 |
| 66.20/71.71秒 | Rack/ZGO HY2 worker依次启动 |
| 73.98秒 | 真实DNS查询验证完成 |
| 77.30/77.88秒 | 完整DNS/缓存就绪，后台审计结束 |

当前270个进程。只读微基准包含ADB开销、在开机后稳定系统中执行；缺进程分支使用不存在的目标路径模拟，只读扫描真实/proc。不是给本次冷启动精确归因每一秒。

| 检查 | 本轮耗时 |
|---|---:|
| 事务`running()`全量扫描，无匹配分支 | 12.406秒 |
| 主代理全量扫描，无匹配分支 | 3.903秒 |
| worker全量扫描，无匹配分支 | 3.732秒 |
| 主代理旧查法，真实进程存在 | 3.637秒 |
| 原生候选筛选后保留原exe/完整argv核验，同一真实进程 | 0.103秒 |
| 原生pgrep仅枚举候选（不能单独当完整判据） | 0.062秒 |
| 15文件事务只读预检 | 0.861秒 |
| sing-box配置check | 0.208秒 |
| 完整防火墙规则只读校验 | 0.186秒 |

源码上事务锁前/锁后各执行一次`running()`，boot主代理检查两次，两个worker跨boot清旧状态时又分别扫描。大量逐进程`readlink/tr`子进程是可优化的实测开销；各阶段存在嵌套与并行，不能把表中时间直接累加成保证可节省的时间。

## 推荐实施顺序

### 第一批：保留安全检查，减少检查开销

1. 为每个启动阶段记录boot ID、uptime起止与返回码。包括事务预检/进程扫描/加锁后二次检查、Android门、主代理check、两worker、DNS/缓存。先建立真正分段基线，不从日志标签猜耗时。
2. 将逐进程派生shell命令改为一次原生进程枚举，再对候选做原有exe、完整argv、boot/startticks检查。`pgrep`原型已证明开销差距，但上线必须覆盖工具失败、读取失败、孤儿进程、PID复用、改名、双实例、未知监听；必要时扩展已有native helper单进程扫描，不能只信PID文件或进程名。
3. 锁前/锁后保护保留，避免为速度引入检查与使用之间的竞态。进程筛选失败时回退旧扫描或明确拒绝，不能空列表当“没有进程”。

先做这批，验收后再决定是否需要更改启动依赖，避免同时改多件事后无法归因。

### 第二批：减少不必要的串行依赖

- 现网DNS：`zgo-dns`（只是tag）→`dns-uplink`→三个直接VLESS/REALITY候选，没有走HY2 worker的19201/19202。不能根据旧文档或tag名判断实际链路。
- 主代理与guardian就绪后，独立推进DNS/缓存验收；Rack/ZGO worker可在各自控制锁下并行初始化。必须保留实际选路依赖：若当前视频确实选HY2，该出口未ready前不能宣布该应用可播。
- 同时记录“DNS/选中应用路径可用”和“所有兜底worker完成”。最终完整健康门仍保留；不能只提前写ready标记，把后台未完成伪装成加速。
- 新后台路径需关闭无关继承锁FD，逐进程保持boot+PID+startticks+exe+config身份，不再复发上一轮维护锁继承问题。

### 第三批：批量文件校验（优先级低于进程扫描）

每个新boot仍执行15文件迁移事务。当前`replace_set`对SHA和权限已匹配的文件会跳过复制，并非每次都重写15文件。预检实测约0.86秒，不能夸大成主要磁盘瓶颈。

Grok复核指出：每次新boot重写`applied-boot-id`仍承担本boot坏配置自动回退功能，不能随意删掉，也不能未经独立设计改成“只有复制过字节才可回滚”。因此本轮方案收敛为批量SHA校验、减少命令派生，继续保持现有回滚标记和完整事务语义。必须保留全部SHA/权限/锚点、未知漂移拒绝、断电恢复及备份恢复；不凭成功marker跳过检查。

## 暂不优先做

本次校时阶段仅约0.58秒；不取消双来源校时、不提前启动依赖正确时钟的TLS、不把YouTube/CDN固定IP。也不通过删除校验、关DNS保护、缩短日志或提前写ready制造数字改善。Magisk post-fs-data是阻塞启动阶段，不把网络等待/主代理初始化移进去；保留当前早期本地保护与后续异步启动的分工。

## 验收标准

同版本做至少两次获授权的软件重启，记录从内核启动到真实DNS/应用路径可用及完整后台健康的独立时间。覆盖旧PID/孤儿/占端口/坏配置/未知漂移/部分事务/主节点故障，保护失败关闭。验证双栈真实正文和有界完整载荷、DoT、5354、15文件及现行外部清单；当前播放归属明确，DIYP不冒充SmartTube。新版真实拔电耐久仍需单独观察。

本轮观察前后主代理及guardian/两worker身份保持，DIYP1080p帧12680→17802、drop/解码错误0。

## Grok独立审查与最终取舍

通过用户指定Codeg Grok路由完成只读审查（task `8f7a3a94-c34f-47ba-9af8-5d53a0f812aa`，会话303），Grok未连接电视或改文件。

共同结论：53.57秒是脚本检查点、NTP本次仅约0.58秒；HY2串行挡住独立REALITY DNS门；事务有两次全表扫描、多个重复哈希；不可删安全判据或把系统/脚本等待混成一个原因。Grok建议先细分日志、后台并行worker、批量哈希、再引入原生扫描。结合本会话新增实机扫描12.406/3.903/3.732秒而只读预检0.861秒的证据，最终优先级调整为：**计时→原生扫描保持安全语义→HY2并行→批量哈希**。

采用Grok对回滚语义的提醒，撤销把`applied-boot-id`简化为纯首次迁移标记的设想。Grok基于源码判断DNS不依赖HY2，本会话又以生产配置脱敏读取确认。其文字中上一故障boot主代理“159.97秒”与现存证据不符：PID为15997，startticks为19941，实际起点为199.41秒；该笔误没有用于本方案的收益判断。所有阶段比较统一采用uptime或startticks，不用PID当时间。

最终推荐先以40～50秒为工程目标，不以加总微基准承诺收益；实际目标是否达到由下一轮真实启动时序及应用可用性验收裁定。当前生产保持77.30秒已验版本，本轮方案未实施、未重启、未commit/push。
