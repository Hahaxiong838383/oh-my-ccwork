# 桌面智能体产品方案分析：以 mycc / mycc-brain 为自进化内核

**日期**：2026-04-15  
**分析目标**：基于产品定义文档与参考项目源码，评估一款“用户可自选模型、内核具备自进化能力”的桌面端产品应如何设计。  
**结论标签**：可做，且差异化明确；但要把“桌面壳、运行时、认知内核、自进化闭环”分层，不能做成一个大而全的单体。

---

## 0. 结论先行

这条路是成立的，而且你的优势不在“再做一个 IDE Agent”，而在于做一个：

**可插拔模型 + 本地运行时 + 自进化认知内核** 的桌面智能体工作台。

如果只看 UI 和基础 Agent Loop，你会很容易落入 Cursor / Windsurf / Cline / opencode / goose 已经覆盖的赛道；但如果把 `mycc-brain` 的感知、记忆、预测、进化、治理做成第一公民，你的产品会更像：

**“个人/团队长期共生的桌面 Agent OS”**，而不是一次性的编码助手。

我最核心的建议只有一句话：

**把产品拆成三层：Desktop Shell、Local Runtime、Brain Kernel。**

其中：

- `Desktop Shell` 负责体验、权限、可视化、检查点、配置。
- `Local Runtime` 负责文件/终端/浏览器/MCP/工作区执行。
- `Brain Kernel` 负责理解、记忆、规划、预测、进化、治理。

这样做的原因是：  
**“接近 Opus 的能力”主要不是来自某个模型名字，而是来自系统编排质量。**

---

## 1. 基于产品定义的判断

从飞书产品定义文档看，`mycc-brain` 已经不是一个普通路由层，而是一个相当完整的认知内核雏形：

- 已上线的能力域有 7 个：感知、记忆、知识、视觉、预测、进化、治理。
- 已形成在线请求管道、离线进化管道、模型路由体系、Admin UI、Eval 系统。
- 已具备 `fitness = value_created × trust_score / steering_tax` 这样的内在优化目标。
- 已有规则层和配置层的进化能力，模型层 SFT 尚未启动。

这意味着：

1. **你最值钱的不是聊天入口，而是“内核”**。  
   这个内核已经开始把“用户理解、长期记忆、经验积累、主动预测、自我修正”连成闭环。

2. **你离产品化差的不是理论，而是运行时与产品壳**。  
   也就是：桌面端体验、权限治理、任务执行环境、检查点、模型配置体系、异步后台任务体系。

3. **你最大的差异化不是单次回答质量，而是长期适配能力**。  
   这也是和多数桌面 Agent 最大的分野。

当前最大缺口也很清楚：

- `Peer Card / 辩证用户建模` 未启动
- `验证引擎（防自欺、防早停、防静默吞错）` 未启动
- `模型层 SFT` 未启动
- 记忆蓝图纵深仍然不足，尤其是六维度摄入、矛盾检测、巩固

换句话说，**你已经有“脑干”和“海马体”雏形，但还缺稳定的“前额叶验证系统”和更强的“自我建模层”。**

## 2. 三个参考项目，分别该借什么

## 2.1 `opencode`：借“开放运行时”，不要照搬“弱记忆内核”

`opencode` 给你的最大启发不是 UI，而是它的运行时分层：

- 内置 `build` / `plan` agent，说明它把“能力模式”而不是“单一 agent”作为产品单位。
- provider-agnostic，支持 Claude / OpenAI / Google / 本地模型，说明模型层抽象做得很彻底。
- 明确走 client/server 架构，桌面端通过 sidecar server 工作，而不是把 agent loop 塞进前端。
- 权限系统和 subagent 任务工具设计都比较干净。

适合借鉴的点：

- 本地 sidecar server
- provider-neutral 模型抽象
- 模式化 agent（plan / build / general）
- 简洁直接的权限匹配模型
- 子 agent 会话继承机制

不建议直接照搬的点：

- 长期记忆不是第一公民
- 自进化不是核心主张
- 更偏“开放编码代理”，不是“长期共生认知体”

一句话总结：  
**`opencode` 适合做你产品的“运行时骨架参考”，不适合做“认知内核参考”。**

## 2.2 `goose`：借“多客户端统一协议”，不要只学“多 Provider”

`goose` 的价值在于它非常明确地在做一件事：

**把 Desktop、CLI、API 统一到同一个 Agent Core 上。**

它对你最有价值的几个信号是：

- 桌面、CLI、API 三端并存
- 15+ provider，且支持本地模型、订阅型 OAuth、ACP provider
- MCP 扩展面很广
- 正在从旧架构收敛到基于 ACP 的统一协议
- 桌面端从 Electron 迁往 Tauri，说明它也在追求更轻的壳与更统一的运行时

适合借鉴的点：

- “一个 Agent Core，多种客户端”的产品策略
- provider onboarding 体验
- ACP/协议化客户端接入思路
- Desktop/CLI/API 一套会话与状态
- 自定义发行版/预配置能力

不该被它带偏的点：

- 多 Provider 本身不是护城河
- 如果没有更强的记忆与进化层，只会变成“模型聚合器 + MCP 面板”

一句话总结：  
**`goose` 给你的是“产品扩展形态”的答案，不是“认知升级”的答案。**

## 2.3 `claude-code-source`：最值得借的其实是“记忆与后台反思中台”

三个项目里，`claude-code-source` 和你的目标最接近。

它最关键的地方不是会调工具，而是已经把这些能力工程化了：

- 结束一轮 query loop 后自动抽取 durable memories
- `autoDream` 做后台巩固，而不是把所有记忆工作都塞在主链路
- `teamMemorySync` 说明记忆可以从个人层走到 repo/team 层
- 工具并发执行有“并发安全”和“非并发安全”区分
- MCP client 很成熟，覆盖 stdio / SSE / HTTP / OAuth / 401 重鉴权
- 有策略限制层和远程 session 管理

适合你重点借鉴的点：

- durable memory 抽取的异步化
- memory consolidation 的 gate 设计
- team/workspace memory 的同步模型
- 并发安全工具编排
- 完整 MCP 中台
- policy limit / remote session / auth lifecycle

一句话总结：  
**如果说 `opencode` 像外骨骼，`goose` 像交通层，`claude-code-source` 更像“内核周边的神经系统”。**

## 3. 还能借鉴哪些相近产品

## 3.1 Cursor

Cursor 的方向是：

- 强调 Agents 异步并行
- 提供多表面能力，不只 IDE 内聊天
- 允许用户使用多种前沿模型
- 把“模型选择”抽象成日常体验的一部分

能借鉴的不是它的编辑器壳，而是两件事：

1. **异步后台 agent**  
   用户不该始终盯着对话框等结果，复杂任务应该可以后台跑、完成后回看。

2. **多表面统一体验**  
   桌面端不是唯一入口，未来 Slack / GitHub / mobile / web 都可以是同一个 brain 的前端。

## 3.2 Windsurf

Windsurf 值得看的是它把很多“长期行为”做成了显式结构：

- Cascade 是 agent 主入口
- 有 `Memories & Rules`
- 有 `Skills`
- 有 `Workflows`
- 有 `Worktrees`
- 有 MCP Marketplace

这说明一款成熟桌面 Agent，不能只有“聊天 + 跑命令”，还必须把这些层显式化：

- 规则层
- 记忆层
- 技能层
- 工作流层
- 外部工具层

这与你的 `mycc-brain` 方向高度一致。

## 3.3 Cline

Cline 最值得借的是“人类在环的信任机制”：

- 每次文件改动和终端命令都有可见审批
- diff / 时间线 / checkpoint 很强
- 浏览器执行闭环成熟
- MCP 不只是接服务器，还支持“让 agent 自己给自己造工具”

如果你要让用户接受“自进化”，就更需要这类机制：

- 看得见它做了什么
- 能回滚
- 能比较前后版本
- 能知道哪些是模型行为，哪些是系统自动进化导致的改变

## 3.4 Continue

Continue 现在更像一套“可配置 Agent 平台”：

- 配置文件统一
- 模型、规则、MCP 工具都能配置
- CLI / IDE / headless 路径统一
- 权限会沉淀到本地策略文件

它的启发是：

**不要让“用户自选模型”变成 UI 杂乱的设置页，而要变成稳定的配置语义。**

## 4. 我建议的产品架构

## 4.1 顶层形态：三层解耦

```text
Desktop Shell
  ├─ 会话 UI / 权限确认 / 检查点 / 配置 / 结果回放
  ├─ 工作区视图 / Browser 视图 / Logs / Timeline
  └─ 用户只与这一层直接交互

Local Runtime
  ├─ 文件系统 / Git / 终端 / 浏览器 / MCP / IDE bridge
  ├─ 会话状态机 / Tool scheduler / Sandboxing / Background jobs
  └─ 对上提供统一 Agent Session API

Brain Kernel (mycc-brain)
  ├─ 上下文装配 / 用户建模 / 记忆检索 / 预测 / 规划 / 反思 / 进化
  ├─ trust_score / steering_tax / value_created
  ├─ 规则层进化 / 配置层进化 / 未来模型层进化
  └─ 对下只看“能力接口”，不直接耦合具体 UI
```

这是最关键的设计决策。  
**不要把桌面壳和 brain 做成同进程单体。**

## 4.2 模型层：不要让用户选“模型名”，要让用户选“能力槽位”

用户当然可以自己配置模型，但产品内部不应该围绕模型名工作，而应该围绕 **能力角色** 工作：

- `Planner`：深度推理、任务拆解、方案生成
- `Executor`：工具调用稳定、低延迟、代码/文件执行
- `Verifier`：独立校验、测试解释、反例检测
- `Memory`：低成本事实提取、巩固、矛盾检测
- `Vision`：多模态理解
- `Judge`：离线评测、对抗评分

然后提供两层配置：

1. **普通用户层**：只选预设  
   如“最强推理 / 均衡执行 / 本地隐私 / 低成本”

2. **高级用户层**：把模型绑定到能力槽位  
   如 `Planner=Claude/Opus级`、`Executor=GPT-5/Codex类`、`Memory=本地 Qwen`

这样做有三个好处：

- 前沿模型快速变化时，产品不需要改架构
- 用户能保留 BYOM 自由
- 你的 brain 能稳定做路由、回退和多模型协作

## 4.3 记忆层：至少要五层，不要只做“对话历史”

建议把记忆体系做成：

- `Scratchpad`：当前任务临时工作记忆
- `Session Memory`：单会话上下文与压缩摘要
- `Durable Personal Memory`：用户长期偏好、环境、关系、习惯
- `Workspace / Team Memory`：项目规则、代码约定、常见流程
- `Knowledge Memory`：外部文档、网页、知识库
- `Trajectory Memory`：成功/失败轨迹、技能表现、修复历史

你的 `mycc-brain` 已经有其中大半，但桌面产品化时要把它们显式展示和治理出来。

特别重要的是两件事：

1. **矛盾检测**  
   记忆不做矛盾处理，越用越烂。

2. **验证后写入**  
   不是所有“猜到的事实”都应该进入 durable memory。

## 4.4 自进化：先进化规则、技能、记忆策略，最后才进化模型权重

你想做“自我进化”，这个方向我支持，但要非常克制地分层：

### 第一层：规则层进化

- 更新 prompt 片段
- 优化规则和禁令
- 调整技能触发条件
- 调整工具选择策略

### 第二层：配置层进化

- 调整记忆检索权重
- 调整模型角色映射
- 调整工具权限默认值
- 调整 compaction / summarization / checkpoint 策略

### 第三层：模型层进化

- 轨迹筛选
- 数据集构建
- SFT / preference tuning

我建议：

**产品前两个大版本都只做前两层，把模型权重进化放到后面。**

原因很简单：

- 风险更低
- 回滚更容易
- 对用户更可解释
- 收益已经足够大

## 5. 如何把“接上强模型后接近 Opus”这件事做出来

这件事的关键不是“找到一个接近 Opus 的模型”，而是让系统把强模型的能力稳定释放出来。

我建议你把主链路做成：

```text
Perceive -> Plan -> Act -> Verify -> Reflect -> Consolidate
```

对应到实现上：

1. **Perceive**
   - 读任务、工作区、用户状态、相关记忆、相关知识、最近失败轨迹

2. **Plan**
   - 让 Planner 先明确目标、约束、风险、任务树

3. **Act**
   - Executor 执行子任务，必要时调工具或子 agent

4. **Verify**
   - 独立 verifier 做测试、diff 审查、约束核对

5. **Reflect**
   - 失败归因：模型不懂、上下文不够、工具选错、记忆误导、规则缺失？

6. **Consolidate**
   - 只把跨会话有用的经验沉淀进 durable memory / skills / rules

这条链路的价值在于：

- 强模型负责真正难的推理
- 系统负责把“思考、执行、校验、沉淀”连接起来
- 用户体验会明显更像“一个会工作的智能体”，而不是“一个能回答问题的大模型”

如果要进一步靠近 Opus 风格体验，我建议默认给高级预设：

- `Deep Reasoning`：Planner 用最强推理模型
- `Fast Execution`：Executor 用快但工具稳的模型
- `Independent Verification`：Verifier 尽量不用同一个 provider
- `Cheap Memory Loop`：Memory/Consolidation 用本地小模型

这实际上是在用 **系统设计弥补单模型短板**。

## 6. 产品功能上，我建议优先做什么

## 6.1 第一版必须有

- 多模型配置与能力槽位绑定
- 本地 sidecar runtime
- 文件/终端/浏览器/MCP 基础执行面
- 明确的权限确认与持久化策略
- checkpoint / compare / restore
- 会话压缩与 resume
- 记忆检索与写入可视化
- 基础后台任务（长任务异步运行）

## 6.2 第二版开始拉开差距

- `mycc-brain` 全量接入
- 预测与主动提醒
- durable memory + consolidation
- skills 生命周期
- evaluation dashboard
- verifier / judge 双保险

## 6.3 第三版进入真正的“自进化”

- Peer Card / 辩证用户建模
- 验证引擎（防自欺）
- 自动生成 patch proposal
- 规则/配置自动升级与回滚
- trajectory package 与高质量样本筛选

---

## 7. 我不建议你怎么做

以下这些做法，短期看省事，长期基本都会拖死产品：

1. **把桌面 UI、agent loop、brain、工具执行塞进一个进程**
2. **直接把 brain 暴露成公网服务**
3. **把“用户自选模型”做成一堆 endpoint / key / model name 表单**
4. **把长期记忆等同于“把历史对话塞回 prompt”**
5. **让自进化直接改生产逻辑而没有验证和回滚**
6. **只做编码场景，不做 workspace / personal memory / background workflows**

你真正要做的是：

**把“执行能力”产品化，把“长期进化能力”系统化。**

## 8. 推荐的路线图

## Phase 0：桌面基础设施

- Tauri 桌面壳
- 本地 runtime
- provider-neutral 模型层
- session / checkpoint / permission / MCP

## Phase 1：brain 接管上下文

- 接入 `mycc-brain`
- 上线 layered memory / workspace memory / knowledge memory
- 建立 planner / executor / verifier 角色路由

## Phase 2：验证与评测

- E2E 任务验证
- judge / verifier 双评估
- task 质量指标
- steering_tax / trust_score / value_created 面板

## Phase 3：自进化闭环

- memory contradictions
- Peer Card
- skills aging / synthesis
- rules/config patch proposals

## Phase 4：模型层学习

- trajectory curation
- SFT / preference optimization
- 个体化 agent 包

## 9. 最终建议

如果我是你，我会把这款产品定义成：

**“一款本地优先、可插拔模型、带自进化认知内核的桌面智能体工作台。”**

它的护城河不是：

- 又一个聊天窗口
- 又一个 IDE 插件
- 又一个模型聚合器

而是这三件事叠在一起：

1. **更强的任务理解与执行组织能力**
2. **更强的长期记忆与用户建模能力**
3. **更强的规则/技能/记忆策略自进化能力**

我建议的产品定位顺序是：

**先做“能稳定完成复杂任务的桌面 Agent”，再做“会自我变强的 Agent”，最后再做“会自己训练自己的 Agent”。**

这个顺序很重要。  
因为前两步就已经能把产品拉到非常强的位置，而第三步只有在验证体系、回滚体系、记忆质量体系稳定后才值得放大。
