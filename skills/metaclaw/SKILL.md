# MetaClaw — 自进化引擎

> 灵感来源：AutoResearchClaw 的 MetaClaw 循环学习 + mem0 的 Universal Memory Layer
> 核心理念：失败分析 → 提取经验 → 转为规则 → 注入未来行为 → 验证效果 → 迭代

## 运行模式

| 模式 | 用途 | 触发方式 |
|------|------|---------|
| `analyze` | 只分析摩擦数据，不写入 | 手动调试 |
| `inject` | 将已确认的模式注入 memory-items | 分析确认后 |
| `report` | 生成自进化简报 | 周复盘 |
| `full` | 完整闭环：分析→聚类→注入→验证 | 默认/定时任务 |

## 完整执行流程

### 第 1 步：摩擦数据采集

从三个数据源采集近 $ARGUMENTS.days 天的摩擦信号：

```
数据源 1: 0-System/task-log.md
  → 筛选 friction_skill ≠ "—" 的条目
  → 提取：时间、任务类型、friction_skill、关键产出描述

数据源 2: 0-System/evolution-log.md
  → 筛选状态 ≠ "已毕业" 且 ≠ "已解决" 的活跃 E-xx
  → 提取：ID、问题描述、假设根因、当前状态

数据源 3: 0-System/RECENT_EVENTS.md
  → 搜索关键词：失败|报错|重试|返工|误诊|超时|卡住
  → 提取：事件描述、时间、关联 skill
```

### 第 2 步：模式聚类

将采集到的摩擦信号按根因聚类：

```
聚类规则：
1. 相同 friction_skill → 归为同一模式
2. 相同错误类型（429/502/超时/权限）→ 归为同一模式
3. 相似描述文本（Jaccard > 0.3）→ 候选合并

输出格式：
┌──────────────────────────────────────────┐
│ 模式 ID: F-{序号}                         │
│ 名称: {简短描述}                          │
│ 触发条件: {什么情况下会触发}               │
│ 出现频率: {近 N 天出现次数}                │
│ 症状: [{症状1}, {症状2}]                   │
│ 根因假设: {为什么会发生}                   │
│ 建议修复: {怎么修}                        │
│ 置信度: {高/中/低}                        │
│ 来源: [{task-log条目}, {evolution-log E-xx}]│
└──────────────────────────────────────────┘
```

### 第 3 步：规则生成

对置信度 ≥ 中 的模式，生成反馈规则：

```
规则格式（写入 0-System/friction-patterns.md）：

## F-{序号}: {名称}（{日期}）

- **触发条件**：{具体条件}
- **症状**：{观察到的表现}
- **根因**：{一句话根因}
- **修复规则**：{cc 应该怎么做}
- **验证状态**：待验证 / 已验证 / 已失效
- **来源**：{task-log 时间 + evolution-log ID}
- **出现次数**：{N}
- **最近触发**：{YYYY-MM-DD}
```

### 第 4 步：注入决策

对每条生成的规则，决定注入位置：

| 规则类型 | 注入位置 | 条件 |
|---------|---------|------|
| 高频摩擦（≥3次/周） | CLAUDE.md 行为规则 | 🔴 自动注入 |
| 中频摩擦（2次/周） | memory-items [agent/踩坑] | 🟡 自动注入+发简报 |
| 低频摩擦（1次/周） | friction-patterns.md 仅记录 | ⚪ 不注入，观察 |
| 已有 E-xx 覆盖 | 不重复注入 | 跳过 |

**注入安全机制**：
1. 注入前检查是否与现有规则冲突（grep CLAUDE.md + memory-items）
2. 每次最多注入 3 条新规则（防止规则膨胀）
3. 注入的规则带 `[metaclaw:{日期}]` 标签，便于追踪和回滚
4. 注入后在 evolution-log 新增对应 E-xx 条目，状态「已实施待验证」

### 第 4.5 步：规则健康度检查（专家系统"规则爆炸"防护，2026-04-01 起）

> 启发来源：1980s 专家系统规则 >5000 条后维护崩溃的教训。
> 当规则总量超过 LLM 有效遵循容量时，每增加一条规则反而降低整体质量。

**每次 full 模式运行时**，在注入新规则前先做健康度检查：

```
规则总量盘点：
1. CLAUDE.md 行为规则行数：wc -l CLAUDE.md（阈值 ≤ 500 行）
2. skills 目录 SKILL.md 数量：ls skills/*/SKILL.md | wc -l（阈值 ≤ 40 个）
3. memory-items 条目数：grep "^- ★" 0-System/memory-items.md | wc -l（阈值 ≤ 300 条）
4. friction-patterns 活跃模式数：grep "^## F-" 0-System/friction-patterns.md | wc -l（阈值 ≤ 10 个）

健康度判定：
- 🟢 全部在阈值内 → 正常，可注入新规则
- 🟡 任一项达 80% 阈值 → 警告，注入前先瘦身
- 🔴 任一项超阈值 → 阻断注入，触发瘦身流程
```

**瘦身策略（🟡/🔴 时执行）**：
1. `memory-items`：归档 access_count=0 且写入 >60 天的条目（Hebbian 反向淘汰）
2. `CLAUDE.md`：合并语义重复的行为规则（同类规则合并为一条）
3. `friction-patterns`：已失效 + 超 30 天未触发的模式移入归档
4. `skills`：14 天内零调用的 skill 降级为按需加载（从 settings 中移除自动注入）

**输出格式**（追加到简报中）：
```
📊 规则健康度
  CLAUDE.md: {N}/500 行 {emoji}
  skills: {N}/40 个 {emoji}
  memory-items: {N}/300 条 {emoji}
  friction-patterns: {N}/10 个 {emoji}
  整体: {🟢/🟡/🔴}
  {瘦身建议（如有）}
```

### 第 5 步：验证与淘汰

每次运行时，同时检查已注入规则的效果：

```
对每条 [metaclaw:*] 标签的规则：
  1. 检查注入后 7 天内：
     - 同类摩擦是否减少？ → 有效，保留
     - 同类摩擦未减少？   → 再观察 7 天
     - 同类摩擦增加？     → 无效，标记 [已失效] 并移除
  2. 超过 14 天未触发的规则：
     - 标记 [待确认]，下次全量运行时询问是否保留
  3. 验证有效的规则：
     - 移除 [metaclaw:*] 标签（毕业为正式规则）
     - 在 evolution-log 已毕业模式追加记录
```

### 第 6 步：输出简报

```
🧬 MetaClaw 自进化简报
━━━━━━━━━━━━━━━━━━━━━
分析窗口：近 {N} 天
摩擦信号：{total} 条（task-log {n1} + evolution-log {n2} + events {n3}）

新发现模式：
  F-{xx}: {名称}（{频率}次，置信度 {高/中/低}）

注入规则：
  ✅ {规则描述} → {注入位置}
  ⏭️ {规则描述} → 观察中（频率不足）

验证结果：
  ✅ F-{xx}: {名称} — 有效（摩擦减少 {N}%）
  ❌ F-{xx}: {名称} — 无效（已移除）
  ⏳ F-{xx}: {名称} — 观察中（{N}天/{14}天）

下次运行：{预计时间}
```

## 回滚机制

如果自进化产生问题（注入了错误规则、规则冲突、性能下降）：

```bash
# 查找所有 metaclaw 注入的规则
grep -n "\[metaclaw:" 0-System/memory-items.md
grep -n "\[metaclaw:" CLAUDE.md

# 一键回滚：移除所有 metaclaw 标签的规则
# （由 cc 手动执行，不自动化，防止误删）
```

## 第 7 层：元策略评估（Meta-Evolution）

> AST 第四层延伸 —— 进化策略本身也需要进化。

每月 1 日 `/metaclaw full` 运行时，额外执行元策略评估：

### 评估流程

```
1. 读取 evolution-log.md 的「进化策略评估」section
2. 对每个维度计算实际指标：
   - 颜色阈值 → 红标规则注入后，该类摩擦 7 天内降低率
   - 注入频率 → 本月新增规则数 vs 本月摩擦降低数
   - 毕业条件 → 已毕业规则中，毕业后 30 天内复发的比例
   - 淘汰条件 → 已淘汰规则中，淘汰后 30 天内本应触发的比例
   - 路由准确度 → autoRouteEngine 路由后，引擎完成率（从 task-log 提取）
3. 输出调整建议（写入 evolution-log 对应行的「上次评估」列）
4. 如果某维度指标偏离目标 >20%，生成 🟡 黄标调整建议
```

### 输出格式

```
🔬 Meta-Evolution 评估（YYYY-MM）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
颜色阈值：摩擦降低率 {N}%（目标 >50%）→ {保持/调整建议}
注入频率：{N}条/月，摩擦降 {M}%  → {保持/调整建议}
毕业条件：复发率 {N}%（目标 <10%）→ {保持/调整建议}
路由准确：完成率 {N}%（目标 >80%）→ {保持/调整建议}
```

## 注意事项

1. **保守注入**：宁可少注入，不可多注入。规则膨胀比摩擦更危险
2. **可追溯**：所有注入带 `[metaclaw:日期]` 标签，便于审计
3. **人类兜底**：高频规则注入 CLAUDE.md 后发飞书通知，老板可随时否决
4. **衰减淘汰**：14 天无触发的规则自动进入待确认状态
5. **不改代码**：MetaClaw 只操作 md 文件（规则/记忆），不修改 TypeScript 代码
