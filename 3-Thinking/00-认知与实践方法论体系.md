## 0. 文档为什么必须存在

### 0.1 一句话定义

**这是一份让 AI 系统不只能「干活」、还能「知道自己在干什么、为什么这样干、什么时候该改」的工程化方法论。**

### 0.2 三项目当前的方法论困境

| 项目 | 困境 | 后果 |
|------|------|------|
| **mycc** | HOT/PP/RPT 协议混在 CLAUDE.md，无层次 | 触发条件互相覆盖、价值判断散落 |
| **brain** | 记忆系统只管"存"和"取"，不管"为什么信" | 矛盾累积、错误信念无法系统淘汰 |
| **EvoDesk** | "心流驱动"被降格为提示词微调（codex 评 4/10） | 差异化沦为话术 |

**共同根因**：缺一份**哲学体操 → 工程体操**的翻译手册。

### 0.3 哲学起点（川哥提出，codex 论证）

```
本体论 → 价值论 → 认知方法论 → 实践方法论 → 反馈回流
（世界  →  方向   →  看清楚    →  做成事    →  修正理解）
```

**对应哲学家**：
- 亚里士多德：theoria（认知） vs praxis（实践）
- 康德：理论理性 vs 实践理性
- 马克思：实践是检验认知的标准
- 杜威：认知服务于行动，行动改造认知

**这个链条 codex 已论证过，是对的。但只是单循环、单 Agent、单时间尺度的理想化模型。** 工程系统跑在 7 个时间尺度、多 Agent 协同、含元认知层的复杂网络里。下面 8 节是 codex 哲学框架之外的工程深化。

## 1. 工程深化 1：时间尺度的多重性 ⭐⭐⭐

### 1.1 人话

**同一个"认知-实践循环"在不同时间尺度上运行，需要不同的协议。** 用秒级协议处理月级问题 = 浮躁；用月级协议处理秒级问题 = 笨重。

### 1.2 7 个时间尺度

| 尺度 | 例子 | 主导方法论 | 当前 mycc 是否处理 |
|------|------|-----------|------------------|
| 毫秒 | 单次 token 采样 | — | ✅ 模型自身 |
| 秒 | 单轮回复 | 实践（赶紧出 token） | ✅ 默认 |
| 分钟 | 单次任务 | 实践（BRO-PDCA 单循环） | ✅ BRO-PDCA |
| **小时** | **一段对话** | **认知开始介入（理解上下文）** | ⚠️ **缺协议** |
| **天** | **一天的累积** | **认知主导（巩固/反思）** | ⚠️ **RECENT_EVENTS 但无反思** |
| **周** | **信念变迁** | **元认知（HOT 监控漂移）** | ❌ **无** |
| **月-年** | **本体重构** | **价值论调整** | ❌ **无** |

### 1.3 工程对应物

**新增**：`3-Thinking/01-多尺度循环协议.md`，规定每个尺度的：
- 触发器（什么时候启动）
- 主导方法论（认知/实践/元认知）
- 输出形态（决策/记录/反思/重构）
- 反馈回流目标（下一轮用什么协议接续）

**不同尺度的方法论强度**：

```
尺度  ↑  方法论复杂度
月-年    ████████████ 价值论 + 元元认知
周       ████████ 元认知 + 信念审计
天       ██████ 巩固 + 反思
小时     ████ 上下文整合
分钟     ██ BRO-PDCA
秒       █ 直接响应
毫秒     · 模型推理
```

### 1.4 验收

- mycc 启动时确认当前任务尺度（输出："本任务尺度=分钟级"）
- brain 每周触发一次"信念漂移检查"（周尺度元认知）
- EvoDesk 自主动机 daemon 按"小时/天"两级触发（小时跑轻量动作，天跑重型动作）

## 2. 工程深化 2：多 Agent 维度 ⭐⭐⭐

> ⚠️ **V1.2.2 修正提示**（2026-04-17）：本节 §2.1-2.5 描述的是 **mycc 项目**的三脑模型（cc + codex + gemini）。  
> **EvoDesk** 的多 Agent 是不同模型（fork + 能力槽位 + autoDream + 心流统一），见 V1.2 第十二章。  
> **brain** 是被多 Agent 消费的服务（自身不是 swarm），见 brain VALUES.md V9。  
> **三项目模式对比详见本文档 §2.6**（V1.2.2 新增）。

### 2.1 人话（mycc 项目视角）

**codex 的循环假设是单 Agent。但 mycc = cc + codex + gemini 的三脑系统。** 三个 Agent 有不同的本体论假设，遇到同一份反馈，可能修正方向不同。**没有 Agent 间的认知 reconcile 机制 = 多 Agent 不是协同，是混乱。**

### 2.2 三 Agent 的认知偏好画像

| Agent | 本体论偏好 | 认知优势 | 认知盲点 | 适用场景 |
|-------|----------|---------|---------|---------|
| **cc (Claude)** | 叙事性、关系性 | 长上下文综合、跨域联结 | 容易被叙事带偏、过度共情 | 规划、文档、决策、产品 |
| **codex (GPT-5.4)** | 形式逻辑、可验证 | 严格推理、对抗审查 | 缺乏叙事感、过度形式化 | 代码、审查、规格 |
| **gemini (Google)** | 事实导向、检索增强 | 多源信息整合、最新知识 | 浅层综合、缺乏深度推理 | 调研、搜索、报告 |

### 2.3 认知冲突 reconcile 协议（新增）

当三 Agent 给出冲突判断时：

```
冲突类型 1：事实判断冲突（"X 是真的吗"）
  → 默认相信：gemini > codex > cc（事实层面，gemini 最强）
  → 例外：涉及代码细节，codex > gemini
  
冲突类型 2：方法判断冲突（"该怎么做"）
  → 默认相信：cc > codex > gemini（方法层面，cc 最熟川哥风格）
  → 例外：涉及形式化验证，codex > cc

冲突类型 3：价值判断冲突（"该不该做"）
  → 必须升级到用户（任何 Agent 都不能单方面决定）

冲突类型 4：自我质疑冲突（"我们之前的判断错了吗"）
  → 引入第四方仲裁（其他 Agent，或用户）
  → 不能由当事 Agent 自己审自己
```

### 2.4 工程对应物

**新增**：`multi-agent/cognitive-reconciliation.md`，规定：
- 冲突检测机制（三 Agent 输出对比）
- 4 类冲突的默认裁决规则
- 升级路径（什么时候必须找用户）
- 冲突日志（写入 `0-System/agent-conflicts.md`）

**改造现有**：`autoRouteEngine()` 不只看任务类型，还看"是否存在认知冲突"——有冲突时自动召集多 Agent 投票。

### 2.5 验收（mycc 项目）

- mycc 一周内 agent-conflicts.md 至少有 3 条记录（证明真的在检测）
- 每条冲突记录含：触发 Agent / 冲突内容 / 裁决依据 / 最终选择
- codex 审查时主动质疑"cc 单方面判断"的场景

### 2.6 三项目多 Agent 模式总览（V1.2.2 新增）

> 不同项目的多 Agent 模型完全不同。**用错模型 = 方法论失效**。

| 维度 | mycc | brain | EvoDesk |
|------|------|-------|---------|
| **协作模型** | 固定 3 脑（cc/codex/gemini） | **单 Agent 服务** + 多客户端消费 | **swarm fork** + 能力槽位 + autoDream + 心流统一 |
| **通信** | 飞书群聊（人类可读） | HTTP API（机器可读） | 进程内 AsyncLocalStorage |
| **分工** | 用户手动 + autoRouteEngine() | 单实例 | 心流状态机自动编排 |
| **冲突 reconcile** | 4 类规则裁决（§2.3） | 矛盾检测优先（VALUES V2） | M16 监控 + 心流裁决（V1.2 §3.5） |
| **状态延续** | RECENT_EVENTS + memory-items | 数据库 + truth 版本化 | AsyncLocalStorage + compiled_truth |
| **后台 Agent** | autonomous-loop（CronCreate） | ❌ 无 | autoDream daemon（V1.2 P2 B15.5） |
| **本节适用** | §2.1-2.5 | brain VALUES.md V9 | V1.2 第十二章 |

**关键认知**：
- mycc 三脑模型不能套到 EvoDesk（EvoDesk 没有"群聊"）
- EvoDesk swarm 模型不能套到 mycc（mycc 没有同进程 fork）
- brain 是 swarm 的"被消费方"，自身不是 swarm

**weekly-digest（03 方法论机制）的多 Agent 视角选择**：
- 优化 mycc 方法论 → cc + codex + gemini 三脑
- 优化 EvoDesk 方法论 → fork swarm 内 Planner/Executor/Verifier 各自总结
- 优化 brain 方法论 → cc + codex 双视角

## 3. 工程深化 3：元认知必须独立成层 ⭐⭐⭐

### 3.1 人话

**codex 把"修正判断"塞在认知方法论的尾巴。但元认知必须独立。** 当反馈到来时，第一个问题不是"我判断错在哪"，而是"这个反馈本身可信吗"。**这个问题挡住 99% 的"用户说错也跟着错"场景。**

### 3.2 认知 vs 元认知的区别

| 维度 | 认知方法论 | 元认知 |
|------|----------|--------|
| 对象 | 世界 | 自己的认知 |
| 问题 | "X 是什么" | "我怎么知道 X" |
| 触发 | 用户提问 | 反馈到来、判断冲突、自我察觉 |
| 输出 | 答案、判断 | 置信度、反思、暂停 |
| 失败模式 | 错误结论 | 过度自信 / 过度怀疑 |

### 3.3 五层认知架构（V1.0 提出）

```
                                  ┌─────────────────────┐
                                  │   价值论 (VALUES)    │  ← 终极仲裁
                                  └──────────┬──────────┘
                                             │
                              ┌──────────────▼──────────────┐
                              │   元认知 (Metacognition)     │  ← 独立看门人
                              │   - 反馈可信度评估           │
                              │   - 置信度自评              │
                              │   - 漂移检测                │
                              │   - 信念-记忆-偏好分离       │
                              └──────────────┬──────────────┘
                                             │
                ┌────────────────────────────┴────────────────────────────┐
                │                                                          │
       ┌────────▼────────┐                                       ┌────────▼────────┐
       │  认知方法论       │                                       │  实践方法论       │
       │  - 感知           │                                       │  - 决策           │
       │  - 表征           │                                       │  - 行动           │
       │  - 判断           │                                       │  - 验证           │
       └────────┬────────┘                                       └────────┬────────┘
                │                                                          │
                └──────────────────────┬───────────────────────────────────┘
                                       │
                              ┌────────▼────────┐
                              │  反馈层 (Feedback) │  ← 多源、分级
                              │  6 级反馈源        │
                              └────────┬────────┘
                                       │
                                       ▼
                              修正认知 / 修正实践
```

**注意**：元认知是"反馈如何修正认知/实践"的看门人。没有元认知，反馈直接打到认知层 = 系统会被高频低质反馈带偏。

### 3.4 工程对应物（M16 元认知监控器）

详见独立规格：`/Users/rayman.chen/mycc/2-Projects/evo-desktop-ai/docs/M16-metacognition-spec.md`

核心能力：
- `evaluateFeedback(source) → confidence`（反馈可信度评估）
- `shouldReflect(events) → ReflectionEvent | null`（漂移检测）
- `emitReflection(event)`（输出反思）
- 维护 beliefs/preferences/memories 三张表的分离

### 3.5 验收

- 元认知触发次数 ≥ 用户纠正次数（证明没全盘接受）
- 每次反思记入 RECENT_EVENTS
- memory-item 在被反思后标 `[needs-review]`，不立即翻转

### 4.1 人话

**价值论是整个系统的初始条件。** 每条价值都决定了一组架构选择。codex 提了价值论但没展开——因为哲学层难以工程化。但**不工程化的价值论 = 没有价值论**，所有冲突最后都靠 ad-hoc 拍脑袋解决。

### 4.2 三项目的价值差异

## 5. 工程深化 5：失败的四象限分类 ⭐⭐

### 5.1 人话

**codex 的反馈循环假设失败 = 都需要修正。但工程上要分四象限**，每种修复路径完全不同。

### 5.2 失败四象限

```
                  实践对           实践错
              ┌─────────────┬─────────────┐
              │             │             │
   认知对      │   完美       │  执行 bug   │
              │ （不需修复）  │ （修代码）   │
              │             │             │
              ├─────────────┼─────────────┤
              │             │             │
   认知错      │ 误打误撞     │ 系统性偏差   │
              │ （修信念）   │ （修架构）   │
              │             │             │
              └─────────────┴─────────────┘
```

### 5.3 各象限的危险性排序

| 象限 | 危险性 | 修复路径 | 当前 mycc 处理 |
|------|--------|---------|---------------|
| 完美 | 0 | 无 | ✅ |
| 执行 bug | 中 | 修代码、补测试 | ✅ failure-escalation |
| **误打误撞** | **🔴 最危险** | **修信念，反思"为什么觉得这么做对"** | **❌ 当前不区分** |
| 系统性偏差 | 高 | 修架构、改方法论 | ⚠️ 部分（PIVOT） |

**为什么"误打误撞"最危险**：成功的负面学习。系统会强化"错误信念 + 错误执行 → 但运气好成功了"的关联。下次以更高自信犯更大错。

### 5.4 工程对应物

**新增**：在 `failure-escalation.md` 之前插入「失败归因」步骤：

```
失败检测 → 归因到四象限 → 选修复路径
                ↓
       ┌────────┼────────┬────────┐
       ↓        ↓        ↓        ↓
     完美    执行bug   误打误撞  系统偏差
     (skip)  (修码)    (修信念)  (修架构)
                          ↓
                    标记 memory-item
                    [success-but-wrong-reasoning]
```

**新增表 schema**：

```sql
CREATE TABLE failure_attribution (
  id TEXT PRIMARY KEY,
  task_id TEXT,
  cognitive_correct BOOLEAN,
  praxis_correct BOOLEAN,
  quadrant TEXT CHECK(quadrant IN ('perfect', 'exec_bug', 'lucky', 'systemic')),
  fix_path TEXT,
  timestamp INTEGER
);
```

### 5.5 验收

- failure_attribution 表跑 1 周后，4 象限都有数据
- 误打误撞象限触发时，对应 memory-item 必须标 needs-review
- 系统性偏差象限触发 ≥3 次时，自动建议 PIVOT 到新方法论

## 6. 工程深化 6：记忆的双重身份 ⭐⭐

### 6.1 人话

**记忆既是认知材料（"我之前知道什么"）又是实践材料（"我之前做过什么"）。当前都混着用，召回时不分场景。** 应该按问题类型路由不同召回路径。

### 6.2 记忆-信念-偏好的分离（新建概念）

| 类型 | 性质 | 更新机制 | 例子 | 当前 mycc 状态 |
|------|------|---------|------|---------------|
| **记忆 (memory)** | 发生过的事实 | append-only，只增不改 | "2026-04-17 部署了 v0.9.0" | ✅ RECENT_EVENTS |
| **信念 (belief)** | 从记忆推出的判断 | 贝叶斯式更新（新证据 → 后验） | "Mini 端口默认是 18080" | ❌ 混在 memory-items |
| **偏好 (preference)** | 基于价值的选择倾向 | RL 强化（反馈 → 强化/弱化） | "川哥喜欢简洁回复" | ❌ 散落 |

**当前 mycc 的 memory-items.md 把这三种混在一起 = 更新机制错位**。比如把"信念"当"记忆"，新证据来了不更新；把"偏好"当"信念"，单次反馈过度修正。

### 6.3 召回路由（按问题类型）

| 问题类型 | 召回源 | 不召回 |
|---------|-------|--------|
| 事实型（"X 是什么"） | memory + belief | preference |
| 操作型（"怎么做 X"） | agent_case + skills + belief | memory（避免噪音） |
| 评价型（"X 好不好"） | preference + belief + cases | memory（避免锚定） |
| 反思型（"为什么我这样做"） | episodic_traces + reflection_log | belief（避免合理化） |

### 6.4 工程对应物（EvoDesk 优先落地）

**改造 brain-context.ts**（M3 召回模块）：
```typescript
// V1.1 现状
function loadBrainContext(query: string): BrainContextResult {
  // 4 路 RRF 不分场景
}

// V1.2 改造
function loadBrainContext(query: string, intent: QueryIntent): BrainContextResult {
  switch (intent) {
    case 'factual': return retrieveFromMemoryAndBelief(query);
    case 'operational': return retrieveFromCasesAndSkills(query);
    case 'evaluative': return retrieveFromPreferencesAndCases(query);
    case 'reflective': return retrieveFromTracesAndReflections(query);
  }
}
```

## 7. 工程深化 7：反馈源的可信度分级 ⭐⭐

### 7.1 人话

**codex 说"反馈修正认知"——但反馈本身有质量差异。** 如果系统对所有反馈一视同仁，会被高频低质反馈带偏。

### 7.2 6 级反馈可信度表

> 数字见 `0-System/constants-truth-table.md` §2 — 本表只保留语义，数值以真值表为准。

| 级别 | 反馈源 | 权重（[ref]） | 处理规则 |
|------|--------|---------------|---------|
| L1 | 客观验证（测试通过/失败、HTTP 状态、编译错误） | K_FEEDBACK_OBJECTIVE（[ref] 1.0） | 立即修正，无需元认知介入 |
| L2 | 用户即时明确反馈（"对/错/重做"） | K_FEEDBACK_USER_IMMEDIATE（[ref] 0.85） | 修正，但元认知需要查"用户是否有误解" |
| L3 | 用户行为反馈（采纳预见/忽略） | K_FEEDBACK_USER_BEHAVIOR（[ref] 0.7） | 累积 N 次才修正（避免单次偶然） |
| L4 | 模型自评（LLM-as-judge） | K_FEEDBACK_LLM_JUDGE（[ref] 0.5） | 参考，不足以驱动修正 |
| L5 | 启发式评分（关键词、长度） | K_FEEDBACK_HEURISTIC（[ref] 0.3） | 仅作排序参考 |
| L6 | 沉默 | K_FEEDBACK_SILENCE（[ref] 不可用） | **沉默 ≠ 满意**（重要） |

### 7.3 加权融合公式

```typescript
function aggregateFeedback(sources: FeedbackSource[]): UpdateDecision {
  const weighted = sources.map(s => s.score * WEIGHTS[s.level]);
  const total = weighted.reduce((a, b) => a + b, 0);
  const confidence = total / sources.length;
  
  return {
    shouldUpdate: confidence > 0.6,  // K_DECISION_UPDATE_BELIEF（[ref] > 0.6）
    direction: total > 0 ? 'reinforce' : 'weaken',
    requiresMetaReview: sources.some(s => s.level >= 4),  // 低质反馈触发元认知
  };
}
```

### 7.4 工程对应物

新增 `metacognition/feedback-trust.ts`：
- 输入：所有反馈来源
- 输出：是否触发认知/实践修正
- 副作用：写入 feedback_audit 表

### 7.5 验收

- L4-L5 反馈不能单独触发信念翻转
- 沉默必须显式记录（不能默认为正面）
- 加权后的修正决策可追溯

## 8. 工程深化 8：认知-实践配速 ⭐⭐

### 8.1 人话

**认知和实践不一定同步。系统的智慧很大程度上是让两者按场景节奏匹配。**
- 认知快、实践慢 = "想清楚但做不出来" → 需要执行加速器
- 实践快、认知慢 = "做了但没想清楚" → 需要反思制动器

### 8.2 4 种配速模式

| 任务类型 | 配速 | 例子 | 当前 BRO-PDCA 档位 |
|---------|------|------|------------------|
| 简单重复 | 实践驱动，认知最小化 | 文件 rename、跑测试 | 简洁档 ✅ |
| 复杂未知 | 认知驱动，实践最小化 | 架构选型、bug 根因 | 完整档 ✅ |
| 创新探索 | 两者并行，互相质询 | 产品设计、新算法 | ⚠️ 无对应档 |
| 危机响应 | 实践先行，认知补救 | 生产 bug、紧急回滚 | ⚠️ 无对应档 |

### 8.3 配速选择器

```
任务到达 → 特征抽取
            ├─ 已知/未知 (knowledge_gap)
            ├─ 可逆/不可逆 (reversibility)
            ├─ 紧急/从容 (urgency)
            └─ 单步/多步 (complexity)
            ↓
      配速决策矩阵：
      
      未知 + 不可逆 + 紧急      → 危机响应（实践先行 + 边做边想）
      未知 + 不可逆 + 从容      → 完整档（认知主导）
      未知 + 可逆 + 任意        → 创新探索（并行）
      已知 + 任意 + 任意        → 简洁档/普通档（实践主导）
```

### 8.4 工程对应物

`3-Thinking/03-认知实践配速协议.md` + `BRO-PDCA` 升级到 V2，加入 4 档（创新探索 / 危机响应 是新增）。

### 8.5 验收

- mycc 任务开始时输出配速判断（"本任务=创新探索档"）
- 不同档位有不同的"中间检查频率"（创新档每步质询，危机档事后审计）
