# 09 · 桌面智能体分层架构方法论 —— 怎么把一款 Agent 产品拆对层

> 提炼自 1-Inbox/2026-04-15-桌面智能体产品方案分析.md，日期 2026-06-17
> 一句话定位：判断"做这类自进化桌面 Agent 该怎么拆"的可复用框架——不是某个产品的方案全文。

---

## 0. 核心结论（先行）

这类产品（用户可自选模型 + 内核具备自进化能力的桌面智能体）这条路**成立，且差异化明确**，但成败不在 UI 和基础 Agent Loop，而在分层质量。

- **差异化不在"再做一个 IDE Agent"**。只看 UI + 基础 Agent Loop，会落入 Cursor / Windsurf / Cline / opencode / goose 已覆盖的赛道。
- **差异化在三件事叠加**：① 更强的任务理解与执行组织 ② 更强的长期记忆与用户建模 ③ 更强的规则/技能/记忆策略自进化。把感知、记忆、预测、进化、治理做成第一公民，产品才从"一次性编码助手"变成"长期共生的桌面 Agent OS"。
- **最关键的一句判断**：「接近 Opus 的能力」主要不来自某个模型名字，而来自**系统编排质量**。所以投入应押在编排/记忆/验证，而非追逐模型。

> 适用对象：评估或设计任何"本地优先 + 可插拔模型 + 带认知内核"的 Agent 产品。

---

## 1. 分层架构方法论（怎么拆这类产品）

**第一原则：拆成三层解耦，绝不做成单进程单体。** 这是源文件认定的"最关键设计决策"。

| 层 | 职责 | 关键判据 |
|----|------|---------|
| **Desktop Shell（桌面壳）** | 体验、权限确认、可视化、检查点、配置、结果回放。用户**只与这一层**直接交互 | 壳越薄越好；体验问题不下沉到内核 |
| **Local Runtime（本地运行时）** | 文件/Git/终端/浏览器/MCP/IDE bridge 的执行；会话状态机、工具调度、沙箱、后台任务。对上提供**统一 Agent Session API** | 用本地 sidecar server，**不要把 agent loop 塞进前端** |
| **Brain Kernel（认知内核）** | 上下文装配、用户建模、记忆检索、预测、规划、反思、进化、治理。对下只看"能力接口"，**不直接耦合 UI** | 内核是最值钱的资产，必须能脱离具体壳独立演进 |

**拆层的复用逻辑（这套思想可迁移到其它 Agent 产品）**：
- 体验层（壳）、执行层（运行时）、认知层（内核）三者变化速率不同——壳随交互趋势变、运行时随工具生态变、内核随长期能力沉淀变。**变化速率不同的东西必须解耦**，否则任一层迭代都会牵动全身。
- "一个 Agent Core，多种客户端"是产品扩展形态的正解：桌面/CLI/API/未来的 Slack/GitHub/web 都只是同一个 brain 的前端。这要求内核与壳从第一天就分开。

---

## 2. 模型层方法论：选"能力槽位"，不选"模型名"

**核心判断：产品内部不应围绕"模型名"工作，而应围绕"能力角色"工作。**

把模型抽象成**能力槽位**（角色），再把具体模型绑定到槽位：

- `Planner`：深度推理、任务拆解、方案生成
- `Executor`：工具调用稳定、低延迟、代码/文件执行
- `Verifier`：独立校验、测试解释、反例检测（尽量不与 Executor 同 provider）
- `Memory`：低成本事实提取、巩固、矛盾检测（可用本地小模型）
- `Vision`：多模态理解
- `Judge`：离线评测、对抗评分

**两层配置**：普通用户只选预设（"最强推理/均衡执行/本地隐私/低成本"）；高级用户把模型绑到槽位（如 Planner=最强推理、Executor=工具稳的快模型、Memory=本地模型）。

**为什么这样拆**（三个收益）：① 前沿模型快速更替时产品不改架构 ② 保留用户 BYOM 自由 ③ 内核能稳定做路由、回退、多模型协作。

> 避坑：不要把"用户自选模型"做成一堆 endpoint/key/model-name 表单——要做成**稳定的配置语义**。

---

## 3. 记忆层方法论：多层 + 矛盾检测 + 验证后写入

**核心判断：长期记忆 ≠ 把历史对话塞回 prompt。** 必须做成显式分层、可治理。

源文件建议的记忆分层（至少五层，实际列了六类）：

- `Scratchpad`：当前任务临时工作记忆
- `Session Memory`：单会话上下文与压缩摘要
- `Durable Personal Memory`：用户长期偏好、环境、关系、习惯
- `Workspace / Team Memory`：项目规则、代码约定、常见流程
- `Knowledge Memory`：外部文档、网页、知识库
- `Trajectory Memory`：成功/失败轨迹、技能表现、修复历史

**两条最重要的设计要点**：
1. **矛盾检测**——记忆不做矛盾处理，越用越烂。
2. **验证后写入**——不是所有"猜到的事实"都该进 durable memory。

> 工程化参考（源文件从 claude-code-source 提炼的可复用模式，非本产品独有）：durable memory 抽取**异步化**（不堵主链路）、consolidation 设 **gate**、team/workspace memory 走**同步模型**。

## 4. 自进化内核的设计要点：先进化软的，最后才动权重

**核心判断：自进化要分层、要克制，三层之间严格排序。**

| 层 | 进化什么 | 风险 |
|----|---------|------|
| **第一层 规则层** | prompt 片段、规则与禁令、技能触发条件、工具选择策略 | 低 |
| **第二层 配置层** | 记忆检索权重、模型角色映射、工具权限默认值、compaction/summarization/checkpoint 策略 | 中 |
| **第三层 模型层** | 轨迹筛选、数据集构建、SFT / preference tuning | 高 |

**排序铁律**：**前两个大版本只做前两层，模型权重进化放最后。** 理由——风险更低、回滚更容易、对用户更可解释，且前两层收益已足够大。

**自进化的信任前提（人类在环）**：要让用户接受"自进化"，必须让它 ① 看得见做了什么 ② 能回滚 ③ 能比较前后版本 ④ 能区分"哪些是模型行为、哪些是系统自动进化导致的改变"。**没有验证 + 回滚体系，不许让自进化直接改生产逻辑。**

**主链路闭环**（用系统设计弥补单模型短板，是"接近 Opus 体验"的实现路径）：

```
Perceive → Plan → Act → Verify → Reflect → Consolidate
```

- Perceive：读任务/工作区/用户状态/相关记忆/相关知识/最近失败轨迹
- Plan：Planner 明确目标、约束、风险、任务树
- Act：Executor 执行子任务，必要时调工具或子 agent
- Verify：独立 verifier 做测试、diff 审查、约束核对
- Reflect：失败归因（模型不懂？上下文不够？工具选错？记忆误导？规则缺失？）
- Consolidate：只把**跨会话有用**的经验沉淀进 durable memory / skills / rules

价值：强模型负责真正难的推理，系统负责把"思考-执行-校验-沉淀"连起来——体验上更像"一个会工作的智能体"而非"一个能回答问题的大模型"。

## 5. 关键判断 / 避坑清单（什么不能做）

源文件明确列出的反模式（短期省事、长期拖死产品）：

1. **把桌面 UI、agent loop、brain、工具执行塞进一个进程**（违背第 1 节第一原则）。
2. **直接把 brain 暴露成公网服务**。
3. **把"用户自选模型"做成一堆 endpoint / key / model name 表单**（违背第 2 节）。
4. **把长期记忆等同于"把历史对话塞回 prompt"**（违背第 3 节）。
5. **让自进化直接改生产逻辑而没有验证和回滚**（违背第 4 节信任前提）。
6. **只做编码场景，不做 workspace / personal memory / background workflows**——会退化成"模型聚合器 + MCP 面板"，没有护城河。

一句话收口：**把"执行能力"产品化，把"长期进化能力"系统化。**

**借鉴的判断框架**（评估参考项目时怎么取舍）：每个开源项目只借它的强项，不照搬它的弱项。源文件的判法——opencode 借"开放运行时分层"（外骨骼），goose 借"多客户端统一协议/一个 Core 多端"（交通层），claude-code-source 借"记忆与后台反思中台"（神经系统）。**多 provider 本身不是护城河**，记忆与进化层才是。

---

## 6. 适用边界

- **适用**：本地优先、可插拔模型、需要长期记忆/用户建模/自进化的桌面或多端 Agent 产品的架构判断。
- **不适用 / 需谨慎**：
  - 纯一次性问答/聊天工具——上三层解耦是过度设计。
  - 不需要长期记忆的轻量场景——记忆分层和矛盾检测是负担。
  - 团队还没把验证体系、回滚体系、记忆质量体系跑稳时——**不要放大到模型层自进化**（源文件反复强调的排序前提）。
- **落地顺序建议**（方法论层面的优先级，非具体功能表）：先做"能稳定完成复杂任务的桌面 Agent" → 再做"会自我变强的 Agent" → 最后才做"会自己训练自己的 Agent"。前两步就能把产品拉到很强的位置，第三步只在验证/回滚/记忆质量稳定后才值得放大。
