# BRO-PDCA 方法论

> 来源：FUTURUS 内部方法论文档
> 定位：做事、沟通、协作的统一语言框架
> 核心理念：充分沟通的目标管理 + 包容创新的持续改善

---

## 一、BRO（目标对齐阶段）

**本质**：在动手之前，先把"为什么做"和"做到什么程度"想清楚、说清楚。

### B — Background（背景）

| 要素 | 说明 |
|------|------|
| B1 事情背景 | 前因后果，详细到读完文档无需面对面解释 |
| B2 干系人 | 相关人员 + 为什么需要他们参与 |

**关键要求**：
- 说清楚"今天的讨论在整个计划的哪一步"
- 说清楚"需要解决什么问题"
- 标准：读完文档就能看懂，无需口头补充

### R — Requirement（需求沟通）

| 要素 | 说明 |
|------|------|
| R1 发起方初步需求 | 草拟的目标 + 原则 + 背后逻辑 |
| R2 团队沟通确认 | 通过表格收集各方观点 → 合并同类项 → 面对面讨论争议 → 达成共识 |

**R2 会议流程**：
1. 填写个人观点（10min）
2. 汇总、合并、简化
3. 面对面讨论争议点（可选）
4. 输出结论：目标+原则 / 待办任务

### O — Objective（目标共识）

| 要素 | 说明 |
|------|------|
| O1 目标和目的 | "做什么" + "为什么做"（why） |
| O2 原则和原因 | "怎么做的边界" + "为什么这么约束"（why） |

**三层递进理解**：
- **目标**（实）：咀嚼后的指令，MBO 最低限度，保证大概结果
- **原则**（虚）：保证过程中做"正确、高效"的模糊决策
- **目的/原因**（底层逻辑）：保证执行人在未来遇到问题时做出最正确的选择

> 越靠近 CEO 的 OKR，越需要详细阐述目的和原因。

## 二、PDCA（执行改善阶段）

**本质**：不追求一步到位，持续改善，与自己和解，与他人共情。

### P — Plan（策划）

| 要素 | 说明 |
|------|------|
| P1-A（WHAT，系统-知） | 事情的逻辑是什么，目标的具象化（图谱/思维导图/画板） |
| P1-B（HOW，统筹-行） | 如何实现，找谁协作，什么时间完成（流程图/泳道图） |
| P2（Plan 本身） | 具体内容：起止时间、交付物、负责人，Be SMART |

**P1 的详细程度 = 授权程度**（越详细 = 授权越明确）

#### 历史摩擦预查（Dyna "在想象中预演"启发，2026-04-01 起）

> 理论来源：Sutton 的 Dyna 架构 —— 用历史经验在"想象"中预演，提前规避已知的坑。

**普通档/完整档任务的 P1 拆解时**，先做一次"历史预演"：

1. **查轨迹**：`0-System/trajectories/` 中是否有同类任务的轨迹 → 复用成功路径，标记失败路径
2. **查已知坑**：`memory-items` 中 `[project/Bug-Fix]` / `[project/Bug-Fix-已知]` 有无相关记录
3. **查摩擦热区**：`task-log.md` 的 `friction_skill` 字段中，该领域的历史摩擦频率是否偏高

**输出**（追加在 P1 拆解后）：
```
[历史预演]
- 相关轨迹：有/无（轨迹文件名）
- 已知坑：[列出命中的 Bug-Fix 条目，或"无"]
- 摩擦热区：[该领域历史摩擦频率 高/中/低/无数据]
```

**触发条件**：仅普通档（20%）和完整档（10%）。简洁档直接执行，不做预演。

#### 探索温度策略（玻尔兹曼机/模拟退火启发，2026-04-01 起）

> 理论来源：玻尔兹曼机的温度参数 —— 高温时广泛探索，低温时收敛到最优解。

不同档位和阶段使用不同的**探索策略**：

| 档位 × 阶段 | 温度 | 策略 |
|-------------|------|------|
| 简洁档（全程） | 🧊 低温 | 用已知最优方案直接执行，不探索替代方案 |
| 普通档 P 阶段 | 🌤️ 中温 | 列 2-3 个备选方案，快速评估后选一个 |
| 普通档 D/C 阶段 | 🧊 低温 | 已选定方案后专注执行，不再发散 |
| 完整档 P 阶段 | 🔥 高温 | 广泛探索（GitHub search + 多方案对比 + 多引擎意见），充分搜索后逐步收敛 |
| 完整档 D 阶段 | 🌤️ 降温 | 执行已选方案，遇阻时允许有限探索替代路径 |
| 完整档 C/A 阶段 | 🧊 低温 | 收敛验证，不再引入新变量 |

**与 failure-escalation 的衔接**：
- RETRY 阶段 = 低温（同方向微调）
- REFINE 阶段 = 中温（换方法）
- PIVOT 阶段 = 高温（换方向，广泛探索）

#### 注意力预测声明（AST 协议，2026-03-31 起）

> 理论来源：Attention as Action —— 注意力是一种可规划的内部行动，不是被动的信息过滤。

**普通档/完整档任务的 P1 拆解时**，追加注意力预测：

```
[注意力预测] 本任务预计需要关注：[类别1], [类别2], [类别3]
```

**执行意义**：
- 预测写入检索轨迹的 `predicted` 字段
- attention-audit skill 定期对比 predicted vs injected → 计算准确率
- 准确率低 → 说明 cc 对自己注意力需求的理解不足 → 触发策略调整

**触发条件**：仅在普通档（20%）和完整档（10%）任务的 P1 阶段启用。简洁档不需要。

### D — Do（实施）

- 创新工作先做 **Demo**（调动少量资源，形成试点）
- 或引用已有案例（同步块/链接）
- 按 P2 推进，实现成果交付

#### 预测-修正循环（PP 协议，2026-03-31 起）

> 理论来源：预测处理理论（Predictive Processing）—— 大脑持续生成预期，通过预测误差驱动学习。

**执行关键步骤前**，显式生成「预期结果声明」：

```
[预期] 执行 <操作> 后，应得到 <预期结果>
[实际] <实际结果>
[惊讶度] 低/中/高
[动作] 符合预期 → 继续 | 轻微偏差 → 微调 | 高度偏离 → 触发 investigate
```

**触发条件**（不是每步都需要，只在以下场景启用）：
- 涉及外部系统交互（API 调用、服务部署、配置变更）
- 普通档/完整档任务的关键里程碑
- failure-escalation 进入 REFINE 阶段后的每次尝试

**惊讶度量表**：
| 等级 | 含义 | 动作 |
|------|------|------|
| 低 | 结果在预期范围内 | 继续执行，不记录 |
| 中 | 结果可解释但非最佳 | 记录偏差，微调后继续 |
| 高 | 结果完全出乎意料 | 暂停执行，先诊断再继续，记入 friction-patterns |

#### 惊讶度累积学习（PP 升级，2026-04-01 起）

> 启发来源：AI 史纲中玻尔兹曼机的"正相-负相"对比学习 —— 预测与实际的差距就是学习信号。

**惊讶度不只是当下的判断，还应该累积形成领域画像**。

每次 PP 协议产生「惊讶度=高」时，追加一行到 `0-System/evolution-log.md` 的**惊讶热力图**section：

```
[惊讶] {领域标签} | 预期: {一句话} | 实际: {一句话} | {日期}
```

**月度分析**（MetaClaw full 模式时自动执行）：
- 统计各领域的高惊讶度频率
- 频率 ≥ 3 次/月的领域 → 标记为「预测盲区」
- 预测盲区的任务自动提升档位（简洁→普通，普通→完整）
- 连续 2 个月零惊讶的领域 → 标记为「校准良好」，可降级档位

**与 HOT 元认知的协同**：惊讶度连续高 → 触发 HOT 元认知反思 → 反思结论更新 memory-items → 下次预测更准 → 惊讶度降低。这是一个自校准闭环。

### C — Check（跟进复盘）

| 层级 | 频率 | 内容 |
|------|------|------|
| 大 CHECK（C1） | 季度/年度复盘会 | P1 是否最优，能否实现目标 |
| 小 check（C2） | 每周例会 | P2 进展跟进，识别具体问题 |

### A — Action（改善更新）

- 把对的加以肯定，对错的进行修正
- 提炼工作标准，进行沉淀
- 更新 O1/O2 → 形成新一轮 PDCA rolling

## 三、使用场景速查

| 场景 | 复杂度 | 操作 |
|------|--------|------|
| 1. 简洁模式 | 极简 | 直接给 O1 + O2（目的和原因已包含背景） |
| 2. 普通模式 | 简单 | B1 + B2 → O1 + O2 |
| 3. 完整模式 A | 创新+经验不足 | B → R1 → R2 → O → PDCA |
| 4. 完整模式 B | 创新+需统战 | B → R1 → R2（争议升级至决策者）→ O → PDCA |
| 5. 会议模式 | 同 3 或 4 | 会议场景下的完整模式 |
| 6. 个人完整模式 | 个人创新 | 自发寻求帮助，走完整 BRO 流程 |
| 7/8. 授权模式 | 复杂授权 | 被授权方写 R1 → 授权方确认 → O |

**选择原则**：
- 30% 的情况用简洁模式（场景 1），避免过度流程化
- 30% 用普通模式（场景 2），补充背景即可
- 剩余用完整模式，按团队/个人/授权场景选择

## 四、实际应用场景

### 1. 系列会议/活动
- B1=会议背景 → B2=参会人和角色 → O1=会议目的 → O2=会议原则
- P1=泳道图（各部门工作安排）→ P2=具体任务和时间节点

### 2. 文档搭建（知识库/方法论/RSF资料）
- BRO 对齐目标 → P1 画逻辑骨架 → P2 拆任务 → D2 填充内容 → C+A 持续迭代

### 3. 流程搭建
- B+R 对齐 → O 确定流程目标和原则
- P1=流程图 → P2=各阶段任务拆解 → D2=多线并行执行
- C1=季度复盘 P1 → C2=周例会跟进 P2 → A2=问题闭环+知识沉淀

### 4. BRO~P 授权模型
- 用 BRO + P1 拆解任务的"授权"
- P1 的详细程度决定授权程度

## 五、文化价值观

BRO-PDCA 不仅是方法论，也是 FUTURUS 的文化：

- **包容**：先从公司角度归因，不急于找个人问题，为员工带来"安全感"
- **创新**：鼓励暴露问题，积极解决问题
- **持续改善**：量变到质变，员工变得越来越"贵"，公司越来越有活力
- **知行合一**：You will never be ready — 在知中行，在行中知

## 六、cc 的理解与应用

> 以下是 cc 对 BRO-PDCA 的理解，便于在日常协作中灵活运用。

### 对 cc 的启发

1. **接到任务先确认 O**：目标是什么？原则是什么？背后的原因是什么？
2. **复杂任务先画 P1**：不急着写代码，先画逻辑图/流程图
3. **交付物要闭环**：做完要 Check，Check 后要 Action
4. **沟通用 BRO 结构**：给老板汇报时，先说背景（B），再说需求/建议（R），最后说目标（O）
5. **场景匹配复杂度**：简单事直接给结论（场景 1），复杂事走完整流程

### 在飞书协作中的应用

- 飞书群任务 → 先确认是哪个场景（简洁/普通/完整）
- 多智能体协同 → BRO 阶段由 cc 主导（规划），PDCA 阶段分发给 codex/gemini
- 定时任务报告 → 自带 Check 环节，异常时触发 Action
