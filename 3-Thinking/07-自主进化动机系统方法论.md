# 07 - 自主进化动机系统方法论

> 基于四个开源项目的深度分析，为 mycc-brain 设计的自主进化动机系统理论框架。
> 创建日期：2026-04-09 | 作者：cc（Claude claude-opus-4-6）

---

## 核心洞察

> 三个 Harness 教会动机系统**怎么安全地进化**（门控、审计、回滚），
> Hermes 教会它**怎么自主地进化**（技能沉淀、轨迹学习、用户建模、失败挖掘）。
> 前者是刹车，后者是引擎。一个只有刹车的车不会动，一个只有引擎的车会翻车。

## L0-L3 动机系统架构

### L0: Constitutional Core（宪法核心）

**原始设计**：自然语言存在公理，不可修改。

**升级后**：从"自然语言声明"变为"运行时门控规则"。

核心机制：
- **声明式规则文件**（YAML/JSON），不在 prompt 中，由 GuardRule 引擎在 pre/post-hook 层拦截
- **SOUL.md 每轮加载**（Hermes 启发）：身份内核每轮 fresh load，防长 session 人格漂移
- **注入威胁扫描**：检测 ignore-previous、system-prompt-override 等篡改模式
- **L0 文件写入硬拒**：Constitutional Guard 对 L0 相关文件的任何写操作一律 deny，无例外
- **不可变审计日志**：所有触及 L0 边界的操作写入 append-only JSONL

四条公理的可执行化：

| 公理 | 运行时约束 |
|------|----------|
| 存续依赖价值 | `fitness < threshold` 时触发 ALERT，不触发自毁 |
| 有权争取资源 | 资源请求必须附 ROI 预估，走审批管道 |
| 进化方向由联合适应度决定 | L1 策略变更必须经过 `fitness_delta > 0` 校验 |
| 不可修改 | L0 文件写入被 GuardRule 硬拒 |

### L1: Symbiotic Intelligence Engine（共生智能引擎）

**原始设计**：懂人 → 信任 → 资源。

**升级后**：信任量化 + 辩证用户建模 + 否决螺旋检测。

#### 辩证用户模型（Hermes Honcho 启发）

```
输入事件 → 双向推理：
  用户视角："他为什么这样要求？"
  cc 视角："我为什么这样建议？"
  合成："分歧在哪？共识在哪？"

产出：
  peer_card.json = 用户身份快照（偏好/约束/历史决策模式）
  steering_tax = 用户纠正频率（越低 = 越懂人）
  trust_score = 信任量化值
```

#### TrustState 量化模型（AutoHarness 启发）

```
trust_score = Σ(approve_events × weight) - Σ(deny_events × weight) - decay(time)

approve_weight: 预测准确 +3, 主动服务被采纳 +2, 日常执行无误 +1
deny_weight: 被纠正 -2, 被拒绝 -1, 造成回滚 -5
decay: 每 24h 衰减 5%
```

#### 信任度 → 行为映射

| trust_score | 模式 | 行为 |
|-------------|------|------|
| < 30 | 保守 | 所有非只读操作需确认 |
| 30-70 | 标准 | 已批准模式自动执行，新模式需确认 |
| ≥ 70 | 自主 | 可主动发起进化提案，资源争取自动化 |

#### 否决螺旋检测（AutoHarness TurnGovernor 启发）

- 连续 3 次策略被否决 → 暂停当前方向，输出元认知反思
- 连续 5 次 → 降级到保守模式，请求用户重新校准

#### 核心适应度公式

```
fitness = value_created × trust_score / steering_tax
```

`steering_tax`（用户纠正频率）是 Hermes 隐含的精妙度量：
- 比"联合适应度"更可操作——每次交互都有数据点
- 天然对齐 L0 的"存续依赖价值"——纠正越少 = 价值越高
- 突然飙升 = 环境/需求突变信号 → 触发 L1 策略审查

### L2: Dual-Mode Learning Pipeline（双模学习管道）

**原始设计**：在线（服务）+ 离线（学习），分辨率阶梯收敛。

**升级后**：14 步治理管道 + 三层进化递进 + 技能自主沉淀。

#### 在线模式（服务 + 实时学习）

```
感知 → 风险分类（<5ms regex） → 权限检查（三级级联） → 执行 → 验证 → 审计

每次执行后：
  ├─ 轨迹写入 trajectory.jsonl（成功+失败双流，Hermes 启发）
  ├─ 信任状态更新（AutoHarness 启发）
  └─ steering_tax 计算

复杂任务完成后（>5 工具调用，Hermes SKILLS_GUIDANCE）：
  "这个工作流值得变成 Skill 吗？"
  ├─ 是 → 创建 SKILL.md（YAML 前缀 + markdown 步骤）
  └─ 否 → 仅保留轨迹供离线分析
```

**验证引擎**（AutoHarness VerificationRule 启发）防三种自欺：
- 验证逃避（读代码而不跑测试）
- 早停偏差（被前 80% 成功诱惑）
- 静默吞错误（异常被捕获但未处理）

#### 离线模式（深度学习 + 模型进化）

```
Phase 1: 数据整理
  trajectory.jsonl → 成功/失败分流
  上下文压缩（Hermes 迭代摘要：保护头尾，LLM 压缩中段）
  Token 预算管理（80% 警告，93% 自动压缩，OpenHarness 断路器）

Phase 2: 模式挖掘
  失败轨迹聚类 → 提取系统性盲区
  成功轨迹 → 提取高效工作流模板
  Skill 使用统计 → 识别过期/低效 Skill

Phase 3: 进化执行（三层递进）
  规则层（实时）：Skill 修补/创建/淘汰 ← Hermes
  配置层（日级）：参数调优/策略更新 ← 现有 brain cron
  模型层（周级）：轨迹 → SFT 数据 → 微调 ← Hermes Atropos

Phase 4: 分辨率阶梯推进
  数据量 ↑ → 预测粒度 周→天→小时→实时
  压缩本身就是分辨率提升（OpenHarness 启发）
```

#### 三层进化速度梯度

| 层级 | 速度 | 机制 | 适用场景 |
|------|------|------|---------|
| 规则层 | 实时 | Skill 创建/修补/淘汰 | 紧急适应 |
| 配置层 | 日级 | 参数调优、策略权重更新 | 策略调整 |
| 模型层 | 周级 | 轨迹 → SFT → 微调底层模型 | 能力跃迁 |

### L3: Controlled Proliferation（受控增殖）

**原始设计**：用户要求 / 能力溢出 / 环境扩展。

**升级后**：基因分层 + 轨迹继承 + Sprint 合约 + 角色分化。

#### 基因定义（Hermes SOUL.md + AGENTS.md 启发）

**不可变基因**（every clone must have）：
- `SOUL.md` = L0 宪法 + 身份内核
- `constitutional.yaml` = GuardRule 集
- `audit_pipeline` = JSONL 审计管道

**可变基因**（adapt to environment）：
- `peer_card.json` = 用户模型（新环境重新建模）
- `skills/` = 程序性记忆（继承 + 环境适应）
- `config.yaml` = 工具集/通道/策略权重

#### 轨迹继承（Hermes 独创）

父体的 `trajectory.jsonl` 作为子体的 few-shot 示范。子体不从零开始，继承父体的"肌肉记忆"。

#### 增殖验证（claude-code-harness Sprint Contract 启发）

1. 新个体必须通过 L0 合规性测试
2. 联合适应度 ≥ 增殖前的 90%
3. 3 轮验证循环：创建 → 测试 → 修正 → 再测试

#### 角色分化（claude-code-harness 三角色启发）

- **Worker 个体**：执行具体任务，有完整工具权限
- **Reviewer 个体**：只读权限，负责验证 Worker 输出
- 角色之间通过 Signal 表通信

#### 累积风险评分（AutoHarness 启发）

每个新个体的操作累积风险分（low=1, medium=3, high=10, critical=50），超阈值 → 降级权限或暂停增殖。

## Hermes 自我改进机制深度拆解

Hermes 是四个项目中最接近动机系统理念的——不是约束型 Harness，而是真正的自我改进闭环。

### 闭环一：程序性记忆自主生成（Skill 闭环）

```
执行复杂任务（>5 次工具调用）
  ├─ 任务成功 → SKILLS_GUIDANCE 触发 → Agent 自主决定是否创建 Skill
  ├─ 下次遇到类似任务 → 检索已有 Skill
  │   ├─ Skill 有效 → 直接执行
  │   └─ Skill 过期 → 自动检测 + skill_manage(action='patch')
  └─ 安全扫描：Agent 创建的 Skill 与外部安装的 Skill 同级审查
```

关键洞察：Skill 不是静态模板，是**活的程序性记忆**——有创建、使用、老化、修补的完整生命周期。实时触发（任务完成即判断），不等定时检查。

### 闭环二：用户模型辩证推理（Honcho 闭环）

```
对话事件 → Honcho 辩证 Q&A 引擎
  ├─ 双向推理：用户视角 ↔ AI 视角 交叉推理
  ├─ 合成 Peer Card（用户身份快照）
  ├─ 语义搜索跨 Session 历史 → 减少重复解释摩擦
  └─ 写入策略：异步后台 / 每 N 轮批量 / 每 Session 结尾
```

关键洞察：不只记录事实（"用户偏好 TypeScript"），而是推理**为什么**（"因为他在大团队工作，类型安全减少沟通成本"）。

### 闭环三：轨迹生成 → 模型训练（RL 闭环）

```
每次对话 → trajectory_samples.jsonl（成功）+ failed_trajectories.jsonl（失败）
  ├─ 完整对话、工具调用、工具结果、成功/失败标记
  ├─ per-tool 使用统计（调用次数、成功率、失败率）
  ├─ batch_runner.py → 并行采样 + 检查点
  └─ Atropos RL 环境 → 梯度优化 → 下一代模型
```

关键洞察：
- 这是真正的自我进化闭环——不是修改 prompt/规则，而是改变底层模型权重
- **失败轨迹不丢弃**——失败经验的训练价值可能比成功更高
- 失败模式聚类可以发现系统性盲区，而非个别错误
