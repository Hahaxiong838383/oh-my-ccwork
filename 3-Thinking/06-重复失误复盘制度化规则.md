# 重复失误复盘制度化规则（Meta-Rule for Repeated Failures）

> **定位**：mycc 方法论体系第 6 条，**元规则**（meta-rule）。高于具体规则（如 05-产品定义回流规则）。
> **触发来源**：2026-04-18 用户指示"重复犯 2 次以上的错误，就要复盘找原因，解决之后将规则进行制度化"。
> **版本**：V1.0
> **权威性**：元规则级（可以生产出新的具体规则）

---

## 一、规则全文

> **任何错误模式重复出现 ≥ 2 次（第二次复现即触发），cc/codex 必须：**
> 1. **立即暂停继续犯同一错误**（元认知优先）
> 2. **做 Why-Why 根因分析**（至少追 5 层）
> 3. **产出修复方案**（单次解决当前问题）
> 4. **制度化升级**（把修复写成永久规则 / 脚本 / 约束，防止第 3 次复现）
> 5. **回流到对应文档**（方法论 / 项目规则 / CLAUDE.md）
> 6. **在下一次汇报开头显式标注**"已触发制度化升级"

## 三、Why-Why 根因分析模板

```
失误: {描述}
Why 1: {表层原因}
Why 2: {{why1}} 为什么发生?
Why 3: {{why2}} 为什么发生?
Why 4: {{why3}} 为什么发生?
Why 5: {根本原因（通常是流程/设计/工具缺陷，而不是"人错了"）}
```

### 示例：codex subagent 失联（3 次）

```
失误: codex:codex-rescue subagent 启动后没返回最终 assistant message
Why 1: codex 的工具执行记录完整但 final assistant block 缺失
Why 2: subagent forwarder 按规则"no final → return nothing"
Why 3: codex 的 stdout message 被 shared runtime broker 的 stream buffer 截断
Why 4: claude-code 的 codex 插件架构选择了 shared runtime 模式以节省资源
Why 5: 「架构设计在性能 vs 可靠性之间选了性能，但对长 assistant message 场景防御不足」
```

### 根因 → 修复路径 3 级

| 级别 | 做什么 | 解决 Why 几层 |
|------|-------|-------------|
| L1 单次修复 | 手工重跑 codex | Why 1 |
| L2 流程修复 | 加 timeout / retry | Why 2-3 |
| **L3 制度化修复**（本规则要求）| **让 codex 把结果写到文件，cc 读文件**（绕过 buffer）| **Why 4-5** |

## 六、调 codex 的标准协议（方案 A 制度化）

> **强制**：cc 调用 codex subagent 时**必须**遵守以下协议。违反即视为重度违反本元规则。

### 协议

1. **codex prompt 开头必含**：
   ```
   ❌ 禁止在 assistant message 输出长内容（会被 subagent forwarder 吞）
   ✅ 必须把完整结果写到 /tmp/codex-<task>-<slug>.md
   ✅ assistant message 只输出一句："结果已写到 /tmp/codex-<task>-<slug>.md"
   ```

2. **cc 等 codex 返回后必做 3 步校验**（codex 声称完成 ≠ 真完成）：
   ```bash
   ls -la /tmp/codex-<task>-<slug>.md  # 文件存在?
   wc -l /tmp/codex-<task>-<slug>.md   # 行数合理?（应 >100 行对于审查任务）
   head -5 /tmp/codex-<task>-<slug>.md  # 内容有效?
   ```

3. **若文件不存在/为空**（即 codex 失联）：
   - cc 主线独立做审查（不等 codex）
   - 触发**本元规则**：记录为失联第 N 次
   - 若 N=1 → 记 RECENT_EVENTS
   - 若 N=2 → 按本规则复盘 + 升级制度化
   - 若 N≥3 → 升级用户 + 考虑暂停 codex subagent 用法，改走 codex app 路径

### 违反处理

- 漏加 prompt 开头约束 → 轻度违反，立即补
- 声称"codex 审查完成"但没校验文件 → 重度违反（典型"真实>表演"失败）
- 第 3+ 次重复 codex 失联不升级 → 触发元认知反思 + 升级用户

## 七、本元规则与其他规则的关系

```
元规则（本规则 06）
  ↓ 约束产生
具体规则（05 产品定义回流 / CLAUDE.md 写后读 / ...）
  ↓ 约束产生
具体动作（7 项 ✅ 列表 / scripts/sync-*.sh / ...）
```

**优先级**：元规则 > 具体规则 > 具体动作。

**冲突时**：元规则赢。例如某具体规则说"某任务可跳过校验"，但本元规则说"重复违反校验 ≥2 次必须升级"，**以本规则为准**。

## 七、codex effort 自动调度（心流映射，V1.1 新增）

> **触发**：用户指出 codex 默认 `xhigh` 导致简单任务也 4-25 分钟，且有失联风险。
> **要求**：按任务难度自动选 effort + 默认 `fast` + 防降智。
> **理论根据**：V1.3.7 §4 心流 challengeRatio。

### 7.1 effort ↔ skill 映射

| effort | skill 值 | 预期耗时 | 适合 taskComplexity |
|--------|---------|---------|-------------------|
| `minimal` | 0.1 | 10-30s | 0.05-0.15（格式检查）|
| `low` | 0.25 | 30s-2min | 0.2-0.3（grep/诊断）|
| `medium` | 0.5 | 2-5min | 0.4-0.6（简单审查）|
| `high` | 0.75 | 5-15min | 0.6-0.85（对抗审查）|
| `xhigh` | 1.0 | 15-40min | 0.85-1.0（架构/深逻辑）|

### 7.2 taskComplexity 估算（cc 调 codex 前）

| 维度 | 打分 | 权重 |
|------|-----|------|
| 涉及文件数 | 1=0.1, 2-3=0.3, 4-7=0.6, 8+=0.9 | 0.3 |
| 代码/文档总行数 | <500=0.2, 500-2K=0.5, 2K-5K=0.75, 5K+=1.0 | 0.25 |
| 任务深度 | 格式=0.1, 诊断=0.3, 审查=0.6, 对抗/架构=0.9 | 0.3 |
| 产出预期长度 | <200字=0.2, 200-1K=0.5, 1K-3K=0.75, 3K+=1.0 | 0.15 |

加权平均 → taskComplexity ∈ [0, 1]

### 7.3 决策规则（目标 FLOW 区间 challengeRatio ∈ [0.8, 1.2]）

```python
def select_effort(complexity):
    target_skill = complexity / 1.0  # 目标 ratio = 1.0
    if target_skill <= 0.15: return 'minimal'
    if target_skill <= 0.3:  return 'low'
    if target_skill <= 0.6:  return 'medium'
    if target_skill <= 0.85: return 'high'
    return 'xhigh'
```

### 7.4 硬约束（防降智 + 防浪费）

| 场景 | 硬要求 |
|------|-------|
| 对抗审查（adversarial）| **至少 `high`** — 低 effort 对抗审查 = 降智，不可接受 |
| 架构决策 / 锁定原则审查 | **至少 `high`** |
| 跨文档（> 3 文件）审查 | **至少 `medium`** |
| 格式检查 / 简单 grep | **禁止 `xhigh`** — 是浪费，等于 BOREDOM 区间 |
| 新任务类型（未知难度）| 先用 `medium` 试，根据输出质量调整 |

### 7.5 默认 `fast` 模式（V1.3.11 制度化）

- `~/.codex/config.toml` 默认含 `service_tier = "fast"` ✅
- 调 codex 时**不指定 service_tier = 继承 config**（不需要 cc 显式传）
- 验证方式：看 codex 响应时间 / config.toml `service_tier` 字段

### 7.6 cc 调 codex 的标准 Agent prompt 头部（V1.3.11 新增）

```
effort: {auto-selected}       # 按 taskComplexity 自动
service_tier: fast (default)
output_contract: write_to_file # 方案 A（本元规则 §六）
writeback_path: /tmp/codex-<slug>.md
```

### 7.7 违反处理

- 简单任务用 `xhigh` → 浪费 + 可能失联，立即改 `medium`/`low`
- 复杂任务用 `low` → 降智输出无效，返工 + 元认知反思
- 连续 ≥2 次错选 effort → 触发元规则 06，修 §7.2 估算权重
