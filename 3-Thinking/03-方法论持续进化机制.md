> 把"前沿监控"从"日报推送"升级为"方法论自进化输入"。

> **目标**：让 mycc / brain / EvoDesk 的认知/实践方法论每周自动接收一次"理论 + 实践"的优化建议，形成**发现 → 综合 → 分诊 → 落地 → 复盘**的闭环，而不是每天刷一下飞书就滑过去。

> 沉淀时间：2026-04-17

> 理论依据：[`00-认知与实践方法论体系.md`](./00-认知与实践方法论体系.md) §1（时间尺度）+ §3（元认知）+ §7（反馈分级）

## 零、一句话定义

**雷达不是为了让川哥每天多看一条飞书，而是为了让 mycc / brain / EvoDesk 的方法论每周、每月、每季度自动接到一次"外部现实"的矫正。**

没有闭环的雷达 = 信息焦虑生成器。
有闭环的雷达 = 方法论的外部反馈源。

## 一、双雷达分工

| 雷达 | 关注域 | 输入的方法论 | 现状 | 触发节奏 |
|------|-------|------------|------|---------|
| **theory-radar** | 前沿学术（arXiv 脑科学/认知科学/神经计算/LLM 机制） | **认知方法论**（怎么想） | 已建（08:15 cc 抓取+分析 / 08:45 codex 归档） | 每日 |
| **github-radar** | 热门开源（AI Agent / 多智能体 / 记忆系统 / Skills 框架） | **实践方法论**（怎么做） | 已建（23:30 抓取+分析+升级建议） | 每日 |

**分工的合理性**：
- 学术理论 → 认知层（看清楚世界）：arXiv 告诉我们"人脑/模型的机制可能是 X"，直接喂给 3-Thinking 母版的认知章节
- 开源项目 → 实践层（做成事情）：GitHub 告诉我们"别人是这么落地的"，直接喂给 skills / agent-orchestration / patterns

**不重叠原则**：两个雷达不应该相互覆盖。如果某天两个雷达同时捡到同一个信号（比如 mem0 既有论文又有 repo），**github-radar 负责实现细节，theory-radar 负责理论根基**，综合阶段再合流。

## 二、闭环机制（V0 → V1 → V2）

### V0（现状）

```
arXiv / GitHub
    ↓
 radar 脚本
    ↓
 飞书日报 ────→ 川哥可能刷到 ────→ 方法论文档基本不更新
```

**问题**：信号进了"人的注意力队列"，但没有进入"系统的记忆-信念-偏好回路"（见 02-HOT §二.4）。大部分当天就被其他消息刷掉了。

### V1（本机制核心目标）

```
arXiv / GitHub
    ↓
 radar 脚本（日）
    ↓
 每周综合（层 2）────→ 分诊（层 3）────→ 分发到三项目（层 4）
    ↑                                          ↓
    └──────────── 复盘回流（层 5） ────────────┘
```

**关键升级**：
- 把信号从"日频"聚合到"周频"（时间尺度从"分钟-天"升到"周"，见 00-母版 §1）
- 用三 Agent 综合（cc 看认知、codex 看实践、gemini 看跨域）避免单 Agent 偏差（见 00-母版 §2）
  - ⚠️ **V1.2.2 澄清**：这里的"三 Agent"是 **mycc 模式**（飞书群聊三脑），适用于优化 mycc 项目的方法论
  - **优化 EvoDesk 项目的方法论时**应改用 EvoDesk 内部 swarm 的多视角（fork Planner/Executor/Verifier 各自总结），见 V1.2 §12.5 多 Agent × M16 协同
  - **优化 brain 项目的方法论时**用 cc + codex 双视角即可（brain 客户端是机器，不需 gemini 跨域综合）
- 过元认知层（见 02-HOT）：不是雷达说什么就采纳什么，先评估反馈可信度
- 落地到 PR/Patch，而不是停在"建议"

### V2（愿景，半年后）

雷达不仅优化方法论，**最终能优化 5 层架构本身**。
- 当雷达连续 N 个月指向"现有 5 层不够用"（比如出现新的时间尺度、新的反馈源类型），触发母版重构提案
- 这就是**元-元认知**：方法论本身的进化方法论（见 02-HOT §九.1 的 2 阶 HOT）

## 三、5 层处理管道

### 层 1：日采集（已有）

| 项 | 内容 |
|---|------|
| theory-radar | 每日 08:15 跑，输出 `/tmp/theory-radar-data.json` + Wiki 归档 |
| github-radar | 每日 23:30 跑，输出 `/tmp/github-radar-data.json` + 飞书升级建议 |
| 产物归集 | 每日数据需要 append 一份快照到 `0-System/radar-archive/YYYY-MM-DD/`，供周综合读取（当前两个脚本各自存档，格式不统一，需要补一个采集钩子，见 §八） |

**不改 skill 本体**：radar 的抓取/分析逻辑保持原样，只在它们产物就绪后加一个**归档钩子**，把 JSON + 飞书发送内容写到 `0-System/radar-archive/`。

### 层 2：周综合（新建）

**脚本**（设计，不实现）：`scripts/weekly-methodology-digest.sh`（主入口） + `scripts/weekly-methodology-digest.ts`（核心逻辑）

**触发**：每周日 22:00（避开工作时段，周一早上用户第一眼看到）

**输入**：`0-System/radar-archive/` 过去 7 天的 JSON

**处理流程**：
1. **读 7 天信号**：合并 theory-radar 论文（~70 篇）+ github-radar 项目（~28 个）
2. **去噪**：
   - 论文去重（按 arxiv_id，过去已经在 radar 内部去过，这里兜底）
   - 项目去重（按 repo，避免连续 7 天挂榜的同一项目被 7 倍计数）
   - 排除价值：stars 涨幅 <10%、论文引用数为 0 且非新兴方向
3. **三视角综合**（关键步骤，用 multi-agent/RULES.md §认知 reconcile 协议）：

| Agent | 视角 | 输出 N 条（目标 3-5 条/视角） |
|-------|------|---------------------------|
| cc（Claude） | **认知方法论角度** | "本周 X 篇论文集中指向 Y 现象，母版 §Z 的论述可能需要更新" |
| codex（GPT-5.4） | **实践方法论角度** | "本周 M 个项目都采用了 pattern P，skills/agent-orchestration 缺这个抽象" |
| gemini（Google） | **跨域联结** | "论文 A 和项目 B 其实在说同一件事：{桥接点}" |

4. **汇总成 digest**：`0-System/methodology-weekly-digest/YYYY-Www.md`（ISO week 号）

**digest 模板**：
```markdown
# Week YYYY-WNN 方法论综合

## 本周雷达总览
- 论文 X 篇，热度 top 3：...
- 项目 Y 个，star 涨幅 top 3：...

## 三视角发现

### cc（认知层）
- 发现 1：[描述] | 关联母版章节：[章节] | 建议动作：[动作]
- ...

### codex（实践层）
- 发现 1：[描述] | 关联 skill/pattern：[路径] | 建议动作：[动作]
- ...

### gemini（跨域）
- 桥接 1：理论 X ↔ 实践 Y | 潜在新 pattern：[描述]
- ...

## 分诊提案
（层 3 输出，见下）

## 元认知审查
（层 3 输出，见下）
```

### 层 3：分诊与提案（digest 内一章）

对层 2 产出的每条"发现"打四个标：

| 标签 | 取值 | 含义 |
|------|-----|------|
| **target** | `mycc` / `brain` / `EvoDesk` / `methodology-foundation` | 改哪个项目。`methodology-foundation` 指 3-Thinking 母版本身 |
| **layer** | `values` / `metacognition` / `cognitive` / `praxis` / `feedback` | 五层架构（见 00-母版 §3.3） |
| **priority** | `P0` / `P1` / `P2` | 见下面 |
| **action** | 具体动作 | 见下面 |

**priority 定义**：
- **P0（颠覆性）**：如果为真，会让现有方法论某章节过时或错误。必须本周内讨论。例：一篇顶会论文证明当前 HOT 协议的置信度自评方向错了
- **P1（重要补强）**：现有方法论能吸收，但需要主动扩充。月度批量更新。例：mem0 的新记忆分层方式值得借鉴到 brain 召回
- **P2（值得跟进）**：记录到 backlog，季度复盘时再看。例：一个 star 500 的小项目用了有意思的 prompt 技巧

**action 动作集**：
| priority | action |
|---------|--------|
| P0 | 立即改方法论文档 + 飞书 @ 川哥 + 更新 RECENT_EVENTS + 启动对抗审查 |
| P1 | 合并到月末 `monthly-methodology-update` PR 草稿 |
| P2 | 追加到 `0-System/methodology-backlog.md`（季度复盘时检查） |

### 层 4：分发与落地

每条动作对应的 PR 位置：

| target | 分发路径 |
|--------|---------|
| mycc | `/Users/rayman.chen/mycc/3-Thinking/` 或 `/Users/rayman.chen/mycc/0-System/`，PR 到本仓库（main 分支） |
| brain | `/Users/rayman.chen/mycc-brain/docs/methodology/`（新建目录），PR 到 brain repo |
| EvoDesk | `/Users/rayman.chen/mycc/2-Projects/evo-desktop-ai/docs/methodology/`（新建目录），PR 到 EvoDesk 独立分支或主线 |
| methodology-foundation | 修改 `3-Thinking/00-认知与实践方法论体系.md`，必须附 codex 对抗审查 |

**落地纪律**：
- 每次落地追加 `RECENT_EVENTS.md`（实时写入门，见 CLAUDE.md §记忆实时写入门）
- 每次落地必须引用对应的 weekly-digest 文件路径（保证可追溯）
- P0 落地必须更新 `3-Thinking/04-决策记录.md`（重要方法论决策）

### 层 5：复盘回流（新建，V1 末期加）

digest 采纳 4 周后，回头看效果：

```markdown
## Week YYYY-WNN 方法论采纳复盘
- Week YYYY-W(NN-4) 提出的 P0/P1 动作：
  - [动作 A]：✅ 已落地 | 实际改善：[指标变化] | 是否需要回滚：否
  - [动作 B]：⚠️ 落地后发现偏差 | 回滚到：[commit] | 教训：[教训]
- 本周综合是否受上一轮教训影响：[是/否 + 说明]
```

**不回滚纪律**：
- 任何方法论改动 4 周内不删，即使感觉"不对"也先观察
- 4 周后回滚需显式理由，记入 `04-决策记录.md`

## 四、双 Reflex 机制（被动 + 主动）

### 主动 Reflex（周定时）

| 时间 | 动作 | 产物 |
|------|------|------|
| 周日 22:00 | `weekly-methodology-digest.sh` 跑一次 | `methodology-weekly-digest/YYYY-Www.md` |
| 周一 09:00 | 飞书推送 digest 摘要（用 tell-me 或 lark-im） | 群消息 |
| 周一 10:00 | 川哥确认 P0 动作（默认 24 小时内没回复视为同意 P1/P2 自动落地） | 动作清单 |

**沉默 ≠ 满意**（见 02-HOT §七.5）：P0 必须用户显式确认，不能因为川哥忙就默认通过。

### 被动 Reflex（事件触发）

雷达发现**异常信号**时，不等周综合，立即触发 mini-digest：

| 触发条件 | 阈值 | 动作 |
|---------|------|------|
| theory-radar 高影响因子论文 | Nature/Science/NeurIPS oral 且跨域（脑科学 + AI） | 当日立即生成 mini-digest（单篇深度），升级为 P0 |
| github-radar 爆款项目 | 单日 +1000 stars 或 7 天 +5000 stars | 当日立即生成 mini-digest，评估是否为新范式 |
| 连续 3 天同主题论文涌现 | 3 天 ≥5 篇论文聚焦同一概念（如"token-level uncertainty"） | 触发 mini-digest，检查是否值得写新的 Thinking 条目 |
| 关键 repo 大版本 | mem0 / autogen / crewAI / letta 等已跟踪项目发新 major | 触发 mini-digest，重点看 breaking change |

**被动触发的元认知保护**：不是每个触发都立即改方法论。先走过一次 HOT §职责1 的"反馈可信度评估"，确认不是虚假信号（例如营销性质的 star 灌水、会议宣传造势）。

## 六、防误更新机制

雷达发现 **≠** 必须采纳。每条 P0/P1 提案在 digest 里必须回答 4 个问题：

### 6.1 元认知反思（见 02-HOT §五）
```
[🪞 元认知] 这条改动如果错了，会怎样？
- 我原本的方法论假设：{一句话}
- 雷达指向的新假设：{一句话}
- 偏差根因（如果采纳错了）：{一句话}
- 调整动作：{采纳 / 暂缓 / 拒绝}
```

### 6.2 可逆性评估
| 等级 | 含义 | 采纳阈值 |
|------|-----|---------|
| 完全可逆 | `git revert` 即可，无 DB schema 变更 | P0 可直接动手 |
| 部分可逆 | 需要数据迁移但不丢数据 | P0 需川哥批准 |
| 不可逆 | 涉及用户信念库、生产数据、外部 API 契约 | 必须 P0 级 + 川哥 + codex 对抗审查三方都通过 |

### 6.3 冲突检测
- 与 **00-母版** 是否冲突？冲突时谁让步？（默认：母版让步需要更高权威 = 川哥）
- 与 **01-BRO-PDCA** 是否冲突？（默认：BRO 让步比母版容易）
- 与已有 **memory-item** 是否冲突？（见 02-HOT §职责4 的路由规则）
- 与 **VALUES.md**（待建）冲突时：价值论绝对优先，雷达信号必须让步

### 6.4 评估周期
采纳后 N 周复盘。默认周期：
- 方法论文字改动：4 周
- skill/pattern 新增：2 周
- 代码级改动（EvoDesk/brain）：1 周

N 周内有负面信号（用户纠正、测试回归、元认知反思），立即回滚。

- weekly-digest 每次必须记 task-log
- 被动 mini-digest 必须记 task-log（因为是异常触发）

## 九、长期愿景（V2 的野心）

### 9.1 从"优化方法论"到"优化 5 层架构本身"

雷达连续 N 个月指向"现有 5 层架构不够"，触发母版重构提案：
- **触发条件**：连续 3 个月 weekly-digest 有条目提议新增"层"或重组"层"
- **重构流程**：
  1. cc 起草新架构（保留旧 5 层 + 建议的新增层）
  2. codex 对抗审查（质疑新层是否真的独立、是否 orthogonal 于旧层）
  3. gemini 外部文献检索（新层是否已有成熟学术支撑）
  4. 川哥终审
  5. 过了终审后，`00-认知与实践方法论体系.md` 升级到 V2.0

### 9.2 元-元认知（见 02-HOT §九.1 的 2 阶 HOT）

雷达不仅评估认知，还评估"cc 自己的置信度评估能力"：
- 如果某个 cc 连续 3 次说"这篇论文 P0"但最终都被证明不重要 → 说明 cc 的 P0 判断标准需要校准
- 写入 `feedback_audit` 表（见 00-母版 §7.4），作为 cc 自我校准的证据

### 9.3 方法论的"生态化"

长远看，mycc / brain / EvoDesk 三项目的方法论不是"三份文档"而是"一个共生体"：
- 共享 00-母版 + VALUES.md（未来）
- 各自特化的方法论（brain 重记忆、EvoDesk 重自主、mycc 重编排）
- **雷达是三者共同的外部输入**，防止三项目各自孤立演化

## 十三、风险与局限

### 13.1 信息过载风险
雷达每天 ~10 篇论文 + ~12 项目，一周 ~70 + 84 = 154 条信号。三 Agent 处理后只能 compress 到 9-15 条 digest 条目。**信噪比至关重要**。

**对策**：
- 严格 priority 标（70% 信号应该是 P2 甚至不出现在 digest 里）
- 月度复盘 P1 的实际采纳率（低于 30% 说明综合阶段筛选过宽）

### 13.2 Agent 幻觉放大
三 Agent 都可能"幻觉"地说一篇论文/项目"很重要"。周综合把三个 Agent 幻觉平均化不会消除幻觉。

**对策**：
- 每条 P0 必须有至少 2 个 Agent 独立提出才升级（投票机制）
- codex 对抗审查作为 gate：必须有 codex 的"no objections"才落地

### 13.3 方法论震荡
如果每周都改方法论，方法论失去稳定性。

**对策**：
- P0 每季度最多 3 次
- P1 每月汇总成一个 PR，不分散改
- 回滚期（4 周）内不能再改同一章节

### 13.4 三 Agent 之一长期不可用
如果 gemini 被封、codex 额度爆了，digest 会连续多周缺视角。

**对策**：
- 允许降级到 2 Agent 或 1 Agent，但 digest 必须标注
- 连续 4 周缺同一 Agent 视角 → 触发元认知"是不是该换 Agent 了"
