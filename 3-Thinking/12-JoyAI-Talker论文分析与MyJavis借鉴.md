## 一、论文是什么

**JoyAI-Talker: Full-Duplex Speech Interactive Large Model Built for Empathetic Voice Agents**（京东 JoyAI 团队）。

三层解耦的 **Duplex-Thinker-Talker** 架构：

| 层 | 职责 | 规模 |
|---|---|---|
| **Joy-Duplex** | 实时话轮控制（该不该被打断/该不该回应） | 独立 1.7B decoder + 流式 audio encoder（160ms chunk） |
| **Thinker** | 语义认知（推理/共情/CoT） | JoyAI-LLM Flash，48.9B MoE（激活 3.28B） |
| **Talker** | 表现力语音合成（指令可控韵律+副语言事件） | JoyVoice 架构（AR Transformer + Diffusion） |

立论核心（§2）：把高频、低层的流式状态跟踪塞进主语言骨干会"割裂上下文注意力、稀释参数容量"→ 认知退化。所以话轮控制必须**卸载到外层轻量模块**，大脑只管想。Joy-Duplex 明确定位为 plug-and-play——"给已有半双工系统装上全双工能力，不改动核心骨干参数"。

## 二、核心机制：语义门控话轮控制（对我们最有价值的部分)

论文点破痛点（§2.3.3）：帧级声学能量判打断，"经常在自然的迟疑中造成误打断"。Joy-Duplex 改为在流式解码里生成五个**状态 token**，构成语义状态机：

| 状态 token | 语义 | 下游动作 |
|---|---|---|
| `<\|partial\|>` | 用户还在说，意图未成形 | 大脑待命，不抢话轮 |
| `<\|complete\|>` | 转写到达完整句法边界 | 触发最终门控判定 |
| `<\|backchannel\|>` | 短反馈（嗯嗯/yeah） | 承认存在，**不交话轮** |
| `<\|accept\|>` | 确认是对系统说的有效请求 | 开闸，大脑说话 |
| `<\|reject\|>` | 背景泄漏/对第三方说话/环境噪声 | 显式压制，防误激活 |

关键设计：`<|complete|>` 之后**还有一道 accept/reject 语义闸**——"有没有人在说完整的话"和"这句是不是对我说的"是两个独立判定。我们现有系统（火山 `InterruptSpeechDuration`、自研线 `min_interruption_words`）都只做到第一层。

**Full-Duplex-Bench v1.5 成绩**（ICASSP 2026，论文引文 [4]）：

| 场景 | 正确行为 | Joy-Duplex | GPT-4o | Gemini 3.1 Live |
|---|---|---|---|---|
| 真插话 | 让位（C_RESPOND ↑） | **0.88** | 0.78 | 0.77 |
| 语气词回应 | 继续说（误触 ↓） | **0.01** | 0.03 | 0.02 |
| 对第三方说话 | 继续说（误触 ↓） | **0.17** | 0.91 | 0.27 |
| 环境音 | 继续说（误触 ↓） | **0.10** | 0.93 | 0.28 |

GPT-4o 环境音场景误触 0.93——**十次有九次被环境音打断**。说明"抗环境音打断"是行业级未解难题，不是我们配置没调好。论文 Limitations 也自认：模型感知集中在语音信号与说话人属性，缺乏通用音频事件/环境声理解能力。

## 三、四条借鉴（按性价比排序）

### 1. 拿 Full-Duplex-Bench v1.5 当打断质量标尺

自制遥测的语义边界由自己定，错了没人纠正（2026-08-04 实证：122 条空 interim 报成环境音打断，实际 104 条是正常播完，量级错 7 倍，见 memory `feedback_event_source_semantics_before_counting`）。该 benchmark 把"被误打断"拆成四个可分别归因的场景 + 公开 SOTA 基线。
⚠️ 未验证：是否开源、评测脚本能否直接跑，用前先查。

### 2. 语气词打断门分两桶（对 2026-08-04 定稿方案的实质修正,详见 §四）

### 3. 声纹进打断门控（仅 MyJavis 主线 + 自研线）

论文 §2.3.2：Speaker Verification 插件与 encoder 并行跑，确保大脑"只被授权说话人触发"。MyJavis 已有火山声纹 Mode=2 资产，但现在只用于记忆分账和称呼，未参与打断决策。
约束三条：
- **火山线装不下**——声纹结果是事后拼进 LLM 文本的，打断决策已在火山侧做完；
- **同事租户线禁用**（2026-08-04 已否决过：注册库无同事家人，开了=所有打断被否决，负收益）；
- 兜底必须是"未识别 → 降级到更严的时长/语义门"，**不是一律否决**。

### 4. 方向确认：解耦架构没走错

论文整节论证话轮控制内嵌主干会认知退化 → 必须外挂。MyJavis 从第一天就是这个形状（火山管 I/O + CustomLLM 管大脑），2026-07-15"不换端到端 realtime 模型"的拍板从此有 SOTA 论文背书。

**架构级观察**：论文最值钱的语义门控，只有自研线（voice-agent LiveKit 栈）装得下——`min_interruption_words`/`false_interruption_timeout`/endpointing 全在自己手里，且有 interim 文本可做语义判据；火山线判定权在火山侧。这给 0.18.0 双栈切换补了一个当时没想到的论据：**自研线是唯一能承载语义级话轮控制的容器**。

## 四、语气词两桶方案（判决逻辑 / 收益 / 限制）

### 4.1 原方案的缺陷

2026-08-04 定稿判据：`短 AND 归一化后整句只由语气词构成 → 否决打断`。词表：嗯/啊/哦/噢/呃/唉/哼/咳/嘿/哈/呀/喔/诶及叠字。

缺陷：**同一个音节承载两种相反的会话功能**——

| 功能 | 例 | 用户意图 | 正确动作 |
|---|---|---|---|
| backchannel（附和/伴随声） | "嗯嗯""哈哈"、咳嗽 | 我在听，你继续 | 不打断 ✓ |
| repair initiator（修复启动） | "嗯？""啊？""什么？" | **我没听懂，你停下** | 必须打断 ✗ 被误杀 |

原方案把整表当一类全部否决，等于把 repair initiator 也当成了 backchannel——**恰好在用户最需要打断的时刻（困惑、要求重说）不让打断**。用户"啊？"之后系统继续自说自话，用户会提高音量重复，形成对抗式交互；这比被环境音误打断更伤体验。会话分析里"嗯？/啊？"是标准的 open-class repair initiator；JoyAI-Talker 的 token 设计同样按功能拆分（`[Confirmation-en]` 与 `[Question-en]` 是两个 token，同音不同功能——`-en/-ah/-ei/-hnn` 对应 嗯/啊/诶/哼 为推断，论文无中文对照，但命名结构可确证"按功能分类"这一点）。

### 4.2 改后的判决逻辑

```
输入: 打断触发瞬间的 ASR interim 文本
norm = 归一化(去空白/标点前先记录是否含问号)

① query 桶（优先级最高）→ 放行打断:
   含 "？/?"  OR  norm 匹配疑问词面(什么/啥/怎么/为什么…)
② backchannel 桶 → 否决打断:
   len(norm) ≤ N  AND  norm 全部由 backchannel 词表构成(嗯/哦/哈/呃/唉/咳/哼…及叠字)
③ 其余 → 放行打断（默认=现状行为）
```

三个要点：
- **query 判定必须先于 backchannel**："嗯？"的字符全在语气词表内，若先走 ② 就会被否决——问号使它短路进 ①。
- **默认失败模式=放行**：任何判定不确定都退化为现状（有字就打断），门只做减法不做加法。
- 落点不变：复用 barge_gate.py 骨架，纯函数 + 单测，先 `act=False` 观测,只上租户线。新增必测用例：「嗯？」「啊？」「什么？」放行；「嗯嗯」「哈哈」否决；「什么时候提醒我吃药」放行（长句不误杀）。

### 4.3 收益

1. **修掉反向伤害**：用户困惑时能立刻打断——这是原方案里唯一"门控方向做反"的场景，改动几行词表+一个优先级。
2. **backchannel 词表可以收得更全**：原方案为防误杀 query 用法只能"宁漏勿误"收紧词表；分桶后 query 用法有独立出口，backchannel 桶可放心扩词 → 语气词/伴随声拦截率上限提高。
3. **query 命中是免费遥测信号**：用户发"啊？"往往因为系统抢话或没说清，与 truncation-suspect（判停切早）同族——query 桶命中率本身就是"上一轮说砸了"的代理指标，观测期顺带采集。

### 4.4 限制（诚实边界）

1. **命门=ASR interim 有没有问号**。问号是文本层唯一的升调代理；若讯飞 interim 阶段标点不全（final 才补），打断判定时刻拿不到信号 → "嗯？"退回 backchannel 桶 → 缺陷复活。**开工前置检查：先数租户线日志里 interim 含问号的比例**。疑问词面（什么/啥/怎么）不依赖标点可先行,纯"嗯？"型只有标点一个区分器。
2. **判据寄生在第三方模型的输出习惯上**：ASR 打不打问号是讯飞模型自己的行为，可能随版本漂移（同 memory `feedback_criteria_must_match_object_variant`：判据必须跟对象形态走）。观测期要为"问号消失"设锚——若某天 query 命中骤降为零，先怀疑 ASR 行为变了而不是用户不困惑了。
3. **query 桶的 trade-off**：每收一个疑问词，backchannel 拦截面就让一块——电视里的"什么？"会穿透。方向上可接受（宁可多打断，不可困惑时不响应），但词表要克制,只收高频疑问词面,不收"吗/呢"这类句尾助词（单独出现无意义）。
4. **天花板没变**：此门只管"有字的语气词打断"；无字的环境音穿透归字数门管,两门正交。且规则版上限远低于论文的训练版——SOTA 模型语气词误触也还有 0.01、环境音 0.10，**没有便宜的完美解**。
5. 范围不变：只上同事租户线（act=False 观测先行）；MyJavis 火山线装不下（打断判定在火山侧）。

## 七、2026-08-10 interim 问号普查（§4.4-1 前置检查的回执）

数据源：64.90 租户线 `voice-worker-colleague` journalctl 全量 14 天（07-27~08-10），
639 条 interrupt telemetry 的 interim 快照（=打断判定点的原生采样）。锚全部对撞
（解析 42=grep 42 / 总数 639=639 / AgentTranscriptFinal 区分器 358 条有效）。
分母清洗后真·带字打断 226 条。脚本 `interim_qmark.py` / `qmark_short.py`（scratchpad + 服务器 /tmp）。

### 硬数据

1. **讯飞 interim 阶段会打标点**：226 条真打断里 30 条含问号（13%），跨 7 个活跃日每天都有——"interim 无标点"的担忧不成立。
2. **但「嗯？」型（纯语气词+句尾问号）14 天零出现**：纯语气词打断 9 条 = 8 条无问号（嗯/嗯嗯/唉/哈…）+ 1 条 `？嗯`（问号在句首，是上一句残留，语义与「嗯？」相反）。
3. **问号率随句长上升**（1-2字 5% → 5-8字 18%），且 19 条句尾问号去重样本清一色是带疑问词面/疑问助词的完整句（"你说什么/然后呢/你怎么不说话了/今天天气热吗"）。
   → 【推断】讯飞的问号来自**句法结构**（疑问词/语气助词），不是升调；单字语气词无句法结构，永远得不到问号。行为层结论（纯语气词不带句尾问号）为已验证。
4. **意外发现——interim 快照跨句拼接**：`？嗯` `？这个` 句首标点是上一句尾部残留。若 query 判据写成"含问号"，会把 `？嗯` 误放行——**问号判据必须限定句尾**，归一化须剥句首残留标点。

### 对 §四 两桶方案的修正（数据裁决）

- **问号腿断了**：query 桶救的对象只有"纯语气词+升调"（其余反问天然含疑问词面、进不了 backchannel 桶、不需要救）；而这类对象文本层无信号（结论 2/3）且样本零出现（结论 2）。
- **方案退化为：原单桶否决 + 一条误杀哨兵**：
  - 判定行为=2026-08-04 原定稿（短 AND 归一化后整句仅语气词 → 否决），不加 query 桶；
  - 新增纯观测哨兵：**纯语气词打断被否决后，同 room 5s 内用户再次开口且带疑问词面** → 计数为"疑似误杀反问"。它是"用户困惑被无视后重述"的行为指纹，act=False 精神下先攒数据；若频发再上音频层（升调/F0）方案。
- 原方案的误杀暴露面比论文推导的小：当前数据零出现，且误杀后用户重述的话语（"你说什么"）天然携带词面、会被放行——失败模式是"多一轮"，不是"永不响应"。
- ⚠️ 不下"反问场景不存在"的结论：语气词打断 08-04 才开始测，样本天然稀少（`feedback_eval_quality_audit_sampling_bias`：历史频次不能给未测过的场景排优先级）——所以用哨兵持续观测，而不是关掉这个问题。

**"先数再动手"的价值实证**：不数就按两桶开工 → 问号判据上线即空转（永远匹配不到目标）+ 引入 `？嗯` 误放行 bug；数完方案反而更简单。
