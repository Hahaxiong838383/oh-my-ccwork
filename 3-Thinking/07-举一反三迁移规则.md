# 举一反三迁移规则（Generalization from Success）

> **定位**：mycc 方法论体系第 7 条，**元规则**（meta-rule）。与 06（失误复盘）对偶互补。
> **触发来源**：2026-04-18 cc 发现 Gemini CLI 直调（方案 B）绕过 MCP 认证问题成功 → 用户指令"举一反三是特别好的特质，固化方法" → 立即验证 codex CLI 直调（方案 C）也成功。
> **版本**：V1.0
> **权威性**：元规则级（生产新的具体规则 + 验证后加入工具链）

---

## 一、规则全文

> **任何模式/工具/方法在一个场景成功后，cc/codex 必须：**
> 1. **立即识别成功模式的本质**（不是表面动作，是底层机制）
> 2. **主动扫描相似场景**（类比迁移：工具 A 能，工具 B 能吗？场景 X 能，场景 Y 能吗？）
> 3. **最快成本验证迁移假设**（一次轻量实测，不追求完整）
> 4. **验证通过 → 立即制度化**（写入方法论 / 脚本 / CLAUDE.md）
> 5. **验证失败 → 记录失败模式 + 分析为什么不能迁移**（避免下次再试）
> 6. **汇报含显式「举一反三」段落**（提示用户看到迁移价值）

## 二、与元规则 06 的关系

| 维度 | 元规则 06（失误复盘） | 元规则 07（举一反三） |
|------|-------------------|-------------------|
| 触发 | 错误复现 ≥ 2 次 | 成功模式首次被验证 |
| 方向 | 反应式（事后补救） | 主动式（事前泛化） |
| 动作 | Why-Why 5 层 → 修复 → 制度化 | 识别本质 → 迁移扫描 → 验证 → 制度化 |
| 产出 | 新约束 / 防御性规则 | 新能力 / 扩展性规则 |
| 风险 | 过度防御（僵化） | 过度泛化（无效迁移） |

**互补机制**：
- 06 让系统**不再重复犯错**
- 07 让系统**快速扩大成功**
- 两者共同构成"**从经验中学习**"的完整闭环

## 三、识别"成功模式"的判据

不是所有成功都要举一反三。触发判据：

| 判据 | 说明 | 例子 |
|------|------|------|
| ✅ 解决了**难以解决的问题** | 不是"能跑通"，是"修复了卡点" | Gemini CLI 直调绕过 MCP 认证 |
| ✅ 模式**底层机制清晰可描述** | 可抽象出"原因 → 结果"的机制 | "CLI 直调绕过 MCP wrapper 的 auth 覆盖" |
| ✅ **可能有类似场景** | 能想到 1-2 个迁移候选 | codex 也有 CLI，类似机制可能适用 |

**不触发**：
- ❌ 常规操作（读文件 / 跑测试这种）
- ❌ 高度特殊化（只在某 1 个场景有效）
- ❌ 无法描述底层机制（说不清为什么成功）

## 四、迁移验证的 4 步法

### Step 1：抽象本质（10 秒思考）
> 刚才我解决了 X。**为什么** 这个方法 work？抽象成 1 句话。

### Step 2：扫描候选（1 分钟想）
> 同样的底层机制还有什么地方可能适用？列 **2-3 个候选**。

### Step 3：最低成本验证（1 次轻量测试）
> 挑最明显的候选，跑一个 **< 1 分钟的 ping test**。

### Step 4：制度化（5-10 分钟）
> - 成功 → 写 helper 脚本 / 更新方法论 / 加规则到 CLAUDE.md
> - 失败 → 记录失败模式到本方法论 §六

## 五、已验证的迁移案例（V1.0）

### 案例 1：CLI 直调绕过 MCP auth（2026-04-18）

| 阶段 | 内容 |
|------|------|
| **起点** | Gemini MCP server 调用触发浏览器认证（尽管 `~/.gemini/oauth_creds.json` 已持久化）|
| **本质** | MCP wrapper 有额外环境变量（`GOOGLE_GENAI_USE_GCA=true`）覆盖了 CLI 的默认 OAuth 路径 |
| **候选** | codex 有 CLI 吗？（`which codex` 实测 `/Users/rayman.chen/local/node/bin/codex`）|
| **验证** | `codex exec --output-last-message /tmp/pong.md "pong"` → 14s 返回 + 文件写入 ✅ |
| **制度化** | 写 `scripts/codex-via-cli.sh` + 加入元规则 06 §八（方案 C）|

**迁移收益**：codex 对抗评审从失联 100%（subagent）→ 100% 成功（CLI 直调）。

### 案例 2：写后读校验跨工具复用（2026-04-17 已完成）

- **起点**：飞书 `lark-cli docs +update` push 成功 ≠ 真生效（V1.3.8 教训）
- **本质**：异步 API 必须 fetch 验证
- **候选**：sync-offline-kit / sync-progress / sync-layers（本次 Agent A 在建）
- **制度化**：所有 sync 脚本内置 `verify_remote()` 函数

## 六、失败迁移案例（V1.0）

### 案例 A：subagent forwarder 写文件绕过（方案 A）

| 阶段 | 内容 |
|------|------|
| 起点 | codex subagent 长 assistant message 被 forwarder 吞 |
| 误认本质 | "让 codex 写文件就能绕过" |
| 实际失败 | codex 根本没执行写文件的 tool_use，subagent 提前放弃 |
| 教训 | **本质抽象错了**。问题不在"输出长度"而在 "shared runtime broker + forwarder" 架构组合 |

**教训**：Step 1 抽象本质必须准确，否则 Step 3 验证浪费时间。
