## 2026-03-21 | Bug Fix | tmux mouse on 导致 ttyd 中文显示为 ____

### 根因

`~/.tmux.conf` 加了 `set -g mouse on` 后，tmux 向终端发送鼠标报告模式转义序列（`\e[?1000h`），导致 ttyd 内置的 xterm.js（含 WebGL 渲染器）切换渲染模式，CJK 字体回退失效，中文显示为 `____`。

### 修复

删除 `~/.tmux.conf`，执行 `tmux set -g mouse off`。

### 教训

**不要在 ttyd 场景下启用 tmux mouse on**。tmux 的鼠标报告模式与 ttyd 的 xterm.js WebGL 渲染器不兼容，会破坏 CJK 显示。如需触摸滚动，必须用其他方案（不改 tmux 配置）。

## 2026-03-21 | 验证通过 | FNOS JSON WS 模式中文显示正常，确认 V3 Binary 协议是根因

### 决策内容

通过 FNOS 项目（Claude-code-on-FNOS）的 JSON WS 模式在 Mac 上验证：**中文、Claude logo、ANSI 颜色全部正常显示**。确认 V3 中文失败的根因是 Binary 协议（`ws.send(Buffer)`），而非 xterm.js 或 node-pty。

### 根因分析

| 模式 | 传输方式 | 中文 |
|------|---------|------|
| V3 Binary | `ws.send(encodeBinaryFrame(opcode, Buffer.from(data, 'utf8')))` | ❌ |
| FNOS JSON | `ws.send(JSON.stringify({ type: "output", data: data }))` | ✅ |

核心差异：JSON 传输时 `data` 是 JS 字符串（Unicode 天然正确），Binary 传输时要经过 `string → Buffer(utf8) → Uint8Array` 编解码链路，在某个环节破坏了 CJK 字符。

### 当前状态

- V0（ttyd + Cloudflare + Caddy）：生产使用中，`cli.hahaxiong.top`
- V3（FNOS JSON 模式）：验证通过，Mac 端口 7681，待整合到腾讯云链路
- 腾讯云 nginx `/ttyd/` 反代已配置，但 SSH 隧道不稳定，需换 FRP 或其他方案

### 下一步

1. 把 FNOS server.js 整合多 session 管理（替代 V0 的 ttyd+Caddy+api.py 5 进程架构）
2. 接入 Cloudflare Named Tunnel 或腾讯云 nginx
3. 验证后替换 V0

## 2026-03-21 | 性能优化 | cc-remote 去掉 Caddy，tunnel 直连 ttyd + Cloudflare Access 认证

### 决策内容

去掉 Caddy 反代层，Cloudflare tunnel ingress 直接指向 ttyd 端口。认证从 Caddy basic auth 迁移到 Cloudflare Access（边缘认证，零额外延迟）。

### 背景

- 延迟测试：ttyd 本地 7ms，经 Cloudflare+Caddy 全链路 2290ms
- Caddy 反代增加 ~200ms 往返

### 变更

| 维度 | 之前 | 之后 |
|------|------|------|
| 认证 | Caddy basic auth (Mac 端) | Cloudflare Access (边缘) |
| 链路 | CF → Caddy:19443 → ttyd | CF → ttyd 直连 |
| 代理层数 | 3 层 | 2 层 |

### 回滚方案

如果 Cloudflare Access 不可用或配置失败，恢复 Caddy：Mac 上执行 `cd ~/mycc/2-Projects/cc-remote && ./start.sh`

## 2026-03-21 | 架构选型 | cc-remote 最终方案确定：Cloudflare Named Tunnel + ttyd + tmux + Caddy

### 决策内容

经过 V2（JSON 封装）→ V3（自研 Binary 协议）→ ttyd + relay → ttyd + nginx + SSH 隧道 四轮迭代，最终回归 V0 方案：**Cloudflare Named Tunnel 直连 Mac，ttyd + tmux 提供终端，Caddy 做认证反代**。

### 迭代历程

| 方案 | 问题 | 结论 |
|------|------|------|
| V2 JSON 封装 | 中文/logo 不显示，延迟高 | ❌ xterm.js CJK 渲染问题 |
| V3 自研 Binary 协议 | reqId 三层转换导致数据无法到达浏览器 | ❌ 过度工程 |
| ttyd + 腾讯云 relay | relay 路径代理与 ttyd WS 不兼容 | ❌ 路径代理根本不适合 ttyd |
| ttyd + nginx + SSH 隧道 | 能工作但 SSH 双重加密导致延迟高 | △ 可用但慢 |
| **V0: Cloudflare + ttyd + Caddy** | DNS CNAME 指向错误（已修复） | ✅ 最终方案 |

### 最终架构

```
浏览器 → cli.hahaxiong.top → Cloudflare 边缘(QUIC) → Mac Caddy:19443(认证) → ttyd:19001-19003 → tmux session
```

### 关键修复

- Cloudflare DNS: `cli.hahaxiong.top` CNAME 从临时 URL 改为 Named Tunnel ID `d31b7bdb-...cfargotunnel.com`
- 腾讯云基础设施已就绪（nginx + relay），但当前不用于终端代理，保留为其他服务使用

### 核心教训

1. **自研 xterm.js 前端的 CJK 渲染始终无法解决**——ttyd 内置的 xterm.js 配置是经过大量测试的，自己配怎么都不对
2. **路径代理（/ttyd/）不适合需要 WS 的 SPA 应用**——WS 路径必须从根开始
3. **中转越多延迟越高**——Cloudflare 直连 > nginx+SSH 中转 > 自研 relay 中转
4. **成熟方案优于自研**——ttyd 一行命令解决的问题，自研花了 600+ 行代码仍未解决

### 复盘点

- [x] V3 自研 Binary 协议：过度工程，应该更早放弃
- [x] 腾讯云 relay：适合 HTTP API 代理，不适合终端 WS 代理
- [ ] 后续：评估是否需要在 ttyd 基础上加 session 管理 UI

## 2026-03-21 | 架构选型 | cc-remote-v3 从自研协议切换到 ttyd

### 决策内容

放弃自研 Binary Protocol（node-pty + tmux + 自定义二进制帧 + 三层 reqId 转换），改用 ttyd 作为终端 Web 化方案。Relay Server 简化为透明 Binary 代理。

### 背景

- V2（JSON 封装 WS 数据）延迟高，中文/logo 显示异常
- V3 自研 Binary Protocol 引入更多问题：三层 reqId 转换调试困难、Binary 帧在 Relay 中转时 reqId 不匹配导致终端数据无法到达浏览器、中文/Nerd Font 显示问题多次迭代仍未解决
- ttyd 是成熟项目（GitHub 7k+ stars），原生处理 xterm.js + WS + PTY + CJK + Nerd Font

### 核心变更

| 维度 | 之前（自研） | 之后（ttyd） |
|------|------------|------------|
| 终端后端 | node-pty + tmux + 自定义 WS server | ttyd（一行命令） |
| 前端 | 自写 index.html + xterm.js CDN | ttyd 内置前端 |
| 代码量 | ~600 行 | ~100 行（tunnel-client + start.sh） |
| 中文/logo | 反复调试未解决 | 开箱即用 |

### 预期效果

- 中文、Claude logo、ANSI 颜色全部正常显示
- 代码量减少 80%，维护成本大幅降低
