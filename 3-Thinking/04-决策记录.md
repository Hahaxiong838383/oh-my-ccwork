## 2026-03-11 | 协作规范 | 引入 BRO-PDCA 任务接收协议

### 决策内容

将 FUTURUS 内部方法论 BRO-PDCA 适配为 cc 与川哥的人机协作协议，写入 CLAUDE.md「任务接收协议（BRO-PDCA）」章节。

### 背景

- cc 经常在缺少 O2（约束/边界）的情况下过度发散执行，导致返工
- 典型案例：被要求"做预警"，实际做了完整的 Budget 管控系统；被要求"修 bug"，顺手重构周边代码
- BRO-PDCA 原本是人与人协作框架，但其核心问题（动手前先对齐目标）在人机协作中同样成立，且更关键

### 核心约定

| 档位 | 场景 | 触发条件 |
|------|------|---------|
| 简洁模式 | 简单任务 <30min | O1 + O2 一句话 |
| 普通模式 | 中等任务 30-60min | B1 + O1 + O2 |
| 完整模式 | 复杂任务 / 架构变更 | B → R1（cc提方案）→ 拍板 O → P1确认 |

判断标准：**做错了代价 > 30min 返工 → 先对齐。否则直接干。**

### 预期效果

- 减少"执行很努力但方向偏了"的情况
- cc 主动问 O2 而不是默默假设
- 复杂任务先出 P1 拆解，降低沟通摩擦

## 2026-03-21 | 架构选型 | cc-remote-v3 从自研协议切换到 ttyd

### 决策内容

放弃自研 Binary Protocol（node-pty + tmux + 自定义二进制帧 + 三层 reqId 转换），改用 ttyd 作为终端 Web 化方案。Relay Server 简化为透明 Binary 代理。

### 背景

- V2（JSON 封装 WS 数据）延迟高，中文/logo 显示异常
- V3 自研 Binary Protocol 引入更多问题：三层 reqId 转换调试困难、Binary 帧在 Relay 中转时 reqId 不匹配导致终端数据无法到达浏览器、中文/Nerd Font 显示问题多次迭代仍未解决
- ttyd 是成熟项目（GitHub 7k+ stars），原生处理 xterm.js + WS + PTY + CJK + Nerd Font

### 核心变更

| 维度 | 之前（自研） | 之后（ttyd） |
|------|------------|------------|
| 终端后端 | node-pty + tmux + 自定义 WS server | ttyd（一行命令） |
| 前端 | 自写 index.html + xterm.js CDN | ttyd 内置前端 |
| 代码量 | ~600 行 | ~100 行（tunnel-client + start.sh） |
| 中文/logo | 反复调试未解决 | 开箱即用 |

### 预期效果

- 中文、Claude logo、ANSI 颜色全部正常显示
- 代码量减少 80%，维护成本大幅降低

### 复盘点

- [ ] ttyd + tmux 是否满足多 session 管理需求？
- [ ] 是否需要自研 session 管理 UI？
- [ ] 延迟实际表现是否优于 V2？
