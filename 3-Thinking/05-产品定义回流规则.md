# 产品定义回流规则（Mandatory Product Definition Reflow）

> **定位**：mycc 方法论体系第 5 条，专门治理"执行进展与产品定义脱节"问题。
> **触发来源**：EvoDesk V1.3.10 实施过程中用户明确要求"执行过程中的优化和调整必须回流到产品定义"。
> **版本**：V1.0（2026-04-18）
> **权威源**：EvoDesk 产品定义附录 B.5（本文档是 B.5 在 mycc 方法论层的抽象版）

---

## 一、为什么需要这条规则

### 1.1 反模式：文档-执行脱节

常见现象：
- 产品定义说"server.ts 1142 行待拆"，实际已拆到 110 行
- 产品定义说"M16 ❌ 0%"，实际已有 MVP
- 产品定义说"常量 SSoT 单向化待落地"，实际脚本已可执行

**后果**：
- 新 session 按旧定义规划 → 做重复工作
- codex 审查按旧定义找问题 → 给错误判决
- 用户看产品定义做决策 → 基于过时信息
- "文档已升级但执行闭环未落地"（V1.3.8 → V1.3.9 的教训）

### 1.2 逆反模式：执行完但只记 L-EXEC 不回流产品定义

L-EXEC（执行进展层）记录"做了什么"，产品定义记录"现状是什么"。**两者必须对齐**。
- 只写 L-EXEC = 执行记录丰富但产品定义过时
- 只改产品定义 = 执行证据缺失，容易"表演"（V1.3.7 铁律 1 违反）

**结论**：**L-EXEC + 产品定义回流 = 工程实质的完整闭环**。

## 三、触发条件（任一命中必须回流）

| 触发 | 回流粒度 |
|------|---------|
| L1 Batch 完成 | 小版本 +1 |
| 新增模块 / 数据表 / 脚本 | 小版本 +1 |
| 核心行为变更（即使 API 契约未变） | 小版本 +1 |
| codex 评审产出新发现 + 采纳 | 小版本 +1 |
| 新增章节 / 治理规则变更 | 中版本 +1 |
| 全面重构 / 基线重写 | 大版本 +1 |

## 四、强制回流动作（缺一不可）

完成触发事件后**同一 session 内**必须：

1. **更新产品定义主文档**
   - 头部元信息（版本号 / 日期 / 核心变更段）
   - 演化历史加行
   - 对应章节（实现度 / 模块清单 / 路线图）

2. **更新主索引 / 入口文件**（L0 INDEX 等）
   - 版本元信息同步
   - 最近演化列表

3. **同步到外部渠道**（飞书 / GitHub / 内部 wiki）
   - 推送 + **写后读校验**（杜绝"push success 但远端未生效"）

4. **同步离线副本 / 镜像**
   - 运行 sync 脚本让所有本地副本对齐新版本

5. **L-EXEC 或等价执行记录层对齐**
   - CURRENT / ROADMAP-STATUS 状态更新
   - 写 event + evidence_refs 指向新 commit

6. **git commit**
   - 带新版本号 + 变更摘要

7. **校验**
   - 版本号跨文件一致
   - 脚本 0 漂移
   - 飞书 head -5 与本地对齐

---

## 五、违反处理

- **轻度**：忘记更新某一项（如 L0 INDEX 版本号漂移）→ 立即补 + 写入 RECENT_EVENTS
- **中度**：声明"已回流"但某步没做（如飞书未同步）→ 撤回声明 + 补齐
- **重度**：多次违反 / 掩盖执行差异 → 触发元认知反思 + 升级用户

## 七、cc / codex 的强制输出模板

**任何 Batch 完成的汇报必须含**：

```
✅ Batch {B13b'} 完成 → 产品定义升版 V1.X.Y → V1.X.Y+1
✅ 主文档已更新 + 飞书同步 + 写后读校验通过
✅ L0 INDEX 已更新 + 飞书同步
✅ 离线包已同步
✅ L-EXEC CURRENT / ROADMAP / EVENTS 3/3 飞书写后读校验通过
✅ git commit: {sha}
✅ validate-constants-ref.sh: 0 漂移

下一步：{下个 Batch}
```

**未含上述 7 项 = 视为重度违反"真实 > 表演"铁律**，撤回汇报。
